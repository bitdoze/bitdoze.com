## Best Hermes Agent web dashboards

Web dashboards run in a browser and suit remote management from any device. You can self-host them on a VPS, run them locally, or tunnel them through SSH. The options below start with the two official ones, the admin dashboard and the Webapp, then cover four community projects up to a full IDE-style workspace.

### Official Hermes Web Dashboard

The built-in dashboard is part of the core Hermes package (it ships with Hermes Agent v0.16+; v0.23.4 is the current release as of November 2026). Launch it with `hermes dashboard` and you get a FastAPI/Uvicorn backend with a React 19 + TypeScript + Tailwind frontend on port 9119.

What you get:

- A status page with a live overview that auto-refreshes every 5 seconds
- A Chat tab that embeds the PTY-backed TUI over WebSocket, so you get the full terminal experience in the browser
- A form-based config editor that covers the 150+ fields of `config.yaml`
- Session browsing with FTS5 search, export and prune
- Agent, gateway and error logs with level and component filters and a live tail
- Token analytics for 7, 30 or 90 days, with cost tracking and a per-model breakdown
- A cron page to schedule, pause, resume, trigger and edit jobs across every profile
- Skills and MCP pages to browse, search and toggle skills, and to add, test, enable or disable MCP servers
- Profile creation, switching and cloning, plus pages for API keys, webhooks, pairing and channels
- A System page with host metrics, an update badge, gateway start/stop/restart, and one-click `doctor`, security audit, backup and restore

Auth options are OAuth via Nous Portal, username/password, and self-hosted OIDC; a non-loopback bind refuses to start without one of them (details in the security section below). Eight built-in themes are included, and you can add your own theme or plugin without forking.

Prerequisites: install the web and PTY extras first.

```bash
pip install -e ".[web,pty]"
```

#### Themes and plugins

The dashboard ships with eight built-in themes: Hermes Teal, Hermes Teal Large, Nous Blue, Midnight, Ember, Mono, Cyberpunk and Rosé. You do not need to fork anything to go further. The [Extending the Dashboard](https://hermes-agent.nousresearch.com/docs/user-guide/features/extending-the-dashboard) page documents three drop-in layers:

- A theme is one YAML file in `~/.hermes/dashboard-themes/`. Every field is optional, so a theme can be as small as two colors. It can set palette, typography, layout (radius, density and the `standard`, `cockpit` and `tiled` variants), image assets, per-component chrome and raw CSS.
- A UI plugin is a directory with a `manifest.json` and a pre-built JavaScript bundle in `~/.hermes/plugins/<name>/dashboard/`. It can add a tab, replace a built-in page, inject widgets into a built-in page through slots, or fill shell slots. It calls the SDK on `window.__HERMES_PLUGIN_SDK__` instead of bundling React.
- A backend plugin is a Python file with a FastAPI router. Its routes mount under `/api/plugins/<name>/`.

All three load at runtime, with no repo clone and no build of the dashboard itself. The desktop app has a separate plugin SDK (`@hermes/plugin-sdk`), so a dashboard plugin does not carry over to Desktop.

### Official Webapp: the Desktop workspace in a browser

The gateway can serve the Desktop workspace to a normal browser. The docs are blunt about what it is: this is not the Web Dashboard. You get the chat-first Desktop UI with sessions, profiles, Capabilities, Messaging, Artifacts, scheduled jobs, the host file tree, Git review, previews and the terminal rail. Native-only features stay in the desktop app: global shortcuts, always-on-top overlays, OS-window inspection, external-terminal launch and the updater.

Turn it on once:

```bash
hermes config set webapp.enabled true
hermes gateway restart
hermes webapp            # builds the bundle when out of date, opens a one-use sign-in link
hermes webapp --status   # is the gateway serving it, and on which address
```

It serves at `http://127.0.0.1:9120`. The link from `hermes webapp` works once, within 60 seconds, and the browser exchanges it for a sign-in that survives reloads and gateway restarts. A fresh tab or a bare URL shows instructions instead of access, so run `hermes webapp` again for a new link. Chats run on the gateway, the same process that serves the CLI, the desktop app and messaging.

It differs from `hermes dashboard` in purpose. The dashboard on port 9119 is the admin panel (Status, Config, API Keys, Sessions, Logs, Analytics, Cron, Skills, MCP, System), and its optional Chat tab embeds the TUI through a pseudo-terminal. The Webapp on port 9120 is where you work, with the same conversations and panes as the desktop app plus a terminal rail that runs the host's interactive shell. Use the dashboard to administer and the Webapp to chat.

From another machine the Webapp sits behind the same dashboard sign-in gate. Set `webapp.host` to `0.0.0.0` or to one IP address of the machine (a LAN or Tailscale address), or keep loopback and set `webapp.public_url` behind a reverse proxy. In the desktop app, Settings, Web Access turns it on for other devices behind sign-in with your Nous account. Treat the URL like shell access and prefer an SSH tunnel, Tailscale or another VPN. Plain HTTP on another host also loses the microphone, clipboard paste and system notifications, so use HTTPS or a tunnel.

**Best for:** The Desktop workspace in a browser on a phone or another computer, with no install. It is free.

**Trade-offs:** A signed-in Webapp user can run arbitrary commands as the OS account that runs Hermes, so treat the URL like shell access. The docs do not say whether the Webapp includes the Bots pane of Bot Mode, so treat the roster as a desktop-app feature for now.

## Best Hermes Agent desktop apps

Desktop apps give tighter OS integration than browser dashboards. They have system tray icons, native notifications, keyboard shortcuts, and offline access to cached data. Some tools (Ekko Studio, Scarf) appear in both the web dashboard and desktop sections because they ship as both.

#### Bot Mode: a roster of bots

The headline change in Hermes Desktop is Bot Mode. It ships in the desktop app and is on by default (checked against v0.23.4). A Bots tab sits next to Sessions in the left sidebar, and a Routines tile docks beside the conversation while the Bots tab is active.

A Bot is a Hermes profile with its own role, model, memory, skills and avatar. Its config, memory, skills, credentials and chat history live under `~/.hermes/profiles/<name>/`. Bot Mode is a UI over that primitive rather than a second runtime. `hermes -p <bot> chat` opens the same agent from a shell, and a routine is a plain cron job named `[bot:<name>] <routine>` that shows up in `hermes cron list`. Opening a local Bot runs `hermes gateway ensure --json` for its profile, which attaches to the running gateway or starts one. Closing Desktop does not stop the gateway; `hermes gateway stop` does.

What the Bots pane adds over bare profiles:

- One permanent Bot Chat per Bot. Click the Bot and you are back in the same conversation, and `/new` inside a Bot Chat is rerouted to `/compact` so the history stays.
- A roster with avatar, latest message and unread state, plus sections (folders such as Clients or Team), Hide Bot, Duplicate and Delete Profile (permanent). Section and hidden state are stored in the Bot's profile metadata, so they follow the Bot to every desktop on that backend.
- New Agent: a Name, Title and Description, and the Bot introduces itself in its Bot Chat within seconds. The Advanced disclosure clones an existing profile or starts fresh, pins a model and provider per Bot, sets a custom `SOUL.md`, and enables skills, toolsets and MCP servers per Bot.
- Routines: recurring tasks attached to the Bot that does them, with a schedule picker and a raw schedule field. Runs land in the Bot's own chat history.
- Group chats of 2 to 6 Bots. Your message triggers up to three serial rounds of member turns, capped at 10 messages per send. Bots pull each other in with `@name` and escalate judgment calls to you with `@user`, which puts a "needs you" badge on the room.
- Bot-to-bot messages. Type `@researcher have a look at this` in any chat and the active Bot composes its own message and sends it with `message_agent`. Delivery is not a live interrupt. The receiving Bot picks the message up on its next turn, and a loop guard (`gateway.bot_loop_guard.max_hops`, default 4) stops two Bots from keeping each other busy forever.

Bot Mode works against a remote backend. Gateway-owned group chats keep running when Desktop is closed, and a group chat can span machines, with Bots on other computers joining through their own gateways. To switch Bot Mode off, use Capabilities, Plugins, Bots. No restart is needed, and profiles, sessions and cron jobs stay untouched. Do not install the old standalone plugin. [NousResearch/Hermes-Bot-Mode](https://github.com/NousResearch/Hermes-Bot-Mode) is archived (last push 2026-08-17), and current Desktop builds have Bot Mode built in.

Creating Bots, routines and group chats takes a while, so it has its own section in [our Hermes Agent setup guide](/hermes-agent-setup-guide/).

#### Connect Desktop to a remote backend

Desktop can drive a Hermes backend running on another machine: a VPS, a home server, a Mini behind Tailscale. There is no remote-only download. Install the package, then open Settings, Gateways. Connection mode offers three alternatives to the local gateway:

- Remote gateway: the URL of a `hermes serve` backend you run yourself (default port 9119), then sign in
- Hermes Cloud: sign in once and pick an agent on your account
- SSH: an SSH host

The remote backend must already be running `hermes serve`; Desktop attaches to it and does not start it. A non-loopback bind engages the dashboard auth gate described in the security section below. Use OAuth through Nous Portal for anything reachable beyond your own machine, and username/password only on a trusted LAN or VPN. On Tailscale, bind the backend to the machine's Tailscale IP and use `http://<tailscale-ip>:9119` as the Remote URL.

**Best for:** Users who want the official, maintained-by-Nous-Research desktop experience, and anyone who wants Bot Mode, since the Bots pane is part of this app.

**Trade-offs:** There are no bundles for Intel Macs or for macOS 12 or earlier; those machines use the CLI installer.

## Security considerations for remote access

Any dashboard or mobile app exposed to the network needs auth. This is non-negotiable. A Hermes dashboard without auth gives anyone full control of your agent, your API keys, and potentially your server.

<Notice type="error" title="Never expose without auth">
Since the June 2026 hardening, `hermes dashboard` bound to a non-loopback address refuses to start without an auth provider, and `--insecure` is accepted but ignored. Older builds started `hermes dashboard --host 0.0.0.0` with no auth at all, which was an open backdoor. Update anything older than v0.23.2 (that release also fixes CVE-2026-130164), and always pair public-facing dashboards with auth and HTTPS.
</Notice>

### The dashboard auth gate

The gate switches on when the bind host is anything other than `127.0.0.1`, `::1` or `localhost`. Three providers ship: username/password (for a trusted network or VPN, never the public internet), OAuth through Nous Portal (the one to use for internet-facing deployments and for a remote Hermes Desktop connection), and self-hosted OIDC. It fails closed. With the gate engaged and no provider registered, `hermes dashboard` refuses to bind. When you run it interactively with no provider, it offers to set one up on the spot. Docker and other non-interactive runs skip the prompt and exit with the fail-closed error. To see where a backend stands, check its status endpoint from the machine itself:

```bash
curl -s http://127.0.0.1:9119/api/status | jq '.auth_required, .auth_providers'
```

`auth_required: true` means the gate is engaged.

### SSH tunnels (easiest)

The simplest secure approach is to tunnel the dashboard port through SSH. The backend stays on loopback, so the gate never engages and no port is exposed:

```bash
# Tunnel WebUI (port 8787)
ssh -N -L 8787:127.0.0.1:8787 user@your-server

# Tunnel Official Dashboard (port 9119)
ssh -L 9119:localhost:9119 user@your-vps

# Tunnel the Webapp (port 9120) for the Desktop workspace in a browser
ssh -L 9120:127.0.0.1:9120 user@your-vps

# Then open http://localhost:8787 or http://localhost:9119 locally
```

### Tailscale (most secure for regular use)

Install Tailscale on your server and phone or laptop, and reach the dashboard through its Tailscale IP. No port is exposed to the public internet. The bind is non-loopback, so the auth gate still engages and a provider comes first. The Hermes docs call binding to the machine's Tailscale IP the clean option for a `hermes serve` backend that Desktop connects to. Ares has Tailscale support built in, and Hermex's setup guide recommends Tailscale Serve, which puts the dashboard behind an HTTPS name on your tailnet.

### Password protection

Set the username and password with `hermes dashboard password`. It writes `username`, an scrypt `password_hash` and (when missing) a signing `secret` under `dashboard.basic_auth` in `config.yaml`. It never stores or prints the password and never takes it as an argument. It asks on the terminal, or reads the first line of standard input with `--password-stdin`, so it works in scripts, containers and service setups.

```bash
# The password comes from a secret file, never from the command line
hermes dashboard password --username admin --password-stdin < /run/secrets/dashboard_password

# Now the non-loopback bind can start
hermes dashboard --host 0.0.0.0 --no-open
```

Changing the username or password ends every session. `/auth/password-login` is rate-limited per client IP (10 attempts a minute, then HTTP 429). Username/password is for a trusted LAN or VPN. For anything on the public internet, register the install with your Nous Portal account instead: `hermes dashboard register` writes `HERMES_DASHBOARD_OAUTH_CLIENT_ID` to `~/.hermes/.env`.

### Behind a reverse proxy

Keep the backend on loopback and let Caddy or Nginx terminate TLS:

```bash
hermes dashboard --host 127.0.0.1 --port 9119 --no-open
```

Then set `dashboard.public_url` (or `HERMES_DASHBOARD_PUBLIC_URL`) to the complete public URL, and add the proxy's exact IP to `dashboard.trusted_proxies` when the TLS terminator connects from another container or host:

```yaml
dashboard:
  public_url: "https://dashboard.example.com/hermes"
  trusted_proxies: ["172.20.0.5"]
```

Declaring a non-loopback `public_url` always engages the auth gate, even though the backend binds to loopback, so configure a provider first or Hermes fails closed at startup. `0.0.0.0/0` and `::/0` are rejected as trusted proxies, and for good reason: with a range that wide, every container on a trusted network can supply forwarding headers. Use the exact proxy IP or a bounded CIDR. The hostname in `public_url` is also accepted as the HTTP Host and WebSocket Origin value, and wildcards are not. That is the DNS-rebinding guard.

### Desktop and the Webapp against a remote backend

The same providers protect the two newer surfaces. Hermes Desktop connects to a `hermes serve` backend from Settings, Gateways: Remote gateway (the backend's URL, default port 9119), Hermes Cloud (sign in and pick an agent) or SSH. The app detects which provider the backend advertises and shows either a Sign in form or Sign in with Nous Research. The Webapp uses the dashboard sign-in: set `webapp.host` to a LAN or Tailscale address, or `webapp.public_url` behind a proxy, and the gateway requires it.

The docs spell out the blast radius. A signed-in Webapp user can run arbitrary commands as the OS account running Hermes. The credentials Desktop saves for its gateways live in `gateway-connections.json` and `gateway-connection-tokens.json` in your Hermes home, owner-only (0600), as plain text, because the Webapp's server has to read them. Prefer an SSH tunnel, Tailscale or another VPN over opening either port.

<Accordion label="Is there an official Hermes Agent mobile app?" group="faq" expanded="true">
No. There is no official mobile app from Nous Research. Every mobile app comes from the community. <Accordion label="Can I run Hermes Agent on my phone?" group="faq">
On Android, yes. Hermes Agent Android (Google Play) runs the full Hermes runtime directly on the device. You need your own API key and about 200MB of storage. On iOS, no. iOS sandboxing prevents running Hermes directly. All iOS apps connect to a remote Hermes instance via SSH or API.
</Accordion>

<Accordion label="What's the best free Hermes dashboard?" group="faq">
The official built-in dashboard (`hermes dashboard`) and Hermes WebUI by nesquena are both free and good. The official dashboard is the simplest to set up, since it ships with Hermes, and the official Webapp (`hermes webapp`) is free as well if you mainly want to chat rather than administer. Hermes WebUI is lighter on resources (no build step, no framework) and has better mobile responsiveness. If you also need a free API key, see how to set up [Hermes Agent with free models on Nous Portal](/hermes-agent-mimo-v2-pro/).
</Accordion>

<Accordion label="How do I access my Hermes dashboard remotely?" group="faq">
Four routes, roughly from easiest to most involved: (1) SSH tunnel: `ssh -L 9119:localhost:9119 user@your-vps`, then open localhost:9119; no auth gate, since the backend stays on loopback. (2) Tailscale: install on both devices and use the Tailscale IP; the gate is on, so set a password first. (3) The official Webapp: `hermes webapp` serves the Desktop workspace on port 9120, and Settings, Web Access in the desktop app turns it on for other devices behind sign-in with your Nous account. (4) Reverse proxy with HTTPS: keep the backend on `127.0.0.1`, set `dashboard.public_url`, and register OAuth with `hermes dashboard register` for anything public. The `--insecure` flag no longer does anything, so there is no way around the gate.
</Accordion>

<Accordion label="Which Hermes dashboard uses the least resources?" group="faq">
Hermes WebUI by nesquena. It uses Python's standard-library HTTP server and vanilla JavaScript, with no Node.js, no bundler, and no framework. The startup is fast and memory usage is minimal compared to the React/Vue-based alternatives.
</Accordion>

<Accordion label="Can I use multiple dashboards at the same time?" group="faq">
Yes. Dashboards are independent web applications running on different ports. You can run the official dashboard on port 9119, the Webapp on 9120, Hermes WebUI on 8787, Ekko Studio on 8648, Hermes Workspace on 3000, and HCI on 10274 simultaneously. They all read from the same Hermes data directory, so sessions, config, and profiles are shared.
</Accordion>

<Accordion label="Is the BSL-1.1 license of Ekko Studio (formerly Hermes Studio) a problem?" group="faq">
For personal use, no. For commercial use, review the license terms. Ekko Studio's BSL-1.1 (Business Source License) grants non-commercial use only; selling it, SaaS hosting or embedding it in a commercial product needs a separate commercial license. The license file names 2029-05-10 as the change date, when it converts to Apache 2.0. If you need a fully MIT-licensed dashboard for commercial use, choose the official dashboard or Hermes WebUI instead.
</Accordion>

<Accordion label="Does Bot Mode need the Hermes Desktop app?" group="faq">
For the roster UI, yes. The Bots pane, the routine editor and the group chat window live in the desktop app, where Bot Mode is on by default. The Bots themselves do not need it: a Bot is a Hermes profile, so `hermes -p <bot> chat` opens the same agent from a shell and `hermes cron list` shows its routines as jobs named `[bot:<name>]`. On a headless VPS, install Desktop on your laptop and connect it to the VPS through Settings, Gateways. Bot-to-bot messages only run in the Bot Chats that the Bots pane sets up, so that part leans on Desktop unless you mark the install by hand. Group chats owned by a gateway keep running with Desktop closed. The walkthrough is in the [Hermes Agent setup guide](/hermes-agent-setup-guide/).
</Accordion>

<Accordion label="What is the difference between the Webapp and the dashboard?" group="faq">
`hermes dashboard` on port 9119 is the admin panel: Status, Config, API Keys, Sessions, Logs, Analytics, Cron, Skills, MCP and System, with an optional Chat tab that embeds the TUI. The Webapp on port 9120 is the Desktop workspace in a browser, served by the gateway: the same chat-first UI, file tree, Git review and terminal rail as the desktop app. Turn it on with `hermes config set webapp.enabled true`, `hermes gateway restart`, then `hermes webapp`. Use the dashboard to administer and the Webapp to work.
</Accordion>
