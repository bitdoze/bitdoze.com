### Install Docker

If Docker isn't set up yet, use the official convenience script or my full walkthrough:

```sh
curl -fsSL https://get.docker.com | sh
```

Full walkthrough: [Install Docker & Docker-compose for Ubuntu](https://www.bitdoze.com/install-docker-ubuntu-arm/).

Verify before moving on:

```sh
docker version && docker compose version
```

You want a Client and Server line at 20.10 or newer, and a `docker compose` (not `docker-compose`) version. If `docker version` throws `permission denied /var/run/docker.sock`, your user isn't in the `docker` group:

```sh
sudo usermod -aG docker $USER
# log out and back in, then re-run docker version
```

## Install Dockhand with Docker Compose

You have three paths: a quick single command for kicking the tires, a SQLite-based Compose stack, or a PostgreSQL-backed one. SQLite is the right default for a single server. If you searched for `dockhand docker compose`, this is the method I recommend.

### Quick install (single command)

If you just want to see it:

```bash
docker run -d \
  --name dockhand \
  --restart unless-stopped \
  -p 3000:3000 \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v dockhand_data:/app/data \
  fnsys/dockhand:v1.0.55
```

Pin the version tag. `:latest` is fine only for a throwaway test.

Verify it came up:

```bash
docker logs dockhand
```

You want the startup banner, no crash loop. Then open `http://your-server-ip:3000` and complete the first-run wizard (create the admin account; the flow is unchanged in v1.0.55). For a permanent setup, use one of the compose methods below instead.

### Docker Compose with SQLite (recommended for most users)

Create a directory and compose file:

```bash
mkdir -p /opt/dockhand
cd /opt/dockhand
```

Create `compose.yaml`:

```yaml
services:
  dockhand:
    image: fnsys/dockhand:v1.0.55
    container_name: dockhand
    restart: unless-stopped
    ports:
      - "3000:3000"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - dockhand_data:/app/data
volumes:
  dockhand_data:
```

Pin the version tag like I did here rather than running `:latest`. Weekly releases are great until one lands while you're not watching. The security section below will tell you when that pin needs to move.

Start it:

```bash
docker compose up -d
```

Verify:

```bash
docker compose ps          # state = running, no restart loop
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000   # expect 200
```

Open `http://your-server-ip:3000`. The first-run wizard walks you through creating an admin account. SQLite is the default database and works well for single-server setups. The data lives in the `dockhand_data` volume.

Common failure modes at this step: if port 3000 is already in use, `ss -tlnp | grep 3000` shows who owns it; change the host port (`"3030:3000"`) or stop the other service. If the container name clashes with leftovers, either `docker compose -p dockhand up -d` or remove the stale container first. Volume permission issues only appear once you add `PUID`/`PGID`, so read the environment variables section before you do.

### Docker Compose with PostgreSQL

If you're managing a lot of containers or want the database running separately for backup purposes, use PostgreSQL. Requires PostgreSQL 14+.

```yaml
services:
  postgres:
    image: postgres:16-alpine
    container_name: dockhand-db
    restart: unless-stopped
    environment:
      POSTGRES_USER: dockhand
      POSTGRES_PASSWORD: change-this-password
      POSTGRES_DB: dockhand
    volumes:
      - postgres_data:/var/lib/postgresql/data

  dockhand:
    image: fnsys/dockhand:v1.0.55
    container_name: dockhand
    restart: unless-stopped
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://dockhand:change-this-password@postgres:5432/dockhand
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - dockhand_data:/app/data
    depends_on:
      - postgres

volumes:
  postgres_data:
  dockhand_data:
```

<Notice type="warning" title="Change the database password">
Replace `change-this-password` in both the `POSTGRES_PASSWORD` and `DATABASE_URL` fields with an actual strong password. Use the same password in both places.
</Notice>

<Notice type="warning" title="No automatic SQLite to PostgreSQL migration">
Switching databases starts you on a fresh database. There is no migration path from SQLite to PostgreSQL. Decide before you have data you care about, not after.
</Notice>

Verify both services:

```bash
docker compose ps
docker compose logs -f dockhand
```

Both containers should show as running/healthy, the Dockhand banner should appear in the logs, and `curl -s -o /dev/null -w "%{http_code}" http://localhost:3000` should print `200`. Postgres adds a second container to back up and monitor; factor that into your routine.

The project has published 12 security advisories so far, and three HIGH/critical batches landed after v1.0.45, the release the previous version of this article called "the" security upgrade. The maintainer patches fast. That's good. It also means an old pin quietly becomes a liability.

<Notice type="error" title="Update path for old installs">
Anything at v1.0.49 or below carries the HIGH OIDC privilege escalation. Anything at v1.0.53 or below carries the HIGH `.env` escape. Anything at v1.0.54 or below carries the HIGH file-browser traversal. Pin a version, yes, but update deliberately and often. Bumping v1.0.48 to v1.0.55 is not a routine chore, it closes three HIGH issues.
</Notice>

The operator rule I follow: pin a version tag, watch the [advisory feed](https://github.com/Finsys/dockhand/security/advisories), and budget five minutes a month for a deliberate bump. And treat Dockhand like any internet-facing panel. Keep it behind a VPN or an authenticated reverse proxy, never raw on `0.0.0.0:3000` in production. That's the same posture I applied to my own Docker hosts, covered in [how I secured my Docker server after the BSI report](/bsi-security-report-docker-ufw/), and if you want the private-network layer you can [keep Dockhand behind a VPN with a self-hosted Headscale/Tailscale server](/headscale-self-hosted-tailscale-setup/). On the box itself: [harden SSH before exposing any management UI](/secure-ssh-server-linux/), so the panel isn't your only line of defense.

<Notice type="info" title="Consider a Docker socket proxy">
The official manual recommends considering a socket proxy (for example the Tecnativa/docker-socket-proxy pattern) instead of mounting `/var/run/docker.sock` raw. The socket is root-equivalent on the host; limiting which API calls the UI can make shrinks the blast radius of any panel bug. The Hawser section below is the other way to keep the socket off the management host.
</Notice>

## Setting up vulnerability scanning

This is Dockhand's headline security feature and it's included in the free tier. You can scan your container images for known vulnerabilities using either Grype or Trivy, and the `dockhand vulnerability scanning` workflow runs entirely against local images, nothing is sent to an external scanning service.

After logging in, go to the settings page and enable vulnerability scanning. Choose your scanner:

<Tabs>
  <Tab name="Grype">
    Grype is the default option. It's fast, developed by Anchore, and pulls vulnerability data from multiple sources. Scans run against your local images without sending anything to external servers. Since v1.0.51 the bundled version is pinned at grype v0.119.0, so a Dockhand upgrade is also a scanner upgrade, on the project's schedule rather than yours.
  </Tab>

  <Tab name="Trivy">
    Trivy by Aqua Security is the other option. It supports more scan targets (OS packages, language-specific dependencies, IaC files) but is slightly slower. The pinned version since v1.0.51 is trivy 0.75.0. If you need deeper scanning beyond container images, Trivy is the better pick.
  </Tab>
</Tabs>

The safe-pull feature ties into scanning. When Dockhand auto-updates a container, it pulls the new image, scans it for vulnerabilities, and only switches over if the scan passes. If the new image has problems, your running container stays untouched. In September it caught two bad image updates in three weeks.

<Notice type="info" title="First scan is slow">
The first scan downloads the vulnerability database, so budget a few minutes and expect one heavy network pull. If your Docker daemon uses the containerd image store (the snapshotter is default on newer installs), scanning had a bug there until v1.0.49. On anything current this works; if scans come back empty on a containerd-backed daemon, upgrade Dockhand first and blame the tooling, not the images. Also confirm the scanner image pulls correctly on that first run, outbound HTTPS and DNS are required.
</Notice>

## Scheduled auto-updates

Dockhand can check for new container images on a schedule and update them automatically. Combined with safe-pull protection, this is usable in practice. And I don't say that lightly: most auto-update tools don't verify the new image works before swapping it in.

Set this up per container or per stack in the UI. You pick a schedule (e.g. daily at 3am), and Dockhand handles the rest. If an update fails or the new container doesn't start properly, it rolls back.

Since v1.0.52 there's a supply-chain guard worth turning on: `MINIMUM_RELEASE_AGE_HOURS` (0-720, also available as a per-environment and global setting in the UI) holds updates until a new image is N hours old. Don't auto-update onto an image that was pushed 20 minutes ago. Two newer additions: targeted redeploy (redeploy one service without recreating the whole stack, v1.0.52) and scheduled container start/stop (v1.0.55).

My recommended defaults:

<ListCheck>
<ul>
<li>Update window: daily at 3am, or whenever your traffic is quietest</li>
<li>Minimum image age: 24 hours (`MINIMUM_RELEASE_AGE_HOURS=24`)</li>
<li>Rollback on failure: enabled</li>
<li>Notification on failure: on, via whichever channel you already read</li>
</ul>
</ListCheck>

One ops note: pinning and auto-updates are not in conflict if you split the job. Pin the major.minor line you trust in the compose file, let safe-pull and rollback handle the patch churn, and read advisories before moving the pin yourself. That's what I do for anything with real data behind it. If you want a dedicated updater that doesn't need the whole UI, [Tugtainer for dedicated container auto-updates](/tugtainer-docker-autoupdate/) covers just that job.

## Configuring OIDC/SSO

OIDC support is free in Dockhand. No paid tier needed. If you run Authentik, Keycloak, or any other OIDC provider, you can set up single sign-on.

In the Dockhand UI, go to Settings and configure your OIDC provider with:

- Client ID
- Client secret
- Issuer URL / Discovery URL

Users are auto-provisioned on first login. v1.0.50 hardened the session handling: OIDC sessions now survive restarts and replicas, which matters the moment you run more than one instance. Two env vars control the login experience:

- `OIDC_AUTOLOGIN=true` skips the login form and sends everyone to the IdP. Keep the escape hatch in mind: `http://your-host/login?local=1` forces the local form so you never lock yourself out.
- `OIDC_END_SESSION` (default `true`) also ends the session at the IdP on logout, not just locally.

<Tabs>
  <Tab name="Hide local login">
    Keep local accounts working but hidden, the safe middle ground:

    ```yaml
    environment:
      DISABLE_LOCAL_LOGIN: "true"
    ```
  </Tab>

  <Tab name="Auto-login">
    Skip the login form entirely, with the `/login?local=1` escape hatch:

    ```yaml
    environment:
      OIDC_AUTOLOGIN: "true"
    ```
  </Tab>

  <Tab name="Full SSO-only">
    Both at once. Only do this after you've confirmed OIDC login works in another browser session:

    ```yaml
    environment:
      DISABLE_LOCAL_LOGIN: "true"
      OIDC_AUTOLOGIN: "true"
      OIDC_END_SESSION: "true"
    ```
  </Tab>
</Tabs>

<Notice type="warning" title="Set ORIGIN before enabling passkeys">
Passkey sign-in (v1.0.52) requires `ORIGIN` to be the exact public origin, including scheme and port, and HTTPS unless you're on localhost. If WebAuthn options never appear in the UI, this is almost always an `ORIGIN` mismatch. Set it even if you don't plan to use passkeys today; it costs nothing and it also makes OIDC redirects predictable behind a reverse proxy.
</Notice>

<Notice type="info" title="MFA is separate from OIDC">
If you're using local accounts instead of OIDC, Dockhand supports TOTP-based MFA. Each user can enable it from their profile settings. If you're using OIDC, MFA is handled by your identity provider instead. Note that LDAP/AD and RBAC sit on the Enterprise tier; OIDC and MFA are what's free. Worth a quick check of the pricing page for the current line if you're buying.
</Notice>

## Reverse proxy setup

Dockhand runs on port 3000 by default. For SSL and a proper domain, put a reverse proxy in front of it. WebSocket support is needed for live container logs, the web terminal, and metrics.

<Tabs>
  <Tab name="Nginx">

```nginx
server {
    listen 443 ssl http2;
    server_name dockhand.yourdomain.com;

    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

The `Upgrade` and `Connection` headers are not optional. Without them the UI loads and then live logs and the terminal hang forever.

  </Tab>

  <Tab name="Traefik">
    Add labels to the Dockhand service in your compose file:

    ```yaml
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.dockhand.rule=Host(`dockhand.yourdomain.com`)"
      - "traefik.http.routers.dockhand.entrypoints=websecure"
      - "traefik.http.routers.dockhand.tls.certresolver=letsencrypt"
      - "traefik.http.services.dockhand.loadbalancer.server.port=3000"
    ```

    Traefik forwards WebSocket upgrades by default. Full Traefik setup: [How to use Traefik as a reverse proxy in Docker](https://www.bitdoze.com/traefik-proxy-docker/).
  </Tab>

  <Tab name="Cloudflare Tunnels">
    Point a tunnel at `http://localhost:3000`. SSL and WebSocket handling are automatic. This is the easiest option if you don't want to manage certificates or open ports. If you'd rather not hand traffic to Cloudflare, a [self-hosted alternative to Cloudflare Tunnels](/pangolin-cloudflare-tunnels-alternative/) gives you the same topology under your own control.
  </Tab>

  <Tab name="Native HTTPS">
    Since v1.0.33 Dockhand can terminate TLS itself, the middle option between bare :3000 and a full proxy:

    ```yaml
    environment:
      HTTPS_MODE: "on"
      HTTPS_CERT_PATH: "/app/data/certs/cert.pem"
      HTTPS_KEY_PATH: "/app/data/certs/key.pem"
    ```

    Mount the cert paths into the container. The healthcheck probes HTTPS automatically when `HTTPS_MODE=on`. Useful on a LAN or behind a tunnel that doesn't terminate TLS, less useful if you already run Nginx or Traefik.
  </Tab>
</Tabs>

Verify the proxy path:

```bash
curl -I https://dockhand.yourdomain.com     # expect 200 or 302
```

Then open the UI, go to any container's logs, and check the browser devtools Network tab for a `101` WebSocket upgrade. In `docker logs dockhand` you'll see `GET /api/... 101` lines when a terminal or log stream is open.

Failure modes here are predictable: 502 means the proxy can't reach `127.0.0.1:3000`; a UI that loads but never streams logs means the WebSocket upgrade headers are missing; mixed-content or redirect loops usually mean `ORIGIN` or `X-Forwarded-Proto` disagree with the public URL. Production posture is reverse proxy plus auth, either proxy-level auth or OIDC against Authentik/Keycloak, which ties back to the security section.

## Managing remote hosts with Hawser

Dockhand can manage Docker on remote machines through the Hawser agent. [Hawser](https://github.com/Finsys/hawser) is open source (Go, MIT), separate from Dockhand itself, at v0.2.52 as of 2026-10-25. It has two modes. In Standard mode the agent listens on port 2376 and Dockhand connects to it. That works for LAN and homelab machines with static IPs, but a `TOKEN` is required on any non-loopback bind: a listening agent without one would expose an unauthenticated Docker API to the network. In Edge mode the agent makes an outbound WebSocket connection to Dockhand. Nothing comes inbound, so it works behind NAT, firewalls, and dynamic IPs. This is the mode most people want.

Pick Edge unless the remote host has a stable inbound path and you enjoy managing TLS and firewall rules for 2376.

Create the remote host inside Dockhand first (Environments, then add) so it generates the agent token. Then on the remote machine:

<Tabs>
  <Tab name="Docker run (Edge)">

```bash
docker run -d \
  --name hawser \
  --restart unless-stopped \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -e DOCKHAND_SERVER_URL=wss://dockhand.yourdomain.com/api/hawser/connect \
  -e TOKEN=your-agent-token \
  ghcr.io/finsys/hawser:v0.2.52
```

Pin the Hawser tag the same way you pin Dockhand. If you'd rather not put the token in the process environment, v0.2.48 added `TOKEN_FILE`, point it at a file mounted read-only into the container.

  </Tab>

  <Tab name="Systemd / OpenRC installer">

```bash
curl -fsSL https://raw.githubusercontent.com/Finsys/hawser/main/scripts/install.sh | bash
# edit /etc/hawser/config:
#   DOCKHAND_SERVER_URL=wss://dockhand.example.com/api/hawser/connect
#   TOKEN=your-agent-token
sudo systemctl enable --now hawser
```

The installer honours `HAWSER_VERSION`, `STACKS_DIR`, and `INSTALL_DIR`. On Alpine it installs an OpenRC script and logs to `/var/log/hawser.log`; on systemd boxes, `journalctl -u hawser -f` is your friend.

  </Tab>
</Tabs>

<Notice type="warning" title="v0.2.52 needs a full reinstall on systemd">
v0.2.52 fixed private-registry pulls and compose builds under systemd by moving `DOCKER_CONFIG`/`TMPDIR` onto a `/run/hawser` tmpfs. If you installed via the systemd script on v0.2.51 or earlier, re-run the installer. Swapping the binary alone leaves the old unit file in place and the registry fix doesn't apply.
</Notice>

The agent connects to your Dockhand instance and the remote host shows up in your dashboard, with auto-reconnect on network drops. Both modes expose a small health endpoint at `/_hawser/health` on port 2376; in Edge mode bind it to localhost (`BIND_ADDRESS=127.0.0.1`) so the host keeps zero reachable surface.

TLS options exist for both modes if you need them: `TLS_CERT`/`TLS_KEY` in Standard mode, `CA_CERT`/`TLS_SKIP_VERIFY` in Edge mode. There's also `MAX_MESSAGE_SIZE_MB` (v0.2.49) for large stacks, `REQUEST_TIMEOUT`, and compose `--pull`/`--no-cache` build flags (v0.2.51).

<Notice type="info" title="Same 1:1 path rule as Arcane">
If your compose stacks use relative bind mounts (`./config.conf:/app/config.conf`), Hawser's `STACKS_DIR` must be a host path mounted at the same path inside the container: `-v /opt/stacks:/opt/stacks -e STACKS_DIR=/opt/stacks`. Docker resolves bind sources on the host filesystem, so a named volume or a mismatched path breaks relative mounts.
</Notice>

Verify the agent:

```bash
# on the remote host
curl -s http://127.0.0.1:2376/_hawser/health
```

Then in Dockhand open Environments and confirm the host shows as connected. On systemd, `journalctl -u hawser -f` should show the WSS handshake; with Docker, `docker logs -f hawser`. If the health check answers but Dockhand never connects, the URL is wrong: Edge mode needs `wss://` plus the `/api/hawser/connect` path, not just the domain.

## Environment variables reference

| Variable | Default | What it does |
|---|---|---|
| `DATABASE_URL` | SQLite | PostgreSQL connection string |
| `PUID` / `PGID` | unset (container starts as root) | File ownership user/group. The entrypoint fixes permissions, then drops to this user |
| `DISABLE_LOCAL_LOGIN` | `false` | Hide password login when SSO is active |
| `SKIP_DF_COLLECTION` | `false` | Skip disk usage collection (useful on NAS devices) |
| `DATA_DIR` | `/app/data` | Custom data directory path |
| `FEAT_API_DOCS` | `false` | Serve the interactive OpenAPI docs at `/api/docs` |
| `ENCRYPTION_KEY` | auto-generated | AES-256 key for stored credentials/secrets, kept in `DATA_DIR` |
| `ORIGIN` | unset | Exact public origin (scheme + host + port). Required for passkeys |
| `MINIMUM_RELEASE_AGE_HOURS` | `0` | Hold auto-updates until a new image is N hours old (0-720) |
| `OIDC_AUTOLOGIN` | `false` | Skip the login form and go straight to the IdP |
| `OIDC_END_SESSION` | `true` | End the session at the IdP on logout |
| `REGISTRY_REQUEST_TIMEOUT` | 10s | Registry request timeout (v1.0.55) |
| `DISABLE_WHATS_NEW` | `false` | Hide the What's New panel (v1.0.37) |
| `EXPORT_METRICS_PUBLIC` | `false` | Serve `/metrics` without a bearer token (v1.0.55) |
| `HTTPS_MODE` | `off` | Native HTTPS termination: `on` / `off` |
| `HTTPS_CERT_PATH` / `HTTPS_KEY_PATH` | unset | TLS cert and key paths for native HTTPS |
| `COMPOSE_TIMEOUT` | 900s | Seconds before a compose operation counts as hung |
| `DOCKER_API_VERSION` | auto | Override the Docker API version for older daemons |
| `HOST_DATA_DIR` / `HOST_DOCKER_SOCKET` | auto-detected | Host paths mapped into the container |
| `DNS_RESULT_ORDER` | `ipv4first` | Set to `verbatim` on hosts with broken IPv4 resolution |
| `DOCKER_STOP_TIMEOUT` | compose default | Seconds to wait when stopping containers (v1.0.54) |
| `ALLOW_WEBHOOKS_WITHOUT_SECRET` | `false` | Allow git webhooks with no secret (v1.0.46) |

If you take one thing from this table, take this one:

<Notice type="error" title="Back up your ENCRYPTION_KEY separately">
Credentials and secrets at rest are encrypted with AES-256 using a key stored in `DATA_DIR`. A backup restored onto a rebuilt instance is unreadable without the same key. Keep a copy of `ENCRYPTION_KEY` alongside, not inside, your backups: a password manager entry plus one offline copy. This is the classic "backups you can't restore" trap, and it will only bite you once, at the worst possible time.
</Notice>

On `PUID`/`PGID`, the pattern that works with the Docker socket:

```yaml
services:
  dockhand:
    image: fnsys/dockhand:v1.0.55
    environment:
      PUID: "1000"
      PGID: "1000"
    group_add:
      - "999"   # the docker group GID: getent group docker
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - dockhand_data:/app/data
```

Set `PUID`/`PGID` to your user and add the `docker` group with `group_add` rather than pretending the socket is readable by everyone. If you're adding `PUID`/`PGID` to an install that ran as root until now, do a one-time `chown -R` of the stacks and data folders first.

<Notice type="warning" title="PUID behavior briefly changed in v1.0.52">
v1.0.52 changed how `PUID` is applied (it made the container run as that user instead of root), and v1.0.53 reverted it the same day because it could alter stack file ownership on upgrade (#1700, #1701). If you jump several versions at once, re-check the ownership of your stacks folder after the upgrade before you blame the app.
</Notice>

The `/metrics` endpoint is authenticated by default (API bearer token, since v1.0.25). A scrape config looks like this:

```yaml
scrape_configs:
  - job_name: dockhand
    scheme: https
    metrics_path: /metrics
    authorization:
      credentials: <api-bearer-token>
    static_configs:
      - targets: ["dockhand.yourdomain.com"]
```

`EXPORT_METRICS_PUBLIC=true` (v1.0.55) removes the token requirement. Leave that off unless the metrics endpoint sits on a private network you trust. For watching the host itself rather than the app, [Uptime Kuma for external monitoring](/install-uptime-kuma/) plus Dockhand's metrics covers both sides.

## Troubleshooting

To back out of a bad start: `docker compose down` stops and removes the containers but keeps the `dockhand_data` volume. Add `-v` only if you really want to delete the database too. For rollback of an individual app container, safe-pull and auto-update rollback already handle that (see the auto-updates section).

<Accordion label="Container logs show permission denied" group="troubleshoot" expanded="true">

Symptom: `permission denied /var/run/docker.sock` in `docker logs dockhand`, or containers don't appear in the UI.

Check the socket group:

```bash
getent group docker
```

Don't run everything as root to dodge this. Add the docker group properly in compose:

```yaml
group_add:
  - "999"   # the GID from getent group docker
```

and keep `PUID`/`PGID` pointed at your normal user. See the environment variables section for the full pattern.

</Accordion>

<Accordion label="Vulnerability scans fail or time out" group="troubleshoot">

The first scan takes longer because Grype or Trivy needs to download the vulnerability database. Subsequent scans are faster. If it keeps timing out, check that the container has internet access (DNS resolution, outbound HTTPS), and that the pinned scanner image (grype v0.119.0 / trivy 0.75.0) pulled on first use.

</Accordion>

<Accordion label="Dockhand uses too much CPU on my NAS" group="troubleshoot">

Set `SKIP_DF_COLLECTION=true` in your environment variables. Disk usage collection can be heavy on certain NAS devices with many mount points.

</Accordion>

<Accordion label="Hawser agent won't connect" group="troubleshoot">

Verify the token is correct and the `DOCKHAND_SERVER_URL` is reachable from the remote machine. Edge mode is a WebSocket, so the URL starts with `wss://` and ends in `/api/hawser/connect`, not just the plain domain. If Dockhand sits behind a reverse proxy, make sure it forwards WebSocket upgrades. In Standard mode, Hawser refuses to start without a `TOKEN` on a non-loopback bind; check the container logs for that error first. If you're on a systemd install from v0.2.51 or older and registry pulls fail, re-run the installer (v0.2.52 fix), swapping the binary is not enough.

</Accordion>

<Accordion label="Locked out, or MFA reset needed" group="troubleshoot">

Two escape hatches exist. If you enabled `OIDC_AUTOLOGIN` and the IdP is down or misconfigured, hit `http://your-host/login?local=1` to force the local login form. If local MFA is the problem, `reset-mfa.sh` ships inside the container (since v1.0.36):

```bash
docker exec -it dockhand reset-mfa.sh
```

Run it, reset the affected user, then re-enable TOTP from the profile page. If you also set `DISABLE_LOCAL_LOGIN=true` and lost IdP access, you're editing compose files, so make sure you still have SSH.

</Accordion>

<Accordion label="Old Docker daemon, handshake errors" group="troubleshoot">

Symptom: API calls fail with protocol version errors against an older engine. Set `DOCKER_API_VERSION` to match what your daemon speaks:

```yaml
environment:
  DOCKER_API_VERSION: "1.41"
```

Check what you have with `docker version` (the Server line shows the API version). Better long-term path: upgrade the engine, 20.10 is the floor anyway.

</Accordion>

<Accordion label="Broken IPv4 or slow DNS resolution" group="troubleshoot">

Symptom: slow logins, flaky registry pulls, odd timeouts on hosts where IPv4 resolution is half-broken. Set:

```yaml
environment:
  DNS_RESULT_ORDER: "verbatim"
```

The default is `ipv4first`, which is right for most boxes and wrong for the odd one. Pair with `COMPOSE_TIMEOUT` if compose operations are getting killed early on slow links.

</Accordion>

## Pricing and licensing

Worth being clear about this. Dockhand has a tiered pricing model, unchanged as of 2026-10-26:

| Tier | Cost | What you get |
|---|---|---|
| Free | $0 | Full features for permitted use, OIDC/SSO included |
| SMB | $499/host/year | Production use rights for business, commercial support, priority updates |
| Enterprise | $1,499/host/year | RBAC, LDAP/AD, environment-scoped permissions, audit logging, dedicated support |

The free tier is legitimately full-featured. OIDC, MFA, vulnerability scanning, auto-updates, restic backups, the secrets-manager integrations, multi-host, all included. The site's own line is "We're not on sso.tax. SSO is free," and that's accurate. Compared with what Portainer offers at the free level, this is the better deal. If you're deciding what to run at work, [the best self-hosted Docker apps for business](/docker-containers-business/) is the wider list this would slot into.

What the free tier does not do is waive the license for business production. Remember the split from the top of the guide:

<Notice type="warning" title="Business production use is paid">
Dev/test/staging/CI/eval inside a company: free. Production use by or for any business or public body: SMB ($499/host/year) or Enterprise. Homelab, personal, non-profits, schools: free in production too. And never offer Dockhand or a fork as a hosted or managed service, the license forbids it without a written agreement.
</Notice>

So the honest cost number: if you run this in production at work, $499 per host per year is the real figure; factor it in before you deploy on a fleet. In a homelab, it's $0 and stays $0. RBAC, LDAP/AD, and audit logging are what the extra $1,000/host/year buys at Enterprise, which is priced for people who need to answer auditors.

## My take, eleven months later

Dockhand is a v1 product that doesn't feel like one. The UI is polished, the security features work, and the update pace has held: 42 releases from v1.0.14 to v1.0.55, 6,886 stars, 305 forks, 46 contributors, 735 commits as of 2026-10-26. An ecosystem started forming around it as of September: a community MCP server, a Home Assistant integration, and an iOS client were floating around. Check current state before betting on any of them.

The safe-pull feature is still my favorite thing about it. I set auto-updates on my non-critical containers in September and let it run. It caught two bad image updates by scanning them before deploying. Both times my running containers were left untouched and the new images got flagged.

What gave me pause in February was the project's age: 74 commits and 7 contributors at the time. Those numbers are no longer the concern. The honest counterweight now is the security-advisory track record: the maintainer patches fast, and also ships regressions, the v1.0.52/53 `PUID` flip-flop being the cleanest example. That combination is exactly why the pin-and-update loop matters more than the pin alone. Keep the instance behind a proxy or VPN, watch the advisory feed, update deliberately.

The other caveat that remains is the license. BSL 1.1 is fine for self-hosting, but it isn't OSI open source, and a company running it in production owes the $499/host/year SMB fee. RBAC and LDAP/AD sit behind Enterprise pricing.

If security features are your priority, Dockhand is worth installing. If you want something more battle-tested or fully open source, check out [how to install Arcane](/arcane-docker-install/) instead. For the rest of the field, my [Portainer alternatives comparison](/portainer-alternatives/) covers Sencho, Dockge, Komodo, and more.
