## What is Coolify? The open-source self-hosted PaaS

Coolify is an open-source, self-hostable platform-as-a-service. Think Heroku or Vercel, but running on your own VPS. You get:

- Git-push deployments from GitHub, GitLab, Gitea, or [Forgejo](/forgejo-woodpecker-ci-cicd/)
- 354+ one-click service templates (apps, databases, and tools)
- Automatic SSL certificates via Let's Encrypt
- Reverse proxy management (Traefik by default; Caddy optional; Custom/None mode available)
- Scheduled database and volume backups with S3-compatible storage targets
- Real-time deployment logs
- Team management with role-based access control
- Preview deployments for pull requests

The difference from Heroku is ownership. You own the server, the data, and the config. No vendor lock-in, no surprise pricing changes. If you're evaluating the broader self-hosted control panel space, check out our [self-hosted server panels compared](/best-self-hosted-panels/) guide for context on where Coolify sits.

## What changed in v4 stable and v4.1

v4.0.0 left beta on April 27, 2026 after two years and 474 beta releases. The stable release brought:

- **SPA navigation**: Replaced Livewire full-page reloads with a proper single-page app. Navigation is faster and state persists between page changes.
- **Security hardening**: Webhook secrets are encrypted with HMAC verification. Volume paths and health check commands are validated against injection. Team scoping was tightened across resource creation flows.
- **Proxy reliability**: Database-backed proxy config storage with automatic recovery and versioned backups. Proxy configs no longer silently break after crashes.
- **GitLab integration**: Full GitLab source support with SSH deploy keys and HTTP basic auth.
- **Service templates updated**: Beszel 0.18.7, Cap captcha service added, Plane re-enabled, Cal.com removed (went closed-source).

v4.1.0 followed on May 18, 2026 with more substantial additions:

- **Railpack build pack**: A new beta build pack alongside Nixpacks and Docker. Railpack supports build-time environment variables, config merging, and multi-stage builds. See our [Nixpacks vs Railpack comparison](/nixpacks-vs-railpack/).
- **Structured audit logging**: API mutations, webhook events, authentication, and authorization outcomes logged in a structured format.
- **MCP server**: Instance-level MCP support launched with read-only tools (it has since grown to read/write, more on that below).
- **Collapsible sidebar**: UI improvement with persisted state and a compact team menu.
- **Configurable stop grace periods**: Per-application grace periods for manual stops, previews, and deployments.
- **Skip CI/CD markers**: `[skip ci]` and `[skip cd]` in commit messages or PR titles skip deployment webhooks.
- **Deployment config diff tracking**: Pending changes and build-impacting modifications surfaced before redeploying.

<Notice type="warning" title="Breaking changes if you're upgrading from v4.1.x">
Five things to handle before upgrading from a May-era v4.1.x install:
1. **Member role is now read-only**. Promote any members who need write access before upgrading (v4.2.0).
2. **State-changing API endpoints require POST**. `/deploy`, `/enable`, `/disable`, start/stop/restart all return 405 on GET since v4.2.0. Update webhooks and API clients.
3. **Compose router names changed** for services with dots or hyphens (v4.3.0).
4. **API/MCP tokens need the `delete` ability** to delete anything since v4.6.0. `write`-only tokens can no longer delete.
5. **Queued webhook deployments auto-cancel** when a newer push arrives (v4.7.0). Opt out via `is_auto_cancel_queued_deployments_enabled` if your CI depends on every push building.
</Notice>

One ops note: Sentinel traffic analytics is **off by default**. Enabling it restarts the proxy and Sentinel process, which costs CPU and RAM on small boxes. Fine on a 4 GB VPS, noticeable on 2 GB.

## Coolify multi-server deployments (now in v4)

This is the single biggest change since the original review. The article used to say "multi-server is missing." That's no longer true. Coolify v4 ships multi-server deployments today.

How it works: the same application deploys to a primary server plus additional standalone servers. The primary (or a dedicated build server) builds the image, pushes it to a Docker registry, and the additional servers pull it. This is registry-based replication, not a full orchestrator. That's what v5 promises at the core level.

Requirements for multi-server deployments:

<ListCheck>
<ul>
<li>Same CPU architecture across all servers (x86_64 or ARM64, no mixing)</li>
<li>Same proxy type across all servers (Traefik on all, or Caddy on all)</li>
<li>Docker registry credentials configured on each server</li>
<li>A <code>/health</code> endpoint defined on your application for load balancer checks</li>
<li>Private networking between servers recommended (see <a href="/tailscale-setup-guide/">Tailscale private networking</a> for a simple mesh)</li>
</ul>
</ListCheck>

**Verify your multi-server setup:** deploy to multi-server, then confirm the app answers on **every** server (direct port or per-server proxy) before attaching a load balancer. Check registry auth on each host. If a server can't pull, the deployment silently targets only the primary.

When adding servers via the UI or CLI, Coolify v4.2.0+ offers Hetzner firewall rules, internal network attachment, and backup configuration during server creation, useful if you're running your fleet on [Hetzner](https://go.bitdoze.com/hetzner).

### Multi-server limits: Compose apps, persistent storage, and load balancing

The honest limits:

- **Not available for Docker Compose apps.** If your app runs via `docker-compose.yml`, multi-server deployment is not an option. Plan single-server for Compose workloads.
- **Not for apps with persistent storage.** Applications that write to local volumes can't replicate cleanly across servers.
- **Coolify does not distribute traffic.** You need to put a cloud load balancer (or external traffic layer) in front. Coolify's docs cover the pattern: define a health endpoint, terminate TLS at the LB, and use private networking between LB and servers.

Failure mode to know: multi-server will be unavailable (or rejected) for Compose and persistent-storage apps. Don't plan your architecture around replicating those. Keep them single-server.

<Tab name="Upgrade from older v4">

If you're running an older v4 line (v4.1.x or earlier), upgrade through the UI:

1. Go to **Settings -> Updates**. The Stable channel is the default.
2. Click Update. Coolify runs an automatic instance-database backup before the update starts (once a backup target is configured).
3. If the database backup fails, **the update will not start**. Check Settings -> Backup for errors first.

Keep your `APP_KEY` saved separately. You need it for restores.

For people who can't jump minor versions right now (e.g., breaking changes in the way), there's a security-only patch line:

```bash
curl -fsSL https://cdn.coollabs.io/coolify/patch.sh | sudo bash
```

This maps your running version to the latest security fix: v4.0.x to v4.0.1, v4.1.x to v4.1.3, v4.2.x to v4.2.1, v4.3.x to v4.3.24, v4.4.x to v4.4.7 (October 2026 security wave).

## Deploying applications with Coolify

### From Git

1. Add your GitHub or GitLab account in Settings -> Git Sources
2. Create a new resource, select Application, choose your repo and branch
3. Coolify detects the framework (Astro, Next.js, Django, etc.) and selects the build pack
4. Set your domain, add environment variables, hit Deploy
5. Coolify builds, deploys, and provisions SSL automatically

Push a new commit and Coolify re-deploys. Enable auto-deployment on push in the resource settings. Use `[skip ci]` or `[skip cd]` in commit messages to skip deployment webhooks when you don't want a rebuild.

**Verify:** push a commit, watch the real-time build logs, then `curl -I https://your-domain` shows a 200 with a valid TLS certificate.

Preview deployments for pull requests work but were historically flaky (v4.1.2 fixed fork-PR safety and submodule auth issues). Test before relying on them for production review workflows.

### From Docker Compose

Coolify supports Docker Compose as a build pack. Paste or upload your `docker-compose.yml`, configure environment variables, and deploy the full stack. This is useful for complex multi-service apps.

Note: Compose apps are excluded from multi-server deployments. Keep them on a single server.

See the [Coolify Docker Compose docs](https://coolify.io/docs/knowledge-base/docker/compose) for details on magic environment variables and volume management.

### One-click services (354+)

The 354 service templates include databases (PostgreSQL, MySQL, MongoDB, Redis, ClickHouse, SQLite), monitoring (Uptime Kuma, Beszel), analytics (Plausible, Umami), automation (n8n), wikis (Outline), and many more. One click, configure a few settings, and the service is running.

Some services we've covered in detail:
- [Uptime Kuma deployment](/deploy-uptime-kuma/)
- [Plausible Analytics installation](/install-plausible-analytics/)
- [Dockge install](/dockge-install/)

Smart scan (v4.5.0) helps when templates lag behind upstream: it auto-detects the build pack and environment variables from your repo or compose file.

## What Coolify does well

After running it for months:

**Deployments are reliable.** Git-push deployments work consistently. Build logs are real-time and searchable. Failed deployments show clear error messages. Preview deployments for PRs are useful for teams.

**SSL management is automatic.** Let's Encrypt certificates are provisioned and renewed without intervention. Traefik (the default proxy) handles the routing layer cleanly.

**One-click services save time.** Deploying a PostgreSQL database with backups configured takes three clicks. Setting up monitoring with [Beszel](/beszel-uptime-kuma/) or Uptime Kuma is equally fast.

**The community is active.** In my experience, issues get fixed within days. The Discord server has 20k+ members. Service templates are updated regularly.

**Cost savings are real.** Running multiple apps and databases on a single VPS in the $5-8/month range costs less than a single Heroku dyno. The exact capacity depends on your workload, but the order-of-magnitude math is clear.

## What's still rough

**Multi-server has real limits.** It exists in v4 now (see above), but it's registry-based replication: no Compose apps, no persistent-storage apps, and no built-in load balancing. If you need full orchestration, that's the v5 promise.

**No built-in CDN.** Coolify serves apps from your VPS. For static assets and global audiences, you need a CDN in front. [Bunny.net](https://go.bitdoze.com/bunny) works well for this. See [my Bunny.net review](/bunny-net-review/) for the details.

**Mobile clients don't exist.** Management is through the web UI only. There's no mobile app for quick checks.

**Service templates can lag upstream.** Community-maintained templates occasionally trail behind upstream releases. Smart scan (v4.5.0) helps detect what's actually needed, but check versions before deploying.

**Proxy edge cases remain.** Switching proxy types (Traefik to Caddy or vice versa) interrupts every public route on that server until configs regenerate. Plan proxy changes during maintenance windows.

**Docker can bypass your firewall.** Published Docker ports ignore UFW rules by default. This surprises people who think they've locked down a server. See [Docker bypasses your firewall](/docker-bypasses-firewall/) for the fix.

## Operating Coolify safely: updates, backups, and security

### Updates

Updates go through Settings -> Updates (Stable channel by default). Once an instance backup target is configured, Coolify runs an automatic database backup before each update. If the backup fails, the update won't start. Check Settings -> Backup first.

Keep your `APP_KEY` saved separately. You need it if you ever restore from a backup.

If you run `upgrade.sh` manually, you're responsible for your own backup first.

### Backups

Coolify supports scheduled backups for:

- **Databases** (PostgreSQL, MySQL, MongoDB, Redis, ClickHouse, SQLite)
- **Persistent volumes and application storage** (with retention controls)
- **The Coolify instance database itself** (auto-backed-up before updates)

Backups can be stored locally or pushed to S3-compatible storage ([Bunny Storage](/bunny-storage-vs-s3-vs-backblaze/), AWS S3, Backblaze). You get manual runs, backup history, and failure notifications (including Telegram topic routing). This replaces the old "manual volume snapshots only" situation. It's a real backup system now.

For full-server backups beyond what Coolify covers, consider [Zerobyte Restic GUI](/zerobyte-restic-gui/).

### Security

October-November 2026 saw active CVE waves (PHP2Shell CVE-2026-109618/19 among them). Coolify pushed security releases across all maintained v4 lines. The patch.sh script (shown in the install section above) maps your version to the latest fix.

Server patching (beta, v4.5.0) can auto-apply security updates per server with reboot warnings for risky packages. Worth enabling on non-critical servers.

v4.7.6 hardened the image: PHP-FPM bound to loopback, 403 responses on dotfiles/backup/config/SQL/shell files, and proper `X-Frame-Options`/`X-Content-Type-Options`/`Referrer-Policy` headers.

For the server itself, don't skip the basics: [hardening your SSH server](/secure-ssh-server-linux/) and [securing a Docker server](/bsi-security-report-docker-ufw/) cover the groundwork.

**Verify after upgrading:** confirm no failed instance-DB backup in Settings -> Backup, and check that Settings -> Updates shows 4.7.x.

## FAQ

<Accordion label="Can I run Coolify alongside other reverse proxies?" group="coolify-faq" expanded="true">
Traefik is the default proxy in Coolify. You can select Caddy instead (currently less documented), or select Custom (None) mode where Coolify manages no routes or TLS and you own the traffic path entirely. Custom (None) is the supported way to coexist with your own nginx or Traefik instance.

If you use the managed proxy modes (Traefik or Caddy), they'll conflict with another proxy on ports 80/443. Either let Coolify manage the proxy layer (recommended), use Custom (None) mode, or run Coolify on a dedicated VPS.

Warning: switching proxy types (Traefik to Caddy or vice versa) interrupts every public route on that server until configs regenerate.
</Accordion>

<Accordion label="Does Coolify support ARM servers?" group="coolify-faq">
Yes. Coolify runs on ARM (including Hetzner's ARM64 instances and Oracle Free Tier ARM VMs). Some service templates may have ARM compatibility issues, but core functionality works. For performance comparisons, see our [ARM vs x86 VPS benchmarks](/arm-vs-x86-vps-server-benchmarks/).
</Accordion>

<Accordion label="How do backups work?" group="coolify-faq">
Coolify supports scheduled database, volume, and application-storage backups with retention controls, manual runs, history, and failure notifications. Backups can be stored locally or pushed to S3-compatible storage ([Bunny Storage](/bunny-storage-vs-s3-vs-backblaze/), AWS S3, Backblaze). The instance database is auto-backed-up before each update. For full-server backups beyond Coolify's scope, consider [Zerobyte Restic GUI](/zerobyte-restic-gui/).
</Accordion>

<Accordion label="Is Coolify production-ready?" group="coolify-faq">
v4.7.x is production-ready for single-server setups. Thousands of companies ran the beta in production for 1-2 years. It has bugs (the creator acknowledges this), but they get fixed fast. For critical production workloads, set up monitoring with [Beszel](/beszel-uptime-kuma/) and keep backups current. Multi-server is usable within its documented limits.
</Accordion>

<Accordion label="What about Coolify Cloud?" group="coolify-faq">
Coolify Cloud is a managed version where they run the Coolify instance for you. Your apps still deploy to your connected VPS. Cloud is a management plane only. Pricing is $5/month base (including 2 connected servers) plus $3/month per additional server. Annual billing saves 20%. The dashboard runs at `app.coolify.io` or a custom domain. Useful if you don't want to maintain the Coolify instance itself.
</Accordion>

<Accordion label="Is v5 worth waiting for?" group="coolify-faq">
No. v5 is unreleased as of November 2026 (development is in scaffolding on `v5.x-*` branches). v4.7.x already has multi-server deployments, and v4 continues receiving security backports. Adopt Coolify now and migrate to v5 when it ships and stabilizes. Waiting means running an older stack or a competitor in the meantime.
</Accordion>
