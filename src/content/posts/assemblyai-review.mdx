## What is AssemblyAI?

A hosted speech-to-text API from a company founded in 2017 by Dylan Fox. You send audio over HTTPS or a WebSocket and get back text, word timings, speaker labels, and optional extras such as summaries, sentiment scores, and PII redaction. The models run in AssemblyAI's cloud, in a US or an EU region. You cannot download them.

Four endpoints cover almost every use case, and each has its own price:

![Diagram of the four AssemblyAI endpoints: recorded files go to the pre-recorded API at $0.21 an hour, live meetings go to the Realtime model at $0.30, voice agents go to the Realtime-Agent model at $0.45, and voice typing goes to the Dictation API at $0.62 with cleanup included](../../assets/images/26/11/assemblyai-endpoints.svg)

The diagram is the pricing model in one picture. A recorded file is the cheapest input because nobody is waiting on it. AssemblyAI bills a live stream by how long the WebSocket stays open, not by how much audio you send, and charges more per hour than for a file. The Dictation API costs close to three times the file rate, and that rate already includes an LLM pass that removes fillers and resolves self-corrections.

The three speech endpoints run models from the AssemblyAI-STT-3.7 family, released on November 17, 2026. The Dictation API runs the previous streaming model, Universal-3.6 Pro, and adds the cleanup step:

## How accurate is AssemblyAI? I sent it six files

It made 1 error in 593 words, and none of the errors were DevOps terms. I built six short recordings. Two use a synthetic voice reading an incident update full of DevOps jargon, with filler words and one self-correction. One is clean and one has pink noise 10 dB below the speech. The other four are a two-voice synthetic dialogue, five clips from five real LibriSpeech speakers, one Spanish clip, and the 1961 JFK recording from the OpenAI Whisper repository. Each file ran twice through `assemblyai-stt-3-7` with default settings. The files, the scoring rules, and Fish Audio's numbers for the same set are in my [OpenAI Whisper alternatives test](/openai-whisper-alternatives/).

| File | Length | Words | Errors |
|---|---|---|---|
| DevOps dictation, clean | 56 s | 140 | 0 |
| DevOps dictation, noisy | 56 s | 140 | 0 |
| Two-voice dialogue | 32 s | 85 | 0 |
| Five real speakers | 52 s | 146 | 0 |
| Spanish clip | 19 s | 60 | 1 |
| JFK clip | 11 s | 22 | 0 |
| Total | 226 s | 593 | 1 |

The single miss was one letter, `correo` instead of `correos`, on the Spanish clip. The pink noise changed nothing: the noisy dictation file came back with the same 0 errors as the clean one. On the second run, only punctuation moved.

The jargon matters more to me than the total. Fish Audio made 13 errors on the same 593 words, and 12 of them were tool names written the way they sound. AssemblyAI wrote them as they are spelled:

| What was spoken | AssemblyAI wrote | Fish Audio wrote |
|---|---|---|
| "kube control" | `kubectl` | `Kube control` |
| "engine X" | `NGINX` | `engine X` |
| `/var/log/syslog` | `/var/log/syslog` | `var log sys log` |
| "PagerDuty paged" | `paged` | `page` |

If you transcribe engineering standups, support calls, or dictated commands, that table is the difference between a transcript you can grep and one you have to correct first.

### How fast is AssemblyAI?

4.7 to 7.7 seconds for clips of 11 to 56 seconds through the batch API, and 0.9 to 1.6 seconds through the Dictation API.

Wall-clock time from the start of the upload to the final text:

| File | AssemblyAI batch | Fish Audio |
|---|---|---|
| DevOps dictation (56 s) | 7.7 s | 1.2 s |
| Dialogue (32 s) | 6.3 s | 1.1 s |
| Five real speakers (52 s) | 7.5 s | 1.1 s |
| Spanish (19 s) | 6.1 s | 0.6 s |
| JFK (11 s) | 4.7 s | 0.4 s |

The gap comes from the request design, not from the model. AssemblyAI's batch endpoint is a job queue: the upload took about 1.6 seconds, then submitting and polling took about 5 more. An 11-second clip still waited 4.7 seconds. Fish Audio answers in one synchronous request.

That is fine for a cron job that transcribes yesterday's calls and a poor fit for a push-to-talk hotkey. When a person is waiting, use the Dictation API, the Sync API for raw text, or a streaming model. The Dictation API answered in 0.9 to 1.6 seconds on my 56-second clip. I ran it again on a 50-second clip with two fillers and a spoken self-correction: three calls took 0.8, 0.9, and 2.8 seconds. Both fillers were gone, and the "No wait, that is not right" sentence stayed. For long files the queue overhead disappears into the processing time. [Artificial Analysis](https://artificialanalysis.ai/speech-to-text/non-streaming) measured the file model at about 109 times real time, so a one-hour recording needs roughly 33 seconds of compute once its job starts.

## How good is AssemblyAI speaker diarization?

Good enough to trust on my tests. It labelled 5 of 5 real speakers on one file and 10 of 10 segments on another, where Fish Audio and Deepgram each merged two voices. Diarization is also where AssemblyAI beat Fish Audio by the widest margin. The two-voice dialogue came back as six utterances, each with a speaker letter and millisecond start and end times. On the five LibriSpeech readers, AssemblyAI returned five labels, A through E, one per voice. Fish Audio returned four labels for the same audio and merged two different readers.

Turning it on takes one field:

```json
{
  "audio_url": "https://example.com/meeting.wav",
  "speech_models": ["assemblyai-stt-3-7"],
  "speaker_labels": true
}
```

Two optional settings change the result. `speakers_expected` sets an exact count, and the docs describe it as a hard boundary: pass the wrong number and the model splits or merges speakers to fit. `speaker_options` takes a range instead, which is what the docs recommend when you are unsure:

```json
{
  "audio_url": "https://example.com/meeting.wav",
  "speech_models": ["assemblyai-stt-3-7"],
  "speaker_labels": true,
  "speaker_options": {
    "min_speakers_expected": 2,
    "max_speakers_expected": 5
  }
}
```

The speaker count is optional. On a second five-voice file, ten sentences shuffled so that each speaker returns after two others, I tried five settings. The default, a range of 2 to 6, and an exact 5 all produced the same five correct labels. So did a range of 8 to 10, set far too high. An exact count of 3, which was wrong, merged three voices into one label, which is what the docs warn about. Leave headroom above the count you expect, but not a lot. The docs also ask for at least 30 seconds of continuous speech per speaker for the best results. My 32-second dialogue never reached that and still came out right, so treat 30 seconds as a guideline rather than a requirement to call the API.

On streams, diarization costs +$0.12 per hour, six times the price of the same feature on files.

## Does AssemblyAI support streaming and voice agents?

Yes, through two streaming models: `assemblyai-stt-3-7-realtime` at $0.30 per session hour and `assemblyai-stt-3-7-realtime-agent` at $0.45. I did not run a streaming session, so the rest of this section summarizes what AssemblyAI publishes. The Realtime model is for live meetings, captions, and notetakers. Speaker labels are final the moment a turn ends, partial transcripts arrive about once a second, and all 32 languages work in one stream with automatic detection. The Realtime-Agent model is for voice agents. It decides when the caller has finished speaking and, in AssemblyAI's benchmark, returns the final transcript 86 ms after speech ends, against 172 ms for the model it replaced.

Both stream from `wss://streaming.assemblyai.com/v3/ws`. AssemblyAI switched the old v2 endpoint off, so older tutorials fail at connect time. A complete voice agent is Realtime-Agent for listening, the LLM Gateway for the reply, and the TTS API for speaking it. The separate Voice Agent API retires on February 1, 2027.

Paid accounts start at 200 new streams per minute, and the limit climbs 10 percent each minute you use 80 percent or more of it. Free accounts stay at 5.

## What replaced LeMUR, and how do summaries work?

The LLM Gateway and the Speech Understanding add-ons replaced LeMUR, an audio summarization model that AssemblyAI deprecated on March 31, 2026. Summaries now run through two routes:

- Speech Understanding add-ons on a finished transcript: summarization, action items, chapters, sentiment, entity detection, topic detection, and auto highlights. AssemblyAI prices them per audio hour, as in the table above.
- The LLM Gateway, an OpenAI-compatible chat endpoint that fronts 65 models from OpenAI, Anthropic, Google and other vendors and bills per token. Use it when you want your own prompt over the transcript.

I ran the summarization add-on on a 9-minute public-domain video. The request goes inside the transcript job as `"speech_understanding": {"request": {"summarization": {"summary_type": "paragraph"}}}`, and the result is a list of sections with a start time, a headline, and a paragraph. Three runs returned 4, 5, and 5 sections: the boundaries stayed close and the wording of the headlines changed each time, so read them before publishing. I did not run action items or the LLM Gateway. Two entries in AssemblyAI's own docs are worth reading before you depend on them. The model reference lists `auto_chapters` and `summarization` on the older Universal-3.5 Pro model as a known trap: the job hangs and ends in a generic 500. And a changelog entry from October 23, 2026 says summarization had been failing on 2 to 4 percent of requests and on most long files before a fix.

## Where does AssemblyAI fall short?

Speed on short clips, three calls per file, model churn, and a 32-language limit on the best model.

The batch queue. Every file spends 5 to 8 seconds in overhead before any text appears. For a job that transcribes thousands of clips overnight, the queue is the right design. For anything a person is watching, it is the wrong endpoint.

Three calls per file. Upload, submit, poll. [Deepgram](/assemblyai-vs-deepgram/) and Fish Audio each return a transcript from one HTTP request, which is less code to write and less code that can fail halfway. A webhook removes the polling, but the webhook payload carries only the transcript ID and a status, so your handler still makes a second request to fetch the text.

Model churn. AssemblyAI deprecated Universal-3.5 Pro on the day STT-3.7 launched and lists Universal-3 Pro as deprecated as well. Pin the model ID in your requests and read the deprecation page before you upgrade a dependency. Parameter names move too: `word_boost` sent alongside STT-3.7 silently routes the whole job to Universal-2.

A smaller language list on the best model. STT-3.7 handles 32 languages. The rest go to Universal-2 at $0.15 an hour, and AssemblyAI's own accuracy tiers rate that model as fair or moderate on dozens of them.

Files stay in the cloud. The self-hosted option covers streaming only and needs an upfront commitment of $50,000.

## Is AssemblyAI HIPAA compliant, and where does your audio go?

Yes, with a BAA you sign from the dashboard, and once you opt out of training AssemblyAI deletes uploaded audio within 24 to 48 hours.

Sign up, and AssemblyAI can use your audio for model training until you opt out of the model improvement program in the dashboard. After the opt-out, AssemblyAI keeps no audio or transcripts for streaming, Sync, and Dictation. For files, it deletes uploaded audio within 24 to 48 hours by default. It keeps the finished transcript for 30 days unless you delete it or set a shorter time-to-live. A `DELETE` request to the transcript URL removes it on demand.

A HIPAA BAA is self-service, with no sales call and no price premium, and SOC 2 Type 2 and ISO 27001 are included as well. The EU endpoints (`api.eu.assemblyai.com`) cost the same as the US ones. Both options are available on pay-as-you-go, which matters if your audio is health data that has to stay in Europe.

## How to start with AssemblyAI

1. Create an account at [AssemblyAI](https://go.bitdoze.com/assemblyai) and copy the API key from the dashboard. You need no card for the $50 credit.
2. Export the key and run the script below against a local file.

The pre-recorded API is a four-step job:

![Diagram of the AssemblyAI batch request flow in four steps: upload the file to get a URL, submit a transcript job with the model and speaker labels, wait for a completed status by polling or webhook, then read the text, per-speaker utterances, word timings, and SRT, with notes on auth, polling limits, webhooks, and deletion](../../assets/images/26/11/assemblyai-batch-flow.svg)

```bash
export ASSEMBLYAI_API_KEY=your_key

# 1. Upload the file and get a temporary URL
upload_url=$(curl -s -X POST https://api.assemblyai.com/v2/upload \
  -H "authorization: $ASSEMBLYAI_API_KEY" \
  --data-binary @meeting.wav | jq -r '.upload_url // empty')
[ -z "$upload_url" ] && { echo "upload failed"; exit 1; }

# 2. Start the job
id=$(curl -s -X POST https://api.assemblyai.com/v2/transcript \
  -H "authorization: $ASSEMBLYAI_API_KEY" \
  -H "content-type: application/json" \
  -d "{\"audio_url\": \"$upload_url\",
       \"speech_models\": [\"assemblyai-stt-3-7\"],
       \"speaker_labels\": true}" \
  | jq -r '.id // empty')
[ -z "$id" ] && { echo "submit failed"; exit 1; }

# 3. Poll until it finishes
while :; do
  result=$(curl -s https://api.assemblyai.com/v2/transcript/$id \
    -H "authorization: $ASSEMBLYAI_API_KEY")
  status=$(echo "$result" | jq -r .status)
  [ "$status" = "completed" ] && break
  [ "$status" = "error" ] && { echo "$result" | jq -r .error; break; }
  sleep 1
done

# 4. Print one line per speaker turn
echo "$result" | jq -r '.utterances[] | "Speaker \(.speaker): \(.text)"'
```

Two details trip up first attempts. The `authorization` header takes the raw key with no `Bearer` prefix. The upload needs `--data-binary @file`, because plain `-d` sends the filename as text and the job fails with a transcoding error. Polling is limited to 60 requests per minute per transcript, and a 429 response carries a `Retry-After` header. Batch transcripts keep fillers by default. `disfluencies: false` is the documented switch for removing them. In three runs on my dictation clip it removed the filler once and kept it twice, so filter them in your own code if they matter.

The official SDKs do all four steps in one call. The current Python SDK exposes the pre-recorded API under `assemblyai.prerecorded.v2`:

```python
import os

from assemblyai import TranscriptStatus
from assemblyai.prerecorded.v2 import Transcriber, TranscriptionConfig

config = TranscriptionConfig(
    speech_models=["assemblyai-stt-3-7", "universal-2"],
    language_detection=True,
    speaker_labels=True,
)

transcriber = Transcriber(api_key=os.environ["ASSEMBLYAI_API_KEY"])
transcript = transcriber.transcribe("meeting.wav", config=config)

if transcript.status == TranscriptStatus.error:
    raise RuntimeError(f"Transcription failed: {transcript.error}")

for utterance in transcript.utterances:
    print(f"Speaker {utterance.speaker}: {utterance.text}")
```

For subtitles, request the SRT from the finished transcript instead of building it yourself:

```bash
curl -s "https://api.assemblyai.com/v2/transcript/$id/srt?chars_per_caption=32" \
  -H "authorization: $ASSEMBLYAI_API_KEY" > meeting.srt
```

Swap `srt` for `vtt` to get WebVTT. The SRT endpoint writes cues of up to 32 characters, which can cut across a speaker turn. For a whole video, with cues that break at each speaker and a chapter list for the description, my [YouTube to SRT guide](/transcribe-youtube-video-srt-assemblyai/) has a tested script.
