## Why WordPress email fails (and why SMTP fixes it)

WordPress sends all mail through `wp_mail()`, which by default calls PHP's `mail()`. On most shared hosting and many VPS setups, `mail()` is either disabled outright or silently rate-limited. The message looks like it sent (WordPress doesn't throw an error), but nothing shows up at the recipient. No bounce, no log entry, nothing.

Routing through SMTP fixes the chain. Here's what happens once FluentSMTP is in place:

```
WordPress wp_mail()
    → FluentSMTP (logs, retries, failure alerts)
        → Zoho SMTP (authenticated, reputation-scored sender)
            → Recipient inbox

  Side notes:
  ├── SPF + DKIM DNS records decide inbox vs spam
  └── Auth uses a Zoho app password, not your main password
```

The same Zoho SMTP account also fixes non-WordPress mail from the server. If you run [Linux email alerts for CPU monitoring](/monitor-cpu-usage-and-send-email-alerts-in-linux/) or cron reports, they suffer from the same `mail()` problem. Pointing them at the same SMTP relay solves both.

<Notice type="info" title="SMTP vs provider API">
FluentSMTP also supports API-based providers (SES, Gmail OAuth, SendGrid, etc.), but Zoho has no dedicated API provider in FluentSMTP, so it goes through the generic SMTP path. This guide's approach is the only one that works with Zoho Mail.
</Notice>

## Set up SPF and DKIM for your sending domain

This is the step most tutorials skip, and it's why test emails land in spam even when the SMTP config is perfect. SPF and DKIM tell receiving mail servers that Zoho is allowed to send on behalf of your domain. Without them, Gmail and Outlook will silently junk your WordPress mail.

Do this **before** the first test send. DNS records need time to propagate (usually minutes, sometimes hours), and deliverability is decided at the DNS level, not in FluentSMTP.

<Notice type="info" title="Don't debug DNS in the plugin">
SPF, DKIM, and DMARC live in the Zoho Admin Console and your DNS provider. FluentSMTP has nothing to do with them. If mail sends but lands in spam, the plugin is not the problem.
</Notice>

### SPF record for Zoho

Publish a TXT record on your root domain:

```text
v=spf1 include:zohomail.com ~all
```

If you already have an SPF record (say, for Google Workspace or another sender), **merge** the `include:zohomail.com` into the existing one. Do not publish a second `v=spf1` record.

<Notice type="warning" title="Never publish two SPF records">
One `v=spf1` string per domain, no exceptions. Stacking two SPF TXT records invalidates both, and every email from your domain goes to spam. Merge the includes into a single record instead.
</Notice>

Verify:

```bash
dig TXT yourdomain.com +short
```

Expected output should show your merged record containing `include:zohomail.com`. If you see two separate `v=spf1` strings, fix that first.

### Enable DKIM in the Zoho Admin Console

1. Log into the [Zoho Mail Admin Console](https://mailadmin.zoho.com/).
2. Go to **Email Configuration → DKIM**.
3. Select your domain and click **Generate**. Zoho gives you a selector (like `zoho`) and a TXT record value.
4. Publish the TXT record at your DNS host at: `<selector>._domainkey.yourdomain.com`.
5. Back in the Zoho console, click **Enable** once the record is visible.

Verify:

```bash
dig TXT zoho._domainkey.yourdomain.com +short
```

You should get back the public key Zoho generated. If the command returns nothing, the record hasn't propagated yet. Wait and re-check.

## Create a Zoho application password

Zoho requires an application-specific password for SMTP **if you have Two-Factor Authentication enabled** (or if your organization enforces TFA). Even with TFA off, use an app password anyway. It's scoped to one app and revocable without rotating your main account password.

1. Go to [Account Security → App Passwords](https://accounts.zoho.com/home#security/app_password).
2. Click **Generate New Password**.
3. Label it something clear like "WordPress SMTP".
4. Copy the password immediately. Zoho shows it only once.

<Notice type="info" title="TFA changes the rules">
If TFA is off and your org doesn't enforce it, the main password can technically work over SMTP. Use an app password regardless. It's the pattern Zoho documents for SMTP clients, and it limits blast radius if the credential leaks. If you're setting up 2FA on WordPress itself, see [two-factor authentication for WordPress](/secure-wordpress-2fa/).
</Notice>

You can revoke or regenerate app passwords anytime from the same page. Revoking a password immediately breaks SMTP auth. That is what you want when a credential leaks.

## Choose the right Zoho SMTP server and port

This is where a lot of setups break. Zoho splits SMTP hosts by **plan**, not by whether you use a custom domain. Getting this wrong produces "Relaying disallowed" or connection timeouts.

```
                    Is your org on a PAID Zoho plan?
                    (Mail Lite, Mail Premium, Workplace)
                           /                \
                         YES                 NO
                          |                   |
                  smtppro.zoho.com      smtp.zoho.com
                          |              (personal + free org)
                          |                   |
                          +--------+----------+
                                   |
                          Port 465 (SSL) or 587 (TLS)
                                   |
                    Not sure? Check "Server Configurations
                    Details" inside your Zoho account.
```

### Personal and free organization accounts: smtp.zoho.com

If you have a personal address (`@zohomail.com` or legacy `@zoho.com`) **or a free-plan organization with a custom domain**, use:

- **Server**: `smtp.zoho.com`
- **Port**: `465` (SSL) or `587` (TLS)
- **Username**: your full Zoho email address or alias
- **Password**: the application password from the previous step

One caveat on the free plan: it excludes IMAP/POP/ActiveSync and is available only in select data centers. SMTP is documented and available for free-org users, but if you hit weird signup or connection issues, your region may be the reason. More on this in the plan table below.

### Paid organization accounts: smtppro.zoho.com

If you're on **Zoho Mail Lite, Mail Premium, or Workplace** (paid) with a domain-based address (`you@yourdomain.com`), use:

- **Server**: `smtppro.zoho.com`
- **Port**: `465` (SSL) or `587` (TLS)
- **Username**: your full Zoho email address or alias
- **Password**: the application password

<Notice type="warning" title="This is where setups break">
Using `smtppro.zoho.com` on a free-org account is the single most common misconfiguration. It produces "Relaying disallowed" errors or auth failures. If you're not sure which plan you're on, open your Zoho account and look at **Server Configurations Details**. Zoho shows the exact host for your account and data center right there. Copy what it says.
</Notice>

## Configure FluentSMTP for Zoho SMTP

Install FluentSMTP from **Plugins → Add New**, search for "FluentSMTP", install, and activate. Current stable is 2.4.5 (Nov 2026). For this Zoho SMTP WordPress setup, FluentSMTP handles all the `wp_mail()` interception and logging. You just need to point it at the right Zoho SMTP host.

After the 2.4.0 admin redesign (Vue 3, Sep 2026), the plugin navigation is: **Dashboard, Settings, Email Logs, Alerts, About**. The settings screen below predates the redesign. The layout has changed but the fields are the same:

<Picture formats={["webp"]} fallbackFormat="webp" src={imgFluentSmtp} alt="FluentSMTP SMTP Server settings configured with Zoho Mail SMTP credentials" />

Go to **Settings** and add a new connection. Choose **SMTP Server**. This is the generic SMTP provider in FluentSMTP 2.4.x (the label was "Other SMTP" in older versions). Zoho has no dedicated API provider in FluentSMTP, so the SMTP path is correct.

<Notice type="info" title="Provider label">
In the FluentSMTP code the provider is titled "SMTP Server" (key `smtp`). The 2.4.x UI may group or label it slightly differently, so look for the generic SMTP option, not a Zoho-specific one.
</Notice>

Fill in:

- **From Email**: the Zoho address or alias you want to send from (must match or be an alias of the Zoho account)
- **From Name**: your site name or your name
- **SMTP Host**: `smtp.zoho.com` or `smtppro.zoho.com` per the section above
- **SMTP Port**: `465` (SSL) or `587` (TLS)
- **Username**: your full Zoho email address
- **Password**: the application password

Save the connection. FluentSMTP logs every email with full headers, body, and the SMTP server's response. This is what makes everything below debuggable.

### Store credentials in wp-config.php

Instead of saving the SMTP password in the WordPress database, define it in `wp-config.php` (above the "That's all, stop editing!" line):

```php
define('FLUENTMAIL_SMTP_USERNAME', 'you@yourdomain.com');
define('FLUENTMAIL_SMTP_PASSWORD', 'your-app-password-here');
// Optional: if defined, they must match the saved connection settings:
define('FLUENTMAIL_SMTP_HOST', 'smtp.zoho.com');
define('FLUENTMAIL_SMTP_PORT', '465');
```

FluentSMTP picks these up automatically and uses them instead of the DB-stored values. Credentials in the database are encrypted (the plugin does this), but `wp-config.php` keeps them away from any plugin that might dump options tables.

<Notice type="info" title="Constants must match the UI">
If you define `FLUENTMAIL_SMTP_HOST` or `FLUENTMAIL_SMTP_PORT`, the values must exactly match what's saved in the FluentSMTP connection settings. Mismatches trigger validation errors and the connection won't work. Define only `FLUENTMAIL_SMTP_PASSWORD` and `FLUENTMAIL_SMTP_USERNAME` if you want the simplest safe setup.
</Notice>

## Verify: send a test email and check the logs

Don't assume it works. Verify three ways:

**1. Test email from the UI.** In FluentSMTP, click **Send Test Email**, enter an address you control, and send. Then check the **Email Logs** tab. You should see the message with its full headers, body, and the SMTP server's response code. A healthy send shows a `250 OK`-style response.

**2. Cross-check in Zoho.** Open your Zoho account's **Sent** folder. Zoho saves a server-side copy of every SMTP send. If FluentSMTP says "sent" but Zoho Sent is empty, something is wrong. (If you see duplicates in Sent, you can disable "Save copy of sent emails" in Zoho Settings → Mail Accounts → SMTP.)

**3. Passive monitoring.** FluentSMTP 2.3.0 added a **Daily Connection Health Check** that verifies the SMTP connection on a schedule and surfaces problems on the dashboard. Combined with failure alerts to Telegram, Slack, Discord, or Pushover (configured under **Alerts**), you'll know when delivery breaks instead of finding out from a customer.

<Notice type="success" title="You're done when…">
The test email arrives in the target inbox, Email Logs shows a `250`/OK server response, and the Zoho Sent folder has a copy. If any of those three fails, jump to the troubleshooting section below.
</Notice>

### Verify from the command line with WP-CLI

FluentSMTP 2.3.0 (Aug 2026) added WP-CLI commands, handy when wp-admin is the thing that's broken, or when you just prefer SSH:

```bash
wp fluent-smtp test        # send a test email
wp fluent-smtp health      # connection health check
wp fluent-smtp stats       # sending statistics
wp fluent-smtp prune-logs  # prune old email logs
```

Run these from your WordPress root directory. `wp fluent-smtp health` is the quickest sanity check. It reports whether the connection is alive and authenticating. `wp fluent-smtp test` sends a real email using your configured connection. Use `wp fluent-smtp prune-logs --days=30` (or similar) to keep the log table from growing forever on busy sites.

## Zoho sending limits, costs, and plan choices

Zoho enforces sending limits on a **1-hour rolling basis**, not a daily reset. Here's what the rates-and-limits page says (last updated November 2, 2026):

- **External outgoing**: 50-500 emails/hour (dynamic, based on sender reputation, recipient engagement, and contact quality)
- **Internal outgoing**: 1,000/hour
- **Recipients per message** (external): 150 (paid) / 100 (free), to+cc+bcc combined
- **On exceeding the limit**: new sends are blocked for up to 1 hour (receiving still works)
- **Bulk/burst sending**: not supported under Zoho's business usage policy

The practical implication: a new Zoho sender on a fresh domain starts near the floor (50/hour). A WooCommerce flash sale that fires 80 order-confirmation emails in 20 minutes can hit that ceiling. The sending block auto-resolves within an hour, but the customer emails are delayed.

<Notice type="warning" title="Don't blast newsletters through Zoho Mail">
Bulk and burst sending violates Zoho's usage policy and will get your sender throttled. For marketing email and newsletters, use a dedicated tool like [Sender (free up to 15,000 emails/month)](https://go.bitdoze.com/sender). Reserve Zoho SMTP for transactional mail: password resets, order confirmations, contact form notifications.
</Notice>

## Troubleshooting common Zoho SMTP errors

Here are the failure modes you'll actually hit, with the fix for each:

| Symptom | Likely cause | Fix |
|---|---|---|
| "Relaying disallowed" error | SMTP username isn't the account's own email or alias | Use the full Zoho address as the SMTP username |
| Authentication rejected | TFA is on but the main password is being used | Generate an app password at `accounts.zoho.com/home#security/app_password` |
| Connection refused or timeout | Wrong host for your plan, or port/encryption mismatch | `smtp.zoho.com` (personal + free org) vs `smtppro.zoho.com` (paid org); port 465 = SSL, 587 = TLS |
| Test email sends but never arrives | Domain lacks SPF/DKIM → landing in spam | See the SPF/DKIM section above |
| "You have reached your email sending limit" | Hit the 50-500/hour rolling limit | Wait up to 1 hour (auto-resolves); reduce send bursts; don't use Zoho Mail for bulk/marketing |
| Free plan connection oddities | Free plan only in select data centers | Copy the server shown in **Server Configurations Details** inside your Zoho account |

**Rollback / undo.** If you need to back out: deactivate FluentSMTP (WordPress falls back to PHP `mail()`), delete the SMTP connection in FluentSMTP settings, and revoke the Zoho app password. If you merged an SPF record, restore the previous single record. Never leave two `v=spf1` strings behind.

## What should you know about fallback connections for WooCommerce stores?

FluentSMTP supports multiple SMTP connections with automatic fallback. If the primary connection (Zoho) is down or rejects a send, it retries through a second provider. Set this up under **Settings → Add Another Connection**.

For most blogs this is overkill. But if you run a WooCommerce store where order emails are revenue-critical, a fallback connection is cheap insurance. Two options worth considering as the backup relay:

- [Mail.Baby cheap SMTP service](/mail-baby-review/): very inexpensive transactional SMTP, good as a silent fallback
- [ZeptoMail SMTP relay setup on a VPS](/how-to-setup-smtp-relay-email-on-zeptomail/): pay-as-you-go transactional email

One operational caveat: FluentSMTP routes by **From address** across connections. A fallback only helps if the second connection is authorized to send as the same From address or alias, otherwise the receiving provider rejects the retry too. Make sure both connections use a From address both providers recognize, or configure the fallback to use its own aligned domain.

If you're managing a large product catalog on top of all this, a [WooCommerce product admin dashboard](/woocommerce-admin-dashboard/) keeps the operational side sane.
