If you've built anything with AI agents that talks to more than one service, you've felt the pain. Your agent needs to read a file from S3, check a Slack thread, pull a Google Doc, and query a GitHub repo. Each one needs its own SDK, its own authentication flow, its own set of method calls. Your prompt engineering turns into a juggling act of API instructions.

[Mirage](https://github.com/strukto-ai/mirage) takes a different approach. It mounts all those services as branches of a single virtual filesystem for AI agents: S3, Google Drive, Slack, GitHub, Redis, Gmail, whatever you need. Your agent navigates them with `ls`, `cat`, `grep`, and pipes.

The reason this works well is simple: LLMs are post-trained in terminal environments, so the Unix filesystem is probably the interface they have the most training data for. Mirage leans on that existing knowledge instead of asking models to learn yet another API surface.

Since this guide first ran, Mirage has grown from a virtual filesystem into a virtual terminal for AI agents: same tree-and-bash core, plus virtual CLIs, virtual machines, and a policy layer. This guide has been updated for v0.0.8.

This walkthrough covers setting up Mirage, mounting your first backends, wiring it into an agent framework, and locking the agent down. You'll have a working setup in about 10 minutes.

</Notice>

## What Mirage actually does

Mirage gives you a `Workspace` object. You mount services onto paths in that workspace, then run shell commands against the combined tree. If you've used FUSE-based tools like ZeroFS or JuiceFS to [mount an S3 bucket as a filesystem on a VPS](/s3-bucket-filesystem-vps/), the mental model is similar, but Mirage runs the tree in-process for your agent, not as a host mount.

```python
import asyncio
from mirage import MountMode, Workspace
from mirage.vfs.ram import RAMVFS
from mirage.vfs.s3 import S3Config, S3VFS
from mirage.vfs.slack import SlackConfig, SlackVFS

async def main() -> None:
    ws = Workspace(
        {
            "/data":  RAMVFS(),
            "/s3":    S3VFS(S3Config(bucket="my-logs-bucket")),
            "/slack": SlackVFS(SlackConfig(token="xoxb-...")),
        },
        mode=MountMode.WRITE,
    )
    result = await ws.shell("ls /s3/logs/")
    print(await result.stdout_str())
    await ws.close()

asyncio.run(main())
```

The shell isn't a real `/bin/bash`. Mirage runs the workspace in-process with its own bash parser (written in Rust, shared via PyO3 for Python and WebAssembly for TypeScript; tree-sitter was removed in v0.0.8) and a dispatcher that routes commands to per-mount handlers. No subprocesses. Pipes, globs, `&&`, `||`, and GNU-grade bash semantics all work across mounts. The command kernels (`jq`, `awk`, `sed`, `grep`, `rg`, `sort`, `tar`, `patch`, and more) live in a single Rust crate called `mirage-rs`.

Since v0.0.5, Mirage has also virtualized CLIs and machines behind the same shell. You can install `git`, `gh`, `slack`, or `office` (Excel/Word/PowerPoint) as virtual commands, and run programs on remote machines (SSH, Docker, Kubernetes) via a machine router. The filesystem is where most agent workflows start, which is the focus of this guide.

One thing to internalize before you write any code: **mounts are read-only by default**. You opt in to writes with `MountMode.WRITE` (and execution with `MountMode.EXEC`), either globally or per mount. The old article examples silently assumed writable mounts. Don't.

### Supported backends

Mirage covers a wide range of services. The list has expanded a lot since v0.0.1. Here's the current picture:

| Category | Backends | Mode |
|---|---|---|
| **Object storage** | S3, Cloudflare R2, GCS, OCI, MinIO, B2, Spaces, Wasabi, Ceph, SeaweedFS, and more | Read/write |
| **Files / drives** | Google Workspace (Drive, Docs, Sheets, Slides), OneDrive, SharePoint, Dropbox, Box, WebDAV, SSH (SFTP) | Read/write |
| **Databases** | Postgres, MongoDB, Redis, SQL, Airtable | Mostly read-only views |
| **AI / vector / observability** | Chroma, Qdrant, HF Datasets/Models, Weights & Biases, Langfuse, Jaeger | Read-only |
| **Chat / productivity** | Slack, Discord, Email (IMAP), Notion, Trello, Linear, Google Calendar | Mostly read-only |
| **Source control** | GitHub (repo at branch/tag/commit) | Read-only |
| **Scratch** | RAM, Disk | Read/write |

A few things to know about how the mounts behave:

- **Search push-down**: on some backends, `grep` is answered by the service's own search API rather than by downloading every file. Faster, but results can differ from local `grep`.
- **Walk limits**: on S3, `grep -r`, `find`, and `du` stop after 1000 files. A glob matching more than that, or `tar -c` / `cp -r` / `rm -r` past that limit, gets refused. You can tune this with `command_limits` / `walk_limit` in the workspace config.
- **Not everything writes**: GitHub repo views, Slack, Discord, Notion, Postgres views, and several others are read-only. Greps and reads work fine; writes are rejected.

<Notice type="info" title="Not every backend does everything">
Run <code>mirage workspace vfs-md</code> or <code>mirage workspace vfs</code> to see exactly what operations each mount supports. The per-backend setup guides at <a href="https://docs.mirage.strukto.ai/home/setup/s3">docs.mirage.strukto.ai</a> have the details for each VFS.
</Notice>

### Mirage vs per-service MCP servers

<Accordion label="How does this compare to MCP?" group="comparison" expanded="true">

If you're coming from [what MCP (Model Context Protocol) is](/mcp-introduction-beginners/) and wondering whether you need both, here's the breakdown:

| Aspect | Mirage | Per-service MCP servers |
|---|---|---|
| **Setup** | One workspace, mount config per service | One server per service |
| **Agent vocabulary** | Standard bash (`ls`, `cat`, `grep`, pipes) | Custom tool schemas per server |
| **Cross-service pipelines** | Native (pipes across mounts) | Manual orchestration in code |
| **Caching** | Built-in two-layer cache (index + file) | Varies by server |
| **Portability** | Snapshot and clone workspaces | State scattered across servers |
| **Framework support** | OpenAI Agents SDK, Vercel AI SDK, Agno, LangChain, Pydantic AI, Mastra | Depends on MCP client |

MCP servers are still useful for services that need structured tool calls, like "create a calendar event" or "send a Slack message." For a comparison of when to use native tools vs MCP in an agent framework, see [Mastra tools vs MCP](/mastra-tools-vs-mcp/). Mirage works best when the interaction pattern is read/write/search, which covers a large chunk of what agents actually do.

They're also complementary now. Mirage's **"From MCP"** feature (v0.0.8) can install an MCP server's tools as a single CLI inside the Mirage shell, so you can keep an existing MCP server and give the agent one `git`-like binary to talk to it. If you've already invested in MCP connectors (say via the [Composio MCP guide](/composio-mcp-guide/)), you don't have to throw that away. And if you're building Agno agents that use MCP, [Context7 MCP with Agno](/agno-mcp-tools-context7/) covers that angle.

</Accordion>

## Step 2: Create a workspace and mount services

The workspace is the central object. You define it with a dictionary mapping mount paths to VFS instances. Mounts are **read-only by default**: you must opt in to writes.

<Notice type="warning" title="Read-only by default">
Mounts reject writes unless you set <code>MountMode.WRITE</code>. This is a least-privilege control: only the mounts you explicitly mark writable accept writes. Start read-only and widen deliberately.
</Notice>

Each VFS reads its credentials from environment variables or explicit config objects. Mirage supports env vars, dotenv files, 1Password service accounts, and AWS Secrets Manager for credential resolution. Check the [S3 setup guide](https://docs.mirage.strukto.ai/home/setup/s3) and the [workspace configuration docs](https://docs.mirage.strukto.ai/home/configuration/workspace) for per-backend details.

Note that `/` is now a real virtual root (the old `/_default` path was removed in v0.0.3). You can mount over it or leave it as the default scratch space.

## Step 3: Run commands against the combined tree

Once the workspace is set up, every command goes through `ws.shell()`:

```python
# List files in S3
result = await ws.shell("ls /s3/logs/2026/05/")
print(await result.stdout_str())

# Search across Slack messages (read-only mount, grep works fine)
result = await ws.shell("grep 'incident' /slack/incidents/*.json")
print(await result.stdout_str())

# Pipe data between backends
result = await ws.shell("cat /s3/report.csv | head -20 > /data/preview.txt")

# Check for failures: ws.shell does NOT raise on error
print(result.exit_code)  # 0 = ok, non-zero = failure
if result.exit_code != 0:
    print(await result.stderr_str())
```

The agent uses the same commands it would use on a local filesystem. No new vocabulary to learn, no SDK method calls to memorize.

<Notice type="warning" title="ws.shell() does not throw">
<code>ws.shell</code> returns a result object even when a command fails. Always check <code>result.exit_code</code> and read the error with <code>await result.stderr_str()</code>. Exit codes: 0 = ok, 1 = tool/VFS/server failure, 2 = usage or policy refusal, 130 = Ctrl-C, 141 = broken pipe.
</Notice>

### Verify it works

Right after setup, run these through the CLI or Python to confirm the workspace is healthy:

```bash
# CLI: write and read back through the RAM scratch mount
mirage shell -w demo -c 'echo ok > /data/x && cat /data/x'

# Scriptable check with JSON output
mirage shell -w demo -c 'ls /s3' --json | jq .stdout
```

In Python, the equivalent check is:

```python
result = await ws.shell("echo ok > /data/x && cat /data/x")
assert result.exit_code == 0
assert "ok" in await result.stdout_str()
```

If the first command returns empty output but exit code 0, the mount exists but credentials may be wrong (see Troubleshooting). If exit code is 2, a policy rule blocked the command.

### Virtual CLIs

The old `ws.command()` custom-command API is gone. Since v0.0.5, custom behavior lives in **virtual CLIs**: real command-line programs installed into the Mirage shell via `clis:` config:

```yaml
clis:
  git: {}
  gh: {}
  slack: {}
  office: {}       # Excel/Word/PowerPoint, credential-free
  pdftotext: {}
  my-script:
    script: scripts/summarize.py
```

Agents discover these via `man` and `which` like any other program. SKILL.md documents them alongside VFS.md. Available CLIs include `git`, `gh`, `slack`, `discord`, `himalaya` (email), `linear`, `ntn` (Notion), `gws` (Google Workspace), `hf` (Hugging Face), `office`, `pdftotext`, `ast-grep`, and more. Custom CLIs can be written as Python or JavaScript scripts.

This extends the "no per-service SDKs" thesis from files to full command-line tools. Instead of teaching the agent a Slack SDK, you install `slack` as a CLI and the agent runs `slack search "incident"` like it would on any Unix box. See the [CLI setup docs](https://docs.mirage.strukto.ai/home/setup/clis) for the full list.

## Step 4: Wire into your agent framework

Mirage ships adapters for the major agent frameworks. The pattern is the same everywhere: pass the workspace, get tools back. Here's what's available:

| Framework | Install | Hand it | Agent gets |
|---|---|---|---|
| Agno | `mirage-ai[agno]` | `MirageToolkit(ws)` | Seven session tools |
| OpenAI Agents | `mirage-ai[openai]` | `MirageShellExecutor(ws)`, `MirageEditor(ws)`, `MirageSandboxClient(ws)` | Shell/patch/sandbox tools |
| Claude Agent SDK | `mirage-ai[claude-agent-sdk]` | `MirageServer(ws)` | Seven session tools |
| Pydantic AI | `mirage-ai[pydantic-ai]` | `MirageWorkspace(ws)` | File + shell tools |
| LangChain Deep Agents | `mirage-ai[deepagents]` | `LangchainWorkspace(ws)` | File + shell tools |
| Vercel AI SDK | `@struktoai/mirage-vercel` | per-package | Tools for `generateText` |
| Mastra | `@struktoai/mirage-mastra` | per-package | Mastra tools |

"Seven session tools" = `shell`, `read`, `write`, `edit`, `ls`, `grep`, `glob` (profile-gated: an agent is never offered a tool whose every call would be refused).

<Notice type="info" title="VFS.md replaces file_prompt">
The old <code>ws.file_prompt</code> property is gone. Generate a filesystem map with <code>vfs_md = await ws.vfs_md(session_id="agent")</code>. The agent reads it by running <code>cat /VFS.md</code>. The format follows the <a href="https://agentvfs.org/vfs">AgentVFS spec</a>. Denied commands and hidden paths are never mentioned in VFS.md. Virtual CLIs are documented separately in SKILL.md.
</Notice>

## Step 5: Configure caching

Every workspace ships with a two-layer cache so repeated reads don't hit the network:

- **Index cache** caches directory listings and metadata. First `ls` hits the API; subsequent ones serve from cache until TTL expires.
- **File cache** stores object bytes. First `cat` streams from origin; later reads come from cache.

The defaults changed in recent releases. The RAM file cache is now **32 MB** (with a `max_drain_bytes` of 8 MiB). For production setups with multiple workers or processes, switch to Redis:

```python
from mirage import Workspace
from mirage.cache.file.config import CacheConfig, RedisCacheConfig

# RAM cache (default: 32 MB)
ws = Workspace(mounts, cache=CacheConfig(limit="2GB"))

# Redis cache for multi-process / multi-worker setups
ws = Workspace(
    mounts,
    workspace_id="agent",
    cache=RedisCacheConfig(url="redis://localhost:6379/0"),
)
```

YAML equivalent:

```yaml
cache:
  type: redis
  url: redis://localhost:6379/0
index:
  type: redis
  url: redis://localhost:6379/0
```

Sessions and jobs can share state via `RedisWorkspaceStateStore` from `mirage.workspace.store.redis`.

<Notice type="warning" title="Redis limit does not evict">
On Redis, the <code>limit</code> setting does <strong>not</strong> evict old entries. Cap the Redis server's memory with <code>maxmemory</code> in your Redis config instead. The default Redis cache limit is 512 MB.
</Notice>

If you're running Mirage inside a container, pair it with a [Redis Docker setup](/multiple-postgres-databases-docker/) for a self-contained stack.

## Locking the agent down

Mirage has a real security layer: profiles, path hiding, command policies, network egress rules, and an approval door. If you're running agents against production data, use it.

![Mirage policy layer: profile rules at command, path, and network doors produce allow, ask, or deny outcomes, with an approval door and decision ledger](../../assets/images/25/05/mirage-policy-doors-diagram.svg)

### MountMode: least privilege per mount

Recap from Step 2: mounts are read-only unless you say otherwise. Set `MountMode.READ`, `WRITE`, or `EXEC` globally or per mount. The stricter setting always wins.

### Profiles: hide paths, deny commands

Profiles define what an agent role can see and do. A hidden file is not merely unreadable; it is absent from the filesystem the agent sees:

```yaml
profiles:
  analyst:
    paths:
      hide: ["/s3/secrets", "/data/credentials"]
    commands:
      deny: ["slack send-message", "curl", "rm -rf"]
      allow: ["ls", "cat", "grep", "sort", "wc", "head", "tail"]
      ask: ["cp", "mv"]
network:
  allowed_domains: ["api.github.com:443", "*.slack.com"]
  denied_domains: ["*:22"]
```

One role per session. Per-session permissions can narrow a profile further ("the stricter of the two wins").

### Network policy

Control egress at the workspace level. Refused connections fail with `EACCES` (a `curl` call exits 7). You can also map `host:port` to another destination with `network.routes` and refuse cloud metadata addresses at the server level.

### Approval door and decision ledger

Commands marked `ask` in a profile pause and wait for a human decision:

```python
from mirage import Outcome, Scope

pending = await ws.decisions.pending()
for d in pending:
    await ws.decisions.answer(d.id, Outcome.ALLOW, scope=Scope.SESSION)
```

Every decision is logged in a queryable ledger. Use `--explain` on the CLI to dry-run any line through the policy layer. It says what the line would do and runs nothing:

```bash
mirage shell -w my-agent -c 'rm -rf /s3' --explain
```

Expect a refusal or dry-run output. This is your "why was this blocked?" debugging tool.

### Policy scripts

For logic that YAML rules can't express, write policy scripts in Python or JavaScript. They run at command, operation, and session doors, and can only restrict, never grant:

```python
# pre_command hook: deny rm and any python that deletes files
def pre_command(ctx):
    if ctx.line.startswith("rm "):
        return Outcome.DENY
    return Outcome.ALLOW
```

See the [policy documentation](https://docs.mirage.strukto.ai/home/policy/overview) for the full hook reference.

<Notice type="warning" title="Denied paths are invisible, not just blocked">
A hidden path never appears in VFS.md, in <code>ls</code> output, or in grep results. The agent doesn't know it exists. This is stronger than permission-denied errors, which leak the existence of a path.
</Notice>

### Resource limits

Know your defaults before an agent surprises you:

| Limit | Default | What happens past it |
|---|---|---|
| `max_memory` | Tens of MB (configurable) | `EDQUOT` (RAM files and command memory bounded) |
| Mount `capacity` | Unset | Caps bytes a mount stores |
| `walk_limit` | 1000 files (S3) | `grep -r`/`find`/`du` stop; `tar -c`/`cp -r`/`rm -r` refused |
| File cache (RAM) | 32 MB | Bounded by `max_drain_bytes` |
| File cache (Redis) | 512 MB | No eviction; use Redis `maxmemory` |
| `max_env` | 2 MB | Per-session variables/functions/aliases |
| `max_body_bytes` | 64 MB | Largest API reply read whole |
| `processes` | 128 per workspace | Hard cap on concurrent processes |

## Portable workspaces

Workspaces are portable. You can snapshot, clone, and version them. The API is now async and supports S3 targets:

```python
# Save workspace state (returns tar size in bytes)
size = await ws.snapshot("run.tar")

# Snapshot directly to S3
await ws.snapshot("snapshots/run.tar", s3={"bucket": "my-backups"})

# Load it elsewhere (no id= parameter in current signatures)
restored = await Workspace.load("run.tar")

# Deep copy without writing a tar
clone = await ws.copy()
```

CLI equivalent:

```bash
mirage workspace snapshot my-agent my-agent.tar
mirage workspace load my-agent.tar
```

During snapshot capture, new writes wait and running lines get 30 seconds before an `OSError(EBUSY)`. Plan accordingly.

You can save an agent's working environment and restore it on another machine, version workspace configs alongside your code, or reproduce agent runs by restoring the exact same filesystem state.

## Real-world example: multi-service log analysis

Here's a concrete workflow that pulls data from three services to produce a report. Note that the Slack and GitHub mounts are read-only; this example only greps them, which is correct:

```python
from mirage import MountMode, Workspace
from mirage.vfs.ram import RAMVFS
from mirage.vfs.s3 import S3Config, S3VFS
from mirage.vfs.slack import SlackConfig, SlackVFS
from mirage.vfs.github import GitHubConfig, GitHubVFS

ws = Workspace(
    {
        "/data":   RAMVFS(),
        "/s3":     S3VFS(S3Config(bucket="app-logs")),
        "/slack":  SlackVFS(SlackConfig(token="xoxb-...")),   # read-only
        "/github": GitHubVFS(GitHubConfig(owner="my-org", repo="my-app", token="ghp-...")),  # read-only
    },
    mode=MountMode.WRITE,
)

# Find errors in S3 logs
r = await ws.shell("grep -i 'error' /s3/production/2026-05-*.log > /data/errors.txt")
assert r.exit_code == 0, await r.stderr_str()

# Count by frequency
await ws.shell("sort /data/errors.txt | uniq -c | sort -rn > /data/top-errors.txt")

# Check if these were reported in Slack (grep against read-only mount)
await ws.shell("grep -i 'error' /slack/incidents/*.json > /data/slack-matches.txt")

# Cross-reference with GitHub issues
await ws.shell("grep -i 'error' /github/issues/ > /data/github-issues.txt")

# Combine into a report
await ws.shell("cat /data/top-errors.txt /data/slack-matches.txt /data/github-issues.txt > /data/report.txt")

# Verify the output exists
r = await ws.shell("wc -l /data/report.txt")
print(await r.stdout_str())
print("exit:", r.exit_code)
```

CLI verification of the same:

```bash
mirage shell -w my-agent -c 'wc -l /data/report.txt' --json | jq .stdout
```

The agent handles this the same way a developer would on a local machine: `grep`, `sort`, `uniq`, pipes. The data lives across S3, Slack, and GitHub, and the agent doesn't need to know that.

## Tips for working with Mirage

<ListCheck>
<ul>
<li>Use <code>RAMVFS</code> as a scratch pad (mount it at <code>/data</code> or similar), like <code>/tmp</code> for intermediate results</li>
<li>Name mount paths clearly: <code>/s3</code>, <code>/slack</code>, <code>/github</code> are easier for agents to reason about than <code>/m1</code>, <code>/m2</code></li>
<li>Start mounts read-only and widen to <code>WRITE</code> deliberately. Don't give write access you don't need</li>
<li>Switch to Redis cache for production; the default 32 MB RAM cache doesn't survive restarts or share across processes</li>
<li>Snapshot workspace state before long-running agent tasks so you can restore if something goes sideways</li>
<li>Use <code>--explain</code> whenever a command is unexpectedly refused: it tells you which policy rule blocked it</li>
<li>Check per-VFS setup guides before building. Not every backend supports every operation (run <code>mirage workspace vfs-md</code> for a quick summary)</li>
<li>Keep walk limits in mind on big S3 trees: <code>grep -r</code> stops at 1000 files by default</li>
<li>Pin <code>mirage-ai==0.0.8</code> in production. The project is experimental and ships breaking changes</li>
<li>Combine Mirage with shell-native coding agents like <a href="/opencode-setup-guide/">OpenCode</a> or <a href="/hermes-agent-setup-guide/">Hermes Agent</a></li>
</ul>

## Troubleshooting

<Accordion label="Commands return empty results" group="faq">
Check that your credentials are set correctly. Mirage reads service credentials from environment variables by default. Verify with:

```python
# Check what's mounted
r = await ws.shell("ls /")
print(await r.stdout_str())

# Check a specific mount
r = await ws.shell("ls /s3/")
print(await r.stdout_str())
```

If the mount is empty but shouldn't be, verify the bucket/token/credential configuration for that specific VFS. Check the per-backend setup guide at [docs.mirage.strukto.ai](https://docs.mirage.strukto.ai/home/setup/s3) for the exact environment variable names.
</Accordion>

<Accordion label="Pipe commands fail or big-tree commands are refused" group="faq">
Most pipes work across mounts. Two common failure modes:

1. **Walk limits**: on S3, `grep -r`, `find`, and `du` stop after 1000 files. `tar -c`, `cp -r`, and `rm -r` are refused past that limit. Fix: raise `command_limits` / `walk_limit` in your workspace config, or split the work.

2. **Resource-specific behavior**: if a pipe fails, split it into separate steps using a RAM mount as intermediate storage:

```python
await ws.shell("cat /s3/data.json > /data/temp.json")
r = await ws.shell("jq '.items[]' /data/temp.json > /data/filtered.json")
print("exit:", r.exit_code)
```
</Accordion>

<Accordion label="Command was refused (exit code 2) or nothing happened" group="faq">
<code>ws.shell</code> does not raise when a command fails. Symptoms of a silent failure: empty output, unexpected exit code, or no visible effect.

1. Check <code>result.exit_code</code> and <code>await result.stderr_str()</code>
2. Run the same command through the CLI with <code>--explain</code> to see which policy rule refused it:
   ```bash
   mirage shell -w my-agent -c 'rm -rf /s3' --explain
   ```
3. Exit codes: 0 = ok, 1 = tool/VFS/server failure, 2 = usage or policy refusal, 130 = Ctrl-C, 141 = broken pipe
</Accordion>

<Accordion label="Performance feels slow" group="faq">
First reads always hit the network. Subsequent reads use the cache. If you're doing heavy I/O:

1. Switch to Redis cache for shared caching across processes (the default is 32 MB RAM, which is small)
2. Use `mirage provision` (CLI) to pre-warm the cache before agent runs
3. Check if your backend has rate limits (especially Slack and Google APIs)
4. On Redis, set `maxmemory` on the server. The Mirage `limit` setting doesn't evict
</Accordion>

<Accordion label="Big tree commands hit EDQUOT or capacity errors" group="faq">
If writes start failing with <code>EDQUOT</code>, you've hit <code>max_memory</code> (bounds RAM files + command memory) or a mount's <code>capacity</code> limit. Fixes:

- Clean up the RAM scratch mount (<code>rm /data/*</code>)
- Raise <code>max_memory</code> in the workspace config
- Set <code>capacity</code> on specific mounts to bound them individually
- Check the file cache limit (32 MB RAM / 512 MB Redis by default)
</Accordion>

<Accordion label="Which model works best with Mirage?" group="faq">
Any model that handles bash well works. Models trained heavily on code and shell commands tend to perform best. If you're looking for affordable options, check [best open source LLMs for coding](/best-open-source-llms-claude-alternative/) or [cheapest AI models for Hermes Agent](/best-cheap-models-hermes-agent/). You can run Mirage with free models through [Hermes Agent with free models on the Nous Portal](/hermes-agent-mimo-v2-pro/) or a [LiteLLM Docker Compose install](/litellm-docker-install/) as well.
</Accordion>

## What's next

Mirage solves a real problem in agent development: connecting agents to multiple services without drowning in SDK boilerplate. The filesystem abstraction is familiar to both developers and LLMs, which makes it a practical foundation for multi-service agent workflows. The addition of virtual CLIs, machines, and a policy layer turns it from a clever trick into something you can run against real data.
