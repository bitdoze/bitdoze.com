## What NanoClaw is

NanoClaw is a lightweight, always-on Claude agent you message from chat apps, self-hosted on your own infrastructure. It runs on Claude's Agent SDK. The main difference from other bots is the isolation model: agents execute in Linux containers (Docker on Linux/macOS/WSL2) with explicitly mounted directories. The agent can't escape the container and can only access what you allow.

v2 lives under the [nanocoai org](https://github.com/nanocoai/nanoclaw) on GitHub (MIT license, roughly 31k stars as of November 2026; re-check on publish day if the number matters to you). Docs are at [docs.nanoclaw.dev](https://docs.nanoclaw.dev), with a Discord community and a web portal at portal.nanoclaw.dev.

The entity model is straightforward: **groups** (chats or trust domains) contain **sessions** (conversations), which spawn **agents** (containers). Messages ride a SQLite inbox/outbox pipeline:

```
messaging apps
  → host process (router) → inbound.db
    → Bun agent container (Claude Agent SDK)
      → outbound.db → host process (delivery) → messaging apps
```

It's a single host Node.js process with per-group message queues and exactly one writer per SQLite file. No microservices, no external message broker, and the codebase is still small enough to read in an evening.

### Why NanoClaw exists

OpenClaw is nearly half a million lines of code, 53 config files, and 70+ dependencies. Everything runs in one Node process with shared memory. Security is application-level: allowlists and pairing codes, not OS isolation.

NanoClaw takes a different approach:

<ListCheck>
<ul>
<li>Small enough to understand. One process, a few source files. The codebase is small enough that Claude Code can walk you through it and safely modify it.</li>
<li>Secure by isolation. Agents run in Linux containers. Bash access is safe because commands run inside the container, not on your host.</li>
<li>Built for one user. This isn't a framework. It's working software that you fork and customize for your exact needs.</li>
<li>Skills over features. Contributors don't add features to the codebase. They contribute Claude Code skills like <code>/add-telegram</code> that transform your fork. Channel adapters and providers literally ship as skill payloads.</li>
</ul>
</ListCheck>

v2 is also AI-native but in a hybrid way: the installer is a deterministic script (no Claude in the loop for setup), and Claude Code handles the judgment calls like diagnosis, resume, `/customize`, `/debug`, and the `/add-*` skills.

## Install NanoClaw v2 on your VPS

The happy path is three commands:

```bash
git clone https://github.com/nanocoai/nanoclaw.git
cd nanoclaw
bash nanoclaw.sh
```

The installer is a deterministic 3-stage pipeline. It auto-installs Node 22, pnpm 10, Docker (via get.docker.com + `usermod -aG docker` on Linux), and the OneCLI credential vault. The wizard then builds or pulls the agent image, installs a systemd user service, configures provider auth, and pairs your first channel (WhatsApp, Slack, Telegram, Discord, iMessage, or CLI).

<Notice type="info" title="Claude Code is still the config interface">
The installer is scripted, with no Claude in the loop for setup. Claude Code is invoked automatically only for diagnosis/resume and for `/add-*` skills after install. If you haven't used Claude Code before, it's Anthropic's CLI tool that can execute commands and modify files. You'll use it for customization and debugging.
</Notice>

### What the installer does (3 stages)

1. **`nanoclaw.sh` bash pre-flight** checks OS, architecture, RAM (warns below 3,700 MB), and sudo access. Exits early on unsupported environments.
2. **`setup.sh`** installs Node 22, pnpm 10, Docker (get.docker.com + docker group), and the OneCLI gateway at `127.0.0.1:10254`.
3. **`pnpm run setup:auto` wizard** handles the agent container image, provider authentication (Claude sign-in or API key), systemd user service, and first channel pairing.

The wizard defaults to pulling a pinned prebuilt **Echo hardened image** (digest-pinned, architecture-checked, provenance-labeled). It requires a free NanoClaw account. A local build is the fallback: set `NANOCLAW_HARDENED_IMAGE` in `.env` to force local. Note: this default has shifted across releases (README vs docs disagree), so verify what you get on a fresh install before relying on it.

### Verify the install

After the wizard finishes:

```bash
systemctl --user status nanoclaw-v2-<slug>   # should show active (running)
ncl sessions list                            # container_status: running | stopped
docker ps                                    # agent containers appear per active session
tail -f logs/nanoclaw.log                    # live output
```

If the service isn't running, check `logs/nanoclaw.error.log` first. If `ncl` isn't found, your PATH may not include the checkout. Run it from the project root or use `pnpm exec ncl`.

### Unattended install (scripted)

For automation or repeatable deployments, drive the installer with env vars:

```bash
NANOCLAW_SKIP=container,service \
NANOCLAW_AGENT_NAME=Nano \
NANOCLAW_DISPLAY_NAME="My Agent" \
NANOCLAW_AGENT_PROVIDER=claude \
NANOCLAW_GATEWAY_PROVIDER=onecli \
SECRET_NAME=anthropic \
HOST_PATTERN=api.anthropic.com \
bash nanoclaw.sh
```

You can re-run individual steps without redoing everything:

```bash
pnpm run setup -- --step container
pnpm run setup -- --step service
pnpm run setup -- --step verify
```

Set `NANOCLAW_NO_DIAGNOSTICS=1` to disable anonymous setup diagnostics if you'd rather not send telemetry.

## Container isolation

This is the main thing that sets NanoClaw apart. Agents run in containers, not in the main process.

<Notice type="warning" title="v2 change: containers DO have network access">
Unlike v1 (which ran containers with `NetworkMode: 'none'`), v2 containers have **normal outbound internet by default**. This is a deliberate change: agents need network access for web searches, API calls, and tool use. If you want to lock down egress, that's opt-in via <code>NANOCLAW_EGRESS_LOCKDOWN=true</code> (covered in [Hardening](#hardening-egress-lockdown--allowlists) below). Don't assume v1's "no network" model.
</Notice>

### How it works (message lifecycle)

When you send a message to NanoClaw:

1. Message arrives via the channel adapter (e.g. WhatsApp/Baileys)
2. Host router writes it to `inbound.db`
3. Host sweep wakes or creates the agent container for that session
4. Bun 1.4.0 agent runner (Claude Agent SDK) processes the message inside the container
5. Response written to `outbound.db`
6. Host delivery sends it back to the chat app

Exactly one writer per SQLite file. A heartbeat file at `/workspace/.heartbeat` tracks container liveness. Main source files:

```
src/router.ts          # message routing
src/delivery.ts        # outbound message delivery
src/host-sweep.ts      # wakes/creates containers on due ticks
src/session-manager.ts # session lifecycle
src/container-runner.ts # spawns hardened agent containers
src/channels/          # channel adapters
src/providers/         # LLM provider integrations
container/agent-runner/ # in-container Bun agent
```

### Container spawn hardening

Every agent container is spawned with hardening flags:

```
--cap-drop=ALL                    # drop all Linux capabilities
--security-opt no-new-privileges  # no privilege escalation
--init                            # proper signal handling / zombie reaping
--pids-limit=2048                 # fork bomb protection
--rm                              # disposable container, removed on exit
```

The container runs as a non-root `node` user. Setuid bits are stripped in the image build. Mounts are explicit: session folder + group workspace (read-write), code mounts (read-only). There is no host home directory mount, no `~/.ssh`, and no Docker socket access. The `container.json` config is remounted read-only.

```
┌─────────────────────────────────────────────────┐
│              agent container                     │
│  ┌───────────────────────────────────────────┐  │
│  │  --cap-drop=ALL                           │  │
│  │  --security-opt no-new-privileges         │  │
│  │  --init --pids-limit=2048 --rm            │  │
│  │  non-root user, stripped setuid           │  │
│  │  explicit mounts only                     │  │
│  └───────────────────────────────────────────┘  │
│  /workspace (group dir, rw)                      │
│  session folder (rw)                             │
│  code mounts (ro)                                │
└─────────────────────────────────────────────────┘
```

Even if the agent tries to run dangerous commands, it's contained. The host system is protected.

## Credentials and security model

v2's biggest security change: **raw credentials never enter agent containers**. Instead, the OneCLI Agent Vault handles secrets at the proxy layer.

### OneCLI credential vault

OneCLI runs a local gateway at `127.0.0.1:10254`. Here's how credentials flow:

```
Claude sign-in / API key
  → OneCLI vault (127.0.0.1:10254)
    → gateway proxy injects auth at the HTTP layer
      → agent container (receives short-lived stubs only)
```

Agents never hold raw API keys. If the vault is unreachable, the spawn aborts. No container starts without the gateway. Per-agent secret grants control what each agent can access:

```bash
onecli agents grants attach-secret --agent <name> --secret <secret-name>
```

<Tabs>
<Tab name="Claude Pro/Max (default)">
Browser-based OAuth sign-in to your Claude Pro or Max subscription. No API key needed. Fixed monthly subscription cost. This is the default credential path in the wizard.
</Tab>
<Tab name="API key">
Standard Anthropic API key (`sk-ant-...`). Usage-based billing. Set during the wizard or add to `.env` manually. The key is stored in the vault, never in containers.
</Tab>
<Tab name="OAuth token">
Long-lived OAuth token (`sk-ant-oat...`). Useful for headless/CI setups where browser sign-in isn't practical.
</Tab>
</Tabs>

For any Anthropic-compatible endpoint (self-hosted proxy, alternative gateway), set `ANTHROPIC_BASE_URL` in `.env`. The real token still lives in the vault:

```bash
# .env
ANTHROPIC_BASE_URL=https://your-api-endpoint.com
```

The alternative Iron Proxy gateway is available via `NANOCLAW_GATEWAY_PROVIDER=iron-proxy`. The `/add-onecli` skill handles vault setup and upgrades.

### Hardening: egress lockdown + allowlists

Container isolation is strong, but you should still review what the agent can reach and what it can see.

**Egress lockdown** restricts containers to gateway-only egress on an internal Docker network:

```bash
# .env
NANOCLAW_EGRESS_LOCKDOWN=true
```

When enabled, containers join the `nanoclaw-egress` Docker network with no direct internet. All outbound traffic routes through the gateway. If the gateway is unreachable, you get an `EgressLockdownError`, failing fast rather than silently dropping to open egress.

**Mount allowlist** controls what host directories the agent can access beyond its own workspace:

```json
// ~/.config/nanoclaw/mount-allowlist.json
{
  "allowedRoots": [
    { "path": "~/projects", "allowReadWrite": true }
  ],
  "blockedPatterns": ["password", "secret", "token"]
}
```

<Notice type="warning" title="Deny-by-default">
If this file doesn't exist, the agent gets <strong>no additional mounts</strong>. That's the safe default. Edit via <code>ncl groups config add-mount</code> or write the file directly. Mounts land under <code>/workspace/extra/</code> inside the container. Use <code>blockedPatterns</code> to refuse paths that match sensitive filename patterns.
</Notice>

**Sender allowlist** at `~/.config/nanoclaw/sender-allowlist.json` controls who can message the agent.

The blast radius is the agent group. Sessions within a group share the group workspace read-write, and `ncl sessions history` can read sibling transcripts. Put different trust domains in separate groups. The inbox symlink guard prevents symlink attacks on the message pipeline.

For a deeper look at how app-level isolation compares to container-level, see our [OpenClaw security guide](/openclaw-security-guide/). For broader server hardening, see [how I secured my Docker server after the BSI Hetzner report](/bsi-security-report-docker-ufw/) and the [CrowdSec guide to securing a VPS](/crowdsec-secure-server/). Layering DNS filtering on top of egress lockdown gives you defense in depth: a DNS firewall like [NextDNS](https://go.bitdoze.com/nextdns) catches lookups the gateway might not.

## WhatsApp setup

WhatsApp via Baileys (`@whiskeysockets/baileys` 7.0.0-rc.9 pinned) is the documented default channel. But note: the trunk ships only the built-in CLI channel. All platform adapters (WhatsApp, Telegram, Discord, Slack, Teams, iMessage, Signal, Mattermost, Matrix, Google Chat, and about a dozen more) install via `/add-<channel>` from the `channels` branch. The wizard pairs your first channel during setup.

<Notice type="error" title="WhatsApp ban risk">
The adapter skill warns that using a shared personal WhatsApp number can get it suspended. Use a dedicated or second number (<code>ASSISTANT_HAS_OWN_NUMBER</code>). This isn't theoretical: WhatsApp actively detects automation on personal accounts. The adapter asks for confirmation before proceeding with a shared number.
</Notice>

### Authentication (QR or pairing code)

The wizard walks you through WhatsApp authentication:

1. Choose QR code or pairing code
2. **QR**: open WhatsApp on your phone → Settings → Linked Devices → Link a Device → scan the code (2-minute timeout)
3. **Pairing code**: enter the code shown in your phone's Linked Devices screen (about 60-second window)

Auth is stored in `store/auth/`. You stay logged in until you explicitly log out or WhatsApp expires the session server-side.

After pairing, send the agent a test message and confirm it replies. Then check the wiring:

```bash
ncl wirings list   # shows chat → agent routes
```

Wire additional chats later via `/manage-channels`.

### Group isolation and trigger word

Each group gets its own context:

| Isolation | What it means |
|-----------|---------------|
| `memory/` tree | Each group has its own memory directory |
| Filesystem | Each group's workspace is a separate directory |
| Container | Each session runs in its own container sandbox |
| History | Conversations are not shared between groups |

The README documents `@Andy` as the default trigger word. The WhatsApp wizard names the agent `Nano` by default and prefixes shared-number replies with the agent name. Verify your actual default on a fresh install and align your examples accordingly. Change it via `/customize`:

```
/customize
Change the trigger word to @Bob
```

From your self-chat (admin), you can manage the bot:

```
@Andy list all scheduled tasks across groups
@Andy pause the Monday briefing task
@Andy join the Family Chat group
```

## Multi-agent teams

v2 replaces the old "Agent Swarms" concept with **multi-agent teams**. There's no swarm engine. Instead, agents can create and message other agents through permission edges.

The `create_agent` MCP tool lets an agent spawn a helper agent. `agent_destinations` defines which agents can talk to which (permission edges). For unprivileged groups, agent creation triggers **approval cards**. A human must approve before the new agent is created. The wizard-created first agent gets `cli_scope: global`; group-created agents default to `cli_scope: group`.

Agent-to-agent messages ride the same SQLite pipeline as chat messages (`channel_type='agent'`).

A practical example:

```
@Andy research the latest React patterns and have the code reviewer check if our codebase follows them
```

This can spawn a researcher agent and a reviewer agent that work together and report back. In 2026.10.1-rc, agents can also create agents from templates (approval-gated). Templates live in the [nanoclaw-templates registry](https://github.com/nanocoai/nanoclaw-templates) and use the Agent Plugins 1.0.0 format. Create a group from a template with `ncl groups create --template <ref>`.

`/add-opencode` adds OpenRouter, Google, DeepSeek, and other providers through a unified interface. For operators who want one endpoint in front of several model vendors, multi-model routing services like [Agent Router](https://go.bitdoze.com/agentrouter) can simplify key management.
</Tab>
<Tab name="Ollama (local)">
`/add-ollama-provider` runs local models via Ollama. Trades API costs for RAM/CPU. Legacy workflow but functional. Good for privacy-sensitive use or offline operation.
</Tab>
</Tabs>

Set `NANOCLAW_DEFAULT_MODEL` in `.env` for a global default. `NANOCLAW_FAST_MODE=true` enables the paid priority tier for Claude/Codex (higher cost per token, faster serving; worth it only if latency matters). For any Anthropic-compatible endpoint, `ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN` in `.env` routes traffic wherever you want (the token still lives in the vault).

## Scheduled tasks

NanoClaw has a built-in task scheduler for recurring jobs. Tasks are stored as `messages_in` rows in `data/v2.db` (`kind='task'`, with `process_after` timestamps and cron-style `recurrence` in your timezone). They persist across restarts. The host sweep wakes or creates containers on due ticks.

Create tasks in natural language from chat:

```
@Andy send an overview of the sales pipeline every weekday morning at 9am
@Andy review the git history for the past week each Friday and update the README if there's drift
@Andy every Monday at 8am, compile news on AI developments from Hacker News and TechCrunch and message me a briefing
```

Manage tasks with the `ncl` CLI:

```bash
ncl tasks list          # list all scheduled tasks
ncl tasks cancel <id>   # cancel a specific task
```

**Script gates** are an operator-friendly optimization: for frequent recurring tasks, a gate script can run before the agent wakes and skip the invocation if there's no work to do. See `docs/scheduled-tasks.md` in the repo.

## Memory system

v2 memory lives in a `memory/` directory per group, using Open Knowledge Format (Markdown files with YAML frontmatter):

```
groups/
├── main/
│   ├── memory/
│   │   ├── project-context.md
│   │   └── preferences.md
│   └── instructions.prepend.md   # persona
├── family-chat/
│   ├── memory/
│   └── instructions.prepend.md
└── work-team/
    ├── memory/
    └── instructions.prepend.md
```

`instructions.prepend.md` shapes the agent's persona. The `memory/` tree stores facts, context, and knowledge the agent accumulates.

<Notice type="warning" title="Don't edit CLAUDE.md">
The group <code>CLAUDE.md</code> is <strong>regenerated at every agent spawn</strong>. Editing it is a footgun: your changes will be overwritten. Edit files in <code>memory/</code> and <code>instructions.prepend.md</code> instead. The old IDENTITY.md/SOUL.md files from v1 are gone (they only appear as OpenClaw-migration artifacts).
</Notice>

### Systemd user service and logs

The installer creates a systemd **user** unit at `~/.config/systemd/user/nanoclaw-v2-<slug>.service` and enables lingering so the service survives SSH logout:

```bash
systemctl --user list-units 'nanoclaw-v2-*'
systemctl --user status nanoclaw-v2-<slug>
systemctl --user restart nanoclaw-v2-<slug>
loginctl show-user $USER | grep Linger   # should show Linger=yes
```

<Notice type="info" title="Logs are files, not journald">
NanoClaw logs to <code>logs/nanoclaw.log</code> and <code>logs/nanoclaw.error.log</code> in the project root. Do NOT use <code>journalctl</code>: the unit doesn't write to the journal. Use <code>tail -f logs/nanoclaw.log</code> instead.
</Notice>

Verify the service: status shows `active (running)`, `Linger=yes`, and a test message round-trips through the agent. If the unit isn't found, check the checkout slug matches. If the service dies at boot, you may have hit the update tripwire (see below).

For a non-root Docker setup inside containers, see the [non-root Docker user guide](/add-users-to-docker-container/). And if you're locking down the Docker host itself, [how I secured my Docker server after the BSI Hetzner report](/bsi-security-report-docker-ufw/) covers firewall and access rules.

### Backups

NanoClaw stores state in a handful of directories. Back these up:

<ListCheck>
<ul>
<li><code>groups/</code>: memory trees and workspaces</li>
<li><code>data/</code>: v2.db (messages, tasks) and v2-sessions</li>
<li><code>store/auth/</code>: WhatsApp session/keystore (the hard-to-replace bit)</li>
<li><code>.env</code>: provider config (keep this secret)</li>
<li><code>~/.config/nanoclaw/</code>: allowlists, account config</li>
</ul>
</ListCheck>

Exclude container images; they're re-pullable. A simple cron + tar + offsite copy works fine. For proper offsite backups, [mount an S3 bucket as a filesystem for backups](/s3-bucket-filesystem-vps/) with ZeroFS or JuiceFS. Restic or rclone to any S3-compatible endpoint works too.

### Updating NanoClaw and uninstalling

<Notice type="warning" title="Never git pull">
Raw <code>git pull</code> trips a boot-time version/commit/tree-hash check and NanoClaw refuses to start ("NanoClaw stopped: update did not go through the supported path"). Always use the supported update path.
</Notice>

Updates go through `/update-nanoclaw` in Claude Code. It's a staged transaction (7 phases) that creates a backup branch/tag before applying changes. To roll back:

```bash
pnpm exec tsx scripts/update-nanoclaw.ts rollback --id <transaction-id>
```

Stable channel is `v2026.10.0` (released 2026-10-09). Beta is `2026.10.1-rc.x`. Pin stable for production unless you need a beta fix. Update skills separately with `/update-skills`.

If you've already done a manual `git pull` and hit the tripwire, use the rollback command above or re-run `/update-nanoclaw` to reconcile.

Uninstall runs through the same script:

```bash
bash nanoclaw.sh --uninstall            # interactive, per-group confirmation
bash nanoclaw.sh --uninstall --dry-run  # preview what would happen
bash nanoclaw.sh --uninstall --yes      # skip confirmations
```

Uninstall is per-checkout scope. Your `.env` is backed up. The shared gateway and credentials at `~/.config/nanoclaw/` are left alone (other checkouts may use them). Other checkouts are untouched.

## Troubleshooting

NanoClaw is designed to be debugged through Claude Code, but you don't have to. The operator toolkit:

<Tabs>
<Tab name="Ask Claude (/debug)">
Run `/debug` in Claude Code. It analyzes logs, checks configuration, and suggests fixes. This is the fastest path for most issues. If it finds an issue likely affecting other users, you can contribute a fix to the setup skill.
</Tab>
<Tab name="Check it yourself">
```bash
tail -f logs/nanoclaw.log logs/nanoclaw.error.log

# For verbose output (mount configs + container stderr):
# Set LOG_LEVEL=debug in .env, restart the service

ncl groups list            # list agent groups
ncl sessions list          # container_status: running | stopped
ncl dropped-messages list  # what the router/access gate refused
ncl wirings list           # chat → agent routes
ncl tasks list             # scheduled tasks
docker ps                  # active agent containers
```

Note: containers run `--rm`, so the host log is the only surviving output after a container exits. The `ncl` CLI uses a Unix socket at `data/ncl.sock` (chmod 0600).
</Tab>
</Tabs>

**Circuit breaker**: after 6 consecutive container crashes, NanoClaw backs off startup for up to 15 minutes. Check `logs/nanoclaw.error.log` for the root cause before restarting.

If you see `FATAL: Container runtime failed to start`, run `docker info`. Docker isn't running or your user lacks access. Disk filling up after image pulls? [Clean up Docker overlay2 to reclaim disk space](/clean-docker-overlay2-dir/).

### Common issues

<Accordion label="WhatsApp disconnected or not pairing" group="troubleshooting" expanded="false">
Server-side logout can wipe `store/auth/`. Re-pair: QR codes have a 2-minute timeout, pairing codes about 60 seconds. If pairing keeps failing, delete `store/auth/` and re-run the WhatsApp adapter skill. Run `/debug` for a guided check.
</Accordion>

<Accordion label="Container runtime failed to start" group="troubleshooting" expanded="false">
Run `docker info` to confirm Docker is running and your user is in the `docker` group. On GCE VMs, sudo restrictions make NanoClaw unsupported. If you're running as root, switch to a non-root sudo user. After a reboot, Docker may start after NanoClaw. Add `After=docker.service` to the user unit if needed.
</Accordion>

<Accordion label="Agent never wakes up" group="troubleshooting" expanded="false">
Check `ncl sessions list` for `container_status`. Check `ncl dropped-messages list`: the access gate or router may have refused the message. Verify the sender is on the allowlist (`~/.config/nanoclaw/sender-allowlist.json`). Confirm `ncl wirings list` shows the chat routed to the right agent.
</Accordion>

<Accordion label="EgressLockdownError" group="troubleshooting" expanded="false">
You enabled `NANOCLAW_EGRESS_LOCKDOWN=true` but the gateway is unreachable. The container needs the gateway for all egress. Either fix the gateway (`onecli` service on `127.0.0.1:10254`) or remove the lockdown flag from `.env` and restart.
</Accordion>

<Accordion label="Service won't start after a manual git pull" group="troubleshooting" expanded="false">
The boot-time version/commit/tree-hash check refuses to start when the tree doesn't match a supported update transaction. Restore via `/update-nanoclaw` (reconciles the state) or use the rollback command with the last transaction ID. Don't try to bypass the check; it's there to prevent half-updated states.
</Accordion>

<Accordion label="Scheduled tasks not firing" group="troubleshooting" expanded="false">
Check `ncl tasks list` for task status. If a gate script is configured, it may be skipping the invocation (by design). Verify the cron recurrence timezone matches yours; tasks use the user's timezone, not UTC. The host sweep wakes containers on due ticks; if the service is down, missed ticks don't replay.
</Accordion>

<Accordion label="Slow responses or disk full" group="troubleshooting" expanded="false">
Container cold-start adds a few seconds per wake. That's the cost of isolation. For disk: run `df -h`, then `docker system prune` or see [Docker overlay2 cleanup](/clean-docker-overlay2-dir/). Agent images are large (Bun + Chromium + CLIs). If you're running multiple agent groups, image pulls add up. Budget 40 GB+ disk.
</Accordion>

## FAQ

<Accordion label="Frequently asked questions" group="faq" expanded="true">

**Why WhatsApp only?**

WhatsApp is the documented default, not the only option. The trunk ships the CLI channel; about 20 adapters (WhatsApp, Telegram, Discord, Slack, Teams, Signal, Matrix, and more) install via `/add-<channel>` skills. The design philosophy is fork-and-customize: run a skill to add what you need.

**Can I run this without Docker?**

No. Docker is the only shipped runtime. Container isolation is core to the security model: the agent runs inside containers, not as part of the main process. Apple Container on macOS is opt-in via `/convert-to-apple-container`, but Docker remains the default and required path.

**How is this different from just running Claude Code?**

Claude Code is an interactive CLI. NanoClaw is an always-on assistant you message from your phone. It has memory, scheduled tasks, and per-group context that persists across conversations. It runs unattended in a systemd service with container isolation.

**Can multiple people use one NanoClaw instance?**

Yes. Use separate groups for different people or trust domains; groups are isolated from each other. v2 has `user_roles` (owners/admins) and per-channel wiring to control who can talk to which agent. Your self-chat is the admin channel.

**What's the cost to run NanoClaw?**

VPS: about $5-10/month for a 4 GB box at [Hetzner](https://go.bitdoze.com/hetzner) or [Hostinger](https://go.bitdoze.com/hostinger-vps). Claude access: the default path is a Claude Pro/Max subscription (fixed monthly cost, you sign in via browser). If you use API keys, billing is usage-based. The actual number depends entirely on how much you interact with the agent. I don't quote token estimates; measure your own usage.

**Can I use a different LLM?**

Yes. v2 supports multiple providers: `/add-codex` (OpenAI), `/add-opencode` (OpenRouter, Google, DeepSeek), `/add-cursor` (Cursor Agent SDK), `/add-ollama-provider` (local models). Each group can use a different provider. For any Anthropic-compatible endpoint, set `ANTHROPIC_BASE_URL` in `.env`. For model recommendations, see [best open source models for OpenClaw](/best-opensource-models-for-openclaw/) and [running local models with Ollama](/openclaw-ollama-local-models/). If you want a non-Claude-Agent-SDK core entirely, [nanobot](/nanobot-setup-guide/), [NullClaw](/nullclaw-deploy-guide/), or [ZeroClaw](/zeroclaw-setup-guide/) are worth a look.

**How do I add Telegram/Discord/Slack?**

Run the appropriate skill in Claude Code:
```
/add-telegram
/add-slack
/add-discord
```
Adapters install from the `channels` branch. Each one wires up through the wizard.
