## DAS vs NAS: which one do you need?

A DAS (direct-attached storage) enclosure is just drive bays, a power supply, a fan, and a USB-to-SATA bridge on a cable. Your mini PC or server owns the filesystems, runs Samba or NFS, and manages redundancy. A NAS puts its own CPU, RAM, OS, and network ports inside the storage box so it can serve files to the network by itself.

| **Reboot isolation** | Rebooting the mini PC takes storage offline | Storage stays online while compute nodes reboot |
| **Setup & maintenance** | You configure mounts, MergerFS/ZFS, and Samba | Web GUI handles RAID, shares, and alerts |

I run this exact split in my own lab: a mini PC runs Docker, Jellyfin, and my self-hosted apps, and a USB DAS holds the bulk media drives. Because Jellyfin reads the disks locally over USB instead of pulling 4K remuxes across the network from a second machine, there is zero network bottleneck between the storage and the transcoder. For the NAS side of that math, see the [best NAS for Docker and Proxmox homelabs](/best-nas-homelab-docker-proxmox/) guide.

The honest counter-case: if you run a three-node Proxmox cluster that needs shared NFS/iSCSI storage to stay online while individual hosts reboot, or if you want a storage appliance you never have to administer via SSH, buy the NAS instead.

## JBOD vs hardware RAID: keep the RAID in software

Most multi-bay USB enclosures expose two ways to handle disks:

- **JBOD / Individual (Single) mode:** the USB bridge passes each physical drive through as a separate block device (`sdb`, `sdc`, `sdd`, `sde`). Your OS sees four independent disks.
- **Hardware RAID mode:** a small controller inside the enclosure combines the drives into a single virtual volume (RAID 0, 1, 5, or 10) configured with physical DIP switches on the back.

In a homelab, **always set the enclosure to JBOD/Individual mode** and manage redundancy in Linux. If a cheap enclosure's internal RAID controller dies three years from now, disks formatted under its proprietary metadata often cannot be read on a standard motherboard SATA port or a different brand's DAS. When the filesystem lives in the host OS, you can pull all four drives out of a dead enclosure, drop them into any other JBOD box or desktop case, and mount them immediately.

| Software stack on host | How it works | Best for | Mixed drive sizes? |
| --- | --- | --- | --- |
| **MergerFS + SnapRAID** | Unions plain ext4/XFS disks into one folder; nightly parity sync | Media libraries (Plex/Jellyfin) where files are written once | Yes (any size, as long as parity disk is ≥ largest data disk) |
| **mdadm (Linux RAID) + ext4/XFS** | Kernel block-level RAID 1/5/6/10 | General shared storage with real-time redundancy | No (sizes match smallest member) |
| **ZFS (RAIDZ1 / mirrors)** | Copy-on-write pool with bit-rot checksumming and snapshots | VM backups, photos, critical documents | Per-vdev sizing; requires clean disk serials |

## Day-one Linux setup: verify serials, UASP, SMART, and `nofail`

USB-attached storage has a few quirks that internal SATA ports don't. Run these four checks on your Linux host before copying terabytes onto the array:

### 1. Confirm unique disk serials (`by-id`)

Some cheap USB-to-SATA bridges rewrite drive serial numbers or present all four bays with the same bridge serial, which breaks ZFS and makes `/dev/sdX` letter shifts dangerous on reboot. Plug in the DAS with at least two drives installed and run:

```bash
ls -l /dev/disk/by-id/ | grep -v "part"
```

You should see each drive's real model and unique serial number (for example `ata-ST12000VN0008-...` and `wwn-0x5000c500...`) pointing to `../../sdb`, `../../sdc`, etc. Always reference `/dev/disk/by-id/...` or filesystem `UUID=` when building pools or `/etc/fstab` entries — never raw `/dev/sdb` letters.

### 2. Check UASP (`uas`) mode and 10Gbps link speed

Verify the enclosure connected on a SuperSpeed+ (10000M) bus using the `uas` (USB Attached SCSI) driver rather than legacy `usb-storage`:

```bash
lsusb -t
```

Look for `Driver=uas, 10000M` on the port holding the DAS. UASP enables command queuing (NCQ) over USB, which makes multi-disk reads and SnapRAID scrubs much smoother.

### 3. Verify SMART passthrough (`smartctl`)

Most modern USB bridges pass SMART data through when queried with `-d sat`:

```bash
sudo smartctl -a -d sat /dev/sdb
```

Confirm you can read `Temperature_Celsius`, `Reallocated_Sector_Ct`, and `Power_On_Hours`. If that works, add `-d sat` to your `/etc/smartd.conf` rules so your server alerts you before a disk dies.

### 4. Mount with `nofail` in `/etc/fstab`

If a normal `/etc/fstab` disk is missing at boot — say the DAS power brick was unplugged or took an extra three seconds to spin up — systemd drops your mini PC into an emergency shell with SSH offline. Always include `nofail` (and `x-systemd.device-timeout=30s`) on USB DAS mounts:

```ini
# /etc/fstab example for individual disks + MergerFS
UUID=1111-aaaa /mnt/disk1 ext4 defaults,nofail,x-systemd.device-timeout=30s 0 2
UUID=2222-bbbb /mnt/disk2 ext4 defaults,nofail,x-systemd.device-timeout=30s 0 2
/mnt/disk*     /mnt/storage fuse.mergerfs defaults,nonempty,allow_other,use_ino,cache.files=off,moveonenospc=true,category.create=mfs,nofail 0 0
```

Once mounted, expose `/mnt/storage` to your LAN with [Samba](/setup-samba-linux/) or [NFS](/setup-nfs-linux/), pass it into your [Docker containers](/docker-containers-home-server/) or [self-hosted Jellyfin](/self-host-jellyfin/) stack, and put both the mini PC and the DAS power brick on the battery side of a [home server UPS](/best-ups-for-home-server/).

## FAQ

<Accordion label="What is a DAS enclosure?" group="faq" expanded="true">
A DAS (direct-attached storage) enclosure is a multi-bay hard drive box that plugs directly into one computer over USB, eSATA, or Thunderbolt. Unlike a NAS, it has no CPU, RAM, OS, or Ethernet port of its own — the host computer manages the filesystems and network shares.
</Accordion>

<Accordion label="Is a DAS or NAS better for a homelab?" group="faq">
If you already run a 24/7 mini PC or home server, a DAS is usually better value: your existing server handles Docker, Jellyfin, and SMB/NFS shares, so you only pay for drive bays instead of a second computer. A NAS is better when multiple servers need storage that stays online across host reboots, or when you want a zero-Linux-admin appliance.
</Accordion>

<Accordion label="Should I use the enclosure's built-in hardware RAID?" group="faq">
No. Set the enclosure to JBOD/Single mode and manage redundancy in your host OS using MergerFS + SnapRAID, ZFS, or Linux mdadm. Software arrays can be moved to any other enclosure or SATA controller if the DAS box fails; cheap hardware RAID controllers lock your drives to that specific bridge chip.
</Accordion>

<Accordion label="Can you run ZFS or TrueNAS over a USB DAS?" group="faq">
It works in a homelab if the enclosure's USB bridge passes unique disk serial numbers (`/dev/disk/by-id/`) and doesn't drop links under load, though ZFS purists prefer direct SATA/SAS HBA connections. If you run ZFS on a USB DAS, verify `by-id` serials first, use a short high-quality USB-C cable, and run a full `zpool scrub` stress test before trusting it with live data.
</Accordion>

<Accordion label="Can I monitor hard drive SMART health over USB?" group="faq">
Yes on most modern 10Gbps USB-SATA bridges, including the TerraMaster D4-320 and Sabrent DS-SC4B. Run `sudo smartctl -a -d sat /dev/sdX` on Linux to confirm temperature and sector counters come through.
</Accordion>

<Accordion label="How fast is a 10Gbps USB DAS with four hard drives?" group="faq">
A 10Gbps USB 3.2 Gen 2 link delivers roughly 1,000–1,050 MB/s of real-world throughput shared across all four bays. Since a modern 3.5-inch 7200 RPM hard drive peaks around 250–270 MB/s, four HDDs can all read at full speed simultaneously without hitting the USB ceiling.
</Accordion>
