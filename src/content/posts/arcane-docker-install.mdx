### Install Docker

If you don't have Docker yet, use Docker's convenience script. It detects the distro and sets up the right repo:

```bash
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER
# log out and back in for the group to apply
```

Verify both the engine and the Compose plugin:

```bash
docker version
docker compose version
```

Broken looks like `permission denied while trying to connect to the Docker daemon socket`. That means the group membership hasn't kicked in yet. Re-login, don't fight it with `sudo` forever. Full walkthrough: [Install Docker & Docker-compose for Ubuntu](/install-docker-ubuntu-arm/).

## Install Arcane with Docker Compose

There are two ways to install Arcane. The convenience script is the fastest, but I prefer the compose method because you can see and control exactly what's happening.

### Quick install (convenience script)

If you want to get running in 30 seconds:

```bash
curl -fsSL https://getarcane.app/install.sh | sudo bash
```

<Notice type="info" title="This is a native install, not a container">
The install script sets up Docker (if missing), downloads the native Arcane binary from GitHub Releases, and registers a systemd service. It symlinks the binary to `/usr/local/bin/arcane`. It does not pull a container image or write a compose file for you. Good for testing; use Compose for a permanent setup so you own the config.
</Notice>

Check it:

```bash
systemctl status arcane
```

Then open `http://your-server-ip:3552`. To remove it later there's an uninstaller. It's interactive, and `--force --remove-all` will take Docker with it, so read the prompts:

```bash
curl -fsSL https://getarcane.app/uninstall.sh | sudo bash
```

### Docker Compose install (recommended)

First, create a directory for Arcane:

```bash
mkdir -p /opt/arcane
cd /opt/arcane
```

Generate the `ENCRYPTION_KEY`:

```bash
openssl rand -hex 32
```

Official alternatives if you prefer Arcane's own generator:

```bash
docker run --rm ghcr.io/getarcaneapp/manager:latest /app/arcane generate secret
# or: arcane-cli generate secret
```

Now create your `compose.yaml`:

```yaml
services:
  arcane:
    image: ghcr.io/getarcaneapp/manager:v2
    container_name: arcane
    ports:
      - "3552:3552"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - arcane-data:/app/data
      - /opt/stacks:/opt/stacks
    environment:
      - APP_URL=http://localhost:3552
      - PUID=1000
      - PGID=1000
      - ENCRYPTION_KEY=your-generated-encryption-key
      - PROJECTS_DIRECTORY=/opt/stacks
      - TZ=Europe/Bucharest
    cgroup: host
    healthcheck:
      test: ["CMD", "./arcane", "health", "--timeout", "2s"]
      interval: 10s
      timeout: 3s
      retries: 5
      start_period: 15s
    restart: unless-stopped
    stop_grace_period: 15s
volumes:
  arcane-data:
```

Replace `ENCRYPTION_KEY` with the value you generated. Set `APP_URL` to your actual server address if you're accessing it remotely. The `cgroup: host` line lets Arcane detect its own container ID, which matters for self-upgrades.

A few notes on that file:

- Pin the image tag. `:v2` gets you patch releases on the 2.x line. `:latest` can surprise you on a Monday morning. Rollback is the reverse: re-pin the previous tag (`v2.16.1` or whatever you were on), then `docker compose pull && docker compose up -d`. See [how to update a container with Docker Compose](/updating-container-docker-compose/) for the full dance.
- The `healthcheck` and `stop_grace_period: 15s` lines come from the official examples. The healthcheck gives `depends_on` something real to gate on once you add a socket proxy.
- Optional mounts: `/builds` for Arcane's Build Workspace (image builds) and `/backups` for exported backups. Add them if you use those features.
- Secrets: every sensitive variable supports the `_FILE` suffix if you'd rather read from a mounted file than pass values inline. See [Docker Compose secrets](/docker-compose-secrets/) for patterns that work with Compose.

<Notice type="info" title="What happened to JWT_SECRET?">
Arcane 2.x signs session tokens with an ML-DSA-87 key it generates and stores itself (ML-DSA-87 is the NIST FIPS 204 post-quantum signature scheme, shipped in Arcane 2.10.0), so `JWT_SECRET` is no longer used. If your compose file still sets it, Arcane logs a warning at startup. Remove it. Same story for the image name: `ghcr.io/getarcaneapp/arcane` is the old name, `ghcr.io/getarcaneapp/manager` is the current one.
</Notice>

<Notice type="warning" title="Stay off v3 tags">
Docker Hub has `v3-beta` tags as of October 2026. They're beta. For anything you care about, pin `v2` (or `v2.17`) and let the v3 crowd find the sharp edges.
</Notice>

<Notice type="info" title="Volume paths">
Identical host and container paths are still the recommendation when Arcane should manage existing compose projects (e.g. `/opt/stacks:/opt/stacks`). It's not a hard requirement anymore: Arcane reads its own container mounts and translates project paths to host paths. If you want to state the mapping yourself, set `PROJECTS_DIRECTORY=<containerPath>:<hostPath>`. Compose files with relative paths resolve correctly either way once the mapping is right.
</Notice>

Start it up:

```bash
docker compose up -d
```

### Verify the installation

Don't skip this. Two minutes here saves a debugging session later.

<ListCheck>
<ul>
<li><code>docker compose ps</code> shows the container as <code>healthy</code> (the healthcheck does its job within ~15s of start)</li>
<li><code>curl -s http://localhost:3552/health</code> returns a health payload from inside the box</li>
<li>Open <code>http://your-server-ip:3552</code>, log in with <code>arcane</code> / <code>arcane-admin</code></li>
<li><code>docker compose logs -f arcane</code> is quiet. No warnings about <code>JWT_SECRET</code> or missing keys</li>
</ul>
</ListCheck>

<Notice type="info" title="First login forces a password change">
Arcane asks you to change the default password the first time you sign in. This is forced, not a suggestion. If you somehow still have `arcane-admin` as the password after first login, something went wrong.
</Notice>

If the container is restarting in a loop, the first thing to check is `ENCRYPTION_KEY`. An empty or malformed value is the usual culprit. If nothing listens on 3552 at all, check the firewall or your provider's security group before blaming Arcane. Both cases are covered in Troubleshooting at the end.

## Hardening: Docker socket proxy

Mounting the Docker socket directly gives Arcane full control over your Docker daemon. That's a security risk. If Arcane gets compromised somehow, an attacker has root-equivalent access to your host. The socket is a root-level API dressed up as a Unix file.

The fix is a socket proxy that filters which Docker API calls Arcane can make. The shape:

<Accordion label="Why use a socket proxy?" group="security" expanded="true">

The Docker socket (`/var/run/docker.sock`) is essentially a root-level API. Any container with access to it can create privileged containers, mount the host filesystem, or run arbitrary commands as root on the host.

A socket proxy sits between Arcane and the Docker daemon. It intercepts API calls and only allows the ones you've explicitly permitted. You get the management functionality without handing over the keys to the kingdom.

This setup is recommended for any internet-facing server, and it's the layout Arcane's own docs suggest for SELinux and hardened hosts. For a homelab behind a firewall, direct socket mounting is probably fine. If your box is internet-facing, pair this with the other boring layers too: [how I secured my Docker server after the BSI report](/bsi-security-report-docker-ufw/) and [how to protect an internet-facing VPS with CrowdSec](/crowdsec-secure-server/).

</Accordion>

Arcane's docs now recommend **wollomatic/socket-proxy** as the default. It's what the official Instance Generator produces. If you already run Tecnativa's docker-socket-proxy, keep it; the corrected allowlist is in Option 2. For new setups, use Option 1.

### Option 1: wollomatic socket proxy (recommended)

The generator writes this file for you. Here's the shape so you know what you're deploying:

```yaml
services:
  arcane:
    image: ghcr.io/getarcaneapp/manager:v2
    container_name: arcane
    ports:
      - "3552:3552"
    volumes:
      - arcane-data:/app/data
      - /opt/stacks:/opt/stacks
    environment:
      - APP_URL=https://arcane.yourdomain.com
      - PUID=1000
      - PGID=1000
      - ENCRYPTION_KEY=your-generated-encryption-key
      - PROJECTS_DIRECTORY=/opt/stacks
      - TZ=Europe/Bucharest
      - DOCKER_HOST=tcp://docker-socket-proxy:2375
    cgroup: host
    depends_on:
      docker-socket-proxy:
        condition: service_healthy
    networks:
      - arcane-net
    restart: unless-stopped
    stop_grace_period: 15s

  docker-socket-proxy:
    image: wollomatic/socket-proxy:1.13.1
    container_name: arcane-docker-proxy
    user: "0:0"
    command:
      - "-listenip=0.0.0.0"
      - "-allowfrom=arcane,arcane-upgrader"
      - "-allowhealthcheck"
      # method+path allow rules (allowGET/allowPOST/allowPUT/allowDELETE)
      # go here. See the note below before starting this
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
    read_only: true
    cap_drop: [ALL]
    security_opt: ["no-new-privileges:true"]
    healthcheck:
      test: ["CMD", "./healthcheck"]
      interval: 2s
      timeout: 5s
      retries: 15
    networks:
      - arcane-net
    restart: unless-stopped

networks:
  arcane-net:
    driver: bridge

volumes:
  arcane-data:
```

About the allow rules: wollomatic is deny-by-default, so without them Arcane can't do anything. The rules are method+path pairs passed as flags (syntax shape: `-allowGET=/v1.*/containers/*`). The full current list is version-specific and lives in [Arcane's socket-proxy docs](https://getarcane.app/docs/security/socket-proxy). The [Instance Generator](https://getarcane.app/generator) writes the complete command block for you. Use one of those two sources rather than a list copied from a blog post (including this one).

Three things that matter in that config:

- `-allowfrom=arcane,arcane-upgrader` needs both names. `arcane-upgrader` is the alias Arcane's self-upgrade helpers use.
- The socket is mounted `:ro`, and the proxy container runs `read_only` with all capabilities dropped and `no-new-privileges`. The proxy is the only container that touches the socket; Arcane talks to it over the internal bridge network.
- `DOCKER_HOST=tcp://docker-socket-proxy:2375` on the Arcane side is the whole switch: Arcane never mounts the socket itself.

<Notice type="warning" title="Existing installs: add arcane-upgrader and recreate">
If you set up wollomatic earlier with only `-allowfrom=arcane`, self-upgrade helpers will get blocked. Add `arcane-upgrader` to the allowlist and recreate the proxy container: `docker compose up -d --force-recreate docker-socket-proxy`. The first upgrade after migrating should go through a normal Compose pull + recreate so you don't get a half-blocked helper mid-upgrade.
</Notice>

Verify the switch worked:

```bash
docker compose ps          # proxy shows healthy
docker compose logs arcane # no Docker API errors in the UI's log stream
```

Then click around the UI: container list loads, logs stream, terminal opens. Each of those is an API path the allowlist has to permit. If something worked before the switch and doesn't after, you're missing an allow rule.

```yaml
services:
  arcane:
    image: ghcr.io/getarcaneapp/manager:v2
    container_name: arcane
    ports:
      - "3552:3552"
    volumes:
      - arcane-data:/app/data
      - /opt/stacks:/opt/stacks
    environment:

      - PUID=1000
      - PGID=1000
      - ENCRYPTION_KEY=your-generated-encryption-key
      - PROJECTS_DIRECTORY=/opt/stacks
      - DOCKER_HOST=tcp://docker-socket-proxy:2375
    cgroup: host
    depends_on:
      - docker-socket-proxy
    networks:
      - arcane-net
    restart: unless-stopped

  docker-socket-proxy:
    image: tecnativa/docker-socket-proxy:latest
    container_name: arcane-socket-proxy
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
    environment:
      - EVENTS=1
      - PING=1
      - VERSION=1
      - POST=1
      - AUTH=0
      - SECRETS=0
      - BUILD=0
      - COMMIT=0
      - CONFIGS=0
      - CONTAINERS=1
      - DISTRIBUTION=1
      - EXEC=1
      - IMAGES=1
      - INFO=1
      - NETWORKS=1
      - NODES=0
      - PLUGINS=0
      - SERVICES=0
      - SESSION=0
      - SWARM=0
      - SYSTEM=1
      - TASKS=0
      - VOLUMES=1
    networks:
      - arcane-net
    security_opt:
      - no-new-privileges:true
    restart: unless-stopped

networks:
  arcane-net:
    driver: bridge

volumes:
  arcane-data:
```

Arcane no longer mounts the Docker socket directly. It connects to the proxy via `DOCKER_HOST=tcp://docker-socket-proxy:2375`. The socket is mounted read-only on the proxy, and both containers sit on an internal bridge network.

The flags control which Docker API endpoint groups are reachable. This set is what Arcane's docs currently recommend, with Swarm, auth, and secrets off. If you use Arcane's Swarm read access, flip `SWARM`, `SERVICES`, `TASKS`, and `NODES` to `1`. Keep `AUTH=0` and `SECRETS=0` unless you have a specific reason not to.

## Setting up OIDC/SSO

If you're already running an identity provider like Authentik, Keycloak, or Authelia, you can hook Arcane into it for single sign-on.

<Tabs>
  <Tab name="Via the web UI">
    Go to **Settings → Authentication** in Arcane. Enter your client ID, client secret, and issuer URL (no trailing slash). Arcane discovers the endpoints from the provider's `.well-known/openid-configuration` page. The redirect URI is:

    ```
    https://your-arcane-url/auth/oidc/callback
    ```

    Save and test the connection. Users who authenticate via OIDC are auto-provisioned on first login, and you can disable local password login entirely once it works.
  </Tab>

  <Tab name="Via environment variables">
    Add these to your compose file:

    ```yaml
    environment:
      - OIDC_ENABLED=true
      - OIDC_CLIENT_ID=your-client-id
      - OIDC_CLIENT_SECRET=your-client-secret
      - OIDC_ISSUER_URL=https://your-idp.example.com
      - OIDC_SCOPES=openid email profile groups
      - OIDC_GROUPS_CLAIM=groups
      - OIDC_ROLE_MAPPINGS=[{"claimValue":"arcane-admins","roleId":"role_admin"}]
    ```

    `OIDC_GROUPS_CLAIM` tells Arcane where group membership lives in the token (`realm_access.roles` for Keycloak, `memberOf` for Azure AD). `OIDC_ROLE_MAPPINGS` binds a claim value to an Arcane role, with an optional `environmentId` to scope it. Mappings set this way are reconciled on every boot and are read-only in the UI; it also supports the `_FILE` suffix for Docker secrets.

    Older guides mention `OIDC_ADMIN_CLAIM` and `OIDC_ADMIN_VALUE`. Those are gone in 2.x, replaced by the role-mappings setup above.
  </Tab>
</Tabs>

Once the basics work, the variables worth knowing about:

- `OIDC_AUTO_REDIRECT_TO_PROVIDER=true` skips the local login form entirely. Before you flip it, confirm the emergency login page `https://your-arcane-url/login/backup` works. That's your escape hatch if the IdP goes down.
- `OIDC_MERGE_ACCOUNTS` links an OIDC identity to an existing local account by email. Since 2.16.0 the merge requires a **verified** email from the provider, which is the behavior you want.
- `OIDC_SKIP_TLS_VERIFY` exists for lab IdPs with self-signed certs. Don't set it in production.
- Provider name/logo variables and manual endpoint overrides are available for non-discovery providers.

<Notice type="warning" title="Don't quote values in list-form environment blocks">
In Compose's list syntax (`- KEY=value`), wrapping the value in quotes makes the quotes part of the value. `OIDC_ISSUER_URL="https://idp.example.com"` will break discovery. This bites everyone once. The JSON in `OIDC_ROLE_MAPPINGS` is the exception: the JSON braces are fine unquoted in list form.
</Notice>

Verify: log in through the IdP once, confirm the user lands in Arcane with the right role, then (and only then) consider disabling local login.

## Reverse proxy setup

You'll want a reverse proxy in front of Arcane for SSL and a clean domain name. Arcane uses WebSockets for real-time updates, so your proxy config needs to support that.

<Tabs>
  <Tab name="Nginx">

```nginx
server {
    listen 443 ssl http2;
    server_name arcane.yourdomain.com;

    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;

    location / {
        proxy_pass http://127.0.0.1:3552;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

The key lines are `proxy_http_version 1.1` and the `Upgrade` / `Connection` headers. Without them, WebSocket connections fail and the UI won't get live updates.

  </Tab>

  <Tab name="Traefik">
    If you're already running Traefik (and you probably should be for Docker setups), add labels to your Arcane service:

    ```yaml
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.arcane.rule=Host(`arcane.yourdomain.com`)"
      - "traefik.http.routers.arcane.entrypoints=websecure"
      - "traefik.http.routers.arcane.tls.certresolver=letsencrypt"
      - "traefik.http.services.arcane.loadbalancer.server.port=3552"
    ```

    Traefik handles WebSocket upgrade automatically. If you'll run **Edge agents on `auto`/`grpc` transport**, two more things are required (see the Remote hosts section): an h2c route for `/api/tunnel/connect`, and the websecure entrypoint's read timeout disabled:

    ```yaml
    # Traefik static/command config: entrypoint level, not router level
    - "--entrypoints.websecure.transport.respondingtimeouts.readtimeout=0s"
    ```

    The default 60s read timeout kills the gRPC tunnel. Full Traefik setup guide: [How to use Traefik as a reverse proxy in Docker](/traefik-proxy-docker/).
  </Tab>

  <Tab name="Cloudflare Tunnels">
    If you don't want to expose ports at all, Cloudflare Tunnels work well. Point a tunnel at `http://localhost:3552` and Cloudflare handles SSL and routing. WebSocket support is automatic.

    This is what I use on my homelab since I don't want to open any ports on my router. If you add Edge agents behind a Cloudflare tunnel, set `EDGE_TRANSPORT=poll` on the agent. Polling works fine through the tunnel; long-lived gRPC through CF is something I wouldn't bet on without testing.
  </Tab>
</Tabs>

<Notice type="warning" title="Set TRUSTED_PROXIES">
Since 2.16.0 Arcane only extracts client IPs from proxies you explicitly trust. Behind any reverse proxy, set `TRUSTED_PROXIES` to your proxy network's CIDR (e.g. `TRUSTED_PROXIES=172.18.0.0/16` for the Docker bridge your proxy joins). Without it, login rate-limiting and IP logging misbehave: you'll see the proxy's IP everywhere and rate limits trigger on the wrong identity. And while we're here: [Docker can bypass your firewall rules](/docker-bypasses-firewall/), so don't rely on UFW alone to keep 3552 closed.
</Notice>

Update the `APP_URL` environment variable in your compose file to match your actual domain (e.g., `https://arcane.yourdomain.com`, no `:3552`; the proxy terminates the port).

If you'd rather skip the reverse proxy entirely, Arcane can serve TLS itself: set `TLS_ENABLED=true`, `TLS_CERT_FILE`, and `TLS_KEY_FILE`. It speaks HTTP/2 over TLS directly. Fine for a lab; I still prefer a proxy in front.

If you installed an older version of this stack, the agent used to be called `arcane-headless`; the current image is `ghcr.io/getarcaneapp/agent` and the binary is `arcane-agent`. Update old compose files to the new names.

**Direct** means the manager reaches out to the agent on TCP port 3553. **Edge** means the agent dials out to the manager over an mTLS tunnel, so the remote host needs no open inbound port. Edge is the one you want for anything behind NAT or a firewall. The mTLS setup is documented at [Arcane's edge-mTLS docs](https://getarcane.app/docs/security/edge-mtls).

Either way, create the environment first: open **Environments → Add Environment** in the Arcane UI, pick Direct or Edge, and it generates the token and a ready-to-run snippet for you. The Edge compose looks like this:

```yaml
services:
  arcane-edge-agent:
    image: ghcr.io/getarcaneapp/agent:v2
    container_name: arcane-edge-agent
    environment:
      - EDGE_AGENT=true
      - EDGE_TRANSPORT=poll
      - AGENT_TOKEN=arc_your-generated-token
      - MANAGER_API_URL=https://arcane.yourdomain.com
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - agent-data:/app/data
    cgroup: host
    restart: unless-stopped
    stop_grace_period: 15s
volumes:
  agent-data:
```

`EDGE_TRANSPORT` options:

| Value | Behavior | When to use |
|---|---|---|
| `poll` | Agent checks in periodically; no persistent tunnel | NAT, Cloudflare tunnels, flaky links. Generated snippets use this |
| `auto` | Continuous gRPC tunnel with WebSocket fallback (default when unset) | Stable networks where you want instant push |
| `websocket` | Continuous WebSocket tunnel | Proxies that choke on gRPC |
| `grpc` | Continuous gRPC tunnel | Direct connections, or Traefik with h2c + read timeout disabled |

On poll environments you'll see statuses **Online / Standby / Pending / Offline** in the connection view. **Standby means healthy**: the agent is idle waiting for the next poll, not down. The first action against an idle poll environment can take a moment while the connection wakes up. Set expectations before you assume it's broken.

The agent can also run as a standalone binary if you don't want a container on the remote host.

One ops detail to avoid confusion: there are two different "Update All" buttons. **Updates → Update All** updates containers and projects. **Environments → Update All** upgrades the agents first, then the manager. Fleet upgrades are a single click instead of a per-host chore.

## Running Arcane on Podman

New in 2.17.0 (October 21, 2026): Arcane manages Podman natively. If your hosts run Podman instead of Docker, this is the first release where the support is real rather than experimental.

The repo ships the examples: `compose.podman-rootful.yaml`, `compose.podman-rootless.yaml`, and quadlet files under `docker/examples/quadlet/`. The practical differences from the Docker install are the socket path (Podman's socket, rootless vs rootful) and the rootless permission model. There's also a dedicated docs section (`docs/podman/`) covering quadlets, kube, secrets, and auto-update.

<Notice type="info" title="Quadlet-managed containers skip Arcane auto-updates">
Deliberately. Containers owned by systemd quadlets would lose their systemd unit if Arcane recreated them, so Arcane leaves them alone. For those, use Podman's own auto-update mechanism (`podman auto-update` + the `io.containers.autoupdate` label).
</Notice>

This support is weeks old as of writing. I'd use it on a lab host now and wait a couple of release cycles before moving a production Podman fleet onto it. If you're still deciding on the container engine itself, here's [how Podman compares to Docker](/podman-vs-docker/).

## Environment variables reference

These are the variables I reach for most. For the full picture of how Docker passes config into containers, see [how Docker environment variables work](/docker-env-vars/).

| Variable | Default | What it does |
|---|---|---|
| `APP_URL` | `http://localhost:3552` | Public URL for the instance (set this to your real domain behind a proxy) |
| `PUID` / `PGID` | `65532:65532` | User/group ID for file permissions. Images start as root to prepare, then drop to this user |
| `ENCRYPTION_KEY` | none | Required. 32-byte key for encrypting sensitive data |
| `PROJECTS_DIRECTORY` | `/app/data/projects` | Where Arcane looks for compose projects. Accepts `<containerPath>:<hostPath>` mapping form |
| `DOCKER_HOST` | `unix:///var/run/docker.sock` | Docker connection. Use `tcp://` for socket proxy |
| `TZ` | container default | Timezone. Matters for cron schedules (backups, auto-update windows) |
| `TRUSTED_PROXIES` | unset | CIDR of proxies allowed to set client IPs. Required behind any reverse proxy (2.16+) |
| `TLS_ENABLED` / `TLS_CERT_FILE` / `TLS_KEY_FILE` | unset | Serve HTTPS directly, no reverse proxy |
| `DATABASE_URL` | SQLite | External database connection string |
| `JWT_REFRESH_EXPIRY` | `168h` | Refresh token lifetime |
| `ADMIN_STATIC_API_KEY` | unset | Static API key for automation |
| `TRIVY_SECURITY_OPTS` / `TRIVY_PRIVILEGED` | unset | Tune Trivy scanning behavior |
| `GIT_WORK_DIR` / `SSH_KNOWN_HOSTS` | built-in | GitOps workspace and SSH host verification |
| `http_proxy` / `https_proxy` / `no_proxy` | unset | Outbound proxy for image pulls and API calls (lowercase) |
| `LOG_LEVEL` | `info` | Logging verbosity |
| `UI_CONFIGURATION_DISABLED` | `false` | Force config via env vars only. Settings-override env vars are only honored when this is `true` (or `AGENT_MODE=true`) |

`JWT_SECRET` still shows up in old docs and compose files but is unused in 2.x. Leave it unset. GPU monitoring variables (`GPU_MONITORING_ENABLED`, `GPU_TYPE`) appear in some older guides but are absent from the current `.env.example`. Check your version's environment-variables doc before relying on them.

## Troubleshooting

<Accordion label="Arcane can't see my existing compose stacks" group="troubleshoot" expanded="true">

Identical host/container paths are still the recommendation. If your compose files live at `/opt/stacks/myapp/compose.yaml`, the simple setup is:

```yaml
volumes:
  - /opt/stacks:/opt/stacks
```

with `PROJECTS_DIRECTORY=/opt/stacks`.

That said, path mismatch is no longer fatal. Arcane reads its own container mounts and translates project paths to host paths. If your mapping is unusual, state it explicitly:

```yaml
environment:
  - PROJECTS_DIRECTORY=/app/data/projects:/opt/stacks
```

Format is `<containerPath>:<hostPath>`. If stacks still don't appear after this, check that the mount exists in the container (`docker exec arcane ls /opt/stacks`) before blaming the mapping.

</Accordion>

<Accordion label="WebSocket errors or UI not updating live" group="troubleshoot">

Your reverse proxy isn't forwarding WebSocket connections. Make sure you have the upgrade headers set. For Nginx, you need:

```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";
```

</Accordion>

<Accordion label="Permission denied on Docker socket" group="troubleshoot">

Either add your user to the `docker` group (`sudo usermod -aG docker $USER`) or make sure the `PUID`/`PGID` values in the compose file match a user with Docker access. Inside the container, files created on bind mounts get the PUID/PGID ownership. Pick IDs that match the user who owns your stacks. For containers you build yourself, see [how to add a non-root user to a Docker container](/add-users-to-docker-container/).

</Accordion>

<Accordion label="Still using the old image or JWT_SECRET" group="troubleshoot">

If your compose references `ghcr.io/getarcaneapp/arcane` or sets `JWT_SECRET`, update to `ghcr.io/getarcaneapp/manager` and drop the JWT line. Arcane starts anyway but logs warnings, and the old image name is gone from current examples and registries.

</Accordion>

<Accordion label="Self-upgrade fails after switching to a socket proxy" group="troubleshoot">

The upgrade helper container is labeled `arcane-upgrader`. If your wollomatic allowlist only has `-allowfrom=arcane`, the helper gets blocked mid-upgrade. Add `arcane-upgrader` to `-allowfrom`, then recreate the proxy:

```bash
docker compose up -d --force-recreate docker-socket-proxy
```

Do the first upgrade after that migration through a normal Compose pull + recreate so you're not relying on the helper while the allowlist is settling.

</Accordion>

<Accordion label="Login rate limits trigger on the wrong IP" group="troubleshoot">

You're behind a reverse proxy and `TRUSTED_PROXIES` isn't set. Arcane (since 2.16.0) only trusts client IPs from configured proxies. Without it, every request looks like it comes from the proxy address, so rate limiting and IP logs are wrong. Set `TRUSTED_PROXIES` to the proxy network CIDR (e.g. `172.18.0.0/16`) and restart.

</Accordion>

<Accordion label="Edge agent stuck in Pending or won't connect through Traefik" group="troubleshoot">

Three checks, in order:

1. `AGENT_TOKEN` and `MANAGER_API_URL` match the environment you created in the UI (regenerate the snippet if unsure).
2. On Traefik with `EDGE_TRANSPORT=auto` or `grpc`: route `/api/tunnel/connect` as h2c and set `--entrypoints.websecure.transport.respondingtimeouts.readtimeout=0s`. The default 60s read timeout drops the tunnel.
3. Behind Cloudflare or any path that dislikes long-lived connections, use `EDGE_TRANSPORT=poll`.

Also: **Standby is not down.** A poll-mode agent sitting in Standby is healthy and idle.

</Accordion>

## What I like and what's missing

I've run Arcane long enough to have opinions now.

The GitOps integration is the feature I use most. I keep my compose files in a private Git repo, and when I push changes, Arcane picks them up and redeploys. No webhook config, no CI pipeline needed.

The REST API is the other one I lean on. I wrote a small script that checks container health and restarts anything that's unhealthy. Took about 20 minutes because the API is straightforward.

The gaps I complained about in the first version of this guide have mostly closed: Trivy scanning, scheduled auto-updates, and backups all shipped in the 2.9 to 2.12 releases, and 2.14 to 2.17 added the processes tab, a risk-based security view, and registry browsing. The new **Update Delay** is the piece I'd turn on for anything internet-facing. It's a supply-chain cool-down so a freshly published malicious tag doesn't get pulled the second it appears:

```yaml
x-arcane:
  updater:
    delay: 72          # project default, hours
services:
  cache:
    image: redis:7
    x-arcane:
      updater:
        delay: 0       # opt a service out of the cool-down
# or label: com.getarcaneapp.arcane.updater.delay=72
```

What's still missing as of v2.17.1: Dockhand-style scan-before-swap gating, where an update only proceeds if the new image scans clean (not in the docs at the time of writing), and a proper file browser inside containers. Neither is a dealbreaker, but both would make Arcane easier to live with. If auto-updates are your thing generally, [Tugtainer's auto-update approach](/tugtainer-docker-autoupdate/) is worth reading too.

If you want those specific features today, take a look at [how to install Dockhand](/dockhand-docker-install/). And for the wider field, my [Portainer alternatives comparison](/portainer-alternatives/) covers Sencho, Dockge, Komodo, and the rest.
