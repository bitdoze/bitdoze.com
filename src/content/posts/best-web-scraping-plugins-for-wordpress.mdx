## How to scrape a website to WordPress without a plugin

Before you pay for a plugin, consider keeping the scraping **off** the WordPress box entirely. A WordPress content scraper that runs inside your site couples three failure domains: target-site changes, PHP resource limits, and your production database. An external scraper that posts via the WordPress REST API (`/wp-json/wp/v2/posts` with an application password) handles JavaScript-heavy targets better than any plugin here and fails safely: the worst case is a rejected request, not a half-written post.

Two routes work well: a self-hosted n8n workflow, or a cron'd Python/Playwright script.

**Prerequisites:**

<ListCheck>
<ul>
<li>WordPress application password created (Users → Profile → Application Passwords (your site needs HTTPS))</li>
<li><code>curl</code> and <code>xmllint</code> installed (or Python 3 + Playwright for the script route)</li>
<li>Target site's robots.txt and ToS checked</li>
<li>A backup taken before the first automated post lands</li>
</ul>
</ListCheck>

<Tabs>
<Tab name="n8n (no-code)">
n8n gives you a visual workflow: an HTTP Request or HTML Extract node fetches and parses the target page, then a WordPress node (or a plain HTTP Request node) posts to `/wp-json/wp/v2/posts`. Scheduling is built in, so you don't touch WP-Cron at all.

If you already run Docker, [self-host n8n for scraping and posting workflows](/n8n-self-host-workflow-automation/). It takes about ten minutes and keeps the workflow editor on your own box.

The n8n route is the one I'd pick for non-developers: you see each step, you can replay a single node for debugging, and a broken selector fails in n8n instead of publishing an empty post.
</Tab>
<Tab name="Python + Playwright (code)">
For JS-heavy targets, Playwright is the honest answer: it renders the page like a real browser, waits for selectors, and extracts what you need. Keep the script out of WordPress's document root, run it from cron, and post via the REST API.

```python
import requests
from playwright.sync_api import sync_playwright

WP = "https://yoursite.com"
AUTH = ("admin", "xxxx-xxxx-xxxx-xxxx")  # application password

with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.goto("https://example.com/target-page")
    page.wait_for_selector("h2.title")
    title = page.locator("h2.title").first.inner_text()
    body = page.locator("div.article-body").first.inner_html()
    browser.close()

# post as draft first; review before publishing
r = requests.post(f"{WP}/wp-json/wp/v2/posts", auth=AUTH, json={
    "title": title,
    "content": body,
    "status": "draft",
})
print(r.status_code, r.json().get("id"))
```

To keep the dependencies off the host, [run a Python Playwright scraper in Docker](/docker-run-python/) and schedule the container with cron or systemd timers.
</Tab>
<Tab name="One-off cURL check">
Before you configure any plugin or workflow, sanity-check that your selector matches. This one-liner fetches the page and extracts a node without any plugin involved:

```bash
curl -s -A "Mozilla/5.0" https://example.com/target-page | xmllint --html --xpath '//h2[@class="title"]/text()' - 2>/dev/null | head
```

If that prints nothing, your selector is wrong. Fix it here, not inside WordPress. Then create the post via the REST API with an application password:

```bash
curl -u "admin:xxxx-xxxx-xxxx-xxxx" https://yoursite.com/wp-json/wp/v2/posts \
  -H "Content-Type: application/json" \
  -d '{"title":"Scraped title","content":"<p>Body content</p>","status":"draft"}'
```

**Verify:** open wp-admin → Posts → Drafts (or `GET /wp-json/wp/v2/posts?status=draft`) and confirm the draft is there with the right title and body. A `401` means the application password is wrong; a `404` on the endpoint means pretty permalinks or the REST API is disabled.
</Tab>
</Tabs>

<Notice type="warning" title="Post as draft first">
Always create posts with `"status": "draft"` until you've confirmed the extraction works end to end. Review one or two drafts, then flip the workflow to publish. This prevents the classic failure where a selector change publishes a stream of empty posts to your live site.
</Notice>

If you'd rather buy the fetching infrastructure than operate Playwright yourself, hosted web-fetch and browser APIs like [TinyFish's web fetch and browser APIs](https://go.bitdoze.com/tinyfish) handle the fetching and rendering, and you keep only the WordPress posting step.

## WordPress scraper plugin troubleshooting: WP-Cron, limits & silent failures

Every crawler plugin eventually hits the same four failure modes. None of them show up in the sales page screenshots. If you're about to let a crawler write posts automatically, make sure you have [free WordPress backup plugins](/best-free-wordpress-backup-plugins/) in place first.

### Scheduled scrapes not firing (WP-Cron)

WordPress schedules these jobs with WP-Cron, which only fires when someone visits your site. On a low-traffic site, schedules silently drift and your scraper runs at 3 PM instead of 3 AM, or not at all. The fix is to disable WP-Cron and call it from system cron:

```php
// wp-config.php
define('DISABLE_WP_CRON', true);
```

```bash
# crontab -u www-data -e  (adjust the path to your install)
*/15 * * * * php /var/www/wordpress/wp-cron.php >/dev/null 2>&1
```

**Verify** that the jobs are queued:

```bash
wp cron event list --fields=hook,next_run_relative | grep -iE 'crawl|scrape|fetch'
```

You should see the plugin's hooks with sensible next-run times. If the list is empty, the plugin's schedule isn't registered; check its settings page. If you control the box, this is easy to set up: [install WordPress on Ubuntu ARM with CloudPanel](/install-wordpress-on-ubuntu-arm/) or [install WordPress with Docker Compose](/install-wordpress-docker/) (Docker users schedule the crontab inside the compose file or the container).

### Memory limits and timeouts on shared hosting

Fetching and parsing pages is heavier than serving them. On shared hosting, a crawl of 50 URLs can exhaust `memory_limit` or hit `max_execution_time` mid-run, leaving half-imported content behind. Start with 3-5 URLs per run and watch `php -i` for both values. If limits bite consistently, you have two options: tune caching so your PHP workers are free for the crawler ([speed up WordPress with Cloudflare, Varnish and Redis](/speed-up-wordpress-with-cloudflare-varnish-and-redis/)), or move to a box with more headroom. A small VPS is single-digit dollars per month versus $10-30 for managed WordPress. For this, [a budget Hetzner VPS](https://go.bitdoze.com/hetzner) is the default I'd pick, or [managed WordPress hosting like Cloudways](https://go.bitdoze.com/cloudways) if you don't want to manage a server at all. If you expect heavy scheduled crawls, see [picking a VPS that can handle them (ARM vs x86 benchmarks)](/arm-vs-x86-vps-server-benchmarks/).

### Silent failures: empty posts when the target site changes

<Notice type="warning" title="The #1 silent failure">
The target site changes its markup, your selectors return empty strings, and the plugin cheerfully publishes an empty or half-empty post on schedule. Nothing errors. Nobody notices for two weeks. This is how scraper sites die quietly.
</Notice>

Three habits keep this from happening:
- Check recent posts and the plugin log weekly. It takes two minutes.
- Enable "skip publishing if content is shorter than N characters" wherever the plugin offers it (most of the paid picks do).
- Audit what the crawler published: [export all your WordPress post URLs and titles](/export-wordpress-post-urls-titles/) and diff the list against what you expected.

### Blocked fetches (403/429)

A 403 or 429 means the target is rate-limiting or blocking you. Don't reach for a proxy first. Slow the crawl schedule, identify your crawler in the User-Agent, and fix the rate. All four paid plugins support proxies when you genuinely need them, but residential bandwidth at $2.50+/GB adds up fast, and you shouldn't pay for proxies to fix a rate-limit problem a slower cron solves for free.

### Verify-it-works checklist (first run)

<ListCheck>
<ul>
<li>Run one manual fetch and read the resulting post body</li>
<li>Confirm the featured image landed in the Media Library (not a hotlinked URL)</li>
<li>Confirm tags and categories mapped correctly</li>
<li>Enable scheduling at the lowest frequency available</li>
<li>Check for duplicates after the first full cycle</li>
</ul>
</ListCheck>

Only after all five pass should you raise the frequency.

If your target is JavaScript-heavy, [Crawlomatic](https://1.envato.market/aZQLW) is the only in-plugin option that renders JS. If it struggles, skip plugins and use the external Playwright route above. For RSS aggregation, use [FeedWordPress](https://wordpress.org/plugins/feedwordpress/) if you want free and boring, or [WordPress Automatic](https://1.envato.market/AYXAj) if you also want AI rewriting and social sources. For multi-source social or AI generation, WordPress Automatic is the pick: nothing else here imports from YouTube, Reddit, and Amazon and generates articles from keywords. For standard static-HTML scraping with a visual selector, [Scrapes](https://octolooks.com/wordpress-auto-post-and-crawler-plugin-scrapes/) is the safer buy today (vendor alive, $29, shared-hosting friendly); [WP Content Crawler](https://1.envato.market/kPGkz) has the nicer inspector and ChatGPT integration, but read the vendor status warning first. For one-off page migration, [WP Scraper](https://wordpress.org/plugins/wp-scraper/) is free and enough.

Don't buy on the feature list. Buy on whether the vendor answered support tickets this month. Crawlomatic and WordPress Automatic (both ValvePress) shipped updates through 2025; Scraper's last hard data is from 2023; WP Content Crawler's docs are offline. Budget accordingly.

Whichever plugin you choose, pair it with a proxy service if you're scraping at any real volume. [Bright Data](https://go.bitdoze.com/brightdata) covers residential from $2.50/GB and datacenter from $0.90/IP. And always check the target site's terms of service: scraping copyrighted content without permission can create legal problems no matter which tool you use.

## FAQ

<Accordion label="Is web scraping from other sites legal?" group="faq" expanded="true">
For publicly accessible data in the US, scraping is largely a contract question rather than a criminal one. hiQ v. LinkedIn was re-affirmed by the 9th Circuit for public data after *Van Buren v. United States* (2021) narrowed the CFAA. The real constraints are the site's terms of service and copyright law. Don't republish copyrighted content wholesale; short excerpts with a link back are the boring, safe path. Check the ToS before you scrape, not after.
</Accordion>

<Accordion label="Do I need a proxy to scrape into WordPress?" group="faq">
Not at low volume with polite schedules: a few pages a day with proper delays rarely triggers anything. Yes once you start seeing 403/429 responses, and yes for any real volume. Fix the schedule first; then add proxies. Residential bandwidth starts around $2.50/GB with [Bright Data](https://go.bitdoze.com/brightdata); datacenter IPs are cheaper (from $0.90/IP) and fine for simple fetching.
</Accordion>

<Accordion label="Can WordPress scraper plugins handle JavaScript-rendered sites?" group="faq">
Only one does it in-plugin: Crawlomatic (headless browser). Scraper can with its PRO add-on at $9/month. Everything else in the table fetches raw HTML and nothing more. For a reliably JS-heavy target, the external Playwright script in [the no-plugin section](#how-to-scrape-a-website-to-wordpress-without-a-plugin) beats all of them. It renders pages like a real browser and posts via the REST API.
</Accordion>

<Accordion label="What's the cheapest way to scrape a website to WordPress?" group="faq">
$0 if the source publishes an RSS feed: FeedWordPress. $0 for one-off page imports: WP Scraper. Otherwise the paid picks are $29-39 one-time, which is the cost of two months of most SaaS scrapers. Don't pay a monthly fee unless you need JavaScript rendering at scale.
</Accordion>

<Accordion label="Why is my scraper publishing empty or duplicate posts?" group="faq">
Empty posts usually mean the target site changed its markup and the selectors now match nothing. Duplicate posts usually mean duplicate detection is off or the source URLs changed. Both are covered in [the troubleshooting section](#wordpress-scraper-plugin-troubleshooting-wp-cron-limits--silent-failures). The short version is: gate publishing on a minimum content length, and check what the crawler published every week.
</Accordion>

Pick the maintained option. Run one manual fetch before you enable any schedule, and check the target site's terms before the first request. A scraper that publishes reliably at a slow pace beats a fast one that gets your IP blocked or fills your site with empty posts.
