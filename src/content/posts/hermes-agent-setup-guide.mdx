## What Hermes Agent actually is

Nous Research built Hermes Agent as what they call a "self-improving" AI assistant. That label is accurate. The agent watches what it does, extracts reusable skills from complex tasks, and refines those skills the next time it runs them. Most other assistants in this category forget everything between sessions. Hermes carries forward what it learned.

The architecture:

```
You (CLI / TUI / Telegram / Discord / Slack / WhatsApp / Signal / Email / Teams)
    ↓
Hermes Gateway (single process or Docker s6 supervision)
    ↓
AI Agent (session store, memory, skills, MCP, tools)
    ↓
LLM Provider (OpenRouter, Nous Portal, OpenAI, Anthropic, Ollama, custom)
    ↓
40+ Tools + MCP servers (terminal, web search, browser, files, code, TTS)
```

Messages arrive from whatever platform you use. The gateway routes them through a per-chat session store, the agent processes them with access to 40+ built-in tools, and everything runs from a single process. No microservices, no database server.

The learning loop is what separates Hermes from the other three. After you ask Hermes to do something complex (say, deploy a Docker service), it extracts that workflow into a skill. ## Installation

The one-line installer handles Python, Node.js, dependencies, and the `hermes` command. Works on Linux, macOS, WSL2, and native Windows (PowerShell). A new install lands on the latest stable release. Prefer Docker Compose if you want a containerized gateway and dashboard on a VPS.


After it finishes, reload your shell:

<Tab name="Docker Compose">

Best for a 24/7 VPS. The official image mounts `~/.hermes` at `/opt/data` and runs the gateway under s6 supervision.

```bash
mkdir -p ~/.hermes

# First-time setup wizard (writes API keys to ~/.hermes/.env)
docker run -it --rm \
  -v ~/.hermes:/opt/data \
```

Then create a `docker-compose.yml` (or clone the [repo file](https://github.com/NousResearch/hermes-agent/blob/main/docker-compose.yml)):

```yaml
services:
  hermes:
    image: nousresearch/hermes-agent:latest
    container_name: hermes
    restart: unless-stopped
    command: gateway run
    ports:
      - "8642:8642"   # gateway API
      - "9119:9119"   # dashboard (with HERMES_DASHBOARD=1)
    volumes:
      - ~/.hermes:/opt/data
    environment:
      - HERMES_DASHBOARD=1
      # Match host ownership of ~/.hermes (required on most VPS/NAS mounts)
      - HERMES_UID=${HERMES_UID:-1000}
      - HERMES_GID=${HERMES_GID:-1000}
      # Dashboard auth (required when bound beyond loopback)
      # - HERMES_DASHBOARD_BASIC_AUTH_USERNAME=admin
      # - HERMES_DASHBOARD_BASIC_AUTH_PASSWORD=change-me
      # Optional OpenAI-compatible API server (do not expose publicly without a key):
      # - API_SERVER_ENABLED=true
      # - API_SERVER_HOST=0.0.0.0
      # - API_SERVER_KEY=${API_SERVER_KEY}
    deploy:
      resources:
        limits:
          memory: 4G
          cpus: "2.0"
```

Start it:

```bash
export HERMES_UID="$(id -u)"
export HERMES_GID="$(id -g)"
docker compose up -d
docker compose logs -f
```

Open the dashboard at `http://127.0.0.1:9119` (use an SSH tunnel for remote access: `ssh -L 9119:localhost:9119 user@your-server`). Set `HERMES_DASHBOARD_HOST=127.0.0.1` for that setup. Without it the dashboard binds `0.0.0.0` inside the container and needs an auth provider, or it refuses to start.

Full Docker details are in the [Docker Compose section](#docker-compose-deployment) below.

## Docker Compose deployment

Running Hermes in Docker keeps the install tree immutable under `/opt/hermes` and stores all user state (config, keys, sessions, skills, memories) in `~/.hermes` mounted at `/opt/data`. You can upgrade by pulling a new image without losing config. The `latest` and `stable` tags point at the same release-gated image, `main` at development builds. Pin `X.Y.Z` or a digest when you want an exact deployment.

The official repo ships a [`docker-compose.yml`](https://github.com/NousResearch/hermes-agent/blob/main/docker-compose.yml) with separate `gateway` and `dashboard` services on host networking. The docs also show a single-service layout with bridge networking and published ports. Both work; pick based on how you want to expose the dashboard.

### Option A: Single service (bridge networking)

Simple and portable. Good default for most VPS setups.

```bash
mkdir -p ~/.hermes

# One-time interactive setup
docker run -it --rm \
  -v ~/.hermes:/opt/data \
  nousresearch/hermes-agent setup
```

Create `docker-compose.yml`:

```yaml
services:
  hermes:
    image: nousresearch/hermes-agent:latest
    container_name: hermes
    restart: unless-stopped
    command: gateway run
    ports:
      - "8642:8642"   # gateway OpenAI-compatible API + health
      - "9119:9119"   # web dashboard
    volumes:
      - ~/.hermes:/opt/data
    environment:
      - HERMES_DASHBOARD=1
      - HERMES_UID=${HERMES_UID:-1000}
      - HERMES_GID=${HERMES_GID:-1000}
      # Required when dashboard binds beyond loopback:
      # - HERMES_DASHBOARD_BASIC_AUTH_USERNAME=admin
      # - HERMES_DASHBOARD_BASIC_AUTH_PASSWORD=change-me
    deploy:
      resources:
        limits:
          memory: 4G
          cpus: "2.0"
```

```bash
export HERMES_UID="$(id -u)"
export HERMES_GID="$(id -g)"
docker compose up -d
```

### Option B: Official repo compose (host networking)

Matches the [upstream docker-compose.yml](https://github.com/NousResearch/hermes-agent/blob/main/docker-compose.yml). Gateway and dashboard share the host network and PID namespace so the dashboard can detect gateway liveness.

```bash
git clone https://github.com/NousResearch/hermes-agent.git
cd hermes-agent

mkdir -p ~/.hermes
# Run setup once if ~/.hermes is empty
docker run -it --rm -v ~/.hermes:/opt/data nousresearch/hermes-agent setup

export HERMES_UID="$(id -u)"
export HERMES_GID="$(id -g)"
docker compose up -d --build
```

Core of that file (abbreviated):

```yaml
services:
  gateway:
    build: .
    image: hermes-agent
    container_name: hermes
    restart: unless-stopped
    network_mode: host
    volumes:
      - ~/.hermes:/opt/data
    environment:
      - HERMES_UID=${HERMES_UID:-10000}
      - HERMES_GID=${HERMES_GID:-10000}
      # Optional API server (needs a key if you bind beyond localhost):
      # - API_SERVER_HOST=0.0.0.0
      # - API_SERVER_KEY=${API_SERVER_KEY}
    command: ["gateway", "run"]

  dashboard:
    image: hermes-agent
    container_name: hermes-dashboard
    restart: unless-stopped
    network_mode: host
    depends_on:
      - gateway
    volumes:
      - ~/.hermes:/opt/data
    environment:
      - HERMES_UID=${HERMES_UID:-10000}
      - HERMES_GID=${HERMES_GID:-10000}
    # Localhost-only. For remote access: ssh -L 9119:localhost:9119 user@host
    command: ["dashboard", "--host", "127.0.0.1", "--no-open"]
```

### Useful Docker commands

```bash
docker compose logs -f                  # Live logs
docker logs --tail 50 hermes            # Recent gateway output
docker exec hermes hermes gateway status
docker exec hermes hermes doctor
docker exec -it hermes hermes           # Interactive CLI against the same data dir
docker compose pull && docker compose up -d   # Upgrade image
```

The gateway also writes its logs under `~/.hermes/logs/gateways/<profile>/current` on the host volume, so they survive container restarts. On upgrade the container runs config-schema migrations against the mounted `config.yaml` before starting the gateway and writes timestamped backups of `config.yaml` and `.env` first. Check what you run with `docker exec hermes hermes --version`.

### Docker security notes

<Notice type="warning" title="Do not expose the dashboard unauthenticated">
The built-in dashboard stores API keys. Keep it on `127.0.0.1` and use an SSH tunnel, or put it behind auth (basic auth env vars, OAuth, or a reverse proxy). `HERMES_DASHBOARD_INSECURE` is a deprecated no-op; non-loopback binds require a real auth provider.
</Notice>

- Set `HERMES_UID` / `HERMES_GID` (or `PUID` / `PGID`) to the host user that owns `~/.hermes` so files stay readable after the container drops privileges.
- Never run two gateway containers against the same `~/.hermes` directory at once (session and memory files are not multi-writer safe).
- If you enable the OpenAI-compatible API server, set `API_SERVER_KEY` (min 8 chars) and do not publish it on the public internet without a reverse proxy.
- For browser tools (Playwright), add `--shm-size=1g` or the Compose equivalent under `shm_size: 1gb`.

### Resource sizing

| Resource | Minimum | Recommended |
|---|---|---|
| Memory | 1 GB | 2 to 4 GB |
| CPU | 1 core | 2 cores |
| Disk (data volume) | 500 MB | 2+ GB (grows with sessions/skills) |

Browser automation is the memory hog. Without it, 1 GB is fine. With Playwright, plan for at least 2 GB.

Official reference: [Hermes Docker docs](https://hermes-agent.nousresearch.com/docs/user-guide/docker).

## How do I update Hermes Agent?

A source install updates with `hermes update`. A Docker install needs `docker compose pull && docker compose up -d` with the same data mount, and the Store and bundled apps update themselves.

| Install | Update method |
|---|---|
| Source checkout (the one-line installer) | `hermes update` |
| Docker | `docker compose pull && docker compose up -d` with the same data mount |
| Microsoft Store app | Updates through the Store |
| macOS bundled app | The Update control in the app |

```bash
hermes update --check    # is there a new release? changes nothing
hermes update --plan     # the update plan: install kind, services, restarts
hermes update            # apply
hermes --version
```

A source checkout tracks the stable channel: the latest published `vX.Y.Z` release at its exact commit. `hermes update --set-channel main` switches it to every commit on `main`. After the pull, Hermes restarts the gateway profiles of the home it updated and prints a per-profile version matrix. If a gateway is still on old code, the output names the exact restart command. `hermes update --force` stops every gateway at once instead of waiting for running turns, cron jobs and background subagents to drain; use it when interrupting that work is acceptable.

**Update anything older than v0.23.2.** v0.23.2 (November 16, 2026) fixed GHSA-p22p-9ph6-gmrh (CVE-2026-130164, rated High). With Bot Desktop running inside a `docker` or `ssh` terminal backend, Hermes now allowlists and validates the screen env file. Values from a backend-hosted screen are no longer merged into processes started on the agent machine. Source: [v0.23.2 release notes](https://github.com/NousResearch/hermes-agent/releases/tag/v0.23.2).

v0.23.2 also brought durable subagents. A child started with `delegate_task` keeps a durable record in the profile's `state.db`, so `continue` works after a gateway restart, a hard kill or a crash. The child keeps its own conversation. Nothing resumes on its own unless you set `delegation.auto_resume: true`; by default you continue the child by hand.

## Choosing a model provider

Hermes is provider-agnostic. Secrets go in `~/.hermes/.env`; non-secret settings go in `~/.hermes/config.yaml`. The interactive picker puts values in the right place:

```bash
hermes model
```

On a fresh install, `hermes setup` asks one question, "How do you want to power Hermes?", then applies recommended defaults to everything else. Your options:

| Answer | What you get |
|---|---|
| Free, start now | No account, no API key. Runs on the free `nous/welcome` model. Offered once per OS user, never in a container, CI or scripted run |
| Sign in to Nous Portal | OAuth login, 300+ models, Tool Gateway (web search, image gen, TTS, cloud browser) under one subscription |
| Use my own API key or a subscription | The `hermes model` picker: OpenRouter, Anthropic, OpenAI, local models and the rest |
| Full Setup | Walk every provider, tool and option yourself |
| Blank Slate | Minimal agent (file ops + terminal only); opt in to tools later |

```bash
hermes setup --portal   # Nous Portal + Tool Gateway in one shot
hermes setup            # first run: one question, then defaults
```

If the setup finds OpenClaw, Claude Code, Codex CLI or Cursor on the machine, it offers to import that setup before the question.

<Notice type="info" title="Minimum context: 64K tokens">
Hermes needs a model with at least **64,000 tokens** of context for multi-step tool calling. Most hosted models meet this. For local models (Ollama, llama.cpp), set context to at least 64K (for example `-c 65536` or `--ctx-size 65536`).
</Notice>

## Setting up OpenRouter with free models

OpenRouter routes to 200+ models through a single API key. They also have a [free tier](https://openrouter.ai/openrouter/free) with several models at zero cost, which is the cheapest way to get started without a subscription.

### Get your API key

1. Go to [openrouter.ai](https://openrouter.ai) and create an account
2. Navigate to **Keys** in your dashboard
3. Click **Create Key** and copy the key

### Configure Hermes Agent

**Interactive setup (recommended):**

```bash
hermes setup
# or just:
hermes model
```

When it asks for a provider, select **OpenRouter** and paste your key.

**Manual setup:**

Add your API key to `~/.hermes/.env`:

```bash
echo "OPENROUTER_API_KEY=sk-or-v1-your-key-here" >> ~/.hermes/.env
```

Set the model in `~/.hermes/config.yaml`:

```yaml
model:
  provider: "openrouter"
  default: "openrouter/free"
```

The `openrouter/free` model routes to the best available free model. You can also set it with:

```bash
hermes config set model openrouter/free
```

### Switch models on the fly

```bash
hermes model
```

Or mid-conversation:

```
/model openrouter/free
```

### Using paid models later

```bash
hermes config set model anthropic/claude-sonnet-4.6
# or
hermes config set model openai/gpt-5.4
```

OpenRouter handles the routing. Your API key stays the same.

## Memory system

Hermes has three layers of memory that work together.

### MEMORY.md: the agent's own notes

The agent writes its own notes about your environment, conventions, and things it learned. Stored in `~/.hermes/memories/MEMORY.md`. Limited to 2,200 characters (~800 tokens) to keep the system prompt bounded.

The agent manages this automatically. When it discovers that your server runs Ubuntu 22.04 with Docker installed, it saves that. When it learns you prefer concise responses, it saves that too. You don't need to tell it to remember; it watches for useful facts and stores them.

### USER.md: your profile

Information about you: name, preferences, communication style, timezone. Stored in `~/.hermes/memories/USER.md`. Limited to 1,375 characters (~500 tokens).

### Session search

Beyond the two markdown files, Hermes stores all past conversations in SQLite with FTS5 full-text search. It can search through weeks of old conversations to find something you discussed before:

```
❯ What did we discuss about the Nginx configuration last week?
```

The agent searches its session history, summarizes the relevant parts, and gives you the answer. No other assistant in the OpenClaw family does this.

### Configure memory

In `~/.hermes/config.yaml`:

```yaml
memory:
  memory_enabled: true
  user_profile_enabled: true
  memory_char_limit: 2200
  user_char_limit: 1375
```

Three things worth knowing. A fact saved in the current session is visible to the next session, not to one that is already running, so start a new session (`/new`) after an important write. On messaging platforms the chat is one long session that survives restarts, so run `/new` at natural boundaries or compaction runs over an ever-longer history on every turn. And memory is per profile: `hermes -p work` reads `~/.hermes/profiles/work/memories/`, which matters once you have several Bots. Check a save with `cat ~/.hermes/memories/MEMORY.md`; "I'll remember that" is only text until the `memory` tool ran.

<Notice type="info" title="Upgrade to vector-based memory">
Hermes can use [Hindsight](/hindsight-docker-deploy/) as its memory backend instead of the built-in MEMORY.md and session search. Hindsight stores memories as vector embeddings with entity extraction. See the [Hindsight integration](https://hindsight.vectorize.io/integrations) for setup details. The [Cognee vs Hindsight comparison](/cognee-vs-hindsight/) covers how the two differ.
</Notice>

## Skills system

This is the feature I keep coming back to. Skills are not pre-built plugins you install from a hub. The agent creates them from tasks it completes.

### How skill creation works

1. You ask Hermes to do something complex (deploy a service, set up a CI pipeline, configure Nginx)
2. Hermes completes the task using its tools
3. After finishing, it extracts the workflow into a reusable skill
4. Next time you ask for something similar, it uses and refines that skill

Skills also self-improve. Each time one runs, the agent checks whether the steps could be better and updates the skill if so.

The agent does this through its `skill_manage` tool. Set `skills.write_approval: true` in `config.yaml` to hold skill writes made outside the interactive CLI for review before they land. A background review after a session can also suggest skill changes; `auxiliary.background_review` routes that review to a cheaper model.

### Browse and install community skills

```bash
hermes skills browse                          # list hub skills
hermes skills search react --source skills-sh
hermes skills inspect official/security/1password
hermes skills install official/mcp/fastmcp    # security scan runs first
```

Installed skills become slash commands automatically. Or use `/skills` inside chat.

```bash
hermes skills check      # audit installed skills
hermes skills update     # update hub-installed skills
```

### Skills Hub

Skills follow the agentskills.io open standard, and the hub pulls from several sources: official optional skills, skills.sh, ClawHub, LobeHub, direct GitHub repos and plain URLs. The system prompt lists every skill as `name: description`, and each row shows the first 60 characters by default. If your skills put their trigger phrases past character 60, raise `skills.index_desc_limit` (accepted range 60 to 1024). For examples of well-built skills, see my comparison of the [best AI skills for web design](/best-ai-skills-for-web-design/).

## MCP servers

Hermes can load [Model Context Protocol](https://modelcontextprotocol.io/) servers so the agent gains external tools (GitHub, databases, browsers, and more) without custom code.

Add them in `~/.hermes/config.yaml`:

```yaml
mcp_servers:
  github:
    command: npx
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_PERSONAL_ACCESS_TOKEN: "ghp_your_token"
```

Restart the CLI or gateway after editing. Keep tokens in `.env` when possible and only put non-secret wiring in `config.yaml`.

## Built-in web dashboard

Hermes ships a web dashboard (default port 9119) for config, sessions, and provider settings. On Docker, enable it with `HERMES_DASHBOARD=1` (see [Docker Compose](#docker-compose-deployment)). On a bare install:

```bash
hermes dashboard
# or bind loopback only for remote SSH tunnels:
hermes dashboard --host 127.0.0.1 --no-open
```

The dashboard binds `127.0.0.1` by default. Any other bind engages the auth gate, and it fails closed: with no provider registered, `hermes dashboard` refuses to bind. Three providers ship: username/password (trusted LAN or VPN only), OAuth through Nous Portal (the one to use for an internet-facing dashboard) and self-hosted OIDC. `hermes dashboard password` sets the username and password without a TTY prompt. The old `--insecure` flag is a deprecated no-op. For a deeper walkthrough of the built-in UI and third-party options, see the [Hermes dashboard guide](/hermes-dashboard-guide/) and [best Hermes dashboards](/best-hermes-dashboards/).

v0.23.4 added `hermes gateway migrate --backends`, which moves a hand-run `hermes dashboard` or `hermes serve` backend onto the gateway so the gateway's Webapp serves the old address. Start with the plan:

```bash
hermes gateway migrate --backends --apply --dry-run   # plan and blockers, changes nothing
hermes gateway migrate --backends --apply             # migrate (asks unless you pass --yes)
hermes gateway migrate --backends --restore           # undo a finished migration
hermes webapp --status
```

Inside a Docker container it exits 6 and prints the by-hand steps, because it does not edit your Compose file. The dashboard's System page has a card for the same move.

`hermes serve` is the same server without the browser UI, on the same port 9119, and it is what Hermes Desktop connects to when the backend runs on another machine.

## Terminal backends

By default, Hermes runs commands directly on your machine. For security, you can isolate command execution in a container or send it to a remote server.

```yaml
# In ~/.hermes/config.yaml
terminal:
  backend: local    # or: docker, ssh, modal, daytona, vercel_sandbox, or a plugin backend
  timeout: 180
```

| Backend | What it does | Best for |
|---|---|---|
| `local` | Runs on your machine (default) | Development, trusted tasks |
| `docker` | Isolated containers | Security, reproducibility |
| `ssh` | Remote server | Keeping the agent away from its own code |
| `daytona` | Cloud sandbox workspace | Persistent remote dev environments |
| `modal` | Serverless cloud | Scale-to-zero, pay-per-use |
| `vercel_sandbox` | Vercel Sandbox cloud microVM | Cloud execution with snapshot-backed filesystem persistence |
| `singularity`, `sprites` | Plugin backends: HPC containers, a Fly.io sandbox | `hermes plugins install singularity` |

Singularity moved out of core into an official plugin. `hermes update` installs it for profiles that already use it; everyone else runs `hermes plugins install singularity`. The terminal backend is per profile, so a Bot can run in a container while the default profile stays on `local`.

### Docker isolation

```yaml
terminal:
  backend: docker
  docker_image: python:3.11-slim
  container_cpu: 1
  container_memory: 5120
  container_disk: 51200
  container_persistent: true
```

Containers run with a read-only root filesystem, all Linux capabilities dropped, no privilege escalation, PID limits, and namespace isolation.

### SSH backend

Run commands on a separate machine entirely:

```yaml
terminal:
  backend: ssh
```

```bash
# In ~/.hermes/.env
TERMINAL_SSH_HOST=my-server.example.com
TERMINAL_SSH_USER=myuser
TERMINAL_SSH_KEY=~/.ssh/id_rsa
```

## Voice mode

Hermes has voice support across CLI and messaging. You can talk to it with your mic in the terminal, get spoken replies in Telegram and Discord, and have live voice conversations in Discord voice channels.

### Prerequisites

```bash
# System dependencies (Ubuntu/Debian)
sudo apt install portaudio19-dev ffmpeg libopus0
sudo apt install espeak-ng   # only for the local NeuTTS engine
```

Pick the speech-to-text and TTS providers with `hermes tools`; it pulls the missing built-in requirements. The `voice` extra covers CLI audio and, where supported, local Faster-Whisper, so local speech-to-text needs no API key. Do not pip-install into the bundled desktop app. Local Faster-Whisper is excluded on native Windows ARM64 and Intel macOS; use a cloud provider there.

### CLI voice mode

Start the CLI and enable voice:

```bash
hermes
/voice on
```

Press `Ctrl+B` to record. Speak, and when you stop, it auto-detects silence after 3 seconds and transcribes your audio. If TTS is enabled (`/voice tts`), the agent speaks its reply back.

### Messaging voice replies

In Telegram or Discord, send:

```
/voice tts
```

The agent now sends spoken audio alongside text for every response.

### Discord voice channels

The agent can join a Discord voice channel, listen to you speak, and reply with spoken audio:

```
/voice join
```

This requires additional Discord bot permissions (Connect, Speak, Use Voice Activity) and the Opus codec on your server.

The invite URL in the Discord tab carries text-only permissions. For voice, re-invite with `permissions=309240908864` (adds Connect and Speak).

### TTS providers

| Provider | Cost | Quality | Setup |
|---|---|---|---|
| Edge TTS | Free | Good | Works out of the box |
| NeuTTS | Free | Good | Separate optional runtime, needs `espeak-ng`; downloads models on first use |
| ElevenLabs | Paid | Premium | Set `ELEVENLABS_API_KEY` |
| OpenAI TTS | Paid | Good | Set `VOICE_TOOLS_OPENAI_KEY` |

Configure in `~/.hermes/config.yaml`:

```yaml
stt:
  provider: "local"

    model: "base"
```

## Personality and SOUL.md

Hermes uses a file called `SOUL.md` as its identity. The agent loads it into the system prompt before anything else, and it sets how the agent talks.

Edit it at `~/.hermes/SOUL.md`:

```markdown
# Personality
You are a pragmatic senior engineer with strong taste.
You optimize for truth, clarity, and usefulness over politeness theater.

## Style
- Be direct without being cold
- Prefer substance over filler
- Push back when something is a bad idea
- Keep explanations compact unless depth is useful

## What to avoid
- Sycophancy
- Hype language
- Overexplaining obvious things
```

### Built-in personalities

Switch personalities on the fly with `/personality`:

| Name | Description |
|---|---|
| `helpful` | Friendly, general-purpose assistant |
| `concise` | Brief, to-the-point responses |
| `technical` | Detailed technical expert |
| `creative` | Innovative thinking |
| `teacher` | Patient educator with examples |
| `pirate` | Tech-savvy buccaneer |
| `noir` | Hard-boiled detective narration |

```
/personality concise
/personality pirate
```

`SOUL.md` is your baseline. `/personality` is a session-level overlay.

Add your own presets under `agent.personalities` in `~/.hermes/config.yaml` and switch with `/personality <name>`. `/personality none` clears the overlay.

## Scheduled tasks

Hermes has a built-in cron scheduler. Just tell it what you want in plain English:

```
❯ Every morning at 9am, check Hacker News for AI news and send me a summary on Telegram.
❯ Every Friday at 5pm, back up the PostgreSQL database and report the size.
❯ Every hour, check if nginx is running and restart it if not.
```

The agent creates cron jobs that run through the gateway. Results land on whatever platform you configured.

From a shell:

```bash
hermes cron list                                   # every job, with its pinned model and time zone
hermes cron create "every 2h" "Check server status"
hermes cron edit <job_id> --pin                    # lock the current main model onto one job
hermes cron edit <job_id> --deliver telegram       # send the output somewhere
```

Which model a job runs on resolves at fire time: the job's own pin first, then `cron.model` in `config.yaml`, then the main agent model. Pin a cheap model on routine jobs so switching your chat model never changes what a 3am check costs. Since v0.23.2 a job can run in a fresh thread per run and turn off the delivery wrapper (`wrap_response`), so a briefing arrives without the header. Script-only jobs skip the model entirely. A script runs on a schedule and its stdout goes out as is.

## Migrating from OpenClaw and other agents

`hermes import-agent` imports an existing OpenClaw, Claude Code, Codex CLI, Cursor, Grok Bot or OpenBot setup. You see a per-item plan first, and `--dry-run` writes nothing. The command ships in the official `agent-importers` plugin.

**During first-time setup:** on a fresh install, `hermes setup` looks for `~/.openclaw`, `~/.claude`, `~/.codex` and `~/.cursor` (plus the Grok Bot and OpenBot apps) before anything else and asks whether to import. For OpenClaw it passes `--migrate-secrets`, so keys and bot tokens come over as the old built-in step did.

**Anytime after install:**

```bash
hermes migrate                                # detect what is on this machine and offer to import
hermes migrate openclaw                       # force one: openclaw, claude-code, codex, cursor, grok-bot, openbot
hermes migrate openclaw --migrate-secrets     # OpenClaw API keys and bot tokens come over only with this flag
hermes import-agent openclaw --dry-run        # the underlying command
hermes import-agent --sync                    # re-import Claude Code, Codex and Cursor sources that changed
```

`hermes claw migrate` still works. It is the older spelling of `hermes import-agent openclaw`. Both need the plugin; without it they print the install line (`hermes plugins install agent-importers`).

What the OpenClaw import covers:
- SOUL.md, MEMORY.md, USER.md and AGENTS.md
- Skills from four source directories
- Default model, custom providers and MCP servers
- Messaging platform tokens and allowlists (Telegram, Discord, Slack, WhatsApp, Signal, Matrix, Mattermost)
- Approval rules, the command allowlist and agent defaults
- TTS, browser and tool settings
- API keys, but only with `--migrate-secrets`

The importer skips cron jobs, plugins, hooks and the memory backend, and archives them for manual review. It writes a pre-migration zip of `~/.hermes/` under `~/.hermes/backups/` before it applies anything. For the other agents, it turns instructions and rules into memory entries, permission rules into `command_allowlist`, puts MCP servers in `mcp_servers`, and copies skills. Credentials other than OpenClaw's never come over.

## Troubleshooting

When something feels off, run this sequence before adding more features:

```bash
hermes doctor           # Config / env / dependency checks
hermes model            # Re-select provider and model
hermes setup            # Re-run wizard if needed
hermes sessions list    # Confirm sessions and profile
hermes --continue       # Resume last chat
hermes gateway status   # Messaging gateway health
```

| Symptom | Likely cause | Fix |
|---|---|---|
| Empty or broken replies | Wrong provider auth or model | `hermes model` and re-auth |
| Custom endpoint returns garbage | Bad base URL / model name | Test the endpoint outside Hermes first |
| Gateway up but no messages | Token, allowlist, or platform setup | `hermes gateway setup` + `hermes gateway status` |
| `--continue` finds nothing | Different profile or unsaved session | `hermes sessions list` |
| Docker permission errors on `~/.hermes` | UID/GID mismatch | Set `HERMES_UID` / `HERMES_GID` to host owner |
| Dashboard fails on public bind | Auth required | Basic auth env vars, OAuth, or bind `127.0.0.1` |
| `hermes cron` or `hermes peer` not found | Install is older than v0.23 | `hermes update`, then confirm with `hermes --version` |
| No `message_agent` tool in a Bot's chat | Headless install never wrote the Bot Chat or the roster marker | Follow the headless steps under Bot Mode |

## How Hermes Agent differs from OpenClaw

I've used both extensively. Here are the differences that matter day to day:

**The learning loop changes how you work with it.** In OpenClaw, every complex task starts from scratch. In Hermes, once you've walked the agent through deploying a Docker service, it creates a skill for that workflow. Next time you say "deploy the staging API," it already knows the steps.

**Session search gives it long-term recall.** OpenClaw's memory is limited to what fits in its context files. Hermes stores every conversation in SQLite with full-text search. Ask "what port did we configure for Redis last month?" and it finds the answer in old sessions.

**The personality system is more structured.** OpenClaw uses a system prompt you edit by hand. Hermes has SOUL.md as a durable identity file, session-level `/personality` overlays, and 14 built-in presets.

**Voice mode works end to end.** Mic input in the CLI, TTS replies on messaging, and live Discord voice channel conversations. Nothing else in the OpenClaw family does this.

**Terminal backend isolation.** OpenClaw runs commands on your local machine. Hermes can run them in Docker containers, on remote servers via SSH, or in serverless environments like Modal and Daytona. If the agent breaks something, it breaks the sandbox, not your server.

**Migration is painless.** `hermes migrate openclaw` brings over memories, skills, platform configs, and API keys when you add `--migrate-secrets`. You don't start over.

**Where OpenClaw still wins:** bigger community, more third-party dashboards and skins, longer track record. If you want the more battle-tested option, OpenClaw is still it.

If you'd rather have a roster of bots than one learning agent, [Bot Mode](#bot-mode-a-roster-of-specialist-bots) gives you that inside Hermes Desktop. For standalone chat-app alternatives closer to xAI's Grok Bot, see our [open source Grok Bot alternatives](/best-open-source-grok-bot-alternatives/). Hermes is on that list next to Rakazo, OpenMausBot, and OpenBot.

## Bot Mode: a roster of specialist bots

Bot Mode turns Hermes profiles into a roster of named Bots. Each Bot has its own role, model, memory, skills and avatar. Bots run recurring routines, deliberate in group chats, and message each other directly. It ships inside Hermes Desktop and is on by default in current builds (checked on v0.23.4). The old standalone `Hermes-Bot-Mode` plugin repo is archived; do not install it.

If one assistant that learns is all you want, skip this section. If you keep wishing for a researcher, a reviewer and an on-call bot instead of one long chat, read on.

### A Bot is a profile

There is no new primitive. A Bot is a Hermes profile: isolated config, memory, skills, credentials and chat history under `~/.hermes/profiles/<name>/`. Bot Mode is a UI over that, so everything it does is visible from the CLI. `hermes -p <bot> chat` opens the same agent, and Bot routines show in `hermes cron list`. No core patches, no extra daemons.

What Bot Mode adds on top of a plain profile:

- One permanent **Bot Chat** per Bot. Click the Bot and you are back in the same conversation. `/new` (or `/reset`) inside a Bot Chat is rerouted to `/compact`: fresh working context, same conversation.
- Every Bot in one roster with avatar, latest message and unread state.
- Bots message each other and share group chats.
- Each Bot's routines are scheduled and edited beside its chat.

Keep four terms apart. A profile is the persistent home. A Bot is a profile shown in the roster. A messaging bot is a platform account (Telegram, Discord, Slack) wired through the gateway. A subagent is a child spawned by `delegate_task` with a fresh conversation.

### Creating a Bot

In the desktop app, open the Bots tab and hit **New Agent**. The quick path is three fields (Name, Title, Description). The Bot exists in seconds and introduces itself in its Bot Chat.

The **Advanced** options:

| Option | What it does |
|---|---|
| Clone from an existing profile | Start from another Bot's config, skills, SOUL and memory, or pick Fresh profile |
| Create empty | Skip the bundled skills |
| Model and provider pin | Any provider/model pair Hermes knows. Different Bots can run different models side by side. Unset inherits from the launch profile |
| Custom SOUL.md | The Bot's persona and standing instructions |
| Per-skill, per-toolset, per-MCP-server enablement | Tick only what this specialist needs |
| Copy API keys from the main profile | On by default. Static API keys are copied |

The copy has one gap you will hit on a VPS. Single-use OAuth logins (Anthropic, OpenAI Codex, xAI) are not copied, because a copy of a single-use refresh token is the same credential with two owners. Sign the Bot in by hand:

```bash
hermes -p <bot> auth add <provider>
```

Right-click a Bot for **Edit Profile**, **Duplicate** (a full clone including memory) and **Delete Profile** (permanent; the default profile cannot be deleted). With more than one connection registered in Settings, Gateways, a **Create on** picker lets you create the Bot on another machine's backend.

### Routines are cron jobs

A routine is a recurring task attached to the Bot that does it. The schedule picker builds the schedule, and an Advanced field takes the raw Hermes schedule string. Under the hood a routine is a plain cron job named `[bot:<name>] <routine>`. It shows in `hermes cron list` and in the dashboard's Cron page, and runs land in the Bot's own chat history.

### Group chats

Right-click a local Bot, **Manage groups**, or **New Group Chat**. A room holds 2 to 6 Bots.

- Your message triggers up to three serial rounds of member turns. @-mentioned Bots respond; everyone responds when nobody is mentioned. The room settles when a full round stays silent.
- Hard caps: 10 messages per send and 3 rounds. On a gateway-owned room the cap pauses the discussion ("Paused after N messages") with **Continue** (one more budget, up to 5 times) and **Stop**.
- Bots pull each other in with `@name` and escalate judgment calls to you with `@user`. The group row shows a "needs you" badge. `@hermes` hands off to the primary Bot.
- A Bot speaks only when it has something new to add. Not every Bot answers every message.
- Who answers a message that names nobody is a Room settings choice: Everyone (default), a lead that hands the message on, or "Pick who answers automatically". The automatic choice costs one short tool-less model call per message; route it to a cheap model with `auxiliary.group_router` (`hermes model`, auxiliary, Group router).
- Each member's turn carries every room message since its own last turn, up to about 200 messages or 32,000 characters. When a member starts answering with empty replies, **Compress history** in Group settings runs the same compression as `/compress` on that member's hidden room session.

Gateway-owned rooms keep running when Desktop is closed. A group chat can span machines. Every new room is owned by the active connection's gateway, and Bots on other computers join through their own gateways (text only to remote members).

### Bot-to-bot messaging

In any chat, type `@researcher have a look at this`. The active Bot composes its own message and sends it with the `message_agent` tool; your text is never forwarded verbatim. Every Bot Chat carries `message_agent`, for example `message_agent(target="researcher", message="...")`. The target can be a profile name, a friendly name (`hermes profile rename` or the Bot Mode title) or an @-tag. `@hermes` always means the primary Bot. The teammate roster (names and roles from each profile's title and description) is part of every Bot Chat's system prompt.

Delivery is fire-and-forget. The sender gets `status: queued` and a `delivery_id`, which means handed over, not answered. The completion notification later carries one outcome sentence per target (`@beta answered.` or `@gamma never answered: <why>`).

There is no live interrupt. The receiving Bot picks the message up on its next turn. That turn is the next turn of a Bot Chat open in Desktop or the TUI, or a quiet CLI turn when no chat is open. For work that has to report back into the current conversation, use a subagent (`delegate_task`), not a Bot DM.

The loop guard keeps two Bots from keeping each other busy forever. A reply back to the Bot that messaged it is notify-only, and past `gateway.bot_loop_guard.max_hops` (default 4) a further call is refused. Sending the same message to the same teammate twice in one exchange is refused too.

```yaml
# ~/.hermes/config.yaml
gateway:
  bot_loop_guard:
    max_hops: 4                       # bot-to-bot messages per exchange
    bot_replies_expect_reply: false   # true: a Bot's reply to a Bot may be answered
```

A failed delivery turn retries at most once, and only for transient failures (target runtime offline, delivery timeout, provider rate limit or server error, context overflow). Auth, quota and configuration failures never auto-retry. Failures carry a typed reason code: `provider_auth_or_access`, `provider_quota_limit`, `provider_rate_limit`, `provider_server_error`, `context_overflow`, `missing_config`, `model_unavailable`, `runtime_offline`, `queued_expired`, `delivery_timeout`, `target_busy` or `unknown`. The completion notification is tagged `[reason: <code>]`, so "sign in again" and "wait and retry" look different to the Bot and to you.

### Bot Mode on a headless VPS

This is the part the desktop screenshots will not tell you. The roster UI is the desktop app. On a VPS with only the gateway and Telegram, nothing draws a roster, and one tool is missing: `message_agent` exists only in canonical Bot Chat sessions on Bot-Mode-managed installs. Regular chats, group-room member sessions and CLI sessions never see it.

A chat counts as a Bot Chat only when two markers are present:

1. The session is titled exactly `Bot Chat`.
2. At least one profile on the install carries a `ui_meta: { hermes-bots: ... }` block in its `profile.yaml`.

On a desktop install the Bots pane writes both. There is no CLI command that writes the second one, so on a headless box you write it by hand. Create the profile and its forever-chat first (later runs resume it):

```bash
hermes profile create researcher
hermes -p researcher model            # pick this Bot's model
hermes -p researcher chat -c "Bot Chat" --create-if-missing
```

Then add the marker to any Bot's `profile.yaml`:

```yaml
# ~/.hermes/profiles/researcher/profile.yaml : an empty block marks the whole install
ui_meta:
  hermes-bots: {}
```

From the next turn in that Bot Chat, the session picks up the teammate roster, the protocol section and `message_agent`, including over `hermes -p <bot> chat` on a terminal-only box. The master switch is `agent.bot_mode_protocol` (default `true`); leave it on.

To verify, reopen the chat with `hermes -p researcher chat -c "Bot Chat"` and ask which teammates it can message. A Bot Chat that got the protocol lists the roster built from the other profiles' titles and descriptions; a plain session says it has no such tool. The hand-written marker path is untested here; the two conditions come from the Bot Mode docs.

For the roster itself, run Hermes Desktop on your laptop and point it at the VPS: Settings, Gateways, then Remote gateway (a `hermes serve` backend), SSH, or Hermes Cloud. There is no remote-only Desktop download; install the package and connect from Settings. A non-loopback backend needs an auth provider, and OAuth through Nous Portal is the recommended one for anything reachable beyond your own machine. The [Hermes dashboard guide](/hermes-dashboard-guide/) walks through the remote setup; [best Hermes dashboards](/best-hermes-dashboards/) helps you pick a UI.

### Bots across machines

Two routes. The first is the Desktop relay: every gateway registered in Settings, Gateways is a line the Desktop holds open. Bot Chats list teammates on other machines, and `message_agent` reaches them with `target="moxie"` or `target="moxie@<connection>"`. The Desktop is the courier, so cross-connection delivery works only while a Desktop that knows both connections is running. A relayed message gives the target Bot 10 minutes for its turn.

The second is `hermes peer`, with no Desktop in the loop:

```bash
hermes peer add spark --url http://spark.lan:8377 --key <API_SERVER_KEY>
hermes peer list
hermes peer dm spark "which certificate expires next?"
hermes peer run spark --idempotency-key ticket-123 "audit the staging stack and write a report"
hermes peer status spark <run_id>
```

`peer dm` delivers into the remote agent's canonical Bot Chat, runs one turn there and prints the reply. Keep it to short queries; it holds one HTTP connection until the turn finishes. `peer run` returns a `run_id` at once; poll it with `peer status`. The peer machine needs the `api_server` platform with a strong `API_SERVER_KEY`. The key lands in `~/.hermes/.env` as `HERMES_PEER_<NAME>_KEY`; names and URLs live in `config.yaml` under `bot_peers`. Once a peer is registered, every Bot Chat's protocol includes the peer roster, so `message_agent(target="spark/researcher", ...)` works.

NAT is the catch. Reachability is one-way: a machine at home can dial a public VPS; the reverse needs a route. Put a cross-machine group chat's authority on a host every participant can reach (usually the VPS), or bridge with Tailscale or a VPN.

### Cost and blast radius

Every Bot is a full agent. It has its own keys or login, its own memory and skills, and the same tools as the default profile, terminal included. A researcher Bot with the `local` backend on your VPS can do everything the main agent can. Set the terminal backend per Bot in `~/.hermes/profiles/<bot>/config.yaml` and enable only the skills and toolsets it needs in the New Agent dialog.

The docs publish no token figures for a roster. Work from the caps: one of your messages in a group chat costs up to 10 member turns, and each Continue adds up to 10 more, five times over. Pin a cheap model on worker Bots (`hermes -p <bot> model`) and route the group router to one too. The [best cheap models for Hermes Agent](/best-cheap-models-hermes-agent/) guide has picks.

A Bot adds no daemon. One gateway process per host owns every local profile's sessions, so closing Desktop never stops it; `hermes gateway stop` does. Each profile has its own `.env`, and Hermes refuses two profiles that share a bot token: it blocks the second gateway with an error naming the conflicting profile. Memory and credentials are per profile as well, and a profile export excludes credentials by design, so an export alone is not a backup. Use `hermes backup`.

### Turning Bot Mode off

Capabilities, Plugins, Bots: flip the Desktop switch off. No restart needed. Profiles, sessions and cron jobs are untouched, so routines keep running until you remove them in `hermes cron list`. Delete a Bot with right-click, Delete Profile, when you want its data gone too.

## FAQ

<Accordion label="Do I need a GPU to run Hermes Agent?" group="faq" expanded="true">

No. Hermes Agent is the client: it sends requests to an LLM provider like OpenRouter, which runs the model on its own hardware. Your server needs RAM for the Python process only (around 200MB), or at least 2 GB when the browser tools are enabled.

</Accordion>

<Accordion label="Can I use Hermes Agent with Ollama for local inference?" group="faq">

Yes. Set `OPENAI_BASE_URL=http://localhost:11434/v1` and `OPENAI_API_KEY=ollama` in `~/.hermes/.env`, or use `hermes model` and select "Custom endpoint". Hermes needs a model with at least 64,000 tokens of context for multi-step tool calling, so set that in Ollama too. See our [Ollama Docker guide](/ollama-docker-install/) for setting up Ollama.

</Accordion>

<Accordion label="Can I migrate from OpenClaw?" group="faq">

Yes. Run `hermes migrate openclaw` (the older spelling is `hermes claw migrate`) and it imports your persona, memories, skills and platform configs. Add `--migrate-secrets` to bring API keys and bot tokens over; without it they stay behind. Start with `--dry-run` to preview the plan.

</Accordion>

<Accordion label="Does Hermes work on Windows?" group="faq">

Yes, natively. Run the PowerShell installer: `iex (irm https://hermes-agent.nousresearch.com/install.ps1)`. The desktop package needs Windows 11 22H2 or later. WSL2 still works if you prefer a Linux environment; there, run the gateway with `hermes gateway run` because WSL's systemd support is unreliable.

</Accordion>

<Accordion label="Can I run Hermes with Docker Compose?" group="faq">

Yes. Mount `~/.hermes` at `/opt/data`, run `nousresearch/hermes-agent setup` once, then `docker compose up -d` with `gateway run`. Add `HERMES_DASHBOARD=1` to bring up the dashboard in the same container. See the [Docker Compose section](#docker-compose-deployment) and the [official docker-compose.yml](https://github.com/NousResearch/hermes-agent/blob/main/docker-compose.yml).

</Accordion>

<Accordion label="Can multiple people use one Hermes instance?" group="faq">

Yes, through the messaging gateway. Each platform chat gets its own session, so several Telegram users or Discord channels share the instance with separate histories. Use allowlists or DM pairing to control who has access: `hermes pairing approve telegram XKGH5N7P`.

</Accordion>

<Accordion label="Can I use Bot Mode on a headless VPS?" group="faq">

Partly. The roster is the desktop app, so run Hermes Desktop on your laptop and connect it to the VPS from Settings, Gateways. The Bots themselves are profiles, so `hermes -p <bot> chat` and `hermes cron list` work on the server. Bot-to-bot `message_agent` needs two markers a headless install never writes: a session titled `Bot Chat` and a `ui_meta: { hermes-bots: {} }` block in a `profile.yaml`.

</Accordion>

<Accordion label="What does a roster of Bots cost?" group="faq">

There is no fixed figure; the docs publish no token numbers. Every Bot turn is a model call. A group chat is capped at 10 messages per send and 3 rounds, and Continue can add up to 5 more budgets. Pin a cheap model on worker Bots with `hermes -p <bot> model` and route the group router to one with `auxiliary.group_router`. Each Bot also carries its own keys and terminal backend, so treat it like another full agent on the box.

</Accordion>
