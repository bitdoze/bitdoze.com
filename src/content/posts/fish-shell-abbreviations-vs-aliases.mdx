If you're coming to Fish from Bash or Zsh, you probably set up aliases for frequently-used commands. Fish Shell abbreviations work differently: instead of wrapping a command in a function, they expand into the full command text on your command line before it runs. I switched all my aliases to abbreviations after a week with Fish, and in most cases that's the better deal.

This guide covers how each mechanism works, when to use which, and what changed recently, including the abbreviation descriptions that landed in fish 4.9. Everything here is pinned to fish 4.9.3 (September 2026), the current stable release.

<ListCheck>
<ul>
<li>Abbreviations expand on your command line, so history stores the real command, not a shorthand</li>
<li>Aliases wrap commands in functions, which is better for scripts, CI, and default flags</li>
<li>fish 4.9 adds <code>--description</code> so you can annotate abbreviations in the completion pager</li>
<li>Abbreviations never expand in scripts, so use a function when a shortcut must work everywhere</li>
</ul>
</ListCheck>

## What are aliases in Fish Shell?

An alias in Fish works the same as in other shells. You define a shortcut that expands to a longer command:

```fish
alias gs="git status"
alias ll="ls -la"
alias dc="docker compose"
```

When you type `gs` and press enter, Fish runs `git status`. In your command history, it saves `gs`, not `git status`.

Fish implements aliases as wrapper functions. When you run `alias gs="git status"`, Fish creates a function called `gs` that runs `git status`. You can verify this with:

```fish
type gs
# verify: output looks like this
# gs is a function with definition
# function gs --wraps='git status' --description 'alias gs=git status'
#   git status $argv
# end
```

This behavior is unchanged through fish 4.9.3. Aliases have worked this way since the early 3.x days, and there are no pending changes on master.

To make aliases persistent, add them to `~/.config/fish/config.fish` or a file in `~/.config/fish/conf.d/`.

## What are abbreviations in Fish Shell?

Abbreviations look similar when you define them:

```fish
abbr -a gs git status
abbr -a ll ls -la
abbr -a dc docker compose
```

The difference is what happens when you use them. Type `gs` and press space or enter, and Fish replaces `gs` with `git status` *on the command line* before running it. You see the full `git status` text, and that's what goes into your history.

This is a text-expansion system, not a command wrapper. The expansion is a command-line editing event: your abbreviation triggers, the text on your command line changes, and then whatever's on the line gets executed.

<Notice type="info" title="Abbreviations are interactive-only">
Abbreviations are not expanded in scripts or any non-interactive context. Only typed-in interactive commands trigger them. If you put <code>gs</code> in a shell script, it stays <code>gs</code>. It does not become <code>git status</code>.
</Notice>

## Why Fish Shell abbreviations are usually better

### Your history stays readable

With aliases, your history is full of short codes. Someone looking at `gs` in your [Fish Shell history](/fish-shell-history-persistence/) (or you, six months later) has to remember what `gs` means. With abbreviations, the history shows `git status` because that's what ran.

This also means `Ctrl+R` history search works with the real commands. Search for "git status" and you'll find it, even though you typed `gs`.

### Other people can read your screen

If you share your terminal (pair programming, screen recordings, tutorials), abbreviations show the real commands. Nobody has to decode your personal shorthand.

### You can edit before running

After an abbreviation expands, the full text is on your command line and you can modify it. Type `gs`, press space (it expands to `git status`), then add `--short` at the end to get `git status --short`. With aliases, you can't easily insert flags into the middle of the aliased command.

### No function overhead

Aliases create wrapper functions that sit in your function namespace. Abbreviations don't. They're pure text replacement. The practical difference is tiny, but abbreviations are conceptually simpler: nothing exists at runtime until you type the trigger.

## When to use Fish Shell aliases instead

Abbreviations are the default choice, but aliases (or rather, the functions behind them) still win in three cases.

### When you need to wrap command arguments

If your shortcut needs to manipulate arguments in ways that go beyond text replacement, a [custom Fish Shell function](/fish-shell-functions-custom-commands/) makes more sense:

```fish
# This needs to be a function, not an abbreviation
function mkcd
    mkdir -p $argv[1] && cd $argv[1]
end
```

An abbreviation can only expand text. It can't create a directory and then change into it using the same argument twice.

### When you need default flags on existing commands

If you want `ls` to always use `--color=auto`, an alias works:

```fish
alias ls="ls --color=auto"
```

You could do this with an abbreviation, but the expansion would be visible every time, which gets noisy for commands you run constantly.

### When the shortcut must work in scripts, config.fish or CI

This is the case that catches people off guard. Abbreviations never expand in scripts. An alias-backed function works everywhere: `config.fish`, CI job scripts, Makefiles, other shell scripts.

<Tabs>
<Tab name="Interactive shell">
```fish
# You type:
gs
# Fish expands it to git status before running.
# Works fine. Abbreviations expand here.
```
</Tab>
<Tab name="In a script">
```bash
# deploy.sh
gs   # stays literal "gs"; no expansion happens
# The script fails with: gs: command not found
# Use "git status" directly, or define a function.
```
</Tab>
</Tabs>

<Notice type="warning" title="Scripts and abbreviations don't mix">
If a shortcut must work in scripts, CI pipelines, or any non-interactive context, use a function or alias. Abbreviations only exist on the interactive command line.
</Notice>

A practical rule: abbreviations for interactive muscle-memory, functions for anything that needs to run unattended.

## Fish Shell abbreviation features (as of fish 4.9)

Fish abbreviations have gotten more powerful over the 4.x series. This section covers the features as of fish 4.9.3 (September 2026). If you're on an older 4.x, most of this applies. The notable additions are called out with version numbers.

One quick related flag: since fish 4.3.3, `abbr` supports `--color auto|always|never` to control syntax highlighting of its output. This pairs well with [Fish Shell syntax highlighting](/fish-shell-syntax-highlighting/) if you want your abbreviation listing to look consistent with your prompt.

### Position: command vs. anywhere

By default, abbreviations only expand when they're in command position (the first word on the line):

```fish
abbr -a gs git status              # only expands as a command
abbr -a -p anywhere L "| less"     # expands anywhere on the line
```

The `L` abbreviation lets you type `cat file.txt L` and it expands to `cat file.txt | less`.

A quick history note: fish 4.8.0 allowed anywhere-position abbreviations to tab-complete in argument position (issue #12630), but 4.8.1 reverted that to keep the completion pager uncluttered (issue #12838). On 4.9.x, abbreviation names show up as command-position completions only. Don't expect them in argument-position tab completion.

### Command-specific abbreviations (`--command`)

Since Fish 4.0, abbreviations can be restricted to specific commands:

```fish
abbr -a --command git co checkout
abbr -a --command git br branch
abbr -a --command docker ps "ps --format 'table {{.Names}}\t{{.Status}}'"
```

Now `co` only expands to `checkout` when the command on the line is `git`. Type `co` on its own and nothing happens.

This is great for git workflows: you can type `git co` and have it expand to `git checkout` without polluting the global abbreviation namespace. But there are four nuances the docs spell out that trip people up.

First, `--command` implies `--position anywhere`. You can't combine it with `--position command`, because the abbreviation must be able to expand mid-line (after the command word), so fish forces `anywhere` positioning. Don't fight this; it's what makes `git co` work.

Second, multiple commands use brace syntax:

```fish
abbr -a --command={git,hg} co checkout   # works with git or hg
```

Third, an empty `--command ''` means "only when there is no command":

```fish
abbr -a --command '' new "type new"   # expands only in empty command position
```

Fourth, names must be unique across all commands. You can't define `co` for `git` and a different `co` for `docker`; the second `--add` fails. If you need the same word to expand differently per command, use `--regex` with a function instead (see below).

### Abbreviation descriptions (fish 4.9+)

The headline abbreviation feature in fish 4.9.0 (issue #11291): you can attach a human-readable description to any abbreviation, and it shows up in the completion pager.

```fish
abbr -a --description "git status (expanded)" gs git status
abbr -a -d "docker compose up detached" dcu docker compose up -d
```

The `-d` flag is shorthand for `--description`. When you type the abbreviation trigger and press Tab, the pager shows your description alongside the expansion. This is useful when you have many abbreviations and want to remember *why* a shortcut exists, not just what it expands to.

It also blurs the alias/abbreviation line a bit: functions have had `--description` for ages (it shows in the `type` output), and now abbreviations can carry the same kind of annotation. For more on how the pager and suggestions work, see [Fish Shell's autocomplete and suggestions](/fish-shell-autocomplete-suggestions/).

<Notice type="info" title="Requires fish 4.9.0 or later">
The <code>-d</code>/<code>--description</code> flag is not recognized on fish 4.8.x or older. If you're on an older release, upgrade first, or the abbreviation definition will fail with an "unknown option" error.
</Notice>

To verify this, define a described abbreviation, then type its name and press Tab. The pager should show your description text next to the expansion.

### Regex abbreviations

You can use regular expressions to match abbreviation triggers. The docs ship two canonical examples worth stealing.

The first is a suffix alias (zsh-style): open any `.txt` file in vim by typing its name.

<Tabs>
<Tab name="Suffix alias (.txt files)">
```fish
function vim_edit
    vim $argv[1]
end
abbr -a --regex '.+\.txt' --position command --function vim_edit
```

Now typing `notes.txt` and pressing space expands to `vim notes.txt`. The regex uses PCRE2 syntax.
</Tab>
<Tab name="multicd (dot-dot)">
```fish
function multicd
    echo cd (string repeat -n (math (string length -- $argv[1]) - 1) ../)
end
abbr --add dotdot --regex '^\.\.+$' --function multicd
```

Type `..` to get `cd ../`, `...` to get `cd ../../`, `....` to get `cd ../../../`, and so on. This is the canonical `--regex + --function` demo from the fish docs.
</Tab>
</Tabs>

The `--function` contract applies to all function-based abbreviations, including the regex ones:

- The function receives the matching token as its first argument (`$argv[1]`).
- If the function exits 0, the token is replaced by its stdout output.
- If it exits non-zero, the token is left unchanged. Nothing happens.
- You can't provide a separate EXPANSION alongside `--function`; the function *is* the expansion.

### Cursor placement with `--set-cursor`

You can control where the cursor ends up after expansion:

```fish
abbr -a gcm --set-cursor "git commit -m '%'"
```

Type `gcm`, press space, and it expands to `git commit -m ''` with your cursor between the quotes. The `%` marker (the default) gets removed and the cursor lands there.

You can also use a custom marker and multi-line templates. Here's the docs' for-loop example:

```fish
abbr 4DIRS --set-cursor=! "$(string join \n -- 'for dir in */' 'cd $dir' '!' 'cd ..' 'end')"
```

Type `4DIRS`, press space, and you get a multi-line for-loop skeleton with the cursor at the `!` position. Abbreviations work as a lightweight snippet system, not just a way to shorten commands.

### Function-based abbreviations

For dynamic expansions, you can point an abbreviation at a function without a regex (it then matches the exact name):

```fish
function last_history_item
    echo $history[1]
end
abbr -a !! --position anywhere --function last_history_item
```

This recreates Bash's `!!` (last command) feature. Type `sudo !!` and it expands to `sudo <your-last-command>`. The same `--function` contract from the regex section applies: the function gets `!!` as `$argv[1]`, exits 0, and its output replaces the token.

## Gotchas and troubleshooting

<Notice type="warning" title="Read this before giving up on abbreviations">
These are the issues that trip people up most often. Check here before filing a bug or reverting to aliases.
</Notice>

<Accordion label="Abbreviations don't expand in scripts" group="faq" expanded="true">
You put an abbreviation trigger in a script, Makefile, or CI job and it stays literal. The script fails with "command not found".

This is by design. Fish only expands abbreviations in an interactive prompt: you don't want your scripts depending on someone's personal abbreviations.

To fix it, use the real command in scripts, or define a function (functions work everywhere):

```fish
# works in scripts and interactively
function gs
    git status $argv
end
```
</Accordion>

<Accordion label="Ctrl+Space doesn't expand the abbreviation" group="faq">
You pressed Ctrl+Space and the abbreviation stayed as-is.

That is the documented behavior. `Ctrl+Space` inserts a literal space *without* triggering expansion. It's the escape hatch for when you want the literal word, for example a filename that happens to match an abbreviation name.

Nothing is broken. Use `Ctrl+Space` to suppress expansion on purpose, and plain space or enter to expand.
</Accordion>

<Accordion label="The abbreviation didn't expand when I pressed enter" group="faq">
You typed an abbreviation, moved the cursor somewhere else on the line, pressed enter, and the unexpanded token ran (or failed).

Fish 3.7.0 (issue #8423) tightened the expansion rule: abbreviations only expand when the cursor is *adjacent* to the token (right after it) when you press space or enter. If you navigate away with arrow keys and then press enter, fish runs what's literally on the line.

Press space immediately after typing the abbreviation to expand it first, then edit the expanded line. If you already ran the unexpanded token, you just get a "command not found". Nothing destructive happens.
</Accordion>

<Accordion label="abbr --erase or --rename fails on a command-scoped abbreviation" group="faq">
You defined `abbr -a --command git co checkout`, then ran `abbr --erase co` and got an error.

For command-scoped abbreviations, `--erase` and `--rename` need the `--command` flag repeated so fish knows which abbreviation you mean. Without it, the name lookup fails.

The correct syntax:

```fish
abbr --erase --command git co     # correct
abbr --rename --command git co ci # rename within the git scope
```
</Accordion>

<Accordion label="Seeing '# imported from a universal variable' in your abbreviation list" group="faq">
Running `abbr` shows lines like `abbr -a -- foo bar # imported from a universal variable`. Your `abbr --list` output looks cluttered.

Before fish 3.6, abbreviations were stored in universal variables. Fish 3.6 moved them to regular abbreviation storage, but upgraded installs may still carry the old universal-variable data, which fish imports with a comment marker on every startup.

The cleanup recipe from the docs:

```fish
abbr >> ~/.config/fish/config.fish   # then edit out the comment lines
abbr --erase (abbr --list)           # clear the legacy entries
```

Restart fish and re-add clean abbreviations (or source the edited config). If you're on macOS and hit this after an upgrade, my [complete Fish Shell setup guide for macOS](/fish-shell-macos-setup/) covers a clean-slate approach.
</Accordion>

## Managing Fish Shell abbreviations

```fish
abbr                             # list all abbreviations (output is re-usable as commands)
abbr --show gs                   # show exact stored definition (import/export format)
abbr --list                      # list abbreviation names only
abbr --query gs; echo $status    # 0 if gs is an abbreviation
abbr --erase gs                  # remove an abbreviation
abbr --rename gs gst             # rename an abbreviation
```

Two distinctions matter here:

- `abbr --show gs` prints the clean import/export format, exactly what you'd put in a config file. Plain `abbr` (no flags) lists everything but may add `# imported from a universal variable` comments for legacy entries (see the gotchas section above).
- `abbr --query gs` returns exit status 0 if `gs` is an abbreviation. The `echo $status` after it is how you see the result in the same line.

<ListCheck>
<ul>
<li>Run <code>abbr --query gs; echo $status</code> after defining. It should print <code>0</code></li>
<li>Type the trigger and press space, then verify the expansion appears on the command line</li>
<li>Run the expanded command, then check <code>history</code>. The expanded text should be stored, not the trigger</li>
</ul>
</ListCheck>

For command-scoped abbreviations, `--erase` and `--rename` require repeating `--command`. See the gotchas section above for the exact syntax.

### Saving abbreviations

The recommended approach is to put your `abbr -a` commands in a config file:

```fish
# ~/.config/fish/conf.d/abbreviations.fish
abbr -a gs git status
abbr -a ga git add
abbr -a gc git commit
abbr -a gp git push
abbr -a gd git diff
abbr -a gl git log --oneline
abbr -a dc docker compose
abbr -a dcu docker compose up -d
abbr -a dcd docker compose down
abbr -a k kubectl
```

You can also dump your current abbreviations to a file:

```fish
abbr --show > ~/.config/fish/conf.d/abbreviations.fish
```

`abbr --show` is the cleaner dump (import/export format, no legacy comments). This saves them in a format that Fish can source directly.

<Notice type="warning" title="The redirect overwrites the file">
<code>abbr --show &gt; file</code> (or plain <code>abbr &gt; file</code>) overwrites the entire target file. It does not append. The docs recommend this intentionally: it replaces the file with a clean snapshot so you don't get duplicates or resurrect erased abbreviations. Don't use <code>&gt;&gt;</code> thinking it appends. If you want to merge, dump to a temp file and edit manually.
</Notice>

The `conf.d/` placement is the same pattern you'd use for other fish config. If you're managing tool versions like Node.js, the same directory structure applies when you [set up NVM with Fish Shell](/nvm-fish-shell/).
