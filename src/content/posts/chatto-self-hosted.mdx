## What did the July 9, 2026 Chat Control vote change?

The vote let providers of messaging and webmail services scan private messages again on a voluntary basis. The result is Regulation (EU) 2026/1881, in force since July 31, 2026 and valid until April 3, 2028.

The EU Parliament didn't pass a new surveillance law. It replaced a temporary derogation that had expired on April 3, 2026. The new text lets US tech companies scan private messages for child sexual abuse material (CSAM) if they choose to. The key word is *voluntarily*: these companies decided to run scanning, and the EU gave them legal cover to keep doing it.

The numbers tell a different story than the one politicians sell:

- **36%**: the share of abuse reports that came from mass scanning of private chats in 2024. The majority came from public posts and cloud storage, which were never affected by this law.
- **48%**: alerts from the German BKA that turned out to not be criminally relevant at all.
- **40%**: investigations triggered by chat control that ended up targeting minors themselves, not adult predators.
- **99%**: Meta's reports that consisted of previously known material, doing little to stop active abuse.
- **Zero**: evidence from the EU Commission that suspicionless scanning increased convictions or rescued children.

All five figures come from [Patrick Breyer's summary](https://www.patrick-breyer.de/en/eu-parliament-greenlights-chat-control-1-0-breyer-our-children-lose-out/) of the vote.

The regulation also excludes end-to-end encrypted communications, so WhatsApp and Signal chats are out of scope *by this vote*. Team chat tools such as Slack, Discord and Microsoft Teams do not use end-to-end encryption for text messages, so that exemption does not cover them. Discord has encrypted voice and video calls since March 2026, but not message text. ([Discord support](https://support.discord.com/hc/en-us/articles/25968222946071-End-to-End-Encryption-for-Audio-and-Video))

Chat Control 2.0, the permanent regulation, is still in trilogue. The sixth round on September 29, 2026 ended without a deal on private messages and reached provisional agreement only on scanning public content and on the EU Centre. ([Breyer, September 30, 2026](https://www.patrick-breyer.de/en/chat-control-2-0-trilogue-update-no-mass-scanning-deal-for-now-european-parliament-stands-firm-against-search-plans)) The next political trilogue is tentatively set for December 8, 2026. ([chat-control.eu](https://chat-control.eu/what-is-chat-control), checked November 16, 2026)

The practical response isn't to wait and see. It's to move your team's communication to infrastructure you own.

## What is Chatto?

Chatto is a self-hosted team chat application that Hendrik Mans open-sourced on July 8, 2026. GitHub measures the repository at 40.3% Go, 39.6% TypeScript and 9.0% Svelte, and the server, CLI and bundled frontend are licensed AGPL-3.0-or-later ([repository](https://github.com/chattocorp/chatto), November 28, 2026).

The pitch is simple: a single binary that serves its own web frontend, requires no database, and uses [NATS](https://nats.io) for persistence. It supports voice and video calls through LiveKit, encrypts data at rest with per-user keys, and includes zero third-party tracking or analytics.

![Chatto 0.6.0 web interface with the general room, messages from two members, a reaction and a three reply thread link](../../assets/images/26/07/chatto-self-hosted-ui.webp)

*Chatto 0.6.0 in a lab on November 28, 2026: the general room with a reaction and a thread of three replies.*

Current release is 0.6.0, published on November 26, 2026, with about 3,000 GitHub stars. Each server is fully isolated, with no federation by design, which is a privacy feature rather than a gap. No data leaks between servers because there's no inter-server communication at all. The docs call the project work in progress: expect bugs, frequent upgrades and breaking API changes while the version stays at 0.x.

<Button text="View Chatto on GitHub" link="https://github.com/chattocorp/chatto" variant="solid" color="blue" size="md" icon="arrow-right" />

Features in 0.6.0:

- **No database required**: NATS JetStream handles all persistence
- **Single binary**: Linux (x86_64 and ARM64), macOS, Windows and FreeBSD, or a Docker image from `ghcr.io/chattocorp/chatto`
- **Voice/video calls**: powered by LiveKit, end-to-end encrypted, includes screen sharing
- **Encryption at rest**: per-user keys with crypto-shredding on account deletion
- **SSO**: OIDC, Google, GitHub, GitLab, Discord, or an AT Protocol handle such as a Bluesky account
- **Roles and permissions**: fine-grained, room groups as permission boundaries, and a 15-minute Shield Mode for protected roles
- **Multiple servers in one client**: the desktop app and the standalone frontend connect to several Chatto servers at once
- **PWA**: install on iOS and Android from the browser; Web Push works once the operator adds VAPID keys
- **ConnectRPC API, bot webhooks and an MCP endpoint**: for bots and integrations

Rooms, threads, replies, reactions, direct messages, notifications, file attachments and full-text search are all in 0.6.0. Uploads default to a 25 MB limit and live in NATS Object Store unless you point `[core.assets.s3]` at an S3-compatible bucket. Video uploads need `CHATTO_VIDEO_ENABLED=true` and `CHATTO_ASSET_PROCESSING_ENABLED=true` in `.env`. Search runs through an optional provider; `chatto init --with-search` turns it on for the binary path.

## Self-hosting Chatto with the standalone binary

The standalone binary is the fastest way to try Chatto. Five minutes from download to running server. This path uses an embedded NATS instance, so there is no external dependency. On November 28, 2026 the 0.6.0 build answered its first request 0.5 seconds after `chatto run`.

**Step 1: download the binary**

Grab the latest release from GitHub. For Linux x86_64:

```bash
# Download the current release (check https://github.com/chattocorp/chatto/releases for newer versions)
wget https://github.com/chattocorp/chatto/releases/download/v0.6.0/chatto_Linux_x86_64.tar.gz
tar xzf chatto_Linux_x86_64.tar.gz
sudo mv chatto /usr/local/bin/chatto
```

The archive is 36 MB and unpacks a 101 MB binary named `chatto`, a `NOTICE` file and the AGPL license text. Compare the archive with `sha256sum` against `chatto_0.6.0_checksums.txt` on the release page. With Homebrew, `brew install chattocorp/tap/chatto` does the same on macOS and Linux.

For ARM64 servers (like Hetzner CAX instances):

```bash
wget https://github.com/chattocorp/chatto/releases/download/v0.6.0/chatto_Linux_arm64.tar.gz
tar xzf chatto_Linux_arm64.tar.gz
sudo mv chatto /usr/local/bin/chatto
```

**Step 2: initialize the configuration**

```bash
chatto init
```

This generates a `chatto.toml` configuration file in the current directory, 18 KB with random cookie, asset and NATS secrets. Edit it to set `webserver.url` to the public address, add your address to `owners.emails`, and fill in the SMTP section if the server must send mail. `chatto init --interactive` opens a full-screen wizard instead.

**Step 3: start the server**

```bash
chatto run
```

Chatto serves its web frontend on `http://localhost:4000`, and `/healthz`, `/livez` and `/readyz` return 200 once it is up. The listener binds every interface by default, so set `bind_address` to `127.0.0.1` when a reverse proxy on the same host terminates TLS. For production use with TLS, you can enable the built-in Let's Encrypt support in `chatto.toml` or put it behind a reverse proxy. Data lands in `./data`; set `nats.embedded.sync_interval` to `always` so JetStream fsyncs every write before acknowledging it.

**Step 4: run it as a systemd service (optional)**

For persistent operation, create `/etc/systemd/system/chatto.service` with this unit:

```ini
[Unit]
Description=Chatto
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=chatto
Group=chatto
WorkingDirectory=/opt/chatto
ExecStart=/opt/chatto/chatto run -c chatto.toml
Restart=always
RestartSec=5
AmbientCapabilities=CAP_NET_BIND_SERVICE

[Install]
WantedBy=multi-user.target
```

Make sure the `chatto` user can read `chatto.toml` and write the data directory. `CAP_NET_BIND_SERVICE` lets Chatto bind ports below 1024 for its own TLS; drop the line when a reverse proxy handles TLS.

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now chatto
```

<Notice type="info" title="When to use the binary vs Docker">
  The standalone binary is ideal for testing, personal use, or small teams with fewer than 10 users. It uses embedded NATS, which means everything runs in one process: simple, but no zero-downtime updates. The binary does not include LiveKit, so calls need a separate LiveKit server. For production deployments with multiple users, voice/video calls through LiveKit, and automatic TLS via Caddy, use the Docker Compose setup below.
</Notice>

If you haven't set up Docker yet, see our guide on [installing Docker on Ubuntu ARM](/install-docker-ubuntu-arm/).

## Self-hosting Chatto with Docker Compose

This is the recommended production setup. You get separate NATS for data persistence (survives container restarts), LiveKit for voice/video calls, and Caddy for automatic TLS.

![Flow diagram of the six setup steps: DNS and ports, the init script, SMTP, docker compose up, the first owner account and the clients](../../assets/images/26/07/chatto-self-hosted-setup-flow.webp)

*The six steps from an empty VPS to a signed-in team, with the ports and commands from the repository's Compose example.*

### Prerequisites

<ListCheck>
**What you need before starting:**
- A VPS with Docker and Compose v2 installed ([install Docker on Ubuntu ARM](/install-docker-ubuntu-arm/))
- A domain name with a DNS A record pointing to your VPS IP (e.g., `chat.example.com`)
- A `livekit.*` subdomain pointing to the same VPS (e.g., `livekit.chat.example.com`)
- SMTP or JMAP credentials for direct sign-up, email verification and password resets (the first owner account needs no email)
- (Optional) S3-compatible storage for file uploads
</ListCheck>

For VPS providers, check our [DigitalOcean vs Vultr vs Hetzner](/digitalocean-vs-vultr-vs-hetzner/) comparison. The [Hetzner Cloud review](/hetzner-cloud-review/) covers the CX23, which replaced the CX22 and costs €5.49 a month before IPv4.

Required ports:
- **TCP 80, 443**: Caddy's HTTP redirect, ACME challenge and HTTPS for both hostnames
- **TCP 7881**: LiveKit WebRTC media fallback when UDP is blocked
- **UDP 3478, 7882**: LiveKit's embedded TURN/STUN relay and direct WebRTC media

The `livekit.*` subdomain (e.g., `livekit.chat.example.com`) is only an example name. Caddy proxies it to LiveKit's WebSocket endpoint on port 7880, which browsers use for call signaling, so any hostname you control works once `CHATTO_LIVEKIT_URL` and the Caddy route match. LiveKit also needs DNS and outbound UDP for STUN-based public IP discovery.

### compose.yml walkthrough

Clone the Docker Compose example from the main Chatto repository:

```bash
git clone --depth 1 --filter=blob:none --sparse https://github.com/chattocorp/chatto.git chatto-source
git -C chatto-source sparse-checkout set examples/dockercompose
cp -R chatto-source/examples/dockercompose chatto
rm -rf chatto-source
cd chatto
```

The folder holds `compose.yml` (not `docker-compose.yml`), `init-env.sh`, `Caddyfile`, `livekit.yaml`, `nats-server.conf` and `.env.example`.

Run the initialization script to generate your `.env` file and LiveKit secrets:

```bash
chmod +x init-env.sh
./init-env.sh chat.example.com admin@example.com
```

Replace `chat.example.com` with your domain and `admin@example.com` with the email you will register with. The script writes `.env` and `livekit.generated.yaml` with matching NATS, Chatto, and LiveKit secrets, creates the `backups/` directory and sets both files to mode 600. The email goes into `CHATTO_OWNERS_EMAILS`; it does not create the account.

Open `.env` and configure your SMTP credentials:

```env
# Public hostname, used by Caddy and by Chatto for absolute URLs
PUBLIC_URL=chat.example.com
# Verified emails that receive the owner role after registration
CHATTO_OWNERS_EMAILS=admin@example.com

# NATS token, shared by the nats and chatto services (generated)
NATS_TOKEN=...
CHATTO_NATS_CLIENT_TOKEN=...
# Required since 0.6.0: the server refuses to start without it
CHATTO_WEBSERVER_URL=https://chat.example.com
CHATTO_WEBSERVER_PORT=4000

# SMTP, the default transport for direct sign-up, verification and password reset
CHATTO_SMTP_ENABLED=true
CHATTO_SMTP_HOST=smtp.sendgrid.net
CHATTO_SMTP_PORT=587
CHATTO_SMTP_TLS=mandatory
CHATTO_SMTP_USERNAME=apikey
CHATTO_SMTP_PASSWORD=your-api-key-here
CHATTO_SMTP_FROM=chat@example.com

# LiveKit settings (generated by init-env.sh)
CHATTO_LIVEKIT_URL=wss://livekit.chat.example.com
CHATTO_LIVEKIT_API_KEY=...
CHATTO_LIVEKIT_API_SECRET=...
```

The `compose.yml` defines four services:

```yaml
services:
  nats:
    image: nats:latest
    restart: unless-stopped
    command: ['--config', '/etc/nats/nats-server.conf', '--auth=${NATS_TOKEN}']
    volumes:
      - ./nats-server.conf:/etc/nats/nats-server.conf:ro
      - nats_data:/data

  livekit:
    image: livekit/livekit-server:latest
    restart: unless-stopped
    command: [--config, /etc/livekit.yaml]
    ports:
      - '7882:7882/udp' # WebRTC media (UDP, must be direct)
      - '7881:7881/tcp' # WebRTC media fallback when UDP is unavailable
      - '3478:3478/udp' # TURN/STUN relay for NAT traversal
    expose:
      - '7880' # WebSocket signaling (proxied through Caddy)
    volumes:
      - ${LIVEKIT_CONFIG_FILE:-./livekit.yaml}:/etc/livekit.yaml:ro

  chatto:
    image: ghcr.io/chattocorp/chatto:latest
    restart: unless-stopped
    env_file: .env
    environment:
      PUID: '${PUID:-1000}'
      PGID: '${PGID:-1000}'
    depends_on:
      - nats
    expose:
      - '4000'
    volumes:
      - ${CHATTO_BACKUP_DIR:-./backups}:/backups

  caddy:
    image: caddy:latest
    restart: unless-stopped
    ports:
      - '80:80'
      - '443:443'
    environment:
      PUBLIC_URL: '${PUBLIC_URL:-chat.example.com}'
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config

volumes:
  nats_data:
  caddy_data:
  caddy_config:
```

NATS reads `nats-server.conf` and fsyncs every JetStream write before acknowledging it. The Chatto container has no data volume of its own: messages and keys live in `nats_data`, and backups go to the `backups/` bind mount. Pin the image to a version such as `ghcr.io/chattocorp/chatto:0.6.0` to control when you upgrade, because `latest` follows each stable release.

### Starting and updating

Start the stack:

```bash
docker compose up -d
```

Verify everything is running:

```bash
docker compose ps
```

All four services should show as `running`. Check the health endpoint and the logs:

```bash
curl -fsS https://chat.example.com/readyz
```

### Backups and troubleshooting

Back up while Chatto is running. The command starts a temporary container, asks for a passphrase and writes a timestamped archive to `backups/`:

```bash
docker compose run --rm chatto backup --encrypt --include-keys
```

Copy the archive, the passphrase, `.env` and `livekit.generated.yaml` to another host. To restore, stop the Chatto service but keep NATS running:

```bash
docker compose stop chatto
docker compose run --rm chatto restore /backups/2026-11-28T13-28-06Z.tar.gz.age
docker compose up -d chatto
```

The restore command was not run for this article. Test it once before you rely on an archive.

The failures you are most likely to meet, with the fixes from the example's README:

- **Chatto can't connect to NATS**: `NATS_TOKEN` and `CHATTO_NATS_CLIENT_TOKEN` must match in `.env`.
- **Registration says email delivery is not configured**: set the `CHATTO_SMTP_*` values, or switch to JMAP with `CHATTO_EMAIL_TRANSPORT=jmap`.
- **Caddy not getting certificates**: both DNS records must point at the server, and ports 80 and 443 must be open.
- **Calls don't connect**: the LiveKit key and secret in `.env` must match the `keys:` block in `livekit.generated.yaml`, and `CHATTO_LIVEKIT_URL` must be the public `wss://` address.
- **LiveKit logs `could not resolve external IP`**: allow DNS and outbound UDP to the STUN servers, or set `rtc.use_external_ip: false` and `rtc.node_ip` on a host with a stable public IP.

To upgrade, run `docker compose pull` and `docker compose up -d` after reading the release notes. The FAQ below has the details and the rollback link.

## Is Chatto encrypted, and is it end to end?

Chatto encrypts message text and profile fields at rest with a per-account key and destroys that key when the account is deleted. Messages are not end to end encrypted; only voice and video calls are ([security documentation](https://docs.chatto.run/guides/operations/security/)).

"Privacy" is a marketing word until you explain the mechanism. Here's how Chatto protects your data.

![Diagram of what Chatto encrypts at rest, what stays unencrypted, and how account deletion destroys the keys](../../assets/images/26/07/chatto-self-hosted-encryption.webp)

*What Chatto 0.6.0 encrypts, what it leaves to the storage layer, and what crypto-shredding removes.*

**Encryption at rest.** Every user gets a unique encryption key. Message text, attachment descriptions and profile fields (login name, display name, bio, verified email) are encrypted with XChaCha20-Poly1305 before being written to NATS. Chatto wraps each account key with key-encryption keys that it keeps in a NATS bucket called `ENCRYPTION_KEYS`. If someone gains raw access to the NATS event stream without the keys, they can't read the messages. Attachments, avatars, filenames, authors and timestamps are not encrypted by Chatto, so the NATS or S3 storage under them needs its own protection.

**Crypto-shredding.** When a user deletes their account, their encryption keys are destroyed. The encrypted data remains on disk but is unreadable, while the user ID, timestamps and room memberships stay in the event history. This is a GDPR-friendly approach, since you can show the keys are gone. The docs add two caveats: key and file cleanup can fail and retry later, and an old backup that includes the keys makes deleted data readable again.

**No third-party tracking.** No Google Analytics, no Sentry breadcrumbs, no Mixpanel events. Chatto doesn't phone home, and self-hosted servers send no usage data to ChattoCorp. The only external connections are the ones you configure (SMTP, S3, OIDC providers).

**Server isolation.** Each Chatto server is fully independent. No federation means no data leaks between organizations. Your server knows nothing about other Chatto servers. This is a deliberate design choice, not a missing feature.

**Calls are E2EE.** Voice and video calls through LiveKit use end-to-end encryption. Chatto issues a short-lived LiveKit token and a call key to each participant. It destroys the key when the last participant leaves, so even your own server can't intercept call content.

**GDPR compliance.** Host Chatto on a European VPS (Hetzner is in Germany and Finland), and your data never leaves the EU. You are the data processor. You decide retention policies, access controls, and deletion schedules. Compare this to Slack or Discord, where data sits on US servers by default, subject to FISA warrants, National Security Letters, and now optional Chat Control scanning.

<Notice type="info" title="Messages are not end-to-end encrypted">
  Encryption at rest protects your data on disk, but Chatto messages are **not** end-to-end encrypted between clients the way Signal or WhatsApp messages are. The server can read message content in memory while processing it. This is the same model as Mattermost and Slack. If your threat model requires true E2EE for text messages (where even the server operator can't read them), Matrix with Olm/Megolm is a better fit. For most teams, encryption at rest plus server isolation is sufficient.
</Notice>

## Honest caveats and limitations

Chatto went open-source in July 2026 and reached 0.6.0 on November 26, 2026. It is not finished, and you should know what you're signing up for.

**Pre-1.0 software.** The current version is 0.6.0, published on November 26, 2026. The docs warn that 0.x releases can bring breaking API changes without notice, and 0.6.0 itself made `webserver.url` mandatory. Read the upgrade notes before each `docker compose pull`.

**Small company.** ChattoCorp GmbH develops Chatto and funds it with its Chatto Cloud hosting. The repository does not accept outside contributions, and the project's public face is Hendrik Mans, who open-sourced it. AGPL keeps the code forkable, but the bus factor is real.

**No native mobile apps yet.** Chatto works as a PWA, installed from the browser on your phone, with Web Push when the operator enables it. It's not the same as a native app. The docs say an official iOS app is in development, and each release ships an experimental desktop app for Linux, macOS and Windows.

**No E2EE for text messages.** Calls are end-to-end encrypted via LiveKit. Messages are encrypted at rest but not between clients. This is the same model as Mattermost and Slack, but it's not Signal-level privacy.

**AGPL license.** If you modify the Chatto server and offer it as a service to others, you must release your modifications under AGPL. The license also forbids presenting a fork as an official Chatto product. For internal team use, this is a non-issue. For SaaS businesses planning to white-label it, talk to a lawyer.

**Limited moderation tooling.** 0.5.0 added privileged mode, which 0.6.0 renamed Shield Mode, and 0.6.0 added a Jobs page for background work. Neither set of release notes lists a report button for messages, so a public community moderates through roles and room membership for now.

**No Slack import.** The `chatto operator import` command reads Chatto's own CHIEF format, still a draft, and the docs state that it does not accept a Slack export directly. A move from Slack starts with an empty history.

**Chat Control 1.0 leaves encrypted chats and EU providers alone.** Regulation (EU) 2026/1881 excludes end-to-end encrypted communications, and Breyer notes that European messaging providers never adopted chat control. Chat Control 2.0 could still change the rules after the December 8, 2026 trilogue.

## Final verdict: should you self-host Chatto?

Yes, if the team can spare one VPS and one administrator who reads the release notes. Chatto 0.6.0 costs about $85 a year on Hetzner and idles at 32 MiB, against $6,000 a year for Mattermost Professional.

The EU has again allowed mass scanning of private messages on major US-owned platforms. The stats show this approach doesn't work: 99% of Meta's reports are known material, 48% of alerts aren't criminally relevant, and there's zero evidence it rescued children. But the law is the law, and it runs until April 3, 2028.

You have three options:

1. **Do nothing.** Keep using Slack/Discord and accept that your team's messages are subject to scanning.
2. **Switch to an E2EE messenger.** Signal and WhatsApp protect 1:1 chats, but they're not team chat tools. No channels, no roles, no file history.
3. **Self-host Chatto.** Run a lightweight, privacy-first chat server on a VPS for €6/month. Full control, no scanning, no tracking.

Chatto isn't perfect. It's pre-1.0, has no native mobile apps, no E2EE for text messages, and depends on one small company. Those are real limitations.

The math still holds. A 36 MB download needs no database and idled at 32 MiB in the lab, with voice and video calls, SSO and encryption at rest included. Software costs $0 and hosting costs €6 a month. For a team of 50 that is about $85 a year on Hetzner against $6,000 a year for Mattermost Professional.

If you already self-host other tools on your VPS, Chatto is a natural addition to the stack. You own the server, you own the data, and no parliament vote changes that.

## FAQ

<Accordion label="Is Chatto production-ready?" group="faq">
It depends on your risk tolerance. For small teams that accept pre-1.0 instability and the occasional breaking change, yes. The core chat works today, and Chatto's own FAQ calls it safe to use with regular backups and upgrades. For deployments where uptime is non-negotiable, wait for 1.0 or use Mattermost.
</Accordion>

<Accordion label="What happens if ChattoCorp stops maintaining Chatto?" group="faq">
The AGPL license means the code stays open and anyone can fork it. NATS is an independently maintained project, so the data layer does not disappear with Chatto. The bus factor is still a planning risk, because ChattoCorp GmbH is a small company. If you need vendor-backed SLAs and multi-year support, a commercial product like Mattermost is the safer pick.
</Accordion>

<Accordion label="How do I update Chatto when a new version is released?" group="faq">
NATS data lives in the `nats_data` volume, so the Chatto container can be replaced without losing messages. Read the upgrade notes first: 0.6.0 refused to start without `CHATTO_WEBSERVER_URL`.

```bash
# Pull the new images
docker compose pull

# Recreate the containers with the new images
docker compose up -d
```

Rooms, accounts and settings survive because they are stored in `nats_data`. A lab restart on November 28, 2026 brought `/readyz` back in about 5 seconds and both test accounts were still listed.

For the full procedure with rollback, see [how to update a container with Docker Compose](/updating-container-docker-compose/). Afterwards, [clean up old Docker images](/cleanup-all-docker-things/) to free disk space. To read everything in one place, [redirect Docker logs to a single file](/redirect-docker-logs-to-a-single-file/).
</Accordion>

<Accordion label="How much RAM does Chatto need?" group="faq">
On November 28, 2026 the Compose stack idled at about 105 MiB in total. The Chatto container took 32 MiB, Caddy 48 MiB, LiveKit 14 MiB and NATS 12 MiB. After two browser sessions the Chatto container reached 60 MiB, and 35 MiB right after a restart. A 2 GB VPS covers a small team with room for LiveKit calls.
</Accordion>

<Accordion label="Does Chatto need SMTP to create the first account?" group="faq">
No. The first visit opens a setup wizard that creates a local owner account without email delivery. SMTP or JMAP is required for direct email and password registration, because Chatto sends the registration code by email. Check the transport before you invite anyone, or registration answers `email delivery is not configured`.
</Accordion>

<Accordion label="Which ports does the Compose stack need open?" group="faq">
TCP 80 and 443 for Caddy, TCP 7881 for the LiveKit media fallback, and UDP 3478 and 7882 for the TURN relay and direct WebRTC media. NATS port 4222 stays on the private Compose network. Without calls you can delete the LiveKit service and close 7881, 3478 and 7882.
</Accordion>

<Accordion label="How do you back up a self-hosted Chatto server?" group="faq">
Run `docker compose run --rm chatto backup --encrypt --include-keys` while Chatto is running. It writes a timestamped archive to the `backups/` directory and asks for a passphrase. Without `--include-keys` the archive cannot decrypt restored messages. A lab backup of a fresh server on November 28, 2026 took 37 ms.
</Accordion>

<Accordion label="Can Chatto run behind an existing reverse proxy?" group="faq">
Yes. Route the Chatto hostname to `chatto:4000` and a second hostname to `livekit:7880`, both with public TLS certificates, then delete the `caddy` service and its volumes. If the proxy runs on the Docker host, publish both upstreams on `127.0.0.1`. Keep the LiveKit `ports` entries for the media.
</Accordion>
