## Step 1: Create SSH keys on your Mac

Before touching the server, generate a key pair on your local machine. You'll use this key to log in without passwords.

Open Terminal on your Mac and run:

```sh
ssh-keygen -t ed25519 -C "your-email@example.com"
```

Press Enter to accept the default path (`~/.ssh/id_ed25519`), then set a passphrase when asked. You can leave it blank, but a passphrase adds a useful layer of protection if someone gets your laptop.

Check that the keys were created:

```sh
ls ~/.ssh/
# id_ed25519  id_ed25519.pub
```

The `.pub` file is your public key. That goes on the server. The other file never leaves your machine.

### Add the key to your SSH agent

So you don't have to type the passphrase every time:

```sh
eval "$(ssh-agent -s)"
ssh-add --apple-use-keychain ~/.ssh/id_ed25519
```

## Step 2: First login and server prep

Log into your VPS as root using the temporary password or key your provider gave you:

```sh
ssh root@your_server_ip
```

Update the system first:

```sh
apt update && apt upgrade -y
```

### Add swap space

Most budget VPS plans have limited RAM. Swap prevents out-of-memory crashes:

```sh
fallocate -l 4G /swapfile
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile
echo '/swapfile none swap sw 0 0' | tee -a /etc/fstab
```

## Step 3: Create a user and add them to sudo

Running everything as root is asking for trouble. Create a regular user for daily work:

```sh
adduser aidev
```

Follow the prompts. Set a password, skip the rest of the fields.

Add the user to the sudo group:

```sh
usermod -aG sudo aidev
```

Allow sudo without a password (since you'll be using SSH key auth, not passwords):

```sh
echo "aidev ALL=(ALL) NOPASSWD:ALL" | tee /etc/sudoers.d/aidev
chmod 0440 /etc/sudoers.d/aidev
```

### Copy your SSH public key to the new user

```sh
mkdir -p /home/aidev/.ssh
cp /root/.ssh/authorized_keys /home/aidev/.ssh/
chown -R aidev:aidev /home/aidev/.ssh
chmod 700 /home/aidev/.ssh
chmod 600 /home/aidev/.ssh/authorized_keys
```

If your root account didn't have an `authorized_keys` file (you logged in with a password), paste the contents of your local `~/.ssh/id_ed25519.pub` into `/home/aidev/.ssh/authorized_keys` manually.

### Test the new user before doing anything else

Open a second terminal on your Mac and verify the connection works:

```sh
ssh aidev@your_server_ip
```

Once inside, confirm sudo works:

```sh
sudo whoami
# root
```

<Notice type="warning" title="Lockout protection">
Keep both terminal windows open until you've finished locking things down. If you lock yourself out at any point (wrong sshd config, bad iptables rule), your provider's web console (KVM/VNC) is the recovery path. Hetzner and Hostinger both have browser-based consoles that get you back in without SSH.
</Notice>

## Step 4: Harden SSH access

Switch to the `aidev` session for the rest of this guide. Now tighten SSH so it only accepts keys and ignores passwords.

```sh
sudo nano /etc/ssh/sshd_config
```

Find and set these lines:

```
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
```

Also add a 15-minute idle timeout so abandoned sessions don't pile up:

```
ClientAliveInterval 900
ClientAliveCountMax 0
```

On Ubuntu 24.04 and 26.04, you can also drop these settings into `/etc/ssh/sshd_config.d/99-hardening.conf` instead of editing the main `sshd_config`. That is cleaner if you manage configs with Ansible or similar.

Save the file, then restart SSH:

```sh
sudo systemctl restart ssh
```

Try connecting again from your Mac to confirm it still works. If it does, your key auth is solid. If you hit "Too many authentication failures" on reconnect, your SSH client is offering too many keys. See [how to fix SSH too many authentication failures](/fix-ssh-too-many-authentication-failures/).

## Step 5: Secure the server with CrowdSec

CrowdSec watches your logs for brute-force attempts, port scans, and other bad behavior. When it spots something suspicious, it blocks the source IP. It's free and surprisingly effective. For a deeper dive into scenarios, collections, and the community blocklist, see my [full CrowdSec VPS security guide](/crowdsec-secure-server/).

### Install CrowdSec

```sh
curl -s https://install.crowdsec.net | sudo sh
sudo apt update && sudo apt install crowdsec -y
```

### Install the firewall bouncer

The bouncer drops traffic from blocked IPs:

```sh
sudo apt install crowdsec-firewall-bouncer-iptables -y
```

On nftables-first systems, the equivalent package is `crowdsec-firewall-bouncer-nftables`.

### Set up firewall rules

Allow only what you need:

```sh
# Keep existing connections alive
sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

# Allow loopback
sudo iptables -A INPUT -i lo -j ACCEPT

# Allow SSH
sudo iptables -A INPUT -p tcp --dport 22 -j ACCEPT

# Allow HTTP and HTTPS (if you later add a web service)
sudo iptables -A INPUT -p tcp --dport 80 -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 443 -j ACCEPT

# Drop everything else
sudo iptables -P INPUT DROP
```

<Notice type="info" title="Provider-side firewall">
Many providers (Hetzner Cloud firewall, Hostinger firewall) filter traffic before it reaches the VM. Set up a provider-side firewall allowing only 22/80/443 as a cheap extra layer. It also prevents lockout while you're changing local firewall rules. If you prefer UFW over raw iptables: `ufw allow 22/tcp && ufw enable`.
</Notice>

### Make firewall rules survive reboots

```sh
sudo apt install iptables-persistent -y
# Select Yes when asked to save IPv4 and IPv6 rules
sudo netfilter-persistent save
```

### Verify CrowdSec is running

```sh
sudo systemctl status crowdsec
sudo cscli collections list   # should show crowdsecurity/sshd
sudo cscli bouncers list       # should show the firewall bouncer
```

CrowdSec monitors SSH login attempts. When something looks like a brute-force attack, it bans the source IP without you lifting a finger.

Useful commands to check on it later:

```sh
sudo cscli decisions list   # active bans
sudo cscli alerts list      # recent events
sudo cscli metrics          # is it seeing sshd events?
```

The first bans can take a few minutes of brute-force traffic to appear. Seeing no decisions at minute zero is normal.

### Verify before you disconnect

Before you close that second terminal, run through this checklist:

<ListCheck><ul>
<li>SSH as <code>aidev</code> from a fresh terminal after the sshd restart</li>
<li><code>sudo ss -tlnp | grep -E ':(22|80|443)\s'</code> confirms what is listening on those ports</li>
<li><code>sudo journalctl -u ssh -n 20</code> proves key auth is working and no password attempts were accepted</li>
<li><code>sudo cscli metrics</code> shows CrowdSec is seeing sshd events</li>
<li>Second-terminal SSH test <em>before closing the first session</em> after <code>iptables -P INPUT DROP</code></li>
</ul></ListCheck>

If you lock yourself out at any point, your provider's web console (KVM/VNC) is the recovery path.

## Step 6: Set up Starship with Catppuccin theme

A good prompt makes a big difference when you're spending hours in a terminal. [Starship](/starship-ghostty-terminal/) is fast and easy to customize.

Install Starship as the `aidev` user:

```sh
curl -sS https://starship.rs/install.sh | sh
```

Add it to your shell's config. For bash:

```sh
echo 'eval "$(starship init bash)"' >> ~/.bashrc
```

### Apply the Catppuccin Mocha theme

Download the theme palette directly into your Starship config:

```sh
mkdir -p ~/.config
curl -o ~/.config/starship.toml \
  https://raw.githubusercontent.com/catppuccin/starship/refs/heads/main/themes/mocha.toml
```

Reload your shell:

```sh
source ~/.bashrc
```

Your prompt now shows Git status, the current directory, language versions, and exit codes, all in Catppuccin Mocha colors. The full setup walkthrough, including [Ghostty terminal configuration, is in this guide](/starship-ghostty-terminal/).

### Run opencode in a persistent session with tmux

If you want opencode to keep running after you disconnect, use tmux. (New to tmux? See [tmux basics for beginners](/tmux-basics/).)

```sh
sudo apt install tmux -y
```

Start a named session:

```sh
tmux new -s coding
```

Run opencode inside it, then detach with `Ctrl+B, D`. When you reconnect later, reattach with:

```sh
tmux attach -t coding
```

Your session and whatever opencode was doing will be exactly where you left it.

V2's background service can keep sessions alive even when the SSH client drops, but tmux preserves the full-screen TUI state. Keep tmux for reliability. If you just need a single terminal session from a phone or iPad, `opencode pair` is a lighter alternative to deploying Termix: it generates a one-time link (binds to `127.0.0.1`, so tunnel it with `ssh -L 49374:127.0.0.1:49374 ai-server`).

## Step 8: Configure SSH on your Mac

Now make connecting to the server as easy as typing its name. Edit your local SSH config:

```sh
nano ~/.ssh/config
```

Add this block:

```
Host ai-server
    HostName your_server_ip
    User aidev
    IdentityFile ~/.ssh/id_ed25519
    AddKeysToAgent yes
    UseKeychain yes
```

Now you can connect with just:

```sh
ssh ai-server
```

The alias covers the IP address, the username, and the key path.

## Step 9: Connect with Zed IDE

Zed has built-in remote development support. Your Mac runs the editor UI, while the actual files and processes live on the server. This keeps the UI responsive even when the server is across the world.

A few 2026 notes: Zed requires **v0.159 or newer** locally. The old relay mode (traffic routed through Zed's servers) was removed in v0.157. Everything now goes over your own SSH. That's a privacy and ops improvement: "SSH works" is the only prerequisite.

1. [Download and install Zed](https://zed.dev) on your Mac
2. Open Remote Projects with `Ctrl+Cmd+Shift+O` (or press `Cmd+Shift+P` and search for "Remote Projects")
3. Click **Connect New Server**
4. Enter your SSH host: `ssh://ai-server` (using the alias you set in `~/.ssh/config`)
5. Zed installs a small headless server on your VPS automatically
6. Once connected, choose a folder to open (e.g., `/home/aidev/projects`)

<Notice type="warning" title="Large directories">
Zed does not handle opening very large directories well (for example `/` or `~` with more than 100,000 files). Open project subfolders, not your home directory, or the editor will hang.
</Notice>

You get a full editor experience (file tree, terminal, AI features), but all the heavy work happens on the server. You can also open it from the terminal:

```sh
zed ssh://ai-server/home/aidev/projects/my-project
```

The terminal inside Zed connects directly to your server, so you can run opencode right there alongside your editor.

## Step 10: Connect with VS Code

If you prefer VS Code, the Remote SSH extension gives you a similar experience.

1. Install the [Remote - SSH extension](https://marketplace.visualstudio.com/items?itemName=ms-vscode-remote.remote-ssh) from the extensions panel
2. Press `Cmd+Shift+P` and search for **Remote-SSH: Connect to Host**
3. Select `ai-server` (it reads your `~/.ssh/config` automatically)
4. VS Code installs its server component on the VPS and opens a remote window
5. Open a folder on the server and you're in

The integrated terminal connects to the server, so you can run opencode, git, or anything else right alongside your editor. Extensions run on the server side, so Python linting, formatters, and language servers work exactly as they would locally.

One gotcha: for Starship icons to render in the VS Code integrated terminal, the Nerd Font must be installed **on your Mac** (the client renders the terminal, not the server). This trips people up when the font is only on the VPS.

## Step 11: Access from anywhere with Termix

Zed and VS Code are great when you're at your computer, but sometimes you want to jump into a terminal from a browser or another device without installing anything. [Termix](/termix-self-host/) is self-hosted server management with a web terminal that you can run on your VPS. The project lives at [Termix-SSH/Termix](https://github.com/Termix-SSH/Termix) and is very actively developed.

The full setup is covered in the [Termix self-hosting guide](/termix-self-host/). The short version: deploy Termix on your server, put it behind a reverse proxy with HTTPS, and you get a full terminal in any browser.

Once it's running, you can:
- SSH into sessions from your iPad or phone
- Share a terminal link with a collaborator
- Access your opencode sessions without installing anything on the client

If you just need one terminal session from a phone and don't want to deploy anything, `opencode pair` + an SSH tunnel (covered in Step 7) is the lighter alternative. Termix is the richer, always-on option. If you want to [control AI agents from your phone](/control-ai-agents-from-phone-moshi-herdr/) more broadly, that guide covers the pattern.

<Notice type="warning" title="Security note">
Put Termix behind authentication. The setup guide covers this, but do not skip it: a web terminal with no auth is a wide-open door. Use HTTP basic auth, an auth proxy, or Termix's built-in token system.
</Notice>

## What to do next

With the server running, here are a few things worth setting up:

### Nerd Fonts for Starship icons

Starship uses icons that only render correctly with a Nerd Font. Install one like [FiraCode Nerd Font](https://www.nerdfonts.com/) in your terminal and configure it in Zed or VS Code. Remember: for VS Code remote, the font goes on your Mac, not the server.

### Node.js or other runtimes

If you're working on JavaScript projects, install Node.js via `nvm` so you can switch versions easily. Grab build tools first. Compiling native modules without them is a classic 1 AM time sink on a fresh VPS:

```sh
sudo apt install build-essential -y
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.41.0/install.sh | bash
source ~/.bashrc
nvm install --lts
```

For the full walkthrough, see [how to install Node.js using nvm](/install-nodejs-using-nvm-macos-ubuntu/).

### Git configuration

Set your name and email on the server so commits look right:

```sh
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
```

For SSH-based GitHub access (push/pull without HTTPS tokens), [link GitHub with an SSH key](/link-github-with-ssh-maco-linux/).

<Notice type="warning" title="Backups">
Your AI agent will happily create files that exist only on this box. Commit or push after every task, or set up automated backups to S3-compatible storage. A VPS loss means code loss for anything not in git or a backup. I use [Zerobyte Restic GUI to automate backups with restic](/zerobyte-restic-gui/). It handles scheduled snapshots to S3-compatible storage without much babysitting.
</Notice>

### Automatic security updates

Keep the server patched without thinking about it:

```sh
sudo apt install unattended-upgrades -y
sudo dpkg-reconfigure --priority=low unattended-upgrades
```
