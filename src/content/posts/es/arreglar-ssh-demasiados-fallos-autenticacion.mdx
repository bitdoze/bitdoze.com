Para arreglar el error SSH "Too many authentication failures", nombra una clave y evita que el agente ofrezca el resto:

```bash
ssh -i ~/.ssh/id_ed25519_server -o IdentitiesOnly=yes deploy@10.0.0.5
```

El error significa que el cliente ofreció seis claves y sshd rechazó las seis. La conexión termina antes de que llegue la petición de contraseña o la clave que funciona. Cada clave que ofrece ssh-agent cuenta como un intento contra `MaxAuthTries` de sshd, que por defecto vale 6.

Todas las salidas de abajo son reales. El cliente es OpenSSH 9.6p1 en Ubuntu 24.04. El servidor es OpenSSH 10.0p2 en un contenedor Debian 13 desechable, al que se accede como `labuser@127.0.0.1` en el puerto 2241, con `MaxAuthTries` dejado en 6. Tómalo como tu usuario, tu host y el puerto 22. El agente guarda siete claves de prueba en `/tmp/bitdoze-refresh-ssh/keys`, de `labkey1` a `labkey7`, y solo `labkey7` está en el `authorized_keys` del servidor. A mí este error me sale cuando cambio entre servidores que usan claves distintas, así que esa es la situación que copia el laboratorio.

| Tu caso | Comando o ajuste | Contrapartida |
|---|---|---|
| Tienes la clave correcta | `ssh -i ~/.ssh/id_ed25519_server -o IdentitiesOnly=yes user@host` | Escribes la ruta de la clave cada vez |
| Quieres que pida la contraseña | `ssh -o PubkeyAuthentication=no user@host` | Escribes la contraseña en cada inicio de sesión |
| Accedes al mismo host a diario | `IdentityFile` e `IdentitiesOnly yes` en un bloque `Host` de `~/.ssh/config` | Un bloque por host que mantener |
| El agente guarda claves antiguas | `ssh-add -d ~/.ssh/id_ed25519_old`, o `ssh-add -D` para todas | `ssh-add -D` vacía el agente para todos los hosts |
| Tú llevas el servidor y los clientes no pueden cambiar | `MaxAuthTries 10` en `/etc/ssh/sshd_config.d/` | Un intento más de contraseña por conexión por cada intento extra |

## ¿Por qué ssh falla con el error "Too many authentication failures"?

El cliente ofrece cada clave de ssh-agent, una por intento, y sshd cuenta cada rechazo contra `MaxAuthTries`. Ese límite vale 6 por defecto, así que con la clave correcta en séptimo lugar de la lista, sshd desconecta después del sexto rechazo.

`MaxAuthTries` en [sshd_config(5)](https://man.openbsd.org/sshd_config) es "the maximum number of authentication attempts permitted per connection", el número máximo de intentos de autenticación permitidos por conexión. El cliente prueba las claves del agente en el orden en que este las guarda, y después los archivos de clave por defecto de `~/.ssh`.

El mismo inicio de sesión en el laboratorio:

```bash
ssh -p 2241 labuser@127.0.0.1 id -un
```

```text
Received disconnect from 127.0.0.1 port 2241:2: Too many authentication failures
Disconnected from 127.0.0.1 port 2241
```

Con `-v` puedes seguir el bucle. El agente devuelve siete claves, el cliente las ofrece en orden y la desconexión llega después de la sexta oferta:

```bash
ssh -v -p 2241 labuser@127.0.0.1 id -un 2>&1 | grep -E "agent returned|Will attempt key: labkey|Offering public key|disconnect"
```


## ¿Cómo arreglo el error SSH "Too many authentication failures"?

Añade `-o IdentitiesOnly=yes` y nombra la clave con `-i`. El cliente ofrece entonces solo esa clave en lugar de todo lo que hay en el agente.

```bash
ssh -i /tmp/bitdoze-refresh-ssh/keys/labkey7 -o IdentitiesOnly=yes -p 2241 labuser@127.0.0.1 id -un
```

```text
labuser
```

El agente sigue guardando siete claves. Con `-v`, las líneas que importan:

```text
debug1: get_agent_identities: agent returned 7 keys
debug1: Will attempt key: /tmp/bitdoze-refresh-ssh/keys/labkey7 ED25519 SHA256:iW9WkycuYQSdrl22anJrNA0J1itbOyir0Wkh5PuGi+Y explicit agent
debug1: Offering public key: /tmp/bitdoze-refresh-ssh/keys/labkey7 ED25519 SHA256:iW9WkycuYQSdrl22anJrNA0J1itbOyir0Wkh5PuGi+Y explicit agent
debug1: Server accepts key: /tmp/bitdoze-refresh-ssh/keys/labkey7 ED25519 SHA256:iW9WkycuYQSdrl22anJrNA0J1itbOyir0Wkh5PuGi+Y explicit agent
Authenticated to 127.0.0.1 ([127.0.0.1]:2241) using "publickey".
```

La palabra `explicit` marca una clave que tú nombraste.

`IdentitiesOnly` es una opción de clave pública y nada más. Con ella, según ssh_config(5), ssh usa solo las identidades de los archivos de configuración, los archivos por defecto y la línea de comandos, aunque ssh-agent ofrezca más. No desactiva la autenticación por clave y no hace nada con las contraseñas. Para que pida la contraseña, usa [PubkeyAuthentication=no](#cómo-consigo-que-pida-la-contraseña-en-vez-de-una-clave) en su lugar.

Deja `IdentitiesOnly=yes` activado aunque `-i` parezca suficiente. Una clave nombrada que está en el agente va primero. Una clave nombrada que no está va al final, después de todas las claves del agente. Aquí el laboratorio quitó `labkey7` del agente, quedaron seis claves y `-i` por sí solo falló:

```bash
ssh-add -d /tmp/bitdoze-refresh-ssh/keys/labkey7
ssh -i /tmp/bitdoze-refresh-ssh/keys/labkey7 -p 2241 labuser@127.0.0.1 id -un
```

```text
Identity removed: /tmp/bitdoze-refresh-ssh/keys/labkey7 ED25519 (labkey7)
Received disconnect from 127.0.0.1 port 2241:2: Too many authentication failures
Disconnected from 127.0.0.1 port 2241
```

El mismo inicio de sesión con `-o IdentitiesOnly=yes` lee la clave de su archivo y no ofrece nada más:

```text
debug1: get_agent_identities: agent returned 6 keys
debug1: Will attempt key: /tmp/bitdoze-refresh-ssh/keys/labkey7 ED25519 SHA256:iW9WkycuYQSdrl22anJrNA0J1itbOyir0Wkh5PuGi+Y explicit
debug1: Offering public key: /tmp/bitdoze-refresh-ssh/keys/labkey7 ED25519 SHA256:iW9WkycuYQSdrl22anJrNA0J1itbOyir0Wkh5PuGi+Y explicit
debug1: Server accepts key: /tmp/bitdoze-refresh-ssh/keys/labkey7 ED25519 SHA256:iW9WkycuYQSdrl22anJrNA0J1itbOyir0Wkh5PuGi+Y explicit
Authenticated to 127.0.0.1 ([127.0.0.1]:2241) using "publickey".
```

Si la clave vive solo en el agente y no hay ningún archivo de clave privada en el disco, nombra su archivo de clave pública: `ssh -i ~/.ssh/id_ed25519_work.pub -o IdentitiesOnly=yes`. ssh(1) toma entonces del agente la clave privada que le corresponde, como en la prueba del laboratorio con el archivo privado apartado:

```text
debug1: Will attempt key: /tmp/bitdoze-refresh-ssh/keys/labkey7.pub ED25519 SHA256:iW9WkycuYQSdrl22anJrNA0J1itbOyir0Wkh5PuGi+Y explicit agent
debug1: Server accepts key: /tmp/bitdoze-refresh-ssh/keys/labkey7.pub ED25519 SHA256:iW9WkycuYQSdrl22anJrNA0J1itbOyir0Wkh5PuGi+Y explicit agent
```

Cuando la clave que nombras es incorrecta, el cliente hace una oferta rechazada y pasa al método de contraseña. Con los intentos de contraseña desactivados, se niega de inmediato:

```bash
ssh -i /tmp/bitdoze-refresh-ssh/keys/labkey1 -o IdentitiesOnly=yes -o NumberOfPasswordPrompts=0 -p 2241 labuser@127.0.0.1 id -un
```

```text
labuser@127.0.0.1: Permission denied (publickey,password).
```

## ¿Cómo dejo IdentitiesOnly permanente para un host?

Pon `IdentityFile` e `IdentitiesOnly yes` en un bloque `Host` de `~/.ssh/config`. Un simple `ssh web1` ofrece entonces solo esa clave:

```ini
Host web1
    HostName 10.0.0.5
    User deploy
    IdentityFile ~/.ssh/id_ed25519_server
    IdentitiesOnly yes
```

Con el bloque del laboratorio se entró a la primera oferta. Hazlo por host. Un bloque global `Host *` con `IdentitiesOnly yes` y sin `IdentityFile` no desactiva las claves. En el laboratorio ofreció una clave, el archivo `id_rsa` por defecto de la estación de trabajo, y nada de lo que vive solo en el agente. El mismo bloque puede guardar un puerto o un jump host, y la [guía de túneles SSH](/es/tuneles-ssh-linux/) muestra ajustes de túnel en bloques `Host`.

## ¿Cómo quito claves del agente ssh?

Lista las claves con `ssh-add -l`. Quita una con `ssh-add -d` y su archivo de clave, o todas con `ssh-add -D`.

```bash
ssh-add -l
```

```text
256 SHA256:+s9qp5Ts1Ha52dmM9x71mWvxKM5QYo2GwKexdXBvsWI labkey1 (ED25519)
...
256 SHA256:iW9WkycuYQSdrl22anJrNA0J1itbOyir0Wkh5PuGi+Y labkey7 (ED25519)
```

En el laboratorio:

```bash
ssh-add -d /tmp/bitdoze-refresh-ssh/keys/labkey1
ssh-add -D
ssh-add -l
ssh-add /tmp/bitdoze-refresh-ssh/keys/labkey7
ssh -p 2241 labuser@127.0.0.1 id -un
```

```text
Identity removed: /tmp/bitdoze-refresh-ssh/keys/labkey1 ED25519 (labkey1)
All identities removed.
The agent has no identities.
Identity added: /tmp/bitdoze-refresh-ssh/keys/labkey7 (labkey7)
labuser
```

El agente guarda las claves en el orden en que las cargas, y el cliente las ofrece en ese orden. Cuando varias tienen que quedar cargadas, carga primero la que necesitas. `ssh-add` habla con el agente indicado en `SSH_AUTH_SOCK` (ssh-agent(1)). Dentro de una sesión SSH con reenvío de agente, ese socket lleva al agente que reenviaste, así que un `ssh-add -D` ahí vacía el tuyo. `AddKeysToAgent` añade al agente cada clave que ssh lee de un archivo (ssh_config(5)), así que la lista puede crecer sin `ssh-add`. Para crear la clave primero, mira la [guía de la clave SSH para GitHub](/es/vincular-github-ssh-macos-linux/).

Un segundo agente que guarda una clave mantiene esa clave separada del resto. Selecciónalo con `IdentityAgent`:

```bash
eval "$(ssh-agent -a ~/.ssh/agent-work -s)"
ssh-add ~/.ssh/id_ed25519_work
ssh -o IdentityAgent=~/.ssh/agent-work deploy@10.0.0.5
```

El segundo agente del laboratorio guardaba una clave, y el inicio de sesión pasó a la primera oferta. En Fish la primera línea es `eval (ssh-agent -c -a ~/.ssh/agent-work)`. `ssh-agent -k` mata el agente indicado en `SSH_AGENT_PID`.

## ¿Cómo consigo que pida la contraseña en vez de una clave?

Añade `-o PubkeyAuthentication=no`. El cliente se salta entonces la autenticación por clave y pide la contraseña, incluso con siete claves en el agente:

```bash
ssh -o PubkeyAuthentication=no -p 2241 labuser@127.0.0.1 id -un
```

```text
debug1: Authentications that can continue: publickey,password
debug1: Next authentication method: password
Authenticated to 127.0.0.1 ([127.0.0.1]:2241) using "password".
```

`-o PreferredAuthentications=password` dio las mismas tres líneas en el laboratorio. Las dos opciones dejan el agente en paz, así que los demás hosts conservan sus claves. Una contraseña incorrecta es un intento fallido contra el mismo `MaxAuthTries`, y `NumberOfPasswordPrompts` te da 3 por defecto (ssh_config(5)).

## ¿Cómo subo MaxAuthTries en el servidor?

Pon el valor en un archivo dentro de `/etc/ssh/sshd_config.d/`, compruébalo con `sudo sshd -t` y ejecuta `sudo systemctl reload ssh`. Súbelo solo en un servidor que tú controlas, cuando los clientes no puedan cambiar: una estación de trabajo compartida con un solo agente, o un runner de CI.

Yo me quedaría ahí y dejaría en paz el resto de sshd. Lee el valor que sshd usa ahora:

```bash
sudo sshd -T | grep -i maxauthtries
```

```text
maxauthtries 6
```

Ubuntu y Debian leen `/etc/ssh/sshd_config.d/*.conf` antes que el resto de `sshd_config`, porque la línea `Include` está arriba del todo. Un archivo drop-in gana por tanto y deja intacto el archivo principal. El laboratorio ejecutó estos comandos como root dentro del contenedor; en un host necesitan `sudo`:

```bash
echo "MaxAuthTries 10" | sudo tee /etc/ssh/sshd_config.d/50-maxauthtries.conf
sudo sshd -t
sudo systemctl reload ssh
sudo sshd -T | grep -i maxauthtries
```

```text
MaxAuthTries 10
maxauthtries 10
```

`sshd -t` revisa toda la configuración y no imprime nada cuando está bien. Las dos líneas `ExecReload` de la unidad `ssh` son `/usr/sbin/sshd -t` y `/bin/kill -HUP $MAINPID`, así que una configuración que no pasa la prueba nunca se carga. En la familia RHEL la unidad es `sshd`, así que el comando es `sudo systemctl reload sshd`. `sshd.service` también funciona en Ubuntu y Debian, como alias de `ssh.service`.

El contenedor no tiene systemd, así que el laboratorio envió la misma señal a mano, `kill -HUP` al PID de sshd. El registro muestra sshd reiniciándose con la configuración nueva:

```text
Received SIGHUP; restarting.
Server listening on 0.0.0.0 port 22.
Server listening on :: port 22.
```

El inicio de sesión que fallaba antes, con el mismo cliente y las mismas siete claves, pasó entonces a la séptima oferta. Encima de esta línea hay seis líneas `Failed publickey` en el registro:

```text
labuser
```

```text
Accepted key ED25519 SHA256:iW9WkycuYQSdrl22anJrNA0J1itbOyir0Wkh5PuGi+Y found at /home/labuser/.ssh/authorized_keys:1
```

<Notice type="warning" title="Deja abierta una segunda sesión">
Deja una shell de root abierta en el servidor mientras cambias sshd, y ejecuta `sudo sshd -t` antes de cada reload. Una configuración que no pasa la prueba nunca se carga, pero una válida que te deja fuera (un `AllowUsers` incorrecto, un puerto cambiado) sí se carga. La vuelta atrás para este cambio es `sudo rm /etc/ssh/sshd_config.d/50-maxauthtries.conf` y el mismo reload.
</Notice>

Un drop-in roto se ve así, y `sshd -t` sale con 255:

```text
/etc/ssh/sshd_config.d/50-maxauthtries.conf line 1: MaxAuthTries integer value invalid.
```

Si el ajuste ya existe en otro sitio, sabe cuál gana. sshd_config(5) conserva "the first obtained value", el primer valor obtenido, para cada palabra clave. sshd procesa los archivos de `Include` en orden lexicográfico, y la línea `Include` está por encima de las líneas propias del archivo principal. En el laboratorio, un `MaxAuthTries 4` añadido al final de `sshd_config` perdió contra el `10` de `50-maxauthtries.conf`, y un `10-early.conf` nuevo con `MaxAuthTries 8` venció a ambos. Solo la salida de `sudo sshd -T | grep -i maxauthtries` muestra el valor en uso. Revisa el directorio antes de añadir un archivo; una máquina Ubuntu puede tener ya un `50-cloud-init.conf` dentro.

¿Cuánto cuesta? Cada intento extra es una oportunidad más de adivinar la contraseña por conexión para alguien que tiene un nombre de usuario válido. `10` deja sitio a tres claves más allá de las siete de este laboratorio. Si el objetivo es dejar fuera la fuerza bruta, [CrowdSec](/es/crowdsec-servidor-seguro/) lo consigue sin tocar `MaxAuthTries`; el resto de los mandos está en la [guía de hardening de SSH](/es/securizar-servidor-ssh-linux/).

## ¿Por qué se rechaza la clave correcta después del error en OpenSSH 9.8 o posterior?

`PerSourcePenalties` añade 5 segundos por cada inicio de sesión fallido para tu dirección, y sshd descarta las conexiones nuevas desde ella en cuanto quedan más de 15 segundos. Cuatro inicios de sesión fallidos en menos de un segundo bastan, y la clave correcta no sirve hasta que la penalización expira.

OpenSSH 9.8 (publicado el 2024-07-01) introdujo la opción, activada por defecto; `sshd -T` en el servidor del laboratorio lista `authfail:5s`, `min:15` y `max:600`. Un inicio de sesión fallido no cambia nada, porque 5 segundos quedan por debajo del umbral. Del registro del servidor después del primer inicio de sesión fallido:

```text
srclimit_penalise: ipv4: new 172.17.0.1/32 deferred penalty of 5 seconds for penalty: failed authentication
```

El segundo y el tercer inicio de sesión fallidos sumaron sus 5 segundos sin línea en el registro. El cuarto cruzó el umbral, y sshd descartó la conexión siguiente:

```text
srclimit_penalise: 172.17.0.1/32: activating ipv4 penalty of 20 seconds for penalty: failed authentication
drop connection #0 from [172.17.0.1]:37852 on [172.17.0.4]:22 penalty: failed authentication
```

Esa conexión siguiente llevaba la clave correcta, y sshd la rechazó igualmente:

```text
debug1: kex_exchange_identification: banner line 0: Not allowed at this time
kex_exchange_identification: Connection closed by remote host
Connection closed by 127.0.0.1 port 2241
```

Veinticinco segundos después, el mismo comando inició sesión. Un bucle de reintentos detrás de este error convierte una clave incorrecta en un bloqueo breve de una dirección entera. Un job de CI o un script que reintenta es un bucle así. El segundo síntoma no se parece en nada al primero. El cliente muestra una conexión cerrada antes del banner y ninguna línea "Too many".

Para ver si tu servidor tiene la función:

```bash
sudo sshd -T | grep -i persourcepenalties
```

En el servidor Debian 13 imprime una línea; en Debian 12 (OpenSSH 9.2) `grep -c` imprime `0`. Para mantener un host bastión o un runner fuera de la tabla de penalizaciones, lista su dirección en un drop-in con `PerSourcePenaltyExemptList 203.0.113.10`. sshd_config(5) acepta ahí una lista de direcciones separadas por comas (no probado en este laboratorio). sshd sigue la penalización por cada dirección IPv4 individual (`PerSourceNetBlockSize 32:128`), así que todos los que están detrás de una misma dirección NAT la comparten. Las [notas de la versión 9.8](https://www.openssh.com/txt/release-9.8) advierten sobre los servidores que reciben conexiones de direcciones detrás de NAT o proxies. Un [VPS preparado para agentes de código IA](/es/vps-configuracion-codificacion-ia/) tiene la misma forma. Cada job que corre en él sale por una misma dirección, así que un job que falla bloquea al resto.

| Ajuste | Qué limita | Por defecto | Qué ve el cliente |
|---|---|---|---|
| `MaxAuthTries` | Intentos de autenticación por conexión | 6 | `Too many authentication failures` |
| `PerSourcePenalties` (9.8 y posteriores) | Conexiones nuevas desde una dirección después de fallos | `authfail:5s`, aplicada a partir de `min:15`, hasta `max:10m` | `Connection closed by host port 22`, antes del banner |
| `MaxStartups` | Conexiones concurrentes sin autenticar | `10:30:100` | sshd descarta la conexión mientras está ocupado con clientes sin autenticar (sshd_config(5), no reproducido aquí) |
| `LoginGraceTime` | Segundos que una conexión puede tardar en iniciar sesión | 120 | sshd desconecta pasado ese tiempo si el inicio de sesión no se ha completado (sshd_config(5), no reproducido aquí) |

Los dos últimos no tienen nada que ver con este error. Si subes `MaxAuthTries`, déjalos en paz.

## ¿Por qué el mensaje dice UNKNOWN port 65535?

La conexión del cliente pasa por la tubería de un `ProxyCommand` o de un [jump host](/es/ssh-proxyjump-jumphost/) en lugar de por un socket, así que no tiene dirección de origen que imprimir. El `packet.c` de OpenSSH rellena `UNKNOWN` y el puerto `65535` para ese caso.

Una conexión directa imprime la dirección del servidor, como arriba. El laboratorio pasó por un `ProxyCommand` con las mismas siete claves:

```bash
ssh -o "ProxyCommand=nc %h %p" -p 2241 labuser@127.0.0.1 id -un
```

```text
Received disconnect from UNKNOWN port 65535:2: Too many authentication failures
Disconnected from UNKNOWN port 65535
```

Un inicio de sesión con `ProxyJump` imprimió la misma primera línea cuando el salto intermedio se autenticó con la clave correcta y el salto final ofreció las siete. Mismo error, misma solución.

## Preguntas frecuentes

<Accordion label="¿Cuántas claves pueden fallar antes de que ssh se rinda?" group="faq">
Seis por defecto: `MaxAuthTries 6` en sshd_config(5). Cada clave rechazada es un intento, así que el cliente nunca ofrece la séptima clave de tu agente. La clave que necesitas tiene que estar entre las seis primeras que prueba el cliente. Sube el número en el servidor u ofrece menos claves.
</Accordion>

<Accordion label="¿Basta con ssh -i y un archivo de clave por sí solo?" group="faq">
No siempre. El cliente ofrece primero una clave nombrada que está en el agente. Una clave nombrada que solo existe en el disco va después de todas las claves del agente, y seis de ellas terminan la conexión. Añade `-o IdentitiesOnly=yes` para que la clave nombrada sea la única que se ofrece.
</Accordion>

<Accordion label="¿Sirve IdentitiesOnly yes si inicio sesión con contraseña?" group="faq">
No. Limita la autenticación por clave pública, y el cliente sigue ofreciendo los archivos de clave por defecto de `~/.ssh`. Para que pida la contraseña usa `ssh -o PubkeyAuthentication=no user@host`, o `PreferredAuthentications=password`, que deja el agente intacto para otros hosts.
</Accordion>

<Accordion label="¿Qué cuesta subir MaxAuthTries?" group="faq">
Cada intento extra es una oportunidad más de adivinar la contraseña por conexión. Súbelo solo en servidores que tú controlas, cuando los clientes no puedan cambiar. Pon el valor en `/etc/ssh/sshd_config.d/50-maxauthtries.conf`, ejecuta `sudo sshd -t`, después `sudo systemctl reload ssh` (`sshd` en la familia RHEL), y confírmalo con `sudo sshd -T | grep -i maxauthtries`.
</Accordion>

<Accordion label="¿Por qué ssh imprime Connection closed by remote host después de inicios de sesión fallidos?" group="faq">
En OpenSSH 9.8 y posteriores, `PerSourcePenalties` añade 5 segundos por cada inicio de sesión fallido para tu dirección. En cuanto quedan más de 15 segundos, sshd descarta las conexiones nuevas durante hasta 10 minutos, antes de que el cliente ofrezca ninguna clave. Espera a que expire, o exime la dirección con `PerSourcePenaltyExemptList`.
</Accordion>

<Accordion label="¿Es UNKNOWN port 65535 un error distinto?" group="faq">
No. La conexión del cliente es una tubería hacia un salto de `ProxyCommand` o `ProxyJump`, no un socket, así que no tiene dirección de origen que imprimir y sustituye `UNKNOWN` y el puerto `65535`. Una conexión directa imprime la dirección y el puerto del servidor. La causa y la solución son las mismas.
</Accordion>

<Accordion label="¿Qué claves prueba ssh primero?" group="faq">
El cliente ofrece primero las claves nombradas con `-i` o `IdentityFile` que además están en el agente. Después van las demás claves del agente, en el orden en que este las guarda. Las claves que solo existen como archivos, nombradas o por defecto en `~/.ssh`, van después de esas. `ssh -v` imprime el orden como líneas `Will attempt key` antes de la primera oferta, así que puedes contar las claves que van delante de la que necesitas.
</Accordion>

<Accordion label="¿Reinicio o recargo sshd después de cambiar la configuración?" group="faq">
Recarga. Ejecuta primero `sudo sshd -t`, después `sudo systemctl reload ssh` (`sudo systemctl reload sshd` en la familia RHEL). La unidad envía SIGHUP, sshd vuelve a leer la configuración y las sesiones en curso siguen abiertas. Deja una segunda sesión abierta mientras lo haces.
</Accordion>
