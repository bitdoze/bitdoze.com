## Lo que Dockhand aporta

Dockhand es un gestor de contenedores Docker enfocado en seguridad, construido sobre Bun y SvelteKit. El enfoque en seguridad es lo que lo diferencia de otras opciones de este espacio.

Los requisitos de sistema de Dockhand son modestos, pero aciértalos antes de empezar.

### Instalar Docker

Si aún no tienes Docker configurado, usa el script oficial de conveniencia o mi tutorial completo:

```sh
curl -fsSL https://get.docker.com | sh
```

Tutorial completo: [Instalar Docker y Docker Compose en Ubuntu](/es/instalar-docker-ubuntu-arm/).

Verifica antes de continuar:

```sh
docker version && docker compose version
```

Necesitas una línea Client y Server en 20.10 o superior, y una versión de `docker compose` (no `docker-compose`). Si `docker version` devuelve `permission denied /var/run/docker.sock`, tu usuario no está en el grupo `docker`:

```sh
sudo usermod -aG docker $USER
# cierra sesión y vuelve a entrar, luego repite docker version
```

## Instalar Dockhand con Docker Compose

Tienes tres caminos: un único comando rápido para probar, un stack de Compose con SQLite, o uno con PostgreSQL. SQLite es la opción correcta para un solo servidor. Si buscaste `dockhand docker compose`, este es el método que recomiendo.

### Instalación rápida (un comando)

Si solo quieres verlo:

```bash
docker run -d \
  --name dockhand \
  --restart unless-stopped \
  -p 3000:3000 \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v dockhand_data:/app/data \
  fnsys/dockhand:v1.0.55
```

Fija la etiqueta de versión. `:latest` solo vale para una prueba desechable.

Verifica que arrancó:

```bash
docker logs dockhand
```

Quieres ver el banner de inicio, sin bucle de errores. Luego abre `http://ip-de-tu-servidor:3000` y completa el asistente inicial (crea la cuenta de administrador; el flujo no cambió en v1.0.55). Para una instalación permanente, usa uno de los métodos con Compose de abajo.

### Docker Compose con SQLite (recomendado para la mayoría)

Crea un directorio y el archivo compose:

```bash
mkdir -p /opt/dockhand
cd /opt/dockhand
```

Crea `compose.yaml`:

```yaml
services:
  dockhand:
    image: fnsys/dockhand:v1.0.55
    container_name: dockhand
    restart: unless-stopped
    ports:
      - "3000:3000"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - dockhand_data:/app/data
volumes:
  dockhand_data:
```

Fija la etiqueta de versión como hice aquí en lugar de usar `:latest`. Las releases semanales están muy bien hasta que una llega cuando no estás mirando. La sección de seguridad de abajo te dirá cuándo hay que mover ese pin.

Inícialo:

```bash
docker compose up -d
```

Verifica:

```bash
docker compose ps          # estado = running, sin bucle de reinicio
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000   # esperas 200
```

Abre `http://ip-de-tu-servidor:3000`. El asistente inicial te guía para crear la cuenta de administrador. SQLite es la base de datos por defecto y funciona bien en instalaciones de un solo servidor. Los datos viven en el volumen `dockhand_data`.

Fallos habituales en este paso: si el puerto 3000 ya está en uso, `ss -tlnp | grep 3000` muestra quién lo ocupa; cambia el puerto del host (`"3030:3000"`) o detén el otro servicio. Si el nombre del contenedor choca con restos anteriores, usa `docker compose -p dockhand up -d` o elimina primero el contenedor viejo. Los problemas de permisos en volúmenes solo aparecen cuando añades `PUID`/`PGID`, así que lee la sección de variables de entorno antes de hacerlo.

### Docker Compose con PostgreSQL

Si gestionas muchos contenedores o quieres la base de datos separada para las copias de seguridad, usa PostgreSQL. Requiere PostgreSQL 14+.

```yaml
services:
  postgres:
    image: postgres:16-alpine
    container_name: dockhand-db
    restart: unless-stopped
    environment:
      POSTGRES_USER: dockhand
      POSTGRES_PASSWORD: change-this-password
      POSTGRES_DB: dockhand
    volumes:
      - postgres_data:/var/lib/postgresql/data

  dockhand:
    image: fnsys/dockhand:v1.0.55
    container_name: dockhand
    restart: unless-stopped
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://dockhand:change-this-password@postgres:5432/dockhand
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - dockhand_data:/app/data
    depends_on:
      - postgres

volumes:
  postgres_data:
  dockhand_data:
```

<Notice type="warning" title="Cambia la contraseña de la base de datos">
Sustituye `change-this-password` tanto en `POSTGRES_PASSWORD` como en `DATABASE_URL` por una contraseña fuerte de verdad. Usa la misma en ambos sitios.
</Notice>

<Notice type="warning" title="No hay migración automática de SQLite a PostgreSQL">
Cambiar de base de datos significa empezar con una base de datos nueva. No hay ruta de migración de SQLite a PostgreSQL. Decídelo antes de tener datos que te importen, no después.
</Notice>

Verifica ambos servicios:

```bash
docker compose ps
docker compose logs -f dockhand
```

Ambos contenedores deberían aparecer como running/healthy, el banner de Dockhand debería verse en los logs, y `curl -s -o /dev/null -w "%{http_code}" http://localhost:3000` debería imprimir `200`. Postgres añade un segundo contenedor que respaldar y monitorizar; tenlo en cuenta en tu rutina.

## Mantente al día: la realidad de los avisos de seguridad

Esta es la sección que me hubiera gustado que existiera cuando instalé Dockhand por primera vez. El proyecto ha publicado 12 avisos de seguridad hasta ahora, y tres tandas HIGH/críticas llegaron después de v1.0.45, la release que la versión anterior de este artículo llamó "el" parche de seguridad. El mantenedor corrige rápido. Eso está bien. También significa que un pin viejo se convierte discretamente en un lastre.

| Aviso | Severidad | Problema | Corregido en |

| GHSA-f6q3-chhc-4hxm | Critical | Exec en contenedores sin autenticar vía upgrade WebSocket | v1.0.34 (2026-06-17) |

| GHSA-8vcv-cvj7-g5vx | High | Bypass del guard de rutas del explorador de archivos vía symlink + `..` (lectura arbitraria, incluida la BD y la clave de cifrado) | v1.0.55 |

<Notice type="error" title="Ruta de actualización para instalaciones antiguas">
Cualquier versión en v1.0.49 o inferior arrastra la escalada de privilegios OIDC de severidad HIGH. Cualquier cosa en v1.0.53 o inferior arrastra el escape de `.env` HIGH. Cualquier cosa en v1.0.54 o inferior arrastra el path traversal del explorador de archivos HIGH. Fija una versión, sí, pero actualiza de forma deliberada y a menudo. Subir de v1.0.48 a v1.0.55 no es una tarea de rutina: cierra tres problemas HIGH.
</Notice>

La regla de operación que sigo yo: fija una etiqueta de versión, vigila el [feed de avisos](https://github.com/Finsys/dockhand/security/advisories) y reserva cinco minutos al mes para un salto deliberado. Y trata a Dockhand como cualquier panel expuesto a internet: detrás de una VPN o de un proxy inverso autenticado, nunca a pelo en `0.0.0.0:3000` en producción. Es la misma postura que apliqué a mis propios hosts Docker, descrita en [cómo securicé mi servidor Docker tras el informe del BSI](/bsi-security-report-docker-ufw/), y si quieres la capa de red privada puedes [mantener Dockhand detrás de una VPN con un servidor Headscale/Tailscale autoalojado](/headscale-self-hosted-tailscale-setup/). En el propio equipo: [securiza SSH antes de exponer cualquier UI de gestión](/secure-ssh-server-linux/), para que el panel no sea tu única línea de defensa.

<Notice type="info" title="Considera un proxy para el socket de Docker">
El manual oficial recomienda considerar un socket proxy (por ejemplo el patrón Tecnativa/docker-socket-proxy) en lugar de montar `/var/run/docker.sock` a pelo. El socket equivale a root en el host; limitar qué llamadas de API puede hacer la UI reduce el radio de explosión de cualquier bug del panel. La sección de Hawser de abajo es la otra forma de quitar el socket del host de gestión.
</Notice>

## Configurar el escaneo de vulnerabilidades

Esta es la función de seguridad estrella de Dockhand y está incluida en el nivel gratuito. Puedes escanear tus imágenes de contenedor en busca de vulnerabilidades conocidas con Grype o Trivy, y el flujo de `dockhand vulnerability scanning` funciona por completo contra imágenes locales: nada se envía a un servicio de escaneo externo.

Tras iniciar sesión, ve a la página de ajustes y activa el escaneo de vulnerabilidades. Elige tu escáner:

<Tabs>
  <Tab name="Grype">
    Grype es la opción por defecto. Es rápido, desarrollado por Anchore, y obtiene datos de vulnerabilidades de múltiples fuentes. Los escaneos se ejecutan contra tus imágenes locales sin enviar nada a servidores externos. Desde v1.0.51 la versión incluida está fijada en grype v0.119.0, así que una actualización de Dockhand también es una actualización del escáner, al ritmo del proyecto y no al tuyo.
  </Tab>

  <Tab name="Trivy">
    Trivy de Aqua Security es la otra opción. Soporta más objetivos de escaneo (paquetes del SO, dependencias por lenguaje, archivos IaC) pero es algo más lento. La versión fijada desde v1.0.51 es trivy 0.75.0. Si necesitas escaneo más profundo más allá de las imágenes de contenedor, Trivy es la mejor elección.
  </Tab>
</Tabs>

La función safe-pull se apoya en el escaneo. Cuando Dockhand auto-actualiza un contenedor, descarga la imagen nueva, la escanea en busca de vulnerabilidades y solo hace el cambio si el escaneo pasa. Si la imagen nueva tiene problemas, tu contenedor en ejecución se queda intacto. En septiembre detectó dos actualizaciones de imagen malas en tres semanas.

<Notice type="info" title="El primer escaneo es lento">
El primer escaneo descarga la base de datos de vulnerabilidades, así que reserva unos minutos y espera una descarga pesada. Si tu daemon Docker usa el almacén de imágenes containerd (el snapshotter por defecto en instalaciones nuevas), el escaneo tenía un bug ahí hasta v1.0.49. En cualquier versión actual funciona; si los escaneos vuelven vacíos en un daemon con containerd, actualiza Dockhand primero y culpa a la herramienta, no a las imágenes. Confirma también que la imagen del escáner se descarga bien en esa primera ejecución: se necesita HTTPS saliente y DNS.
</Notice>

## Auto-actualizaciones programadas

Dockhand puede buscar imágenes de contenedor nuevas según un horario y actualizarlas automáticamente. Combinado con la protección safe-pull, es usable en la práctica. Y no lo digo a la ligera: la mayoría de herramientas de auto-actualización no verifican que la imagen nueva funcione antes de ponerla en marcha.

Esto se configura por contenedor o por stack en la UI. Eliges un horario (por ejemplo, a diario a las 3 de la mañana) y Dockhand se encarga del resto. Si una actualización falla o el contenedor nuevo no arranca bien, hace rollback.

Desde v1.0.52 hay un guard de cadena de suministro que vale la pena activar: `MINIMUM_RELEASE_AGE_HOURS` (0-720, también disponible como ajuste por entorno y global en la UI) retiene las actualizaciones hasta que una imagen nueva tenga N horas de antigüedad. No auto-actualices a una imagen publicada hace 20 minutos. Dos novedades más recientes: redeploy selectivo (redespliega un servicio sin recrear todo el stack, v1.0.52) y arranque/parada programada de contenedores (v1.0.55).

Mis valores recomendados:

<ListCheck>
<ul>
<li>Ventana de actualización: a diario a las 3 de la mañana, o cuando tu tráfico esté más tranquilo</li>
<li>Edad mínima de imagen: 24 horas (`MINIMUM_RELEASE_AGE_HOURS=24`)</li>
<li>Rollback en caso de fallo: activado</li>
<li>Notificación en caso de fallo: activada, por el canal que ya leas</li>
</ul>
</ListCheck>

Una nota operativa: fijar versiones y las auto-actualizaciones no están en conflicto si repartes el trabajo. Fija la línea major.minor en la que confías en el archivo compose, deja que safe-pull y el rollback gestionen el ruido de los parches, y lee los avisos antes de mover el pin tú mismo. Eso es lo que hago con todo lo que tiene datos reales detrás. Si quieres un actualizador dedicado que no necesita toda la UI, [Tugtainer para auto-actualizaciones dedicadas de contenedores](/tugtainer-docker-autoupdate/) cubre exactamente esa tarea.

## Configurar OIDC/SSO

El soporte OIDC es gratis en Dockhand. No necesitas un nivel de pago. Si usas Authentik, Keycloak o cualquier otro proveedor OIDC, puedes configurar el inicio de sesión único.

En la UI de Dockhand, ve a Settings y configura tu proveedor OIDC con:

- Client ID
- Client secret
- Issuer URL / Discovery URL

Los usuarios se aprovisionan automáticamente en el primer inicio de sesión. v1.0.50 endureció la gestión de sesiones: las sesiones OIDC ahora sobreviven reinicios y réplicas, lo que importa en cuanto ejecutas más de una instancia. Dos variables de entorno controlan la experiencia de inicio de sesión:

- `OIDC_AUTOLOGIN=true` se salta el formulario de login y envía a todo el mundo al IdP. Ten presente la vía de escape: `http://tu-host/login?local=1` fuerza el formulario local para que nunca te quedes fuera.
- `OIDC_END_SESSION` (por defecto `true`) también cierra la sesión en el IdP al hacer logout, no solo en local.

<Tabs>
  <Tab name="Ocultar login local">
    Mantiene las cuentas locales funcionando pero ocultas, el término medio seguro:

    ```yaml
    environment:
      DISABLE_LOCAL_LOGIN: "true"
    ```
  </Tab>

  <Tab name="Auto-login">
    Se salta el formulario de login por completo, con la vía de escape `/login?local=1`:

    ```yaml
    environment:
      OIDC_AUTOLOGIN: "true"
    ```
  </Tab>

  <Tab name="Solo SSO completo">
    Ambas a la vez. Hazlo solo después de confirmar que el login OIDC funciona en otra sesión del navegador:

    ```yaml
    environment:
      DISABLE_LOCAL_LOGIN: "true"
      OIDC_AUTOLOGIN: "true"
      OIDC_END_SESSION: "true"
    ```
  </Tab>
</Tabs>

<Notice type="warning" title="Define ORIGIN antes de activar passkeys">
El inicio de sesión con passkeys (v1.0.52) requiere que `ORIGIN` sea el origen público exacto, incluidos esquema y puerto, y HTTPS salvo en localhost. Si las opciones WebAuthn nunca aparecen en la UI, casi siempre es un desajuste de `ORIGIN`. Defínelo aunque no pienses usar passkeys hoy; no cuesta nada y además hace predecibles las redirecciones OIDC detrás de un proxy inverso.
</Notice>

<Notice type="info" title="MFA es independiente de OIDC">
Si usas cuentas locales en lugar de OIDC, Dockhand soporta MFA basado en TOTP. Cada usuario puede activarlo desde sus ajustes de perfil. Si usas OIDC, el MFA lo gestiona tu proveedor de identidad. Ten en cuenta que LDAP/AD y RBAC están en el nivel Enterprise; OIDC y MFA es lo que es gratis. Vale la pena echar un vistazo rápido a la página de precios por la línea actual si vas a comprar.
</Notice>

## Configuración de proxy inverso

Dockhand corre en el puerto 3000 por defecto. Para SSL y un dominio en condiciones, pon un proxy inverso delante. Se necesita soporte WebSocket para los logs de contenedores en vivo, la terminal web y las métricas.

<Tabs>
  <Tab name="Nginx">

```nginx
server {
    listen 443 ssl http2;
    server_name dockhand.yourdomain.com;

    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Los headers `Upgrade` y `Connection` no son opcionales. Sin ellos la UI carga pero los logs en vivo y la terminal se cuelgan para siempre.

  </Tab>

  <Tab name="Traefik">
    Añade labels al servicio de Dockhand en tu archivo compose:

    ```yaml
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.dockhand.rule=Host(`dockhand.yourdomain.com`)"
      - "traefik.http.routers.dockhand.entrypoints=websecure"
      - "traefik.http.routers.dockhand.tls.certresolver=letsencrypt"
      - "traefik.http.services.dockhand.loadbalancer.server.port=3000"
    ```

    Traefik reenvía los upgrades WebSocket por defecto. Configuración completa de Traefik: [Cómo usar Traefik como proxy inverso en Docker](/es/traefik-proxy-docker/).
  </Tab>

  <Tab name="Cloudflare Tunnels">
    Apunta un túnel a `http://localhost:3000`. SSL y la gestión de WebSocket son automáticos. Es la opción más fácil si no quieres gestionar certificados ni abrir puertos. Si prefieres no entregar el tráfico a Cloudflare, una [alternativa autoalojada a Cloudflare Tunnels](/es/pangolin-alternativa-cloudflare-tunnels/) te da la misma topología bajo tu control.
  </Tab>

  <Tab name="HTTPS nativo">
    Desde v1.0.33 Dockhand puede terminar TLS por sí mismo, la opción intermedia entre el :3000 pelado y un proxy completo:

    ```yaml
    environment:
      HTTPS_MODE: "on"
      HTTPS_CERT_PATH: "/app/data/certs/cert.pem"
      HTTPS_KEY_PATH: "/app/data/certs/key.pem"
    ```

    Monta las rutas de los certificados dentro del contenedor. El healthcheck prueba HTTPS automáticamente cuando `HTTPS_MODE=on`. Útil en una LAN o detrás de un túnel que no termina TLS; menos útil si ya usas Nginx o Traefik.
  </Tab>
</Tabs>

Verifica la ruta del proxy:

```bash
curl -I https://dockhand.yourdomain.com     # esperas 200 o 302
```

Luego abre la UI, ve a los logs de cualquier contenedor y comprueba en la pestaña Network de las devtools del navegador que haya un upgrade WebSocket `101`. En `docker logs dockhand` verás líneas `GET /api/... 101` cuando una terminal o un stream de logs esté abierto.

Los fallos aquí son predecibles: un 502 significa que el proxy no alcanza `127.0.0.1:3000`; una UI que carga pero nunca muestra logs en vivo significa que faltan los headers del upgrade WebSocket; el contenido mixto o los bucles de redirección suelen significar que `ORIGIN` o `X-Forwarded-Proto` no coinciden con la URL pública. La postura de producción es proxy inverso más autenticación, ya sea auth a nivel de proxy u OIDC contra Authentik/Keycloak, lo que enlaza con la sección de seguridad.

## Gestionar hosts remotos con Hawser

Dockhand puede gestionar Docker en máquinas remotas a través del agente Hawser. [Hawser](https://github.com/Finsys/hawser) es open source (Go, MIT), separado del propio Dockhand, en v0.2.52 a fecha de 2026-10-25. Tiene dos modos. En modo Standard el agente escucha en el puerto 2376 y Dockhand se conecta a él. Funciona para máquinas LAN y homelab con IPs estáticas, pero se requiere un `TOKEN` en cualquier bind que no sea loopback: un agente escuchando sin él expondría una API de Docker sin autenticar a la red. En modo Edge el agente hace una conexión WebSocket saliente hacia Dockhand. No entra nada, así que funciona detrás de NAT, firewalls e IPs dinámicas. Este es el modo que la mayoría quiere.

Elige Edge salvo que el host remoto tenga una ruta entrante estable y disfrutes gestionando TLS y reglas de firewall para el 2376.

Crea primero el host remoto dentro de Dockhand (Environments, luego añadir) para que genere el token del agente. Luego en la máquina remota:

<Tabs>
  <Tab name="Docker run (Edge)">

```bash
docker run -d \
  --name hawser \
  --restart unless-stopped \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -e DOCKHAND_SERVER_URL=wss://dockhand.yourdomain.com/api/hawser/connect \
  -e TOKEN=your-agent-token \
  ghcr.io/finsys/hawser:v0.2.52
```

Fija la etiqueta de Hawser igual que fijas la de Dockhand. Si prefieres no poner el token en el entorno del proceso, v0.2.48 añadió `TOKEN_FILE`: apúntalo a un archivo montado en solo lectura dentro del contenedor.

  </Tab>

  <Tab name="Instalador systemd / OpenRC">

```bash
curl -fsSL https://raw.githubusercontent.com/Finsys/hawser/main/scripts/install.sh | bash
# edita /etc/hawser/config:
#   DOCKHAND_SERVER_URL=wss://dockhand.example.com/api/hawser/connect
#   TOKEN=your-agent-token
sudo systemctl enable --now hawser
```

El instalador respeta `HAWSER_VERSION`, `STACKS_DIR` e `INSTALL_DIR`. En Alpine instala un script OpenRC y registra en `/var/log/hawser.log`; en equipos con systemd, `journalctl -u hawser -f` es tu amigo.

  </Tab>
</Tabs>

<Notice type="warning" title="v0.2.52 necesita una reinstalación completa en systemd">
v0.2.52 corrigió los pulls de registros privados y los builds de compose bajo systemd moviendo `DOCKER_CONFIG`/`TMPDIR` a un tmpfs en `/run/hawser`. Si instalaste con el script systemd en v0.2.51 o anterior, vuelve a ejecutar el instalador. Cambiar solo el binario deja el archivo unit antiguo en su sitio y la corrección del registro no se aplica.
</Notice>

El agente se conecta a tu instancia de Dockhand y el host remoto aparece en tu panel, con reconexión automática tras cortes de red. Ambos modos exponen un pequeño endpoint de salud en `/_hawser/health` en el puerto 2376; en modo Edge vincúlalo a localhost (`BIND_ADDRESS=127.0.0.1`) para que el host mantenga superficie alcanzable cero.

Hay opciones TLS para ambos modos si las necesitas: `TLS_CERT`/`TLS_KEY` en modo Standard, `CA_CERT`/`TLS_SKIP_VERIFY` en modo Edge. También existen `MAX_MESSAGE_SIZE_MB` (v0.2.49) para stacks grandes, `REQUEST_TIMEOUT`, y los flags de build de compose `--pull`/`--no-cache` (v0.2.51).

<Notice type="info" title="La misma regla de ruta 1:1 que en Arcane">
Si tus stacks de compose usan bind mounts relativos (`./config.conf:/app/config.conf`), el `STACKS_DIR` de Hawser debe ser una ruta del host montada en la misma ruta dentro del contenedor: `-v /opt/stacks:/opt/stacks -e STACKS_DIR=/opt/stacks`. Docker resuelve los orígenes de los binds en el sistema de archivos del host, así que un volumen con nombre o una ruta que no coincida rompe los mounts relativos.
</Notice>

Verifica el agente:

```bash
# en el host remoto
curl -s http://127.0.0.1:2376/_hawser/health
```

Luego en Dockhand abre Environments y confirma que el host aparece como conectado. Con systemd, `journalctl -u hawser -f` debería mostrar el handshake WSS; con Docker, `docker logs -f hawser`. Si el health check responde pero Dockhand nunca conecta, la URL está mal: el modo Edge necesita `wss://` más la ruta `/api/hawser/connect`, no solo el dominio.

## Referencia de variables de entorno

| Variable | Por defecto | Qué hace |
|---|---|---|
| `DATABASE_URL` | SQLite | Cadena de conexión a PostgreSQL |
| `PUID` / `PGID` | sin definir (el contenedor arranca como root) | Usuario/grupo propietario de archivos. El entrypoint corrige permisos y luego baja a este usuario |
| `DISABLE_LOCAL_LOGIN` | `false` | Oculta el login por contraseña cuando hay SSO activo |
| `SKIP_DF_COLLECTION` | `false` | Omite la recolección de uso de disco (útil en NAS) |
| `DATA_DIR` | `/app/data` | Ruta de directorio de datos personalizada |
| `FEAT_API_DOCS` | `false` | Sirve la documentación OpenAPI interactiva en `/api/docs` |
| `ENCRYPTION_KEY` | autogenerada | Clave AES-256 para credenciales/secretos almacenados, guardada en `DATA_DIR` |
| `ORIGIN` | sin definir | Origen público exacto (esquema + host + puerto). Obligatorio para passkeys |
| `MINIMUM_RELEASE_AGE_HOURS` | `0` | Retiene auto-actualizaciones hasta que la imagen tenga N horas (0-720) |
| `OIDC_AUTOLOGIN` | `false` | Salta el formulario de login y va directo al IdP |
| `OIDC_END_SESSION` | `true` | Cierra también la sesión en el IdP al hacer logout |
| `REGISTRY_REQUEST_TIMEOUT` | 10s | Timeout de peticiones al registro (v1.0.55) |
| `DISABLE_WHATS_NEW` | `false` | Oculta el panel What's New (v1.0.37) |
| `EXPORT_METRICS_PUBLIC` | `false` | Sirve `/metrics` sin bearer token (v1.0.55) |
| `HTTPS_MODE` | `off` | Terminación HTTPS nativa: `on` / `off` |
| `HTTPS_CERT_PATH` / `HTTPS_KEY_PATH` | sin definir | Rutas del certificado y la clave TLS para el HTTPS nativo |
| `COMPOSE_TIMEOUT` | 900s | Segundos antes de que una operación compose cuente como colgada |
| `DOCKER_API_VERSION` | auto | Sobrescribe la versión de la API de Docker para daemons antiguos |
| `HOST_DATA_DIR` / `HOST_DOCKER_SOCKET` | autodetectado | Rutas del host mapeadas dentro del contenedor |
| `DNS_RESULT_ORDER` | `ipv4first` | Pon `verbatim` en hosts con resolución IPv4 rota |
| `DOCKER_STOP_TIMEOUT` | default de compose | Segundos de espera al parar contenedores (v1.0.54) |
| `ALLOW_WEBHOOKS_WITHOUT_SECRET` | `false` | Permite webhooks de git sin secret (v1.0.46) |

Si te llevas una sola cosa de esta tabla, que sea esta:

<Notice type="error" title="Respalda tu ENCRYPTION_KEY por separado">
Las credenciales y secretos en reposo se cifran con AES-256 usando una clave almacenada en `DATA_DIR`. Una copia restaurada sobre una instancia reconstruida es ilegible sin la misma clave. Guarda una copia de `ENCRYPTION_KEY` junto a tus copias, no dentro de ellas: una entrada en el gestor de contraseñas más una copia offline. Es la trampa clásica de "copias de seguridad que no puedes restaurar", y solo te morderá una vez, en el peor momento posible.
</Notice>

Sobre `PUID`/`PGID`, el patrón que funciona con el socket de Docker:

```yaml
services:
  dockhand:
    image: fnsys/dockhand:v1.0.55
    environment:
      PUID: "1000"
      PGID: "1000"
    group_add:
      - "999"   # el GID del grupo docker: getent group docker
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - dockhand_data:/app/data
```

Pon `PUID`/`PGID` a tu usuario y añade el grupo `docker` con `group_add` en lugar de fingir que el socket lo puede leer cualquiera. Si añades `PUID`/`PGID` a una instalación que hasta ahora corría como root, haz primero un `chown -R` único de las carpetas de stacks y datos.

<Notice type="warning" title="El comportamiento de PUID cambió brevemente en v1.0.52">
v1.0.52 cambió cómo se aplica `PUID` (hacía que el contenedor corriera como ese usuario en lugar de root), y v1.0.53 lo revirtió el mismo día porque podía alterar la propiedad de los archivos de stack al actualizar (#1700, #1701). Si saltas varias versiones de golpe, revisa la propiedad de tu carpeta de stacks tras la actualización antes de culpar a la app.
</Notice>

El endpoint `/metrics` está autenticado por defecto (bearer token de API, desde v1.0.25). Una config de scrape se ve así:

```yaml
scrape_configs:
  - job_name: dockhand
    scheme: https
    metrics_path: /metrics
    authorization:
      credentials: <api-bearer-token>
    static_configs:
      - targets: ["dockhand.yourdomain.com"]
```

`EXPORT_METRICS_PUBLIC=true` (v1.0.55) elimina el requisito del token. Déjalo desactivado salvo que el endpoint de métricas esté en una red privada de confianza. Para vigilar el host en sí y no la app, [Uptime Kuma para monitorización externa](/es/instalar-uptime-kuma/) más las métricas de Dockhand cubren ambos lados.

## Solución de problemas

Para dar marcha atrás tras un mal arranque: `docker compose down` para y elimina los contenedores pero conserva el volumen `dockhand_data`. Añade `-v` solo si de verdad quieres borrar también la base de datos. Para el rollback de un contenedor de app concreto, safe-pull y el rollback de auto-actualización ya se encargan (ver la sección de auto-actualizaciones).

<Accordion label="Los logs del contenedor muestran permission denied" group="troubleshoot" expanded="true">

Síntoma: `permission denied /var/run/docker.sock` en `docker logs dockhand`, o los contenedores no aparecen en la UI.

Comprueba el grupo del socket:

```bash
getent group docker
```

No ejecutes todo como root para esquivar esto. Añade el grupo docker correctamente en el compose:

```yaml
group_add:
  - "999"   # el GID de getent group docker
```

y mantén `PUID`/`PGID` apuntando a tu usuario normal. Consulta la sección de variables de entorno para el patrón completo.

</Accordion>

<Accordion label="Los escaneos de vulnerabilidades fallan o caducan" group="troubleshoot">

El primer escaneo tarda más porque Grype o Trivy necesita descargar la base de datos de vulnerabilidades. Los siguientes son más rápidos. Si sigue agotando el tiempo, comprueba que el contenedor tenga acceso a internet (resolución DNS, HTTPS saliente) y que la imagen del escáner fijada (grype v0.119.0 / trivy 0.75.0) se descargó en el primer uso.

</Accordion>

<Accordion label="Dockhand usa demasiada CPU en mi NAS" group="troubleshoot">

Pon `SKIP_DF_COLLECTION=true` en tus variables de entorno. La recolección de uso de disco puede ser pesada en ciertos NAS con muchos puntos de montaje.

</Accordion>

<Accordion label="El agente Hawser no conecta" group="troubleshoot">

Verifica que el token es correcto y que `DOCKHAND_SERVER_URL` es alcanzable desde la máquina remota. El modo Edge es un WebSocket, así que la URL empieza por `wss://` y termina en `/api/hawser/connect`, no es solo el dominio. Si Dockhand está detrás de un proxy inverso, asegúrate de que reenvía los upgrades WebSocket. En modo Standard, Hawser se niega a arrancar sin `TOKEN` en un bind que no sea loopback; mira primero ese error en los logs del contenedor. Si tienes una instalación systemd de v0.2.51 o anterior y los pulls del registro fallan, vuelve a ejecutar el instalador (corrección de v0.2.52); cambiar solo el binario no basta.

</Accordion>

<Accordion label="Bloqueado fuera, o necesito resetear el MFA" group="troubleshoot">

Existen dos vías de escape. Si activaste `OIDC_AUTOLOGIN` y el IdP está caído o mal configurado, entra en `http://tu-host/login?local=1` para forzar el formulario de login local. Si el problema es el MFA local, `reset-mfa.sh` se incluye dentro del contenedor (desde v1.0.36):

```bash
docker exec -it dockhand reset-mfa.sh
```

Ejecútalo, resetea el usuario afectado y vuelve a activar TOTP desde la página de perfil. Si además pusiste `DISABLE_LOCAL_LOGIN=true` y perdiste acceso al IdP, ya estás editando archivos compose, así que asegúrate de que aún tienes SSH.

</Accordion>

<Accordion label="Daemon Docker viejo, errores de handshake" group="troubleshoot">

Síntoma: las llamadas a la API fallan con errores de versión de protocolo contra un engine antiguo. Ajusta `DOCKER_API_VERSION` a lo que habla tu daemon:

```yaml
environment:
  DOCKER_API_VERSION: "1.41"
```

Comprueba lo que tienes con `docker version` (la línea Server muestra la versión de API). Mejor camino a largo plazo: actualiza el engine; 20.10 es el mínimo de todos modos.

</Accordion>

<Accordion label="IPv4 roto o resolución DNS lenta" group="troubleshoot">

Síntoma: logins lentos, pulls de registro inestables, timeouts raros en hosts donde la resolución IPv4 está medio rota. Ajusta:

```yaml
environment:
  DNS_RESULT_ORDER: "verbatim"
```

El valor por defecto es `ipv4first`, correcto para la mayoría de equipos e incorrecto para el caso raro. Combínalo con `COMPOSE_TIMEOUT` si las operaciones compose mueren pronto en enlaces lentos.

</Accordion>

## Precios y licencia

Merece la pena ser claro con esto. Dockhand tiene un modelo de precios por niveles, sin cambios a fecha de 2026-10-26:

| Nivel | Coste | Qué obtienes |
|---|---|---|
| Free | 0 $ | Funciones completas para el uso permitido, OIDC/SSO incluido |
| SMB | 499 $/host/año | Derechos de uso en producción para empresas, soporte comercial, actualizaciones prioritarias |
| Enterprise | 1.499 $/host/año | RBAC, LDAP/AD, permisos por entorno, registro de auditoría, soporte dedicado |

El nivel gratuito es legítimamente completo. OIDC, MFA, escaneo de vulnerabilidades, auto-actualizaciones, copias restic, las integraciones con gestores de secretos, multi-host: todo incluido. La frase de la propia web es "We're not on sso.tax. SSO is free", y es exacta. Comparado con lo que ofrece Portainer en el nivel gratuito, este es mejor trato. Si estás decidiendo qué ejecutar en el trabajo, [las mejores apps Docker autoalojadas para empresa](/docker-containers-business/) es la lista más amplia donde encajaría esto.

Lo que el nivel gratuito no hace es eximir de la licencia en producción empresarial. Recuerda la división del inicio de la guía:

<Notice type="warning" title="El uso en producción empresarial es de pago">
Dev/test/staging/CI/eval dentro de una empresa: gratis. Producción por parte de o para cualquier empresa u organismo público: SMB (499 $/host/año) o Enterprise. Homelab, uso personal, ONG, colegios: también gratis en producción. Y nunca ofrezcas Dockhand o un fork como servicio alojado o gestionado: la licencia lo prohíbe sin un acuerdo por escrito.
</Notice>

Así que la cifra honesta de coste: si lo ejecutas en producción en el trabajo, 499 $ por host al año es el número real; tenlo en cuenta antes de desplegarlo en una flota. En un homelab, son 0 $ y seguirán siendo 0 $. RBAC, LDAP/AD y el registro de auditoría es lo que compran los 1.000 $/host/año extra del nivel Enterprise, que está pensado para quien tiene que responder ante auditores.

## Mi opinión, once meses después

Dockhand es un producto v1 que no lo parece. La UI está pulida, las funciones de seguridad funcionan, y el ritmo de actualización se ha mantenido: 42 releases de v1.0.14 a v1.0.55, 6.886 estrellas, 305 forks, 46 contribuidores, 735 commits a fecha de 2026-10-26. Un ecosistema empezó a formarse a su alrededor en septiembre: circulaban un servidor MCP de la comunidad, una integración con Home Assistant y un cliente iOS. Comprueba su estado actual antes de apostar por cualquiera de ellos.

La función safe-pull sigue siendo lo que más me gusta. Puse auto-actualizaciones en mis contenedores no críticos en septiembre y la dejé correr. Detectó dos actualizaciones de imagen malas escaneándolas antes de desplegar. Las dos veces mis contenedores en ejecución quedaron intactos y las imágenes nuevas quedaron señaladas.

Lo que me hizo dudar en febrero era la edad del proyecto: 74 commits y 7 contribuidores por aquel entonces. Esos números ya no son el problema. El contrapeso honesto ahora es el historial de avisos de seguridad: el mantenedor corrige rápido y también mete regresiones, siendo el vaivén de `PUID` en v1.0.52/53 el ejemplo más limpio. Esa combinación es exactamente la razón por la que el ciclo pin-y-actualiza importa más que el pin solo. Mantén la instancia detrás de un proxy o VPN, vigila el feed de avisos, actualiza de forma deliberada.

La otra salvedad que sigue en pie es la licencia. BSL 1.1 está bien para autoalojar, pero no es open source OSI, y una empresa que lo ejecute en producción debe los 499 $/host/año del nivel SMB. RBAC y LDAP/AD están detrás del precio Enterprise.

Si las funciones de seguridad son tu prioridad, merece la pena instalar Dockhand. Si quieres algo más curtido o totalmente open source, mira [cómo instalar Arcane](/es/instalar-arcane/). Para el resto del campo, mi [comparativa de alternativas a Portainer](/es/alternativas-portainer/) cubre Sencho, Dockge, Komodo y más.
