Esta guía muestra cómo construir un bot de IA autoalojado para Discord con [Agno](https://github.com/agno-agi/agno). Transmite las respuestas, recuerda conversaciones, busca en una base de conocimiento que tú controlas y puede delegar trabajo a agentes especializados y equipos multi-agente. Si eres nuevo en Agno, lee primero la [guía de inicio de Agno](/es/empezar-agno/) y luego vuelve aquí.

Una nota de versión por adelantado, porque si no te va a morder: el repositorio apunta actualmente a **Agno 2.5.10** mediante su `uv.lock`, mientras que PyPI publica Agno 3.1.10. Agno 3.0 es una versión con cambios rotundos que requiere una migración de base de datos, así que no actualices las dependencias a la ligera. La ruta de actualización está cubierta en [Actualización a Agno 3](#actualización-a-agno-3).

<Notice type="warning" title="Versión de Agno fijada">
El bot apunta a Agno 2.5.10. Agno 3.0+ (publicado el 2026-08-24) es una versión con cambios rotundos y necesita una migración de base de datos. `uv sync` instala el 2.5.10 bloqueado y es seguro. `uv lock --upgrade` o `uv sync -U` salta a 3.x y romperá el bot hasta que migres. Comprueba lo que estás ejecutando con `uv pip show agno`.
</Notice>

## Qué hace este bot

- Responde cuando lo `@mencionas` en Discord
- Transmite las respuestas, así el mensaje se actualiza a medida que se genera el contenido
- Guarda recuerdos y aprende tus preferencias con el tiempo
- Busca en una base de conocimiento respaldada por LanceDb o PgVector
- Ejecuta tareas programadas mediante cron más un heartbeat de 30 minutos
- Delega trabajo complejo a equipos de agentes, incluido un pool de fan-out en paralelo
- Restringe las herramientas por rol, canal y usuario, con un registro de auditoría

![Arquitectura del bot de Discord con Agno: las menciones de Discord alimentan un runtime de discord.py que enruta hacia agentes y equipos de Agno, que leen y escriben memoria SQLite o PostgreSQL, una base de conocimiento LanceDb o PgVector y memoria opcional a largo plazo de Cognee o Hindsight, con herramientas, cron, heartbeat y telemetría debajo](@assets/images/26/02/bitdoze-bot-architecture.svg)

Por debajo hay cinco piezas móviles. El runtime `discord_bot.py` gestiona las ediciones en streaming, los prefijos de enrutamiento y el control de acceso. Los agentes y equipos de Agno hacen el trabajo real; la configuración por defecto incluye un agente `main`, un agente `research`, un `delivery-team` y un pool `general-subagents` para trozos de trabajo en paralelo. El estado vive en tres almacenes: SQLite o PostgreSQL para conversaciones y memoria, LanceDb o PgVector para búsqueda de documentos, y Cognee o Hindsight opcionales para memoria semántica a largo plazo. Cron y heartbeat mantienen al bot útil cuando está inactivo, y la telemetría de ejecución más un watchdog te avisan cuando algo se atasca. Los permisos de herramientas deciden cuáles de estas capacidades se ejecutan y dónde.

## Inicio rápido

```bash
git clone https://github.com/bitdoze/bitdoze_bot.git
cd bitdoze_bot
uv sync
python scripts/setup_bot.py
```

El asistente de configuración te pide el token de Discord, las claves de API y los ajustes opcionales. Escribe `~/.bitdoze-bot/` con `config.yaml`, `.env` y los directorios de datos.

<Notice type="info" title="Lo que fija uv sync">
El repositorio incluye un `uv.lock`, así que `uv sync` es reproducible: instala Agno 2.5.10 más el conjunto exacto de dependencias con el que se construyó el bot. Es el comportamiento que quieres. Si más tarde ejecutas `uv lock --upgrade` o `uv sync -U`, traerás Agno 3.x y necesitarás la migración de la sección de actualización de abajo.
</Notice>

**Verifica la instalación:**

```bash
uv run pytest -q
uv run main.py
```

Los tests deberían pasar, y en el primer arranque deberías ver el bot conectarse en Discord. Comprueba que se están escribiendo `logs/bitdoze-bot.log` y `logs/run-telemetry.jsonl`. Si ningún log crece, el proceso murió pronto y el traceback está en tu terminal.

## Configuración del bot de Discord

1. Ve a [discord.com/developers](https://discord.com/developers) y crea una aplicación.
2. Añade un bot a la aplicación y copia el token.
3. Activa **Message Content Intent** en los privileged gateway intents del bot. Es obligatorio: el bot no puede leer el texto de las `@menciones` sin él.
4. Invita al bot a tu servidor. Permisos mínimos: Send Messages, Embed Links, Read Message History, Attach Files.
5. Pon el token en `~/.bitdoze-bot/.env` como `DISCORD_BOT_TOKEN` (o deja que lo haga el asistente).

<Notice type="warning" title="Message Content Intent es el fallo número uno">
Si el bot se conecta pero ignora todos los mensajes, el intent está desactivado en el portal de desarrolladores. Vuelve a revisar el interruptor, reinicia el bot e inténtalo de nuevo. Un 403 en el enlace de invitación significa permisos que faltan, no un problema de código.
</Notice>

**Verifica:** `@menciona` al bot en un canal que pueda leer. Deberías recibir una respuesta en streaming.

## Estructura del proyecto

```text
bitdoze-bot/
  main.py
  config.example.yaml
  docker-compose.yml
  bitdoze_bot/
    agents.py                     # agent + team construction from config
    cognee.py / cognee_tools.py   # long-term memory client and tools
    config.py                     # config schema
    cron.py                       # CRON.yaml scheduler
    discord_bot.py                # discord.py runtime, streaming, routing
    discord_runtime_utils.py
    discord_tool_fallback.py      # parser-level denied-tool guard
    discovery_tools.py            # self-improvement / learned knowledge
    heartbeat.py                  # 30-minute heartbeat loop
    logging_setup.py              # rotating file logs
    run_monitor.py                # run telemetry + watchdog
    setup_wizard.py
    tool_permissions.py           # allow/deny rules + audit log
    utils.py
  scripts/
    setup_bot.py                  # interactive setup wizard
    generate_soul.py              # SOUL.md personality generator
    setup_knowledge.py            # ingest workspace/knowledge/
  tests/
```

Los módulos que aguantan el peso son `agents.py` (cómo el YAML se convierte en objetos de Agno), `cognee.py` (memoria), `run_monitor.py` (telemetría) y `tool_permissions.py` (restricciones). Los helpers de `scripts/` son las herramientas del día dos: configura una vez, luego vuelve a ejecutar `setup_knowledge.py` cada vez que cambies documentos.

## Configuración

La configuración vive en `~/.bitdoze-bot/config.yaml`. Cada clave de abajo existe en el `config.example.yaml` del repositorio.

### Variables de entorno

```env
DISCORD_BOT_TOKEN=your_discord_token
OPENAI_API_KEY=your_api_key            # works for OpenRouter too
GITHUB_ACCESS_TOKEN=optional_github_token
GLM_API_KEY=optional_zai_key
MEMORY_DB_URL=optional_postgres_url    # memory backend: postgres
PGVECTOR_DB_URL=optional_pgvector_url  # knowledge backend: pgvector
COGNEE_API_TOKEN=optional_cognee_token
```

Los secretos se quedan en `.env`, nunca en YAML. El bot lee los *nombres* de las variables de entorno desde la configuración (`api_key_env`, `token_env`) y resuelve los valores en tiempo de ejecución.

### Configuración básica

```yaml
model:
  provider: openai_like        # Agno's OpenAILike; Agno 3 also has a native openrouter provider
  id: <pick-a-currently-free-model>   # browse https://openrouter.ai/models?max_price=0
  base_url: https://openrouter.ai/api/v1
  api_key_env: OPENAI_API_KEY
  structured_outputs: false

discord:
  token_env: DISCORD_BOT_TOKEN

runtime:
  streaming_enabled: true
  streaming_edit_interval: 1.5
  agent_timeout: 600

memory:
  backend: sqlite              # sqlite | postgres
  db_file: data/bitdoze.db     # sqlite path
  # db_url_env: MEMORY_DB_URL  # postgres: falls back to PGVECTOR_DB_URL
  mode: automatic
  enable_session_summaries: true

learning:
  enabled: true
  mode: always
  stores:
    user_profile: true
    user_memory: true
    learned_knowledge: agentic   # the bot decides when to store insights
```

La memoria es SQLite por defecto. Cambia a `backend: postgres` y define `MEMORY_DB_URL` (o `PGVECTOR_DB_URL`) cuando ya ejecutes PostgreSQL y quieras un único almacén de datos que respaldar. En Agno 3 la opción de memoria de usuario pasa a llamarse `update_memory_on_run`, que es uno de los pequeños cambios de mapeo de configuración que implica la migración.

<Notice type="warning" title="Los IDs de modelos gratuitos rotan">
Los modelos gratuitos en OpenRouter van y vienen. A fecha de 2026-10-24 solo quedan 17 modelos `:free` de 469 en total. Si todos los mensajes devuelven 401/404 `model_not_found`, tu ID de modelo ha desaparecido. Elige otro de la lista gratuita y mantén `structured_outputs: false` en los niveles gratuitos. Lo gratis es un nivel de demostración: cuenta con un modelo de pago para cualquier cosa en la que confíes.
</Notice>

<Button text="Explorar modelos gratuitos de OpenRouter" link="https://openrouter.ai/models?max_price=0" variant="outline" color="blue" size="md" />

### Streaming

Define `runtime.streaming_enabled: true` y el bot editará su mensaje de Discord a medida que llega el contenido, cada `streaming_edit_interval` segundos. Las ejecuciones de equipo vuelven al modo sin streaming, que es lo esperado. `runtime.slow_run_threshold_seconds: 45` hace que el bot publique un mensaje de "sigo trabajando" en ejecuciones largas para que la gente no asuma que murió.

### Base de conocimiento

La base de conocimiento es búsqueda vectorial sobre documentos en `workspace/knowledge/`. Elige el backend que encaje con tu infraestructura.

<Tabs>
<Tab name="LanceDb (predeterminado)">
Cero configuración. Los embeddings y los vectores viven en disco en `data/lancedb`.

```yaml
knowledge:
  enabled: true
  backend: lancedb
  embedder: text-embedding-3-small
  lance_uri: data/lancedb
  table_name: bitdoze_knowledge
  learnings_table_name: bitdoze_learnings
```

Haz copia de seguridad de `data/lancedb` junto con el resto de `~/.bitdoze-bot/`. Reconstruirlo significa re-embedir tus documentos, lo que cuesta dinero y tiempo.
</Tab>
<Tab name="PgVector (PostgreSQL)">
Usa esto cuando ya ejecutes PostgreSQL, por ejemplo la instalación de [PgVector con Docker](/deploy-pgvector-pgadmin-docker/).

```yaml
knowledge:
  enabled: true
  backend: pgvector
  embedder: text-embedding-3-small
  db_url_env: PGVECTOR_DB_URL
  table_name: bitdoze_knowledge
  learnings_table_name: bitdoze_learnings
```

`learnings_table_name` guarda el conocimiento aprendido, y se puede buscar a través de la misma KB que tus documentos.
</Tab>
</Tabs>

Después de añadir documentos, ingiérelos:

```bash
python scripts/setup_knowledge.py
```

**Verifica:** pregúntale al bot algo que solo respondan tus documentos. **Modo de fallo:** si responde desde el conocimiento general, la KB está vacía. Vuelve a ejecutar `setup_knowledge.py` y comprueba que existe `data/lancedb`.

### Memoria Cognee (opcional)

Cognee añade memoria semántica a largo plazo: el bot puede sincronizar conversaciones y recuperar contexto relevante por su cuenta.

```yaml
memory:
  cognee:
    enabled: true
    base_url: http://localhost:8000
    auth_token_env: COGNEE_API_TOKEN
    auto_sync_conversations: true
    auto_recall_enabled: true
    auto_recall_limit: 5
    auto_recall_timeout_seconds: 10
    cognify_cooldown_seconds: 60
```

El recall tiene tanto un tope como un timeout, así que las consultas de memoria no pueden disparar la latencia de respuesta. Inicia Cognee con `docker compose up -d` (ver la sección de Docker más abajo).

<Notice type="info" title="Alternativa: Hindsight">
Para un sistema de memoria más capaz, [Hindsight con Docker](/es/desplegar-hindsight-docker/) tiene una integración directa con Agno (`hindsight-agno` 0.4.20 en PyPI a fecha de 2026-10-24). Sustituye a Cognee por una memoria basada en vectores que incluye extracción de entidades, modelos mentales y cuatro estrategias de búsqueda en paralelo. Si estás eligiendo entre los dos, la comparación [Cognee vs Hindsight: qué sistema de memoria de agente autoalojar](/es/cognee-vs-hindsight/) expone las diferencias.
</Notice>

### Agentes y enrutamiento

```yaml
agents:
  default: main
  workspace_dir: workspace/agents
  definitions:
    - name: main
      tools: [web_search, hackernews, website, github, youtube, file, shell, discord, discoveries, cognee]
    - name: research
      tools: [web_search, hackernews, website, github, youtube, shell, cognee]
      skills: [web-research]
  aliases:
    engineer: software-engineer
    worker: general-subagent
  routing:
    rules:
      - agent: delivery-team
        starts_with: ["team:"]
      - agent: research
        contains: ["research:"]
      - agent: main
        channel_ids: [123456789012345678]
        user_ids: [111111111111111111]
```

Las reglas de enrutamiento coinciden con `contains` y `starts_with`, y también pueden restringirse por `channel_ids`, `user_ids` y `guild_ids`. Los alias permiten escribir `agent:engineer` en lugar de `agent:software-engineer`. Las herramientas `discovery` son lo que hace funcionar el bucle de automejora: combinadas con `learned_knowledge: agentic`, el bot guarda sus propios aprendizajes y los busca después.

### Equipos

```yaml
teams:
  definitions:
    - name: delivery-team
      members: [architect, software-engineer]
      respond_directly: true
      determine_input_for_members: true
      delegate_to_all_members: false
      add_team_history_to_members: true
      num_team_history_runs: 5
    - name: general-subagents
      members: [general-subagent, general-subagent-2, general-subagent-3]
      delegate_to_all_members: true
```

`delivery-team` es la pareja clásica: un arquitecto planifica, un ingeniero de software implementa, y el equipo responde directamente. `general-subagents` es un pool de difusión para trozos de trabajo independientes en paralelo, útil cuando puedes dividir una tarea en tres piezas que no necesitan la salida de las demás.

<Notice type="warning" title="Modos de equipo y una trampa de configuración">
No actives a la vez `delegate_to_all_members: true` y `respond_directly: true` salvo que quieras el comportamiento de difusión. El bot avisa cuando ve esto. En Agno 3 prefiere `mode:` sobre las opciones heredadas: `mode: route` reemplaza a `respond_directly: true`, y `mode: broadcast` reemplaza a `delegate_to_all_members: true`. Las opciones heredadas siguen existiendo en el constructor de Agno 3, pero `determine_input_for_members` y `add_team_history_to_members` no están documentadas ahí y la capa de configuración del bot necesitará un mapeo cuando actualice. Para patrones multi-agente más allá de este repositorio, mira cómo [construir un equipo de investigación de IA con Agno](/es/agno-squad/).
</Notice>

Forma preferida en Agno 3:

```yaml
teams:
  definitions:
    - name: delivery-team
      members: [architect, software-engineer]
      mode: route
```

### Runtime y monitorización

Estas claves deciden el comportamiento multi-usuario y cuánto gastas.

```yaml
runtime:
  max_concurrent_runs: 4
  slow_run_threshold_seconds: 45
  session_id_strategy: channel_user   # channel | user | channel_user

monitoring:
  run_telemetry: true
  telemetry_path: logs/run-telemetry.jsonl
  watchdog_enabled: true
  watchdog_threshold_seconds: 300

tool_fallback:
  denied_tools: [shell, discord]

logging:
  level: INFO
  file: logs/bitdoze-bot.log
  max_bytes: 10485760
  backup_count: 5

context:
  scope_workspace_context_by_tenant: true
  main_session_scope: dm_only
```

`session_id_strategy` y `max_concurrent_runs` son tus diales de gasto de tokens. `channel_user` mantiene separadas las conversaciones de cada usuario por canal; `user` fusiona todo lo que dice un usuario en una sola sesión. El watchdog informa de ejecuciones atascadas más de `watchdog_threshold_seconds`. Los logs de archivo rotativos (10MB x 5) capturan el detalle de auditoría de herramientas que `journalctl` no ve. `scope_workspace_context_by_tenant` aísla los archivos de contexto del workspace (`USER.md`, `MEMORY.md`, `AGENTS.md`, `SOUL.md`) por guild más usuario, que es la historia de aislamiento multi-servidor. `main_session_scope: dm_only` mantiene la sesión del agente principal fuera de los canales públicos.

### Permisos de herramientas y control de acceso

Tres capas deciden qué se ejecuta y dónde, y quieres las tres:

```yaml
tool_permissions:
  enabled: true
  default_effect: deny
  rules:
    - effect: allow
      tools: [shell]
      role_ids: [123456789012345678]
      channel_ids: [987654321098765432]
  audit:
    enabled: true
    path: logs/tool-audit.jsonl

discord:
  token_env: DISCORD_BOT_TOKEN
  access_control:
    allowed_user_ids: [111111111111111111]
    allowed_role_ids: [123456789012345678]

tool_fallback:
  denied_tools: [shell, discord]
```

La historia para "bloquear shell en público, permitirlo en un canal privado" es: una regla allow de `tool_permissions` con alcance a `channel_ids`, más `discord.access_control` para que solo tus roles puedan hablar con el bot, más las reglas de enrutamiento para la selección de agente. `tool_fallback.denied_tools` es el respaldo a nivel de parser por si una llamada a herramienta se cuela por el código generado.

**Modo de fallo:** con `default_effect: deny` y sin regla allow, el bot rechaza herramientas en silencio. Revisa `logs/tool-audit.jsonl` antes de depurar el agente.

## Añadir nuevos agentes

Crea una carpeta en `workspace/agents/<nombre>/` con dos archivos.

**agent.yaml**

```yaml
name: product-manager
enabled: true
model:
  id: z-ai/glm-5.3-flash
  base_url: https://openrouter.ai/api/v1
  api_key_env: OPENAI_API_KEY
tools: []
skills: []
```

**AGENTS.md**

```md
# Product Manager Agent

Focus on scope, priorities, and delivery risk.
```

Conéctalo a un equipo en `config.yaml`:

```yaml
teams:
  definitions:
    - name: delivery-team
      members: [architect, software-engineer, product-manager]
```

El ejemplo usa los [modelos GLM de Z.ai](https://go.bitdoze.com/glm) en OpenRouter, que es la ruta que yo mantendría: los IDs de modelo están verificados contra el catálogo de OpenRouter (`z-ai/glm-5.3-flash`, `z-ai/glm-5.3` y el resto de la familia 5.x a fecha de 2026-10-24). Si prefieres el endpoint directo de z.ai para coding (`https://api.z.ai/api/coding/paas/v4`) con `GLM_API_KEY`, verifica que sirve `glm-5.x` en tu cuenta antes de comprometerte; los IDs de OpenRouter son la opción por defecto segura.

Si quieres búsqueda web y fetch gestionados para las herramientas de tu agente en lugar de scrapers hechos a mano, las [APIs de búsqueda web y fetch de TinyFish](https://go.bitdoze.com/tinyfish) cubren eso. Y si prefieres extender un agente con servidores de herramientas externos, puedes [añadir herramientas MCP a un agente Agno](/es/agno-herramientas-mcp-context7/) de la misma forma.

## Uso en Discord

Mención normal:

```text
@YourBot help me design a migration plan
```

Forzar un agente o equipo concreto:

```text
@YourBot agent:research find papers on distributed systems
@YourBot agent:delivery-team Build and validate this feature
@YourBot team: implement the API with tests
```

Repartir trabajo en paralelo y usar alias:

```text
@YourBot agent:general-subagents summarize these three reports independently
@YourBot agent:engineer refactor the config loader
```

**Verifica:** envía una mención por cada ruta de enrutamiento (default, `agent:research`, `team:`, `agent:general-subagents`) y confirma que cada una aterriza en el agente correcto. Las respuestas del agente equivocado suelen significar una coincidencia de regla de enrutamiento que no pretendías; revisa primero los patrones `contains`/`starts_with`.

## Heartbeat y cron

**workspace/CRON.yaml**

```yaml
enabled: true
timezone: Europe/Bucharest
channel_id: 123456789012345678
jobs:
  - name: daily-status
    cron: "0 9 * * *"
    agent: main
    message: "Send a daily status update."
    session_scope: isolated
```

El heartbeat se ejecuta cada 30 minutos usando `workspace/HEARTBEAT.md`. Si devuelve exactamente `HEARTBEAT_OK`, el mensaje se suprime. Hay un agente `heartbeat` dedicado de bajo contexto con la memoria y el aprendizaje desactivados para esto, que existe para mantener bajo el gasto en reposo.

<Notice type="warning" title="Gasto en reposo y heartbeats silenciosos">
Las ejecuciones de heartbeat y cron son gasto real de tokens aunque nadie esté chateando. `session_scope: isolated` los mantiene fuera de las sesiones principales para que no contaminen el contexto. Si el heartbeat nunca se dispara: confirma que existe `workspace/HEARTBEAT.md`, y recuerda que el ack silencioso debe ser la cadena exacta `HEARTBEAT_OK`.
</Notice>

## Docker (PgVector + Cognee)

El archivo compose levanta PostgreSQL con pgvector en el puerto 5532 y una API de Cognee en `127.0.0.1:8000`.

```bash
docker compose up -d
curl http://127.0.0.1:8000/health
```

El `curl` debería devolver una respuesta healthy de tu imagen de Cognee. Trata ese endpoint como verificar-en-tu-instancia: las APIs de las imágenes cambian, y el cliente `cognee.py` de este bot espera una forma REST concreta.

<Notice type="warning" title="Fija los tags de tus imágenes">
No ejecutes `cognee/cognee:latest` en nada que te importe. Fija un tag de versión en `docker-compose.yml` (Cognee 1.6.5 existe a fecha de 2026-10-24), y usa `docker compose pull` solo para actualizaciones deliberadas. `:latest` elimina tu camino de rollback. Los datos de Cognee viven en `~/.bitdoze-bot/data/cognee` y deben formar parte de tus copias de seguridad junto con `data/bitdoze.db` y `data/lancedb`.
</Notice>

**Rollback:** `docker compose down` detiene el stack. Añade `-v` solo si pretendes borrar los volúmenes con nombre, porque eso borra tus vectores y los datos de Cognee.

Para un despliegue de Cognee más completo con copias de seguridad y actualizaciones detalladas, mira cómo [autoalojar Cognee con Docker Compose](/es/cognee-autoalojado/).

## Producción (systemd)

`~/.config/systemd/user/bitdoze-bot.service` (el repositorio también incluye `bitdoze-bot.service`):

```ini
[Unit]
Description=Bitdoze Bot
After=network.target

[Service]
WorkingDirectory=/home/you/.bitdoze-bot
ExecStart=/home/you/.local/bin/uv run main.py
Restart=always
RestartSec=5
Environment=PYTHONUNBUFFERED=1
EnvironmentFile=/home/you/.bitdoze-bot/.env

[Install]
WantedBy=default.target
```

```bash
systemctl --user daemon-reload
systemctl --user enable --now bitdoze-bot
loginctl enable-linger $USER
journalctl --user -u bitdoze-bot -f
```

`loginctl enable-linger` importa: sin él, la unidad de usuario muere cuando cierras sesión. Cualquier VPS Linux pequeño en el rango de $4-6/mes sirve para esto.

**Verifica:** `systemctl --user status bitdoze-bot` muestra active, `journalctl --user -u bitdoze-bot -f` muestra el bot en línea, y una prueba de reinicio (`systemctl --user restart bitdoze-bot`) lo devuelve. **Rollback:** `systemctl --user disable --now bitdoze-bot`.

## Actualización a Agno 3

Agno v3.0.0 (2026-08-24) es una versión con cambios rotundos. Las ejecuciones pasan de un blob JSON dentro de las sesiones a su propia tabla `agno_runs`, y aparecen nuevas tablas `agno_jobs` y `agno_tool_results`. La amplificación de escritura baja de O(N^2) a O(N), que es la razón de la migración. PyPI está en 3.1.10 (2026-10-23) en el momento de escribir esto. El propio bot apunta a Agno 2.5.10 y no se ha verificado de extremo a extremo en 3.x, así que trata esto como una guía de actualización, no como una afirmación de compatibilidad.

![Flujo de migración de Agno 2 a 3: detener el bot, hacer una copia de seguridad restaurable, ejecutar MigrationManager up, verificar get_runs, reanudar el bot, y solo entonces considerar la limpieza irreversible de la columna heredada](@assets/images/26/02/agno-2-to-3-migration.svg)

<Notice type="warning" title="Primero la copia, la limpieza al final">
Detén todos los escritores, y haz una copia de seguridad restaurable de `data/bitdoze.db` (más `data/lancedb` y `~/.bitdoze-bot/data/cognee`) antes de ejecutar la migración. `cleanup_legacy_runs_column(force=True)` elimina permanentemente el historial heredado. Es opcional, y va último. La propia documentación de Agno v3 insiste en el mismo orden: copia, migración, verificación, y solo entonces limpiar.
</Notice>

Ejecuta la migración con la misma configuración de base de datos que usa la aplicación:

```python
# migrate_to_v3.py: run with the bot STOPPED, after a restorable backup
import asyncio
from agno.db.sqlite import SqliteDb            # or PostgresDb
from agno.db.migrations.manager import MigrationManager

db = SqliteDb(db_file="data/bitdoze.db")
asyncio.run(MigrationManager(db).up())
print(db.get_runs(limit=5))                    # inspect, don't assume completion
```

Tanto SQLite como PostgreSQL están cubiertos. Una "v3 learning re-key" se ejecuta como parte de la migración y no es transaccional (read/copy/delete), que es otra razón por la que la copia va primero.

### Problemas tras la migración

- Varios parámetros de agente están renombrados. `enable_user_memories` pasa a ser `update_memory_on_run`, `search_session_history` pasa a `search_past_sessions`, `num_history_sessions` pasa a `num_past_sessions_to_search`, `num_past_session_runs` pasa a `num_past_session_runs_in_search`, y `reasoning=True` es reemplazado por `reasoning_mode`. El `config.example.yaml` del repositorio sigue usando los nombres antiguos, lo cual es en sí mismo prueba del código 2.x. Los nombres antiguos pasan en silencio y las funciones de memoria simplemente dejan de funcionar.
- LanceDb eliminó `use_tantivy`. Pasarlo lanza `TypeError`. El repositorio aún lista `tantivy` en `pyproject.toml`; en 3.x esa dependencia es peso muerto y cualquier `use_tantivy=True` explícito se rompe inmediatamente. Las tablas vectoriales anteriores a v3 consultadas con `user_id` lanzan `ValueError` y necesitan una migración de la base de datos vectorial.
- Las negativas de credenciales del workspace están activadas por defecto. Los agentes v3 se niegan a leer `.env*`, `*.pem`, `*.key`, `id_rsa*`, `.ssh/`, `.aws/`, `.kube/`, `credentials.json`, `*.tfvars` y similares. Para un bot de Discord con herramientas `file`/`shell` esto es una función. Vuelve a permitir rutas concretas con `Workspace(..., allow_paths=[...])` si realmente las necesitas.
- Para los equipos, prefiere `mode: route` / `mode: broadcast` sobre las opciones heredadas (ver la sección de Equipos más arriba).
- Las herramientas MCP son opt-in desde v3.1.0. Si añades servidores de herramientas MCP más adelante, las herramientas por defecto/de ciclo de vida ya no se cargan automáticamente.
- Las migraciones del filesystem son aparte. AgentOS Filesystem en v3.1.0 usa scripts de una sola ejecución (`migrate_filesystem_sqlite.py` / `migrate_filesystem_postgres.py`), no `MigrationManager`.

**Modos de fallo a esperar:** `TypeError` en `use_tantivy`, `ValueError` en tablas vectoriales antiguas, y rotura silenciosa de memoria por parámetros renombrados. La fuente de verdad para el resto son las páginas de migración a v3 y changelog de Agno; las ventajas de v3 que importan aquí son `offload_tool_results=True` (los resultados de herramientas de más de 16.000 caracteres pasan a AgentFS con un handle, lo que doma las herramientas de GitHub y website) y las filas por ejecución que hacen más fácil la observabilidad estilo `run_monitor.py`.

**Verifica:** `uv run pytest -q` pasa, `db.get_runs(limit=5)` devuelve historial real, luego arranca el bot y confirma que streaming, recall de memoria y búsqueda de conocimiento funcionan cada uno en una mención real de Discord.

## Solución de problemas

Checklist de primer arranque:

<ListCheck>
<ul>
<li>El bot aparece en línea en Discord</li>
<li>Una mención obtiene una respuesta en streaming</li>
<li><code>logs/bitdoze-bot.log</code> y <code>logs/run-telemetry.jsonl</code> crecen</li>
<li><code>uv pip show agno</code> reporta 2.5.10</li>
<li><code>uv run pytest -q</code> pasa</li>
</ul>
</ListCheck>

| Síntoma | Causa | Solución |
|---|---|---|
| El bot ignora las menciones | Message Content Intent está desactivado | Activa el privileged intent en el portal de desarrolladores, reinicia el bot |
| 401/404 `model_not_found` en cada mensaje | El ID de modelo gratuito rotó fuera de OpenRouter | Elige otro modelo `:free`, mantén `structured_outputs: false` |
| Versión de Agno inesperada tras `uv sync` | Ejecutaste `uv lock --upgrade` o `uv sync -U` | Comprueba `uv pip show agno`; vuelve a fijar 2.5.10 o sigue la migración a Agno 3 |
| La base de conocimiento devuelve respuestas genéricas | Documentos no ingeridos | Vuelve a ejecutar `python scripts/setup_knowledge.py` |
| Heartbeat silencioso | Falta `workspace/HEARTBEAT.md`, o el ack no es exacto | Crea el archivo, devuelve exactamente `HEARTBEAT_OK` |
| Herramientas rechazadas en silencio | `default_effect: deny` sin regla allow | Lee `logs/tool-audit.jsonl`, añade la regla allow que falta |
| Bot desconectado tras reinicio | Linger no activado o unidad no habilitada | `loginctl enable-linger $USER`, `systemctl --user enable bitdoze-bot` |
| El enlace de invitación falla con 403 | Permisos que faltan | Re-invita con Send Messages, Embed Links, Read Message History, Attach Files |

## Preguntas frecuentes

<Accordion label="¿Funciona este bot con Agno 3?" group="faq" expanded="true">
No tal cual. El repositorio apunta a Agno 2.5.10 mediante `uv.lock`, y Agno 3.0+ requiere una migración de base de datos más cambios de configuración y de código. La sección [Actualización a Agno 3](#actualización-a-agno-3) es la ruta de migración. Las opciones heredadas de equipo siguen existiendo en el constructor de 3.x, pero los parámetros de agente renombrados y la eliminación de `use_tantivy` de LanceDb significan que el propio código del bot no se ha verificado de extremo a extremo en 3.x.
</Accordion>

<Accordion label="¿Qué modelo gratuito debería usar?" group="faq">
El que `openrouter.ai/models?max_price=0` liste hoy. La lista gratuita es pequeña (17 modelos `:free` de 469 en total a fecha de 2026-10-24) y rota, así que fijar un ID gratuito en el código es una carga de mantenimiento. Para cualquier cosa en la que confíes, usa un modelo de pago; el coste por token en los modelos pequeños es lo bastante bajo como para que sea un error de redondeo frente al VPS.
</Accordion>

<Accordion label="¿SQLite o PostgreSQL para la memoria?" group="faq">
SQLite es el valor por defecto correcto para un bot de un solo servidor: menos piezas móviles, un archivo que respaldar. Cambia a PostgreSQL (`memory.backend: postgres`) cuando ya ejecutes PgVector para la base de conocimiento y quieras un solo motor de base de datos que operar. No ejecutes producción en SQLite y luego te preguntes por las escrituras concurrentes; si tienes varias instancias del bot, necesitas Postgres.
</Accordion>

<Accordion label="¿Cuánto cuesta ejecutarlo 24/7?" group="faq">
Un VPS pequeño es el suelo: unos $4-6/mes como orden de magnitud. El uso del modelo puede ser nivel gratuito, y la única dependencia de pago por defecto es `text-embedding-3-small` para la base de conocimiento. El coste continuo real es el gasto en reposo: heartbeat cada 30 minutos y trabajos cron que se ejecutan con tokens aunque nadie chatee. El agente dedicado de heartbeat, `session_scope: isolated` y `session_id_strategy` son los diales que mantienen eso a raya.
</Accordion>
