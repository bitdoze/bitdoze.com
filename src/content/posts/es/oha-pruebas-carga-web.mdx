Las pruebas de carga con oha empiezan con un comando: `oha https://example.com` envía 200 peticiones en 50 conexiones e imprime un resumen con percentiles de latencia. Su línea `Success rate` no baja con respuestas 500, así que un pipeline necesita una comprobación propia.

Todas las salidas de abajo son reales. oha está en 1.17.0, la versión actual desde el 2026-11-14, ejecutado desde el binario del release de GitHub en una estación de trabajo Linux. Los dos objetivos corrían en la misma máquina. Un contenedor nginx en 127.0.0.1:2251 servía una página estática, y un servidor Python en 127.0.0.1:2252 respondía a `/slow` tras una pausa de 100 a 300 ms. Lee las direcciones como si fueran las de tu propio host.

| Quieres | Comando |
|---|---|
| Una cifra rápida para una página | `oha --no-tui https://example.com` |
| Una ejecución a ritmo fijo | `oha -q 20 -z 30s --latency-correction --no-tui https://example.com` |
| Un POST con cuerpo JSON | `oha -m POST -T application/json -d '{"key":"value"}' https://example.com/api` |
| Un resultado que un pipeline pueda comprobar | `oha -z 30s --output-format json -o run.json https://example.com` |

## ¿Qué es oha?

oha es un generador de carga HTTP escrito en Rust y publicado bajo licencia MIT por hatoo. Abre varias conexiones y envía peticiones tan rápido como se lo permiten, o a un ritmo fijo.

Mientras corre dibuja un panel en el terminal, y al final imprime un resumen. El repositorio tenía 10,758 estrellas el 2026-11-27, y su última versión es la [1.17.0](https://github.com/hatoo/oha/releases/tag/v1.17.0). El nombre es el saludo japonés "ohayou".

oha habla HTTP y nada más. La versión 1.17.0 no tiene scripting, modo WebSocket ni navegador, y `--http-version 3` necesita una compilación con la característica `http3`.

## ¿Cómo instalo oha?

Instala oha desde el binario de su release de GitHub, con Homebrew (`brew install oha`), con `winget install hatoo.oha` en Windows, con Cargo o mediante Docker. Todas las rutas terminan en el mismo comando `oha`.

| Ruta | Comando | Nota |
|---|---|---|
| Binario del release | descarga `oha-linux-amd64` de la [página de releases](https://github.com/hatoo/oha/releases), `chmod +x`, ponlo en `PATH` | los archivos de arm64, macOS y Windows están al lado |
| Homebrew | `brew install oha` | la fórmula estaba en 1.17.0 el 2026-11-27 |
| Windows | `winget install hatoo.oha` | según el README |
| Cargo | `cargo install oha` | necesita `make` y `cmake` |
| Docker | `docker run --rm --network=host ghcr.io/hatoo/oha:1.17.0 --no-tui URL` | etiquetas `1.17.0` y `latest` |

Comprueba primero la versión:

```bash
oha --version
```

```text
oha 1.17.0
```

Una copia de Homebrew instalada antes puede ir por detrás. La de la estación de trabajo informaba de 1.16.0. `--network=host` permite al contenedor llegar a un objetivo en el `127.0.0.1` del host; en el laboratorio la imagen pidió la página de nginx 20 veces con estado 200.

### Qué significa cada línea del resumen

| Línea | Qué contiene |
|---|---|
| `Success rate` | peticiones respondidas dividido entre respondidas más las que dieron error. El código de estado no entra en la cuenta (mira la sección de fallos) |
| `Total` | tiempo de reloj de toda la ejecución, desde justo antes de que arranque el primer worker hasta que termina el último |
| `Slowest`, `Fastest`, `Average` | la duración mayor, la menor y la media de las peticiones respondidas |
| `Requests/sec` | todas las peticiones, errores incluidos, dividido entre `Total` |
| `Total data`, `Size/request`, `Size/sec` | bytes del cuerpo de las peticiones respondidas, sumados, promediados por petición y por segundo |
| `Response time histogram` | 11 cubos entre la petición respondida más rápida y la más lenta |
| `Response time distribution` | los percentiles: `90.00% in 7.6339 ms` significa que el 90% de las peticiones respondidas terminó en 7.6339 ms o menos. La unidad de tiempo sigue a la petición más lenta, milisegundos hasta un segundo y segundos por encima, y `-u` la fija |
| `Details` | media, la más rápida y la más lenta de `DNS+dialup`, `DNS-lookup` y `First byte`, en ese orden. oha mide `DNS+dialup` solo en una conexión nueva, así que con keep-alive cubre la primera petición de cada conexión |
| `Status code distribution` | cuántas respuestas volvieron con cada estado |
| `Error distribution` | peticiones que no recibieron respuesta; oha las cuenta por mensaje de error |

## ¿Cómo leo los percentiles de latencia?

Lee `50.00% in 203.4916 ms` así: la mitad de las peticiones respondidas terminó en 203.4916 ms o menos. Pon el presupuesto en p99 o p95, y usa la media solo como comprobación de sentido común.

En la primera salida la media es 3.9593 ms y el p99 es 15.5769 ms, casi cuatro veces más. El endpoint lento da una distribución extendida:

oha --no-tui -n 200 -c 10 http://127.0.0.1:2252/slow

El servidor duerme entre 100 y 300 ms, y los percentiles lo siguen: 126 ms en p10, 203 ms en la mediana, 300 ms en p99.

Los percentiles salen de las duraciones respondidas, ordenadas. oha toma el valor en el índice `p / 100 * n`, con `n` el número de peticiones respondidas. En una ejecución de 200 peticiones el p99 es el valor del índice 198, así que las dos peticiones más lentas lo deciden. Sube `-n`, o usa `-z`, antes de citar una cifra de la cola.

| Percentil | La pregunta que responde |
|---|---|
| p50 | lo que espera un visitante típico |
| p90 | lo que espera uno de cada diez visitantes |
| p99 | lo que espera uno de cada cien visitantes. Pon el presupuesto aquí, con suficientes peticiones detrás: 5,000 peticiones dejan 50 detrás del p99 |
| p99.9 y p99.99 | una parada en mil y una en diez mil. 10,000 peticiones dejan 10 detrás del p99.9 y 1 detrás del p99.99 |

## ¿Qué significa el número de concurrencia?

`-c 50` abre 50 conexiones, los workers del diagrama de arriba, y cada una envía la siguiente petición en cuanto termina la respuesta anterior. No hay tiempo de reflexión, así que cincuenta conexiones golpean una página más fuerte de lo que lo harían cincuenta personas en un navegador.

Las peticiones en vuelo son el ritmo por los segundos por petición (ley de Little). La ejecución por duración de abajo entregó 49.9750 peticiones por segundo con una media de 0.2029 segundos. El producto, 10.1, es el número de conexiones. Para convertir tráfico real en un número, parte de los visitantes por hora y fija `-q`, el ritmo de toda la ejecución:

| `-q` | Peticiones por hora | Peticiones por día |
|---|---|---|
| 1 | 3,600 | 86,400 |
| 10 | 36,000 | 864,000 |
| 100 | 360,000 | 8,640,000 |

Con `-q`, `-c` pasa a ser un techo. En cuanto todas las conexiones están ocupadas, las peticiones pendientes esperan a que haya una libre (más abajo, la corrección de latencia). El keep-alive sigue activado por defecto. `--disable-keepalive` hace que cada petición abra una conexión TCP nueva y, en HTTPS, ejecute un nuevo handshake TLS.

## ¿Cuánto debería durar una ejecución de oha?

Lo suficiente para varios miles de peticiones. Recomiendo `-z 30s` tras una ejecución de calentamiento que descartas, y `-n` solo para comprobaciones rápidas.

`-n` cuenta peticiones. `-z` corre durante un tiempo como `10s` o `3m`. Cuando termina en HTTP/1, oha aborta las peticiones aún en vuelo y las cuenta aparte:

```bash
oha --no-tui -z 5s -c 10 http://127.0.0.1:2252/slow
```

```text
Status code distribution:
  [200] 240 responses

Error distribution:
  [10] aborted due to deadline
```

La tasa de éxito deja fuera las 10 peticiones abortadas, porque las cortó el límite de tiempo y no el servidor. `-w` hace que oha las espere en su lugar.

El calentamiento importa en ambos extremos. oha resuelve el nombre una vez y lo guarda en caché, y cada conexión paga su configuración en su primera petición. En la primera salida `DNS+dialup` tiene una media de 1.1329 ms, y solo la primera petición de cada una de las 50 conexiones lo pagó. El servidor tiene costes de primer uso propios, que el laboratorio no midió. Ejecuta una vez, descarta y después mide.

`-t` limita cada petición y por defecto es infinito. Fíjalo, o un endpoint colgado bloquea la ejecución.

## ¿Cuándo importa la corrección de latencia?

Solo con `-q` o `--burst-delay`, y solo cuando todas las conexiones están ocupadas. Una petición pendiente espera entonces una conexión libre, y su duración sin corregir empieza cuando por fin se envía.

La espera desaparece de las cifras de latencia, así que el resultado luce mejor de lo que vería un cliente a ese ritmo. Este es el problema de la omisión coordinada.

El laboratorio pidió 50 peticiones por segundo en 5 conexiones al endpoint de 200 ms. Cinco conexiones llevan unas 25 por segundo, así que la mitad del plan esperó:

```bash
oha --no-tui -q 50 -c 5 -z 5s http://127.0.0.1:2252/slow
```

```text
Summary:
  Success rate: 100.00%
  Total:        5002.2816 ms
  Slowest:      300.5832 ms
  Fastest:      102.3770 ms
  Average:      200.2119 ms
  Requests/sec: 25.1885
```

La media de 200 ms luce sana. Solo `Requests/sec` muestra que se pidieron 50 y llegaron 25. La misma ejecución con `--latency-correction`:

```bash
oha --no-tui -q 50 -c 5 -z 5s --latency-correction http://127.0.0.1:2252/slow
```

```text
Summary:
  Success rate: 100.00%
  Total:        5.0018 sec
  Slowest:      2.6309 sec
  Fastest:      0.1110 sec
  Average:      1.3881 sec
  Requests/sec: 24.7910
```

La mediana de esa ejecución es 1.3886 segundos y el p99 es 2.6129 segundos. La línea `First byte` de la misma salida se queda cerca de 200 ms:

```text

  DNS+dialup:   0.0002 sec, 0.0002 sec, 0.0003 sec
  DNS-lookup:   0.0000 sec, 0.0000 sec, 0.0001 sec

```

El servidor sigue respondiendo a su velocidad habitual; el segundo extra es tiempo de cola dentro de oha. Un cliente real siempre espera, así que la cifra corregida es la honesta. Sube `-c` hasta que las medianas corregida y sin corregir coincidan; el [README](https://github.com/hatoo/oha#stress-test-in-more-realistic-condition) recomienda `--latency-correction` junto con `-q`.

## ¿Cómo pruebo un endpoint POST con cuerpo y cabeceras?

`-m` fija el método, `-T` el tipo de contenido, `-d` el cuerpo y `-H` una cabecera extra:

```bash
oha --no-tui -n 20 -c 5 -m POST -T application/json -d '{"key":"value"}' -H 'X-Api-Key: test-key' http://127.0.0.1:2252/api/echo
```

```text
Summary:
  Success rate: 100.00%
  Total:        11.3191 ms
  Slowest:      7.1894 ms
  Fastest:      0.3436 ms
  Average:      2.2999 ms
  Requests/sec: 1766.9320
```

Las 20 respuestas tuvieron estado 200. Antes de una ejecución larga, comprueba lo que sale de la máquina: `--debug` hace una sola petición y la vuelca junto con la respuesta.

```bash
oha --no-tui --debug -m POST -T application/json -d '{"key":"value"}' -H 'X-Api-Key: test-key' http://127.0.0.1:2252/api/echo
```

```text
Request {
    method: POST,
    uri: /api/echo,
    version: HTTP/1.1,
    headers: {
        "accept": "*/*",
        "accept-encoding": "gzip, compress, deflate, br",
        "user-agent": "oha/1.17.0",
        "content-type": "application/json",
        "x-api-key": "test-key",
        "host": "127.0.0.1:2252",
    },
    body: Full {
        data: Some(
            b"{\"key\":\"value\"}",
        ),
    },

```

El volcado muestra el cuerpo, la cabecera `x-api-key` y los valores por defecto que oha añade. La parte de la respuesta devolvió la misma cabecera y el mismo cuerpo.

| Flag | Función | Por defecto |
|---|---|---|
| `-m` | método | GET |
| `-H` | cabecera extra, repítelo para cada una | ninguna más allá de `accept`, `accept-encoding` y `user-agent` |
| `-T` | cabecera `Content-Type` | ninguna |
| `-d` | cuerpo como cadena | ninguno |
| `-D` | cuerpo desde un archivo | ninguno |
| `-Z` | una línea al azar de un archivo por petición, como cuerpo | ninguno |
| `-F` | datos de formulario multipart en sintaxis de curl, por ejemplo `-F 'file=@path'` | ninguno |
| `-A` | cabecera `Accept` | `*/*` |
| `-a` | autenticación Basic como `user:password`, o claves AWS con `--aws-sigv4` | ninguna |
| `--host` | cabecera `Host` | el host de la URL |
| `--disable-compression` | quita `Accept-Encoding` | compresión aceptada |

`-d`, `-D`, `-Z` y `-F` se excluyen entre sí. Con autenticación Basic, cinco peticiones al endpoint protegido dieron `[401] 5 responses`, y las mismas cinco con `-a labuser:labpass` dieron `[200] 5 responses`.

## ¿Cómo se ven un 429, un 5xx y un timeout en oha?

Aparecen como códigos de estado bajo `Status code distribution`, no como fallos. oha cuenta cada petición respondida como un éxito, y solo una petición sin respuesta baja la tasa de éxito.

<Notice type="warning" title="Una tasa de éxito del 100% no significa que la página funcione">
Una ejecución en la que todas las peticiones devuelven 500 imprime `Success rate: 100.00%`. Lee la distribución de códigos de estado de cada ejecución, o condiciónala en la siguiente sección.
</Notice>

Cuatro casos del laboratorio:

| Caso | Comando | Lo que imprimió oha |
|---|---|---|
| 20 peticiones a un endpoint que devuelve 500 | `oha --no-tui -n 20 http://127.0.0.1:2252/error` | `Success rate: 100.00%` y `[500] 20 responses` |
| Ejecución por defecto contra nginx con `limit_req` a 100 peticiones por segundo | `oha --no-tui http://127.0.0.1:2251/limited` | `Success rate: 100.00%`, `[503] 198 responses`, `[200] 2 responses` |
| 10 peticiones a un endpoint que duerme 10 s, con `-t 500ms` | `oha --no-tui -n 10 -c 5 -t 500ms http://127.0.0.1:2252/hang` | `Success rate: 0.00%` y `[10] timeout` |
| 5 peticiones a un puerto cerrado | `oha --no-tui -n 5 http://127.0.0.1:2259/` | `Success rate: 0.00%` y `[5] Connection refused (os error 111)` |

El primer caso informa de `Success rate: 100.00%` y termina con:

```bash
oha --no-tui -n 20 http://127.0.0.1:2252/error
```

```text
Status code distribution:
  [500] 20 responses
```

Qué significa cada caso:

- Un 429 o un 503 de un limitador de ritmo dice que respondió el limitador, no la aplicación. nginx `limit_req` rechaza con 503 por defecto ([documentación de nginx](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html)). Sube el límite para la dirección de prueba, o mantén `-q` por debajo.
- Un 5xx de la aplicación significa que la aplicación falló en esa petición. El endpoint de laboratorio devolvía 500 a propósito, así que sus errores no dicen nada sobre la carga.
- `timeout` significa que la petición no terminó dentro de `-t`. En el laboratorio el servidor aceptó la conexión y durmió 10 s.
- `Connection refused` significa que nada escucha en ese puerto, o que una regla del firewall respondió con un reset.

Una herramienta que bloquea direcciones en el firewall añade sus propios errores a esa distribución. La [guía de CrowdSec](/es/crowdsec-servidor-seguro/) muestra dónde lista CrowdSec las direcciones que bloquea.

Cada estado respondido, el 500 incluido, entra en los percentiles. `--stats-success-breakdown` añade un histograma y una distribución para las respuestas 2xx y otro para las 4xx y 5xx, así que una ejecución de laboratorio con `[500] 26 responses`, `[200] 17 responses` y `[429] 17 responses` mostró cada clase por separado.

## ¿Cómo guardo los resultados de oha para CI?

`--output-format json` con `-o` escribe el resultado en un archivo y no imprime nada. El bloque `metrics` contiene las cifras que un pipeline puede comprobar:

```bash
oha --no-tui -z 3s -c 10 --output-format json -o result.json http://127.0.0.1:2252/slow
jq '.summary, .metrics' result.json
```

La opción `-e` de jq convierte el último valor en un código de salida, 0 para true y 1 para false o null:

```

```

La misma comprobación sobre el JSON del endpoint que devuelve 500 falla, porque los códigos de estado forman parte de ella:

```bash
jq -e '.summary.successRate == 1 and (.statusCodeDistribution | keys | map(tonumber) | all(. < 400))' error.json
```

```text
false
```

```bash

```

## ¿Desde dónde debería ejecutar oha?

En una segunda máquina, no en el servidor bajo prueba. En el mismo host el generador y el servidor comparten CPU, y el tráfico de loopback se salta la tarjeta de red y, a menudo, el proxy inverso.

La estación de trabajo del laboratorio envió 23,063 peticiones por segundo de la página estática con `-n 1k -c 50`, en el mismo host que nginx. Una segunda máquina vuelve a incluir la tarjeta de red y el proxy inverso en la medición. Para un generador de alquiler, los [benchmarks de ARM en Hetzner y Oracle](/es/rendimiento-arm-hetzner-oracle/) comparan los planes ARM pequeños. Cuando en cambio es el servidor el que tiene que crecer, la [guía de benchmarking de VPS](/es/benchmark-servidores-cloud/) muestra cómo medir un plan. Los [benchmarks de VPS ARM contra x86](/es/comparativa-arm-vs-x86-vps/) comparan dos clases de servidor para un sitio WordPress.

Apunta oha al camino que recorren los usuarios. Una cifra del puerto 8080 del servidor no dice nada sobre el proxy inverso o el túnel que tiene delante. Para un sitio publicado a través de un túnel como Pangolin, prueba también el nombre de host público ([guía de Pangolin](/es/pangolin-alternativa-cloudflare-tunnels/)).

Un `-c` grande puede agotar los descriptores de archivo del shell que ejecuta oha. La ejecución de laboratorio con `-c 500` bajo un límite flexible de 256 falló en más de la mitad de sus peticiones:

```bash
ulimit -n 256
oha --no-tui -c 500 -n 500 http://127.0.0.1:2251/
```

```text
Status code distribution:
  [200] 219 responses

Error distribution:
  [281] No file descriptors available (os error 24)
```

Sube el límite flexible con `ulimit -n 4096` o baja `-c`. El backlog de escucha del servidor debe admitir ese mismo número de conexiones.

Vigila el objetivo durante la ejecución; la [guía de monitorización de recursos del servidor y Docker](/es/monitorizar-servidor/) muestra la configuración. Después de la ejecución, confirma desde fuera que el sitio volvió ([guía de Beszel y Uptime Kuma](/es/beszel-uptime-kuma/)).

Si arrancas un contenedor como objetivo, publica su puerto solo en 127.0.0.1, como hizo el laboratorio con `-p 127.0.0.1:2251:80`. Un `-p 2251:80` a secas lo abre en todas las interfaces, porque [Docker evita UFW](/es/docker-evita-firewall/) en los puertos publicados.

## ¿Qué está permitido al hacer pruebas de carga?

Prueba lo que es tuyo, o lo que su propietario permitió por escrito; los endpoints propios del proveedor y los sitios que no administras están fuera de los límites sin ese permiso. Un VPS alquilado es tuyo hasta donde llegue la política de uso aceptable del proveedor.

AWS pone el límite por escrito. Su [EC2 Testing Policy](https://aws.amazon.com/ec2/testing/) llama network stress test a una prueba que envía "a large volume of legitimate or test traffic to a specific intended target application". Una prueba que intenta saturar un objetivo es una prueba de DDoS, que la misma página califica de "explicitly prohibited from the Amazon EC2 platform". Su [política de pruebas de seguridad](https://aws.amazon.com/security/penetration-testing/) lista "Request flooding" como prohibida (ambas comprobadas el 2026-11-27).

<ListCheck>
<ul>
<li>Una copia de staging, o una ventana de producción que el propietario acordó por escrito</li>
<li>Un ritmo de peticiones y una duración anotados antes del inicio</li>
<li>`-t` fijado, para que un endpoint colgado no pueda bloquear la ejecución</li>
<li>Solo peticiones GET en producción, o una cuenta de prueba para las escrituras, porque una ejecución con POST crea filas reales</li>
<li>Alguien vigilando el servidor, con una condición de parada como una tasa de error por encima del 1%</li>
</ul>
</ListCheck>

## oha o k6: ¿cuál deberías usar?

Usa oha cuando la prueba sea una URL y la respuesta sea una cifra. Usa k6 cuando la prueba sea un script: varias peticiones seguidas, un login, una comprobación del cuerpo de una respuesta o un umbral que falle la ejecución por sí solo.

| | oha 1.17.0 | k6 2.4.0 |
|---|---|---|
| Qué escribes | oha toma una línea de comandos | k6 toma un script de JavaScript |
| Aprobar o fallar en CI | oha escribe JSON, y tú añades la comprobación de jq | k6 toma umbrales en el script. Un umbral fallido termina la prueba con un código de salida distinto de cero |
| Protocolos | oha habla HTTP/0.9, 1.0, 1.1 y 2, y 3 solo en un binario compilado por tu cuenta | k6 habla HTTP/1.1, HTTP/2, WebSockets y gRPC integrados, y ejecuta pruebas de navegador a través de su API de navegador |
| Licencia | oha es MIT | k6 es AGPL-3.0 |
| Ideal para | oha para una cifra rápida, una ejecución con ritmo limitado o una puerta de humo en un endpoint | k6 para recorridos de usuario con tiempo de reflexión y comprobaciones de la respuesta |
| Contrapartida | oha no tiene scripting, tiempo de reflexión ni comprobaciones del cuerpo | k6 tiene un runtime y un script que mantener |

k6 2.4.0 se publicó el 2026-11-12. Sus columnas siguen la documentación de [protocolos](https://grafana.com/docs/k6/latest/using-k6/protocols/) y [umbrales](https://grafana.com/docs/k6/latest/using-k6/thresholds/) de k6, comprobada el 2026-11-27.

## Referencia de flags de oha 1.17.0

Cada flag de `oha --help` en 1.17.0, agrupado por función. Los flags de HTTPS y proxy salen solo del texto de ayuda; el laboratorio corrió HTTP sin cifrar.

| Función | Flags | Por defecto |
|---|---|---|
| Cuántas, cuánto tiempo | `-n`, `-z`, `-w`, `--burst-delay`, `--burst-rate` | 200 peticiones. `-q` anula los flags de ráfaga |
| Con qué intensidad | `-c`, `-p`, `-q` | 50 conexiones, 1 flujo por conexión HTTP/2 (`-c` por `-p` workers en total), sin límite de ritmo (`-q 0` también significa ninguno) |
| Petición | `-m`, `-H`, `-A`, `-T`, `-d`, `-D`, `-Z`, `-F`, `--host`, `--disable-compression` | GET, sin cuerpo, compresión aceptada |
| Autenticación | `-a`, `--aws-session`, `--aws-sigv4` | ninguna |
| Objetivos | `--urls-from-file`, `--rand-regex-url`, `--max-repeat`, `--dump-urls` | la URL de la línea de comandos. Con un archivo, oha elige una línea al azar por cada petición |
| Transporte | `--http-version`, `--http2`, `--disable-keepalive`, `-r`, `--connect-timeout`, `-t`, `--ipv4`, `--ipv6`, `--no-pre-lookup`, `--connect-to`, `--unix-socket`, `--vsock-addr` | HTTP/1.1, keep-alive activado, oha no sigue redirecciones (`-r 0`), timeout de conexión de 5s, sin timeout de petición, oha resuelve el nombre una vez al inicio |
| Proxy | `-x`, `--proxy-http-version`, `--proxy-http2`, `--proxy-header` | ninguno |
| TLS | `--cacert`, `--cert`, `--key`, `--insecure` | almacén del sistema, verificación activada, sin certificado de cliente |
| Medición | `--latency-correction`, `--stats-success-breakdown`, `-u` | todos apagados. La unidad sigue a la petición más lenta |
| Salida | `--no-tui`, `--fps`, `--no-color`, `--output-format`, `-o`, `--db-url`, `--debug` | panel activado a 16 fotogramas por segundo, texto a stdout. Sin `-q` ni `--burst-delay`, `--no-tui` también cambia oha a una implementación más rápida que deja de recoger datos para la vista en directo ([README](https://github.com/hatoo/oha#performance)). `--db-url` guarda cada petición con éxito en una tabla SQLite llamada `oha`, y las ejecuciones siguientes añaden al final. `quiet` no imprime nada |
| Runtime | `--worker-threads` | un hilo por núcleo físico |

El valor por defecto de las redirecciones pasó a 0 en 1.15.0. Una ejecución por defecto contra un endpoint que responde 302 informa de `[302] 200 responses`, y la misma ejecución con `-r 3` informa de `[200] 200 responses`.

`--urls-from-file` toma una URL por línea, por ejemplo las rutas de un log de acceso, y elige una al azar para cada petición ([README](https://github.com/hatoo/oha#urls-from-file-feature)). Guarda un solo host en ese archivo:

<Notice type="info" title="Guarda un solo host por archivo de URLs con el keep-alive activado">
Con `--urls-from-file`, un worker envía su siguiente petición por la conexión que ya tiene, aunque la URL nombre otro host. En el laboratorio, un archivo con tres URLs en dos servidores devolvió de 78 a 106 respuestas con estado 404 en 15 de 16 ejecuciones. La ruta `/slow` había llegado a nginx, que no tiene esa ruta. Con `--disable-keepalive` el mismo archivo devolvió `[200] 300 responses` en cada una de tres ejecuciones.
</Notice>

## Preguntas frecuentes

<Accordion label="¿Qué envía un comando oha sin opciones?" group="faq">
`oha https://example.com` envía 200 peticiones en 50 conexiones con el keep-alive activado y no sigue ninguna redirección, los valores por defecto de `-n`, `-c` y `-r` en 1.17.0. Añade `-z 30s` para correr durante un tiempo en lugar de un número de peticiones.
</Accordion>

<Accordion label="¿Por qué oha informa de una tasa de éxito del 100% junto a respuestas 500?" group="faq">
oha cuenta cada petición respondida como un éxito; solo una petición sin respuesta es un error. Lee `Status code distribution`, o condiciónalo con `jq -e '(.statusCodeDistribution | keys | map(tonumber) | all(. < 400))' run.json`, que sale con 1 ante un 500.
</Accordion>

<Accordion label="¿oha admite WebSocket o HTTP/3?" group="faq">
No hay modo WebSocket en 1.17.0. HTTP/3 necesita una compilación con la característica `http3`; el binario del release responde `Error: Your Oha instance has not been built with HTTP/3 support.` k6 habla WebSockets de fábrica.
</Accordion>

<Accordion label="¿oha sigue las redirecciones?" group="faq">
No por defecto. El límite de redirecciones es 0 desde 1.15.0, así que oha registra un 302 como `[302] 200 responses`. `-r 3` sigue hasta tres redirecciones, y el laboratorio informó entonces de `[200] 200 responses`. oha no sigue redirecciones en HTTP/2.
</Accordion>

<Accordion label="¿Cuántas peticiones dan un p99 utilizable?" group="faq">
oha toma el p99 en el índice `99 / 100 * n` de las duraciones ordenadas, así que en una ejecución de 200 peticiones dos peticiones lo deciden. Usa `-n 5000` o `-z 30s`, que deja 50 peticiones detrás del p99.
</Accordion>

<Accordion label="¿Cómo evito que a oha se le acaben los descriptores de archivo?" group="faq">
Cada conexión usa un descriptor. Una ejecución de laboratorio con `-c 500` bajo `ulimit -n 256` falló en 281 de 500 peticiones con `No file descriptors available (os error 24)`. Sube el límite flexible con `ulimit -n 4096` o baja `-c`.
</Accordion>

<Accordion label="¿Cuál es la diferencia entre -n y -z?" group="faq">
`-n` se detiene tras un número de peticiones y por defecto es 200. `-z` se detiene tras una duración como `5s` o `3m`. En HTTP/1, oha aborta las peticiones en vuelo al llegar al límite de tiempo y las lista como `aborted due to deadline`, que la tasa de éxito deja fuera.
</Accordion>

<Accordion label="¿Puedo hacer una prueba de carga a un sitio que no es mío?" group="faq">
Solo con permiso por escrito del propietario. AWS, por ejemplo, prohíbe pruebas contra su propia infraestructura y lista "Request flooding" entre las actividades prohibidas, mientras que su EC2 Testing Policy permite pruebas de estrés sobre la aplicación objetivo del cliente. Prueba primero una copia de staging.
</Accordion>
