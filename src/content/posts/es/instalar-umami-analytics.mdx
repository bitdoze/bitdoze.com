[Umami](https://umami.is/) es una herramienta de analítica web sencilla, rápida y centrada en la privacidad, y una sólida alternativa a Google Analytics. Tiene licencia MIT, más de 37.000 estrellas en GitHub y solo recopila las métricas que necesitas sin rastrear a tus visitantes. Si quieres comparar opciones, [Plausible](/es/herramienta-plausible/) y [Matomo](https://matomo.org/) son herramientas de analítica autoalojadas similares. También puedes [instalar Plausible Analytics](/es/instalar-plausible-analytics/) con una configuración de Docker parecida.

Con Google Analytics 4 y la aplicación del RGPD en la UE, la analítica web autoalojada se ha convertido en la opción por defecto para quienes quieren la propiedad total de sus datos. Los scripts de Google Analytics son pesados y ralentizan tu sitio. Umami añade menos de 2 KB de sobrecarga.

Esta guía cubre cómo instalar Umami Analytics en Docker con Docker Compose, incluida la configuración del tracker, cómo evitar los bloqueadores de anuncios, las actualizaciones y las copias de seguridad. Umami v3 se lanzó en noviembre de 2025 con una nueva interfaz, mapas de calor, reproducción de sesiones, y ahora es solo compatible con PostgreSQL (se eliminó el soporte de MySQL).

<Notice type="info" title="Umami v3 (noviembre de 2025)">
Umami v3 es una versión mayor con una interfaz rediseñada, Segments, Cohorts, Session Replay, Heatmaps y seguimiento de Web Vitals. MySQL ya no es compatible. PostgreSQL es la única opción de base de datos. Los archivos compose de esta guía están actualizados para v3. Consulta el <a href="https://umami.is/blog/umami-v3" rel="nofollow">artículo del blog sobre Umami v3</a> para todos los detalles.
</Notice>

> Puedes encontrar más aplicaciones autoalojadas de código abierto y gratuitas en la [sección self-hosted de toolhunt.net](https://toolhunt.net/sh/).

### 1. Requisitos previos

<ListCheck>
<ul>
<li>Un VPS con Docker y Docker Compose v2 instalados. Un <a href="https://go.bitdoze.com/hetzner" rel="nofollow">Hetzner</a> CX22 a ~€4/mes es suficiente (Umami + Postgres usan ~300 MB de RAM en total). <a href="https://go.bitdoze.com/hostinger-vps" rel="nofollow">Hostinger</a> es otra opción económica.</li>
<li>Dockge o cualquier herramienta de gestión de Docker, o simplemente <code>docker compose</code>. Consulta la <a href="/es/instalar-dockge/">guía de instalación de Dockge</a> para un recorrido completo. También puedes ver otros <a href="/es/mejores-paneles-autoalojados/">paneles de servidor autoalojados</a>.</li>
<li>Un túnel de Cloudflare configurado para tu VPS (o cualquier proxy inverso con terminación SSL)</li>
<li>Un dominio o subdominio listo para Umami</li>
<li>PostgreSQL v12.14+ (usamos v15-alpine, que cumple este requisito)</li>
</ul>
</ListCheck>

_Los precios de los VPS subieron en todos los proveedores en 2026: si estás reconsiderando un servidor alquilado, mira [qué cambió y cuándo gana un mini PC](/es/subidas-precios-vps/)._

<Notice type="warning" title="No uses 'analytics' como subdominio">
Los bloqueadores de anuncios suelen bloquear las peticiones a <code>analytics.yourdomain.com</code>. Usa algo como <code>stats</code>, <code>metrics</code> o <code>track</code> en su lugar. Esto aplica tanto al subdominio como a la ruta del script.
</Notice>

### 2. Archivo Docker Compose para Umami

A continuación tienes dos archivos compose. El primero es una configuración limpia sin copias de seguridad; úsalo si piensas hacer backups con un `pg_dump` programado por cron (recomendado). El segundo añade un contenedor sidecar `tiredofit/db-backup` para volcados automáticos programados.

<Tabs>
<Tab name="Simple (sin backup)">

```yaml
services:
  umami:
    image: docker.umami.is/umami-software/umami:postgresql-latest
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@umami-db:5432/${POSTGRES_DB}
      APP_SECRET: ${APP_SECRET}
      DISABLE_TELEMETRY: ${DISABLE_TELEMETRY:-1}
    depends_on:
      umami-db:
        condition: service_healthy
    init: true
    restart: always
    healthcheck:
      test: ["CMD-SHELL", "curl http://localhost:3000/api/heartbeat"]
      interval: 5s
      timeout: 5s
      retries: 5

  umami-db:
    image: postgres:15-alpine
    environment:
      POSTGRES_DB: ${POSTGRES_DB}
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      TZ: UTC
    volumes:
      - ./umami-db-data:/var/lib/postgresql/data
    restart: always
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 5s
      timeout: 5s
      retries: 5
```

El servicio de Umami se ejecuta en el puerto 3000, se conecta a PostgreSQL a través de la red interna de Docker e incluye un health check que consulta `/api/heartbeat`. Los datos de Postgres viven en un volumen local en `./umami-db-data`. Puedes cambiar el mapeo de puertos a lo que prefieras.

</Tab>

El sidecar de backup vuelca la base de datos cada 12 horas y elimina las copias con más de 50 días. Los volcados se guardan en `./backups`. La imagen `tiredofit/db-backup` es más pesada que un simple cron. Si quieres algo más ligero, consulta la [sección de copia de seguridad y restauración](#copia-de-seguridad-y-restauración-de-la-base-de-datos) para una alternativa de `pg_dump` en una sola línea.

### 3. Configura el archivo .env

Crea un archivo `.env` en el mismo directorio que tu archivo compose (o añade las variables en la sección de entorno de Dockge).

```sh
POSTGRES_USER=umami
POSTGRES_PASSWORD=your-secure-password
POSTGRES_DB=umami
APP_SECRET=run-openssl-rand-hex-32-to-generate
DISABLE_TELEMETRY=1
```

<Notice type="warning" title="Genera un APP_SECRET único">
Nunca uses el valor de ejemplo. Genera un secreto seguro con:<br /><code>openssl rand -hex 32</code><br />Pega la salida como tu <code>APP_SECRET</code>. Se usa para el cifrado de sesiones.
</Notice>

### 4. Despliega Umami

Si usas Dockge, ponle un nombre a tu stack y pulsa deploy. Con Docker Compose directamente:

```sh
docker compose up -d
```

Verifica que ambos contenedores estén saludables:

```sh
docker compose ps
```

Deberías ver tanto `umami` como `umami-db` con estado `healthy`. Revisa los logs de Umami para confirmar que las migraciones se ejecutaron:

```sh
docker compose logs -f umami
```

Una salida correcta muestra `All migrations have been successfully applied` seguido del servidor escuchando en el puerto 3000.

Accede a Umami en `http://tu-ip-del-vps:3000`. Inicia sesión con las credenciales por defecto:

- **Usuario:** `admin`
- **Contraseña:** `umami`

<Notice type="error" title="Cambia la contraseña por defecto ahora">
Las credenciales por defecto <code>admin</code> / <code>umami</code> son de dominio público. Ve a <strong>Settings → Profile → Change password</strong> de inmediato, antes de exponer Umami a internet.
</Notice>

Verificación rápida con curl:

```sh
curl http://localhost:3000/api/heartbeat
# Debería devolver: OK
```

## Código de seguimiento de Umami y configuración del tracker

Una vez añadido tu sitio web, Umami te proporciona un script de seguimiento. Así se usa y estas son las opciones disponibles.

### Script de seguimiento básico

El embed estándar tiene este aspecto:

```html
<script
  defer
  src="https://your-umami-domain.com/script.js"
  data-website-id="your-website-id"
></script>
```

- `data-website-id` (el UUID del sitio web que añadiste en Umami, visible en el fragmento del código de seguimiento)
- `data-host-url` (configúralo si el dominio del tracker difiere del dominio del panel, por ejemplo si sirves el script desde una CDN)

### Eventos personalizados y opciones avanzadas

Umami admite el seguimiento de eventos tanto programático como declarativo.

**Programático** (llamada desde JavaScript):

```js
// Registra un evento personalizado con propiedades
umami.track("signup", { plan: "pro", source: "header" });
```

**Declarativo** (añade atributos HTML a cualquier elemento):

```html
<button data-umami-event="click-download" data-umami-file="whitepaper.pdf">
  Download
</button>
```

Otros atributos data útiles:

| Atributo | Propósito |
|-----------|---------|
| `data-domains="example.com,api.example.com"` | Restringe el seguimiento a dominios específicos |
| `data-do-not-track="true"` | Respeta la cabecera DNT del navegador |
| `data-auto-track="false"` | Desactiva el seguimiento automático de páginas vistas (útil en SPAs que gestionan su propio enrutado) |
| `data-performance="true"` | Registra las Core Web Vitals (nuevo en v3.1.0) |
| `data-auto-pageview="false"` | Suprime el pageview automático al cargar el script (nuevo en v3.2.0) |

> Si usas un sitio Astro, consulta [Plausible Analytics para Astro con Cloudflare Workers](/es/astro-plausible-cloudflare-workers/) para ver un enfoque de integración de analítica relacionado.

### Evitar los bloqueadores de anuncios

Los bloqueadores de anuncios atacan dos rutas por defecto: `/script.js` y `/api/send`. Puedes renombrar ambas con variables de entorno:

```env
TRACKER_SCRIPT_NAME=custom-tracker
COLLECT_API_ENDPOINT=/api/collect
```

Añádelas al entorno del servicio `umami` en tu archivo compose y reinicia. Actualiza el `src` de tu script de seguimiento para que coincida:

```html
<script
  defer
  src="https://your-domain.com/custom-tracker.js"
  data-website-id="your-website-id"
></script>
```

<Notice type="info" title="Evitar los bloqueadores requiere cambios en el compose">
Tras añadir <code>TRACKER_SCRIPT_NAME</code> y <code>COLLECT_API_ENDPOINT</code> a tu archivo compose, reinicia el contenedor de Umami: <code>docker compose up -d --force-recreate umami</code>. Asegúrate de que las reglas del proxy inverso dejen pasar la nueva ruta del endpoint.
</Notice>

<Accordion label="Ejemplo completo para evitar bloqueadores de anuncios" group="tracker">

Aquí tienes un fragmento completo para añadir al entorno del servicio `umami` en tu archivo compose:

```yaml
environment:
  DATABASE_URL: postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@umami-db:5432/${POSTGRES_DB}
  APP_SECRET: ${APP_SECRET}
  DISABLE_TELEMETRY: ${DISABLE_TELEMETRY:-1}
  TRACKER_SCRIPT_NAME: my-stats
  COLLECT_API_ENDPOINT: /api/c
  CLIENT_IP_HEADER: cf-connecting-ip
```

Después, en el HTML de tu sitio:

```html
<script
  defer
  src="https://stats.yourdomain.com/my-stats.js"
  data-website-id="your-website-id"
></script>
```

Si usas un proxy inverso (Nginx, Caddy, Traefik), asegúrate de que las rutas personalizadas se reenvíen al contenedor de Umami en el puerto 3000. No hace falta configuración de enrutado adicional si el proxy envía todo el tráfico a Umami.

</Accordion>

## Cómo actualizar Umami Analytics en Docker

### Actualizaciones estándar (misma versión mayor)

Para actualizaciones menores dentro de v3.x:

```bash
# 1. Haz primero una copia de seguridad de la base de datos
docker compose exec -T umami-db pg_dump -U umami umami | gzip > backups/umami-$(date +%F-%H%M).sql.gz

# 2. Descarga la última imagen
docker compose pull

# 3. Recrea los contenedores
docker compose up -d --force-recreate

# 4. Verifica: busca "All migrations have been successfully applied"
docker compose logs -f umami
```

### Actualizar de Umami v2 a v3

<Notice type="warning" title="Cambios importantes en Umami v3">
v3 elimina el soporte de MySQL, tiene una interfaz completamente nueva y ejecuta migraciones de esquema que pueden tardar en bases de datos grandes. <strong>Haz siempre una copia de seguridad antes de actualizar.</strong> Si estabas en MySQL, sigue primero la <a href="https://docs.umami.is/docs/guides/migrate-mysql-postgresql" rel="nofollow">guía de migración de MySQL a PostgreSQL</a>.
</Notice>

Pasos:

```bash
# 1. Copia de seguridad
docker compose exec -T umami-db pg_dump -U umami umami > umami-backup-$(date +%F-%H%M).sql

# 2. Descarga y recrea
docker compose pull
docker compose up -d --force-recreate umami

# 3. Revisa los logs para ver la salida de las migraciones
docker compose logs -f umami

# 4. Ejecuta ANALYZE en PostgreSQL (crítico tras actualizaciones mayores)
docker compose exec -T umami-db psql -U umami umami -c "ANALYZE;"
```

El comando `ANALYZE` actualiza las estadísticas del planificador de consultas de PostgreSQL tras las migraciones de esquema. La [documentación oficial de Umami](https://docs.umami.is/docs/updates) lo recomienda. Sin él, las consultas del panel pueden volverse lentas después de una actualización mayor.

Tras actualizar, las imágenes Docker antiguas se acumulan en el disco. Puedes [limpiar el espacio en disco de Docker](/es/limpiar-docker-overlay2/) para recuperar almacenamiento.

### Copia de seguridad y restauración de la base de datos

<Notice type="error" title="Haz siempre copia de seguridad antes de actualizar">
Una migración fallida puede corromper los datos. Ejecuta siempre <code>pg_dump</code> antes de descargar una nueva versión mayor.
</Notice>

<Tabs>
<Tab name="pg_dump manual">

**Copia de seguridad** (una sola línea, se puede programar con cron):

```bash
docker compose exec -T umami-db pg_dump -U umami umami | gzip > backups/umami-$(date +%F).sql.gz
```

Añádelo al crontab para copias diarias a las 3 AM:

```bash
0 3 * * * cd /path/to/umami && docker compose exec -T umami-db pg_dump -U umami umami | gzip > backups/umami-$(date +\%F).sql.gz
```

**Restauración:**

```bash
gunzip < backups/umami-YYYY-MM-DD.sql.gz | docker compose exec -T umami-db psql -U umami umami
```

Para copias externas, sube el volcado comprimido a cualquier almacenamiento compatible con S3 (MinIO, Cloudflare R2, Backblaze B2).

</Tab>
<Tab name="tiredofit/db-backup">

Si usaste el archivo compose "Con backup", los volcados están en el directorio `./backups` y se crean cada 12 horas. Para restaurar desde un backup de tiredofit:

```bash
# Encuentra el último backup
ls -lt backups/

# Restáuralo
zcat backups/umami-db-*.sql.gz | docker compose exec -T umami-db psql -U umami umami
```

El sidecar `tiredofit/db-backup` es más pesado que un enfoque basado en cron (ejecuta su propio programador, compresión y limpieza). Para una huella mínima, el cron manual de `pg_dump` es más ligero.

</Tab>
</Tabs>

## Verifica y soluciona problemas de tu instalación de Umami

<ListCheck>
<ul>
<li><code>docker compose ps</code>: tanto <code>umami</code> como <code>umami-db</code> muestran el estado <code>healthy</code></li>
<li><code>docker compose logs umami</code>: muestra "All migrations have been successfully applied"</li>
<li><code>curl http://localhost:3000/api/heartbeat</code>: devuelve OK</li>
<li>El inicio de sesión funciona con <code>admin</code> / <code>umami</code> (cambia la contraseña de inmediato)</li>
<li>Incrusta el script de seguimiento en una página de prueba, abre las DevTools del navegador → pestaña Network, y confirma que <code>script.js</code> carga (200 OK)</li>
<li>Visita la página de prueba y comprueba el panel de Umami para ver una visita en tiempo real</li>
</ul>
</ListCheck>

Si quieres [monitorizar los recursos de tu servidor](/es/monitorizar-servidor/) junto a Umami, monta un stack de monitorización ligero.

<Accordion label="El contenedor se reinicia constantemente" group="troubleshoot">

Revisa `docker compose logs umami`. La causa más común es una `DATABASE_URL` incorrecta o que el contenedor de la base de datos aún no esté saludable. Verifica que las variables de tu `.env` coincidan con lo que referencia el archivo compose. La condición `depends_on` debería esperar al health check de la base de datos, pero si tarda en arrancar en un VPS con poca memoria, dale 30 segundos.

</Accordion>

<Accordion label="Error 'service umami-db not found'" group="troubleshoot">

Un error tipográfico en `depends_on`. Asegúrate de que ponga `umami-db` (con "m"), no `unami-db`. Era un fallo en versiones anteriores del archivo compose de esta guía.

</Accordion>

<Accordion label="Panel en blanco o lento tras actualizar" group="troubleshoot">

Tras una actualización de versión mayor (sobre todo de v2 a v3), el planificador de consultas de PostgreSQL puede tener estadísticas desactualizadas. Ejecuta:

```bash
docker compose exec -T umami-db psql -U umami umami -c "ANALYZE;"
```

</Accordion>

<Accordion label="Las IPs de los visitantes aparecen como 'Unknown'" group="troubleshoot">

Cuando Umami se ejecuta detrás de Cloudflare Tunnels o de un proxy inverso, la IP del cliente no le llega directamente. Añade al entorno del servicio `umami`:

```env
CLIENT_IP_HEADER=cf-connecting-ip
```

Usa `x-forwarded-for` si estás detrás de Nginx o Traefik en lugar de Cloudflare. Reinicia el contenedor tras el cambio.

</Accordion>

<Accordion label="El script de seguimiento está bloqueado por bloqueadores de anuncios" group="troubleshoot">

Las rutas por defecto `/script.js` y `/api/send` están en las listas de bloqueo. Usa las variables de entorno `TRACKER_SCRIPT_NAME` y `COLLECT_API_ENDPOINT` para renombrarlas. Consulta la [sección sobre cómo evitar los bloqueadores de anuncios](#evitar-los-bloqueadores-de-anuncios) más arriba.

</Accordion>

<Accordion label="Sin memoria / OOM kills" group="troubleshoot">

Umami usa ~200 MB de RAM y Postgres ~50-100 MB. Un VPS de 1 GB es el mínimo práctico. Comprueba el uso de recursos con `docker stats`. Si los contenedores sufren OOM kills, considera añadir límites de memoria en el compose:

```yaml
deploy:
  resources:
    limits:
      memory: 256M
```

</Accordion>

## Conclusión

Ya tienes Umami Analytics instalado en Docker, con una configuración de tracker funcional, opciones para evitar los bloqueadores de anuncios y un flujo sólido de actualizaciones y copias de seguridad.
