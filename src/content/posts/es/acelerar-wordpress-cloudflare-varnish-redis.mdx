## Cómo funciona la pila de caché de tres capas para WordPress

Cada capa gestiona un tipo de petición distinto:

1. **Cloudflare**: los visitantes llegan primero a Cloudflare. Si la página está en la caché de su CDN, se sirve desde el nodo edge más cercano sin tocar tu servidor.
2. **Varnish**: si la página no está en la caché de Cloudflare (primera visita, tras publicar, contenido dinámico), la petición llega a Varnish en tu servidor. Varnish sirve el HTML cacheado sin ejecutar PHP.
3. **Redis**: cuando Varnish necesita generar una página nueva, PHP habla con Redis para la caché de objetos y consultas en lugar de golpear MySQL repetidamente.

En un fallo de caché completo, la petición cae hasta PHP-FPM, que lee objetos de Redis y solo consulta MySQL cuando Redis falla. El resultado son cargas rápidas para los visitantes que vuelven y una carga del servidor manejable durante los picos de tráfico.

## Plugins necesarios

Tres plugins gratuitos conectan WordPress con la pila.

<Notice type="warning" title="No apiles plugins de caché de páginas">
La propia documentación de Super Page Cache dice que desactives la caché de páginas de WP Rocket, LiteSpeed Cache y W3 Total Cache antes de activarlo. Es seguro junto a Optimole, Autoptimize, Perfmatters y ShortPixel. Ten en cuenta también que Super Page Cache ahora hace caché en disco y presume de purga automática de Varnish. Ejecutarlo junto a CLP Varnish Cache significa que dos plugins pueden intentar purgar la misma capa. Ver la nota sobre el dueño de la purga en Solución de problemas, más abajo.
</Notice>

### CLP Varnish Cache

Purga el Varnish de CloudPanel cuando cambia el contenido. Es el plugin que la propia documentación de CloudPanel recomienda para WordPress. Funciona nada más salir de la caja. Una vez activado, expone ajustes de caché y acciones de purga en wp-admin y gestiona la purga automática cuando publicas o actualizas contenido.

- [CLP Varnish Cache en wordpress.org](https://wordpress.org/plugins/clp-varnish-cache/)

### Redis Object Cache

Conecta WordPress con Redis para la caché de objetos y consultas. Después de activarlo, ve a **Ajustes → Redis** y haz clic en **Enable Object Cache**. El plugin suelta un archivo `object-cache.php` en `wp-content/` y WordPress empieza a guardar transients, consultas y objetos en Redis en lugar de en la tabla de opciones.

Hay un nivel de pago llamado Object Cache Pro con analíticas de caché y optimizaciones específicas para WooCommerce, pero la versión gratuita va bien para la mayoría de los sitios. Si tienes una tienda WooCommerce pesada con muchos compradores simultáneos, merece un vistazo.

- [Redis Object Cache en wordpress.org](https://wordpress.org/plugins/redis-cache/)

### Super Page Cache for Cloudflare

Nombre completo en wordpress.org: **Super Page Cache - Cloudflare Cache, Page Speed & Core Web Vitals**. Respaldado por Themeisle, este plugin conecta WordPress con las Cache Rules de Cloudflare y purga la caché del edge automáticamente al publicar. También incluye caché en disco, lazy loading, eliminación de CSS/JS sin usar, optimización de base de datos y precarga de caché. Para esta guía solo usamos las funciones de caché y purga de Cloudflare.

<Notice type="info" title="Desactiva los extras que no necesitas">
Super Page Cache v5 hace mucho más que conectar con Cloudflare. Si ya tienes un plugin de optimización aparte para lazy loading o minificación de assets, apaga esas funciones dentro de Super Page Cache para evitar conflictos. La integración de caché + purga de Cloudflare es todo lo que necesitas de él aquí.
</Notice>

- [Super Page Cache en wordpress.org](https://wordpress.org/plugins/wp-cloudflare-page-cache/)


## Configuración de Varnish en CloudPanel

Activa Varnish para tu sitio en CloudPanel:

1. Ve a **CloudPanel → tu sitio → Settings → Varnish Cache** y actívalo.
2. Confirma que el sitio sigue cargando tras activarlo.
3. El plugin CLP Varnish Cache gestiona la purga automática cuando publicas o actualizas contenido.

<Picture formats={["webp"]} fallbackFormat="webp" src={imgVarnish} alt="Ajustes de la caché Varnish de CloudPanel para un sitio WordPress" />

Para operadores que quieran profundizar en el ajuste del VCL, los prefijos de cache tags y los parámetros excluidos, mira la [guía de configuración de CloudPanel Varnish Cache](/es/varnish-cache-cloudpanel/).

Dónde viven las cosas en el servidor: la configuración VCL está en `/etc/varnish/default.vcl` (ejecuta `varnishreload` tras editarla), la unidad de servicio está en `/lib/systemd/system/varnish.service`, y Varnish escucha en el puerto 6081 para las peticiones de purga.

## Configuración de Cloudflare con Super Page Cache

Recorre los ajustes de Super Page Cache en wp-admin. Las etiquetas exactas cambian entre versiones del plugin, pero el flujo es:

1. **Crea un token de API de Cloudflare con alcance** (no la Global API key) con permisos **Zone.Cache Purge** y **Zone.Settings Read** para tu dominio. Acotar limita el radio de daño si la clave se filtra alguna vez.

<Notice type="info" title="Usa un token de API, no la Global API key">
Un token acotado solo puede purgar la caché y leer ajustes de una zona. La Global API key da acceso completo a la cuenta. Prefiere siempre el token.
</Notice>

2. Pega el token en los ajustes de Super Page Cache y selecciona tu dominio de la lista de zonas.
3. Activa la caché de páginas. El plugin maneja las Cache Rules de Cloudflare. No es el viejo interruptor del "modo Standard" de las versiones anteriores a la v5.
4. Confirma que el plugin informa de que las reglas de caché se crearon correctamente.
5. Configura reglas de bypass para las páginas dinámicas (cart, checkout, my-account). Los detalles están en la siguiente sección.

Al publicar, el plugin purga automáticamente la copia de la página cambiada en Cloudflare.

## Cómo verificar cada capa de caché

Antes de fiarte de cualquier configuración de caché, mídela. [Haz benchmark a tu VPS con YABS](/es/benchmark-servidores-cloud/) o al menos anota tus tiempos de carga actuales para comparar después. Luego comprueba cada capa con un solo comando.

<ListCheck>
<ul>
<li>Cloudflare: `cf-cache-status: HIT` en la segunda petición</li>
<li>Varnish: cabecera `x-cache-age` presente y subiendo</li>
<li>Redis: Ajustes → Redis muestra "Connected" y `redis-cli ping` devuelve `PONG`</li>
</ul>
</ListCheck>

### Comprueba las cabeceras de caché de Cloudflare

Ejecuta esto desde tu máquina local (o desde una ventana privada del navegador):

```bash
curl -sI https://example.com | grep -iE 'cf-cache-status|x-wp-cf-super-cache'
```

Salida esperada en una página cacheada:

```
cf-cache-status: HIT
x-wp-cf-super-cache: cache
x-wp-cf-super-cache-active: 1
```

Qué significan los valores: `HIT` significa que la página se sirvió desde el edge de Cloudflare, que es lo que quieres. `MISS` significa primera petición o caché caducada. Carga la página otra vez y debería pasar a `HIT`. `BYPASS` significa que una regla excluyó la página. No es necesariamente un error, pero revisa tus reglas de bypass si no lo esperabas. `EXPIRED` significa que la copia cacheada está vieja y Cloudflare está revalidando. `DYNAMIC` significa no cacheada, que suele ser lo correcto para páginas dinámicas.

`x-wp-cf-super-cache: cache` significa que el plugin está cacheando esta página. `x-wp-cf-super-cache-active: 1` significa que la página aterrizó en la caché de Cloudflare.

### Comprueba las cabeceras de caché de Varnish

El controlador PHP de CloudPanel emite las cabeceras `x-cache-age`, `x-cache-lifetime` y `x-cache-tags` en las páginas cacheadas:

```bash
curl -sI https://example.com | grep -iE 'x-cache-age|x-cache-tags'
```

Salida esperada:

```
x-cache-age: 3
x-cache-tags: aac6
```

Repite la petición y confirma que `x-cache-age` sube (4, 5, 6…). Si se resetea a 0 cada vez, la página no está siendo cacheada por Varnish. Revisa tus exclusiones.

Prueba rápida de purga manual (desde el servidor):

```bash
curl -v -X PURGE -H 'X-Cache-Tags: aac6' 127.0.0.1:6081
```

Sustituye `aac6` por el tag real de tu cabecera `x-cache-tags`. Luego vuelve a pedir la página y confirma que se recachea (x-cache-age se resetea y empieza a subir de nuevo).

### Comprueba la caché de objetos de Redis

Tres comprobaciones rápidas:

1. En wp-admin, abre **Ajustes → Redis**. Muestra "Connected" con métricas de aciertos/fallos tras activarlo.
2. A nivel de SO, ejecuta `redis-cli ping`. Debería devolver `PONG`.
3. El archivo drop-in `wp-content/object-cache.php` debería existir.

Si Ajustes → Redis muestra un error de conexión, la causa habitual es una ruta de socket PHP o un puerto equivocados. Revisa la configuración de Redis de tu versión de PHP en CloudPanel y compárala con la dirección de escucha del servidor Redis.

## Contenido dinámico y reglas de bypass de caché

Esta pila funciona bien para contenido mayormente estático: entradas de blog, landing pages, páginas de producto que no cambian por usuario. Todo lo que sea por usuario debe excluirse de **ambas** capas de caché.

<Notice type="warning" title="Nunca cachees carritos, checkouts ni páginas con sesión iniciada">
Servir páginas cacheadas a usuarios con sesión iniciada significa que un cliente ve el carrito, los datos de la cuenta o la sesión de otro cliente. Es la mala configuración de caché más común y la más dañina.
</Notice>

En el lado de Varnish, añade estos **Excludes** con regex en los ajustes de Varnish de CloudPanel (tal cual de la documentación de CloudPanel):

```
^/my-account/
/cart/
wp-login.php
```

Usa también el campo **Excluded Params** para los parámetros GET que nunca deberían cachearse (p. ej. `__SID`).

En el lado de Cloudflare, añade reglas de bypass equivalentes para las mismas rutas en Super Page Cache. El plugin también tiene una metabox por página para excluir páginas concretas de la caché.

Para una configuración de Varnish más profunda (prefijos de cache tags, comportamiento del controlador PHP), mira la [documentación para desarrolladores de CloudPanel Varnish](https://www.cloudpanel.io/docs/v2/frontend-area/varnish-cache/developer-guide/php-controller/).

## Solución de problemas comunes de caché

### Los usuarios con sesión iniciada ven páginas viejas

Super Page Cache añade un query var anticaché `swcfpc` a los enlaces internos mientras tienes la sesión iniciada. Si los editores ven contenido viejo, suele ser por eso. El rompe-caché fuerza una carga nueva, pero si un rol personalizado evita la detección de sesión iniciada del plugin, el bypass no se dispara.

Solución: confirma que el bypass para usuarios con sesión del plugin está activo y añade la página a las exclusiones si un rol personalizado no está siendo detectado.

### Exclusiones de WooCommerce y páginas de membresía

Síntoma: contenido del carrito compartido entre visitantes, checkout roto o páginas de cuenta mostrando datos equivocados.

Solución: aplica las exclusiones regex de la sección anterior en los ajustes de Varnish de CloudPanel (`^/my-account/`, `/cart/`, `wp-login.php`) más las exclusiones equivalentes de Cloudflare en Super Page Cache. Ambas capas necesitan las mismas exclusiones. Arreglar solo una deja a la otra capa sirviendo páginas dinámicas viejas.

### Subir la memoria de Varnish por encima de 512 MB

El valor por defecto de Varnish en CloudPanel es solo `-s malloc,512m`. En servidores multisitio o sitios con muchas páginas se llena rápido y verás rotación por expulsiones.

Edita la unidad de servicio:

```bash
sudo nano /lib/systemd/system/varnish.service
```

Cambia `-s malloc,512m` por algo como `-s malloc,2048m`, y luego:

```bash
sudo systemctl daemon-reload && sudo systemctl restart varnish
```

Nota sobre el presupuesto de RAM: el malloc de Varnish + Redis + PHP-FPM comparten la memoria de tu VPS. Una máquina de 4 GB va cómoda para esta pila; 2 GB va justa y tendrás que mantener Varnish en 512 MB o hacer swap agresivamente. Esto enlaza con el consejo de "ampliar a un VPS más grande" de más abajo.

### La caché no se purga al publicar

Síntoma: actualizas una entrada pero los visitantes siguen viendo la versión vieja.

Lista de comprobación:
1. El plugin CLP Varnish Cache está activo.
2. Ningún otro plugin de optimización es dueño de la purga. Desactiva la caché de páginas en WP Rocket / LiteSpeed Cache / W3 Total Cache (requisito del propio Super Page Cache).
3. La purga manual funciona: `curl -X PURGE -H 'X-Cache-Tags: <tag>' 127.0.0.1:6081` (ver la sección de verificación).
4. La purga de Cloudflare ocurre vía Super Page Cache. Revisa su página de estado/registro.

<Notice type="error" title="Un dueño de purga por capa">
CLP Varnish Cache es dueño de la purga de Varnish (por tags en el :6081). Super Page Cache es dueño de la purga de Cloudflare (API de Cache Rules). Si la purga automática de Varnish de Super Page Cache entra en conflicto con la purga por tags de CLP en CloudPanel, desactiva una de las dos. Dos plugins purgando la misma capa produce condiciones de carrera y fallos de caché fantasma.
</Notice>

### Dónde viven las cosas en el servidor

| Componente | Ruta / detalle |
|---|---|
| Unidad de servicio de Varnish | `/lib/systemd/system/varnish.service` (escucha en :6081) |
| Configuración VCL | `/etc/varnish/default.vcl` (ejecuta `varnishreload` tras editarla) |
| Controlador PHP | `/home/$siteUser/.varnish-cache/controller.php` (inyectado vía `auto_prepend_file`) |
| Drop-in de Redis | `wp-content/object-cache.php` |
| Puerto de purga | 6081 (Varnish, PURGE por tags) |

El controlador PHP es lo que pone las cabeceras `X-Cache-*` y ejecuta las purgas. Su código está en [github.com/cloudpanel-io/varnish-controllers](https://github.com/cloudpanel-io/varnish-controllers/).

Antes de ejecutar las funciones de optimización de base de datos de Super Page Cache (limpieza de revisiones, OPTIMIZE TABLE), asegúrate de tener copias de seguridad que funcionen. Mira los [plugins gratuitos de backup para WordPress](/es/mejores-plugins-gratuitos-backup-wordpress/) si aún no tienes una estrategia de backup.

### Cómo revertir o desactivar una capa

Desmontaje seguro en orden inverso:

1. **Capa de Cloudflare**: desactiva la caché de páginas en Super Page Cache (o purga y desactiva las Cache Rules que creó).
2. **Capa de Varnish**: apaga Varnish Cache en los ajustes del sitio en CloudPanel.
3. **Capa de Redis**: ve a Ajustes → Redis y haz clic en Disable Object Cache. Eso quita el drop-in. Opcionalmente, para el servicio Redis.

Confirma con las mismas comprobaciones de `curl -sI` de la sección de verificación. Las cabeceras `cf-cache-status` y `x-cache-age` deberían desaparecer. Desactivar una capa de caché no toca tu contenido, así que es seguro hacerlo en cualquier momento.

</Notice>

## Cuando esta pila no es suficiente

Esta configuración de tres capas gestiona bien la mayoría de los sitios WordPress. Si aun así topas con muros de rendimiento, los siguientes pasos en orden:

- **Amplía a un VPS más grande.** Más núcleos de CPU ayudan con las peticiones no cacheadas/dinámicas. Revisa los [benchmarks de VPS ARM vs x86 para WordPress](/es/comparativa-arm-vs-x86-vps/) antes de comprar. Las máquinas ARM suelen dar más núcleos por euro. Si cambias de proveedor, la [comparativa DigitalOcean vs Vultr vs Hetzner](/es/digitalocean-vs-vultr-vs-hetzner/) cubre los pros y contras.
- **Usa una CDN dedicada** como [Bunny.net](https://go.bitdoze.com/bunny) junto a la CDN de Cloudflare o en su lugar. Una CDN dedicada te da más control sobre las reglas de caché y las ubicaciones edge. Mira mi [reseña de Bunny.net](/es/resena-bunny-net/) para números del mundo real.
- **Cambia a un plugin de caché especializado** como FlyingPress para una optimización de páginas más agresiva. Sáltate LiteSpeed Cache en CloudPanel. Solo ayuda en servidores LiteSpeed, y CloudPanel ejecuta NGINX.
- **Mira Object Cache Pro** si tienes WooCommerce con una carga pesada de base de datos. Las analíticas de caché y las optimizaciones específicas de WooCommerce ayudan a identificar consultas lentas.

Si prefieres no operar un VPS en absoluto, pásate a un hosting WordPress gestionado como [Cloudways](https://go.bitdoze.com/cloudways) y deja que ellos se encarguen de la pila de caché.

## Preguntas frecuentes

<Accordion label="¿Necesito las tres capas?" group="faq" expanded="true">
No, pero cada capa cubre un hueco distinto. Cloudflare gestiona la caché global en el edge, Varnish cubre la caché de página completa de tu servidor para las peticiones que fallan en el edge, y Redis acelera las lecturas de objetos/consultas de PHP. Podrías ejecutar solo Cloudflare + Redis y saltarte Varnish, pero entonces cada fallo del edge golpea PHP directamente. En un VPS económico con tráfico real, las tres capas se ganan su sitio.
</Accordion>

<Accordion label="¿Esta pila funciona con WooCommerce?" group="faq">
Sí, con las reglas de bypass de caché de la sección de contenido dinámico aplicadas. Excluye `/cart/`, `^/my-account/`, `wp-login.php` y las páginas de checkout tanto de la caché de Varnish como de la de Cloudflare. Las páginas de producto y categoría se cachean bien y son las que más ganan. Para tiendas pesadas, Object Cache Pro añade optimizaciones de Redis específicas para WooCommerce.
</Accordion>

<Accordion label="¿Esto funciona sin CloudPanel?" group="faq">
Los conceptos, sí. Cloudflare + Varnish + Redis es una pila estándar. Pero la configuración concreta de esta guía (el plugin CLP Varnish Cache, la interfaz de ajustes de Varnish de CloudPanel, el controlador PHP que pone las cabeceras X-Cache) es específica de CloudPanel. En otro panel o en NGINX pelado configurarías Varnish y Redis a mano y usarías otros plugins de purga.
</Accordion>

<Accordion label="¿Super Page Cache es de verdad tan bueno como APO?" group="faq">
Para la mayoría de los sitios, sí. Ambos cachean páginas completas en el edge de Cloudflare y purgan al publicar. APO usa Workers y almacenamiento KV; Super Page Cache usa Cache Rules. El propio FAQ del plugin afirma que ofrece más funciones que APO para los usuarios del plan gratuito. El único escenario en el que gana APO es si ya estás en Cloudflare Pro, ya que viene incluido y te ahorras un plugin. Mira la [sección de verificación](#cómo-verificar-cada-capa-de-caché) para confirmar que cualquiera de los dos enfoques está cacheando tus páginas.
</Accordion>
