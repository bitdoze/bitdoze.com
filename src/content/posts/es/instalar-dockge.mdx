Escribí por primera vez sobre Dockge en 2024, y dos años después sigue siendo mi UI de compose favorita. Esta guía de instalación de Dockge cubre la versión actual 1.5.x: la instalación con Docker Compose, el cambio de seguridad de la consola con el que tropieza mucha gente, el multi-agente y cómo exponer la UI sin salir quemado. Dockge es un gestor de docker compose ligero. Escribes o pegas un archivo compose, haces clic en desplegar, y los archivos se quedan en disco. Donde otras UIs de gestión de Docker siguen apilando funciones, Dockge se mantuvo enfocado en ese único trabajo.

[Dockge](https://github.com/louislam/dockge) está construido por Louis Lam, el mismo desarrollador detrás de [Uptime Kuma](/uptime-kuma-tool/). Tiene más de 24.500 estrellas en GitHub. El soporte multi-agente llegó en v1.4.0 en enero de 2024, y v1.5.0 (marzo de 2025) fue una versión de seguridad que desactivó la consola del host por defecto. Ambas cosas importan para esta instalación, así que las cubro abajo.

## Lo que Dockge hace (y no hace)

Dockge es un gestor de archivos compose. Escribes o pegas un YAML de docker-compose, haces clic en desplegar, y eso es todo. Todos tus archivos compose se quedan en disco en el directorio que elijas. Nada queda bloqueado en una base de datos. Todavía puedes ejecutar `docker compose up -d` desde la terminal y Dockge recoge los cambios.

Esto es lo que obtienes:

<ListCheck>
<ul>
<li>Crear, editar, iniciar, detener, reiniciar y eliminar stacks compose desde una UI web</li>
<li>Editor interactivo de compose.yaml con validación en tiempo real</li>
<li>Terminal web para hacer exec en contenedores en ejecución (funciona desde el primer momento)</li>
<li>Host Console para ejecutar comandos en el propio servidor (desactivada por defecto desde 1.5.0, ver abajo)</li>
<li>Seguimiento de progreso en tiempo real para pulls de imágenes y operaciones de stack</li>
<li>Convertir comandos docker run en YAML compose</li>
<li>Soporte multi-agente (desde v1.4.0) para gestionar stacks en hosts Docker remotos</li>
<li>Almacenamiento basado en archivos, tus archivos compose viven en disco en formato estándar</li>
</ul>
</ListCheck>

Lo que Dockge no tiene: escaneo de vulnerabilidades, RBAC, OIDC/SSO, API REST, GitOps ni auto-actualizaciones. Si necesitas alguna de esas, revisa [Arcane](/es/instalar-arcane/) (GitOps + API), [Dockhand](/es/instalar-dockhand/) (escaneo de seguridad + auto-actualizaciones), o [UsulNet](/es/instalar-usulnet/) (todo en un binario). ### Instalar Docker

Si Docker aún no está instalado, el script oficial de conveniencia es el camino correcto más corto. Detecta tu distro y configura el repositorio adecuado:

```sh
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER
```

Cierra sesión y vuelve a entrar (o ejecuta `newgrp docker`) para que la pertenencia al grupo tenga efecto. Los usuarios de Podman pueden saltarse esto e instalar `podman-docker` en su lugar.

Verifica que funcionó:

```sh
docker version && docker compose version
```

Ambos comandos deberían imprimir una versión. Si `docker version` dice `permission denied on /var/run/docker.sock`, la pertenencia al grupo aún no ha hecho efecto. Vuelve a iniciar sesión e inténtalo de nuevo. Guía completa con notas sobre ARM: [Instalar Docker y Docker-compose para Ubuntu](/install-docker-ubuntu-arm/).

## Instalar Dockge con Docker Compose

Yo uso la disposición del README: `/opt/dockge` para la propia app de Dockge, `/opt/stacks` para los stacks compose que gestiona. Mantenerlos separados significa que puedes respaldar o mover tus stacks sin tocar los datos propios de Dockge.

Todos los ejemplos fijan `louislam/dockge:1`. Eso sigue la última versión mayor estable sin saltar a `nightly`. Si quieres las funciones nightly hoy, mira la sección del [canal nightly](#canal-nightly).

### Instalación rápida

La forma más rápida de tener Dockge funcionando:

```sh
mkdir -p /opt/stacks /opt/dockge
cd /opt/dockge

curl https://raw.githubusercontent.com/louislam/dockge/master/compose.yaml --output compose.yaml

docker compose up -d
```

Eso descarga el archivo compose, crea el directorio de stacks e inicia Dockge.

Verifica antes de abrir el navegador:

```sh
docker compose ps        # state should be "running"
docker compose logs --tail=20
```

Luego abre `http://ip-de-tu-servidor:5001` y confirma que se renderiza la pantalla de primer inicio. Si el contenedor sale inmediatamente, lee los logs. Si obtienes `port is already allocated`, otra cosa ocupa el 5001: `ss -tlnp | grep 5001` te dice qué.

### Instalación personalizada

Si quieres cambiar el puerto o el directorio de stacks, usa la URL generadora:

```sh
mkdir -p /opt/stacks /opt/dockge
cd /opt/dockge

curl "https://dockge.kuma.pet/compose.yaml?port=5001&stacksPath=/opt/stacks" --output compose.yaml

docker compose up -d
```

Cambia `port` y `stacksPath` a lo que necesites. O simplemente crea el archivo compose manualmente:

```yaml
services:
  dockge:
    image: louislam/dockge:1
    restart: unless-stopped
    ports:
      - 5001:5001
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - ./data:/app/data
      - /opt/stacks:/opt/stacks
      # Needed if your stacks pull from private registries:
      # - /root/.docker/:/root/.docker
    environment:
      - DOCKGE_STACKS_DIR=/opt/stacks
```

El montaje comentado de `/root/.docker` es lo que permite a Dockge autenticarse contra registries privados cuando hace pull de imágenes para tus stacks. Descoméntalo solo si lo necesitas, y recuerda que le entrega a Dockge tus credenciales de registry.

<Notice type="warning" title="La ruta de stacks debe coincidir">
El lado izquierdo y derecho del montaje de volumen de stacks deben ser idénticos. Si tus stacks viven en <code>/opt/stacks</code>, móntalo como <code>/opt/stacks:/opt/stacks</code>, no como <code>/opt/stacks:/alguna/otra/ruta</code>. Los archivos compose usan rutas relativas, y se rompen si las rutas no coinciden dentro y fuera del contenedor.
</Notice>

#### Propiedad de los archivos de stack (PUID/PGID)

Si quieres que los archivos de stack pertenezcan a un usuario no-root, puedes definir `PUID` y `PGID`:

```yaml
    environment:
      - DOCKGE_STACKS_DIR=/opt/stacks
      # Stack file ownership. Both required, no-op if only one is set.
      - PUID=1000
      - PGID=1000
```

<Notice type="info" title="PUID/PGID es solo de nightly">
Esto se mergeó en abril de 2026 (PR #83) y solo está en la imagen <code>nightly</code>. En la estable 1.5.0 estas dos variables no hacen nada. Ambas deben estar definidas para que funcione.
</Notice>

## Activa la consola de Dockge (y por qué está desactivada por defecto)

Este es el cambio que pilla a la gente tras una actualización. Desde 1.5.0, la **Console** de Dockge está desactivada por defecto. Si actualizas desde 1.4.x y la pestaña Console desaparece, no es un bug.

Existen dos terminales diferentes en Dockge y no son lo mismo:

- La **terminal de contenedor** (exec dentro de un contenedor en ejecución) funciona desde el primer momento. No necesita configuración.
- La **Console** es una shell del host. Ejecuta comandos en el propio servidor, con una lista limitada de comandos permitidos en la UI.

La Console viene desactivada por [GHSA-7vx4-hf96-mqq6](https://github.com/louislam/dockge/security/advisories/GHSA-7vx4-hf96-mqq6), un aviso de severidad HIGH publicado el 31 de marzo de 2025. En Dockge 1.4.2 y anteriores, los metacaracteres de shell (`&&`, `|`, backticks) saltaban la lista de comandos permitidos de la Console y daban ejecución arbitraria de comandos como root. Se arregló en 1.5.0 apagando la función salvo que la pidas.

Si quieres la Console de vuelta en 1.5.0 o más reciente:

```yaml
    environment:
      - DOCKGE_STACKS_DIR=/opt/stacks
      # Optional: enable the host Console (terminal) in the UI.
      # Disabled by default since 1.5.0 for security. Requires 1.5.0+.
      - DOCKGE_ENABLE_CONSOLE=true
```

Recrea el contenedor tras editar:

```sh
cd /opt/dockge
docker compose up -d
```

Verifica: la entrada Console aparece en la UI. Quita la variable y recrea de nuevo para volver a apagarla.

<Notice type="error" title="Esto es una shell de root">
Activar la Console da a cualquier usuario de Dockge con sesión iniciada una shell de root en el host. En una máquina de homelab con un solo admin es un trato razonable. En cualquier cosa compartida o expuesta a internet, déjala apagada y usa SSH en su lugar.
</Notice>

## Protege Dockge antes de exponerlo

Dockge monta `/var/run/docker.sock`. Ese socket equivale a root en el host. Cualquiera con un login de Dockge puede arrancar un contenedor privilegiado y adueñarse de la máquina. Trata el login de Dockge como una contraseña de root.

<Notice type="warning" title="docker.sock equivale a root">
No publiques el puerto 5001 en crudo a internet. Encima, los puertos publicados por Docker saltan las reglas de UFW por completo, así que tu firewall puede darte una falsa sensación de seguridad. Mira [los puertos publicados de Docker saltan las reglas del firewall UFW](/es/docker-evita-firewall/) para saber por qué, y [cómo aseguré mi servidor Docker con UFW tras el informe del BSI](/es/informe-seguridad-bsi-docker-ufw/) para el refuerzo completo que aplico en servidores nuevos.
</Notice>

Opciones ordenadas para un operador en solitario:

| Opción | Esfuerzo | Exposición |
|---|---|---|
| Solo LAN / Tailscale / WireGuard | Bajo | Ninguna pública. Mi opción por defecto para homelab |
| Cloudflare Tunnel + Cloudflare Access | Bajo | Ninguna pública, auth zero-trust delante |
| Proxy inverso + TLS + auth | Medio | Público, con barrera. Config abajo |
| `:5001` en crudo en una IP pública | Ninguno | Radio de explosión total. No lo hagas |

Cloudflare Tunnel más Cloudflare Access es gratis a escala de homelab. No necesitas un WAF de pago para ejecutar una UI de compose personal.

Checklist de refuerzo:

<ListCheck>
<ul>
<li>Pon TLS y autenticación delante de Dockge (proxy inverso, Tunnel + Access, o VPN)</li>
<li>Mantén la Console del host apagada salvo que de verdad la necesites</li>
<li>Mantén el pin de imagen <code>:1</code> y actualiza de forma deliberada, no con un cron</li>
<li>Respalda el directorio de datos y el directorio de stacks (ver abajo)</li>
<li>No reutilices tu contraseña de admin de Dockge en ningún otro sitio</li>
<li>Si debes exponer el puerto directamente, aplícale firewall bien y sabe que Docker atravesará UFW</li>
</ul>
</ListCheck>

## Actualizar Dockge

Haz pull de la última imagen y reinicia:

```sh
cd /opt/dockge
docker compose pull && docker compose up -d
```

Tus datos y stacks se conservan ya que viven en volúmenes montados. El pin `:1` apunta actualmente a código de la era 1.5.0, así que las actualizaciones rutinarias se quedan dentro de esa versión mayor.

Verifica que la nueva imagen está realmente en ejecución:

```sh
docker compose images
docker compose logs --tail=20
```

Luego carga la UI. Si algo se rompe, el rollback es aburrido a propósito: `docker compose down`, vuelve a fijar el tag o digest anterior en tu archivo compose, `docker compose up -d`. Tu base de datos SQLite y tus stacks no se tocaron nunca.

Tras unos cuantos ciclos de actualización, las imágenes viejas se acumulan en disco. [Limpia las imágenes Docker viejas tras hacer pull de actualizaciones](/cleanup-all-docker-things/) para recuperar el espacio.

### Canal nightly

Si quieres las funciones de la era 1.6.0 ahora (editor CodeMirror, editor global de `.env`, estadísticas de recursos por stack), cambia a la imagen nightly:

```yaml
services:
  dockge:
    image: louislam/dockge:nightly
    restart: unless-stopped
    # ...
```

<Notice type="warning" title="Nightly no tiene garantías de estabilidad">
La imagen nightly se autogenera desde <code>master</code>. Puede romperse, y no hay contrato semver sobre ella. Si necesitas reproducibilidad, fija por digest: <code>louislam/dockge@sha256:...</code>.
</Notice>

Mi regla: quédate en `:1` para cualquier cosa que te importe, ejecuta nightly en una máquina de laboratorio si quieres jugar. Si un build de nightly se come tu editor de compose, el rollback es el mismo de arriba.

## Configuración de proxy inverso

Para SSL y un dominio apropiado, pon un proxy inverso delante de Dockge. El soporte WebSocket es necesario para las actualizaciones en tiempo real y las terminales. Sin él la UI carga y luego se congela.

<Tabs>
  <Tab name="Nginx">

```nginx
server {
    listen 443 ssl http2;
    server_name dockge.yourdomain.com;

    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;

    location / {
        proxy_pass http://127.0.0.1:5001;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

  </Tab>

  <Tab name="Traefik">
    Añade labels al servicio Dockge en tu archivo compose:

    ```yaml
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.dockge.rule=Host(`dockge.yourdomain.com`)"
      - "traefik.http.routers.dockge.entrypoints=websecure"
      - "traefik.http.routers.dockge.tls.certresolver=letsencrypt"
      - "traefik.http.services.dockge.loadbalancer.server.port=5001"
    ```

    Configuración completa de Traefik: [Cómo usar Traefik como proxy inverso en Docker](/es/traefik-proxy-docker/). Para certificados SSL wildcard con Dockge y Traefik, mira la [configuración de certificado wildcard de Traefik](/es/traefik-certificado-wildcard/).
  </Tab>

  <Tab name="Cloudflare Tunnels">
    Apunta un tunnel a `http://localhost:5001`. El manejo de SSL y WebSocket es automático. No hay puertos que abrir en tu servidor. Esta es mi configuración preferida para uso en homelab. Pon Cloudflare Access delante y obtienes autenticación gratis a esta escala.

    ¿Quieres mantener todo autoalojado? [Pangolin es una alternativa autoalojada a Cloudflare Tunnels](/es/pangolin-alternativa-cloudflare-tunnels/) que cubre el mismo terreno con tu propio VPS.
  </Tab>
</Tabs>

También tengo una guía sobre [configurar Dockge con CloudPanel](/cloudpanel-setup-dockge/) si usas ese panel.

Verifica el proxy antes de seguir:

```sh
curl -I https://dockge.yourdomain.com
```

Quieres un 200 (o 302 al login) sobre TLS. Luego abre la UI y mira cómo llega una línea de log en vivo sin refrescar. Si los logs nunca se actualizan, faltan las cabeceras de upgrade de WebSocket. Si obtienes un 502, el puerto upstream es incorrecto o Dockge no está en ejecución.

## Configuración multi-agente

Desde v1.4.0 (enero de 2024), Dockge puede gestionar stacks en hosts Docker remotos. Ejecutas un agente Dockge en cada máquina remota, y todos aparecen en la UI principal de Dockge. El navegador solo habla con la instancia principal. La principal hace proxy de cada acción hacia los agentes por su conexión de agente.

<Image src={agentTopology} alt="Topología multi-agente: el navegador solo habla con la instancia principal de Dockge, que conecta con agentes Dockge en hosts remotos, cada uno con su propio socket Docker y directorio de stacks" />

En la máquina remota, despliega el agente:

```yaml
services:
  dockge-agent:
    image: louislam/dockge:1
    restart: unless-stopped
    ports:
      - 5001:5001
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - ./data:/app/data
      - /opt/stacks:/opt/stacks
    environment:
      - DOCKGE_STACKS_DIR=/opt/stacks
```

Luego en tu instancia principal de Dockge, ve a la página de agentes y añade el host remoto por su dirección y puerto. Los stacks de ese host aparecen en tu panel junto a tus stacks locales.

<Notice type="info" title="No expongas los puertos de agente públicamente">
Los agentes no necesitan DNS público ni TLS. La principal los alcanza, el navegador no. Mantén los puertos de agente en una red privada, detrás de una VPN, o con firewall para que solo la principal pueda conectar.
</Notice>

Verifica: los stacks remotos aparecen en el panel principal tras añadir el agente, y puedes iniciar/detener un stack en el host remoto desde la UI principal. Si el agente es inalcanzable, revisa primero firewall y DNS. Si el agente conecta pero faltan sus stacks, el `DOCKGE_STACKS_DIR` del agente está mal. La misma regla de desajuste que la principal.

Un detalle solo de nightly: los nombres amigables de agente se mergearon en abril de 2026 (PR #414) pero aún no están en la estable.

## Variables de entorno de Dockge

Todo lo que Dockge lee del entorno, verificado contra el árbol de código (octubre de 2026):

| Variable | Qué hace | Notas |
|---|---|---|
| `DOCKGE_STACKS_DIR` | Directorio que contiene tus stacks compose, un subdirectorio por stack | Defínela explícitamente. Debe coincidir con el montaje de volumen |
| `DOCKGE_PORT` | Puerto en el que escucha la UI web | Por defecto `5001` |
| `DOCKGE_HOSTNAME` | Dirección de enlace para la UI web | Opcional |
| `DOCKGE_DATA_DIR` | Dónde vive la base de datos SQLite (usuarios, ajustes, agentes) | Por defecto `/app/data` en el contenedor |
| `DOCKGE_ENABLE_CONSOLE` | Activa la Console del host en la UI | Desactivada por defecto desde 1.5.0 |
| `DOCKGE_HIDE_LOG` | Oculta la salida de log propia de Dockge en la UI | Opcional |
| `DOCKGE_SSL_CERT` | Ruta del certificado TLS si Dockge termina TLS por sí mismo | Normalmente déjalo a tu proxy inverso |
| `DOCKGE_SSL_KEY` | Ruta de la clave privada TLS | Igual |
| `DOCKGE_SSL_KEY_PASSPHRASE` | Passphrase para la clave TLS, si tiene una | Igual |
| `PUID` / `PGID` | Propietario de los archivos de stack al guardar | Solo nightly / 1.6.0. Ambas requeridas |

<Notice type="info" title="No está en la documentación">
<code>DOCKGE_ENABLE_CONSOLE</code> y <code>PUID</code>/<code>PGID</code> se comportan de forma diferente entre la estable 1.5.0 y master. La tabla lo marca por fila. No existe ninguna variable <code>DOCKGE_ENDPOINTS</code>, pese a lo que afirman algunos artículos.
</Notice>

Estos valores viven en tu archivo compose o en un `.env` junto a él. No subas ninguno de los dos a un repo público. El editor global de `.env` que llega en 1.6.0 hará esto más cómodo, pero las reglas no cambian: para cualquier cosa sensible, mira [los secretos de Docker Compose y sus alternativas seguras](/es/secretos-docker-compose/).

## Dockge vs Portainer y otros gestores de Docker

Dockge vs Portainer es la comparación que más pregunta la gente. Portainer es una plataforma completa de gestión de Docker: RBAC, equipos, gestión de registries, edge agents, una API de verdad. Dockge es un gestor de archivos compose con un login. Si necesitas acceso multi-usuario con roles, Portainer gana. Si quieres una UI fina sobre archivos compose en una máquina o un puñado de máquinas, Dockge es menos que ejecutar y menos que se rompa. No comparten estado, así que no hay ruta de migración entre ellos.

Dónde se sitúa Dockge junto a las herramientas más nuevas:

| | Dockge | Arcane | Dockhand |
|---|---|---|---|
| Enfoque | UI de compose | Gestión completa de Docker | Enfocado en seguridad |
| Complejidad | Mínima | Media | Media |
| Escaneo de vulns | No | No | Sí |
| OIDC/SSO | No | Sí | Sí |
| GitOps | No | Sí | Webhooks |
| Auto-actualizaciones | No | No | Sí + rollback |
| API | No | REST | REST |
| Licencia | MIT | BSD-3-Clause | BSL 1.1 |

Dockge es la herramienta correcta cuando no necesitas todos los extras. Encaja en homelab y configuraciones de un solo host donde solo quieres ver tus stacks, revisar logs y reiniciar cosas cuando se rompen. Cuando necesitas GitOps y acceso a API, [Arcane](/es/instalar-arcane/) es la opción mejor.

Para una comparación completa de todas las opciones, mira mi artículo de [alternativas a Portainer](/es/alternativas-portainer/).

## Copia de seguridad de Dockge

Dos directorios contienen todo lo que es difícil de reemplazar:

<ListCheck>
<ul>
<li><code>./data</code> (montado en <code>/app/data</code>): la base de datos SQLite de Dockge, usuarios, ajustes, lista de agentes</li>
<li><code>/opt/stacks</code> (o lo que apunte <code>DOCKGE_STACKS_DIR</code>): tus archivos compose y el <code>.env</code> de cada stack</li>
<li>Ambos, con programación, fuera de la máquina</li>
</ul>
</ListCheck>

Las imágenes no forman parte de esto. Se vuelven a descargar del registry al restaurar. Solo importan las configuraciones y la base de datos de Dockge.

Un patrón simple que funciona: empaqueta los dos directorios en un tar con un cron y envía el tarball a almacenamiento de objetos compatible con S3. Unos pocos GB de almacenamiento de objetos al mes es calderilla comparado con recrear un conjunto de stacks de memoria. Si quieres que el bucket parezca un directorio local, [monta un bucket S3 como filesystem en un VPS](/es/montar-bucket-s3-sistema-archivos-vps/).

Restaurar es lo contrario: copia los directorios de vuelta, `docker compose up -d`, y confirma que aún puedes iniciar sesión. El directorio de datos restaura tus usuarios y agentes, el directorio de stacks restaura tus archivos compose. Se restauran de forma independiente.

Haz una restauración de prueba una vez tras configurar esto. Una copia de seguridad que nunca has restaurado es una esperanza, no una copia.

## Solución de problemas

<Accordion label="Dockge no puede ver stacks compose existentes" group="troubleshoot" expanded="true">

Tus stacks necesitan estar en el directorio que configuraste con `DOCKGE_STACKS_DIR`. Cada stack debería estar en su propio subdirectorio con un archivo compose. Dockge solo recoge archivos llamados `compose.yaml`, `docker-compose.yaml` o `docker-compose.yml`. Cualquier otra cosa es invisible para él. La estructura de directorios debería verse así:

```
/opt/stacks/
├── myapp/
│   └── compose.yaml
├── another-app/
│   └── docker-compose.yml
```

Asegúrate también de que las rutas de montaje de volumen coincidan en ambos lados, como se menciona en la sección de instalación.

</Accordion>

<Accordion label="Errores de WebSocket o la UI no se actualiza" group="troubleshoot">

Tu proxy inverso no está reenviando conexiones WebSocket. Para Nginx, necesitas:

```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";
```

</Accordion>

<Accordion label="Permission denied en el socket de Docker" group="troubleshoot">

El contenedor necesita acceso al socket de Docker. Asegúrate de que el usuario que ejecuta Docker tiene los permisos correctos:

```bash
sudo usermod -aG docker $USER
```

Luego cierra sesión y vuelve a entrar, o reinicia el daemon de Docker.

</Accordion>

<Accordion label="Falta Console tras actualizar a 1.5.0" group="troubleshoot">

Es por diseño, no un bug. La Console del host está desactivada por defecto desde 1.5.0 por un aviso de seguridad. Define `DOCKGE_ENABLE_CONSOLE=true` si la quieres de vuelta, como se cubre en la [sección de consola](#activa-la-consola-de-dockge-y-por-qué-está-desactivada-por-defecto). Las terminales exec de contenedor siguen funcionando sin ninguna variable.

</Accordion>

<Accordion label="PUID/PGID parece no hacer nada" group="troubleshoot">

En la estable 1.5.0 no hace nada. Esa función es solo de nightly/1.6.0, y ambas variables deben estar definidas. Mira la tabla de [variables de entorno](#variables-de-entorno-de-dockge).

</Accordion>

<Accordion label="El puerto 5001 ya está en uso" group="troubleshoot">

Encuentra al culpable:

```sh
ss -tlnp | grep 5001
```

O detén ese servicio o cambia el lado izquierdo del mapeo de puertos en el archivo compose de Dockge, por ejemplo `5002:5001`, y accede a `http://ip-de-tu-servidor:5002` en su lugar.

</Accordion>
