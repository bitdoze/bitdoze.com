Durante el primer año tras el fork de Forgejo a finales de 2022, ambos proyectos eran casi idénticos. Podías cambiar la etiqueta de la imagen en Docker sin notar diferencia. Eso ya no ocurre. Desde que Forgejo se convirtió en un hard fork en 2024, la licencia, los números de versión, el soporte LTS y las rutas de migración se han separado del todo.

La comunidad ya ha votado con sus archivos Compose: en la encuesta de selfh.st de 2026, Forgejo superó a Gitea por primera vez. Aun así, elegir bien depende de lo que realmente necesitas de una forja Git y no del ruido de los foros. Aquí tienes la comparativa directa entre Forgejo v17 y Gitea v28, seguida de un Docker Compose probado para Forgejo 17.0.2 con su runner nativo de Actions (`v13.2.2`).

## Forgejo vs Gitea a finales de 2026

Ambos son servidores Git escritos en Go con pull requests, issues, registro de paquetes/contenedores y Actions CI integrados. Los dos rondan los 100 MB de RAM en reposo (medí `codeberg.org/forgejo/forgejo:17` en **104.5 MiB** en Docker 29.2), unas 20 veces más ligeros que GitLab. Aquí es donde realmente divergen:

| Aspecto | Forgejo | Gitea |
|---|---|---|
| Última versión (nov 2026) | **v17.0.2** (18 nov 2026) | **v28.3.0** (quitó el prefijo `1.` en la 28.0) |
| Rama LTS | **Sí** (v15.0.12 soportada hasta el 15 jul 2027) | Sin línea LTS documentada |
| Licencia | **GPL-3.0-or-later** (desde v9.0) | **MIT** |
| Gobernanza | Dirigido por contribuidores bajo la asociación sin ánimo de lucro Codeberg e.V. | CommitGo, Inc. (empresa) + TOC de 6 puestos (3 empresa, 3 electos) |
| Edición comercial / Enterprise | Ninguna; todo el software es abierto | Planes Enterprise de pago y Gitea Cloud |
| CI / Actions | Forgejo Actions + `forgejo-runner` v13 (alta compatibilidad, prioridad en independencia) | Gitea Actions + `act_runner` (busca paridad con GitHub Actions) |
| Federación ActivityPub | En desarrollo activo (experimental, estrellas federadas ya activas) | Sin trabajo documentado |
| Migración directa desde Gitea | Solo hasta Gitea 1.22; versiones nuevas requieren migración vía API | N/A |

## Por qué tantos self-hosters se pasan a Forgejo

Hay tres motivos concretos y solo uno es político:

1. **Ramas LTS predecibles.** Forgejo publica una versión estable cada trimestre y convierte la primera de cada año en LTS con 15 meses de soporte (actualmente v15.0.x hasta julio de 2027). Si mantienes una forja personal o de equipo pequeño y solo quieres parches de seguridad sin cambios incompatibles cada tres meses, el LTS marca la diferencia.
2. **Sin deriva hacia funciones de pago.** Cuando Gitea Ltd (hoy CommitGo, Inc.) asumió marcas y operación comercial en 2022, el temor era ver funciones enterprise separándose de la edición comunitaria. El paso de Forgejo a GPL-3.0-or-later bajo una entidad sin ánimo de lucro cierra esa puerta.
3. **Endurecimiento y parches más rápidos.** Forgejo suele priorizar seguridad y privacidad antes (v17.0.2 acaba de reforzar validación de claves SSH, tokens con permisos limitados y acceso a secretos en pull requests).

¿Cuándo sigue teniendo sentido **Gitea**? Si el equipo legal de tu empresa prohíbe GPL-3.0, necesitas un contrato de soporte comercial con SLA, o dependes de una paridad muy estricta con GitHub Actions donde `act_runner` sigue de cerca al upstream.

<Notice type="warning" title="¿Todavía puedes cambiar la imagen de Gitea directamente a Forgejo?">
Solo si sigues en Gitea 1.22 o anterior. Las migraciones de base de datos se separaron tras el hard fork, así que arrancar Forgejo 17 sobre una base de Gitea 28 fallará. En versiones recientes de Gitea, levanta un contenedor limpio de Forgejo e importa los repositorios (con issues y PRs) usando el migrador de Gitea integrado por API.
</Notice>

## Desplegar Forgejo 17 + PostgreSQL + Forgejo Runner en Docker

Si prefieres un motor CI externo con YAML más limpio, mi guía de [Forgejo con Woodpecker CI](/es/forgejo-woodpecker-ci-cicd/) sigue plenamente vigente. Si prefieres mantenerlo todo dentro de Forgejo usando `.forgejo/workflows/` al estilo GitHub Actions, aquí tienes el stack nativo probado con `codeberg.org/forgejo/forgejo:17` (17.0.2) y `data.forgejo.org/forgejo/runner:13` (v13.2.2).

Un tropiezo real durante mis pruebas: **no existe la etiqueta `:latest`** para Forgejo Runner en `data.forgejo.org` (`data.forgejo.org/forgejo/runner:latest` devuelve `not found`). Fija siempre la versión mayor (`:13`).

### Paso 1: prepara la carpeta de datos del runner

El contenedor del runner corre sin privilegios root (`uid 1000`). Crea el directorio antes, genera su configuración base y asigna propietario:

```bash
mkdir -p forgejo-stack/runner-data/.cache
cd forgejo-stack

docker run --rm data.forgejo.org/forgejo/runner:13 \
  forgejo-runner generate-config > runner-data/config.yml

sudo chown -R 1000:1000 runner-data
```

### Paso 2: crea `compose.yaml`

Este stack levanta Forgejo 17, PostgreSQL 19 (fíjate en la ruta `/var/lib/postgresql` obligatoria en PG 18+; consulta mi [guía de PostgreSQL 19](/es/postgresql-19-novedades/)), un demonio Docker-in-Docker aislado para los contenedores de CI y el Forgejo Runner. Usar `docker:dind` mantiene las ejecuciones de CI lejos del socket Docker de tu host.

```yaml
services:
  db:
    image: postgres:19-alpine
    container_name: forgejo-db
    restart: unless-stopped
    environment:
      POSTGRES_USER: forgejo
      POSTGRES_PASSWORD: cambia-esta-contrasena-segura
      POSTGRES_DB: forgejo
    volumes:
      - pgdata:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U forgejo"]
      interval: 5s
      timeout: 5s
      retries: 5
    networks:
      - forgejo_net

  forgejo:
    image: codeberg.org/forgejo/forgejo:17
    container_name: forgejo
    restart: unless-stopped
    depends_on:
      db:
        condition: service_healthy
    environment:
      USER_UID: 1000
      USER_GID: 1000
      FORGEJO__database__DB_TYPE: postgres
      FORGEJO__database__HOST: db:5432
      FORGEJO__database__NAME: forgejo
      FORGEJO__database__USER: forgejo
      FORGEJO__database__PASSWD: cambia-esta-contrasena-segura
      FORGEJO__actions__ENABLED: "true"
      FORGEJO__actions__DEFAULT_ACTIONS_URL: "https://data.forgejo.org"
    volumes:
      - ./forgejo-data:/data
      - /etc/timezone:/etc/timezone:ro
      - /etc/localtime:/etc/localtime:ro
    ports:
      - "127.0.0.1:3000:3000"
      - "2222:22"
    networks:
      - forgejo_net

  docker-dind:
    image: docker:dind
    container_name: forgejo-dind
    restart: unless-stopped
    privileged: true
    command: ["dockerd", "-H", "tcp://0.0.0.0:2375", "--tls=false"]
    networks:
      - runner_net

  runner:
    image: data.forgejo.org/forgejo/runner:13
    container_name: forgejo-runner
    restart: unless-stopped
    depends_on:
      - docker-dind
      - forgejo
    user: "1000:1000"
    environment:
      DOCKER_HOST: tcp://docker-dind:2375
    volumes:
      - ./runner-data:/data
    command: ["forgejo-runner", "daemon", "--config", "/data/config.yml"]
    networks:
      - forgejo_net
      - runner_net

volumes:
  pgdata:

networks:
  forgejo_net:
  runner_net:
```

Arranca primero Forgejo y Postgres (el runner necesita registrarse antes de iniciar el demonio):

```bash
docker compose up -d db forgejo
```

Abre `http://127.0.0.1:3000`, completa el instalador de una pantalla y crea tu cuenta de administrador.

### Paso 3: registra el runner y arranca CI

En Forgejo ve a **Administración del sitio -> Actions -> Runners -> Crear nuevo runner** y copia el token. Regístralo una sola vez:

```bash
docker compose run --rm runner forgejo-runner register \
  --no-interactive \
  --instance http://forgejo:3000 \
  --token PEGA_TU_TOKEN_AQUI \
  --name homelab-runner \
  --labels "docker:docker://node:22-bookworm,ubuntu-latest:docker://catthehacker/ubuntu:act-latest"
```

Eso genera `.runner` dentro de `./runner-data/`. Ahora arranca DinD y el runner:

```bash
docker compose up -d docker-dind runner
docker compose logs -f runner
```

El runner aparecerá como **Idle** en la interfaz de Forgejo.

### Paso 4: prueba un workflow

Guarda esto en `.forgejo/workflows/ci.yml` en cualquier repositorio:

```yaml
name: Build check
on: [push, pull_request]

jobs:
  test:
    runs-on: docker
    steps:
      - uses: actions/checkout@v4
      - name: Check environment
        run: |
          node -v
          ls -la
```

Como `FORGEJO__actions__DEFAULT_ACTIONS_URL` apunta a `https://data.forgejo.org`, `actions/checkout@v4` se descarga del espejo oficial de Forgejo sin depender de GitHub.

## Notas antes de pasarlo a producción

<ListCheck>
<ul>
<li><b>Fija la rama LTS si prefieres estabilidad.</b> Cambia <code>codeberg.org/forgejo/forgejo:17</code> por <code>codeberg.org/forgejo/forgejo:15</code> (LTS) para recibir solo parches de seguridad sin cambios de comportamiento trimestrales.</li>
<li><b>Saca contraseñas de <code>compose.yaml</code>.</b> Muévelas a un archivo <code>.env</code> o a [secretos de Docker Compose](/es/secretos-docker-compose/).</li>
<li><b>Respalda tanto Postgres como <code>./forgejo-data</code>.</b> Los repositorios Git están en disco y los issues/PRs en Postgres; con Dokploy puedes automatizarlo siguiendo mi guía de [backups de Dokploy a Cloudflare R2](/es/backups-dokploy-cloudflare-r2/).</li>
<li><b>Pon HTTPS delante.</b> Termina TLS con [Traefik](/es/traefik-proxy-docker/) o Caddy y ajusta <code>ROOT_URL</code> para que las URLs de clonado coincidan con tu dominio.</li>
</ul>
</ListCheck>

## Conclusión

Si montas un servidor Git autoalojado nuevo para homelab o equipo pequeño en 2026, instala **Forgejo**. Tienes el mismo consumo de ~100 MB que Gitea, una rama LTS real, protección GPL-3.0 y Actions CI nativo listo en diez minutos. Quédate con **Gitea** solo si necesitas licencia MIT o soporte comercial de CommitGo.

## Preguntas frecuentes

<Accordion label="¿Forgejo Actions ejecuta workflows existentes de GitHub Actions?" group="faq" expanded="true">
La mayoría de workflows simples (checkout, tests en Node/Python/Go, builds Docker) funcionan con mínimos cambios. Los que dependen de APIs propias de GitHub o acciones publicadas solo en github.com pueden requerir ajustes o URLs completas en `uses:`.
</Accordion>

<Accordion label="¿Conviene usar Forgejo Actions o Woodpecker CI?" group="faq">
Usa Forgejo Actions si ya dominas el YAML de GitHub Actions y quieres menos contenedores. Usa [Woodpecker CI](/es/forgejo-woodpecker-ci-cicd/) si prefieres sintaxis de pipelines más limpia y un motor CI desacoplado de tu servidor Git.
</Accordion>

<Accordion label="¿Por qué falla docker compose con runner:latest not found?" group="faq">
Forgejo Runner no publica etiqueta `:latest` en `data.forgejo.org` a propósito para evitar saltos incompatibles al hacer pull. Fija siempre una etiqueta mayor como `data.forgejo.org/forgejo/runner:13`.
</Accordion>

<Accordion label="¿Puede Forgejo funcionar con SQLite en lugar de PostgreSQL?" group="faq">
Sí. Para un solo desarrollador con unas decenas de repositorios, SQLite funciona bien y ahorra un contenedor. En cuanto hay varios usuarios o muchos logs de Actions, PostgreSQL evita bloqueos de escritura.
</Accordion>
