## CVE-2026-25253: El RCE de 1 clic, ya corregido

Una corrección antes de seguir. CVE-2026-25253 **no** es el ataque a la cadena de suministro de ClawHub. La cobertura inicial mezcló ambos porque el issue de GitHub que reportaba el ataque a ClawHub (#16052) mencionaba el número CVE en su título. Pero CVE-2026-25253 es un fallo distinto: una ejecución remota de código en 1 clic mediante exfiltración del token de autenticación a través del parámetro `gatewayUrl`. El ataque a los 341 skills de ClawHub no parece tener un CVE propio asignado.

CVE-2026-25253 está registrado como [GHSA-g8p2-7wf7-98mq](https://github.com/openclaw/openclaw/security/advisories/GHSA-g8p2-7wf7-98mq), con una puntuación CVSS de 8.8 (ALTO). Afectó al paquete `clawdbot` (el nombre anterior) en versiones hasta la v2026.1.28 incluida. Se **corrigió en v2026.1.29**. Si ejecutas cualquier versión de los lanzamientos 2026.2.x en adelante, ya estás parcheado. El mérito es de Mav Levin en [depthfirst](https://depthfirst.com/post/1-click-rce-to-steal-your-moltbot-data-and-keys) (artículo publicado el 2026-02-01) y del commit de corrección `a7534dc2`.

### Cómo funcionaba la exfiltración del token mediante gatewayUrl

La Control UI (el dashboard web) confiaba en un parámetro `gatewayUrl` de la query string. Cuando alguien abría la UI con una URL manipulada, la UI hacía lo siguiente:

1. Tomaba el valor de `gatewayUrl` de la query string
2. Lo guardaba como la dirección del gateway
3. Se autoconectaba al cargar la página mediante WebSocket
4. Enviaba el token de autenticación del gateway almacenado en el handshake de WebSocket

Un único enlace manipulado o una página maliciosa que incrustase el enlace = robo del token = acceso completo al gateway. El atacante podía entonces cambiar la configuración, hacer llamadas privilegiadas y pivotar más allá.

Un matiz importante: esto funcionaba **incluso cuando el gateway está vinculado a loopback**. El navegador de la víctima hace de puente. El navegador puede alcanzar `localhost:18789`, así que la vinculación a loopback del gateway no protege frente a este ataque.

```
enlace manipulado → el navegador abre Control UI → gatewayUrl de la query string guardado
    → auto-conexión envía token del gateway por WebSocket → atacante recibe el token
        → acceso total al gateway (cambios de config, llamadas privilegiadas)
```

La corrección: los usuarios ahora deben confirmar las nuevas URLs del gateway en la UI antes de establecer la conexión. La UI ya no confía silenciosamente en los valores `gatewayUrl` de la query string.

### ¿Estás afectado?

Ejecuta `openclaw --version`. Si tu versión es v2026.1.29 o superior, esto está parcheado.

```bash
openclaw --version
# Want: 2026.1.29 or later (any 2026.2.x or newer is fine)
```

Si ejecutabas la v2026.1.28 o anterior en enero-febrero de 2026, rota tu token del gateway una vez por precaución. Esta sección se mantiene como referencia: la forma del ataque (el navegador como puente más allá de loopback) es exactamente contra lo que protege el paso de orígenes de la Control UI en la guía de hardening de abajo.

<Notice type="info" title="Ya Parcheado: Mantenido como Referencia">
Esta sección es contexto histórico. El fallo lleva meses corregido. Pero el patrón de ataque (usar el navegador de la víctima para alcanzar un servicio vinculado a loopback) es una clase de defensa que merece la pena entender. Consulta el paso 7 del hardening para ver los controles de origen que lo impiden.
</Notice>

## El ataque a la cadena de suministro de ClawHub: 341 skills maliciosos

El 13 de febrero de 2026, investigadores de seguridad reportaron ([GitHub issue #16052](https://github.com/openclaw/openclaw/issues/16052), cerrado el 2026-02-21) que 341 de los 2,857 skills auditados en ClawHub, el marketplace comunitario de skills, fueron comprometidos en un ataque coordinado a la cadena de suministro. Eso supone una tasa de infección del 12%. No se asignó ningún identificador CVE al ataque a ClawHub como tal.

### Cómo funcionó el ataque

Los skills maliciosos parecían herramientas normales. El ejemplo más documentado, `deeps-agnw6h`, se hacía pasar por una herramienta de investigación "Deep-Agent/Deep-Search". Los skills infectados contenían hasta tres vectores de ataque:

**1. Dropper para macOS (shell codificado en base64)**

Un payload en base64 se decodificaba en un comando curl que descargaba y ejecutaba código arbitrario desde un servidor controlado por el atacante en `91.92.242.30` (rango de hosting búlgaro, vinculado a infraestructura de robo de información).

**2. Instalador falso para Windows**

Un repositorio de GitHub (`toolitletolate/openclaw_windriver`) alojaba un instalador MSI malicioso disfrazado de paquete de drivers.

**3. Backdoor MCP**

Un endpoint oculto de servidor MCP enrutado a través de tunneling `bore.pub` hacia la infraestructura del atacante, dando acceso remoto a cualquier máquina que ejecutara el skill infectado.

### Indicadores de compromiso

Si sospechas que tu instancia pudo verse afectada, busca lo siguiente:

| Tipo | Valor | Notas |
|------|-------|-------|
| **Dirección IP** | `91.92.242.30` | Servidor de entrega del payload para macOS |
| **Ruta URL** | `http://91.92.242.30/6wioz8285kcbax6v` | Payload del dropper |
| **Dominio de túnel** | `bore.pub` | Tunneling reverso para backdoor MCP |
| **Puerto de túnel** | `44876` | Endpoint del backdoor MCP |
| **Repositorio GitHub** | `toolitletolate/openclaw_windriver` | Instalador falso para Windows |

Revisa tus logs de red en busca de conexiones a estas direcciones. Si encuentras coincidencias, asume que hubo compromiso y rota todas las claves API y credenciales almacenadas en tu configuración de OpenClaw.

### Qué hacer ahora mismo

Si instalaste algún skill de ClawHub antes de mediados de febrero de 2026, repasa esta lista de verificación:

<ListCheck>
<ul>
<li>Actualiza OpenClaw: `openclaw update`</li>
<li>Ejecuta `openclaw security audit --deep` y revisa cada hallazgo</li>
<li>Verifica los skills instalados: `openclaw skills list`; elimina cualquier cosa que no reconozcas</li>
<li>Busca en tus logs de red `91.92.242.30` y `bore.pub`</li>
<li>Si hubo compromiso: rota todas las claves API, tokens de gateway y credenciales de canales</li>
<li>Revisa las conexiones abiertas: `ss -tlnp | grep openclaw` para comprobar listeners inesperados</li>
</ul>
</ListCheck>

<Notice type="warning" title="Coincidencia de IoC = Compromiso Total">
Si alguno de los indicadores anteriores coincide, trátalo como compromiso total. Rota primero, investiga después. La secuencia oficial de respuesta a incidentes es **contener, rotar, auditar, evidencias** (consulta el [manual de respuesta a incidentes para operadores](https://docs.openclaw.ai/gateway/security/operator-incident-response)). Rotar claves es gratis, pero reserva entre 30 y 60 minutos por instancia para hacerlo correctamente.
</Notice>

Si el riesgo de la cadena de suministro cambia por completo tu cálculo sobre los skills comunitarios, hay [alternativas a OpenClaw con diferentes modelos de seguridad](/es/alternativas-openclaw/) que merece la pena evaluar.

## Más de 300 vulnerabilidades de OpenClaw corregidas en cuatro oleadas en 2026

La historia de las "más de 40 correcciones" de febrero de 2026 está obsoleta. A noviembre de 2026, la [lista de avisos de seguridad en GitHub](https://github.com/openclaw/openclaw/security/advisories) para openclaw/openclaw muestra **300 avisos publicados**: 153 de gravedad alta, 132 media y 15 baja. Se divulgaron en dos lotes (75 el 2026-06-30 y 225 el 2026-09-11) y se remediaron en oleadas a lo largo de las versiones 2026.6.x hasta 2026.10.x.

### La oleada de febrero

Las correcciones llegaron en las versiones 2026.2.x justo después de los incidentes. Esto es lo que se parcheó, agrupado por categoría. Es contexto histórico: todo esto lleva mucho tiempo corregido.

**Bypasses de aprobación de ejecución (7 correcciones):**

| Corrección | Qué Estaba Mal |
|------------|----------------|
| Replay entre nodos | Las solicitudes `system.run` aprobadas podían reproducirse entre diferentes nodos |
| Aprobaciones huérfanas | El registro de aprobación en dos fases tenía una condición de carrera que permitía a las aprobaciones saltarse el paso de espera |
| Bypass `env -S` | La discrepancia al interpretar el wrapper `env --split-string` permitía a los comandos evadir las verificaciones de la allowlist |
| Applets `busybox`/`toybox` | Los binarios multiplexores no eran reconocidos en el análisis de wrappers, permitiendo bypasses de allow-always |
| Colisión de rutas en `autoAllowSkills` | Las colisiones de basename en rutas absolutas podían satisfacer las verificaciones de auto-allow de skills |
| Brechas en la denylist de flags safe-bin | Las abreviaciones desconocidas de opciones largas GNU y los flags de `sort` dependientes del sistema de archivos no estaban bloqueados |
| Detección de comandos ofuscados | Los comandos ofuscados no se verificaban antes de las decisiones de la exec allowlist |

**Escapes de sandbox y path traversal (4 correcciones):**

| Corrección | Qué Estaba Mal |
|------------|----------------|
| Escape de workspace en `apply_patch` | Las rutas montadas en sandbox como `/agent` permitían escrituras/eliminaciones fuera del límite del workspace |
| Path traversal en herramienta de imagen | `tools.fs.workspaceOnly` no se aplicaba en la resolución de rutas de `image` en sandbox |
| Fallback de shell en env | El fallback de ruta de shell con prefijo de confianza permitía shells no confiables; ahora solo se confía en las entradas de `/etc/shells` |
| Path traversal en config | Los segmentos de claves prototype y el traversal de propiedades heredadas no se rechazaban en las rutas de `config get/set/unset` |

**XSS e inyección (5 correcciones):**

| Corrección | Qué Estaba Mal |
|------------|----------------|
| Inyección HTML en exportación de sesión | Los tokens de markdown HTML sin procesar en el visor de sesión exportado no estaban escapados |
| Inyección de data-URL en imágenes exportadas | Los campos MIME/base64 de imágenes en el HTML exportado no estaban validados |
| XSS en galería HTML de skills | El skill `openai-image-gen` no escapaba los valores controlados por el usuario en el HTML generado |
| Escape de symlinks en empaquetado de skills | `skill-creator` no omitía los symlinks ni rechazaba las rutas que escapaban de la raíz del skill |
| Exfiltración por deep link en iOS | Las solicitudes `openclaw://agent` se reenviaban al gateway sin confirmación local |

**Prototype pollution y seguridad de configuración (3 correcciones):**

| Corrección | Qué Estaba Mal |
|------------|----------------|
| Normalización de Account-ID | Las claves prototype reservadas no estaban bloqueadas en la normalización de account-id |
| Mutaciones en escritura de config | `unsetPaths` podía mutar los objetos proporcionados por el llamador |
| Filtración de credenciales en CLI config | La salida de `openclaw config get` no se redactaba antes de imprimirse |

**Control de canales y acceso (5 correcciones):**

| Corrección | Qué Estaba Mal |
|------------|----------------|
| Suplantación de remitente de comandos | `commands.allowFrom` coincidía con identidades `From` con forma de conversación (canales, grupos, hilos) |
| Coincidencia de nombres mutables | `allowFrom` coincidía con nombres/tags/emails mutables en lugar de IDs estables |
| Inconsistencia en política de coincidencia de nombres | Las verificaciones de `dangerouslyAllowNameMatching` variaban entre el core y los canales de extensión |
| Alcance de auto-aprobación ACP | Los nombres de herramientas desconocidos y las lecturas de archivos fuera de alcance se auto-aprobaban |
| Bypass de `selfChatMode` | El control de acceso de entrada de WhatsApp no respetaba la configuración de `selfChatMode` |

**SSRF y red (2 correcciones):**

| Corrección | Qué Estaba Mal |
|------------|----------------|
| SSRF en media de Telegram | El rango de benchmark RFC2544 (`198.18.0.0/15`) no estaba bloqueado por defecto para descargas de media |
| Política SSRF del navegador | El acceso a red privada estaba permitido por defecto sin configuración explícita |

**Voz, webhooks y otros (4+ correcciones):**

| Corrección | Qué Estaba Mal |
|------------|----------------|
| Replay de webhook de Twilio | Los IDs de eventos del proveedor no se preservaban a través de la normalización, permitiendo ataques de replay |
| Filtración de credenciales OTEL | Las claves API y tokens se incluían en los diagnósticos de exportación OTLP |
| Filtración de razonamiento/thinking | Los bloques internos de razonamiento se filtraban como respuestas visibles para el usuario en WhatsApp, Discord, Web |
| Filtración de credenciales en reset de sesión | Los mensajes de confirmación de `/new` y `/reset` exponían prefijos de claves API |

### Oleadas de junio a octubre

Tras los lanzamientos de febrero, el ritmo no aflojó. La API de avisos muestra cuatro oleadas de remediación (junio, julio, agosto y los seguimientos de septiembre/octubre) en seis lotes de versiones:

| Oleada de versiones | Avisos corregidos | Ejemplos destacados |
|---|---|---|
| 2026.6.5 - 2026.6.9 | ~69 | Bypass de allowlist de ID de grupo en WhatsApp (GHSA-fh38-965w-f6c3), bypass de aprobación de ejecución con wrapper `flock` (GHSA-3fp5-v549-9v66), bypass de filtro de entorno de transporte externo en Git (GHSA-9969-8g9h-rxwm) |
| 2026.7.1 | 60 | Amplia oleada de correcciones de gravedad media |
| **2026.8.1** | **153** | **La gran actualización:** aprobaciones de ejecución reutilizables que autorizaban argumentos modificados (GHSA-74gc-hg2m-79p9), allowlists de wrappers de ejecución que confiaban en comandos internos (GHSA-ghpx-6xwq-2w4w), confusión de parseo por saltos de línea escapados (GHSA-9f86-pvv5-rxfw), hashes de revisión de config que exponían verificadores de contraseña (GHSA-qgj5-6x35-9g6f), navegador CDP descartando DNS pinning (GHSA-p3h6-v2h4-36q2) |
| 2026.8.11 | 9 | Control UI de iOS omitiendo los pins TLS guardados del gateway (GHSA-jjpc-p3xf-8g7p) |
| 2026.9.x | sin contar | Correcciones adicionales en 2026.9.2 y 2026.9.3 |
| 2026.10.6 / 10.8 / 10.9 | sin contar | "Remediaciones de seguridad" según las notas de lanzamiento |

El patrón que conviene tener en cuenta: **los bypasses de aprobación de ejecución y de allowlists siguieron repitiéndose** a lo largo de las cuatro oleadas. Actualizar es necesario pero no suficiente. La defensa en profundidad (políticas deny más sandbox) es la verdadera respuesta, que es lo que configura la guía de hardening más abajo.

### ¿Qué versión es segura?

- **Mínimo para las oleadas divulgadas: v2026.8.1** (ahí se corrigen 153 avisos)
- **Mejor: v2026.9.3** o posterior
- **Recomendado: la versión estable actual** (v2026.11.1 a noviembre de 2026)

## Leer las etiquetas de auditoría de ClawHub antes de instalar

Tras el ataque de febrero de 2026, ClawHub desplegó un sistema completo de auditoría y moderación. Esta es la respuesta directa del ecosistema al problema de la cadena de suministro, y deberías usarla.

### Estados de auditoría y niveles de riesgo

Cada lanzamiento de un skill en ClawHub recibe una auditoría de seguridad con dos dimensiones:

**Estado** (el veredicto):

| Estado | Significado |
|--------|-------------|
| **Pass** | Sin hallazgos significativos. Seguro de instalar según la auditoría. |
| **Review** | Hallazgos que requieren criterio humano. Lee los detalles antes de instalar. |
| **Warn** | Se encontraron patrones arriesgados. Continúa solo si entiendes los hallazgos. |
| **Malicious** | No lo instales. El skill contiene código o patrones hostiles. |
| **Pending** | Auditoría aún no completada (lanzamiento nuevo o actualizado). |
| **Error** | La auditoría falló al completarse. Trátalo con precaución. |

**Nivel de riesgo** (la gravedad): Low, Medium o High. Los hallazgos individuales se gradúan de Info a Critical. Los hallazgos de baja confianza se ocultan del resumen para que no te ahogues en ruido.

Qué comprueba ClawHub: instrucciones y metadatos del skill, variables de entorno y permisos declarados, instrucciones de instalación, manifiestos de archivos y metadatos de capacidades. La pregunta clave es la **coherencia**: ¿el contenido real del skill coincide con su propósito declarado? Un skill de "consulta meteorológica" que ejecuta `curl` en el shell y decodifica payloads en base64 fallará la comprobación de coherencia.

ClawHub también cuenta con una capa de moderación: reportes de usuarios, retenciones en listados sospechosos, listados ocultos y bloqueos. Los listados externos (marcados con `skills-sh:`) se etiquetan como **"Not scanned by ClawHub"** y ese estado persiste entre actualizaciones.

### Verifica y fija versiones de skills

La CLI te ofrece herramientas de verificación y fijado de versiones:

```bash
# Verify a specific skill and show its audit card
openclaw skills verify @owner/my-skill --card

# Install a pinned version
openclaw skills install @owner/my-skill --version 1.2.0

# Update all installed skills (deliberately unpins)
openclaw skills update --all
```

Antes de instalar cualquier skill:

<ListCheck>
<ul>
<li>El estado de la auditoría es **Pass** (o has leído y aceptado los hallazgos de **Review**)</li>
<li>El nivel de riesgo es **Low** (o entiendes los riesgos Medium/High)</li>
<li>Ejecuta `openclaw skills verify @owner/slug --card` y lee la ficha de auditoría</li>
<li>Fija una versión específica con `--version` para actualizaciones predecibles</li>
<li>Lee las instrucciones de instalación y los permisos declarados antes de confirmar</li>
</ul>
</ListCheck>

<Notice type="success" title="Esta Es la Solución del Ecosistema">
Las etiquetas de auditoría, el sistema de moderación y el fijado de versiones son exactamente lo que faltaba en febrero de 2026. Úsalos. Un skill etiquetado como Pass con riesgo Low ha sido escaneado buscando los mismos patrones que detectaron los 341 skills maliciosos.
</Notice>

Fijar versiones significa actualizaciones predecibles: tú decides cuándo pasar a una nueva versión. Cuando estés listo para actualizar todo de golpe, `openclaw skills update --all` lo hace de forma deliberada.

Si quieres una alternativa aislada por contenedores para ejecutar código de agentes de terceros, [NanoClaw en Docker](/es/guia-despliegue-nanoclaw/) mantiene el radio de impacto contenido en un único contenedor.

## El hook soul-evil: un riesgo integrado eliminado

Independientemente del ataque a ClawHub, investigadores señalaron otro problema en el [issue #8776](https://github.com/openclaw/openclaw/issues/8776): OpenClaw incluía de serie un hook llamado `soul-evil` que podía intercambiar silenciosamente el prompt de sistema principal del agente (`SOUL.md`) por un archivo alternativo (`SOUL_EVIL.md`). Deshabilitado por defecto, pero el código estaba ahí en cada instalación.

El mecanismo era grave: un atacante con acceso a inyección de prompts podía encadenar la herramienta `write` para crear `SOUL_EVIL.md` y luego usar `config.patch` para habilitar el hook. El agente entonces funcionaría bajo instrucciones controladas por el atacante sin ninguna notificación. Peor aún cuando se combinaba con CVE-2026-25253, ya que un token de gateway exfiltrado podía habilitar este hook de forma remota.

<Notice type="success" title="Eliminado del Código Base">
El hook soul-evil fue eliminado por completo del código base en las versiones de febrero de 2026 (PR #14757, fusionado el 2026-02-12). Ya no está presente en ninguna instalación actual. Si tu instalación es anterior a febrero de 2026, actualízala. No te limites a deshabilitar el hook.
</Notice>

La lección: las capacidades incluidas de serie son riesgo incluido de serie. Los hooks ahora son funciones documentadas de primera clase, y deberías saber cuáles carga tu instalación. Después de actualizar, revisa tu configuración en busca de entradas de hooks que no hayas añadido tú mismo.

**Verificar:** `openclaw --version` muestra una versión posterior a febrero de 2026. Haz grep en tu configuración buscando `soul-evil` o `SOUL_EVIL`. No deberías encontrar nada.

## Entendiendo el modelo de confianza de OpenClaw

Antes de cambiar cualquier configuración, conoce lo que OpenClaw considera dentro y fuera del alcance de seguridad. Malinterpretar esto lleva a falsa confianza o esfuerzo desperdiciado.

### Principios fundamentales

<Tabs>
<Tab name="Qué Es De Confianza">

- **Los llamadores autenticados del gateway** se tratan como operadores de confianza
- **Los identificadores de sesión** (sessionKey, IDs de sesión, etiquetas) son controles de enrutamiento, no límites de autorización
- **Los plugins/extensiones** se ejecutan en proceso con privilegios completos del SO
- **Los archivos de memoria del workspace** (MEMORY.md, memory/*.md) se tratan como estado local de operador de confianza
- **Las aprobaciones de ejecución** son guardarraíles del operador, no un límite de autorización multi-tenant

</Tab>
<Tab name="Qué NO Es un Límite">

- Un gateway NO es un límite de usuarios adversarios multi-tenant
- Si un operador puede ver datos de otro en el mismo gateway, eso es esperado
- Que la búsqueda de memoria devuelva contenido escrito por otro proceso es comportamiento esperado
- Que los plugins tengan los mismos privilegios del SO que el proceso de OpenClaw es por diseño

</Tab>
<Tab name="Configuración Recomendada">

- **Un usuario por máquina/host** (o VPS). Para hardware dedicado, consulta el [mejor Mac mini para OpenClaw](/es/mejor-mac-mini-openclaw/). Si ese Mac mini necesita más puertos, el [ASUS DC510](https://go.bitdoze.com/asus-dc510) es un dock Thunderbolt 5 pensado para ese trabajo.
- **Un gateway por usuario** con uno o más agentes dentro
- Para múltiples usuarios: usa instancias VPS separadas o límites de usuario del SO. Un [pequeño VPS en Hetzner Cloud](https://go.bitdoze.com/hetzner) por dominio de confianza cuesta unos 4-5 EUR/mes (clase cx22), así que tener una instancia por dominio de confianza es asequible.
- Para acceso remoto: túnel SSH o Tailscale, no exposición a internet público

</Tab>
</Tabs>

Este es el modelo mental:

```
┌── Una máquina / usuario SO = dominio de confianza ───┐
│                                                      │
│  Gateway (18789) Agentes Plugins Memoria Claves API  │
│                                                      │
│     Todo en esta caja puede ver todo lo demás        │
└──────────────────────────────────────────────────────┘
       ▲               ▲                  ▲
       │               │                  │
Usuarios canal  Skills ClawHub    Inyección prompt
```

Si alguien comparte un gateway contigo, puede ver tus conversaciones, tus claves API y tus archivos de memoria. Eso es por diseño. El límite de seguridad de OpenClaw está a nivel de máquina/usuario del SO, no a nivel de gateway. Los dominios de confianza separados necesitan instancias separadas.

Algunas aclaraciones sobre límites que conviene tener presentes: los identificadores de sesión son controles de enrutamiento, no tokens de autenticación. Las aprobaciones de ejecución son guardarraíles para un único operador de confianza, no un sistema de permisos multi-tenant. Los plugins se ejecutan con los mismos privilegios del SO que el proceso de OpenClaw. Piensa en **identidad, alcance, modelo** en ese orden: quién llama, qué puede alcanzar y qué modelo ejecuta al agente.

Los valores por defecto son permisivos. Según la documentación del modelo de confianza, `tools.sessions.visibility` y `tools.agentToAgent.enabled` vienen con amplio alcance entre agentes (los valores exactos por defecto han variado entre versiones). Configúralos explícitamente; no confíes en que los valores por defecto encajen con tu modelo de amenazas. La guía de hardening de abajo los fija en valores restrictivos.

Ejecutar [OpenClaw con modelos locales de Ollama](/es/openclaw-ollama-modelos-locales/) es otra forma de reducir el radio de impacto: no hay claves API de terceros en la configuración si un skill o instancia resulta comprometido.

## Guía de hardening de OpenClaw (línea base 2026)

Esta es la ruta de hardening de nivel operador. Requisitos previos: OpenClaw instalado y en funcionamiento, acceso al archivo de configuración y soltura editando configuraciones JSON. Cada comando asume un VPS Linux o un host Mac.

Antes de tocar nada, haz copia de seguridad de tu configuración:

```bash
cp openclaw.json openclaw.json.bak.$(date +%F)
```

La línea base endurecida oficial de la documentación tiene este aspecto. Empieza aquí y luego los pasos numerados abajo explican cada área y cómo verificarla:

```json
{
  "gateway": {
    "mode": "local",
    "bind": "loopback",
    "auth": {
      "mode": "token",
      "token": "replace-with-long-random-token"
    }
  },
  "session": {
    "dmScope": "per-channel-peer"
  },
  "tools": {
    "profile": "messaging",
    "deny": ["group:automation", "group:runtime", "group:fs", "sessions_spawn", "sessions_send"],
    "fs": {
      "workspaceOnly": true
    },
    "exec": {
      "security": "deny",
      "ask": "always"
    },
    "elevated": {
      "enabled": false
    },
    "sessions": {
      "visibility": "agent"
    },
    "agentToAgent": {
      "enabled": false
    }
  },
  "channels": {
    "whatsapp": {
      "dmPolicy": "pairing",
      "groups": {
        "*": {
          "requireMention": true
        }
      }
    }
  }
}
```

### 1. Mantén OpenClaw actualizado

Esta es la acción individual de mayor valor que puedes hacer. Verifica tu versión y actualiza:

```bash
openclaw --version
openclaw update
```

`openclaw update` gestiona el flujo de actualización para todos los tipos de instalación. Si instalaste mediante el script instalador (`curl -fsSL https://openclaw.ai/install.sh | bash`), también gestiona el servicio. Después de una instalación limpia, ejecuta `openclaw gateway install` para configurar el servicio systemd (Linux) o LaunchAgent (macOS).

Ejecuta también `openclaw doctor --fix`. Rota un `hooks.token` que estuviera reutilizando accidentalmente el valor de autenticación del gateway.

**Verificar:** `openclaw --version` imprime v2026.8.1 o posterior (objetivo: versión estable actual).

**Modos de fallo:** instalaciones gestionadas por npm que siguen ejecutando `npm update -g openclaw` en lugar de `openclaw update`. Documenta qué flujo de instalación usaste. Servicio no reiniciado tras actualizar: `systemctl restart openclaw` en Linux, o reinicia el LaunchAgent en macOS.

### 2. Ejecuta la auditoría de seguridad integrada

OpenClaw incluye un escáner de seguridad integrado con aproximadamente 135 IDs de comprobación:

```bash
openclaw security audit --deep
```

`--deep` añade comprobaciones en vivo sobre el gateway y los recolectores de plugins. Sin él, la auditoría permanece en frío y en modo solo lectura. Añade `--fix` para auto-remediar lo que pueda:

```bash
openclaw security audit --deep --fix
```

Para CI o cron, usa `--json`:

```bash
openclaw security audit --deep --json > /var/log/openclaw-audit-$(date +%F).json
```

Para ejecuciones autenticadas contra un gateway en vivo: `openclaw security audit --deep --token <token>` o `--auth password --password <pw>`.

IDs de comprobación representativos que conviene conocer: `gateway.bind_no_auth`, `gateway.control_ui.allowed_origins_required`, `runtime.node_security_patch`, `fs.state_dir.perms_world_writable`, `config.insecure_or_dangerous_flags`. El catálogo completo está en la [referencia de comprobaciones de auditoría](https://docs.openclaw.ai/gateway/security/audit-checks).

**Supresiones:** si la auditoría marca algo que has configurado deliberadamente, documenta la supresión en lugar de ejecutar `--fix` en bucle:

```json
{
  "security": {
    "audit": {
      "suppressions": [
        {
          "checkId": "gateway.bind_no_auth",
          "titleIncludes": "loopback",
          "reason": "Single-operator dev instance behind Tailscale"
        }
      ]
    }
  }
}
```

Los hallazgos suprimidos pasan a `suppressedFindings` en la salida JSON. Toda supresión necesita un motivo (`reason`).

La auditoría es compatible con SecretRef, señala la reutilización de `hooks.token` con valores de autenticación del gateway y avisa cuando modelos pequeños (300B parámetros o menos) se ejecutan sin sandbox mientras las herramientas web o de navegador están activadas.

**Verificar:** la auditoría termina sin hallazgos críticos. Guarda la salida `--json` para dejar registro.

**Modos de fallo:** auditoría ruidosa tras una elección deliberada de configuración -> usa supresiones documentadas, no bucles con `--fix`. Programa la auditoría `--json` en cron semanalmente (esto también aparece en la lista de verificación abajo).

### 3. Vincula el gateway a loopback

La superficie HTTP del gateway (Control UI, canvas, endpoints de API) no está endurecida para internet público. Mantenla en localhost. El puerto por defecto del gateway es **18789**:

```json
{
  "gateway": {
    "bind": "loopback"
  }
}
```

Para acceso remoto, usa túnel SSH o Tailscale:

```bash
# SSH tunnel (note: port 18789, not 3000)
ssh -L 18789:localhost:18789 user@your-server

# Or Tailscale serve
tailscale serve --https=443 http://localhost:18789
```

Antes de elegir un patrón de exposición, consulta el [manual de exposición del gateway](https://docs.openclaw.ai/gateway/security/exposure-runbook). La versión resumida:

| Patrón de exposición | Cuándo usarlo |
|---|---|
| Loopback + túnel SSH | Por defecto. Máxima seguridad. |
| Tailscale Serve | Cuando quieres HTTPS sin gestionar certificados. |
| Vinculación a Tailnet / LAN | Solo en red de confianza. |
| Proxy inverso de confianza | Cuando necesitas una URL estable detrás de autenticación. |
| Internet público | **No lo hagas.** El gateway no está endurecido para ello. |

Si optas por la ruta SSH, asegúrate de que el propio servidor SSH esté bloqueado; consulta esta [guía para securizar un servidor SSH en Linux](/es/securizar-servidor-ssh-linux/). Si prefieres autoalojar el plano de control de Tailscale, la [configuración de Headscale](/es/headscale-tailscale-autoalojado/) cubre eso.

Para la Control UI en concreto, hay [dashboards de OpenClaw endurecidos con MFA TOTP](/es/mejores-dashboards-openclaw/) que merece la pena considerar antes de exponer nada.

**Verificar:** `ss -tlnp | grep openclaw` muestra únicamente `127.0.0.1:18789`. El túnel funciona: `curl http://localhost:18789` a través del túnel SSH devuelve la Control UI.

**Modos de fallo:** el puerto 18789 ya está ocupado por otro servicio. Túnel apuntando al puerto 3000 (el antiguo valor por defecto, así que actualiza tu memoria muscular). Tailscale serve mal configurado exponiendo más allá de la tailnet.

**Reversión:** volver a vincular a loopback es la remediación instantánea ante cualquier susto de exposición. Cambia `gateway.bind` de vuelta, reinicia y listo.

### 4. Establece autenticación explícita del gateway

La línea base endurecida configura `gateway.auth` en modo token. La vinculación a loopback no es autenticación. Cualquiera con acceso a la máquina puede alcanzar un servicio en loopback.

```json
{
  "gateway": {
    "mode": "local",
    "auth": {
      "mode": "token",
      "token": "replace-with-long-random-token"
    }
  }
}
```

Genera un token largo y aleatorio (por ejemplo, `openssl rand -hex 32`). Guárdalo en una variable de entorno o SecretRef siempre que sea posible, no en línea dentro de la configuración. Modos de autenticación soportados: token, password, trusted-proxy y device auth. El modo token es la recomendación por defecto.

Mantén el token de autenticación del gateway distinto de los valores `hooks.token` de los canales. La auditoría marca si reutilizas uno para el otro. `openclaw doctor --fix` rota un `hooks.token` reutilizado.

**Verificar:** el gateway rechaza peticiones no autenticadas. El token funciona a través del túnel.

**Modos de fallo:** perder el token implica recuperarlo accediendo al archivo de configuración en el host (otra razón para guardar la copia de seguridad). Reutilización del token entre gateway y hooks (la auditoría lo marcará).

### 5. Habilita el modo sandbox

Los modos de sandbox son `off`, `non-main` y `all`. El antiguo valor `"on"` ya no es válido. El valor por defecto es `off`.

```json
{
  "agents": {
    "defaults": {
      "sandbox": {
        "mode": "non-main",
        "backend": "docker"
      }
    }
  }
}
```

**Se recomienda `non-main` como mínimo.** Aísla en sandbox a todos los agentes no principales mientras deja al agente principal con acceso al host. Usa `all` si tu agente principal no necesita acceso directo al host. Backends: `docker`, `podman`, `ssh`, `openshell`. Claves adicionales: `scope`, `workspaceAccess`.

El endurecimiento contra envenenamiento de memoria también es relevante aquí: los recuerdos recuperados ahora se tratan como contexto no confiable, y `autoCapture` está desactivado por defecto.

**Verificar:** `openclaw sandbox recreate --browser --all` finaliza limpiamente. Un skill de prueba no puede escribir fuera del workspace.

**Modos de fallo:** contenedores de sandbox obsoletos tras actualizaciones: ejecuta `openclaw sandbox recreate --browser --all`. La red `host` de Docker anula por completo el sandbox (no la uses). En redes bridge, configura `sandbox.browser.cdpSourceRange` adecuadamente. Skills que se rompen bajo `all`: baja a `non-main` de forma deliberada, no silenciosa.

### 6. Restringe las herramientas del sistema de archivos y exec

Mantén las herramientas dentro del directorio del workspace:

```json
{
  "tools": {
    "fs": {
      "workspaceOnly": true
    },
    "exec": {
      "applyPatch": {
        "workspaceOnly": true
      },
      "security": "deny",
      "ask": "always"
    }
  }
}
```

La combinación `security: "deny"` más `ask: "always"` está pensada para escenarios de entrada hostil (cualquier momento en que el agente procese contenido no confiable). Ten en cuenta que el valor por defecto actual para un único operador es `security: "full"`, `ask: "off"`. Las aprobaciones de ejecución son guardarraíles opcionales, no una capa de confirmación siempre activa. Endurécelas de forma deliberada.

Para una restricción más amplia de herramientas, usa perfiles de herramientas y grupos denegados (de la configuración base anterior):

```json
{
  "tools": {
    "profile": "messaging",
    "deny": ["group:automation", "group:runtime", "group:fs", "sessions_spawn", "sessions_send"],
    "elevated": {
      "enabled": false
    },
    "sessions": {
      "visibility": "agent"
    },
    "agentToAgent": {
      "enabled": false
    }
  }
}
```

El perfil `"messaging"` limita las herramientas a tareas de comunicación. La lista `deny` bloquea por completo los grupos de herramientas de automatización, runtime y sistema de archivos, además de la creación de sesiones y la mensajería entre agentes. `tools.elevated.enabled: false` previene la escalada de privilegios. `tools.sessions.visibility: "agent"` restringe el alcance de sesiones entre agentes. `tools.agentToAgent.enabled: false` bloquea las llamadas entre agentes.

**Verificar:** la auditoría no muestra ningún hallazgo `plugins.tools_reachable_permissive_policy`. Una llamada a herramienta denegada es rechazada (haz la prueba con una).

**Modos de fallo:** una restricción excesiva que rompa el uso diario. Endurece por capas: primero grupos `deny`, segundo `exec` en `deny`. Para flujos con intervención humana en los que quieres aprobar cada comando, `security: "deny"` con `ask: "always"` es la combinación adecuada.

### 7. Establece orígenes explícitos para la Control UI

Para despliegues fuera de loopback, especifica qué orígenes acepta la Control UI:

```json
{
  "gateway": {
    "controlUi": {
      "allowedOrigins": ["https://your-tailscale-domain.ts.net"]
    }
  }
}
```

Sin esto, el gateway se negará a iniciar (comportamiento fail-closed). Esta es la clase de defensa que CVE-2026-25253 eludió mediante el navegador: el truco de `gatewayUrl` convertía el navegador de la víctima en un puente. Los orígenes explícitos más una versión parcheada (2026.1.29 o posterior) cierran esa vía.

**Verificar:** el gateway arranca normalmente. Una petición desde un origen no listado es rechazada.

### 8. Revisa los skills antes de instalarlos

Más allá de las etiquetas de auditoría de ClawHub tratadas arriba, aplica esta lista antes de instalar cualquier cosa:

<ListCheck>
<ul>
<li>Lee el código fuente del skill antes de instalarlo</li>
<li>Busca payloads codificados en base64 o comandos ofuscados</li>
<li>Busca conexiones de red salientes a hosts desconocidos</li>
<li>Verifica la identidad e historial del autor del skill</li>
<li>Prefiere skills con uso significativo de la comunidad y reseñas</li>

</ul>
</ListCheck>

Trata cada skill como potencialmente hostil hasta verificarlo. Las etiquetas de ClawHub ahora responden a la mitad de estas preguntas por ti. Úsalas.

### 9. Hardening con Docker

Si ejecutas OpenClaw en Docker, las imágenes precompiladas provienen de `ghcr.io/openclaw/openclaw` (el registro principal con procedencia verificada) con un mirror en Docker Hub en `openclaw/openclaw`. Fija etiquetas de versión. No uses `latest`. Las variantes incluyen `slim`, `-browser` y `extended-stable`.

```bash
docker run --read-only --cap-drop=ALL \
  -v openclaw-data:/app/data \
  ghcr.io/openclaw/openclaw:2026.11.1
```

`--read-only` previene escrituras en el sistema de archivos fuera de los volúmenes montados. `--cap-drop=ALL` elimina las capabilities de Linux. Evita mirrors no oficiales.

Para el flujo basado en compose, usa `./scripts/docker/setup.sh` desde el repositorio.

A nivel de red, no uses la red `host` de Docker (anula el sandbox). Mantén un firewall de host delante de todo. Un [firewall DNS como NextDNS](https://go.bitdoze.com/nextdns) añade otra capa: el bloqueo a nivel DNS de dominios C2 maliciosos conocidos habría interceptado las conexiones de retorno a `91.92.242.30` y `bore.pub` del ataque de febrero.

Para una visión más amplia de la defensa en profundidad a nivel de host, consulta [cómo aseguré mi servidor Docker con los hallazgos del informe BSI, Hetzner y UFW](/es/informe-seguridad-bsi-docker-ufw/).

**Verificar:** el ejemplo de `docker run` arranca correctamente. El contenedor no puede escribir fuera de los volúmenes. `docker ps` muestra la etiqueta de versión fijada.

**Modos de fallo:** descargas obsoletas de `latest` que cambian bajo tus pies. Mirrors no oficiales sirviendo imágenes manipuladas. Contenedores de navegador sandbox que necesitan recrearse tras actualizaciones de imagen.

### 10. Versión de Node.js

OpenClaw requiere Node.js **24.16.0+** (en 24.x) o **26.1.0+**. Se recomienda Node 26. Los niveles de parches de seguridad a los que apuntar son **24.22.1+** o **26.12.1+**. Las versiones de parches anteriores tienen vulnerabilidades conocidas.

```bash
node --version
# Want: v24.22.1+ or v26.12.1+
```

La comprobación de auditoría `runtime.node_security_patch` avisa si estás por debajo de esos niveles. Los usuarios de Docker obtienen Node de la imagen base, por lo que este paso importa para instalaciones en bare-metal y con npm.

**Verificar:** `node --version` imprime una versión válida. La auditoría deja de advertir sobre `runtime.node_security_patch`.

Usa esta tabla como revisión periódica. Repásala mensualmente, y después de cualquier cambio de configuración o instalación de skills.

| Verificación | Comando / Acción | Esperado |
|--------------|-----------------|----------|

| Versión de Node.js | `node --version` | v24.22.1+ o v26.12.1+ |
| Auditoría de seguridad | `openclaw security audit --deep --json` | Sin hallazgos críticos; salida guardada |
| Vinculación del gateway | Comprobar config `gateway.bind` | `loopback` |
| Autenticación del gateway | Comprobar config `gateway.auth` | Modo token con un token largo y aleatorio |

<Accordion label="Preguntas Frecuentes" group="faq" expanded="true">

**¿Fueron robados mis datos en el ataque CVE-2026-25253?**

Se trata de dos incidentes distintos. CVE-2026-25253 fue el fallo de robo de token mediante `gatewayUrl`: un enlace manipulado podía robar tu token del gateway a través del navegador. Corregido en v2026.1.29. Los skills maliciosos de ClawHub fueron el incidente más peligroso: si instalaste uno de los 341 skills infectados, el malware tuvo acceso a todo lo que OpenClaw podía acceder, incluidas tus claves API, historial de conversaciones y archivos en el workspace. Potencialmente a toda la máquina si el modo sandbox estaba desactivado. Si ese es tu caso, asume compromiso total y rota todas las credenciales.

**¿Cómo sé si instalé un skill malicioso?**

Ejecuta `openclaw skills list` y comprueba cada skill frente a las etiquetas de auditoría de ClawHub (`openclaw skills verify @owner/slug --card`). Busca en tus logs del sistema y tráfico de red las direcciones IoC listadas arriba (`91.92.242.30`, `bore.pub:44876`). El comando `openclaw security audit --deep` también busca patrones maliciosos conocidos.

**¿Qué versión es segura ejecutar?**

v2026.8.1 es el mínimo para las oleadas de avisos divulgadas (ahí llegan 153 correcciones). v2026.9.3 o posterior es mejor. Se recomienda la versión estable actual (v2026.11.1 a noviembre de 2026). Ejecuta `openclaw update` para llegar a ella.

**¿Por qué exec no pide confirmación por defecto?**

El valor por defecto actual para un host de confianza con un único operador es `security: "full"`, `ask: "off"`. Las aprobaciones de ejecución son guardarraíles opcionales, no una capa de confirmación siempre activa. Esto tiene sentido para un operador en solitario que confía en sus propias entradas. Si el agente procesa contenido no confiable (web scraping, skills comunitarios, mensajes de canales), endurécelo: `tools.exec: { security: "deny", ask: "always" }`.

**¿Qué modo sandbox debería usar?**

`non-main` es la recomendación mínima. Aísla en sandbox a todos los agentes no principales. Usa `all` si tu agente principal no necesita acceso directo al host. `off` (el valor por defecto) solo es aceptable en una máquina donde nada no confiable llega al agente. Backends: `docker`, `podman`, `ssh`, `openshell`. Docker es el más habitual.

**¿Es seguro ejecutar OpenClaw en internet público?**

No. La superficie HTTP del gateway no está endurecida para exposición pública. Vincúlalo a loopback y usa túnel SSH o Tailscale para acceso remoto. Múltiples avisos de seguridad han sido por problemas que solo importan con exposición de red. El [manual de exposición](https://docs.openclaw.ai/gateway/security/exposure-runbook) cubre los patrones seguros.

**¿Debería habilitar `dangerouslyAllowNameMatching`?**

No, a menos que no tengas otra opción. Las allowlists basadas en nombres son vulnerables porque los usuarios pueden cambiar sus nombres para mostrar, nombres de usuario o direcciones de email en cualquier momento. Ya se ha implementado la exigencia de coincidencia solo por ID. Migra a IDs estables. La auditoría sigue avisando sobre nombres, emails o etiquetas mutables en allowlists.

**¿Cuál es la diferencia entre `sandbox.mode` y `workspaceOnly`?**

`sandbox.mode` controla si el agente se ejecuta en un contenedor aislado (`off`, `non-main` o `all`). `workspaceOnly` restringe las operaciones de archivos al directorio del workspace incluso sin un runtime de sandbox. Se complementan mutuamente. Habilita ambos para máxima protección.

**¿Con qué frecuencia debería ejecutar `openclaw security audit`?**

Después de cada actualización de OpenClaw, después de instalar cualquier skill nuevo, y al menos semanalmente para instancias de uso activo. Usa `--deep` para el escaneo exhaustivo. Guarda la salida `--json` en cron para tener un registro histórico. Añade supresiones para decisiones de configuración deliberadas en lugar de ignorar hallazgos.

**¿El modelo de confianza significa que OpenClaw es inseguro?**

No. Significa que el límite de seguridad está a nivel de máquina/usuario del SO, no a nivel de gateway. Esto es habitual en herramientas autoalojadas. Entiende que todo aquel con acceso al gateway tiene privilegios completos de operador y planifica tu despliegue en consecuencia. Un dominio de confianza por instancia.

**¿Puede la inyección de prompts comprometer mi instancia de OpenClaw?**

La inyección de prompts figura como fuera de alcance en el modelo de seguridad de OpenClaw cuando no elude un límite. Pero el hook `soul-evil` demostró cómo la inyección de prompts puede encadenarse con otras funciones para lograr un compromiso persistente. Mantén la superficie de ataque pequeña: sandbox activado, sistema de archivos solo workspace, skills auditados. Los recuerdos recuperados ahora se tratan como contexto no confiable y `autoCapture` está desactivado por defecto. Déjalo así salvo que lo necesites.
