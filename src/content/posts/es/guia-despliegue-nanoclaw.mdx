NanoClaw es la forma con aislamiento en contenedores de ejecutar un agente Claude en tu propio VPS. La reescritura de v2 cambió cómo lo instalas y lo aseguras. Esta guía de despliegue de NanoClaw cubre el flujo completo de v2: instalación, aislamiento en contenedores, WhatsApp, equipos multi-agente, tareas programadas, backups, actualizaciones y solución de problemas. v2 (CalVer `v2026.10.x`) movió el repo a [nanocoai/nanoclaw](https://github.com/nanocoai/nanoclaw), reemplazó el viejo flujo `/setup` con un instalador determinista `bash nanoclaw.sh`, y agregó un vault de credenciales para que las claves API nunca toquen los contenedores.

## Qué es NanoClaw

NanoClaw es un agente Claude ligero y siempre activo al que le envías mensajes desde apps de chat, autoalojado en tu propia infraestructura. Se ejecuta sobre el Agent SDK de Claude. La diferencia principal con otros bots es el modelo de aislamiento: los agentes se ejecutan en contenedores Linux (Docker en Linux/macOS/WSL2) con directorios montados explícitamente. El agente no puede escapar del contenedor y solo puede acceder a lo que tú permites.

v2 vive bajo la [org nanocoai](https://github.com/nanocoai/nanoclaw) en GitHub (licencia MIT, ~31k estrellas a noviembre de 2026; revísalo el día de publicación si el número te importa). Los docs están en [docs.nanoclaw.dev](https://docs.nanoclaw.dev), con una comunidad en Discord y un portal web en portal.nanoclaw.dev.

El modelo de entidades es directo: los **grupos** (chats o dominios de confianza) contienen **sesiones** (conversaciones), que generan **agentes** (contenedores). Los mensajes viajan por un pipeline SQLite de inbox/outbox:

```
messaging apps
  → host process (router) → inbound.db
    → Bun agent container (Claude Agent SDK)
      → outbound.db → host process (delivery) → messaging apps
```

Es un único proceso Node.js en el host con colas de mensajes por grupo y exactamente un escritor por archivo SQLite. Sin microservicios, sin broker de mensajes externo, y el codebase sigue siendo lo suficientemente pequeño como para leerlo en una tarde.

### Por qué existe NanoClaw

OpenClaw tiene casi medio millón de líneas de código, 53 archivos de configuración y más de 70 dependencias. Todo se ejecuta en un proceso Node con memoria compartida. La seguridad es a nivel de aplicación: listas de permitidos y códigos de emparejamiento, no aislamiento a nivel de SO.

NanoClaw toma un enfoque diferente:

<ListCheck>
<ul>
<li>Lo suficientemente pequeño para entender. Un proceso, unos pocos archivos fuente. El codebase es lo suficientemente pequeño como para que Claude Code te lo explique y lo modifique de forma segura.</li>
<li>Seguro por aislamiento. Los agentes se ejecutan en contenedores Linux. El acceso a Bash es seguro porque los comandos se ejecutan dentro del contenedor, no en tu host.</li>
<li>Construido para un usuario. Esto no es un framework. Es software funcional que forkeas y personalizas para tus necesidades exactas.</li>
<li>Skills en lugar de funcionalidades. Los contribuidores no agregan funcionalidades al codebase. Contribuyen skills de Claude Code como <code>/add-telegram</code> que transforman tu fork. Los adaptadores de canales y proveedores literalmente se distribuyen como payloads de skills.</li>
</ul>
</ListCheck>

v2 también es nativo de IA pero de forma híbrida: el instalador es un script determinista (sin Claude en el loop para el setup), y Claude Code maneja las decisiones que requieren criterio como diagnóstico, resume, `/customize`, `/debug` y los skills `/add-*`.

Antes de empezar, asegúrate de tener:

| Requisito | Por qué |

| macOS, Linux o WSL2 | NanoClaw se ejecuta en sistemas tipo Unix |
| Node.js 22+ | Runtime (engines `>=22`; el instalador puede auto-instalarlo) |

## Instala NanoClaw v2 en tu VPS

El camino feliz son tres comandos:

```bash
git clone https://github.com/nanocoai/nanoclaw.git
cd nanoclaw
bash nanoclaw.sh
```

El instalador es un pipeline determinista de 3 etapas. Auto-instala Node 22, pnpm 10, Docker (via get.docker.com + `usermod -aG docker` en Linux) y el vault de credenciales OneCLI. El asistente luego compila o descarga la imagen del agente, instala un servicio systemd de usuario, configura el auth del proveedor y empareja tu primer canal (WhatsApp, Slack, Telegram, Discord, iMessage o CLI).

<Notice type="info" title="Claude Code sigue siendo la interfaz de configuración">
El instalador es scripted, sin Claude en el loop para el setup. Claude Code se invoca automáticamente solo para diagnóstico/resume y para los skills `/add-*` después de la instalación. Si no has usado Claude Code antes, es la herramienta CLI de Anthropic que puede ejecutar comandos y modificar archivos. La usarás para personalización y depuración.
</Notice>

<Tabs>
<Tab name="Instalador (recomendado)">
```bash
git clone https://github.com/nanocoai/nanoclaw.git
cd nanoclaw
bash nanoclaw.sh
```
El asistente te guía por la selección de imagen de contenedor, auth del proveedor, instalación del servicio y emparejamiento del primer canal.

### Qué hace el instalador (3 etapas)

1. **Pre-flight bash de `nanoclaw.sh`** verifica SO, arquitectura, RAM (avisa por debajo de 3.700 MB) y acceso sudo. Sale temprano en entornos no soportados.
2. **`setup.sh`** instala Node 22, pnpm 10, Docker (get.docker.com + grupo docker) y el gateway OneCLI en `127.0.0.1:10254`.
3. **El asistente `pnpm run setup:auto`** maneja la imagen del contenedor del agente, autenticación del proveedor (inicio de sesión de Claude o clave API), servicio systemd de usuario y emparejamiento del primer canal.

El asistente por defecto descarga una **imagen endurecida Echo** precompilada y pineada (digest-pinneada, verificada por arquitectura, con etiquetas de procedencia). Requiere una cuenta NanoClaw gratuita. Un build local es el fallback: define `NANOCLAW_HARDENED_IMAGE` en `.env` para forzar local. Nota: este default ha cambiado entre releases (el README y los docs no coinciden), así que verifica lo que obtienes en una instalación fresca antes de confiar en ello.

### Verificar la instalación

Después de que el asistente termine:

```bash
systemctl --user status nanoclaw-v2-<slug>   # should show active (running)
ncl sessions list                            # container_status: running | stopped
docker ps                                    # agent containers appear per active session
tail -f logs/nanoclaw.log                    # live output
```

Si el servicio no está corriendo, revisa primero `logs/nanoclaw.error.log`. Si no se encuentra `ncl`, puede que tu PATH no incluya el checkout. Ejecútalo desde la raíz del proyecto o usa `pnpm exec ncl`.

### Instalación desatendida (scripted)

Para automatización o despliegues repetibles, maneja el instalador con variables de entorno:

```bash
NANOCLAW_SKIP=container,service \
NANOCLAW_AGENT_NAME=Nano \
NANOCLAW_DISPLAY_NAME="My Agent" \
NANOCLAW_AGENT_PROVIDER=claude \
NANOCLAW_GATEWAY_PROVIDER=onecli \
SECRET_NAME=anthropic \
HOST_PATTERN=api.anthropic.com \
bash nanoclaw.sh
```

Puedes re-ejecutar pasos individuales sin rehacer todo:

```bash
pnpm run setup -- --step container
pnpm run setup -- --step service
pnpm run setup -- --step verify
```

Define `NANOCLAW_NO_DIAGNOSTICS=1` para desactivar los diagnósticos de setup anónimos si prefieres no enviar telemetría.

### One-liner para Proxmox VE (helper de la comunidad)

Si usas Proxmox, el helper de la comunidad [glifocat/nanoclaw-proxmox](https://github.com/glifocat/nanoclaw-proxmox) crea un LXC Debian 13 sin privilegios con defaults sensatos (2 núcleos / 8 GiB / 40 GB, usuario `nanoclaw` dedicado) y un comando `update` integrado.

Si tienes un checkout de v1, `migrate-v2.sh` encuentra una instalación v1 hermana y migra estado de BD, carpetas de grupos, sesiones, tareas programadas y auth de canales (incluyendo el keystore de Baileys).

## Aislamiento en contenedores

Esta es la principal característica que diferencia a NanoClaw. Los agentes se ejecutan en contenedores, no en el proceso principal.

<Notice type="warning" title="Cambio en v2: los contenedores SÍ tienen acceso a red">
A diferencia de v1 (que ejecutaba contenedores con `NetworkMode: 'none'`), los contenedores de v2 tienen **internet saliente normal por defecto**. Es un cambio deliberado: los agentes necesitan acceso a red para búsquedas web, llamadas API y uso de herramientas. Si quieres bloquear el egreso, es opt-in via <code>NANOCLAW_EGRESS_LOCKDOWN=true</code> (se cubre en [Endurecimiento](#endurecimiento-bloqueo-de-egreso--listas-de-permitidos) más abajo). No asumas el modelo de "sin red" de v1.
</Notice>

### Cómo funciona (ciclo de vida del mensaje)

Cuando envías un mensaje a NanoClaw:

1. El mensaje llega via el adaptador de canal (ej. WhatsApp/Baileys)
2. El router del host lo escribe en `inbound.db`
3. El host sweep despierta o crea el contenedor del agente para esa sesión
4. El agent runner Bun 1.4.0 (Claude Agent SDK) procesa el mensaje dentro del contenedor
5. La respuesta se escribe en `outbound.db`
6. La entrega del host la envía de vuelta a la app de chat

Exactamente un escritor por archivo SQLite. Un archivo heartbeat en `/workspace/.heartbeat` rastrea la vivacidad del contenedor. Archivos fuente principales:

```
src/router.ts          # message routing
src/delivery.ts        # outbound message delivery
src/host-sweep.ts      # wakes/creates containers on due ticks
src/session-manager.ts # session lifecycle
src/container-runner.ts # spawns hardened agent containers
src/channels/          # channel adapters
src/providers/         # LLM provider integrations
container/agent-runner/ # in-container Bun agent
```

### Endurecimiento del spawn de contenedores

Cada contenedor de agente se genera con flags de endurecimiento:

```
--cap-drop=ALL                    # drop all Linux capabilities
--security-opt no-new-privileges  # no privilege escalation
--init                            # proper signal handling / zombie reaping
--pids-limit=2048                 # fork bomb protection
--rm                              # disposable container, removed on exit
```

El contenedor se ejecuta como usuario `node` no-root. Los bits setuid se eliminan en el build de la imagen. Los montajes son explícitos: carpeta de sesión + workspace del grupo (lectura-escritura), montajes de código (solo lectura). No hay montaje del home del host, ni `~/.ssh`, ni acceso al socket de Docker. El config `container.json` se remonta como solo lectura.

```
┌─────────────────────────────────────────────────┐
│              agent container                     │
│  ┌───────────────────────────────────────────┐  │
│  │  --cap-drop=ALL                           │  │
│  │  --security-opt no-new-privileges         │  │
│  │  --init --pids-limit=2048 --rm            │  │
│  │  non-root user, stripped setuid           │  │
│  │  explicit mounts only                     │  │
│  └───────────────────────────────────────────┘  │
│  /workspace (group dir, rw)                      │
│  session folder (rw)                             │
│  code mounts (ro)                                │
└─────────────────────────────────────────────────┘
```

Incluso si el agente intenta ejecutar comandos peligrosos, está contenido. El sistema host está protegido.

## Credenciales y modelo de seguridad

El mayor cambio de seguridad de v2: **las credenciales en crudo nunca entran a los contenedores de agentes**. En su lugar, el OneCLI Agent Vault maneja los secretos en la capa de proxy.

### Vault de credenciales OneCLI

OneCLI ejecuta un gateway local en `127.0.0.1:10254`. Así fluyen las credenciales:

```
Claude sign-in / API key
  → OneCLI vault (127.0.0.1:10254)
    → gateway proxy injects auth at the HTTP layer
      → agent container (receives short-lived stubs only)
```

Los agentes nunca tienen claves API en crudo. Si el vault es inalcanzable, el spawn aborta. Ningún contenedor arranca sin el gateway. Los grants de secretos por agente controlan a qué puede acceder cada agente:

```bash
onecli agents grants attach-secret --agent <name> --secret <secret-name>
```

<Tabs>
<Tab name="Claude Pro/Max (por defecto)">
Inicio de sesión OAuth por navegador a tu suscripción Claude Pro o Max. No necesita clave API. Costo mensual fijo de suscripción. Es la ruta de credenciales por defecto en el asistente.
</Tab>
<Tab name="Clave API">
Clave API estándar de Anthropic (`sk-ant-...`). Facturación por uso. Se define durante el asistente o se agrega a `.env` manualmente. La clave se almacena en el vault, nunca en los contenedores.
</Tab>
<Tab name="Token OAuth">
Token OAuth de larga duración (`sk-ant-oat...`). Útil para setups headless/CI donde el inicio de sesión por navegador no es práctico.
</Tab>
</Tabs>

Para cualquier endpoint compatible con Anthropic (proxy autoalojado, gateway alternativo), define `ANTHROPIC_BASE_URL` en `.env`. El token real sigue viviendo en el vault:

```bash
# .env
ANTHROPIC_BASE_URL=https://your-api-endpoint.com
```

El gateway alternativo Iron Proxy está disponible via `NANOCLAW_GATEWAY_PROVIDER=iron-proxy`. El skill `/add-onecli` maneja el setup y upgrades del vault.

### Endurecimiento: bloqueo de egreso + listas de permitidos

El aislamiento en contenedores es fuerte, pero aún deberías revisar a qué puede llegar el agente y qué puede ver.

**El bloqueo de egreso** restringe los contenedores a egreso solo-via-gateway en una red Docker interna:

```bash
# .env
NANOCLAW_EGRESS_LOCKDOWN=true
```

Cuando está habilitado, los contenedores se unen a la red Docker `nanoclaw-egress` sin internet directo. Todo el tráfico saliente se enruta por el gateway. Si el gateway es inalcanzable, obtienes un `EgressLockdownError`, fallando rápido en lugar de caer silenciosamente a egreso abierto.

**La lista de montajes permitidos** controla a qué directorios del host puede acceder el agente más allá de su propio workspace:

```json
// ~/.config/nanoclaw/mount-allowlist.json
{
  "allowedRoots": [
    { "path": "~/projects", "allowReadWrite": true }
  ],
  "blockedPatterns": ["password", "secret", "token"]
}
```

<Notice type="warning" title="Denegado por defecto">
Si este archivo no existe, el agente obtiene <strong>cero montajes adicionales</strong>. Ese es el default seguro. Edítalo via <code>ncl groups config add-mount</code> o escribe el archivo directamente. Los montajes aterrizan bajo <code>/workspace/extra/</code> dentro del contenedor. Usa <code>blockedPatterns</code> para rechazar rutas que coincidan con patrones de nombres de archivo sensibles.
</Notice>

**La lista de remitentes permitidos** en `~/.config/nanoclaw/sender-allowlist.json` controla quién puede enviar mensajes al agente.

El radio de explosión es el grupo de agentes. Las sesiones dentro de un grupo comparten el workspace del grupo en lectura-escritura, y `ncl sessions history` puede leer transcripts hermanos. Pon dominios de confianza diferentes en grupos separados. El guard de symlinks del inbox previene ataques de symlink en el pipeline de mensajes.

Para una mirada más profunda de cómo se compara el aislamiento a nivel de app vs. a nivel de contenedor, mira nuestra [guía de seguridad de OpenClaw](/es/guia-seguridad-openclaw/). Para hardening de servidor más amplio, mira [cómo aseguré mi servidor Docker después del informe BSI de Hetzner](/es/informe-seguridad-bsi-docker-ufw/) y la [guía de CrowdSec para asegurar un VPS](/es/crowdsec-servidor-seguro/). Poner filtrado DNS encima del bloqueo de egreso te da defensa en profundidad: un firewall DNS como [NextDNS](https://go.bitdoze.com/nextdns) atrapa lookups que el gateway podría no atrapar.

## Configuración de WhatsApp

WhatsApp via Baileys (`@whiskeysockets/baileys` 7.0.0-rc.9 pineado) es el canal por defecto documentado. Pero ojo: el trunk solo incluye el canal CLI integrado. Todos los adaptadores de plataforma (WhatsApp, Telegram, Discord, Slack, Teams, iMessage, Signal, Mattermost, Matrix, Google Chat y una docena más) se instalan via `/add-<channel>` desde la rama `channels`. El asistente empareja tu primer canal durante el setup.

<Notice type="error" title="Riesgo de baneo de WhatsApp">
El skill del adaptador advierte que usar un número personal compartido de WhatsApp puede hacer que lo suspendan. Usa un número dedicado o secundario (<code>ASSISTANT_HAS_OWN_NUMBER</code>). No es teórico: WhatsApp detecta activamente la automatización en cuentas personales. El adaptador pide confirmación antes de proceder con un número compartido.
</Notice>

### Autenticación (QR o código de emparejamiento)

El asistente te guía por la autenticación de WhatsApp:

1. Elige código QR o código de emparejamiento
2. **QR**: abre WhatsApp en tu teléfono → Configuración → Dispositivos vinculados → Vincular un dispositivo → escanea el código (timeout de 2 minutos)
3. **Código de emparejamiento**: ingresa el código mostrado en la pantalla de Dispositivos vinculados de tu teléfono (ventana de ~60 segundos)

El auth se almacena en `store/auth/`. Permaneces conectado hasta que cierres sesión explícitamente o WhatsApp expire la sesión del lado del servidor.

Después de emparejar, envía un mensaje de prueba al agente y confirma que responde. Luego verifica el cableado:

```bash
ncl wirings list   # shows chat → agent routes
```

Conecta chats adicionales después via `/manage-channels`.

Cada grupo obtiene su propio contexto:

| Aislamiento | Qué significa |

## Equipos multi-agente

v2 reemplaza el viejo concepto de "Agent Swarms" con **equipos multi-agente**. No hay motor de swarms. En su lugar, los agentes pueden crear y enviar mensajes a otros agentes a través de aristas de permisos.

La herramienta MCP `create_agent` permite a un agente generar un agente ayudante. `agent_destinations` define qué agentes pueden hablar con cuáles (aristas de permisos). Para grupos sin privilegios, la creación de agentes dispara **tarjetas de aprobación**. Un humano debe aprobar antes de que se cree el nuevo agente. El primer agente creado por el asistente obtiene `cli_scope: global`; los agentes creados por grupos tienen por defecto `cli_scope: group`.

Los mensajes agente-a-agente viajan por el mismo pipeline SQLite que los mensajes de chat (`channel_type='agent'`).

Un ejemplo práctico:

```
@Andy research the latest React patterns and have the code reviewer check if our codebase follows them
```

Esto puede generar un agente investigador y un agente revisor que trabajan juntos y reportan de vuelta. En 2026.10.1-rc, los agentes también pueden crear agentes desde plantillas (con aprobación requerida). Las plantillas viven en el [registro nanoclaw-templates](https://github.com/nanocoai/nanoclaw-templates) y usan el formato Agent Plugins 1.0.0. Crea un grupo desde una plantilla con `ncl groups create --template <ref>`.

### Agregar otros proveedores LLM

Claude es el default, pero v2 no es solo-Claude:

<Tabs>
<Tab name="Claude (por defecto)">
Claude Agent SDK. Proveedor por defecto. Funciona con inicio de sesión de suscripción Pro/Max, claves API o tokens OAuth. Selección de modelo por grupo: alias como `sonnet`, `opus`, `haiku`, o IDs de modelo completos. Ajuste `effort` por grupo: `low|medium|high|xhigh|max`.
</Tab>
<Tab name="Codex">

</Tab>
<Tab name="Ollama (local)">

Define `NANOCLAW_DEFAULT_MODEL` en `.env` para un default global. `NANOCLAW_FAST_MODE=true` habilita el tier prioritario pago para Claude/Codex (mayor costo por token, serving más rápido; vale la pena solo si la latencia importa). Para cualquier endpoint compatible con Anthropic, `ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN` en `.env` enruta el tráfico donde quieras (el token sigue viviendo en el vault).

## Tareas programadas

NanoClaw tiene un planificador de tareas integrado para trabajos recurrentes. Las tareas se almacenan como filas `messages_in` en `data/v2.db` (`kind='task'`, con timestamps `process_after` y `recurrence` estilo cron en tu zona horaria). Persisten entre reinicios. El host sweep despierta o crea contenedores en los ticks debidos.

Crea tareas en lenguaje natural desde el chat:

```
@Andy send an overview of the sales pipeline every weekday morning at 9am
@Andy review the git history for the past week each Friday and update the README if there's drift
@Andy every Monday at 8am, compile news on AI developments from Hacker News and TechCrunch and message me a briefing
```

Gestiona tareas con el CLI `ncl`:

```bash
ncl tasks list          # list all scheduled tasks
ncl tasks cancel <id>   # cancel a specific task
```

**Los script gates** son una optimización amigable para el operador: para tareas recurrentes frecuentes, un script gate puede ejecutarse antes de que el agente despierte y saltarse la invocación si no hay trabajo que hacer. Mira `docs/scheduled-tasks.md` en el repo.

## Sistema de memoria

La memoria de v2 vive en un directorio `memory/` por grupo, usando Open Knowledge Format (archivos Markdown con frontmatter YAML):

```
groups/
├── main/
│   ├── memory/
│   │   ├── project-context.md
│   │   └── preferences.md
│   └── instructions.prepend.md   # persona
├── family-chat/
│   ├── memory/
│   └── instructions.prepend.md
└── work-team/
    ├── memory/
    └── instructions.prepend.md
```

`instructions.prepend.md` da forma a la persona del agente. El árbol `memory/` almacena hechos, contexto y conocimiento que el agente acumula.

<Notice type="warning" title="No edites CLAUDE.md">
El <code>CLAUDE.md</code> del grupo se <strong>regenera en cada spawn del agente</strong>. Editarlo es una trampa: tus cambios serán sobrescritos. Edita los archivos en <code>memory/</code> e <code>instructions.prepend.md</code> en su lugar. Los viejos archivos IDENTITY.md/SOUL.md de v1 ya no existen (solo aparecen como artefactos de migración desde OpenClaw).
</Notice>

### Servicio systemd de usuario y logs

El instalador crea una unit systemd de **usuario** en `~/.config/systemd/user/nanoclaw-v2-<slug>.service` y habilita lingering para que el servicio sobreviva al logout de SSH:

```bash
systemctl --user list-units 'nanoclaw-v2-*'
systemctl --user status nanoclaw-v2-<slug>
systemctl --user restart nanoclaw-v2-<slug>
loginctl show-user $USER | grep Linger   # should show Linger=yes
```

<Notice type="info" title="Los logs son archivos, no journald">
NanoClaw loguea a <code>logs/nanoclaw.log</code> y <code>logs/nanoclaw.error.log</code> en la raíz del proyecto. NO uses <code>journalctl</code>: la unit no escribe al journal. Usa <code>tail -f logs/nanoclaw.log</code> en su lugar.
</Notice>

Verifica el servicio: el status muestra `active (running)`, `Linger=yes`, y un mensaje de prueba hace round-trip por el agente. Si no se encuentra la unit, verifica que el slug del checkout coincida. Si el servicio muere al boot, puede que hayas chocado con el tripwire de actualización (ver abajo).

Para un setup Docker no-root dentro de contenedores, mira la [guía de usuario Docker no-root](/es/anadir-usuarios-contenedor-docker/). Y si estás blindando el host Docker en sí, [cómo aseguré mi servidor Docker después del informe BSI de Hetzner](/es/informe-seguridad-bsi-docker-ufw/) cubre firewall y reglas de acceso.

### Backups

NanoClaw almacena estado en un puñado de directorios. Respalda estos:

<ListCheck>
<ul>
<li><code>groups/</code>: árboles de memoria y workspaces</li>
<li><code>data/</code>: v2.db (mensajes, tareas) y v2-sessions</li>
<li><code>store/auth/</code>: sesión/keystore de WhatsApp (la parte difícil de reemplazar)</li>
<li><code>.env</code>: config del proveedor (mantenlo secreto)</li>
<li><code>~/.config/nanoclaw/</code>: listas de permitidos, config de cuenta</li>
</ul>
</ListCheck>

Excluye las imágenes de contenedores; se pueden re-descargar. Un cron simple + tar + copia offsite funciona bien. Para backups offsite apropiados, [monta un bucket S3 como sistema de archivos para backups](/es/montar-bucket-s3-sistema-archivos-vps/) con ZeroFS o JuiceFS. Restic o rclone a cualquier endpoint compatible con S3 también funciona.

### Actualizar NanoClaw y desinstalar

<Notice type="warning" title="Nunca hagas git pull">
Un <code>git pull</code> en crudo dispara una verificación de versión/commit/tree-hash al boot y NanoClaw se niega a arrancar ("NanoClaw stopped: update did not go through the supported path"). Usa siempre la ruta de actualización soportada.
</Notice>

Las actualizaciones pasan por `/update-nanoclaw` en Claude Code. Es una transacción por etapas (7 fases) que crea una rama/tag de backup antes de aplicar cambios. Para hacer rollback:

```bash
pnpm exec tsx scripts/update-nanoclaw.ts rollback --id <transaction-id>
```

El canal estable es `v2026.10.0` (liberado 2026-10-09). Beta es `2026.10.1-rc.x`. Pinea estable para producción a menos que necesites un fix de beta. Actualiza los skills por separado con `/update-skills`.

Si ya hiciste un `git pull` manual y chocaste con el tripwire, usa el comando de rollback de arriba o re-ejecuta `/update-nanoclaw` para reconciliar.

La desinstalación pasa por el mismo script:

```bash
bash nanoclaw.sh --uninstall            # interactive, per-group confirmation
bash nanoclaw.sh --uninstall --dry-run  # preview what would happen
bash nanoclaw.sh --uninstall --yes      # skip confirmations
```

La desinstalación es por alcance de checkout. Tu `.env` se respalda. El gateway compartido y las credenciales en `~/.config/nanoclaw/` se dejan intactos (otros checkouts pueden usarlos). Otros checkouts no se tocan.

## Solución de problemas

NanoClaw está diseñado para depurarse a través de Claude Code, pero no es obligatorio. El toolkit del operador:

<Tabs>
<Tab name="Pregunta a Claude (/debug)">
Ejecuta `/debug` en Claude Code. Analiza logs, verifica la configuración y sugiere fixes. Es el camino más rápido para la mayoría de problemas. Si encuentra un problema que probablemente afecte a otros usuarios, puedes contribuir un fix al skill de setup.
</Tab>
<Tab name="Revísalo tú mismo">
```bash
tail -f logs/nanoclaw.log logs/nanoclaw.error.log

# For verbose output (mount configs + container stderr):
# Set LOG_LEVEL=debug in .env, restart the service

ncl groups list            # list agent groups
ncl sessions list          # container_status: running | stopped
ncl dropped-messages list  # what the router/access gate refused
ncl wirings list           # chat → agent routes
ncl tasks list             # scheduled tasks
docker ps                  # active agent containers
```

Nota: los contenedores corren `--rm`, así que el log del host es la única salida que sobrevive después de que un contenedor termina. El CLI `ncl` usa un socket Unix en `data/ncl.sock` (chmod 0600).
</Tab>
</Tabs>

**Circuit breaker**: después de 6 crashes consecutivos de contenedores, NanoClaw retrocede el arranque hasta 15 minutos. Revisa `logs/nanoclaw.error.log` por la causa raíz antes de reiniciar.

Si ves `FATAL: Container runtime failed to start`, ejecuta `docker info`. Docker no está corriendo o tu usuario no tiene acceso. ¿El disco se llena después de los pulls de imágenes? [Limpia el overlay2 de Docker para recuperar espacio](/es/limpiar-docker-overlay2/).

### Problemas comunes

<Accordion label="WhatsApp desconectado o no empareja" group="troubleshooting" expanded="false">
El logout del lado del servidor puede borrar `store/auth/`. Re-empareja: los códigos QR tienen un timeout de 2 minutos, los códigos de emparejamiento unos 60 segundos. Si el emparejamiento sigue fallando, borra `store/auth/` y re-ejecuta el skill del adaptador de WhatsApp. Ejecuta `/debug` para una revisión guiada.
</Accordion>

<Accordion label="Fallo al iniciar el runtime de contenedores" group="troubleshooting" expanded="false">
Ejecuta `docker info` para confirmar que Docker está corriendo y tu usuario está en el grupo `docker`. En VMs de GCE, las restricciones de sudo hacen que NanoClaw no esté soportado. Si estás corriendo como root, cambia a un usuario no-root con sudo. Después de un reboot, Docker puede arrancar después de NanoClaw. Agrega `After=docker.service` a la unit de usuario si es necesario.
</Accordion>

<Accordion label="El agente nunca despierta" group="troubleshooting" expanded="false">
Revisa `ncl sessions list` por el `container_status`. Revisa `ncl dropped-messages list`: el access gate o el router pueden haber rechazado el mensaje. Verifica que el remitente esté en la lista de remitentes permitidos (`~/.config/nanoclaw/sender-allowlist.json`). Confirma que `ncl wirings list` muestre el chat enrutado al agente correcto.
</Accordion>

<Accordion label="EgressLockdownError" group="troubleshooting" expanded="false">
Habilitaste `NANOCLAW_EGRESS_LOCKDOWN=true` pero el gateway es inalcanzable. El contenedor necesita el gateway para todo el egreso. O arregla el gateway (servicio `onecli` en `127.0.0.1:10254`) o quita el flag de lockdown de `.env` y reinicia.
</Accordion>

<Accordion label="El servicio no arranca después de un git pull manual" group="troubleshooting" expanded="false">
La verificación de versión/commit/tree-hash al boot se niega a arrancar cuando el árbol no coincide con una transacción de actualización soportada. Restaura via `/update-nanoclaw` (reconcilia el estado) o usa el comando de rollback con el último ID de transacción. No intentes saltarte la verificación; está ahí para prevenir estados medio-actualizados.
</Accordion>

<Accordion label="Las tareas programadas no se disparan" group="troubleshooting" expanded="false">
Revisa `ncl tasks list` por el estado de las tareas. Si hay un script gate configurado, puede estar saltándose la invocación (por diseño). Verifica que la zona horaria del recurrence cron coincida con la tuya; las tareas usan la zona horaria del usuario, no UTC. El host sweep despierta contenedores en los ticks debidos; si el servicio está caído, los ticks perdidos no se re-ejecutan.
</Accordion>

<Accordion label="Respuestas lentas o disco lleno" group="troubleshooting" expanded="false">
El cold-start del contenedor agrega unos segundos por despertar. Es el costo del aislamiento. Para el disco: ejecuta `df -h`, luego `docker system prune` o mira la [limpieza de overlay2 de Docker](/es/limpiar-docker-overlay2/). Las imágenes de agentes son grandes (Bun + Chromium + CLIs). Si corres múltiples grupos de agentes, los pulls de imágenes se acumulan. Presupuesta 40 GB+ de disco.
</Accordion>

## FAQ

<Accordion label="Preguntas frecuentes" group="faq" expanded="true">

**¿Por qué solo WhatsApp?**

WhatsApp es el default documentado, no la única opción. El trunk incluye el canal CLI; unos 20 adaptadores (WhatsApp, Telegram, Discord, Slack, Teams, Signal, Matrix y más) se instalan via skills `/add-<channel>`. La filosofía de diseño es fork-y-personaliza: ejecuta un skill para agregar lo que necesites.

**¿Puedo ejecutar esto sin Docker?**

No. Docker es el único runtime incluido. El aislamiento en contenedores es central al modelo de seguridad: el agente corre dentro de contenedores, no como parte del proceso principal. Apple Container en macOS es opt-in via `/convert-to-apple-container`, pero Docker sigue siendo la ruta por defecto y requerida.

**¿En qué se diferencia de simplemente ejecutar Claude Code?**

Claude Code es un CLI interactivo. NanoClaw es un asistente siempre activo al que le envías mensajes desde tu teléfono. Tiene memoria, tareas programadas y contexto por grupo que persiste entre conversaciones. Corre desatendido en un servicio systemd con aislamiento en contenedores.

**¿Pueden varias personas usar una instancia de NanoClaw?**

Sí. Usa grupos separados para diferentes personas o dominios de confianza; los grupos están aislados entre sí. v2 tiene `user_roles` (owners/admins) y wiring por canal para controlar quién puede hablar con qué agente. Tu chat contigo mismo es el canal de admin.

**¿Cuánto cuesta ejecutar NanoClaw?**

VPS: unos $5-10/mes por una máquina de 4 GB en [Hetzner](https://go.bitdoze.com/hetzner) o [Hostinger](https://go.bitdoze.com/hostinger-vps). Acceso a Claude: la ruta por defecto es una suscripción Claude Pro/Max (costo mensual fijo, inicias sesión via navegador). Si usas claves API, la facturación es por uso. El número real depende enteramente de cuánto interactúes con el agente. No cito estimaciones de tokens; mide tu propio uso.

**¿Puedo usar un LLM diferente?**

Sí. v2 soporta múltiples proveedores: `/add-codex` (OpenAI), `/add-opencode` (OpenRouter, Google, DeepSeek), `/add-cursor` (Cursor Agent SDK), `/add-ollama-provider` (modelos locales). Cada grupo puede usar un proveedor diferente. Para cualquier endpoint compatible con Anthropic, define `ANTHROPIC_BASE_URL` en `.env`. Para recomendaciones de modelos, mira [mejores modelos open source para OpenClaw](/es/mejores-modelos-opensource-openclaw/) y [ejecutar modelos locales con Ollama](/es/openclaw-ollama-modelos-locales/). Si quieres un núcleo completamente distinto al Claude Agent SDK, [nanobot](/es/guia-configuracion-nanobot/), [NullClaw](/es/guia-despliegue-nullclaw/) o [ZeroClaw](/es/guia-configuracion-zeroclaw/) valen una mirada.

**¿Cómo agrego Telegram/Discord/Slack?**

Ejecuta el skill correspondiente en Claude Code:
```
/add-telegram
/add-slack
/add-discord
```
Los adaptadores se instalan desde la rama `channels`. Cada uno se conecta a través del asistente.

</Accordion>
