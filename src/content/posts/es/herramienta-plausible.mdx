Plausible Analytics es una herramienta de analítica web de código abierto que no usa cookies. Cloud es de pago tras una prueba de 30 días. La Community Edition autoalojada es gratuita, pero no tiene embudos ni objetivos de ingresos, y se ejecuta con Docker Compose, Postgres y ClickHouse.

Esta reseña cubre lo que tienes hoy, lo que le falta a la edición autoalojada gratuita, cómo montarla con Docker Compose y cómo confirmar que tu sitio envía datos. La reescribí porque la versión de 2023 era una lista de puntos. Desde entonces se rehízo la Stats API y el script del tracker cambió de forma en octubre de 2025, como describe la [guía de actualización del script](https://plausible.io/docs/script-update-guide).

## Qué es Plausible hoy

Plausible es de código abierto bajo la GNU AGPL v3, y el código vive en el repositorio [plausible/analytics](https://github.com/plausible/analytics). El snippet del tracker que incrustas tiene licencia MIT, así que ponerlo en un sitio comercial no arrastra la AGPL a tu código base. El proyecto se financia solo con su nube de pago, sin inversores ni ingresos por publicidad.

Puedes usarlo de dos formas:

- **Plausible Cloud**: el servicio gestionado, alojado en la UE en infraestructura de Hetzner y UpCloud. Añades un snippet y ellos se encargan de actualizaciones, copias de seguridad y filtrado de bots.
- **Plausible Community Edition (CE)**: la edición gratuita y autoalojada. El mismo código base, la ejecutas en tu propio servidor con Docker Compose.

La documentación compara solo Cloud y CE, y CE es lo único que puedes instalar desde el repositorio oficial.

## Qué le falta a la Community Edition

CE no es el producto completo. Plausible reserva algunas funciones solo para la nube a propósito, para que las suscripciones sigan financiando el desarrollo. Según la [página de self-hosting](https://plausible.io/docs/self-hosting), consultada el 2026-11-23:

| | Cloud | Community Edition |
|---|---|---|
| Embudos y recorridos de usuario | Sí | No |
| Objetivos de ingresos de e-commerce | Sí | No |
| Sites API (aprovisionamiento) | Enterprise | No |
| SSO | Enterprise | No |
| Filtrado de bots | Avanzado, toda la red | Básico, User-Agent y spam de referrers |
| Versiones | Varias por semana | Versión de largo plazo, dos veces al año |
| Soporte | Del equipo | Solo comunitario |
| Conector de Data Studio | Sí | No |

La cadencia de versiones es lo que pillará a más de uno. La documentación llama a CE una versión de largo plazo que se publica dos veces al año, así que una función anunciada en el blog de Plausible puede tardar meses en llegar a tu instancia. El [CHANGELOG](https://github.com/plausible/analytics/blob/master/CHANGELOG.md) lista la v3.1.0 el 2025-11-13, la v3.2.0 el 2026-01-16, la v3.2.1 el 2026-05-12 y la v3.2.2 el 2026-11-23, la última etiqueta al escribir esto.

## Tamaño del script, cookies y datos personales

La versión anterior de este artículo decía que el script pesa "menos de 1 KB". Ya no es cierto. El 2026-11-23 el `https://plausible.io/js/script.js` heredado midió 2841 bytes en crudo y unos 1.3 KB con gzip. El script por sitio que entrega hoy el instalador, `pa-<id>.js`, midió 5972 bytes en crudo y unos 2.5 KB con gzip en plausible.io. Una instancia de prueba CE v3.2.2 sirvió su propio `pa-<id>.js` con 6190 bytes y sin cabecera `Content-Encoding`, aunque la petición pedía gzip, así que pon delante un proxy que comprima si los bytes te importan. Ya no cites la cifra de 1 KB.

Las afirmaciones sobre privacidad se mantienen. La [política de datos](https://plausible.io/data-policy) declara que Plausible no usa cookies, ni almacenamiento local, ni identificadores persistentes. Los visitantes únicos se calculan por día con un hash con salt del dominio del sitio, la dirección IP y la cadena User-Agent, y el salt diario cambia cada 24 horas. Por eso no hace falta un banner de cookies para la analítica. En la misma página publican una evaluación legal del RGPD, que es lo que te pedirá la persona de cumplimiento.

Un matiz si lo autoalojas: la política describe la nube. En tu propia instancia, tú eres el responsable del tratamiento, y lo que queda registrado depende de la configuración de tu proxy inverso y de ClickHouse. Mantén el registro de acceso del proxy corto o desactivado para la ruta `/api/event`.

Este es todo el camino de la petición. El navegador carga un script pequeño por sitio, cada página vista sale como un `POST /api/event` y el evento acaba en ClickHouse:

Un evento personalizado con una propiedad se ve así en el navegador:

```html
<button onclick="plausible('Signup', {props: {plan: 'pro'}})">Upgrade</button>
```

Con el seguimiento por clases, el mismo evento es `class="plausible-event-name=Sign+Up plausible-event-plan=pro"` en el elemento. Ninguna de las dos formas aparece en el panel hasta que añades un objetivo de evento personalizado con el mismo nombre en Goals. Los embudos también necesitan que los eventos existan primero; luego encadenas objetivos como pasos.

Las mediciones opcionales son interruptores en la configuración del sitio, y surten efecto sin tocar el snippet. Las opciones que antes eran archivos de script aparte ahora son argumentos de `plausible.init`: `hashBasedRouting: true` para una single page app con URLs con `#`, `fileDownloads: { fileExtensions: [...] }` para acotar los tipos de archivo y `autoCapturePageviews: false` si envías las páginas vistas a mano.

## API: Stats API v2 y Sites API

La Stats API se rehízo como v2. Es una interfaz HTTP de solo lectura con un único endpoint, `POST /api/v2/query`, y los endpoints antiguos de la v1 aparecen ya como heredados en la documentación. Cada consulta necesita un `site_id`, un `date_range` y una lista de `metrics`; `dimensions`, `filters` y `order_by` son opcionales. Devuelve JSON, así que encaja mejor en un cron o en un widget de página de estado que las exportaciones CSV de la v1. Las claves se limitan a un equipo. La documentación da como límite por defecto 600 peticiones por hora, mientras que el código de CE v3.2.2 fija 1.000.000 por hora. En Community Edition no hay planes: cuando lo monté el 2026-11-23, una clave creada en Settings, API keys devolvió `200` con un array `results`.

La Sites API (`/api/v1/sites`) es la interfaz de aprovisionamiento: crear sitios, cambiar dominios, gestionar invitados. El acceso de escritura es una función del plan Enterprise. En Cloud, los endpoints de solo lectura (listar sitios, equipos, objetivos y propiedades personalizadas) también funcionan con una clave normal de la Stats API. Las rutas existen solo en la build de Cloud: en una instancia de prueba CE v3.2.2, `/api/v1/sites` devolvió una página 404, no un error de plan.

Si autoalojas, espera que la Stats API funcione y que `/api/v1/sites` devuelva un 404. Coincide con el "No" de la columna CE de arriba.

## ¿Cuánto cuesta Plausible Cloud?

Plausible Cloud es una suscripción con 30 días de prueba y sin plan gratuito. El precio depende del plan y de tus páginas vistas mensuales. No pongo precios exactos porque cambian; consulta la [sección de precios en plausible.io](https://plausible.io/#pricing).

Hay cuatro planes: Starter para un sitio, Growth para equipos y compartir, Business para embudos, propiedades personalizadas, la Stats API y Data Studio, y Enterprise para SSO, la Sites API, el proxy gestionado y las exportaciones en bruto. El nivel cuenta páginas vistas más eventos personalizados (clics salientes, descargas de archivos, envíos de formularios, seguimiento de 404 y eventos manuales). La prueba incluye todas las funciones de Business sin tarjeta de crédito. Lo que importa para decidir, según la [documentación de suscripciones](https://plausible.io/docs/subscription-plans):

- Un sitio con poco tráfico cae en el nivel de páginas vistas más bajo.
- Un solo mes por encima de tu nivel no cuesta nada extra. Si te pasas dos meses seguidos, Plausible te pide que subas de plan, y los paneles se bloquean si no lo haces en una semana desde el aviso. El autoalojamiento no tiene esa curva, solo la factura de tu servidor.
- Los embudos, los objetivos de ingresos y el conector de Data Studio requieren un plan de pago. Si los necesitas, CE queda fuera tenga el presupuesto que tenga.

## Autoalojar Plausible con Docker Compose

La forma compatible es el repositorio [community-edition](https://github.com/plausible/community-edition). Es un ejemplo de Compose con tres servicios: el propio Plausible, una base de datos Postgres para usuarios y sitios, y ClickHouse para los eventos. Requisitos de su README, consultados el 2026-11-23:

- Docker y Docker Compose
- Una CPU con SSE 4.2 o NEON (ClickHouse lo necesita)
- Al menos 2 GB de RAM recomendados
- Un dominio apuntando al servidor, si quieres TLS de Let's Encrypt

Un VPS pequeño cubre esto, por ejemplo uno de los planes cloud de la [reseña de Hetzner Cloud](/es/hetzner-cloud-resena/). El README recomienda 2 GB porque ClickHouse es la parte que más memoria consume, y el archivo compose monta configuraciones de ClickHouse de bajo consumo para servidores pequeños.

Estos son los nueve pasos, desde el clon hasta una instancia cerrada:

![Diagrama del flujo de instalación de Plausible Community Edition en nueve pasos: clonar, .env, exponer el puerto, docker compose up, registrarse, añadir sitio, instalar el snippet, verificar, cerrar el registro](@assets/images/23/03/plausible-selfhost-setup-flow.webp)

*Flujo de autoalojado de Community Edition: nueve pasos desde el clon hasta un registro cerrado.*

### Arrancar la pila

```bash
git clone -b v3.2.2 --single-branch https://github.com/plausible/community-edition plausible-ce
cd plausible-ce
touch .env
echo "BASE_URL=https://stats.example.com" >> .env
echo "SECRET_KEY_BASE=$(openssl rand -base64 48)" >> .env
echo "HTTP_PORT=80" >> .env
echo "HTTPS_PORT=443" >> .env
cat > compose.override.yml <<'EOF'
services:
  plausible:
    ports:
      - 80:80
      - 443:443
EOF
docker compose up -d
```

`SECRET_KEY_BASE` debe tener al menos 64 bytes; `openssl rand -base64 48` da 64 caracteres. `BASE_URL` debe coincidir con la dirección que abres en el navegador, porque alimenta la comprobación de origen del WebSocket. Una prueba con `BASE_URL=http://localhost:18000` abierta como `127.0.0.1:18000` registró un error de origen y el formulario de registro no hizo nada. El `compose.yml` del repositorio fija la etiqueta de la imagen (v3.2.2 cuando escribí esto). CE también lee un ajuste de `/run/secrets` cuando hay un archivo con el nombre de la variable, así que puedes guardar secretos en archivos. [Secretos de Docker Compose](/es/secretos-docker-compose/) explica cómo funciona ese montaje.

El primer arranque descarga Postgres, ClickHouse y Plausible, así que dale unos minutos y mira `docker compose logs -f plausible` hasta que terminen las migraciones. La primera petición redirige entonces a `/register`.

### Detrás de un proxy inverso

Los puertos 80 y 443 suelen estar ocupados por tu proxy (Traefik, Caddy, Dokploy). Desde la v2.1.2 CE puede emitir sus propios certificados de Let's Encrypt, así que el proxy es opcional. Si mantienes uno, quita el override de 80 y 443, define `HTTP_PORT=8000` en `.env` y publica ese puerto solo en localhost, con `127.0.0.1:8000:8000` bajo `ports` en `compose.override.yml`. Después apunta el proxy a `localhost:8000`. Caddy solo necesita `reverse_proxy localhost:8000`. Nginx necesita `X-Forwarded-For` y un segundo bloque `location /live/websocket` con las cabeceras `Upgrade`. La [página de proxy inverso de la wiki](https://github.com/plausible/community-edition/wiki/reverse-proxy) tiene los bloques completos, y mi [guía de Traefik](/es/traefik-proxy-docker/) cubre la parte de etiquetas de Docker.

<Notice type="warning" title="Copia de seguridad de dos bases de datos">
  Tienes un volumen Postgres y un volumen ClickHouse. Los sitios, objetivos y usuarios viven en Postgres; los eventos viven en ClickHouse. Copia ambos, o tu restauración dará un panel vacío.
</Notice>

Para actualizar, ejecuta `git pull origin <nueva-etiqueta>` (el repositorio tiene una rama por versión) y luego `docker compose up -d`. La wiki recomienda fijar la imagen a una etiqueta de parche completa y avisa de que los arreglos de seguridad no se portan a versiones anteriores. El comando de compose ejecuta `db migrate` en cada arranque. Lee las notas de la versión antes: una versión de largo plazo salta muchas versiones menores de golpe. La rutina genérica de descargar, recrear y volver atrás está en [actualizar contenedores de Docker Compose](/es/actualizar-contenedor-docker-compose/).

### Comprobar que el registro está cerrado

CE usa por defecto `DISABLE_REGISTRATION=invite_only`, según la [wiki de configuración](https://github.com/plausible/community-edition/wiki/configuration#disable_registration). Cuando existe la primera cuenta, `/register` redirige a la página de inicio de sesión con "Registration is disabled on this instance", que es lo que hizo una instancia de prueba v3.2.2. Solo pueden registrarse los usuarios invitados. Define `DISABLE_REGISTRATION=true` en `.env` para cerrar también las invitaciones, o `false` para abrir el registro a todos, y ejecuta `docker compose up -d`. Es el último paso del diagrama: abre `/register` en una ventana privada para confirmarlo.

## Incrustar el snippet y verificar los datos

En el panel de Cloud, o en tu instancia, añade tu dominio en **+ Add website**. Desde octubre de 2025 cada sitio tiene su propio script, `pa-` seguido del ID del sitio, así que copia el snippet real de **Settings**, **General**, junto a **Site installation** (el enlace dice **Review installation** en CE v3.2.2). Tiene esta forma; el host y el ID del sitio cambian en cada instalación:

```html
<!-- Privacy-friendly analytics by Plausible -->
<script async src="https://plausible.io/js/pa-XXXXXXXX.js"></script>
<script>
  window.plausible=window.plausible||function(){(plausible.q=plausible.q||[]).push(arguments)},plausible.init=plausible.init||function(i){plausible.o=i||{}};
  plausible.init()
</script>
```

La página de instalación tiene pestañas para **Script**, **WordPress** y **NPM**, un botón para copiar el snippet, los interruptores de **Optional measurements** (Outbound links, File downloads, Form submissions), un enlace a **Advanced options** y una guía de migración para el snippet antiguo de `data-domain`:

![Página Script installation de Plausible CE con las pestañas Script, WordPress y NPM, el snippet con un botón de copia, los interruptores de mediciones opcionales y el botón Verify Script installation](@assets/images/23/03/plausible-ce-install-snippet.webp)

*Página de instalación del script en CE v3.2.2: snippet, mediciones opcionales y el botón de verificación.*

En una instancia autoalojada la URL del script apunta a tu `BASE_URL`. Ponlo en el `<head>` de tu sitio; la etiqueta script lleva `async`, así que no bloquea el análisis de la página. En Astro, eso es el layout base o un componente pequeño; escribí una guía aparte sobre [Plausible en Astro con Cloudflare Workers](/es/astro-plausible-cloudflare-workers/) que proxifica el script en tu propio dominio. El `/js/script.js` heredado se sigue sirviendo en la v3.2.2, pero una instalación nueva debería usar el snippet que muestra el instalador.

Hasta que llega el primer evento, el panel del sitio muestra "Awaiting your first pageview":

![Panel del sitio en Plausible CE antes de recibir datos, con el mensaje Awaiting your first pageview](@assets/images/23/03/plausible-ce-awaiting-pageview.webp)

*El panel del sitio de una instancia CE recién instalada, antes del primer evento.*

Después comprueba tres cosas:

1. Abre tu sitio en una ventana privada. El panel debería dejar de mostrar "Awaiting your first pageview" y enseñar la visita entre los visitantes actuales en pocos segundos.
2. Mira la pestaña de red de las herramientas de desarrollo del navegador. Quieres un `202` en `POST /api/event` y ninguna cookie en la respuesta. Un `202` por sí solo prueba poco: cuando monté esto el 2026-11-23, el endpoint respondía `202 ok` para un sitio registrado y también para un dominio desconocido, porque el evento se descarta en silencio. Un evento descartado lleva la cabecera de respuesta `x-plausible-dropped: 1`. La prueba es el panel, no el código de estado.
3. Consulta la API, para saber que la clave y el `site_id` funcionan antes de que un script dependa de ellos.

Para el paso 3, crea una clave de la Stats API en la configuración de tu cuenta (las claves se limitan a un equipo) y ejecuta:

```bash
curl --request POST \
  --header 'Authorization: Bearer YOUR-KEY' \
  --header 'Content-Type: application/json' \
  --url 'https://plausible.io/api/v2/query' \
  --data '{
    "site_id": "example.com",
    "metrics": ["visitors", "pageviews"],
    "date_range": "day"
  }'
```

Una clave que funciona devuelve JSON con un array `results`. Sin clave, el endpoint responde `401` con `{"error":"Missing API key. Please use a valid Plausible API key as a Bearer Token."}`, que es lo que devolvió cuando monté esto el 2026-11-23. Un `401` con clave significa que la clave es incorrecta o pertenece a otro equipo; un error que menciona tu plan significa que la Stats API no está incluida en él; un conjunto de resultados vacío con un `200` significa que la clave está bien y que el sitio aún no recibió datos.

Dos consultas más de la [referencia de la Stats API](https://plausible.io/docs/stats-api). Páginas principales de los últimos siete días, una fila por página. Ten en cuenta que `7d` deja fuera el día actual; usa `day` cuando quieras ver los eventos de hoy:

```bash
curl --request POST \
  --header 'Authorization: Bearer YOUR-KEY' \
  --header 'Content-Type: application/json' \
  --url 'https://plausible.io/api/v2/query' \
  --data '{
    "site_id": "example.com",
    "metrics": ["visitors", "pageviews"],
    "date_range": "7d",
    "dimensions": ["event:page"],
    "order_by": [["visitors", "desc"]]
  }'
```

Visitantes de una sola página, con un filtro y el operador `is`:

```bash
curl --request POST \
  --header 'Authorization: Bearer YOUR-KEY' \
  --header 'Content-Type: application/json' \
  --url 'https://plausible.io/api/v2/query' \
  --data '{
    "site_id": "example.com",
    "metrics": ["visitors", "pageviews"],
    "date_range": "7d",
    "filters": [["is", "event:page", ["/pricing"]]]
  }'
```

Los filtros son arrays de `[operador, dimensión, valores]`, con `is`, `is_not`, `contains`, `contains_not`, `matches` y `matches_not` (sintaxis re2), combinados con `and`, `or` y `not`. Cada fila del resultado lleva una lista `dimensions` y una lista `metrics` en el orden que pediste.

Si el panel se queda a cero:

- **Bloqueadores de anuncios**: algunas listas de bloqueo bloquean `plausible.io`, mientras que Firefox y Safari no lo hacen por defecto. Proxifica el script en tu propio dominio para recuperar la mayor parte. Tu proxy debe reenviar la IP del visitante en `X-Forwarded-For`, o el filtro de bots descarta el evento y sigues recibiendo un `202`.
- **CSP**: añade el host de Plausible a `script-src` y `connect-src`, o el evento nunca sale del navegador.
- **`localhost`**: el tracker ignora las páginas vistas de localhost por defecto, así que prueba desde un nombre de host real, o un preview desplegado, no desde tu servidor de desarrollo. Para contar el tráfico de desarrollo, pasa `captureOnLocalhost: true` a `plausible.init`.
- **Snippet equivocado**: usa el snippet emitido para ese sitio. Con el snippet antiguo de `data-domain`, el atributo debe coincidir con el sitio que añadiste, o el evento se rechaza.
- **Caché**: una página en caché puede seguir sirviendo el HTML antiguo sin el snippet. Vacía la caché después de añadirlo.
- **Shields**: una regla activa para la IP, el país, la página o el hostname del visitante descarta la visita antes de guardarla.

## Configuración del sitio en CE v3.2.2

El menú de configuración del sitio que vi el 2026-11-23 dice: General, People, Visibility, Goals, Custom properties, Integrations, Imports & exports, Shields (IP addresses, Countries, Pages, Hostnames), Email reports, Danger zone. La página General tiene Domain, Reporting timezone y el enlace **Review installation** que abre la página del snippet. Tres de ellos merecen una nota:

- **Shields**: bloquea aquí la IP de tu oficina o de tu casa, una dirección cada vez, hasta 30 por sitio. Añade también la dirección IPv6, o tus visitas siguen contando.
- **Imports & exports**: aquí viven el importador de GA4, el de CSV y la exportación de todas las estadísticas. La importación de GA4 enlaza tu cuenta de Google, eliges una propiedad y la página te envía un correo cuando termina. En CE necesita SMTP y un cliente OAuth de Google, configurados como en la [wiki de integración con Google](https://github.com/plausible/community-edition/wiki/google-integration). Trata los datos importados como una referencia aproximada: los [documentos de importación](https://plausible.io/docs/google-analytics-import) dicen que los filtros simples por fuente, página o país funcionan y los filtros por propiedades personalizadas no.
- **Visibility**: las estadísticas son privadas hasta que activas el panel público o creas un enlace compartido. Un enlace compartido puede llevar contraseña (se fija al crearlo y no se edita) y puede quedarse fijado a un segmento.

## ¿Cloud, CE autoalojada o Umami?

Empieza con la prueba de Cloud si necesitas embudos u objetivos de ingresos, o si no quieres responsabilizarte de la disponibilidad. Autoaloja CE si ya gestionas un VPS con Docker y solo necesitas páginas vistas, fuentes, objetivos y propiedades.

Cambias las funciones premium y el filtrado avanzado de bots por una factura de servidor fija y datos que nunca salen de tu máquina. Autoalojar también hace tuya la disponibilidad, así que pon un monitor como [Uptime Kuma](/es/instalar-uptime-kuma/) sobre la URL del panel.

Si CE sin embudos te sabe a poco y sigues queriendo autoalojar, mira [Umami](/es/instalar-umami-analytics/). La [documentación de Umami](https://umami.is/docs) describe la v3, consultada el 2026-11-23:

| | Plausible Cloud | Plausible CE | Umami |
|---|---|---|---|
| Licencia | AGPL v3, alojado | AGPL v3 | MIT |
| Base de datos | Gestionada por ellos | Postgres y ClickHouse | PostgreSQL (v12.14 o posterior) |
| Embudos | Sí, plan Business | No | Sí, en la build autoalojada |
| API | Stats API v2, plan Business | Stats API v2, sin planes | API REST con clave de API, todas las operaciones |
| Script | `pa-<id>.js` desde plausible.io, unos 2.5 KB con gzip | El mismo script desde tu host | `script.js` desde tu instancia, proxy documentado |

Umami también lista recorridos, retención, cohortes y grabaciones de sesión en su documentación de la v3, y una base de datos en lugar de dos es menos que copiar.

Si usas Coolify y prefieres saltarte la terminal, [cómo instalar Plausible analytics](/es/instalar-plausible-analytics/) cubre la ruta de un clic.

## Preguntas frecuentes

<Accordion label="¿Usa Plausible Analytics cookies o localStorage?" group="faq">
  No. La [política de datos](https://plausible.io/data-policy) declara que Plausible no fija cookies, no escribe en el almacenamiento local y no guarda identificadores persistentes. Un visitante único es un hash diario con salt del dominio, la dirección IP y el User-Agent, y el salt rota cada 24 horas. En una instancia autoalojada tú eres el responsable del tratamiento, así que mantén el registro de acceso del proxy fuera de `/api/event`.
</Accordion>

<Accordion label="¿Cuánto pesa el script de seguimiento de Plausible?" group="faq">
  El `script.js` heredado midió 2841 bytes en crudo y unos 1.3 KB con gzip el 2026-11-23. El `pa-<id>.js` por sitio que reciben las instalaciones nuevas es mayor, unos 6 KB en crudo y 2.5 KB con gzip en plausible.io, y carga con `async`. Una instancia de prueba CE v3.2.2 lo sirvió sin comprimir, con 6190 bytes. La cifra de "menos de 1 KB" de los artículos antiguos ya no vale.
</Accordion>

<Accordion label="¿Autoalojar Plausible es gratis y qué le falta a CE?" group="faq">
  Sí, Community Edition es gratuita bajo AGPL v3 y solo cuesta tu servidor: 2 GB de RAM recomendados, Postgres más ClickHouse. No tiene embudos, recorridos de usuario, objetivos de ingresos de e-commerce, SSO, Sites API ni conector de Data Studio, y la documentación la llama versión de largo plazo que se publica unas dos veces al año. Tras la primera cuenta, el registro es solo por invitación por defecto; `DISABLE_REGISTRATION` en `.env` lo cambia.
</Accordion>

<Accordion label="¿Ralentiza Plausible mi sitio web?" group="faq">
  El snippet añade un script pequeño, unos 2.5 KB con gzip para el `pa-<id>.js` por sitio (el `script.js` heredado ocupa unos 1.3 KB), cargado con `async` desde el `<head>`. No hay banner de cookies que renderizar ni cadena de píxeles de terceros. Lo único que puede romper la página es una Content Security Policy estricta: añade el host de Plausible a `script-src` y `connect-src`.
</Accordion>

<Accordion label="¿Cómo cuento a los visitantes que usan bloqueadores de anuncios?" group="faq">
  Proxifica el script y el endpoint de eventos a través de tu propio dominio para que las peticiones parezcan de primer nivel. La [documentación del proxy](https://plausible.io/docs/proxy/introduction) lista guías para Cloudflare, Vercel, Netlify, Nginx, Apache, Caddy y Laravel, y el plugin de WordPress tiene un proxy de un clic. El proxy debe reenviar la IP del visitante en `X-Forwarded-For` (y `CF-Connecting-IP` en Cloudflare), o el evento se descarta en silencio con un `202`. Mi [guía de Astro con Cloudflare Workers](/es/astro-plausible-cloudflare-workers/) muestra un montaje.
</Accordion>

<Accordion label="¿La Stats API necesita un plan de pago?" group="faq">
  En Plausible Cloud la Stats API v2 es una función del plan Business; la prueba la incluye. En Community Edition no hay planes: el endpoint responde `401` con "Missing API key" hasta que crees una clave, y luego `POST /api/v2/query` devuelve JSON, como ocurrió en mi prueba con CE v3.2.2 el 2026-11-23. Las claves se limitan a un equipo. La documentación da como límite en Cloud 600 peticiones por hora, y el código de CE v3.2.2 fija 1.000.000.
</Accordion>

<Accordion label="¿Puedo importar mis datos de Google Analytics a Plausible?" group="faq">
  Sí, las estadísticas históricas de GA4 se importan desde la configuración del sitio, en Imports & exports. Enlazas tu cuenta de Google, eliges una propiedad y recibes un correo cuando termina la importación: unos minutos en la mayoría de los sitios, hasta un par de horas en los grandes. En CE antes debes configurar SMTP y un cliente OAuth de Google. También hay un importador de CSV para otras herramientas, y los datos importados admiten filtros simples por fuente, página o país, pero no filtros por propiedades personalizadas.
</Accordion>

<Accordion label="¿Cómo muevo un sitio a otro dominio?" group="faq">
  Abre la configuración del sitio, General, y pulsa Change junto al dominio. Escribe el dominio raíz sin `https://` ni `www` y confirma. Conservas las estadísticas históricas y no exportas ni importas nada. Durante 72 horas Plausible cuenta las estadísticas con el dominio antiguo y con el nuevo, y después rechaza el tráfico enviado con el antiguo. El snippet nuevo `pa-` no necesita cambios, pero el snippet heredado necesita actualizar su `data-domain`.
</Accordion>
