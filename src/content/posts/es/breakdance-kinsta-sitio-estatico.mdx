Un sitio WordPress estático con Breakdance te da la salida visual de un page builder sin la superficie de ataque de PHP. Conviertes WordPress a archivos de sitio estático con el plugin Simply Static, los subes a un repositorio Git y [Sevalla](https://sevalla.com/) (antes Kinsta) los sirve desde el edge de Cloudflare. La contrapartida es que pierdes las funciones dinámicas, lo que hace este enfoque ideal para sitios de presentación, portafolios y landing pages que no necesitan logins ni datos en vivo.

**Actualización (noviembre de 2026):** Kinsta movió su hosting de sitios estáticos a una plataforma aparte llamada [Sevalla](https://sevalla.com/) el 2 de febrero de 2026. Tus datos, ajustes y precios se mantienen, y puedes entrar con tus credenciales de MyKinsta. Desde entonces los docs se movieron a [docs.sevalla.com](https://docs.sevalla.com/), las builds de sitios estáticos migraron a Oracle Cloud Infrastructure (completado el 1 de septiembre de 2026), y Sevalla lanzó una CLI, un provider de Terraform, un servidor MCP y una GitHub Action oficial para despliegues.

Este flujo asume un sitio WordPress construido con [Breakdance](https://go.bitdoze.com/breakdance). Cualquier builder exporta, pero Breakdance ya quita mucha grasa por defecto, lo que mantiene pequeña la salida estática. Si aún estás decidiendo el builder, lee primero [nuestra reseña de Breakdance builder](/es/resena-breakdance-builder/). Abajo está el camino completo: optimizar, exportar, desplegar, apuntar tu dominio y verificar.

## ¿Por qué pasar a estático con un sitio WordPress de Breakdance?

<Button
  text="Prueba Breakdance"

Un sitio WordPress estándar necesita PHP, una base de datos y procesos de servidor web corriendo las 24 horas. Cada visita de página es una consulta a la base de datos. Cuando conviertes WordPress a salida de sitio estático, cada visita se convierte en la lectura de un archivo desde una ubicación edge del CDN. Para el hosting de sitios WordPress estáticos, los beneficios prácticos son:

<ListCheck>
<ul>
<li>Cargas de página mucho más rápidas, sin consultas a base de datos ni ejecución de PHP por petición</li>
<li>Sin vulnerabilidades de WordPress que parchear en el sitio público, porque no hay WordPress en el sitio público</li>
<li>El hosting de sitios estáticos de Sevalla es gratis para uso básico: 100 sitios, 600 minutos de build al mes y 100 GB de ancho de banda al mes por cuenta de empresa</li>
<li>Sin mantenimiento de servidor, sin ajuste de PHP-FPM, sin MySQL en una máquina pública</li>
<li>Las animaciones de Breakdance y las secciones movidas por JavaScript sobreviven intactas a la exportación</li>
</ul>
</ListCheck>

Esto funciona mejor para sitios que no cambian en cada petición: páginas de empresa, portafolios, documentación, landing pages de campaña. No funciona para sitios que necesitan logins, áreas de membresía, datos en vivo o un carrito de WooCommerce. Si tu sitio cae en el segundo grupo, querrás que WordPress siga siendo dinámico.

El ángulo del coste es lo que suele venderlo. La autoría sigue en WordPress (en local o en un VPS pequeño), y el sitio público cuesta 0 $ en el nivel gratuito de Sevalla. Si quieres las cifras completas de ejecutar WordPress frente a ir a estático, mira el [desglose de costes y operaciones de Astro vs WordPress](/es/astro-vs-wordpress/).

## Pasos

El flujo en una línea: WordPress + Breakdance (autoría), luego exportación con Simply Static (HTML/CSS/JS), luego push a Git, luego Sevalla (build OFF, publicar tal cual), luego edge de Cloudflare.

![Pipeline de publicación estática: WordPress con Breakdance como sitio de autoría, Simply Static exportando HTML CSS y JS, un push de Git a GitHub GitLab o Bitbucket, Sevalla publicando los archivos tal cual con el paso de build apagado, y Cloudflare sirviendo el resultado desde más de 260 ubicaciones](@assets/images/wordpress/breakdance-static-pipeline.svg)

### 1. Optimiza WordPress para una exportación estática

Breakdance ya quita mucha sobrecarga de WordPress por defecto. Ve a **Breakdance → Settings → Performance** y desactiva el editor Gutenberg, los oEmbeds y cualquier función que no uses. Cada asset que desactivas aquí es un archivo menos en la exportación estática.

<Notice type="info" title="Haz copia primero">
Haz una copia del sitio de autoría antes de cambiar ajustes o ejecutar una exportación. Un cambio de ajustes que rompe una plantilla es fácil de revertir desde una copia, doloroso de revertir de memoria. Mira la comparativa de <a href="/es/mejores-plugins-gratuitos-backup-wordpress/">plugins gratuitos de copias para WordPress</a> si aún no tienes una rutina de copias.
</Notice>

Ya que estás aquí, mantén ligera la biblioteca de medios. Comprime las imágenes hero sobredimensionadas y borra las subidas sin usar. Esto importa después: Sevalla limita el directorio de publicación de cada despliegue a 1 GB (cubierto en la sección de límites).

### 2. Configura Simply Static

Instala [Simply Static](https://wordpress.org/plugins/simply-static/) desde el directorio de plugins de WordPress. En **Simply Static → Settings**, define:

- **Output**: Local directory (o descarga ZIP, si prefieres mover los archivos a mano)
- **Destination URL**: tu subdominio `your-site-name.sevalla.page`, o el dominio personalizado que añadirás después
- **Exclusions**: URL de admin, `wp-admin`, `wp-login.php`, endpoints de comentarios, endpoints de carrito/checkout si existen

La URL de destino importa porque Simply Static reescribe los enlaces internos para que coincidan con ella. Si la pones mal, cada enlace interno del sitio exportado apuntará al host equivocado.

<Notice type="info" title="Mejora de automatización">
El plugin gratuito se queda en producir archivos. <a href="https://simplystatic.com/simply-static-pro/">Simply Static Pro</a> (de pago) empuja la exportación directamente a GitHub, AWS S3, BunnyCDN, SFTP o cualquier flujo de despliegue basado en Git. Empuja al mismo repositorio que Sevalla vigila y la propia exportación dispara el auto-despliegue. El camino gratuito de abajo funciona bien para un sitio que actualizas de vez en cuando.
</Notice>

### 3. Genera los archivos estáticos

Haz clic en **Generate** en Simply Static. Los sitios pequeños terminan en segundos. Un sitio medio (50 a 100 páginas) suele terminar en menos de un minuto, pero el tiempo depende del número de páginas y del volumen de medios.

**Verifica:** abre la carpeta de exportación y confirma que `index.html` está en la raíz (o en la subcarpeta que configuraste). Abre un par de imágenes en un visor y confirma que son archivos reales, no unos pocos bytes de texto placeholder. Archivos de texto diminutos donde deberían estar las imágenes suele significar que hubo punteros de Git LFS de por medio en la copia, lo que romperá el despliegue después.

La salida es HTML, CSS y JavaScript planos. No hay PHP en ninguna parte. Ese es el punto.

### 4. Despliega en el hosting de sitios estáticos de Sevalla

Sube la exportación al repositorio que Sevalla vigilará. Si la carpeta de exportación es un repo Git propio:

```bash
# desde tu carpeta local static-export
git add .
git commit -m "publish static export"
git push -u origin main
```

<Notice type="warning" title="Evita git push --force">
El force-push solo es seguro cuando el repo no contiene más que la última exportación y reemplazas todo el historial a propósito. En cualquier repo compartido o longevo destruye el historial y rompe las previsualizaciones de pull requests. Un push normal basta para actualizaciones de contenido.
</Notice>

En Sevalla, crea un sitio estático y conecta el repositorio. Cada push a la rama configurada dispara un despliegue, y también puedes disparar uno a mano con **Deploy now**.

<Notice type="warning" title="Acierta la estrategia de build">
Tu exportación ya es HTML construido. El paso de build por defecto de Sevalla intentaría ejecutar <code>npm run build</code> y fallaría. Ve a <strong>Settings → Update build strategy</strong> y pon <strong>Build site before publishing: OFF</strong>. Luego define <strong>Index file</strong> como <code>index.html</code>, <strong>Error file</strong> como <code>404.html</code> si tienes uno, y deja <strong>Publish directory</strong> vacío para publicar la raíz del repo (o apúntalo a tu subcarpeta de exportación). Este interruptor es el único ajuste que hace que una exportación pre-generada de Simply Static se despliegue limpiamente.
</Notice>

Los despliegues son atómicos. Los archivos se suben primero al almacenamiento de objetos, luego todos los dominios cambian al nuevo despliegue en un paso y la caché del edge se purga automáticamente. Los visitantes nunca ven un sitio a medio subir.

**Verifica:** abre el registro de despliegue y busca `Static site has been deployed successfully`. Si usas un archivo `_redirects`, busca también `Redirects processed successfully!` (más sobre ambos en la sección de redirecciones).

### 5. Añade tu dominio personalizado

Puedes saltarte esta sección por completo y seguir usando el subdominio gratuito `your-site-name.sevalla.page`. Cuando quieras tu propio dominio, el flujo son tres pasos en la hoja de **DNS records** del sitio: **Add domain → Verify domain → Point domain**. Los estados pasan de Verification a Pointing a Active.

![Flujo de dominio personalizado: añade el dominio en Sevalla, verifica con dos registros TXT en _cf-custom-hostname y _acme-challenge, apunta con un registro A o un CNAME para Cloudflare DNS, y luego el dominio pasa a activo con SSL gratis](@assets/images/wordpress/breakdance-static-domain-flow.svg)

**Verificar** significa añadir dos registros TXT en tu proveedor de DNS:

1. Registro de propiedad de `your-domain.com` en `_cf-custom-hostname.your-domain.com`
2. Registro de validación SSL en `_acme-challenge.your-domain.com`

Mantén el registro `_acme-challenge` en su sitio de forma permanente. Las renovaciones de certificado lo necesitan. El registro de propiedad puede eliminarse una vez que el dominio muestra Active.

<Notice type="warning" title="Registro A, no CNAME">
Para cualquier proveedor de DNS que no sea Cloudflare, apunta el dominio con un <strong>registro A</strong> a la dirección IP que muestra el dashboard de Sevalla. Un CNAME solo funciona cuando tu DNS está alojado en Cloudflare. Equivocarse aquí es la razón más común por la que un dominio nunca pasa a Active.
</Notice>

<Tabs>
<Tab name="Cloudflare DNS">
Añade un registro CNAME para `your-domain.com` apuntando al destino que muestra Sevalla, típicamente `to.sevalla.app`. Cloudflare es el único proveedor donde un CNAME en el dominio apex está permitido.
</Tab>
<Tab name="Cualquier otro proveedor de DNS">
Añade un registro A para `your-domain.com` apuntando a la dirección IP que muestra la hoja de DNS records de Sevalla. Borra primero cualquier registro A, AAAA o CNAME en conflicto en el mismo hostname, o tendrás un bucle de redirecciones o una verificación atascada.
</Tab>
</Tabs>

Sevalla vuelve a comprobar el DNS cada 30 minutos (cada 10 segundos mientras la hoja de DNS records está abierta) durante un máximo de 7 días. Si la verificación se estanca durante 7 días, el dominio pasa a **Timed out**, que es final: tienes que borrarlo y añadirlo de nuevo.

Algunos casos límite que conviene conocer de antemano:

- Los dominios `.ru` no están soportados
- Un dominio ya vinculado a cualquier otro servicio de Sevalla (en cualquier empresa) no puede añadirse de nuevo
- Los registros A, AAAA o CNAME en conflicto deben borrarse en tu proveedor de DNS antes de que el apuntado funcione
- `http://` se redirige con 301 a `https://` automáticamente una vez que el dominio está Active
- Los certificados SSL los emite y renueva Sevalla gratis, así que no hay nada que gestionar

**Verifica:** ejecuta `curl -I https://your-domain.com` y espera `HTTP/2 200` con `server: cloudflare`. Luego ejecuta `curl -I http://your-domain.com` y espera una redirección `301` a la URL HTTPS.

### 6. Resuelve los formularios

El constructor de formularios integrado de Breakdance depende de PHP para procesar los envíos. En un sitio estático no hay PHP, así que esos formularios fallan en silencio. Usa un servicio de formularios externo y pega su código de inserción en un elemento HTML/embed de Breakdance.

<Notice type="warning" title="Netlify Forms no funcionará aquí">
Netlify Forms solo funciona cuando el sitio está alojado en Netlify. En Sevalla no hace nada en absoluto: los envíos desaparecen sin error. Usa un servicio de formularios que funcione en cualquier hosting estático.
</Notice>

<Tabs>
<Tab name="Formspree (rápido, sin builder)">
[Formspree](https://formspree.io/) Free cuesta 0 $ con 50 envíos al mes, formularios ilimitados, sin subida de archivos y un archivo de envíos de 30 días. Apunta el atributo `action` de tu formulario a tu endpoint de Formspree y listo. Si te quedas corto, Personal cuesta 15 $/mes por 200 envíos.
</Tab>
<Tab name="AIDAForm (builder de arrastrar y soltar)">
[AIDAForm](https://aidaform.com/) tiene un nivel gratuito y un constructor visual de formularios. Genera el código de inserción que sueltas directamente en Breakdance. Comprueba sus límites actuales de envíos en el nivel gratuito antes de comprometerte, los límites se mueven.
</Tab>
</Tabs>

Ambas opciones son agnósticas de plataforma, así que siguen funcionando si alguna vez mueves el sitio estático fuera de Sevalla. Para más opciones, incluidas las autoalojadas, mira cómo [añadir un formulario de contacto a cualquier sitio web estático](/es/anadir-formulario-contacto-sitios-estaticos/).

## Los límites de sitios estáticos de Sevalla que importan

El nivel gratuito es genuinamente usable, pero los límites de abajo son los que causan despliegues fallidos o facturas sorpresa. Todas las cifras son de los docs de Sevalla a noviembre de 2026.

| Límite | Valor | Qué se rompe sin él |
|---|---|---|
| Tamaño del directorio de publicación | 1 GB por despliegue | El despliegue falla directamente |
| Tiempo de build | 30 minutos por despliegue | La build se detiene y el despliegue falla |
| Builds concurrentes por sitio | 1 | Las builds encoladas esperan, no corren en paralelo |
| Contenedor de build | 4 CPU / 8 GB RAM, Ubuntu 24.04 | Los pasos de build pesados pueden agotar la memoria |
| Sitios estáticos por empresa | 100 | La creación de sitios se bloquea más allá |
| Minutos de build | 600 al mes, por empresa | Exceso a 0,05 $ por minuto de build |
| Ancho de banda | 100 GB al mes, por empresa | Exceso a 0,10 $ por GB |

<Notice type="warning" title="Límite de 1 GB de publicación">
Una exportación de Breakdance cargada de medios puede superar 1 GB sin que nadie se dé cuenta. Comprime y redimensiona las imágenes antes de exportar, borra las subidas sin usar de la biblioteca de medios, y si aun así superas el límite, sirve los medios pesados desde almacenamiento de objetos. El almacenamiento de objetos compatible con S3 de Sevalla corre sobre Cloudflare R2 a 0,02 $/GB al mes sin tasas de entrada ni salida: mantén el HTML en el hosting estático y apunta las etiquetas `<img>` a URL de R2.
</Notice>

Dos hechos que juegan a tu favor:

- Los 600 minutos de build y los 100 GB de ancho de banda son **por empresa al mes, compartidos entre todos los sitios estáticos**, incluidos los despliegues de previsualización de pull requests. Un sitio pesado puede comerse la cuota de todos. Pon una alerta de uso (ver la lista de abajo).
- Con **Build site before publishing** en OFF, cada despliegue es una subida, no una build. El tiempo de build por actualización es cercano a cero, así que los 600 minutos llegan muy lejos en este flujo.

## Redirecciones, 404 y cabeceras

Una migración de WordPress a estático suele cambiar algunas URL. Sevalla lee un archivo `_redirects` (formato Netlify) y un archivo `_headers` del directorio de publicación en cada despliegue, más un ajuste de **Pretty URLs** para URL con barra final y sin extensión. Así conservas el valor SEO de los enlaces antiguos.

```text
# _redirects (colócalo en el directorio de publicación, junto a index.html)
/old-about   /about      301
/pricing-old /pricing    301

# devuelve un estado 404 real para las páginas que faltan
/*           /404.html   404
```

Para construir el mapa de URL antiguas a nuevas, [exporta todas las URL y títulos de tus entradas de WordPress](/es/exportar-urls-titulos-wordpress/) antes de desmontar nada.

Dos trampas, ambas de los docs de Sevalla:

1. Si alguna línea de `_redirects` no se puede parsear, el despliegue **sigue teniendo éxito pero con cero reglas de redirección aplicadas**. Revisa siempre el registro de despliegue buscando `Redirects processed successfully!` antes de dar por hecho que las redirecciones están en vivo.
2. El archivo de error (`404.html`) se sirve con **estado HTTP 200** por defecto. Los buscadores tratan los soft-404 como páginas reales, lo que arruina una migración en silencio. La regla `/* /404.html 404` de arriba es lo que hace que las páginas que faltan devuelvan un 404 real.

<Notice type="warning" title="Los 404 se sirven como 200 por defecto">
Añade la regla <code>/* /404.html 404</code> a <code>_redirects</code> desde el primer día. Comprobarlo después, cuando un soft-404 ya ha sido indexado, es la forma cara de aprender esto.
</Notice>

Los despliegues son atómicos y la caché del edge se purga automáticamente en cada despliegue, así que las nuevas redirecciones y cabeceras entran en vigor sin limpieza manual de caché.

**Verifica:** ejecuta `curl -s -o /dev/null -w "%{http_code}" https://your-domain.com/nonexistent` y espera `404` (solo después de que la regla de `_redirects` esté desplegada). Ejecuta `curl -s -o /dev/null -w "%{http_code}" https://your-domain.com/old-about` y espera `301`. Revisa el registro de despliegue buscando `Redirects processed successfully!`.

## Solución de problemas habituales

<Accordion label="El despliegue falla: directorio de publicación de más de 1 GB" group="troubleshooting" expanded="true">
El error de build nombra el tamaño. Comprime y redimensiona las imágenes antes de exportar, borra las entradas sin usar de la biblioteca de medios y mueve los medios pesados (vídeo, galerías grandes) al almacenamiento de objetos de Sevalla en Cloudflare R2. El HTML puede quedarse en el hosting estático mientras las etiquetas `<img>` y `<video>` apuntan a URL de R2.
</Accordion>

<Accordion label="La build falla o agota el tiempo" group="troubleshooting">
Con **Build site before publishing** en ON, Sevalla ejecuta `npm run build` y falla en un repo de HTML plano. Apaga el interruptor. Dos límites relacionados: las builds se detienen a los 30 minutos, y Sevalla ignora `engines`, `.nvmrc` y `netlify.toml`, así que una suposición equivocada de versión de Node en el repo no hace nada. Solo corre una build a la vez por sitio.
</Accordion>

<Accordion label="No hay despliegue tras un push" group="troubleshooting">
Comprueba que la rama que Sevalla vigila coincide con la rama a la que subiste. Revisa también: límite de despliegues pendientes alcanzado, permisos o visibilidad del repositorio cambiados, y si la cuenta de Sevalla tiene una suspensión operativa (eso bloquea todas las operaciones).
</Accordion>

<Accordion label="Contenido antiguo tras un despliegue" group="troubleshooting">
Haz un refresco duro o prueba primero en una ventana de incógnito. Si el contenido sigue siendo antiguo, confirma que el despliegue nuevo es el marcado como Active. El cambio atómico debería haber purgado la caché del edge; si no lo hizo, usa **Deploy now** para forzar un despliegue nuevo.
</Accordion>

<Accordion label="Las páginas que faltan devuelven estado 200" group="troubleshooting">
El archivo de error se sirve como HTTP 200 por defecto, lo que es un soft-404. Añade `/* /404.html 404` a `_redirects` y redespliega. Este importa para el SEO. Mira la sección de redirecciones de arriba.
</Accordion>

<Accordion label="Demasiadas redirecciones en el dominio personalizado" group="troubleshooting">
Casi siempre un conflicto de DNS: registros A, AAAA o CNAME obsoletos en el mismo hostname, o el dominio sigue vinculado a otro servicio de Sevalla en alguna empresa. Borra los registros en conflicto y asegúrate de que solo queda el registro que Sevalla espera (registro A, o CNAME en Cloudflare DNS).
</Accordion>

<Accordion label="Las imágenes y archivos grandes aparecen como archivos de texto diminutos" group="troubleshooting">
Son archivos puntero de Git LFS que nunca se resolvieron. Activa el soporte de Git LFS en Sevalla, o no uses LFS para el repositorio de exportación. Re-exporta y re-sube si los punteros ya aterrizaron en el despliegue.
</Accordion>

<Accordion label="Dominio atascado en Verification o Timed out" group="troubleshooting">
Registros TXT que faltan o propagación lenta. Sevalla comprueba cada 30 minutos durante un máximo de 7 días. Confirma ambos registros TXT en tu proveedor de DNS. Un dominio que llega a **Timed out** no puede revivirse: bórralo y añádelo de nuevo. La <a href="https://docs.sevalla.com/static-sites/go-live-checklist">lista de verificación de salida en vivo</a> de Sevalla cubre las comprobaciones restantes previas al lanzamiento.
</Accordion>

## Resultado

Lo que obtienes es un sitio que se ve idéntico al original de Breakdance, animaciones movidas por JavaScript incluidas, servido desde el edge de Cloudflare sin PHP, sin base de datos y sin WordPress en la parte pública. Las cargas de página son lecturas de archivos desde un CDN. No queda nada que parchear.

Para un sitio pequeño de presentación esto es casi gratis. El nivel gratuito cubre 100 sitios estáticos, 600 minutos de build y 100 GB de ancho de banda por empresa al mes, y con el paso de build apagado, la mayoría de despliegues apenas usan minutos de build. Pasadas las cuotas son 0,10 $/GB de ancho de banda y 0,05 $ por minuto de build. Una alerta de uso evita sorpresas.

Dónde vive el WordPress de autoría es decisión tuya. Puedes [instalar WordPress con Docker Compose](/es/instalar-wordpress-docker/) en local, mantenerlo en una máquina de staging o correrlo en un VPS pequeño de [Hetzner](https://go.bitdoze.com/hetzner) si quieres tenerlo accesible desde cualquier parte. Si vas por la ruta del VPS, los [benchmarks de VPS ARM vs x86](/es/comparativa-arm-vs-x86-vps/) muestran lo que obtienes por tu dinero, y los [benchmarks de servidores cloud](/es/benchmark-servidores-cloud/) cubren cómo probar la máquina tú mismo.

Si has llegado hasta aquí y decidiste que al final sí necesitas formularios, logins o datos en vivo, mantén WordPress dinámico y ponle una caché delante. [Acelerar WordPress con caché Varnish](/es/varnish-cache-cloudpanel/) te da la mayor parte del rendimiento de sitio estático sin renunciar a las funciones dinámicas.

Para escalar más allá de las exportaciones manuales, Sevalla tiene ahora herramientas de despliegue de verdad: una GitHub Action oficial (`sevalla/sevalla-deploy`), una CLI, un provider de Terraform y un servidor MCP al que puedes apuntar un agente de código. Mete la exportación en CI y todo se convierte en push-para-publicar.
