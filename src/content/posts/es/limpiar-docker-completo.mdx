Una limpieza segura de Docker ejecuta primero `docker system df`, luego elimina contenedores, imágenes, volúmenes, redes y caché de construcción de un tipo cada vez y después vuelve a ejecutar `docker system df`. En el daemon desechable que produjo cada salida de abajo, ese orden dejó en cero las cuatro filas de `docker system df`. Los volúmenes con nombre necesitan `docker volume prune -a` por separado, porque `docker system prune -a --volumes` los deja en paz.

Mi primera limpieza de Docker llegó después de una actualización fallida, y la ejecuté en el orden equivocado. El stack ejecutaba [Plausible](/es/instalar-plausible-analytics/) para varios sitios web, sobre Docker y docker-compose. Apareció una actualización, y la nueva imagen pedía PostgreSQL 14 mientras la base de datos seguía en la 12. Cambié la configuración de la imagen y la actualización falló, así que revertí la base de datos a su estado anterior con la imagen antigua y reinicié. Los sitios ya no aparecían en las analíticas. [Volver a descargar las últimas imágenes](/es/actualizar-contenedor-docker-compose/) terminó en dos mensajes:

```text
ERROR: for plausible_plausible_events_db_1  Cannot create container for service plausible_events_db: open /var/lib/docker/volumes/plausible_event-data/_data: no such file or directory
```

```text
WARNING: Service "plausible_events_db" is using volume "/var/lib/clickhouse" from the previous container. Host mapping "plausible_event-data2" has no effect. Remove the existing containers (with `docker-compose rm plausible`)
```

Los dos nombres de volumen que aparecen en ellos se diferencian por un `2`, `plausible_event-data` y `plausible_event-data2`. Los mensajes salieron de docker-compose v1, el binario de Python que se escribe con guion y que Docker [ya no mantiene](https://docs.docker.com/retired/). Compose v2 no imprime nada ante el mismo tipo de error. Renombré un volumen en el archivo Compose de un stack de pruebas mientras el contenedor antiguo todavía existía y ejecuté `docker compose up -d`:

```text
 Container rf-dock-site-worker-1 Running
 Volume rf-dock-site_html2 Creating
 Volume rf-dock-site_html2 Created
 Container rf-dock-site-web-1 Recreate
 Container rf-dock-site-web-1 Recreated
 Container rf-dock-site-web-1 Starting
 Container rf-dock-site-web-1 Started
```

Ningún error, ninguna advertencia. El contenedor ahora monta un volumen nuevo con los archivos por defecto de la imagen dentro, y el volumen antiguo todavía guarda los datos:

```bash
docker run --rm -v rf-dock-site_html:/old:ro alpine cat /old/index.html
```

```text
v1
```

Ahí no se perdió nada, pero desde entonces el volumen antiguo quedó sin usar, a un `docker volume prune -a` de desaparecer. En el host de Plausible empecé solo con las imágenes, y los volúmenes causaron el siguiente problema. Así que opté por la medida drástica: borrar todo lo que el stack había dejado atrás, volúmenes incluidos, e instalar de nuevo desde cero. Ejecuté el orden completo en ese daemon, Engine 29.10.1 con el almacén de imágenes de containerd y Compose v5.8.0. Parte de dos stacks en ejecución, un contenedor detenido, cinco imágenes, cinco volúmenes, seis redes y 11 registros de caché de construcción.

<Notice type="warning" title="Los volúmenes guardan los datos que no puedes reconstruir">
`docker volume prune -a` y `docker compose down -v` borran para siempre los volúmenes con nombre, así que el paso de copia de seguridad de abajo va antes de la primera eliminación. Las imágenes, las redes y la caché de construcción vuelven con un pull o con una build, y `docker compose up` recrea un contenedor a partir de su imagen.
</Notice>


## ¿Por qué fallan los comandos de una línea clásicos?

Porque cada uno da por terminado el paso anterior. `docker rm` rechaza los contenedores en ejecución, y `docker rmi` rechaza las imágenes que usa un contenedor y las imágenes con dos etiquetas.

`docker stop $(docker ps -a -q)` detiene todos los contenedores del host por ID. Funciona. `-a` incluye los contenedores que ya están detenidos, así que imprime su ID y sigue. `stop` envía SIGTERM y después SIGKILL a los 10 segundos. Un proceso que ignora SIGTERM, como los de `sleep 3600` de aquí, retiene el comando durante todo el tiempo de espera y termina con el código de salida 137.

```text
$ docker stop $(docker ps -a -q)
82736c14412c
e94c72b1efcb
54de3a31ae66
b6f91c1db70e
```

`docker rm $(docker ps -a -q)` es donde se rompe la secuencia. Elimina los contenedores detenidos, rechaza los que están en ejecución y sale con el código 1:

```text
$ docker rm $(docker ps -a -q)
5650d42dc193
Error response from daemon: cannot remove container "f2628490d96d": container is running: stop the container before removing or force remove
Error response from daemon: cannot remove container "5d6a0e61fd99": container is running: stop the container before removing or force remove
Error response from daemon: cannot remove container "12bbc2ef3126": container is running: stop the container before removing or force remove
```

`docker rmi $(docker images -q)` falla por tres razones. El daemon rechaza una imagen que usa un contenedor en ejecución. `docker images -q` imprime una imagen una vez por etiqueta, así que una imagen con dos etiquetas está dos veces en la lista. Y la lista no incluye ninguna imagen colgante (dangling), las que no tienen etiqueta.

```text
$ docker rmi $(docker images -q)
Untagged: rf-dock-old:1
Deleted: sha256:f4e75d90f8cc50fd548a9652d91b099f1bb1ea5103b56cd2c8c148de1e10456b
Untagged: rf-dock-demo:1
Deleted: sha256:04bd2aca67ecb4463c1dfc74ba6a1e84a8445987fcd120617af07cae8315ab16
Error response from daemon: conflict: unable to delete c3ac91f4f4e5 (cannot be forced) - image is being used by running container bf32925199f4
Error response from daemon: conflict: unable to delete acbc1de7a6a5 (cannot be forced) - image is being used by running container 8c803e029aae
Error response from daemon: conflict: unable to delete acbc1de7a6a5 (cannot be forced) - image is being used by running container 8c803e029aae
```

La imagen alpine está dos veces en la lista, una por etiqueta, y el daemon la rechaza las dos veces. Sin los contenedores, las dos etiquetas siguen bloqueándola:

```text
Error response from daemon: conflict: unable to delete acbc1de7a6a5 (must be forced) - image is referenced in multiple repositories
```

Las formas que funcionan están en la siguiente sección: `docker compose down` para un stack y luego un prune por tipo. En un host donde todo se va de una vez, el comando de una línea es `docker rm -f $(docker ps -aq)`. `-f` envía SIGKILL, y el selector coincide con todos los contenedores del daemon, incluidos los que creó un panel como [Dokploy](/es/actualizar-docker-compose-dokploy/). Ejecútalo una segunda vez en el host vacío y se detiene con:

```text
docker: 'docker rm' requires at least 1 argument
```

El resto de la familia está en la [referencia de comandos de Docker](/es/comandos-docker/).

## ¿Cómo limpio Docker en un orden seguro?

Detén y elimina primero los contenedores, y después haz prune de imágenes, volúmenes, redes y caché de construcción, un comando por tipo. Los contenedores referencian imágenes y retienen volúmenes, así que nada más puede ir primero.

### Contenedores, un stack cada vez

```bash
cd /work/rf-dock-site
docker compose down
```

```text
 Container rf-dock-site-web-1 Stopping
 Container rf-dock-site-worker-1 Stopping
 Container rf-dock-site-web-1 Stopped
 Container rf-dock-site-web-1 Removing
 Container rf-dock-site-web-1 Removed
 Container rf-dock-site-worker-1 Stopped
 Container rf-dock-site-worker-1 Removing
 Container rf-dock-site-worker-1 Removed
 Network rf-dock-site_front Removing
 Network rf-dock-site_front Removed
```

`down` detiene los contenedores, los elimina y elimina la red del stack. No aparece ninguna línea de volumen. Los volúmenes con nombre y los anónimos se quedan. El mismo comando en la carpeta del otro stack se encarga de ese, y `docker ps -a` muestra lo que queda:

```text
CONTAINER ID   IMAGE           COMMAND             CREATED          STATUS                      PORTS     NAMES
68a708564d3f   alpine:latest   "sh -c 'sleep 2'"   28 seconds ago   Exited (0) 26 seconds ago             rf-dock-stopped
```

El contenedor arrancado a mano está detenido, así que `docker container prune` se lo lleva:

```bash
docker container prune -f
```

```text
Deleted Containers:
68a708564d3f93db7e34e30d7cadb58589e97819e98614fa060bb0c7949cf4f8

Total reclaimed space: 8.192kB
```

La comprobación es `docker ps -a`. Solo la cabecera significa que el daemon no guarda ningún contenedor.

```text
CONTAINER ID   IMAGE     COMMAND   CREATED   STATUS    PORTS     NAMES
```

Aquí eliminar gana a detener. Un contenedor detenido con la [política de reinicio `always`](https://docs.docker.com/engine/containers/start-containers-automatically/#use-a-restart-policy) arranca de nuevo la próxima vez que se reinicia el daemon, y entonces vuelve a retener su imagen. Una base de datos que necesita más de 10 segundos en apagarse se lleva `docker compose down -t 60`.

Y después de que [herramientas de autoactualización como Tugtainer](/es/tugtainer-autoactualizacion-docker/) pongan una imagen nueva en un contenedor, la imagen antigua sigue en el disco hasta que se ejecuta este comando.

### Volúmenes al final: `docker volume prune` en dos pasos

Haz una copia de seguridad de un volumen antes de la primera eliminación, con un contenedor desechable que lo monta en modo de solo lectura:

```bash
cd /work/rf-dock-site
mkdir -p bak
docker run --rm -v rf-dock-site_html:/data:ro -v "$PWD/bak:/backup" alpine tar czf /backup/html-vol.tgz -C /data .
tar tzf bak/html-vol.tgz
```

```text
./
./index.html
./50x.html
```

Copia también en `bak` el archivo Compose y el `.env` que tiene al lado, y lee la [guía de secretos de Docker Compose](/es/secretos-docker-compose/) antes de reinstalar. Para copias de `/var/lib/docker/volumes` fuera de la máquina está [Pluton](/es/pluton-backup-autoalojado/).

Después de eliminar los contenedores, la parte de volúmenes de `docker system df -v` muestra `LINKS 0` en todas las líneas, la marca de un volumen sin uso:

```text
VOLUME NAME                                                        LINKS     SIZE
rf-dock-db_data                                                    0         0B
46aaf8854ddf74764a6b07e56a32e79f298bb3e10a113bea1811bdfb38213c29   0         0B
rf-dock-old_data                                                   0         5B
rf-dock-site_html                                                  0         500B
ed079a0333ce882fb1a04a900edc6c1067c15c54669a214d31201837c417c325   0         0B
```

`docker volume prune` elimina dos de ellos, los que tienen nombres de 64 caracteres:

```bash
docker volume prune -f
```

```text
Deleted Volumes:
46aaf8854ddf74764a6b07e56a32e79f298bb3e10a113bea1811bdfb38213c29
ed079a0333ce882fb1a04a900edc6c1067c15c54669a214d31201837c417c325

Total reclaimed space: 0B
```

Esos son volúmenes anónimos, creados por una línea `VOLUME` en una imagen o por un montaje sin nombre. Desde [Engine 23.0](https://docs.docker.com/engine/release-notes/23.0/) el prune por defecto se detiene ahí. Los volúmenes creados antes de esa versión no llevan la etiqueta de anónimo, así que cuentan como volúmenes con nombre. Los tres con nombre necesitan `-a`:

```bash
docker volume ls
docker volume prune -a -f
```

```text
DRIVER    VOLUME NAME
local     rf-dock-db_data
local     rf-dock-old_data
local     rf-dock-site_html
```

```text
Deleted Volumes:
rf-dock-db_data
rf-dock-old_data
rf-dock-site_html

Total reclaimed space: 505B
```

Este es el comando que borra una base de datos. Para cualquier cosa que no sea un reinicio completo, la forma que usaría yo es `docker volume rm` con un nombre cada vez. Para deshacerlo, crea el volumen de nuevo y descomprime el tar dentro:

```bash
docker volume create rf-dock-site_html
docker run --rm -v rf-dock-site_html:/data -v "$PWD/bak:/backup:ro" alpine tar xzf /backup/html-vol.tgz -C /data
docker run --rm -v rf-dock-site_html:/data:ro alpine cat /data/index.html
```

```text
rf-dock-site_html
v1
```

La restauración de arriba cubre archivos estáticos. Un volumen de base de datos necesita un dump hecho con `pg_dump` antes del prune, y esta ejecución no probó ese camino.

```bash

```


## ¿Qué elimina `docker system prune`?

Contenedores detenidos, redes que ningún contenedor usa, imágenes colgantes y la caché de construcción. `-a` añade todas las imágenes sin contenedor, `--volumes` añade los volúmenes anónimos sin uso, y los volúmenes con nombre se quedan.

`docker system prune` ejecuta de una vez la mayoría de los pasos de arriba, y su advertencia enumera lo que va a eliminar:

```bash
docker system prune
```

```text
WARNING! This will remove:
  - all stopped containers
  - all networks not used by at least one container
  - all dangling images
  - unused build cache

Are you sure you want to continue? [y/N] y
...
Total reclaimed space: 82.23kB
```

Eso fue el contenedor detenido, la red sin uso, la imagen colgante y 8 de los 11 registros de caché. Las imágenes con etiqueta y los cinco volúmenes se quedaron.

Con `-a --volumes` la advertencia gana la línea de los volúmenes anónimos y amplía la línea de las imágenes:

```bash
docker system prune -a --volumes
```

```text
WARNING! This will remove:
  - all stopped containers
  - all networks not used by at least one container
  - all anonymous volumes not used by at least one container
  - all images without at least one container associated to them
  - all build cache

Are you sure you want to continue? [y/N] y
...
Total reclaimed space: 8.846MB
```

Lee la tercera línea: volúmenes anónimos. Después de la ejecución, `docker volume ls` sigue listando cuatro volúmenes:

```text
DRIVER    VOLUME NAME
local     a02a833d832151355e1e17d0cfb5e0d06c4b21dd6f9f89bb7db3a2797bcc4a36
local     rf-dock-db_data
local     rf-dock-old_data
local     rf-dock-site_html
```

`rf-dock-old_data` no tiene contenedor y sigue ahí. Así que una limpieza completa de una vez son dos comandos:

```bash
docker system prune -a --volumes -f
docker volume prune -a -f
```

`-f` se salta la pregunta. Sin él, una ejecución desde un script o con stdin cerrado imprime la advertencia y no elimina nada.

`--filter until=24h` conserva todo lo que tenga menos de un día, contenedores, imágenes, redes y registros de caché:

```bash
docker system prune -a -f --filter until=24h
```

```text
Total reclaimed space: 0B
```

Cero, porque todos los objetos del laboratorio tenían minutos. Esa es la forma para un temporizador nocturno. En el almacén de imágenes de containerd, el predeterminado en las instalaciones nuevas de Engine 29 y posteriores, la antigüedad de una imagen cuenta desde su pull. Así que una imagen descargada hoy sobrevive al filtro aunque su fecha de compilación tenga meses. En el almacén de imágenes clásico cuenta desde la fecha de compilación.

Las cuatro formas, cada una ejecutada en una copia nueva del estado del laboratorio:

| Comando | Eliminado en el laboratorio | Lo que quedó en el laboratorio | Contrapartida |
|---|---|---|---|
| `docker system prune` | 1 contenedor detenido, 1 red sin uso, 1 imagen colgante, 8 de 11 registros de caché, 82.23kB | Los contenedores en ejecución y sus 2 imágenes, otras 2 imágenes con etiqueta, los 5 volúmenes | Libera poco mientras las imágenes antiguas conservan sus etiquetas |
| `docker system prune -a` | Lo mismo, más 2 imágenes con etiqueta sin contenedor y el resto de la caché, 8.846MB | Los contenedores en ejecución y sus 2 imágenes, los 5 volúmenes | Recuperar un stack empieza con un pull nuevo |
| `docker system prune -a --volumes` | Lo mismo, más 1 volumen anónimo sin uso, 8.846MB | 3 volúmenes con nombre, 1 volumen anónimo en uso | Los volúmenes con nombre necesitan `docker volume prune -a` |
| `docker system prune -a -f --filter until=24h` | Nada, 0B | Todo lo creado o usado en las últimas 24 horas | En el almacén de imágenes de containerd una imagen es tan joven como su pull |

## Qué comando puede borrar cada tipo de dato

| Dato | Dónde vive | Lo borra | Lo conserva |
|---|---|---|---|
| Volumen con nombre | `/var/lib/docker/volumes/<name>/_data` | `docker volume prune -a`, `docker volume rm`, `docker compose down -v` | `docker system prune -a --volumes`, `docker volume prune` a secas, `docker compose down` |
| Volumen anónimo | `/var/lib/docker/volumes/<64 characters>/_data` | `docker volume prune` a secas, `docker system prune --volumes`, `docker rm -v`, `docker compose down -v` | `docker system prune` sin `--volumes`, `docker compose down` |
| Bind mount | La carpeta del host que indicaste | Solo un `rm -rf` en el host | Todos los prune, y `rm -rf /var/lib/docker` |
| Capa de escritura de un contenedor | La propia instantánea del contenedor | `docker rm`, `docker container prune`, `docker compose down`, `docker system prune` | `docker stop` |
| Caché de construcción | `/var/lib/docker/buildkit` | `docker builder prune -a`, `docker buildx prune`, `docker system prune` | Los otros tipos de prune |

`docker compose down` conserva los dos tipos de volumen. Un volumen anónimo no tiene un nombre estable, así que el siguiente `up` no lo vuelve a montar y crea uno nuevo. El laboratorio tenía cinco volúmenes antes de un par de `down` y `up` y seis después.

`down -v` es el que no tiene vuelta atrás. El archivo estaba en el volumen un momento antes:

```bash
docker run --rm -v rf-dock-db_data:/d:ro alpine ls /d
docker compose down -v
```

```text
rows.txt
 Container rf-dock-db-data-1 Stopping
 Container rf-dock-db-data-1 Stopped
 Container rf-dock-db-data-1 Removing
 Container rf-dock-db-data-1 Removed
 Volume rf-dock-db_data Removing
 Network rf-dock-db_default Removing
 Volume rf-dock-db_data Removed
 Network rf-dock-db_default Removed
```

El archivo tar del paso de volúmenes es la única forma de deshacerlo.

## Nunca borres /var/lib/docker con Docker en marcha

`rm -rf /var/lib/docker` aparece en la documentación de Docker, en el [procedimiento de desinstalación](https://docs.docker.com/engine/install/ubuntu/#uninstall-docker-engine), después de eliminar los paquetes. Bajo un daemon en ejecución hace otra cosa. El daemon del laboratorio tenía tres contenedores en ejecución cuando ejecuté el comando:

```bash
rm -rf /var/lib/docker
```

```text
rm: can't remove '/var/lib/docker/rootfs/overlayfs/7b7482a5ee449493e43b71678edc5d05a37fbe8c933f0e6d590aab2adc1d0835': Resource busy
rm: can't remove '/var/lib/docker/rootfs/overlayfs/637e23f32498a121aa8a9b38ffb7272398f564448abdbe3673408b19dbfea18c': Resource busy
rm: can't remove '/var/lib/docker/rootfs/overlayfs/c1586ea0cb4500d7a8a9a3741127908bb0af66beadfb78644f060b64b6490905': Resource busy
```

El comando termina con un error y deja un daemon que existe a medias. `docker ps` sigue listando los contenedores, con los ID de imagen en lugar de los nombres. `docker system df` falla:

```text
Error response from daemon: error getting build cache usage: error getting build cache usage: failed to get usage for vwh921yk5p3wnux8p1kb4z1c8: lstat /var/lib/docker/containerd/daemon/io.containerd.snapshotter.v1.overlayfs/snapshots/689/fs: no such file or directory
```

`docker volume inspect` sigue informando del punto de montaje de un volumen cuyo directorio ya no existe:

```text
ls: /var/lib/docker/volumes/rf-dock-site_html/_data: No such file or directory
```

`docker exec` en un contenedor en ejecución falla con `open /var/lib/docker/tmp/runc-process2931786969: no such file or directory`, y `docker run` falla con `blob not found`. El `rm` no tocó la carpeta montada como bind mount.

El directorio guarda más que imágenes. El listado del laboratorio tenía `buildkit` para la caché de construcción, `containerd` para el almacén de imágenes cuando dockerd arranca containerd por sí mismo, `containers`, `image`, `network`, `volumes`, `rootfs` y algunos archivos de estado. En un host instalado desde los paquetes de Docker con el almacén de imágenes de containerd, el contenido de las imágenes y las instantáneas de los contenedores viven en `/var/lib/containerd` y el resto en `/var/lib/docker` ([documentación del daemon](https://docs.docker.com/engine/daemon/#daemon-data-directory)). El comando ni siquiera elimina las imágenes allí.

<Notice type="error" title="Detén el daemon antes de borrar su directorio">
`rm -rf /var/lib/docker` bajo un dockerd en ejecución deja contenedores en los que no puedes hacer exec, imágenes que no puedes ejecutar y volúmenes que existen sin sus datos. Detén primero `docker.socket`, `docker` y `containerd`.
</Notice>

Dos caminos lo reemplazan.

Para una reinstalación limpia, el camino del prune basta: `docker compose down` para cada stack y luego `docker system prune -a --volumes -f` y `docker volume prune -a -f`. El resultado son los cuatro ceros de arriba, y el siguiente `docker compose up` descarga las imágenes que faltan.

Para un reinicio real del daemon, deténlo primero. El procedimiento de desinstalación elimina los directorios solo después de que `apt purge` haya eliminado los paquetes. El mismo orden sin el purge es:

```bash
sudo systemctl stop docker.socket docker containerd
sudo rm -rf /var/lib/docker /var/lib/containerd
sudo systemctl start containerd docker
```

No ejecuté estas tres líneas, porque el laboratorio no tiene systemd. En un segundo daemon del laboratorio, arrancado como un proceso normal, ejecuté el mismo orden: eliminar los contenedores, detener dockerd, borrar su directorio de datos y arrancarlo de nuevo. Volvió vacío, sin ningún error.

Cada `docker compose down` deja su stack fuera de línea, así que en un host de producción cada `down` necesita una ventana de mantenimiento. Si `/var/lib/docker` sigue siendo grande después de los cuatro ceros, la siguiente lectura es [la guía de limpieza de overlay2](/es/limpiar-docker-overlay2/). Para ver cómo se llena el disco antes de que se agote, [monitoriza el servidor y los recursos de Docker](/es/monitorizar-servidor/).

## Preguntas frecuentes

<Accordion label="¿docker system prune elimina los contenedores en ejecución?" group="faq">
No. Elimina solo los contenedores detenidos, además de las imágenes y las redes que ningún contenedor usa. En el laboratorio, tres contenedores en ejecución sobrevivieron a `docker system prune -a --volumes`, con sus imágenes y sus volúmenes.
</Accordion>

<Accordion label="¿Por qué docker volume prune deja volúmenes sin borrar?" group="faq">
Desde Engine 23.0 el prune por defecto elimina solo los volúmenes anónimos sin uso, los que tienen un nombre de 64 caracteres. Un volumen con nombre se queda hasta que `docker volume prune -a` o `docker volume rm` lo elimina, y los volúmenes creados antes de Engine 23 cuentan como volúmenes con nombre.
</Accordion>

<Accordion label="¿docker system prune -a --volumes borra los volúmenes con nombre?" group="faq">
No. `--volumes` cubre los volúmenes anónimos sin contenedor. Después de la ejecución, `docker volume ls` en el laboratorio seguía mostrando tres volúmenes con nombre, uno con `LINKS 0`, así que añade `docker volume prune -a -f` para esos.
</Accordion>

<Accordion label="¿Existe un dry run para docker system prune?" group="faq">
No existe ninguna opción para eso. Sin `-f` el comando imprime el bloque `WARNING!` y espera la respuesta. Para saber los objetos exactos, `docker ps -q -a --filter status=exited`, `docker volume ls -q --filter label=com.docker.volume.anonymous`, `docker network ls -q --filter dangling=true` y `docker images -q --filter dangling=true` listan lo que elimina cada prune por defecto.
</Accordion>

<Accordion label="¿Qué conserva la opción --filter until=24h?" group="faq">
Todo lo de las últimas 24 horas: contenedores, imágenes, redes y registros de caché. En el almacén de imágenes de containerd una imagen cuenta desde su pull, así que `docker images -a --filter until=24h` queda vacío justo después de un pull. En el almacén de imágenes clásico cuenta desde la fecha de compilación.
</Accordion>

<Accordion label="¿Docker builder prune o docker buildx prune: cuál usar?" group="faq">
Ambos llegan a la caché del builder por defecto. Sin `-a`, `docker builder prune` conservó 8.751MB de 8.8MB en el laboratorio, los registros que una imagen todavía comparte, así que `-a` la vacía. `docker buildx prune` añade filtros como `until=24h`, el límite `--max-used-space` y `--builder` para otro builder.
</Accordion>

<Accordion label="¿docker compose down elimina volúmenes?" group="faq">
Un `down` a secas conserva los volúmenes con nombre y los anónimos, y elimina solo los contenedores y las redes del stack. `docker compose down -v` además borra los volúmenes con nombre declarados en el archivo Compose y los volúmenes anónimos de sus contenedores, sin forma de deshacerlo.
</Accordion>

<Accordion label="¿Qué pasa si borro /var/lib/docker con dockerd en ejecución?" group="faq">
Falla y deja un daemon roto. En el laboratorio `rm` devolvió `Resource busy` para cada contenedor en ejecución y borró todo lo demás, así que `docker system df` dio un error y los volúmenes existían sin sus datos. Detén primero `docker.socket`, `docker` y `containerd`, o haz un prune en su lugar.
</Accordion>
