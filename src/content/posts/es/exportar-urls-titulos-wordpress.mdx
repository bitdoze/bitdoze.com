Esta guía muestra cómo exportar todas las URLs y títulos de las entradas de WordPress, tanto si los necesitas para un mapa de redirecciones, una auditoría SEO o una migración. Hay cinco métodos gratuitos: SQL en phpMyAdmin, WP-CLI, la API REST, el sitemap XML del núcleo o un plugin gratuito. Cada uno lleva alrededor de un minuto cuando sabes cuál encaja con tu nivel de acceso. Si vas a construir un mapa de redirecciones, exporta la lista de URLs del sitio de *origen* **antes** del cambio de DNS. Tras una migración, la nueva base de datos no puede decirte cuáles eran las URLs antiguas.

Usé esta exportación como primer paso al [migrar mi sitio de WordPress a Astro](/es/migracion-wordpress-a-astro/), y es lo primero que hago al [analizar la lista de URLs exportadas en una herramienta de analítica SEO como SEO Gets](/es/herramienta-seo-gets/). La sección de "Errores comunes" al final explica por qué a veces las URLs exportadas dan error 404. Léela antes de fiarte de cualquier exportación para redirecciones.

<Notice type="info" title="Todo aquí es gratuito">
Todos los métodos de esta guía son gratis. Sin claves API, sin herramientas SaaS, sin planes de pago. El SQL corre en tu base de datos, WP-CLI es código abierto, la API REST y el sitemap XML vienen incluidos en el núcleo de WordPress y el plugin es GPL.
</Notice>

## ¿Qué método de exportación deberías usar?

| Tu situación | Método | Tiempo |
|---|---|---|
| Acceso SSH al servidor | WP-CLI | ~10 segundos |
| Solo panel de control del hosting | SQL en phpMyAdmin | ~1 minuto |
| Sin SSH y sin acceso a base de datos | API REST o sitemap XML | ~1 minuto |
| Sitio grande, necesitas filtros/JSON/diffs | Plugin Export All URLs | Unos minutos |

La fila de "sin SSH, sin BD" es habitual en [proveedores económicos de hosting PHP en la nube](/es/alojamiento-cloud-php/) que bloquean ambos accesos. La API REST y el sitemap funcionan desde el navegador o con `curl`, sin credenciales.

## Exportar URLs y títulos con SQL en phpMyAdmin

El método SQL es el más rápido si tienes acceso a phpMyAdmin desde el panel de control de tu hosting.

### 1. Abre phpMyAdmin

Inicia sesión en el panel de control de tu hosting y haz clic en phpMyAdmin.

<Picture formats={["webp"]} fallbackFormat="webp" src={imgPhpMyAdmin} alt="Enlace de phpMyAdmin en el panel de control del hosting" />

### 2. Selecciona tu base de datos y abre la pestaña SQL

Haz clic en tu base de datos de WordPress en la barra lateral izquierda y luego abre la pestaña **SQL**.

<Picture formats={["webp"]} fallbackFormat="webp" src={imgSqlTab} alt="Pestaña SQL de phpMyAdmin" />

### 3. Ejecuta la consulta

Pega este SQL. Lee la URL `home` de `wp_options` para que no tengas que escribir tu dominio a mano:

```sql
SELECT p.post_title,
       CONCAT((SELECT option_value FROM wp_options WHERE option_name = 'home'), '/', p.post_name)
FROM wp_posts p
WHERE p.post_status = 'publish' AND p.post_type = 'post';
```

Si el prefijo de tus tablas no es `wp_`, ajústalo en consecuencia (comprueba el nombre real de la tabla en la barra lateral izquierda). En multisitio, cada sitio tiene sus propias tablas (`wp_2_posts`, `wp_3_posts`, etc.), así que consulta la correcta.

Pulsa **Continuar**.

<Picture formats={["webp"]} fallbackFormat="webp" src={imgSqlGo} alt="Ejecutando la consulta SQL en phpMyAdmin" />

### 4. Exporta los resultados

Aparece una tabla con los títulos y URLs de las entradas. Haz clic en **Exportar**.

<Picture formats={["webp"]} fallbackFormat="webp" src={imgExport} alt="Botón Exportar de phpMyAdmin" />

Elige tu formato de archivo (CSV va muy bien para hojas de cálculo), define el delimitador si hace falta y pulsa **Continuar**.

<Picture formats={["webp"]} fallbackFormat="webp" src={imgFormat} alt="Selección del formato de exportación en phpMyAdmin" />

Obtendrás un archivo con el título de cada entrada publicada y su URL. Para incluir páginas o tipos de entrada personalizados, cambia `post_type = 'post'` por `post_type = 'page'` o elimina la condición de `post_type` por completo para sacarlo todo.

En sitios grandes, phpMyAdmin puede toparse con límites de memoria o tiempo de PHP. Divide la consulta por lotes con `LIMIT 1000 OFFSET 0`, luego `LIMIT 1000 OFFSET 1000`, etc., o pásate a WP-CLI o al plugin (que pagina automáticamente).

### La trampa de la estructura de enlaces permanentes (por qué las URLs exportadas dan 404)

<Notice type="warning" title="Las URLs solo son exactas con enlaces permanentes 'Nombre de la entrada'">
La consulta anterior construye las URLs como `home + "/" + post_name`. Eso solo es correcto si tu estructura de enlaces permanentes es "Nombre de la entrada" (Ajustes → Enlaces permanentes). Con prefijos de fecha o categoría, cada URL generada dará un 404. Si necesitas URLs exactas para redirecciones, usa el campo `url` de WP-CLI, la API REST o el sitemap.
</Notice>

El problema: `post_name` es solo el último segmento de una URL:

```
URL real (enlaces permanentes con fecha):
https://yourdomain.com/2024/03/my-post-slug
└───── home ─────┘└─año─┘└mes┘└── post_name ──┘

El SQL construye:
https://yourdomain.com/my-post-slug
└───── home ─────┘└── post_name ──┘  ← faltan los segmentos de fecha → 404
```

Lo mismo pasa con estructuras `/%category%/%postname%/`, donde desaparece el segmento de categoría. Y con enlaces "Simples" (`?p=123`) no existe ninguna URL amigable que exportar.

La variante con la opción `home` de arriba resuelve el problema de esquema/dominio (no fija a mano `https://` ni `www.`), pero sigue arrastrando la limitación de la estructura de enlaces permanentes. Ese es el compromiso: SQL es rápido, pero no sabe nada sobre tus reglas de reescritura.

Ejecuta las comprobaciones de [Comprueba los números exportados](#comprueba-los-números-exportados) antes de dar la salida por buena.

## Exportar URLs de entradas de WordPress con WP-CLI

Si tienes acceso SSH al servidor (por ejemplo, un VPS en [Hetzner Cloud](https://go.bitdoze.com/hetzner)), WP-CLI es la vía más rápida. Suele venir preinstalado en stacks gestionados; si tu servidor ejecuta [WordPress en Ubuntu con CloudPanel](/es/instalar-wordpress-ubuntu-arm/), WP-CLI está a un `wget` de distancia. Si quieres probar antes con seguridad, [instala WordPress con Docker Compose](/es/instalar-wordpress-docker/) y ejecuta los comandos sobre una copia local.

### Obtén URLs completas con el campo `url` (no `guid`)

```bash
wp post list --post_type=post --post_status=publish --fields=post_title,url --format=csv > posts.csv
```

WP-CLI inyecta un campo `url` calculado por `get_permalink()` del núcleo de WordPress. Respeta tu estructura de enlaces permanentes (`/%year%/%postname%/`, bases de categoría, lo que uses) y saca el dominio y esquema correctos. Este es el comando que usaría para cualquier tarea de redirecciones.

No uses `guid` en lugar de `url`. El núcleo de WordPress es tajante con esto: [el GUID no debe usarse como enlace](https://developer.wordpress.org/reference/functions/get_the_guid/). La documentación de `get_the_guid()` explica que el guid "parecerá un enlace" pero no debe usarse como tal, porque se rompe cuando mueves el blog entre dominios. Tras una migración, `guid` sigue mostrando el dominio y esquema antiguos, así que no sirve para armar redirecciones. Consulta [la trampa del GUID después de una migración](#la-trampa-del-guid-después-de-una-migración) más abajo.

La variante con el slug `post_name` sigue siendo útil si solo necesitas slugs (no URLs completas):

```bash
wp post list --post_type=post --post_status=publish --fields=post_title,post_name --format=csv > posts.csv
```

Tendrías que anteponer tu dominio manualmente. Mismo aviso sobre los enlaces permanentes que en el método SQL.

### Variante de auditoría: IDs, fechas y todos los tipos de entrada

Para una auditoría de contenido, saca más campos:

```bash
wp post list --post_type=post --post_status=publish --fields=ID,post_title,post_date,url --format=csv > posts-audit.csv
```

Para sacarlo todo, en todos los estados (borradores, pendientes, privados, tipos de contenido personalizados):

```bash
wp post list --post_type=any --post_status=any --fields=ID,post_title,post_status,post_type,url --format=csv > everything.csv
```

Las URLs de borradores y entradas privadas pueden devolver 404 al público. Útil para auditoría interna, erróneo para un mapa de redirecciones.

Si quieres la salida SQL sin abrir phpMyAdmin, `wp db query` lo hace de golpe:

```bash
wp db query "SELECT post_title, post_name FROM wp_posts WHERE post_status='publish' AND post_type='post'" --csv > posts.csv
```

Verifica el recuento con `wp post list --post_type=post --post_status=publish --count`. Debería coincidir con las filas exportadas. La [documentación de `wp post list` en WP-CLI](https://make.wordpress.org/cli/handbook/references/commands/post/) cubre todos los campos disponibles.

## Exportar URLs con la API REST de WordPress (sin plugin)

WordPress incluye una API REST pública (desde la versión 4.7) que devuelve valores `link` fieles a tus enlaces permanentes, calculados por el núcleo igual que `get_permalink()`. Funciona incluso en hostings que no te dan ni SSH ni acceso a la base de datos.

```bash
curl -s 'https://yourdomain.com/wp-json/wp/v2/posts?per_page=100&_fields=link,title' | jq -r '.[] | [.title.rendered, .link] | @csv'
```

Esto saca un CSV con título y URL. El campo `title` viene como HTML renderizado (`title.rendered`). Limpia etiquetas si tus títulos llevan formato, o usa `_fields=link` para sacar solo las URLs. Para páginas, cambia a `/wp/v2/pages`. Para descubrir tipos de entrada personalizados, consulta `/wp/v2/types`.

### Paginar sitios grandes

`per_page` acepta de 1 a 100 (100 es el máximo). Para sitios con más de 100 entradas, recorre las páginas:

```bash
curl -s 'https://yourdomain.com/wp-json/wp/v2/posts?per_page=100&page=2&_fields=link,title'
```

Las cabeceras de respuesta `X-WP-Total` y `X-WP-TotalPages` te dicen cuántas páginas hay que descargar. Un sitio de 10.000 entradas tarda varios minutos reales en recorrer 100 páginas, así que no esperes "un minuto" aquí. Consulta la [documentación de paginación de la API REST](https://developer.wordpress.org/rest-api/using-the-rest-api/pagination/) para más detalles.

Algunos plugins de seguridad o proveedores restringen o exigen autenticación en `/wp-json/`. Si recibes un 401 o 404, el endpoint está bloqueado. Usa otro método. No es un fallo de tu instalación; es una decisión deliberada de endurecimiento en ese hosting.

## Exportar todas las URLs desde el sitemap XML

La respuesta más rápida si solo quieres las URLs: el núcleo de WordPress incluye sitemaps XML desde la versión 5.5 (2020). Abre esto en tu navegador:

```
https://yourdomain.com/wp-sitemap.xml
```

Ese es el índice de sitemaps. Haz clic hacia el archivo de entradas (`wp-sitemap-posts-post-1.xml`) para ver tus URLs publicadas. Los sitios con más de ~2.000 entradas se dividen en varios archivos (`wp-sitemap-posts-post-2.xml`, etc.).

Para extraer solo las URLs del XML:

```bash
curl -s 'https://yourdomain.com/wp-sitemap-posts-post-1.xml' | grep -o '<loc>[^<]*' | sed 's/<loc>//' > urls.txt
```

Los sitemaps solo incluyen contenido publicado e indexable, que es justo lo que quieres para mapas de redirecciones y auditorías SEO, aunque no obtendrás títulos ni URLs en borrador. El anuncio de [sitemaps del núcleo de WordPress](https://make.wordpress.org/core/2020/07/22/introducing-wordpress-core-sitemaps/) recoge la arquitectura original por si quieres los detalles.

## Plugin Export All URLs

Si no quieres tocar SQL ni la línea de comandos, el plugin gratuito [Export All URLs en wordpress.org](https://wordpress.org/plugins/export-all-urls/) hace esto desde el panel de administración de WordPress. Lleva activo desde 2016 y supera las 50.000 instalaciones activas. Con la v6.0 (actualizada en octubre de 2026, probada hasta WordPress 7.1.4), es una opción sólida.

Instálalo desde Plugins → Añadir nuevo, configura tus filtros (tipo de entrada, estado, rango de fechas, autor), exporta y luego desactívalo al terminar. Déjalo instalado si vas a usar la función de instantáneas (snapshots) que vemos abajo.

### Novedades de Export All URLs 6.0

La versión 6.0 fue una reescritura importante. Lo más útil que añade:

- La columna URL es un campo principal de exportación, junto con URLs de categorías, URLs de etiquetas, slug, recuento de palabras, extracto, URL de imagen destacada, recuento de comentarios y tipo de entrada.
- Salida en CSV y JSON, o resultados como tabla paginada en pantalla.
- Exportaciones por lotes, para que los sitios grandes dejen de chocar con timeouts y errores de memoria. Resuelve directamente el problema de phpMyAdmin en sitios grandes.
- Las descargas fluyen directo al navegador, así que no queda nada guardado en `wp-content/uploads`. Los plugins antiguos eran famosos por dejar allí CSVs legibles públicamente.
- Protección contra inyección de fórmulas en CSV y escape/nonces endurecidos. Conviene mencionarlo porque este plugin tuvo fallos históricos de XSS corregidos en versiones anteriores.
- Opción de "Excluir el dominio de las URLs", pensada para comparar conjuntos de URLs antes y después de migrar. Muy práctica al montar un mapa de redirecciones.
- Instantáneas (Snapshots): toma una huella del sitio y compara dos capturas para ver contenido añadido, eliminado o modificado. Si usas esto, mantén el plugin instalado en vez de desactivarlo.
- Columnas para WPML y Polylang con idioma y URLs de traducción.

Es gratis/GPL, sin cuenta y sin clave API. Corre sobre WP 3.6+ / PHP 5.4+, así que funciona en casi cualquier WordPress.

### El mini flujo de trabajo para mapas de redirecciones

Si estás montando un mapa de redirecciones 301 para una migración: exporta la lista de URLs del sitio origen antes del cambio de DNS, normaliza el esquema y el prefijo `www.`, impórtalo como mapa 301 y verifica después con `curl -sI -o /dev/null -w '%{http_code}'` sobre una muestra. Haz copia de seguridad primero (los [plugins gratuitos de backup para WordPress](/es/mejores-plugins-gratuitos-backup-wordpress/) cubren esto) antes de tocar la base de datos o migrar. ## Errores comunes y por qué fallan las URLs exportadas

### ¿Por qué mis URLs exportadas devuelven 404?

Dos causas explican casi todos los casos:

Desajuste en la estructura de enlaces permanentes. `post_name` es solo el último segmento de la URL. El método SQL construye `home + "/" + post_name`, que solo acierta en enlaces "Nombre de la entrada". Con `/%year%/%monthnum%/%postname%/` o `/%category%/%postname%/`, todas las URLs salen mal. Con enlaces "Simples" (`?p=123`) no existe ninguna URL amigable. Solución: usa un método consciente de los enlaces permanentes (`url` en WP-CLI, `link` en la API REST o el sitemap), o reconstruye tu estructura a mano.

Desajuste de dominio o esquema. Exportaciones antiguas pueden arrastrar valores `http://` o `www.` de una configuración previa. La variante SQL con la opción `home` ayuda aquí, pero confirma siempre que el dominio exportado coincide con el sitio activo antes de importar.

### La trampa del GUID después de una migración

<Notice type="warning" title="Nunca construyas redirecciones desde la columna guid">
El núcleo de WordPress indica que el GUID no debe usarse como enlace. Tras una migración de dominio o HTTPS, los GUID guardados siguen mostrando el dominio y esquema antiguos, justo los valores equivocados para un mapa de redirecciones.
</Notice>

La columna `guid` en `wp_posts` guarda un valor con aspecto de URL que WordPress usa como identificador único, no como enlace. La [referencia de `get_the_guid()`](https://developer.wordpress.org/reference/functions/get_the_guid/) es clara: el guid no debe usarse como enlace a la entrada porque puedes "mover el blog entre dominios". Tras una migración, exportar `guid` te da las URLs viejas, justo lo contrario de lo que necesita una auditoría posterior. Usa en su lugar el campo `url` de WP-CLI, `link` en la API REST o el sitemap.

### Multisitio, borradores y tipos de entrada personalizados

En multisitio, cada sitio tiene su propio prefijo de tabla (`wp_2_posts`, `wp_3_posts`, etc.). Consulta o ejecuta CLI en el sitio correcto; si los mezclas obtendrás URLs de otro sitio.

Los borradores, entradas pendientes y privadas tienen URLs que pueden dar 404 al público. Eso vale para una auditoría interna y está mal para un mapa de redirecciones. Usa `--post_status=any` (WP-CLI) o los filtros de estado del plugin para la auditoría.

Un filtro `post_type = 'post'` deja fuera por completo los tipos de contenido personalizados. Usa `--post_type=any` (WP-CLI), el selector de tipos del plugin o consulta `/wp/v2/types` en la API REST para descubrir qué tienes registrado.

## Preguntas frecuentes

<Accordion label="¿Cómo exporto URLs de WordPress sin ningún plugin?" group="faq" expanded="true">
Dos métodos sin dependencias: la API REST (`/wp-json/wp/v2/posts?_fields=link,title`) o el sitemap XML del núcleo (`/wp-sitemap.xml`). Ambos son funciones nativas de WordPress, así que no hay nada que instalar y no necesitas acceso SSH ni a la base de datos. La API REST te da títulos y URLs; el sitemap solo URLs. Mira [la sección de la API REST](#exportar-urls-con-la-api-rest-de-wordpress-sin-plugin) y [la sección del sitemap XML](#exportar-todas-las-urls-desde-el-sitemap-xml) para los comandos.
</Accordion>

<Accordion label="¿Puedo exportar también páginas y tipos de contenido personalizados?" group="faq">
Sí. En SQL, cambia `post_type = 'post'` por `'page'` o quita la condición por completo. En WP-CLI, usa `--post_type=any` para sacarlo todo o especifica un tipo concreto. El plugin Export All URLs incluye un desplegable para filtrar por tipo de entrada. Para descubrir tipos registrados en la API REST, consulta `/wp/v2/types`.
</Accordion>

<Accordion label="¿Qué problema tiene la columna guid?" group="faq">
El núcleo de WordPress dice que el GUID no debe usarse como enlace. Guarda el dominio y esquema de cuando se creó la entrada por primera vez, así que después de una migración de dominio o cambio a HTTPS, cada `guid` apunta a la URL antigua. Usa el campo `url` de WP-CLI (calculado con `get_permalink()`), `link` de la API REST o el sitemap. Los tres respetan tu estructura de enlaces permanentes y dominio actuales.
</Accordion>
