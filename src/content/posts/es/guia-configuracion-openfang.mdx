## Qué es realmente OpenFang


<YouTubeEmbed
  url="https://www.youtube.com/embed/JX-MbP0qMCk"
  label="Conoce OpenFang: Mejor Alternativa Open-Source a OpenClaw"
/>

OpenFang es un proyecto de código abierto de [RightNow AI](https://www.rightnowai.co/), construido enteramente en Rust. Está estructurado como un workspace de 14 crates con un total de 137.728 líneas de código, 2.696+ pruebas y cero advertencias de clippy. Todo compila en un único binario de ~32MB que consume unos 40MB de RAM en reposo (cifras de benchmark del README; la huella real en un VPS puede variar, así que mide antes de planificar con ella). Tenía 18.250 estrellas y 2.282 forks en GitHub a junio de 2026, así que ya pasó la etapa de "proyecto de fin de semana con tres usuarios".

La arquitectura se ve así:

![Diagrama de arquitectura de OpenFang Agent OS mostrando los 40 adaptadores de canales de chat alimentando el daemon de OpenFang con sus capas de kernel y runtime, proveedores LLM como MiniMax M2.5 y GLM-5, y Hands autónomos ejecutándose en horarios](@assets/images/26/03/openfang-architecture.svg)

Los mensajes llegan desde tu app de chat y se enrutan al LLM que hayas configurado. Los agentes pueden usar 53 herramientas integradas, conectarse a servidores MCP y ejecutarse dentro de un sandbox WASM. La parte a la que siempre vuelvo es Hands. Son agentes autónomos que se despiertan en un horario, hacen su trabajo y reportan a tu dashboard sin que tú envíes un solo mensaje.

## Por qué GLM-5 y MiniMax M2.5

Ambos modelos funcionan bien con el sistema de proveedores de OpenFang y mantienen los costes bajos para configuraciones de agentes siempre activos. Esa segunda parte importa más que la posición en los leaderboards: los Hands queman tokens cada día lo mires o no, así que un precio barato por token gana a los derechos de presumir cuando un agente corre en cron.

### GLM-5

GLM-5 de Zhipu AI es un modelo MoE de 744B con unos 40-44B de parámetros activos. Ocupa el primer puesto entre modelos de código abierto en BrowseComp, que mide tareas de búsqueda e investigación web, una buena pareja para el Hand Researcher de OpenFang.

| Especificación | Valor |
|------|-------|
| Arquitectura | 744B MoE, ~40B activos |
| Ventana de contexto | 200K tokens |
| SWE-Bench Verified | 77,8% |
| BrowseComp | #1 open source |
| Licencia | MIT |

La ventana de contexto de 200K maneja tareas de investigación largas sin toparse con límites.

### MiniMax M2.5

MiniMax M2.5 es un modelo MoE de 230B con solo 10B de parámetros activos por pasada. Es más rápido y barato que GLM-5, y la ventana de contexto de 1M de tokens es difícil de ignorar:

| Especificación | Valor |
|------|-------|
| Arquitectura | 230B MoE, 10B activos |
| Ventana de contexto | 1M tokens |
| Velocidad (Lightning) | 100 tokens/seg |
| Coste (Lightning) | $0,30/M entrada, $2,40/M salida |
| SWE-Bench Verified | 80,2% |
| Licencia | MIT modificado (código abierto) |

MiniMax M2.5 saca un 80,2% en SWE-Bench Verified, lo que lo pone al lado de los modelos frontier a una fracción del precio. El contexto de 1M es excesivo para chat pero útil cuando los Hands procesan grandes cantidades de datos de investigación. Para ver cómo se compara con otros modelos baratos para bots siempre activos, mira nuestro análisis de [mejores modelos open source para OpenClaw](/es/mejores-modelos-opensource-openclaw/).

Ambos modelos están disponibles a través de sus APIs directas y a través de OpenRouter.

Una nota de honestidad antes de configurar nada: estas specs y precios se comprobaron cuando se escribió esta guía, y la lista de modelos se mueve rápido. Nombres más nuevos (GLM-5.3, MiniMax M2.7, MiniMax M3.1) ya aparecen en listados de 2026. Esta guía mantiene GLM-5 y MiniMax M2.5 como la configuración probada porque es la que usan los configs de abajo, y ambos siguen disponibles a través de sus APIs directas.

## Requisitos previos

Lo que tiene que existir antes de tocar el paso 1:

<ListCheck>
<ul>
<li>Un VPS Linux o máquina local. 1 vCPU y 1-2GB de RAM es suficiente (OpenFang consume unos 40MB en reposo)</li>
<li>Acceso SSH y un editor de terminal que sepas manejar (nano vale)</li>
<li>Una clave API de Z.AI (GLM-5), MiniMax (M2.5) o ambas</li>
<li>Una aplicación de Discord con token de bot, si quieres el canal de Discord</li>
<li>Puerto 4200 para la API y el dashboard, mantenido en 127.0.0.1</li>
<li>Un plan para los secretos: las claves viven en variables de entorno, nunca en config.toml</li>
</ul>
</ListCheck>

<Notice type="info" title="No necesitas las tres cuentas">
Solo GLM-5 o solo MiniMax M2.5 ya es una configuración que funciona. Discord también es opcional; el daemon funciona bien solo con una API y el dashboard TUI integrado.
</Notice>

Reserva 30-45 minutos de principio a fin en un VPS limpio, la mayor parte esperando aprobaciones de claves y peleando con el portal de desarrolladores de Discord.

## Instalar OpenFang

Tres caminos para conseguir el binario, más una app de escritorio para uso fuera de servidor.

<Tabs>
<Tab name="Script de instalación (recomendado)">

La forma más rápida. Funciona en macOS y Linux.

```bash
curl -sSf https://openfang.sh | sh
```

Esto descarga el binario precompilado para tu plataforma y lo pone en tu PATH.

</Tab>
<Tab name="Desde el código fuente">

Si quieres el código más reciente o planeas contribuir:

```bash
# Instala Rust si no lo tienes
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
source $HOME/.cargo/env

# Clona y compila
git clone https://github.com/RightNow-AI/openfang.git
cd openfang
cargo build --workspace --release

# El binario está en target/release/openfang
sudo cp target/release/openfang /usr/local/bin/
```

</Tab>
<Tab name="Windows">

PowerShell:

```powershell
irm https://openfang.sh/install.ps1 | iex
```

</Tab>
</Tabs>

<Notice type="info" title="App de escritorio">
OpenFang también trae una app de escritorio nativa construida con Tauri 2.0: .msi para Windows, .dmg para macOS, .AppImage y .deb para Linux, con bandeja de sistema y auto-actualizaciones. Bien para un equipo de escritorio. En un VPS, quédate con el binario o Docker.
</Notice>

Después de instalar, inicializa el workspace y la configuración:

```bash
openfang init
```

Esto crea el directorio `~/.openfang/` con un `config.toml` por defecto, configura el workspace local y te guía para elegir un proveedor LLM. Para instalaciones desatendidas (scripts, CI), `openfang init --quick` se salta las preguntas interactivas. Cuando ya existe una configuración, `openfang config edit` la abre en `$EDITOR`.

### Verifica que funciona

```bash
# Ejecuta diagnósticos: config, claves API, DB, puertos, dependencias de herramientas
openfang doctor

# Confirma lo que ve el daemon
openfang status
```

`openfang doctor` es el comando a ejecutar antes de culpar a tu configuración. Te dice qué variables de entorno ve, si la DB se inicializó y qué puertos están libres.

Modos de fallo en esta etapa:

- **El instalador muestra una pantalla negra en Arch/CachyOS con fish.** Un bug en instaladores anteriores a v0.6.4. Actualiza más allá de v0.6.4 o compila desde el código fuente.
- **`openfang: command not found` tras instalar.** Vuelve a cargar tu shell (`source ~/.bashrc`) o copia el binario a `/usr/local/bin/`.

## Configurar GLM-5 (Zhipu)

OpenFang usa un archivo `config.toml` en `~/.openfang/config.toml` (`/data/config.toml` en Docker). En la práctica, la configuración más limpia es definir el modelo seleccionado en `[default_model]` y luego mantener las credenciales y endpoints de API específicos del proveedor en el bloque `[providers.<nombre>]` correspondiente.

### Obtener una clave API

1. Ve a [z.ai](https://z.ai/manage-apikey/apikey-list)
2. Regístrate y crea una clave API

<Notice type="success" title="Plan Coding GLM de Z.AI: 10% de descuento">
Z.AI ofrece [planes GLM Coding](https://go.bitdoze.com/glm) pensados para cargas de trabajo continuas de desarrollo. Usa nuestro enlace para un 10% de descuento.
</Notice>

<Notice type="info" title="Endpoint del plan Coding de Zhipu">
Si estás en el plan de programación de Zhipu, configura `api_base = "https://api.z.ai/api/coding/paas/v4"` en tu configuración del proveedor zhipu. Esto enruta a través de su endpoint optimizado para código.
</Notice>

### Agregar a la configuración

```toml
[default_model]
provider = "openai"
model = "glm-5"
api_key_env = "ZHIPU_API_KEY"
base_url = "https://api.z.ai/api/coding/paas/v4"
```

Zhipu se configura a través del proveedor `openai` de OpenFang porque el endpoint de GLM es compatible con OpenAI. GLM-5 no está en el catálogo detallado de proveedores de OpenFang, así que el `base_url` personalizado es lo que hace que esto funcione.

<Notice type="warning" title="Los secretos nunca van en config.toml">
Desde las primeras versiones, la documentación es explícita: campos como `api_key_env` y `bot_token_env` contienen el **nombre** de una variable de entorno, nunca el secreto en sí. Expórtala antes de arrancar el daemon: `export ZHIPU_API_KEY="tu-clave-aqui"`. Lo cablearemos bien con systemd en un momento.
</Notice>

### Probarlo

```bash
openfang chat
> ¿Cuánto es 42 * 17?
```

Si obtienes una respuesta, GLM-5 está configurado correctamente. Escribe `exit` para salir del chat. `openfang doctor` también debería reportar la clave como detectada.

### Agregar a la configuración

MiniMax es un proveedor registrado en la documentación oficial de proveedores de OpenFang, así que `provider = "minimax"` con `MINIMAX_API_KEY` es el camino documentado. La base de la API difiere por región:

<Tabs>
<Tab name="Plataforma global">

```toml
[default_model]
provider = "minimax"
model = "MiniMax-M2.5"

[memory]
decay_rate = 0.05

[providers.minimax]
api_key_env = "MINIMAX_API_KEY"
api_base = "https://api.minimax.io/v1"

[agents.defaults]
model = "MiniMax-M2.5"
```

</Tab>
<Tab name="Plataforma de China continental">

```toml
[default_model]
provider = "minimax"
model = "MiniMax-M2.5"

[memory]
decay_rate = 0.05

[providers.minimax]
api_key_env = "MINIMAX_API_KEY"
api_base = "https://api.minimaxi.com/v1"

[agents.defaults]
model = "MiniMax-M2.5"
```

</Tab>
</Tabs>

Esto mantiene la declaración del proveedor explícita: `default_model` selecciona MiniMax, `[providers.minimax]` contiene los ajustes de la API y `[agents.defaults]` mantiene el modelo del agente por defecto alineado con el proveedor. `decay_rate = 0.05` es un valor personalizado que conserva los recuerdos más tiempo; el valor documentado por defecto es 0.1.

Si `provider = "minimax"` no se reconoce en tu build (el catálogo de proveedores sigue evolucionando pre-1.0), cae al driver compatible con OpenAI:

```toml
[default_model]
provider = "openai"
model = "MiniMax-M2.5"
api_key_env = "MINIMAX_API_KEY"
base_url = "https://api.minimax.io/v1"
```

Misma API, distinto enrutado. `openfang doctor` te dice lo que tu build reconoce de verdad.

### Configurar ambos proveedores

Si quieres ambos proveedores disponibles en la misma configuración, mantén cada uno en su propio bloque de proveedor y apunta el modelo por defecto al que quieras usar primero:

```toml
[default_model]
provider = "openai"
model = "glm-5"
base_url = "https://api.z.ai/api/coding/paas/v4"

[providers.openai]
api_key_env = "ZHIPU_API_KEY"

[providers.minimax]
api_key_env = "MINIMAX_API_KEY"
api_base = "https://api.minimax.io/v1"

[agents.defaults]
model = "glm-5"
```

Para cambiar a MiniMax, cambia `default_model.provider` a `"minimax"`, quita la línea `base_url` y pon `agents.defaults.model` a `"MiniMax-M2.5"`.

Verifica con `openfang chat` (la respuesta debería venir del modelo que esperas) y `openfang doctor` (ambas claves deberían aparecer como detectadas).

## Configuración del bot de Discord de OpenFang

Discord es sencillo con OpenFang porque es uno de los 40 adaptadores de canal soportados. Los pasos del lado de Discord no han cambiado desde que se publicó esta guía; la configuración del lado de OpenFang sí.

### Crear un bot de Discord

1. Ve a [discord.com/developers/applications](https://discord.com/developers/applications)
2. Haz clic en **New Application**, dale un nombre
3. Ve a **Bot** en la barra lateral izquierda, haz clic en **Add Bot**
4. Copia el token del bot

### Habilitar intents

Todavía en la página de configuración del Bot:

1. Desplázate hacia abajo hasta **Privileged Gateway Intents**
2. Habilita **MESSAGE CONTENT INTENT** (requerido para que el bot lea mensajes)
3. Opcionalmente habilita **SERVER MEMBERS INTENT** si planeas usar listas de permitidos

<Notice type="warning" title="Este es el fallo nº1">
Sin MESSAGE CONTENT INTENT, el bot se une a tu servidor y en silencio no lee nada. Sin error, sin línea en el log, simplemente no hay respuestas. Revisa esto antes de depurar cualquier otra cosa.
</Notice>

### Obtener tu ID de usuario

1. Abre Configuración de Discord → **Advanced** → habilita **Developer Mode**
2. Haz clic derecho en tu avatar en cualquier lugar de Discord
3. Haz clic en **Copy User ID**

### Configurar OpenFang

El formato de configuración actual usa nombres de variables de entorno para el token. No hay clave `enabled = true`; incluir la sección enciende el adaptador:

```toml
[channels.discord]
bot_token_env = "DISCORD_BOT_TOKEN"
allowed_users = ["YOUR_USER_ID"]
# allowed_guilds = []      # restringe a IDs de servidor concretos
# intents = 33280          # bitmask de intents del gateway por defecto
```

Después exporta el token antes de arrancar el daemon:

```bash
export DISCORD_BOT_TOKEN="tu-token-del-bot"
```

`allowed_users` restringe quién puede hablar con el bot. Déjalo vacío para que cualquiera en el servidor pueda usar el bot, o añade IDs de usuario concretos para un bot privado. `allowed_guilds` limita en qué servidores se queda el bot.

### Invitar el bot a tu servidor

1. En el portal de desarrolladores de Discord, ve a **OAuth2** → **URL Generator**
2. En **Scopes**, marca `bot`
3. En **Bot Permissions**, marca `Send Messages` y `Read Message History`
4. Copia la URL generada y ábrela en tu navegador
5. Selecciona el servidor al que quieres agregar el bot

### Iniciar el daemon

```bash
openfang start
```

**Verifica:** envía un mensaje en Discord y el bot debería responder. `curl http://127.0.0.1:4200/api/health` debería devolver OK, y `openfang status` muestra el adaptador de Discord conectado. El dashboard está en `http://127.0.0.1:4200`.

Fallos comunes aquí:

- **Bot en silencio:** MESSAGE CONTENT INTENT está desactivado (ver arriba), o el token se pegó en config.toml en lugar de en la variable de entorno `DISCORD_BOT_TOKEN`. La documentación nueva avisa al arrancar cuando encuentra tokens inline.
- **El bot entra pero no puede publicar:** la invitación se generó sin el permiso `Send Messages`.

Si prefieres construir un bot a medida desde cero en lugar de ejecutar un SO de agentes, mira [crear tu propio bot de Discord con IA](/es/crear-tu-propio-agente-ia/).

## Ejemplo de config.toml de OpenFang

Así se ve un `~/.openfang/config.toml` completo (o `/data/config.toml` en Docker) con MiniMax M2.5, Discord y la API expuesta con una contraseña:

```toml
api_listen = "0.0.0.0:4200"
api_key = "cambia-esto-por-una-contrasena-larga-y-aleatoria"

[default_model]
provider = "minimax"
model = "MiniMax-M2.5"
max_tokens = 8192
temperature = 0.7

[memory]
decay_rate = 0.05

[providers.minimax]
api_key_env = "MINIMAX_API_KEY"
api_base = "https://api.minimax.io/v1"

[agents.defaults]
model = "MiniMax-M2.5"

[channels.discord]
bot_token_env = "DISCORD_BOT_TOKEN"
allowed_users = ["YOUR_USER_ID"]
```

<Notice type="warning" title="Exporta cada variable de entorno antes de arrancar">
`MINIMAX_API_KEY`, `DISCORD_BOT_TOKEN` y (si se usa) `ZHIPU_API_KEY` tienen que existir en el entorno del daemon. Las variables que faltan aparecen como errores de autenticación del proveedor o un adaptador de Discord en silencio. `openfang doctor` lista las que puede ver.
</Notice>

Una nota rápida sobre puertos, porque la documentación se contradice. La referencia CLI, el README y la guía de inicio usan el puerto **4200** tanto para la API como para el dashboard web. La referencia de configuración sigue listando `api_listen = "127.0.0.1:50051"` como valor documentado por defecto. Esta guía usa 4200 en todo. En una instalación real, `openfang doctor` o `ss -tlnp` te dice qué está enlazado de verdad.

![Diagrama del flujo de secretos de OpenFang: config.toml referencia nombres de variables de entorno como MINIMAX_API_KEY, el entorno del proceso guarda los valores reales y el daemon borra las claves de la memoria tras usarlas](@assets/images/26/03/openfang-secrets-flow.svg)

### Ajustes de configuración explicados

| Ajuste | Por defecto | Qué hace |
|---------|---------|-------------|
| `api_listen` | `127.0.0.1:4200` (la doc dice 50051, ver arriba) | Dirección a la que se enlazan la API y el dashboard |
| `api_key` | ninguno (sin autenticar) | Token Bearer requerido para acceder a la API |
| `default_model.provider` | n/a | Qué proveedor usa OpenFang primero |
| `default_model.model` | n/a | Nombre del modelo enviado a ese proveedor |
| `memory.decay_rate` | 0.1 | Qué tan rápido se desvanece la memoria almacenada |
| `providers.minimax.api_key_env` | n/a | **Nombre** de la variable de entorno que guarda la clave MiniMax |
| `providers.minimax.api_base` | por defecto del proveedor | Endpoint de la API de MiniMax para tu región |
| `agents.defaults.model` | n/a | Modelo por defecto usado por agentes generados y Hands |
| `channels.discord.bot_token_env` | n/a | **Nombre** de la variable de entorno que guarda el token del bot |
| `channels.discord.allowed_users` | vacío | Restringe quién puede hablar con el bot |
| `channels.discord.allowed_guilds` | vacío | Restringe en qué servidores se queda el bot |
| `channels.discord.intents` | 33280 | Bitmask de intents del gateway |

```toml
temperature = 0.7
max_tokens = 8192

[channels.discord]
bot_token_env = "DISCORD_BOT_TOKEN"
allowed_users = ["YOUR_USER_ID"]
```

Esto mantiene el puerto en 4200 y solo cambia la dirección de enlace para que sea accesible remotamente. Dos cosas a saber: un `api_key` vacío significa una API sin autenticar, así que pon siempre una al enlazar a `0.0.0.0`. Y el dashboard web comparte este puerto, así que todo lo que expongas para clientes de la API queda expuesto junto. Limita el puerto por firewall a IPs de confianza, o no lo enlaces públicamente en absoluto.

## Despliegue Docker de OpenFang

OpenFang publica imágenes de contenedor. Ojo al nombre de organización en mayúsculas en la ruta de la imagen: `ghcr.io/RightNow-AI/openfang:latest`. La imagen define `OPENFANG_HOME=/data`, así que la configuración vive en `/data/config.toml` y el estado en el mismo directorio.

<Tabs>
<Tab name="Docker Compose (recomendado)">

```yaml
# docker-compose.yml
services:
  openfang:
    image: ghcr.io/RightNow-AI/openfang:latest
    container_name: openfang
    restart: unless-stopped
    ports:
      - "127.0.0.1:4200:4200"
    environment:
      MINIMAX_API_KEY: ${MINIMAX_API_KEY}
      DISCORD_BOT_TOKEN: ${DISCORD_BOT_TOKEN}
    volumes:
      - openfang-data:/data
      - ./config.toml:/data/config.toml
    extra_hosts:
      - "host.docker.internal:host-gateway"

volumes:
  openfang-data:
```

```bash
# Crea primero la config (si falta el archivo, Docker crea un
# directorio llamado config.toml y el contenedor no arranca)
nano config.toml    # pega la config completa de la sección de arriba

docker compose up -d
```

El `./config.toml` montado por bind hace que editar esté a un `docker compose restart` de distancia. El volumen nombrado `openfang-data` conserva el estado (base de datos, historial de Hands) entre `compose down` y actualizaciones de imagen. Si prefieres gestionar la config dentro del volumen también, quita el bind mount y mete archivos con `docker compose cp config.toml openfang:/data/config.toml`.

</Tab>
<Tab name="docker run">

```bash
docker run -d \
  --name openfang \
  --restart unless-stopped \
  -p 127.0.0.1:4200:4200 \
  -e MINIMAX_API_KEY \
  -e DISCORD_BOT_TOKEN \
  -v openfang-data:/data \
  --add-host=host.docker.internal:host-gateway \
  ghcr.io/RightNow-AI/openfang:latest
```

Seguirás necesitando un `config.toml` en `/data/config.toml` dentro del volumen. O lo siembras con `docker run --rm -v openfang-data:/data ghcr.io/RightNow-AI/openfang:latest init`, o copias uno dentro con `docker cp`.

</Tab>
</Tabs>

<Notice type="warning" title="Alcanzar el host desde Docker">
Si ejecutas Ollama, vLLM o un servidor MCP en el mismo host, el contenedor no puede alcanzarlo en `localhost`. El flag `--add-host=host.docker.internal:host-gateway` (ya incluido en los fragmentos de arriba) te da un hostname estable; apunta el `base_url` del proveedor a `http://host.docker.internal:11434/v1` para Ollama.
</Notice>

**Verifica:**

```bash
docker compose logs -f
curl http://127.0.0.1:4200/api/health
```

**Modos de fallo:**

- **El pull de la imagen falla con el nombre en minúsculas.** Usa `ghcr.io/RightNow-AI/openfang:latest` con mayúsculas como está documentado.
- **`config.toml` es un directorio.** Arrancaste Compose antes de crear el archivo. Elimina el directorio, crea el archivo, arranca de nuevo.
- **Bind mount viejo de `~/.openfang` de la versión anterior de esta guía.** La configuración ahora vive en `/data/config.toml`. Mueve tu config al volumen o al bind mount.
- **El contenedor no alcanza Ollama del host.** Falta host-gateway, mira el aviso de arriba.

**Rollback:** `docker compose down` detiene el contenedor y conserva el volumen `openfang-data`. `docker compose down -v` destruye ese volumen, historial de Hands incluido. Usa `-v` solo cuando lo dices en serio.

## Modelo de seguridad de OpenFang

OpenFang tiene 16 sistemas de seguridad, cada uno ejecutándose de forma independiente. Estos son los que importan para una configuración personal:

### Sandbox WASM

Cada herramienta se ejecuta dentro de un sandbox WebAssembly con medición de combustible. Si una herramienta intenta correr para siempre, el watchdog la mata.

Esto está habilitado por defecto. A diferencia de las verificaciones de permisos a nivel de aplicación, la herramienta físicamente no puede escapar de su sandbox.

### Rastro de auditoría

Cada acción se agrega a una cadena hash de Merkle. Manipula una entrada y toda la cadena se rompe.

### Listas de permitidos por canal

Mismo concepto que en la instalación de nanobot: restringe quién puede interactuar con el bot.

```toml
[channels.discord]
allowed_users = ["123456789"]
```

### Zeroización de secretos

Las claves API se borran automáticamente de la memoria en el momento en que dejan de necesitarse. OpenFang usa `Zeroizing<String>` en todo el código, así que los secretos no permanecen en RAM.

Una cosa más sobre esta capa: OpenFang carga skills SKILL.md en tiempo de ejecución, y el ecosistema está creciendo. Para una mirada más profunda a las skills maliciosas y a lo que hay que bloquear en plataformas de agentes, la [guía de seguridad de OpenClaw](/es/guia-seguridad-openclaw/) cubre los modos de fallo que aquí también me preocuparían. La v0.6.7 añadió verificación de firmas Ed25519 en las skills.

Checklist de producción antes de que esto toque algo que te importe:

<ListCheck>
<ul>
<li><code>api_key</code> configurado (una clave vacía significa una API sin autenticar)</li>
<li>Dashboard en 127.0.0.1, alcanzado por túnel SSH o proxy inverso</li>
<li>Reglas de firewall: solo SSH (y tu proxy) alcanzable desde fuera</li>
<li>SSH endurecido (auth por clave, sin login de root por contraseña)</li>
<li>Versión fijada, no solo <code>:latest</code></li>
<li>Secretos en un archivo de entorno o EnvironmentFile de systemd, no en el historial del shell</li>
</ul>
</ListCheck>

## Soporte MCP y A2A

OpenFang soporta tanto el [Model Context Protocol](/es/introduccion-mcp-principiantes/) para servidores de herramientas como la comunicación Agent-to-Agent (A2A). Trae 25 plantillas MCP y una bóveda de credenciales AES-256-GCM para guardar credenciales de servidores MCP.

### Agregar un servidor MCP

El formato actual envuelve el comando de lanzamiento en una sub-tabla `[mcp_servers.transport]`:

```toml
[[mcp_servers]]
name = "filesystem"
timeout_secs = 30
env = []
[mcp_servers.transport]
type = "stdio"
command = "npx"
args = ["-y", "@modelcontextprotocol/server-filesystem", "/home/user/documents"]

[[mcp_servers]]
name = "remote_server"
[mcp_servers.transport]
type = "sse"
url = "https://mcp.example.com/sse"
```

Las herramientas MCP se descubren automáticamente cuando OpenFang arranca. El LLM puede usarlas junto a las 53 herramientas integradas.


- **Seguimiento de costes y cuotas.** Los costes por modelo aparecen en el dashboard, y las cuotas de presupuesto por agente viven en la sección `[agents.resources]` de la doc de configuración. Para Hands siempre activos, pon un techo y deja que el kernel lo haga cumplir.

## Solución de problemas de OpenFang

Empieza con el trío oficial de diagnóstico:

```bash
openfang doctor                     # config, claves, DB, puertos, dependencias de herramientas
curl http://127.0.0.1:4200/api/health
RUST_LOG=debug openfang start       # ejecución en primer plano con logs detallados
```

| Síntoma | Causa probable | Solución |
|---------|-------------|-----|
| "Address already in use" al arrancar | 4200 (o 50051) ocupado | Revisa listeners con `ss -tlnp`, detén el otro servicio o cambia `api_listen` |
| Errores de auth del proveedor | Variables de entorno no exportadas | `openfang doctor` lista las claves visibles; expórtalas antes de `openfang start` |
| Bot de Discord en silencio | Intent desactivado, o token en config.toml | Activa MESSAGE CONTENT INTENT; mueve el token a `DISCORD_BOT_TOKEN` |
| La config no se recoge | Ruta equivocada | Bare metal: `~/.openfang/config.toml`. Docker: `/data/config.toml` |
| Pantalla negra del instalador | Bug fish/Arch en instaladores antiguos | Usa un instalador posterior a v0.6.4 o compila desde fuente |
| El contenedor no alcanza Ollama del host | Falta host-gateway | Añade `--add-host=host.docker.internal:host-gateway` |
| `openfang: command not found` | PATH no refrescado | Recarga el shell o copia el binario a `/usr/local/bin/` |
| OOM o permission denied | Máquina pequeña o usuario equivocado | Revisa `free -h`; asegúrate de que el usuario del servicio posee `~/.openfang/` |

Los logs están en los sitios de siempre: `journalctl -u openfang -f` para systemd, `docker compose logs -f` para Docker y `RUST_LOG=debug` cuando necesitas más.

Actualizar es simple: re-ejecuta el instalador o `docker compose pull && docker compose up -d`. Para producción, fija un tag de versión (`ghcr.io/RightNow-AI/openfang:v0.6.9`) y actualiza de forma deliberada.

**Rollback/deshacer:** `systemctl stop openfang` o `docker compose down` conserva tus datos. `~/.openfang/` en bare metal y el volumen `openfang-data` en Docker es el estado que merece copias de seguridad. Nada más es precioso.

Correr modelos locales en una Pi es otra historia; si quieres inferencia local, mira los [mejores mini PC para LLMs locales](/es/mejores-mini-pc-llm-local/).

**¿Pueden varias personas usar una instancia de OpenFang?**

Sí. OpenFang tiene listas de permitidos por canal, políticas de DM/grupo y control de acceso basado en roles. Ahora hay roles por usuario (owner, admin, user, viewer) con asignación por canal en la sección `[[users]]` de la config.

**¿Qué tan estable es OpenFang para uso en producción?**

Es v0.6.9, feature-complete pero todavía pre-1.0. El conjunto de pruebas tiene 2.696+ tests y el proyecto ha publicado más de 30 releases, lo que supera a un proyecto de fin de semana, pero los cambios que rompen todavía pueden llegar entre versiones menores. Fija una versión concreta para producción y vigila los releases de GitHub.

**¿Pueden los Hands trabajar con cualquier proveedor LLM?**

Sí. Los Hands usan el modelo que configures como por defecto, o puedes poner overrides de modelo por Hand. El Hand Researcher funciona bien con GLM-5 dadas sus puntuaciones en BrowseComp, mientras Clip y Lead van bien con MiniMax M2.5.

**¿Qué puerto usa OpenFang, 4200 o 50051?**

Ambos aparecen en la documentación. La referencia CLI, el README y la guía de inicio usan el puerto 4200 para la API y el dashboard. La referencia de configuración sigue listando `api_listen = "127.0.0.1:50051"` como valor documentado por defecto. Esta guía usa 4200. En una instalación real, `openfang doctor` o `ss -tlnp` te dice qué está enlazado de verdad.
