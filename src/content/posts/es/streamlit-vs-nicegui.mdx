Streamlit vs NiceGUI es la comparación que más veo cuando alguien quiere un framework web Python y no quiere escribir HTML a mano. Ambos te permiten construir apps web interactivas mayormente en Python, ambos son open source, y ambos corren bien como un único contenedor Docker en un VPS pequeño. Ambos también cambiaron lo suficiente en el último año como para que los posts de comparación más viejos estén ahora mal.

**Actualizado octubre 2026.** Versiones comprobadas contra PyPI y GitHub el 2026-10-07: Streamlit 1.65.0 (publicado 2026-10-02) y NiceGUI 3.17.1 (2026-09-18). Si lees una guía que sigue llamando a NiceGUI un framework de la era 2.0, ciérrala.

El posicionamiento corto sigue siendo el mismo que en 2024. [Streamlit](https://streamlit.io/) apunta a apps de datos: dashboards, exploración de datos, demos de ML. Escribes un script Python de arriba a abajo y Streamlit lo renderiza como una app web con gráficos, tablas y filtros integrados. [NiceGUI](https://nicegui.io/) apunta a UIs estilo aplicación: formularios, paneles de administración, herramientas de monitorización, controladores IoT. Es orientado a eventos, corre sobre FastAPI, y te da mucho más control sobre layout, eventos y estado.

## Vista rápida de comparación

| Función | Streamlit 1.65 | NiceGUI 3.17 |
|---|---|---|
| Mejor para | Apps de datos, dashboards, demos ML | UIs estilo app: formularios, paneles, monitorización |
| Modelo de autoría | Reejecución de script (con fragments para actualizaciones parciales) | Componentes orientados a eventos sobre WebSockets |
| Servidor subyacente | Starlette/Uvicorn (ASGI, rutas personalizadas vía `st.App`) | FastAPI/Starlette (móntalo en tu propia app) |
| Personalización | Theming + custom components v2 | Control total del layout, Quasar/Vue, Tailwind 4 |
| Auth integrada | `st.login()` / `st.logout()` (OIDC) | Middleware + patrón `app.storage.user` |
| Python | >= 3.10 | >= 3.10, < 4 |
| Licencia | Apache-2.0 (respaldado por Snowflake) | MIT (independiente) |

Esta tabla es orientación, no el veredicto. La decisión sigue reduciéndose al modelo de desarrollo: reejecuciones de script versus callbacks de eventos. Acertar ahí y el resto sigue.

> Para más opciones más allá de estos dos, mira: [Mejores Frameworks Web Python](https://www.bitdoze.com/best-python-web-frameworks/)

### Propósito principal

Streamlit está construido para ciencia de datos, ML y dashboards de analítica. Su set de widgets, renderizado de DataFrames y helpers de gráficos asumen ese flujo de trabajo. NiceGUI está construido para aplicaciones web de propósito general con interfaces estilo escritorio: formularios, paneles de administración, pantallas de control.

Ningún framework ha cruzado al otro lado en 2026. Streamlit sigue pareciendo un notebook al que le creció un servidor web. NiceGUI sigue pareciendo un toolkit GUI que por casualidad corre en el navegador. NiceGUI además trae los extras que lo convierten en framework de apps y no en herramienta de dashboards: ventanas nativas/de escritorio (basadas en PySide6), `run.cpu_bound` y `run.io_bound` para trabajo en segundo plano, y `ui.timer` para dashboards en vivo.

### Modelo de desarrollo: reejecución de script vs orientado a eventos

Este es el factor de decisión. Todo lo demás es secundario.

Streamlit corre tu script de arriba a abajo en cada interacción. Ese modelo es mortalmente simple hasta que tu app acumula trabajo pesado al inicio del archivo. Desde 1.37 y con adiciones constantes hasta 1.63, `@st.fragment` acota una reejecución a un bloque de la página (1.58 añadió `parallel=True`; 1.63 añadió reejecuciones por evento con `@st.fragment(key=...)` y `st.rerun("name")`). Los fragments arreglan lo peor del jank de la reejecución completa, pero el modelo mental sigue siendo "el script corre otra vez".

NiceGUI llama a tu handler y actualiza los elementos que tocas. El estado de la UI se sincroniza por un WebSocket persistente. Nada se reejecuta desde arriba.

Si tu modelo mental es un notebook, Streamlit gana. Si es una GUI con event handlers, NiceGUI gana. Mira el diagrama de arriba otra vez.

### Personalización

La vieja frase "Streamlit es limitado" necesita un asterisco ahora. Streamlit 1.51 (2025-10-29) envió custom components v2 (sin frame, bidireccionales), temas claros y oscuros personalizados, y archivos de tema reutilizables. Puedes construir un dashboard interno de marca sin forkear el framework.

Sigue sin acercarse a NiceGUI. NiceGUI se asienta sobre Quasar/Vue con Tailwind 4 (actualizado en 3.0), y puedes bajar a HTML/CSS/JS crudo cuando la librería de componentes se agota. Los layouts son explícitos: filas, columnas, grids, tabs, dialogs, drawers. Las apps multi-página son un patrón de primera clase vía `@ui.page` (mira cómo [añadir múltiples páginas a NiceGUI](https://www.bitdoze.com/nicegui-pages/)).

Streamlit también tiene apps multi-página, pero la navegación es basada en archivos y el chrome de la página está mayormente fijo. Si necesitas control a nivel de píxel o un layout que no parezca una app Streamlit, NiceGUI es la elección.

### Arquitectura backend

Ambos frameworks son apps ASGI en 2026. El viejo encuadre "Streamlit tiene un servidor de juguete, NiceGUI tiene FastAPI" está muerto.

Streamlit reemplazó Tornado por Starlette/Uvicorn en 1.57 (2026-04-29). `st.App` (experimental en 1.53, disponible con el cambio a Starlette) es un entry point ASGI que acepta rutas personalizadas, middleware y hooks de ciclo de vida, y convive con apps FastAPI o Starlette. Async/await en código de app llegó en 1.64 (2026-09-15), funciones cacheadas incluidas.

NiceGUI ha sido FastAPI/Starlette/Uvicorn desde siempre y puede montarse en una app FastAPI existente para que la API y la UI compartan un proceso. El punto de integración documentado es `ui.run_with(app)` (revisa la sección Configuration and deployment de los docs de NiceGUI para la firma exacta en tu versión).

<Notice type="info" title="Ambos frameworks corren sobre ASGI en 2026">
El viejo argumento "Streamlit no tiene backend real" está desactualizado. El diferenciador es el modelo de autoría, no el servidor debajo. Elige por cómo quieres escribir la app, no por qué stack HTTP trae.
</Notice>

### Funciones en tiempo real

Streamlit actualiza en interacción: un cambio de widget reejecuta el script (o el fragment). Desde 2026 puedes apuntar las reejecuciones con más precisión, pero el modelo sigue siendo pull-en-interacción. Suficiente para filtros, drilldowns y dashboards que se refrescan cuando un usuario hace clic.

NiceGUI es el ajuste natural para paneles de monitorización y control. `ui.timer` sondea o empuja, cada cliente mantiene su propio estado, y los handlers actualizan elementos individuales. Contadores en vivo, colas de logs, controles IoT y UIs de "la página se actualiza sin que yo la toque" son el comportamiento por defecto, no un workaround.

### Curva de aprendizaje

Streamlit sigue siendo el camino más amigable hacia las apps web en Python. Si puedes escribir un script con pandas, puedes enviar un dashboard en una tarde. No escribes HTML ni callbacks, y no hay máquina de estado que gestionar.

NiceGUI es ligeramente más empinado. Necesitas entender event handlers, cuándo usar `ui.clear()`, y cómo funciona el estado por cliente. Conocimiento básico de HTML/CSS ayuda con el layout. Devuelve ese coste en el momento en que construyes algo con más de unas pocas interacciones.

Ambos requieren ahora Python >= 3.10 (`requires_python` en PyPI, comprobado 2026-10-07). En una imagen base vieja, la instalación falla antes de que escribas una línea de código.

### Comunidad y recursos

Estrellas de GitHub al 2026-10-07: Streamlit 45.909, Gradio 43.677, Reflex 28.937, Dash 24.442, Flet 17.263, NiceGUI 16.269. Las descargas y estrellas no son calidad, pero sí predicen lo rápido que encuentras una respuesta en Stack Overflow.

Streamlit publica cada 4 a 6 semanas y tiene un gran ecosistema de ejemplos, más Streamlit Community Cloud para publicación gratis. NiceGUI está activo (58 issues abiertos en la última comprobación) con la línea 3.x madurando hacia una 4.0 ya anunciada en notas de versión. Su comunidad es más pequeña y enfocada al autoalojamiento. Leerás los docs más y Stack Overflow menos.

### Licencia y coste

Streamlit es Apache-2.0 y pertenece a Snowflake desde 2022. El paquete OSS sigue siendo Apache; "Streamlit in Snowflake" es el camino comercial. NiceGUI es MIT, mantenido por Zauberzeug (independiente), sin tier de pago.

## Autenticación en 2026

El viejo consejo era "Streamlit no tiene auth, NiceGUI necesita patrones FastAPI". La mitad de eso ahora está mal. Streamlit envió OIDC de primera mano en 1.42 (2025-02-04) y `st.user.tokens` en 1.53 (2026-01-14). La historia de NiceGUI no ha cambiado: montas la auth tú mismo, y posees el stack de sesión.

### OIDC integrado de Streamlit (`st.login()` / `st.logout()`)

`st.login()` redirige a cualquier proveedor OIDC que configures (Google, Okta, Auth0, Keycloak, lo que hable OIDC). `st.user` te da los claims tras la redirección; `st.user.tokens` expone los tokens OIDC crudos si necesitas llamar a APIs downstream. La configuración vive en `.streamlit/secrets.toml`. Los docs sobre la forma exacta de los secrets se han movido, así que copia de la página actual de auth de Streamlit en vez de un tutorial viejo.

### Patrón middleware + `app.storage.user` de NiceGUI

NiceGUI documenta un patrón de autenticación construido sobre middleware, `app.storage.user`, y un `storage_secret`. Cableas tú la comprobación de login, guardas la identidad del usuario en almacenamiento por usuario, y rediriges a los clientes no autenticados. Cuando montas NiceGUI en tu propia app FastAPI, puedes usar en su lugar el middleware de auth o la inyección de dependencias que ya corras. Más montaje, pero posees el stack de sesión y auth de extremo a extremo.

Los dos patrones como formas mínimas de código:

<Tab name="Streamlit OIDC">

```python
import streamlit as st

if not st.user.is_logged_in:
    st.login()  # redirects to your OIDC provider
else:
    st.write(f"Hello, {st.user.name}")
    # st.user.tokens has the raw OIDC tokens (since 1.53)
    st.button("Log out", on_click=st.logout)
```

```python
from nicegui import ui, app

# storage_secret comes from ui.run(storage_secret='change-me-to-a-long-random-string')
# and is required before app.storage.user works.

@ui.page('/private')
def private_page():
    if not app.storage.user.get('authenticated', False):
        ui.navigate.to('/login')
        return
    ui.label(f"Hello, {app.storage.user.get('username')}")

# Wire the actual login check in middleware (see NiceGUI docs,
# Authentication section) or use FastAPI auth when mounted via ui.run_with(app)
```

## Cuándo elegir cada framework

"Streamlit vs NiceGUI cuál es mejor" es la pregunta equivocada. Cuál encaja en el proyecto es la correcta. Esta es la división que uso.

### Elige Streamlit si...

Streamlit es el camino más rápido del notebook al dashboard compartido.

<ListCheck>
<ul>
<li>Necesitas dashboards de datos con gráficos, tablas y filtros, y el trabajo tiene forma de pandas o SQL</li>
<li>Estás construyendo demos de modelos ML o prototipos internos y los quieres públicos hoy</li>
<li>Quieres prototipado rápido con código mínimo y sin background de desarrollo web</li>
<li>Compartir importa más que el pulido (Streamlit Community Cloud saca un link en minutos)</li>
<li>Estás cableando una herramienta de IA o datos y quieres que la capa UI se quede aburrida: por ejemplo [usa la API gratis de Groq en tu app Streamlit](https://www.bitdoze.com/groq-api-mistral-streamlit/) o [construye un escritor de artículos con IA con Streamlit](/es/equipo-escritura-agno-workflow/)</li>
<li>El despliegue está a un VPS de distancia: [despliega Streamlit en un VPS con Cloudflare Tunnels](https://www.bitdoze.com/streamlit-deploy-vps-cloudflare/)</li>
</ul>
</ListCheck>

Casos de uso de ejemplo: dashboard de analítica de ventas, demo de modelo de machine learning, explorador de datos financieros, visualización de datos de investigación.

### Elige NiceGUI si...

NiceGUI es la herramienta cuando el "dashboard" le crecen botones, formularios y usuarios.

<ListCheck>
<ul>
<li>Estás construyendo aplicaciones estilo escritorio en el navegador (paneles de administración, herramientas, controladores)</li>
<li>Las interacciones en tiempo real sin recargas son un requisito, no un nice-to-have</li>
<li>Necesitas layouts y componentes personalizados más allá de un set de widgets estándar</li>
<li>Quieres APIs y UI en la misma app, con control explícito sobre routing y auth</li>
<li>Múltiples usuarios operarán la app, no solo la mirarán</li>
<li>Quieres primero un recorrido guiado: [tutorial de NiceGUI para principiantes](/es/empezar-nicegui/)</li>
</ul>
</ListCheck>

Casos de uso de ejemplo: herramientas de gestión de proyectos, controladores de dispositivos IoT, formularios y encuestas interactivas, sistemas de monitorización en tiempo real.

NiceGUI también corre como ventana de escritorio nativa (PySide6), un buen truco cuando la "app web" resulta ser una herramienta de escritorio interna.

### Cuándo ningún framework encaja

<Notice type="info" title="Límites honestos">
El CRUD multiusuario de larga vida con permisos complejos, sistemas de roles estrictos, o modelado relacional pesado pertenece a Django, FastAPI con plantillas, Reflex, o un framework JS full-stack. Tanto Streamlit como NiceGUI pelearán contigo en esa forma de problema. Y si necesitas una app móvil, ninguno de estos es la respuesta. Elige la opción aburrida y sigue adelante.
</Notice>

## Empezando: ejemplos de código

<Notice type="warning" title="Fija tus versiones">
Ambos frameworks requieren Python >= 3.10 (si el tuyo es más viejo, mira [cómo instalar y actualizar Python en Mac](https://www.bitdoze.com/install-upgrade-python-mac/)). Fija versiones en `requirements.txt` y recompila deliberadamente. NiceGUI 3.0 (2025-10-03) fue breaking y las deprecations de 4.0 ya están anunciadas. Streamlit elimina APIs deprecadas agresivamente (1.58 soltó `element.add_rows` y el callback handler de LangChain). No hagas `pip install -U` a ciegas en un contenedor de producción. Yo gestiono proyectos Python con uv; aquí está [cómo configurar un proyecto Python con uv](/es/empezar-uv/) si quieres el mismo flujo.
</Notice>

### Ejemplo Streamlit: dashboard de datos

```python
import streamlit as st
import pandas as pd

st.title("Sales Dashboard")

data = pd.DataFrame({
    "Month": ["Jan", "Feb", "Mar", "Apr"],
    "Sales": [100, 150, 120, 200],
})

month = st.selectbox("Select month", data["Month"])
filtered = data[data["Month"] == month]

st.bar_chart(data.set_index("Month"))
st.metric(f"Sales for {month}", f"${int(filtered['Sales'].iloc[0])}")

@st.fragment  # reruns only this block, not the whole script
def notes():
    if st.button("Add note"):
        st.session_state.notes = st.session_state.get("notes", []) + [month]

notes()
```

**Verifica:** instala y ejecútalo, luego comprueba que la app sirve.

```bash
pip install streamlit pandas
streamlit run app.py
```

Abre `http://localhost:8501`. Como sanity check antes de escribir nada, `streamlit hello` corre la app demo integrada. Si `curl -s http://localhost:8501/_stcore/health` imprime `ok`, el servidor está arriba.

**Modo de fallo:** `Port 8501 is already in use` significa que algo más posee el puerto. O lo paras o corres `streamlit run app.py --server.port 8502`.

### Ejemplo NiceGUI: formulario interactivo

```python
from nicegui import ui

def handle_submit():
    ui.notify(f"Hello {name.value}! You are {age.value} years old.")

ui.label("User Information Form")

with ui.row():
    name = ui.input("Name", placeholder="Enter your name")
    age = ui.number("Age", value=25, min=0, max=120)

ui.button("Submit", on_click=handle_submit)

ui.run(title="bitdoze demo")  # NiceGUI 3.x, Uvicorn under the hood, WebSocket UI sync
```

**Verifica:**

```bash
pip install nicegui
python main.py
```

Abre `http://localhost:8080`, envía el formulario, y confirma que la notificación toast aparece en la esquina inferior derecha. El terminal muestra la línea de arranque de Uvicorn; esa es tu pista de que el servidor está escuchando.

**Modo de fallo:** el error de instalación más común es `Requires-Python >=3.10` (o un error de resolución que lo mencione). La solución es un Python más nuevo, no un pip más nuevo.

### ¿Cuál es más fácil de aprender?

Streamlit gana para principiantes absolutos. Entra script lineal, sale app web. NiceGUI es accesible una vez que el modelo mental de callback más `ui.clear()` hace clic, y sigue pagando a medida que la app crece. Ambos necesitan Python >= 3.10. Si nunca has construido una app web, empieza con Streamlit un fin de semana, y luego mira NiceGUI cuando el modelo de reejecución empiece a molestarte.

### Setup de Docker y healthchecks

Un contenedor sin healthcheck es un contenedor que no puedes reiniciar con seguridad. Streamlit tiene un endpoint integrado. NiceGUI no, así que expones uno.

<Tabs>
<Tab name="Healthcheck Streamlit">

```dockerfile
FROM python:3.12-slim
WORKDIR /app
RUN apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8501
HEALTHCHECK CMD curl -f http://localhost:8501/_stcore/health || exit 1
CMD ["streamlit", "run", "app.py", "--server.port=8501", "--server.address=0.0.0.0"]
```

</Tab>
<Tab name="Healthcheck NiceGUI">

```python
# main.py
from fastapi import FastAPI
from nicegui import ui

app = FastAPI()

@app.get('/health')
def health():
    return {'ok': True}

@ui.page('/')
def index():
    ui.label('Hello from NiceGUI')

# Mount NiceGUI into the FastAPI app so /health and the UI share one process.
# Check the exact run_with signature in the NiceGUI docs for your version.
ui.run_with(app)
```

```dockerfile
FROM python:3.12-slim
WORKDIR /app
RUN apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8080
HEALTHCHECK CMD curl -f http://localhost:8080/health || exit 1
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8080"]
```

</Tab>
</Tabs>

<Notice type="info" title="Streamlit tiene un endpoint de salud real">
`GET /_stcore/health` devuelve `ok` y es el healthcheck de contenedor estándar para Streamlit (Streamlit Knowledge Base). NiceGUI no trae ruta de salud integrada, por eso el patrón de montaje FastAPI de arriba vale las cinco líneas extra. Revisa el nombre de la API `run_with` contra la sección Configuration and deployment de los docs de NiceGUI para tu versión fijada antes de hornearlo en una imagen.
</Notice>

Una forma mínima de archivo compose (recortada a las partes móviles):

```yaml
services:
  streamlit:
    build: ./streamlit-app
    ports:
      - "8501:8501"
    restart: unless-stopped
  nicegui:
    build: ./nicegui-app
    ports:
      - "8080:8080"
    restart: unless-stopped
```

**Verifica:**

```bash
curl -f http://localhost:8501/_stcore/health   # -> ok
curl -f http://localhost:8080/health          # -> {"ok": true}
docker ps                                     # STATUS column shows (healthy)
```

**Modos de fallo:** `curl: (7) Connection refused` dentro del contenedor normalmente significa que la app aún está arrancando o se enlazó a `127.0.0.1` en vez de `0.0.0.0`. `curl: (22)` desde el healthcheck significa que el endpoint dio 404, lo que en NiceGUI significa que la ruta FastAPI no está montada. `unhealthy` en `docker ps` con una app que funciona en el navegador es casi siempre un typo en la URL de salud.

Para un tratamiento más largo de correr apps Python en contenedores, mira [correr cualquier app Python en Docker con Docker Compose](https://www.bitdoze.com/docker-run-python/).

### Reverse proxy y notas WebSocket

El fallo número uno en el mundo real para ambos frameworks es una página en blanco o un spinner infinito detrás de un reverse proxy. Ambos síntomas significan lo mismo: el upgrade WebSocket no se está reenviando.

<Tabs>
<Tab name="Nginx">

```nginx
location / {
    proxy_pass http://streamlit:8501;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 86400;
}
```

</Tab>
<Tab name="Traefik">

```yaml
labels:
  - traefik.http.routers.streamlit.rule=Host(`app.example.com`)
  - traefik.http.services.streamlit.loadbalancer.server.port=8501
  # Traefik forwards WebSocket upgrades by default.
  # Raise forwardAuth/response timeouts if you see idle sockets drop.
```

</Tab>
<Tab name="Caddy">

```
app.example.com {
    reverse_proxy streamlit:8501
    # Caddy forwards WebSocket upgrades without extra config
}
```

</Tab>
</Tabs>

**Verifica:** abre la app a través de la URL del proxy, no del puerto del contenedor. Dev tools del navegador, pestaña Network: la petición WebSocket debería mostrar estado 101 (Switching Protocols). Un estado 200 o 400 en esa petición es tu upgrade fallando.

**Modos de fallo:**

- Página en blanco, sin errores en el log de la app: headers `Upgrade`/`Connection` faltantes (Nginx sin el bloque `proxy_http_version 1.1` de arriba).
- La app carga, luego el spinner nunca se resuelve: un idle timeout está matando el socket. Sube `proxy_read_timeout` o el equivalente en Traefik.
- Streamlit 1.60 (2026-07-21) envió hardening de seguridad breaking: comprobaciones de origen y host-message (CWE-346), límites de query string a 512 KiB / 1.000 campos, y `server.maxWidgetStateSize` (por defecto 25 MB). Si corres Streamlit detrás de un proxy con manejo no estándar de `Host` o `X-Forwarded-Host`, lee esa nota de versión antes de actualizar y prueba en tu propio stack. Un setup estándar de Caddy o Traefik no debería verse afectado, pero la reescritura inusual de headers es exactamente lo que esas comprobaciones buscan.

<Notice type="error" title="No corras un NiceGUI 3.x viejo en un endpoint público">
NiceGUI 3.16 y 3.17 enviaron correcciones de seguridad que quieres: un bug de agotamiento de memoria al desconectar sockets (GHSA-46f2-xhpw-8vh3, ago 2026), un XSS vía inyección de props (GHSA-955g-h32v-mvrr), y rutas `ui.download` de un solo uso inadivinables (GHSA-p92q-2755-mhgh, sep 2026). Actualiza al menos a 3.17.1 antes de que la app sea alcanzable desde internet. Este es también el argumento para fijar versiones: fija, luego sube deliberadamente.
</Notice>

### Notas de coste y recursos

Números de orden de magnitud, porque es donde la gente se sorprende:

- Ambas apps se autoalojan en un VPS pequeño (2 vCPU, 2-4 GB RAM, unos 5 EUR/mes). Ninguna necesita base de datos. Un [VPS de Hostinger](https://go.bitdoze.com/hostinger-vps) es una alternativa económica con almacenamiento NVMe si quieres más disco para cargas de datos.
- Streamlit mantiene el estado por proceso de sesión. La RAM escala con las sesiones concurrentes, no solo con el código. Si veinte personas abren tu dashboard, presupuesta para veinte sesiones. Esta es la consideración real de dimensionado del VPS.
- NiceGUI también mantiene estado por cliente en el worker. Los despliegues multi-worker tienen caveats (documentados en los docs de NiceGUI), así que lee eso antes de escalar horizontalmente.
- Streamlit Community Cloud: gratis, pero con hibernación a las 12 horas más límites de recursos, como se cubrió arriba. Bien para demos. Para herramientas internas siempre-encendidas, autoaloja.
- Fija tus tags de imagen y versiones de paquetes. NiceGUI 3.0 fue breaking y las deprecations de 4.0 ya están anunciadas; Streamlit elimina APIs deprecadas cada pocas versiones.
- Ruta de rollback: guarda el tag de imagen anterior. Si una subida rompe la app, `docker compose` up del tag viejo. Ese es todo el plan de deshacer, y funciona.

Si quieres la ruta con forma de PaaS en vez de Compose crudo, [despliega un proyecto Python uv con Dokploy](/es/dokploy-python-railpack-uv/). ## FAQ Streamlit vs NiceGUI

<Accordion label="¿Es NiceGUI más rápido que Streamlit?" group="faq" expanded="true">
No es una pregunta de velocidad sí/no, porque los modelos de ejecución difieren. NiceGUI actualiza solo los elementos tocados por el event handler. Streamlit reejecuta el script (o un fragment) y difiere la UI, así que el trabajo pesado al inicio del archivo duele hasta que lo cacheas o fragmentas. Mide en tu carga de trabajo, pero para UIs con mucha interacción el modelo de NiceGUI hace menos trabajo redundante por defecto.
</Accordion>

<Accordion label="¿Puede Streamlit manejar apps multi-página y formularios?" group="faq">
Sí. Streamlit tiene apps multi-página, fragments y session state, y puedes construir formularios reales con ellos. Donde se resiente es en UIs estilo app con muchos botones, formularios y usuarios concurrentes: ahí es donde el modelo orientado a eventos de NiceGUI mantiene el código más simple y el navegador respondiendo.
</Accordion>

<Accordion label="¿Funciona NiceGUI con FastAPI?" group="faq">
Sí. NiceGUI está construido sobre FastAPI y puede montarse en una app FastAPI existente para que tus rutas API y la UI compartan un proceso. El punto de integración documentado es `ui.run_with(app)`; comprueba la firma exacta en los docs de NiceGUI para tu versión fijada. También puedes mantenerlos separados y correr NiceGUI standalone con `ui.run()`.
</Accordion>

<Accordion label="¿Necesito Docker para autoalojar cualquiera de los frameworks?" group="faq">
No. `streamlit run app.py` y `python main.py` funcionan bien en un VPS pelado detrás de Nginx o Caddy. Pero un contenedor más un reverse proxy es el camino aburrido y fiable: builds reproducibles, healthchecks, políticas de reinicio, y un rollback de una línea al tag de imagen anterior. Si quieres el enfoque de contenedor, mira [cómo correr cualquier app Python en Docker con Docker Compose](https://www.bitdoze.com/docker-run-python/).
</Accordion>

<Accordion label="¿Es Streamlit gratis para uso comercial?" group="faq">
Sí. Streamlit es Apache-2.0; puedes construir y vender apps comerciales sobre él. El camino de pago es Streamlit in Snowflake, no el paquete OSS. Streamlit Community Cloud tiene un tier gratis con hibernación tras 12 horas y límites de recursos. El autoalojamiento no tiene coste de licencia ni para Streamlit ni para NiceGUI (NiceGUI es MIT), solo tu factura de servidor.
</Accordion>
