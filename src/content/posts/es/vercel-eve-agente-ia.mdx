Eve es un framework open source (Apache-2.0) para agentes de IA durables, y cada parte del agente es un archivo: las instrucciones en `agent/instructions.md`, las herramientas en `agent/tools/`, los canales en `agent/channels/`. Un comando genera el proyecto y abre una interfaz de terminal: `npx eve@latest init my-agent`. El [repositorio de GitHub](https://github.com/vercel/eve) data de junio de 2026.

La forma más fácil de describirlo es "Next.js, pero para agentes". Eve lee esa estructura de carpetas y la convierte en un agente en ejecución que funciona en local, sirve HTTP y mantiene una conversación viva a lo largo de muchos turnos.

He construido agentes con varios frameworks distintos, y lo que me convenció aquí es lo poca ceremonia que hay. Puedes leer un proyecto de Eve completo con solo mirar el árbol de directorios. Eso es todo. Sin registro que mantener sincronizado, sin archivo de cableado que quede desactualizado.

En esta guía generaremos un agente desde cero, le daremos una herramienta, lo conectaremos a Slack y Discord y cambiaremos el modelo por defecto por uno open source. El último paso lo despliega, ya sea en Vercel o en tu propio VPS con Dokploy. Los comandos se comprobaron contra eve 1.5.0 el 28 de noviembre de 2026.

<Notice type="info" title="Fija tu versión de Eve">
  Este artículo sigue eve 1.5.0, publicado el 25 de noviembre de 2026. Eve 1.0 renombró la mayoría de los eventos de sesión y varias APIs de canal, así que fija la versión en `package.json` y lee el changelog en `node_modules/eve/CHANGELOG.md` antes de actualizar. La documentación completa viene dentro del paquete en `node_modules/eve/docs/` y coincide exactamente con la versión instalada; [eve.dev/docs](https://eve.dev/docs/introduction) es la copia en línea.
</Notice>

## Qué es Vercel Eve

Eve es un framework open source para agentes durables escritos como archivos ordinarios en un proyecto TypeScript. Lo generas con un comando `npx` y despliegues la misma carpeta a Vercel o a un VPS.

"Durable" es la palabra que importa. Una sesión de Eve no es una petición y una respuesta. Puede emitir progreso en streaming mientras trabaja, llamar a herramientas y subagentes, pausarse para pedir aprobación a un humano, reanudarse cuando llega la respuesta y mantener el estado entre turnos. Internamente se apoya en el [Workflow SDK](https://workflow-sdk.dev/) open source para hacer las sesiones reanudables y resistentes a fallos, para que tu código pueda centrarse en el trabajo en lugar de la fontanería.

![Arquitectura de Eve: la carpeta del agente con instrucciones, agent.ts, herramientas, canales y conexiones alimenta el runtime de Eve, que habla con el proveedor de modelos, Slack, Discord, clientes HTTP y servicios externos](@assets/images/26/06/vercel-eve-ai-agent-architecture.webp)

*La carpeta del agente a la izquierda, el runtime de Eve en el medio y todo con lo que se comunica a la derecha.*

Así se ve un proyecto pequeño:

```text
my-agent/
├── package.json         # scripts: dev, build, start, typecheck, deploy
└── agent/
    ├── instructions.md   # who the agent is, how it behaves
    ├── agent.ts          # picks the model, runtime config
    ├── channels/
    │   ├── eve.ts        # the HTTP API and its auth policy (scaffolded)
    │   ├── slack.ts      # added with `eve add channel/slack`
    │   └── discord.ts    # added with `eve add channel/discord`
    ├── tools/            # typed functions the model can call
    │   └── get_weather.ts
    ├── skills/           # longer procedures, loaded on demand
    ├── connections/      # MCP servers and OpenAPI APIs
    ├── subagents/        # specialist child agents
    └── schedules/        # cron jobs
```

La ubicación de un archivo dice qué hace, y su ruta suele darle su nombre. Coloca `agent/tools/get_weather.ts` en su sitio y Eve descubre una herramienta llamada `get_weather`. Renombra el archivo y el nombre de la herramienta lo acompaña. Ese es todo el modelo mental.

<ListCheck>
- **`instructions.md`** le dice al agente quién es y cómo comportarse (el system prompt siempre activo)
- **`agent.ts`** elige el modelo y establece las opciones de ejecución
- **`tools/`** contiene funciones tipadas que el modelo puede llamar
- **`skills/`** contiene procedimientos más largos que el modelo solo carga cuando son útiles
- **`channels/`** contiene la API HTTP (`eve.ts`) y los adaptadores para Slack, Discord y otras plataformas de chat
</ListCheck>

Empieza con `instructions.md` y `agent.ts`. El scaffold también escribe `channels/eve.ts` con una política de autenticación de marcador de posición. Añade las demás carpetas cuando las necesites.

## Requisitos previos

Antes de generar nada, asegúrate de tener:

<ListCheck>
- **Node 24 o superior**, que incluye npm. El scaffold de 1.5.0 escribe `"node": "26.x"` bajo `engines`; en Node 24.17 npm imprime un aviso EBADENGINE, y la instalación, typecheck, build y servidor de desarrollo funcionaron todos
- **Una credencial de modelo**: una suscripción a ChatGPT, una cuenta de Vercel, o una clave de AI Gateway, OpenAI o Anthropic. No necesitas un proyecto de Vercel para empezar a chatear
</ListCheck>

El scaffold configura `openai/gpt-6-luna-fast` con `reasoning: "high"`, enrutado a través del Vercel AI Gateway. Cuando no hay ninguna credencial, la interfaz de terminal abre `/login` para añadir una, y `/model` cambia el modelo o el esfuerzo de razonamiento.

## Paso 1: Genera tu primer agente

`npx` puede ejecutar `eve init` sin instalar nada antes:

```bash
npx eve@latest init my-agent
```

Ese comando crea el proyecto, instala las dependencias, inicializa Git, arranca el servidor de desarrollo y abre una interfaz de terminal interactiva. Escribe un mensaje y verás el bucle del modelo ejecutándose en tiempo real.

![Terminal con la salida del scaffold de eve 1.5.0, el informe de eve info con 0 errores y los archivos bajo agent/](@assets/images/26/06/vercel-eve-ai-agent-terminal-scaffold.webp)

*Un scaffold nuevo en eve 1.5.0: `eve info` informa de 0 errores y lista los archivos descubiertos.*

Un par de cosas que conviene saber:

<ListCheck>
- Pasa `-n` (`--non-interactive`) para generar el proyecto sin abrir la interfaz de terminal, `--model <provider/model-id>` para elegir el modelo, o `--agents support,research` para un espacio de trabajo con varios agentes
- `eve init` retiene la terminal, así que pulsa `Ctrl+C` para recuperar tu shell antes de empezar a editar archivos
- Para añadir Eve a un proyecto que ya tienes, ejecuta `eve init .` desde una carpeta que tenga un `package.json` y aún no tenga archivos `agent/`. Añade `eve`, `ai` y `zod` sin tocar el resto
</ListCheck>

Si prefieres conectarlo a mano, instala las tres dependencias y declara un engine de Node. La documentación de 1.5.0 dice que fijes Node 26:

```bash
npm install eve@latest ai zod
```

```json
{
  "engines": {
    "node": "26.x"
  }
}
```

Después escribe los dos archivos que Eve necesita. `agent/instructions.md`:

```md
You are a concise assistant. Use tools when they are available.
```

Y `agent/agent.ts`:

```ts
import { defineAgent } from "eve";

export default defineAgent({
  model: "openai/gpt-6-luna-fast",
});
```

Incluso con este tamaño el agente ya puede hacer trabajo real, porque el arnés por defecto incluye `bash`, `read_file`, `write_file`, `edit_file`, `web_fetch`, `web_search` y una herramienta de delegación `agent`. `npx eve info` lista lo que Eve descubrió.

<Notice type="info" title="Dejar que un agente de codificación haga la configuración">
  Si usas Claude Code, Cursor o una herramienta similar, pásale este prompt: "Configura un agente eve: lee la documentación de eve (incluida en `node_modules/eve/docs` una vez instalado eve), genera el scaffold con `npx eve@latest init <name>`, añade una herramienta tipada en `agent/tools/get_weather.ts`, ejecútalo con `npm run dev`, luego crea una sesión, haz streaming de ella y envía un mensaje de seguimiento". Una vez instalado `eve`, la documentación completa vive localmente en `node_modules/eve/docs/`, así que el modelo no tiene que adivinar una API que no conoce.
</Notice>

## Paso 2: Dale una herramienta al agente

Una herramienta es una acción tipada que el agente puede llamar: consultar una API, ejecutar una query, escribir un archivo. El nombre del archivo se convierte en el nombre de herramienta que ve el modelo, y tiene que ser snake_case. Crea `agent/tools/get_weather.ts`:

```ts
import { defineTool } from "eve/tools";
import { z } from "zod";

// El modelo ve esta herramienta como `get_weather`, por el nombre del archivo.
export default defineTool({
  description: "Get the current weather for a city.",
  inputSchema: z.object({ city: z.string().min(1) }),
  async execute({ city }) {
    return { city, condition: "Sunny", temperatureF: 72 };
  },
});
```

Las piezas de una herramienta:

<ListCheck>
- Un **slug de nombre de archivo** dentro de `agent/tools/`, que es el nombre que ve el modelo
- Una **`description`** escrita para el modelo, que le dice qué hace la herramienta
- Un **`inputSchema`**, un esquema de Zod (pasa `z.object({})` si no hay entrada)
- Una función **`execute(input, ctx)`**, síncrona o asíncrona, que hace el trabajo
</ListCheck>

Las herramientas se ejecutan en el runtime de tu app con acceso completo a `process.env`, no dentro del sandbox, así que pueden importar código compartido desde `lib/` y leer tus secretos directamente. Una cosa a tener en cuenta: un paso que se interrumpe a mitad de ejecución se vuelve a ejecutar al reanudar, así que haz que los efectos secundarios como cargos o emails sean idempotentes, o protégelos detrás de una aprobación (más sobre esto abajo).

## Paso 3: Ejecútalo y envía un mensaje

Una app generada con el scaffold tiene un script `dev`, y `eve dev` se recarga con cada cambio:

```bash
npm run dev
```

El servidor de desarrollo escucha en el puerto 2000 por defecto. Para un servidor en segundo plano, `npx eve dev --no-ui --port 55951` omite la interfaz de terminal e imprime una línea cuando está listo: `[DEV] ready at http://127.0.0.1:55951/`.

![Flujo de una petición: llega un mensaje, el canal comprueba quién llama, se ejecuta la llamada al modelo, una llamada a herramienta vuelve al modelo y la respuesta va al canal](@assets/images/26/06/vercel-eve-ai-agent-request-flow.webp)

*Un turno con los nombres de eventos de v27: el resultado de la herramienta alimenta la siguiente llamada al modelo, y Eve guarda un checkpoint después de cada paso.*

Toda app de Eve también expone la misma API HTTP. Inicia una sesión durable con `curl`:

```bash
curl -X POST http://127.0.0.1:2000/eve/v1/session \
  -H 'content-type: application/json' \
  -d '{"message":"What is the weather in Brooklyn?"}'
```

La respuesta es `202` con el id de sesión en el cuerpo y en la cabecera `x-eve-session-id`:

```json
{"ok":true,"sessionId":"wrun_01M8H47YXAXRZ994AVN90Z3CHA","deliveryId":"b30a7939-ae75-46f3-a382-0f37eda59814"}
```

Conéctate al stream con el id de sesión:

```bash
curl "http://127.0.0.1:2000/eve/v1/session/<sessionId>/stream?follow=true"
```

El stream es NDJSON. Para este turno verás `session.started`, `turn.started`, `model.requested`, `model.started`, `call.requested` (la llamada a la herramienta), `call.settled` (su resultado), `content.completed` (la respuesta), y después `turn.settled` y `delivery.settled`. Los nombres `actions.requested`, `action.result`, `message.completed` y `session.completed` pertenecen al stream v26 que Eve 1.0 reemplazó. Para continuar la conversación, envía un mensaje de seguimiento al mismo id de sesión:

```bash
curl -X POST http://127.0.0.1:2000/eve/v1/session/<sessionId> \
  -H 'content-type: application/json' \
  -d '{"message":"Now do Queens."}'
```

El mensaje de seguimiento solo necesita `message`. El campo `continuationToken` de versiones anteriores de Eve se rechaza con `Unknown field 'continuationToken'`.

El 28 de noviembre de 2026, una ejecución de laboratorio con eve 1.5.0 apuntó el agente a un mock local compatible con OpenAI en el puerto 55950. El primer turno hizo dos llamadas al modelo, una llamada a `get_weather`, y terminó en unos 0.2 segundos.

![Terminal con el servidor de desarrollo, la llamada de creación de sesión y los nombres de eventos del stream](@assets/images/26/06/vercel-eve-ai-agent-terminal-run.webp)

*Un turno real: el id de sesión vuelve de la llamada de creación, y el stream muestra la llamada a la herramienta y la respuesta.*

Ese es el hola mundo. Un bot del tiempo no le sirve a nadie, así que ahora el agente va a donde la gente ya trabaja.

## Paso 4: Conecta el agente a Slack

Un canal es el adaptador entre una plataforma y tu agente. Normaliza los mensajes entrantes, posee el token de reanudación para esa superficie y decide cómo se entregan las respuestas. El canal de Slack responde a `@mentions` y mensajes directos, contesta en hilos, muestra indicadores de escritura y convierte las peticiones de human-in-the-loop en botones de Slack.

La parte buena: las credenciales pueden pasar por [Vercel Connect](https://vercel.com/kb/guide/vercel-connect), que gestiona tanto el token de bot saliente como la verificación del webhook entrante. No hay ningún `SLACK_BOT_TOKEN` ni `SLACK_SIGNING_SECRET` en tu proyecto. Este paso necesita un espacio de trabajo de Slack del que seas administrador, así que sigue la [documentación de Slack](https://eve.dev/docs/channels/slack) y no se ejecutó aquí.

Ejecuta la configuración guiada desde el proyecto del agente y después despliega:

```bash
npx eve add channel/slack
npx eve deploy
```

La configuración te inicia sesión en Vercel, vincula un proyecto, crea o reutiliza una app de Slack a través de Connect, te pide instalarla en un espacio de trabajo y escribe el archivo de canal:

```ts
import { connectSlackCredentials } from "@vercel/connect/eve";
import { slackChannel } from "eve/channels/slack";

export default slackChannel({
  credentials: connectSlackCredentials("slack/my-agent"),
});
```

`connectSlackCredentials` devuelve el token de bot y el verificador de webhook, manteniendo la rotación de tokens y la verificación de peticiones dentro de Connect en lugar de en tu código. Para gestionar la app de Slack tú mismo, ejecuta `eve add channel/slack` y elige **Use portable credentials**. Eve entonces escribe un `slackChannel()` básico que lee `SLACK_BOT_TOKEN` y `SLACK_SIGNING_SECRET`, y tú añades los scopes `app_mentions:read`, `chat:write` e `im:history` en los ajustes de la app de Slack. Apunta Event Subscriptions a `https://<your-host>/eve/v1/slack`.

`eve deploy` instala las dependencias y ejecuta `vercel deploy --prod --logs`. Las guías antiguas, incluida la versión anterior de esta, reapuntaban a mano el trigger de Connect con `vercel connect detach` y `vercel connect attach --trigger-path /eve/v1/slack`. La referencia de 1.5 dice que no ejecutes `detach`, porque elimina el acceso al token del proyecto.

### Incorporar el contexto del hilo

Por defecto el canal te da la mención que lo activó, pero no las respuestas anteriores del hilo. Si quieres que el agente lea lo que se dijo antes de ser llamado, añade una opción:

```ts
import { connectSlackCredentials } from "@vercel/connect/eve";
import { slackChannel } from "eve/channels/slack";

export default slackChannel({
  credentials: connectSlackCredentials("slack/my-agent"),
  threadContext: { since: "last-agent-reply" },
});
```

`since: "last-agent-reply"` significa que menciones repetidas en un mismo hilo solo inyectan lo nuevo, así que no vuelves a alimentar todo el historial en cada turno. La opción necesita el scope de historial de Slack correspondiente, como `channels:history`. Para un filtrado personalizado, `loadThreadContextMessages` del mismo módulo sigue devolviendo los mensajes en bruto del hilo.

<Notice type="warning" title="Avisa a la gente de que está hablando con un bot">
  Eve no añade por ti un aviso de "soy una IA". Dependiendo de dónde estén tus usuarios, puede que estés legalmente obligado a revelar que están hablando con un sistema automatizado. Incorpóralo en tu `instructions.md` o en las respuestas del canal.
</Notice>

## Paso 5: Conecta el agente a Discord

Discord funciona a través de HTTP Interactions: comandos de barra, componentes de mensaje y modales. Discord impone un plazo de tres segundos para confirmar un comando, así que el canal verifica la firma, confirma de inmediato y ejecuta el trabajo real en segundo plano. No tienes que pensar en nada de eso; está resuelto.

Discord tiene los mismos dos caminos. `npx eve add channel/discord` pasa por Connect, apunta la Interactions Endpoint URL al trigger de Connect y registra `/ask` por ti. La ruta manual empieza con el `agent/channels/discord.ts` mínimo y un bot que creas en el Developer Portal; estos pasos vienen de la [documentación de Discord](https://eve.dev/docs/channels/discord) y no se ejecutaron aquí:

```ts
import { discordChannel } from "eve/channels/discord";

export default discordChannel();
```

Discord necesita tres variables de entorno:

```bash
DISCORD_PUBLIC_KEY=...      # verifies the signature headers
DISCORD_APPLICATION_ID=...  # edits the deferred response, sends followups
DISCORD_BOT_TOKEN=...       # proactive messages, fallback, typing indicators
```

La ruta es `POST /eve/v1/discord` por defecto. Pega esa URL pública en el campo Interactions Endpoint URL de tu aplicación de Discord en el Developer Portal.

Registrar los comandos es cosa tuya, no del canal. Una opción de tipo string llamada `message` coincide con la extracción de prompt por defecto de Eve:

```bash
curl -X PUT "https://discord.com/api/v10/applications/$DISCORD_APPLICATION_ID/commands" \
  -H "Authorization: Bot $DISCORD_BOT_TOKEN" -H "Content-Type: application/json" \
  -d '[{"name":"ask","description":"Ask the eve agent","type":1,
    "options":[{"name":"message","description":"What should the agent do?","type":3,"required":true}]}]'
```

Usa comandos de guild durante el desarrollo; se propagan mucho más rápido que los globales. Para subir archivos, añade una opción de adjunto llamada `file` junto a `message`. Aquí tienes un canal algo más completo que decide la autenticación por comando y publica la respuesta:

```ts
import { discordChannel } from "eve/channels/discord";

export default discordChannel({
  onCommand: (ctx, interaction) => ({
    auth: {
      principalId: interaction.user.id,
      principalType: "user",
      authenticator: "discord",
      attributes: { channel_id: interaction.channelId, guild_id: interaction.guildId ?? "" },
    },
  }),
  events: {
    "content.completed"(event, ctx) {
      if (event.data.phase !== "reply" || typeof event.data.value !== "string") return;
      return ctx.channel.discord.post(event.data.value);
    },
  },
});
```

Los archivos adjuntos funcionan en ambos canales: Slack prepara los archivos adjuntos a una mención, y Discord los recibe a través de la opción `file` del comando. Responder a mensajes directos, menciones y respuestas en hilo en Discord requiere más configuración, porque Discord solo envía eso por su Gateway WebSocket. Eve ejecuta un relé experimental para ello, y la documentación cubre cómo ejecutarlo dentro y fuera de Vercel.

Lo que me gusta es que la misma lógica de agente sirve a ambas plataformas. Tu herramienta `get_weather` no sabe ni le importa si la pregunta vino de Slack, Discord, la terminal o un navegador. Escribe el comportamiento una vez, expónlo en todas partes.

## Paso 6: Cómo usar modelos open source con Eve

Cambia una línea en `agent/agent.ts` y el agente se ejecuta en cualquier modelo que sirva el Vercel AI Gateway, o en un proveedor al que llamas directamente. El modelo del scaffold es `openai/gpt-6-luna-fast`, pero no estás casado con él.

En los últimos años aprendimos por las malas que un modelo del que dependes puede quedar obsoleto o desaparecer de un día para otro, así que poder cambiar importa. Eve convierte el modelo en una sola línea de configuración.

Tienes dos opciones de enrutado.

<Tabs>
<Tab name="Gateway (id de texto)">

Un id de modelo en forma de string se enruta a través del Vercel AI Gateway. Cambia el valor y ya estás usando otro modelo, sin más cambios:

```ts
import { defineAgent } from "eve";

export default defineAgent({
  // cualquier modelo que exponga el gateway
  model: "moonshotai/kimi-k2.6",
});
```

Esto funciona en Vercel con OIDC de proyecto, o en cualquier otro sitio con `AI_GATEWAY_API_KEY` definida. El Gateway es el camino con menos configuración: una clave, muchos modelos, y es fácil hacer A/B entre un modelo rápido y barato y uno más potente.

</Tab>
<Tab name="Proveedor directo">

Para saltarte el Gateway por completo, pasa una instancia de modelo de un paquete de proveedor del AI SDK y define la clave de ese proveedor. Eve también incluye los helpers `openai()` y `anthropic()` bajo `eve/models/` que leen `OPENAI_API_KEY` o `ANTHROPIC_API_KEY`. Para un endpoint local o compatible con OpenAI, `@ai-sdk/openai-compatible` es el camino más corto, y es lo que usó la ejecución de laboratorio del paso 3:

```bash
npm install @ai-sdk/openai-compatible
```

```ts
import { createOpenAICompatible } from "@ai-sdk/openai-compatible";
import { defineAgent } from "eve";

const local = createOpenAICompatible({
  name: "local-mock",
  baseURL: "http://127.0.0.1:55950/v1",
  includeUsage: true,
});

export default defineAgent({
  model: local("mock-model"),
  modelContextWindowTokens: 64_000,
});
```

Apunta la `baseURL` a Ollama, LM Studio, OpenRouter, Together, Groq o tu propio endpoint, y estarás ejecutando un modelo abierto con el mismo código de agente. Define `modelContextWindowTokens` con la longitud de contexto que asigna el servidor, porque el Gateway no guarda metadatos de un modelo que no sirve. Elige un modelo con llamada a herramientas nativa, ya que los agentes de Eve llaman a herramientas en la mayoría de los turnos. Para un modelo o un CLI de agente mantenidos dentro de un contenedor, mira la [guía para ejecutar herramientas de IA CLI de forma segura en Docker o Podman](/es/docker-podman-entorno-seguro-ia/). Para los precios actuales de los modelos, la [guía de modelos baratos para Hermes Agent](/es/mejores-modelos-baratos-hermes-agent/) tiene las cifras.

</Tab>
</Tabs>

¿Qué modelo abierto deberías elegir? Modelos como GLM-5.2, Kimi K2.6 y Qwen 3.6 se mantienen bien en trabajo agéntico de llamadas a herramientas por una fracción del coste de los modelos frontera. Profundicé en las ventajas e inconvenientes en mi guía de los [mejores LLMs open source para reemplazar a Claude](/es/mejores-llms-opensource-alternativa-claude/), así que consúltala si vas a elegir uno para una carga de trabajo real. La versión corta: enruta modelos baratos y rápidos a los turnos simples y guarda los caros para los problemas difíciles. Eve te permite hacer exactamente eso, incluso por subagente.

<Notice type="info" title="Enrutado de modelos por tarea">
  Como el modelo es solo configuración, puedes ejecutar subagentes en modelos distintos. Un subagente de investigación podría usar un modelo barato de contexto largo mientras el agente raíz se queda con algo más potente. Construyes la skill una vez y la enrutas donde tenga sentido.
</Notice>

## Paso 7: Añade herramientas de servicios externos con conexiones

Más allá de las herramientas que escribes, Eve puede incorporar herramientas de servidores MCP externos y documentos OpenAPI. Estas viven en `agent/connections/`, y el modelo nunca ve la URL ni las credenciales: descubre las herramientas y las llama por su nombre.

Una conexión al servidor MCP de Linear se ve así:

```ts
import { defineMcpClientConnection } from "eve/connections";

export default defineMcpClientConnection({
  url: "https://mcp.linear.app/mcp",
  description: "Linear workspace: issues, projects, cycles, and comments.",
  auth: {
    getToken: async () => ({ token: process.env.LINEAR_API_TOKEN! }),
  },
});
```

Para cualquier cosa que toque dinero, borre datos o envíe mensajes, protégela detrás de una aprobación. Los helpers viven en `eve/tools/approval`: `never()` es el valor por defecto, `once()` pregunta la primera vez en una sesión y `always()` pregunta cada vez. Con `auto()`, un modelo de decisión solo pregunta por las llamadas arriesgadas. El mismo flujo de pausa y reanudación que impulsa las herramientas human-in-the-loop se encarga de ello. Los elementos listos para usar viven en un registro: `npx eve registry search linear` los encuentra y `npx eve add connection/linear` instala uno.

## Paso 8: Despliégalo

Ya tienes un agente funcionando. Ahora necesita vivir en algún sitio. Eve se ejecuta igual en local, en Vercel y en un host de Node normal, así que pasar a producción es casi todo mecánico. Si todavía lo estás sopesando contra otro framework, la [comparativa Mastra vs Eve](/es/mastra-vs-eve-agentes-ia-typescript/) cubre las diferencias.

![Rutas de despliegue comparadas: eve build alimenta Vercel con eve deploy, Vercel Workflow y Sandbox, o un VPS con eve start, un almacén de workflows local, un sandbox de Docker y dos prefijos de proxy](@assets/images/26/06/vercel-eve-ai-agent-deploy-paths.webp)

*La misma salida de `eve build` va a Vercel o a un VPS; cada camino necesita una configuración distinta de almacén de sesiones, sandbox, credenciales y proxy.*

### Opción A: Desplegar en Vercel

`eve build` compila el agente y escribe la salida del host. En Vercel eso es el bundle de Build Output en `.vercel/output`, más los artefactos compilados en `.eve/`. Vincula el proyecto una vez y después despliega desde la raíz del proyecto:

```bash
npx eve link
npx eve deploy
```

`eve link` descarga el entorno del proyecto, así que una credencial de AI Gateway acaba en `.env.local`. También puedes hacer push a un proyecto conectado a Git.

![Terminal con la configuración del agente de laboratorio, npm run typecheck pasando y eve build imprimiendo una salida de 9.49 MB](@assets/images/26/06/vercel-eve-ai-agent-terminal-build.webp)

*El agente de laboratorio: `npm run typecheck` pasa y `eve build` escribe un servidor de 9.49 MB en `.output/` en unos 3 segundos (build local, sin la variable `VERCEL`).*

Antes de esa primera petición de producción, recorre esta checklist corta:

<ListCheck>
- Define una **credencial de modelo** y cualquier **secreto de autenticación de rutas** en el entorno de despliegue, nunca en el código
- Sustituye el `placeholderAuth()` del scaffold por una política de autenticación real (Basic, JWT, OIDC o un verificador propio) de la [documentación de autenticación](https://eve.dev/docs/guides/auth-and-route-protection); una app sin configurar falla en cerrado y rechaza el tráfico del navegador, que es el comportamiento seguro por defecto
- Confirma que el **backend del sandbox** coincide con el entorno (Vercel Sandbox en Vercel, Docker u otro proveedor en cualquier otro sitio)
</ListCheck>

Una vez desplegado, la plataforma detecta Eve automáticamente y muestra una pestaña Agent Runs en la vista de Observability de tu proyecto, donde puedes explorar sesiones y leer la traza de cada conversación.

Eve en sí es Apache-2.0 y gratis. En Vercel pagas por lo que usa el agente: tokens de Workflow, Sandbox y AI Gateway. El nivel gratuito del Gateway incluye un crédito de $5 al mes y vende tokens al precio de lista del proveedor sin recargo ([precios de AI Gateway](https://vercel.com/docs/ai-gateway/pricing), comprobado el 28 de noviembre de 2026). Las páginas de precios de Workflow y Sandbox muestran sus cifras en el navegador, así que consulta [Workflows](https://vercel.com/workflows/pricing) y [Sandbox](https://vercel.com/sandbox/pricing) para las tarifas actuales.

### Opción B: Autoalojar en tu propio VPS

Si prefieres no atarte a la plataforma de Vercel, Eve se ejecuta como un servicio de Node normal detrás de tu propio gestor de procesos o proxy inverso:

```bash
eve build
PORT=3000 eve start --host 0.0.0.0
```

Fuera de Vercel, Eve escribe la salida estándar de Nitro en `.output/`, y el Workflow SDK usa su mundo local, que guarda el estado en `.eve/.workflow-data`. El sandbox se ejecuta en Docker cuando `eve build` puede alcanzar un daemon de Docker. Algunas cosas que conviene dejar claras al autoalojar:

<ListCheck>
- Coloca `.eve/.workflow-data` en **almacenamiento persistente** para que el estado de las sesiones sobreviva a los reinicios, y hazle backup junto con el resto de tus datos
- Usa un **modelo de proveedor directo** con `OPENAI_API_KEY` o `ANTHROPIC_API_KEY`, o mantén `AI_GATEWAY_API_KEY` si aún quieres el enrutado del Gateway
- Sustituye `vercelOidc()` por una autenticación que tu host pueda verificar
- Reenvía tanto **`/eve/`** como **`/.well-known/workflow/`** a través del proxy sin reescribir la ruta; con solo `/eve/`, una sesión arranca pero la ejecución se queda colgada
- Ten presente la versión de eve: un build nuevo sobre la misma versión mantiene las sesiones en marcha, una actualización de eve las deja inservibles
- Si tu agente usa tareas programadas, ejecútalas en un solo proceso (`eve start --no-schedules` en los demás), o lanza el mismo trabajo desde tu propio cron
</ListCheck>

La forma más limpia que he encontrado de ejecutar un servicio de Node como este en un VPS es [Dokploy](/es/instalar-dokploy/), una alternativa open source y autoalojable a Vercel y Heroku. Te da despliegues basados en Git, HTTPS automático vía Traefik, gestión de variables de entorno y logs, todo desde un panel que controlas tú. Mi [guía de instalación de Dokploy](/es/instalar-dokploy/) cubre cómo ponerlo en marcha en un servidor nuevo.

El flujo de despliegue de un agente Eve se corresponde casi exactamente con el de una app de Node normal, así que si ya has desplegado algo con Dokploy, esto te resultará familiar. Mi tutorial sobre [desplegar TanStack Start en un VPS con Dokploy](/es/desplegar-tanstack-start-dokploy/) muestra el patrón completo (comando de build, comando de arranque, variables de entorno, dominio). Los mismos pasos aplican aquí: define el comando de build como `npm run build` (que ejecuta `eve build`), el de arranque como `eve start --host 0.0.0.0`, expón el puerto y añade tus secretos de modelo y autenticación en el panel de entorno. Un punto delicado: un paso `RUN npm run build` de un Dockerfile no tiene daemon de Docker, así que el build no registra ningún sandbox. Selecciona `DockerSandbox.environment()` en `agent/sandbox.ts` para esa configuración, según la [documentación de autoalojamiento](https://eve.dev/docs/guides/deployment/self-hosting). Para un primer proyecto más pequeño con el mismo stack, el [tutorial de la app de tareas con TanStack Start](/es/tanstack-start-bunny-database-drizzle/) usa Drizzle y Bunny Database.

<Notice type="success" title="Por qué autoalojar el agente">
  Ejecutarlo en tu propio VPS significa que tus datos de conversación y credenciales se quedan en infraestructura que controlas, los costes son predecibles y no estás expuesto a cambios de precios de la plataforma. El contrapunto es que tú te encargas de los backups, el escalado y el almacenamiento persistente de `.workflow-data`.
</Notice>

### Verifica el despliegue

Tomaras el camino que tomaras, haz una prueba de humo de las rutas en vivo: primero el health, luego un turno real. La ruta de health es pública; la ruta de sesión sigue tu política de autenticación. Una ejecución de laboratorio del build de producción el 28 de noviembre de 2026 respondió `{"ok":true,"status":"ready"}` en health y `401 unauthorized` en una sesión sin autenticar. Ese es el resultado esperado mientras `placeholderAuth()` siga en su sitio:

```bash
curl https://<your-app>/eve/v1/health

curl -X POST https://<your-app>/eve/v1/session \
  -H 'content-type: application/json' \
  -d '{"message":"Hello from production"}'
```

También puedes manejar el despliegue en vivo con la terminal de desarrollo, lo cual viene bien para una comprobación rápida en producción:

```bash
npx eve remote connect --url https://<your-app>
npx eve remote connect --url https://<your-app> --print "Hello from production"
```

La segunda forma envía un mensaje, imprime la respuesta final y sale con un código distinto de cero si el turno falla.

## Qué construir después

El bot del tiempo era solo una forma de ver el bucle en marcha. Lo interesante es lo que pones en `tools/` y `skills/`. Un agente de reutilización de contenido que redacta posts sociales y llama a herramientas de generación de imágenes. Un agente de investigación de leads que extrae datos de tu CRM. Un bot de triaje de soporte viviendo en tu Slack. El andamiaje es siempre el mismo, que es justo la idea: dejas de reinventar el arnés y dedicas tu tiempo a la capacidad real.

<ListCheck>
- Añade una **skill** en `agent/skills/` para cualquier procedimiento de varios pasos que el modelo deba cargar solo cuando sea relevante
- Levanta **subagentes** para trabajo en paralelo o especializado, cada uno con su propio modelo
- Añade **tareas programadas** para trabajos recurrentes como un resumen diario
- Pon un **front end en Next.js** delante del agente con el hook `useEveAgent`
</ListCheck>

## Para cerrar

Eve toma la parte de la construcción de agentes que suele ser un lío (canales, estado durable, enrutado de modelos, despliegues) y la convierte en una carpeta que puedes leer de arriba abajo. Generas el scaffold con un comando, añades una herramienta como un único archivo, apuntas un canal a Slack o Discord y eliges el modelo que encaje con el trabajo y tu presupuesto. Despliégalo en Vercel para el camino de cero configuración, o autoalójalo en un VPS con Dokploy cuando quieras ser dueño de todo el stack.

Si vienes de otro framework, el cambio casi no te cuesta nada, ya que tus herramientas y skills son TypeScript y Markdown planos que puedes llevarte a otra parte. Empieza con el hola mundo del tiempo y luego reemplázalo por algo que tu equipo usaría de verdad.

## Preguntas frecuentes

<Accordion label="¿Es Vercel Eve gratis y open source?" group="faq" expanded="true">
Sí. Eve es open source bajo Apache-2.0 y vive en [GitHub](https://github.com/vercel/eve). Puedes ejecutarlo enteramente en tu propia infraestructura con tus propias claves de modelo. Las comodidades opcionales (AI Gateway, Sandbox alojado, Vercel Connect, el panel Agent Runs) son funciones de la plataforma Vercel a las que puedes adherirte, no requisitos.
</Accordion>

<Accordion label="¿Necesito una cuenta de Vercel para usar Eve?" group="faq">
No. Necesitas una credencial de modelo, que puede ser una suscripción a ChatGPT o una clave directa de proveedor como `ANTHROPIC_API_KEY` u `OPENAI_API_KEY`. Una cuenta de Vercel facilita el AI Gateway, las credenciales de Slack vía Connect y los sandboxes alojados. También puedes autoalojar todo en un VPS con Dokploy y nunca vincular un proyecto de Vercel.
</Accordion>

<Accordion label="¿Qué versión de Node y qué puerto necesita Eve?" group="faq">
Eve requiere Node 24 o superior, y el scaffold de 1.5.0 fija `"node": "26.x"` bajo `engines`. `eve dev` escucha en el puerto 2000 y `eve start` en el puerto 3000, y ambos aceptan `--port`. Para un servidor en segundo plano, pasa `--no-ui`, que omite la interfaz de terminal e imprime una línea cuando está listo.
</Accordion>

<Accordion label="¿Puede un agente atender Slack y Discord al mismo tiempo?" group="faq">
Sí. Añade tanto `agent/channels/slack.ts` como `agent/channels/discord.ts`, con `eve add channel/slack` y `eve add channel/discord`. Las instrucciones, herramientas y skills del agente se comparten; cada canal solo adapta la entrada y salida de su plataforma. Tus herramientas no necesitan saber de qué superficie vino un mensaje.
</Accordion>

<Accordion label="¿Puedo usar modelos open source en lugar del predeterminado?" group="faq">
Sí. Cambia el valor de `model` en `agent/agent.ts`. Usa un id de texto de gateway como `moonshotai/kimi-k2.6`, o instala un proveedor del AI SDK y apunta su `baseURL` a OpenRouter, Together, Groq o un endpoint autoalojado. Para un servidor local, `@ai-sdk/openai-compatible` funciona con Ollama, LM Studio, llama.cpp y vLLM. Mira mi [comparativa de LLMs open source](/es/mejores-llms-opensource-alternativa-claude/) para elegir uno.
</Accordion>

<Accordion label='¿Qué significa "durable" para una sesión de Eve?' group="faq">
Una sesión puede emitir progreso en streaming, llamar a herramientas y subagentes, pausarse para pedir aprobación humana, reanudarse cuando llega la respuesta y mantener el estado a lo largo de muchos turnos. Está construida sobre el Workflow SDK open source, que hace las ejecuciones reanudables y resistentes a fallos. Un paso completado nunca se reejecuta; un paso interrumpido sí, así que haz que los efectos secundarios sean idempotentes.
</Accordion>

<Accordion label="¿Por qué se rechaza mi mensaje de seguimiento por un campo desconocido?" group="faq">
Eve 1.0 eliminó `continuationToken` de la API HTTP y renombró los eventos del stream de v26 a v27. Un mensaje de seguimiento ahora envía `{"message":"..."}` a `/eve/v1/session/<sessionId>`, y el stream informa de `call.requested`, `call.settled`, `content.completed` y `turn.settled`. El servidor responde `Unknown field 'continuationToken'` con la forma antigua.
</Accordion>

<Accordion label="¿Qué necesita el autoalojamiento que Vercel hace por ti?" group="faq">
Cuatro cosas: almacenamiento persistente para `.eve/.workflow-data`, Docker en el host cuando el agente usa las herramientas de shell y archivos, una política de autenticación de rutas que tu host pueda verificar en lugar de `vercelOidc()`, y un proxy que reenvíe `/eve/` y `/.well-known/workflow/`. En Vercel, Vercel Workflow y Vercel Sandbox proporcionan las dos primeras por defecto.
</Accordion>
