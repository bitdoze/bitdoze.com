### Instalar Docker

Si aún no tienes Docker, usa el script de conveniencia de Docker. Detecta la distro y configura el repo correcto:

```bash
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER
# log out and back in for the group to apply
```

Verifica tanto el engine como el plugin de Compose:

```bash
docker version
docker compose version
```

Roto se ve como `permission denied while trying to connect to the Docker daemon socket`. Eso significa que la membresía del grupo aún no se ha aplicado. Vuelve a iniciar sesión, no lo pelees con `sudo` para siempre. Recorrido completo: [Instalar Docker y Docker-compose para Ubuntu](/install-docker-ubuntu-arm/).

## Instalar Arcane con Docker Compose

Hay dos formas de instalar Arcane. El script de conveniencia es el más rápido, pero prefiero el método compose porque puedes ver y controlar exactamente lo que está pasando.

### Instalación rápida (script de conveniencia)

Si quieres tenerlo corriendo en 30 segundos:

```bash
curl -fsSL https://getarcane.app/install.sh | sudo bash
```

<Notice type="info" title="Esto es una instalación nativa, no un contenedor">
El script de instalación configura Docker (si falta), descarga el binario nativo de Arcane desde GitHub Releases y registra un servicio systemd. Enlaza el binario a `/usr/local/bin/arcane`. No descarga una imagen de contenedor ni escribe un archivo compose por ti. Bueno para pruebas; usa Compose para una configuración permanente para que la config sea tuya.
</Notice>

Compruébalo:

```bash
systemctl status arcane
```

Luego abre `http://ip-de-tu-servidor:3552`. Para quitarlo después hay un desinstalador. Es interactivo, y `--force --remove-all` se llevará Docker con él, así que lee los prompts:

```bash
curl -fsSL https://getarcane.app/uninstall.sh | sudo bash
```

### Instalación con Docker Compose (recomendado)

Primero, crea un directorio para Arcane:

```bash
mkdir -p /opt/arcane
cd /opt/arcane
```

Genera la `ENCRYPTION_KEY`:

```bash
openssl rand -hex 32
```

Alternativas oficiales si prefieres el generador propio de Arcane:

```bash
docker run --rm ghcr.io/getarcaneapp/manager:latest /app/arcane generate secret
# or: arcane-cli generate secret
```

Ahora crea tu `compose.yaml`:

```yaml
services:
  arcane:
    image: ghcr.io/getarcaneapp/manager:v2
    container_name: arcane
    ports:
      - "3552:3552"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - arcane-data:/app/data
      - /opt/stacks:/opt/stacks
    environment:
      - APP_URL=http://localhost:3552
      - PUID=1000
      - PGID=1000
      - ENCRYPTION_KEY=your-generated-encryption-key
      - PROJECTS_DIRECTORY=/opt/stacks
      - TZ=Europe/Bucharest
    cgroup: host
    healthcheck:
      test: ["CMD", "./arcane", "health", "--timeout", "2s"]
      interval: 10s
      timeout: 3s
      retries: 5
      start_period: 15s
    restart: unless-stopped
    stop_grace_period: 15s
volumes:
  arcane-data:
```

Reemplaza `ENCRYPTION_KEY` con el valor que generaste. Configura `APP_URL` a la dirección real de tu servidor si accedes remotamente. La línea `cgroup: host` permite a Arcane detectar su propio ID de contenedor, lo que importa para las auto-actualizaciones.

Algunas notas sobre ese archivo:

- Fija la etiqueta de la imagen. `:v2` te da releases de parche en la línea 2.x. `:latest` puede sorprenderte un lunes por la mañana. El rollback es a la inversa: vuelve a fijar la etiqueta anterior (`v2.16.1` o la que tuvieras), luego `docker compose pull && docker compose up -d`. Mira [cómo actualizar un contenedor con Docker Compose](/updating-container-docker-compose/) para la danza completa.
- Las líneas `healthcheck` y `stop_grace_period: 15s` vienen de los ejemplos oficiales. El healthcheck le da a `depends_on` algo real en lo que apoyarse una vez que agregues un socket proxy.
- Montajes opcionales: `/builds` para el Build Workspace de Arcane (builds de imágenes) y `/backups` para backups exportados. Añádelos si usas esas features.
- Secretos: cada variable sensible soporta el sufijo `_FILE` si prefieres leer desde un archivo montado en lugar de pasar valores inline. Mira [secretos de Docker Compose](/es/secretos-docker-compose/) para patrones que funcionan con Compose.

<Notice type="info" title="¿Qué pasó con JWT_SECRET?">
Arcane 2.x firma los tokens de sesión con una clave ML-DSA-87 que genera y almacena por sí mismo (ML-DSA-87 es el esquema de firma post-cuántica NIST FIPS 204, incorporado en Arcane 2.10.0), así que `JWT_SECRET` ya no se usa. Si tu archivo compose todavía lo define, Arcane registra una advertencia al arrancar. Quítalo. La misma historia para el nombre de imagen: `ghcr.io/getarcaneapp/arcane` es el nombre viejo, `ghcr.io/getarcaneapp/manager` es el actual.
</Notice>

<Notice type="warning" title="Aléjate de las etiquetas v3">
Docker Hub tiene etiquetas `v3-beta` desde octubre de 2026. Son beta. Para cualquier cosa que te importe, fija `v2` (o `v2.17`) y deja que la gente de v3 encuentre los bordes afilados.
</Notice>

<Notice type="info" title="Rutas de volúmenes">
Las rutas idénticas en host y contenedor siguen siendo la recomendación cuando Arcane debe gestionar proyectos compose existentes (ej. `/opt/stacks:/opt/stacks`). Ya no es un requisito duro: Arcane lee sus propios montajes de contenedor y traduce las rutas de proyecto a rutas del host. Si quieres declarar el mapeo tú mismo, define `PROJECTS_DIRECTORY=<containerPath>:<hostPath>`. Los archivos compose con rutas relativas resuelven correctamente de cualquier forma una vez que el mapeo es correcto.
</Notice>

Inicia:

```bash
docker compose up -d
```

### Verifica la instalación

No te saltes esto. Dos minutos aquí ahorran una sesión de depuración después.

<ListCheck>
<ul>
<li><code>docker compose ps</code> muestra el contenedor como <code>healthy</code> (el healthcheck hace su trabajo en ~15s desde el arranque)</li>
<li><code>curl -s http://localhost:3552/health</code> devuelve un payload de salud desde dentro de la máquina</li>
<li>Abre <code>http://ip-de-tu-servidor:3552</code>, inicia sesión con <code>arcane</code> / <code>arcane-admin</code></li>
<li><code>docker compose logs -f arcane</code> está tranquilo. Sin advertencias sobre <code>JWT_SECRET</code> ni claves faltantes</li>
</ul>
</ListCheck>

<Notice type="info" title="El primer login fuerza un cambio de contraseña">
Arcane te pide cambiar la contraseña por defecto la primera vez que inicias sesión. Es forzado, no una sugerencia. Si de alguna forma sigues teniendo `arcane-admin` como contraseña después del primer login, algo salió mal.
</Notice>

Si el contenedor está reiniciando en bucle, lo primero a revisar es `ENCRYPTION_KEY`. Un valor vacío o mal formado es el culpable habitual. Si nada escucha en el 3552 en absoluto, revisa el firewall o el security group de tu proveedor antes de culpar a Arcane. Ambos casos están cubiertos en Solución de problemas al final.

## Endurecimiento: socket proxy de Docker

<Accordion label="¿Por qué usar un socket proxy?" group="security" expanded="true">

El socket de Docker (`/var/run/docker.sock`) es esencialmente una API de nivel root. Cualquier contenedor con acceso a él puede crear contenedores privilegiados, montar el filesystem del host o ejecutar comandos arbitrarios como root en el host.

Un socket proxy se sienta entre Arcane y el daemon Docker. Intercepta las llamadas de API y solo permite las que has permitido explícitamente. Obtienes la funcionalidad de gestión sin entregar las llaves del reino.

Esta configuración se recomienda para cualquier servidor expuesto a internet, y es el layout que las propias docs de Arcane sugieren para SELinux y hosts endurecidos. Para un homelab detrás de un firewall, el montaje directo del socket probablemente está bien. Si tu máquina está expuesta a internet, combina esto también con las otras capas aburridas: [cómo aseguré mi servidor Docker tras el informe BSI](/es/informe-seguridad-bsi-docker-ufw/) y [cómo proteger un VPS expuesto a internet con CrowdSec](/es/crowdsec-servidor-seguro/).

</Accordion>

### Opción 1: socket proxy wollomatic (recomendado)

El generador escribe este archivo por ti. Aquí está la forma para que sepas qué estás desplegando:

```yaml
services:
  arcane:
    image: ghcr.io/getarcaneapp/manager:v2
    container_name: arcane
    ports:
      - "3552:3552"
    volumes:
      - arcane-data:/app/data
      - /opt/stacks:/opt/stacks
    environment:
      - APP_URL=https://arcane.yourdomain.com
      - PUID=1000
      - PGID=1000
      - ENCRYPTION_KEY=your-generated-encryption-key
      - PROJECTS_DIRECTORY=/opt/stacks
      - TZ=Europe/Bucharest
      - DOCKER_HOST=tcp://docker-socket-proxy:2375
    cgroup: host
    depends_on:
      docker-socket-proxy:
        condition: service_healthy
    networks:
      - arcane-net
    restart: unless-stopped
    stop_grace_period: 15s

  docker-socket-proxy:
    image: wollomatic/socket-proxy:1.13.1
    container_name: arcane-docker-proxy
    user: "0:0"
    command:
      - "-listenip=0.0.0.0"
      - "-allowfrom=arcane,arcane-upgrader"
      - "-allowhealthcheck"
      # method+path allow rules (allowGET/allowPOST/allowPUT/allowDELETE)
      # go here. See the note below before starting this
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
    read_only: true
    cap_drop: [ALL]
    security_opt: ["no-new-privileges:true"]
    healthcheck:
      test: ["CMD", "./healthcheck"]
      interval: 2s
      timeout: 5s
      retries: 15
    networks:
      - arcane-net
    restart: unless-stopped

networks:
  arcane-net:
    driver: bridge

volumes:
  arcane-data:
```

Sobre las reglas allow: wollomatic deniega por defecto, así que sin ellas Arcane no puede hacer nada. Las reglas son pares método+ruta pasados como flags (forma de sintaxis: `-allowGET=/v1.*/containers/*`). La lista completa actual es específica de la versión y vive en las [docs de socket-proxy de Arcane](https://getarcane.app/docs/security/socket-proxy). El [Instance Generator](https://getarcane.app/generator) escribe el bloque de comandos completo por ti. Usa una de esas dos fuentes en lugar de una lista copiada de un post de blog (incluido este).

Tres cosas que importan en esa config:

- `-allowfrom=arcane,arcane-upgrader` necesita ambos nombres. `arcane-upgrader` es el alias que usan los helpers de auto-actualización de Arcane.
- El socket se monta `:ro`, y el contenedor proxy corre `read_only` con todas las capabilities quitadas y `no-new-privileges`. El proxy es el único contenedor que toca el socket; Arcane habla con él por la red bridge interna.
- `DOCKER_HOST=tcp://docker-socket-proxy:2375` en el lado de Arcane es todo el interruptor: Arcane nunca monta el socket él mismo.

<Notice type="warning" title="Instalaciones existentes: añade arcane-upgrader y recrea">
Si configuraste wollomatic antes con solo `-allowfrom=arcane`, los helpers de auto-actualización serán bloqueados. Añade `arcane-upgrader` a la lista permitida y recrea el contenedor proxy: `docker compose up -d --force-recreate docker-socket-proxy`. La primera actualización tras migrar debería pasar por un pull + recreate normal de Compose para no quedarte con un helper medio bloqueado a mitad de la actualización.
</Notice>

Verifica que el cambio funcionó:

```bash
docker compose ps          # proxy shows healthy
docker compose logs arcane # no Docker API errors in the UI's log stream
```

Luego haz clic por la UI: la lista de contenedores carga, los logs fluyen, la terminal abre. Cada uno de esos es una ruta de API que la lista permitida tiene que permitir. Si algo funcionaba antes del cambio y no después, te falta una regla allow.

```yaml
    networks:
      - arcane-net
    restart: unless-stopped

  docker-socket-proxy:
    image: tecnativa/docker-socket-proxy:latest
    container_name: arcane-socket-proxy
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
    environment:
      - EVENTS=1
      - PING=1
      - VERSION=1
      - POST=1
      - AUTH=0
      - SECRETS=0
      - BUILD=0
      - COMMIT=0
      - CONFIGS=0
      - CONTAINERS=1
      - DISTRIBUTION=1
      - EXEC=1
      - IMAGES=1
      - INFO=1
      - NETWORKS=1
      - NODES=0
      - PLUGINS=0
      - SERVICES=0
      - SESSION=0
      - SWARM=0
      - SYSTEM=1
      - TASKS=0
      - VOLUMES=1
    networks:
      - arcane-net
    security_opt:
      - no-new-privileges:true
    restart: unless-stopped

networks:
  arcane-net:
    driver: bridge

volumes:
  arcane-data:
```

Arcane ya no monta el socket de Docker directamente. Se conecta al proxy vía `DOCKER_HOST=tcp://docker-socket-proxy:2375`. El socket se monta de solo lectura en el proxy, y ambos contenedores están en una red bridge interna.

Los flags controlan qué grupos de endpoints de la API de Docker son alcanzables. Este conjunto es lo que las docs de Arcane recomiendan actualmente, con Swarm, auth y secrets apagados. Si usas el acceso de lectura a Swarm de Arcane, pon `SWARM`, `SERVICES`, `TASKS` y `NODES` en `1`. Mantén `AUTH=0` y `SECRETS=0` a menos que tengas una razón específica para no hacerlo.

## Configurar OIDC/SSO

Si ya estás ejecutando un proveedor de identidad como Authentik, Keycloak o Authelia, puedes conectar Arcane a él para single sign-on.

<Tabs>
  <Tab name="Vía la UI web">
    Ve a **Settings → Authentication** en Arcane. Introduce tu client ID, client secret y la issuer URL (sin barra final). Arcane descubre los endpoints desde la página `.well-known/openid-configuration` del proveedor. El redirect URI es:

    ```
    https://your-arcane-url/auth/oidc/callback
    ```

    Guarda y prueba la conexión. Los usuarios que se autentican vía OIDC se aprovisionan automáticamente en el primer login, y puedes deshabilitar el login con contraseña local por completo una vez que funcione.
  </Tab>

  <Tab name="Vía variables de entorno">
    Agrega estas a tu archivo compose:

    ```yaml
    environment:
      - OIDC_ENABLED=true
      - OIDC_CLIENT_ID=your-client-id
      - OIDC_CLIENT_SECRET=your-client-secret
      - OIDC_ISSUER_URL=https://your-idp.example.com
      - OIDC_SCOPES=openid email profile groups
      - OIDC_GROUPS_CLAIM=groups
      - OIDC_ROLE_MAPPINGS=[{"claimValue":"arcane-admins","roleId":"role_admin"}]
    ```

    `OIDC_GROUPS_CLAIM` le dice a Arcane dónde vive la membresía de grupos en el token (`realm_access.roles` para Keycloak, `memberOf` para Azure AD). `OIDC_ROLE_MAPPINGS` vincula un valor de claim a un rol de Arcane, con un `environmentId` opcional para acotarlo. Los mappings definidos así se reconcilian en cada arranque y son de solo lectura en la UI; también soporta el sufijo `_FILE` para secretos de Docker.

    Guías antiguas mencionan `OIDC_ADMIN_CLAIM` y `OIDC_ADMIN_VALUE`. Esos ya no existen en 2.x, reemplazados por el setup de role-mappings de arriba.
  </Tab>
</Tabs>

Una vez que lo básico funciona, las variables que vale conocer:

- `OIDC_AUTO_REDIRECT_TO_PROVIDER=true` se salta el formulario de login local por completo. Antes de activarlo, confirma que la página de login de emergencia `https://tu-url-arcane/login/backup` funciona. Es tu escotilla de escape si el IdP se cae.
- `OIDC_MERGE_ACCOUNTS` vincula una identidad OIDC a una cuenta local existente por email. Desde la 2.16.0 la fusión requiere un email **verificado** del proveedor, que es el comportamiento que quieres.
- `OIDC_SKIP_TLS_VERIFY` existe para IdPs de laboratorio con certificados autofirmados. No lo actives en producción.
- Variables de nombre/logo del proveedor y overrides manuales de endpoints están disponibles para proveedores sin discovery.

<Notice type="warning" title="No pongas valores entre comillas en bloques de entorno en forma de lista">
En la sintaxis de lista de Compose (`- KEY=value`), envolver el valor en comillas hace que las comillas formen parte del valor. `OIDC_ISSUER_URL="https://idp.example.com"` romperá el discovery. Esto le pica a todo el mundo una vez. El JSON en `OIDC_ROLE_MAPPINGS` es la excepción: las llaves JSON van bien sin comillas en forma de lista.
</Notice>

Verifica: inicia sesión a través del IdP una vez, confirma que el usuario aterriza en Arcane con el rol correcto, y entonces (y solo entonces) considera deshabilitar el login local.

## Configuración de proxy inverso

Querrás un proxy inverso frente a Arcane para SSL y un nombre de dominio limpio. Arcane usa WebSockets para actualizaciones en tiempo real, así que tu config de proxy necesita soportar eso.

<Tabs>
  <Tab name="Nginx">

```nginx
server {
    listen 443 ssl http2;
    server_name arcane.yourdomain.com;

    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;

    location / {
        proxy_pass http://127.0.0.1:3552;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Las líneas clave son `proxy_http_version 1.1` y los encabezados `Upgrade` / `Connection`. Sin ellos, las conexiones WebSocket fallan y la UI no obtiene actualizaciones en vivo.

  </Tab>

  <Tab name="Traefik">
    Si ya estás ejecutando Traefik (y probablemente deberías para configuraciones Docker), agrega labels a tu servicio Arcane:

    ```yaml
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.arcane.rule=Host(`arcane.yourdomain.com`)"
      - "traefik.http.routers.arcane.entrypoints=websecure"
      - "traefik.http.routers.arcane.tls.certresolver=letsencrypt"
      - "traefik.http.services.arcane.loadbalancer.server.port=3552"
    ```

    Traefik maneja el upgrade de WebSocket automáticamente. Si vas a ejecutar **agentes Edge en transporte `auto`/`grpc`**, se requieren dos cosas más (mira la sección de hosts remotos): una ruta h2c para `/api/tunnel/connect`, y el read timeout del entrypoint websecure deshabilitado:

    ```yaml
    # Traefik static/command config: entrypoint level, not router level
    - "--entrypoints.websecure.transport.respondingtimeouts.readtimeout=0s"
    ```

    El read timeout por defecto de 60s mata el túnel gRPC. Guía completa de Traefik: [Cómo usar Traefik como proxy inverso en Docker](/es/traefik-proxy-docker/).
  </Tab>

  <Tab name="Cloudflare Tunnels">
    Si no quieres exponer puertos en absoluto, Cloudflare Tunnels funciona bien. Apunta un túnel a `http://localhost:3552` y Cloudflare maneja SSL y enrutamiento. El soporte WebSocket es automático.

    Esto es lo que uso en mi homelab ya que no quiero abrir ningún puerto en mi router. Si añades agentes Edge detrás de un túnel de Cloudflare, define `EDGE_TRANSPORT=poll` en el agente. El polling funciona bien a través del túnel; gRPC de larga duración a través de CF es algo en lo que no apostaría sin probar.
  </Tab>
</Tabs>

<Notice type="warning" title="Define TRUSTED_PROXIES">
Desde la 2.16.0 Arcane solo extrae IPs de cliente de proxies en los que confías explícitamente. Detrás de cualquier proxy inverso, define `TRUSTED_PROXIES` al CIDR de la red de tu proxy (ej. `TRUSTED_PROXIES=172.18.0.0/16` para el bridge de Docker al que se une tu proxy). Sin él, el rate-limiting de login y el registro de IPs se comportan mal: verás la IP del proxy por todas partes y los límites de tasa se disparan sobre la identidad equivocada. Y ya que estamos: [Docker puede saltarse tus reglas de firewall](/es/docker-evita-firewall/), así que no confíes solo en UFW para mantener el 3552 cerrado.
</Notice>

Actualiza la variable de entorno `APP_URL` en tu archivo compose para que coincida con tu dominio real (ej., `https://arcane.tudominio.com`, sin `:3552`; el proxy termina el puerto).

Si prefieres saltarte el proxy inverso por completo, Arcane puede servir TLS por sí mismo: define `TLS_ENABLED=true`, `TLS_CERT_FILE` y `TLS_KEY_FILE`. Habla HTTP/2 sobre TLS directamente. Vale para un laboratorio; yo sigo prefiriendo un proxy delante.

**Direct** significa que el manager alcanza al agente en el puerto TCP 3553. **Edge** significa que el agente llama hacia afuera al manager por un túnel mTLS, así que el host remoto no necesita ningún puerto entrante abierto. Edge es el que quieres para cualquier cosa detrás de NAT o un firewall. El setup de mTLS está documentado en las [docs de edge-mTLS de Arcane](https://getarcane.app/docs/security/edge-mtls).

De cualquier forma, crea primero el entorno: abre **Environments → Add Environment** en la UI de Arcane, elige Direct o Edge, y te genera el token y un snippet listo para ejecutar. El compose de Edge se ve así:

```yaml
services:
  arcane-edge-agent:
    image: ghcr.io/getarcaneapp/agent:v2
    container_name: arcane-edge-agent
    environment:
      - EDGE_AGENT=true
      - EDGE_TRANSPORT=poll
      - AGENT_TOKEN=arc_your-generated-token
      - MANAGER_API_URL=https://arcane.yourdomain.com
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - agent-data:/app/data
    cgroup: host
    restart: unless-stopped
    stop_grace_period: 15s
volumes:
  agent-data:
```

Opciones de `EDGE_TRANSPORT`:

| Valor | Comportamiento | Cuándo usarlo |
|---|---|---|
| `poll` | El agente se reporta periódicamente; sin túnel persistente | NAT, túneles de Cloudflare, enlaces inestables. Los snippets generados usan esto |
| `auto` | Túnel gRPC continuo con fallback a WebSocket (por defecto cuando no se define) | Redes estables donde quieres push instantáneo |
| `websocket` | Túnel WebSocket continuo | Proxies que se atragantan con gRPC |
| `grpc` | Túnel gRPC continuo | Conexiones directas, o Traefik con h2c + read timeout deshabilitado |

En entornos poll verás los estados **Online / Standby / Pending / Offline** en la vista de conexión. **Standby significa sano**: el agente está inactivo esperando el siguiente poll, no caído. La primera acción contra un entorno poll inactivo puede tardar un momento mientras la conexión despierta. Ajusta las expectativas antes de asumir que está roto.

El agente también puede ejecutarse como binario standalone si no quieres un contenedor en el host remoto.

Un detalle de operaciones para evitar confusión: hay dos botones "Update All" distintos. **Updates → Update All** actualiza contenedores y proyectos. **Environments → Update All** actualiza los agentes primero, luego el manager. Las actualizaciones de flota son un solo clic en lugar de una tarea por host.

## Ejecutar Arcane en Podman

Nuevo en la 2.17.0 (21 de octubre de 2026): Arcane gestiona Podman nativamente. Si tus hosts ejecutan Podman en lugar de Docker, esta es la primera release donde el soporte es real en lugar de experimental.

El repo trae los ejemplos: `compose.podman-rootful.yaml`, `compose.podman-rootless.yaml`, y archivos quadlet bajo `docker/examples/quadlet/`. Las diferencias prácticas respecto a la instalación de Docker son la ruta del socket (el socket de Podman, rootless vs rootful) y el modelo de permisos rootless. También hay una sección de docs dedicada (`docs/podman/`) que cubre quadlets, kube, secrets y auto-actualización.

<Notice type="info" title="Los contenedores gestionados por quadlet se saltan las auto-actualizaciones de Arcane">
A propósito. Los contenedores propiedad de quadlets de systemd perderían su unidad de systemd si Arcane los recreara, así que Arcane los deja en paz. Para esos, usa el mecanismo de auto-actualización propio de Podman (`podman auto-update` + la etiqueta `io.containers.autoupdate`).
</Notice>

Este soporte tiene semanas al momento de escribir. Yo lo usaría en un host de laboratorio ahora y esperaría un par de ciclos de release antes de mover una flota Podman de producción a él. Si aún estás decidiendo el motor de contenedores, aquí está [cómo se compara Podman con Docker](/es/podman-vs-docker/).

## Referencia de variables de entorno

Estas son las variables que más uso. Para el panorama completo de cómo Docker pasa config a los contenedores, mira [cómo funcionan las variables de entorno de Docker](/es/variables-entorno-docker/).

| Variable | Default | Qué hace |
|---|---|---|
| `APP_URL` | `http://localhost:3552` | URL pública de la instancia (defínela a tu dominio real detrás de un proxy) |
| `PUID` / `PGID` | `65532:65532` | ID usuario/grupo para permisos de archivos. Las imágenes arrancan como root para preparar, luego bajan a este usuario |
| `ENCRYPTION_KEY` | ninguno | Requerida. Clave de 32 bytes para encriptar datos sensibles |
| `PROJECTS_DIRECTORY` | `/app/data/projects` | Dónde busca Arcane proyectos compose. Acepta la forma de mapeo `<containerPath>:<hostPath>` |
| `DOCKER_HOST` | `unix:///var/run/docker.sock` | Conexión Docker. Usa `tcp://` para socket proxy |
| `TZ` | default del contenedor | Zona horaria. Importa para horarios cron (backups, ventanas de auto-actualización) |
| `TRUSTED_PROXIES` | sin definir | CIDR de proxies permitidos para definir IPs de cliente. Requerido detrás de cualquier proxy inverso (2.16+) |
| `TLS_ENABLED` / `TLS_CERT_FILE` / `TLS_KEY_FILE` | sin definir | Servir HTTPS directamente, sin proxy inverso |
| `DATABASE_URL` | SQLite | String de conexión a base de datos externa |
| `JWT_REFRESH_EXPIRY` | `168h` | Vida del refresh token |
| `ADMIN_STATIC_API_KEY` | sin definir | Clave API estática para automatización |
| `TRIVY_SECURITY_OPTS` / `TRIVY_PRIVILEGED` | sin definir | Ajustar el comportamiento del escaneo Trivy |
| `GIT_WORK_DIR` / `SSH_KNOWN_HOSTS` | integrado | Workspace de GitOps y verificación de host SSH |
| `http_proxy` / `https_proxy` / `no_proxy` | sin definir | Proxy saliente para pulls de imágenes y llamadas API (en minúsculas) |
| `LOG_LEVEL` | `info` | Verbosidad de logging |
| `UI_CONFIGURATION_DISABLED` | `false` | Forzar config solo por env vars. Las env vars de override de settings solo se honran cuando esto es `true` (o `AGENT_MODE=true`) |

`JWT_SECRET` todavía aparece en docs y archivos compose viejos pero no se usa en 2.x. Déjalo sin definir. Las variables de monitoreo GPU (`GPU_MONITORING_ENABLED`, `GPU_TYPE`) aparecen en algunas guías antiguas pero están ausentes del `.env.example` actual. Revisa el doc de variables de entorno de tu versión antes de confiar en ellas.

## Solución de problemas

<Accordion label="Arcane no puede ver mis stacks compose existentes" group="troubleshoot" expanded="true">

Las rutas idénticas en host/contenedor siguen siendo la recomendación. Si tus archivos compose viven en `/opt/stacks/miapp/compose.yaml`, el setup simple es:

```yaml
volumes:
  - /opt/stacks:/opt/stacks
```

con `PROJECTS_DIRECTORY=/opt/stacks`.

Dicho esto, el desajuste de rutas ya no es fatal. Arcane lee sus propios montajes de contenedor y traduce las rutas de proyecto a rutas del host. Si tu mapeo es inusual, decláralo explícitamente:

```yaml
environment:
  - PROJECTS_DIRECTORY=/app/data/projects:/opt/stacks
```

El formato es `<containerPath>:<hostPath>`. Si los stacks aún no aparecen después de esto, comprueba que el montaje existe en el contenedor (`docker exec arcane ls /opt/stacks`) antes de culpar al mapeo.

</Accordion>

<Accordion label="Errores WebSocket o la UI no se actualiza en vivo" group="troubleshoot">

Tu proxy inverso no está reenviando las conexiones WebSocket. Asegúrate de tener los encabezados de upgrade configurados. Para Nginx, necesitas:

```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";
```

</Accordion>

<Accordion label="Permission denied en el socket de Docker" group="troubleshoot">

Agrega tu usuario al grupo `docker` (`sudo usermod -aG docker $USER`) o asegúrate de que los valores `PUID`/`PGID` en el archivo compose coinciden con un usuario con acceso a Docker. Dentro del contenedor, los archivos creados en bind mounts obtienen la propiedad de PUID/PGID. Elige IDs que coincidan con el usuario dueño de tus stacks. Para contenedores que construyes tú mismo, mira [cómo agregar un usuario no-root a un contenedor Docker](/add-users-to-docker-container/).

</Accordion>

<Accordion label="Aún usando la imagen vieja o JWT_SECRET" group="troubleshoot">

Si tu compose referencia `ghcr.io/getarcaneapp/arcane` o define `JWT_SECRET`, actualiza a `ghcr.io/getarcaneapp/manager` y quita la línea JWT. Arcane arranca igual pero registra advertencias, y el nombre de imagen viejo ya no está en los ejemplos y registries actuales.

</Accordion>

<Accordion label="El self-upgrade falla tras cambiar a un socket proxy" group="troubleshoot">

El contenedor helper de actualización está etiquetado `arcane-upgrader`. Si tu lista permitida de wollomatic solo tiene `-allowfrom=arcane`, el helper queda bloqueado a mitad de la actualización. Añade `arcane-upgrader` a `-allowfrom`, luego recrea el proxy:

```bash
docker compose up -d --force-recreate docker-socket-proxy
```

Haz la primera actualización tras esa migración mediante un pull + recreate normal de Compose para no depender del helper mientras la lista permitida se asienta.

</Accordion>

<Accordion label="Los límites de tasa de login se disparan en la IP equivocada" group="troubleshoot">

Estás detrás de un proxy inverso y `TRUSTED_PROXIES` no está definido. Arcane (desde la 2.16.0) solo confía en IPs de cliente de proxies configurados. Sin él, cada solicitud parece venir de la dirección del proxy, así que el rate limiting y los logs de IP están mal. Define `TRUSTED_PROXIES` al CIDR de la red del proxy (ej. `172.18.0.0/16`) y reinicia.

</Accordion>

<Accordion label="Agente Edge atascado en Pending o no conecta a través de Traefik" group="troubleshoot">

Tres chequeos, en orden:

1. `AGENT_TOKEN` y `MANAGER_API_URL` coinciden con el entorno que creaste en la UI (regenera el snippet si dudas).
2. En Traefik con `EDGE_TRANSPORT=auto` o `grpc`: enruta `/api/tunnel/connect` como h2c y define `--entrypoints.websecure.transport.respondingtimeouts.readtimeout=0s`. El read timeout por defecto de 60s tira el túnel.
3. Detrás de Cloudflare o cualquier ruta a la que no le gusten las conexiones de larga duración, usa `EDGE_TRANSPORT=poll`.

También: **Standby no es caído.** Un agente en modo poll en Standby está sano e inactivo.

</Accordion>

## Lo que me gusta y lo que falta

He ejecutado Arcane lo suficiente para tener opiniones ahora.

La integración GitOps es la feature que más uso. Mantengo mis archivos compose en un repo Git privado, y cuando pusheo cambios, Arcane los recoge y redespliega. Sin configuración de webhook, sin pipeline CI necesario.

La API REST es la otra en la que me apoyo. Escribí un script pequeño que revisa la salud de los contenedores y reinicia cualquier cosa que esté unhealthy. Tomó unos 20 minutos porque la API es directa.

Los huecos de los que me quejé en la primera versión de esta guía se han cerrado en su mayoría: el escaneo Trivy, las auto-actualizaciones programadas y los backups llegaron en las releases 2.9 a 2.12, y las 2.14 a 2.17 añadieron la pestaña de procesos, una vista de seguridad basada en riesgo y navegación de registries. El nuevo **Update Delay** es la pieza que activaría para cualquier cosa expuesta a internet. Es un enfriamiento de la cadena de suministro para que una etiqueta maliciosa recién publicada no se descargue en el segundo en que aparece:

```yaml
x-arcane:
  updater:
    delay: 72          # project default, hours
services:
  cache:
    image: redis:7
    x-arcane:
      updater:
        delay: 0       # opt a service out of the cool-down
# or label: com.getarcaneapp.arcane.updater.delay=72
```

Lo que aún falta en la v2.17.1: la compuerta de escanear-antes-de-cambiar estilo Dockhand, donde una actualización solo procede si la imagen nueva escanea limpia (no está en las docs al momento de escribir), y un navegador de archivos adecuado dentro de los contenedores. Ninguno es un dealbreaker, pero ambos harían a Arcane más fácil de vivir. Si las auto-actualizaciones son lo tuyo en general, el [enfoque de auto-actualización de Tugtainer](/es/tugtainer-autoactualizacion-docker/) también vale la lectura.

Si quieres esas features específicas hoy, echa un vistazo a [cómo instalar Dockhand](/es/instalar-dockhand/). Y para el campo más amplio, mi [comparación de alternativas a Portainer](/es/alternativas-portainer/) cubre Sencho, Dockge, Komodo y el resto.
