Si has intentado darle a un agente de IA acceso al navegador, ya conoces el problema. Playwright MCP te ata a Node. Browser Use necesita Python. El backend de navegador de OpenClaw solo funciona dentro de su propio ecosistema. Cambia de agente, o intenta hacer una solicitud curl rápida para inspeccionar una página, y tendrás que reescribir la integración desde cero.

[Pinchtab](https://github.com/pinchtab/pinchtab) toma un enfoque diferente: te da control del navegador para agentes de IA sobre HTTP simple. Un binario Go de ~30MB sin Node, sin Python, sin dependencias. Lanza su propio Chrome y expone navegación, clics, relleno de formularios, capturas de pantalla y snapshots de accesibilidad a través de una API REST simple. Cualquier agente que uses ya habla HTTP. Esa es toda la historia de integración. A fecha de v0.15.2 (ago 2026), el proyecto supera las 10,000 estrellas en GitHub.

## ¿Qué es Pinchtab?

Pinchtab es un servidor HTTP independiente escrito en Go que te da control del navegador para agentes de IA. Lanza instancias de Chrome, expone navegación, acciones, snapshots y capturas sobre una API REST, y no requiere runtime de Node ni Python. Tiene licencia MIT, actualmente en v0.15.2 (publicada el 2026-08-26), con 10,472 estrellas y 785 forks en GitHub. Las versiones con soporte de seguridad son v0.14.0 y posteriores.

## Por qué árboles de accesibilidad en lugar de capturas de pantalla

Para la automatización de navegador con IA, la mayoría de la gente recurre primero a las capturas de pantalla porque es obvio: toma una foto, envíala a un modelo de visión, listo. El problema es el costo y la fiabilidad. Un modelo de visión adivina coordenadas a partir de píxeles. Los árboles de accesibilidad te dan referencias de nodo estables (`e0`, `e1`, `e2`…) vinculadas a los elementos DOM reales. Haz clic en `e5` y acertarás en el botón correcto, independientemente de cómo se renderice la página.

Desde v0.15.1, las refs denotan un nodo DOM específico en lugar de un índice de fila. Sobreviven a cambios en los parámetros `filter`, `selector` o `depth` y solo expiran cuando navegas a un nuevo documento. Eso significa que puedes tomar un snapshot filtrado, interactuar, y luego tomar un snapshot más amplio sin perder tu posición.

La diferencia de costo se acumula rápidamente. El endpoint `/text` de Pinchtab extrae contenido legible a unos 800 tokens por página usando la biblioteca Readability de Mozilla (lo mismo que hay detrás de Firefox Reader View). El README lo presenta como 5-13 veces más barato que las capturas de pantalla para trabajo intensivo de lectura. El trabajo de 50 páginas de abajo muestra dónde queda cada método en tokens brutos.

| Método | ~Tokens (trabajo de 50 páginas) | Costo relativo |
|--------|-------------------------------|----------------|
| Capturas de pantalla (visión) | ~100,000 | El más alto |
| Snapshot completo de a11y | ~525,000 | Alto |
| Pinchtab `?filter=interactive` | ~180,000 | Bajo |
| Pinchtab `/text` | ~40,000 | El más bajo |

El propio benchmark de Pinchtab contra agent-browser (autopublicado, con muestras pequeñas de 5/3/2 ejecuciones y ~25-30% de varianza, así que tómalo como orientativo) muestra un costo del bucle de agente de extremo a extremo entre un 9.5 y un 20.3% menor en la API de Anthropic. La ganancia viene de agrupar clic+snapshot en un solo round trip mediante `--snap`. Para equipos que eligen modelos junto a su stack de navegador, los [modelos de IA más baratos por debajo de $1/M tokens](/es/mejores-modelos-baratos-hermes-agent/) importan tanto como el recuento de tokens por página.

## La arquitectura de Pinchtab: servidor, instancias y perfiles

Pinchtab v0.15.x ya no es una herramienta de un solo bridge. Es un plano de control que gestiona múltiples instancias de Chrome, cada una con su propio perfil aislado. Estos son los cuatro conceptos que necesitas:

- El **servidor** es el plano de control en el puerto 9867. Es la superficie de la API HTTP con la que hablan tus agentes, y un solo servidor lo gestiona todo.
- Una **instancia** es un proceso de Chrome en ejecución. Cada instancia tiene su propio perfil y su propio puerto interno (p.ej. 9868). Puedes ejecutar varias instancias en paralelo, una para tareas de "trabajo" y otra para "scraping", con aislamiento completo de cookies y sesiones.
- Un **perfil** es el estado persistente del navegador (cookies, localStorage, inicios de sesión guardados). Inicia sesión una vez a través de un perfil y cada instancia posterior que use ese perfil mantiene la sesión. Los perfiles con nombre se gestionan mediante `POST /profiles` y se almacenan en `profiles.baseDir`.
- El **bridge** es el runtime de instancia única que el servidor genera. No interactuarás con él directamente; el servidor gestiona el ciclo de vida.

```
agents / CLI / MCP
        │
        ▼
┌─────────────────────────┐
│  Pinchtab server :9867  │  ← control plane, REST API
└────────┬────────┬───────┘
         │        │
         ▼        ▼
  ┌──────────┐ ┌──────────┐
  │Instance A│ │Instance B│   ← Chrome processes
  │profile:  │ │profile:  │
  │  "work"  │ │"scraping"│
  │  :9868   │ │  :9869   │
  └──────────┘ └──────────┘
         │        │
         ▼        ▼
    ~/.pinchtab/  (state, profiles)
```

El recorrido principal del usuario es instalar Pinchtab una vez como daemon para que todos tus agentes compartan un solo plano de control:

```bash
pinchtab daemon install
pinchtab daemon
```

Esto ejecuta un servicio en segundo plano a nivel de usuario. Los agentes se conectan a `http://127.0.0.1:9867`, y el servidor genera o reutiliza instancias de Chrome según sea necesario. El control de navegador multi-instancia con perfiles de navegador aislados para agentes de IA es la capacidad estrella que separa a Pinchtab de un simple wrapper de CDP.

### Primera ejecución y verificación

Ejecutar `pinchtab` sin argumentos dispara la configuración de seguridad (autogenera un token de autenticación) e imprime el estado. Luego instala el daemon y haz una prueba de humo:

```bash
pinchtab daemon install
pinchtab daemon

# Obtener el token autogenerado
export PINCHTAB_TOKEN=$(pinchtab config token --stdout)

# Prueba de humo: navegar y snapshot en un solo round trip
pinchtab nav https://pinchtab.com --snap

# Comprobar salud (requiere el token)
pinchtab health
```

Verifica cada paso:

- `pinchtab --version` imprime la versión. Si dice `v0.15.2` estás al día.
- `pinchtab nav https://pinchtab.com --snap` debería devolver un snapshot de página. Si obtienes un 401, el token no está configurado en tu entorno.
- `pinchtab health` debería reportar el estado del servidor y de Chrome. Si dice `status: running`, todo bien.

Modos de fallo:
- La instalación con `curl | bash` falla en distros poco comunes → recurre a `brew` o `npm`.
- `go build` falla → comprueba que estás en Go 1.26+ (`go version`). El objetivo de compilación es `./cmd/pinchtab`, no la raíz del repo.
- Puerto 9867 ya en uso → `pinchtab config set server.port 9868` (o el puerto que esté libre).
- Comportamiento extraño del navegador en macOS → `pinchtab doctor browsers`. Prefiere Chrome for Testing sobre tu Chrome habitual para evitar conflictos de perfil.

## Configurar Pinchtab

Toda la configuración vive en un archivo JSON anidado en `~/.pinchtab/config.json` (forma configVersion 0.8.0). Las variables de entorno `BRIDGE_*` de versiones anteriores han desaparecido. Consulta la nota de migración más abajo.

Gestiona la configuración a través del CLI:

```bash
pinchtab config init                # crea ~/.pinchtab/config.json
pinchtab config show                # imprime la configuración efectiva
pinchtab config get server.port     # lee una sola clave
pinchtab config set server.token "$(openssl rand -hex 32)"
pinchtab config validate            # comprueba errores tras editar
```

Solo sobreviven cinco variables de entorno, y anulan el archivo de configuración (env > archivo):

| Variable | Propósito |
|----------|-----------|
| `PINCHTAB_CONFIG` | Ruta al archivo de configuración |
| `PINCHTAB_TOKEN` | Anulación en runtime de `server.token` |
| `PINCHTAB_URL` | URL base para CLI/MCP al apuntar a un servidor remoto |
| `PINCHTAB_RATE_LIMIT_MAX` | Límite de solicitudes por cliente por ventana de 10 segundos |
| `PINCHTAB_STATE_KEY` | Clave de cifrado para el archivo de estado |

Claves de configuración comunes:

```bash
# Servidor
pinchtab config set server.port "9867"
pinchtab config set server.stateDir "~/.pinchtab"

# Valores por defecto de instancia (aplicados a nuevas instancias de Chrome)
pinchtab config set instanceDefaults.mode "headless"
pinchtab config set instanceDefaults.stealthLevel light       # light | medium | full (anti-bot opt-in)
pinchtab config set instanceDefaults.blockImages true
pinchtab config set instanceDefaults.blockAds true             # nuevo desde la era BRIDGE_*
pinchtab config set instanceDefaults.humanize false            # por defecto: CDP puro, rápido y determinista

# Navegador
pinchtab config set browser.binary "/usr/bin/chromium"

# Gates de seguridad (todos por defecto false; activa solo lo que necesites)
pinchtab config set security.allowEvaluate true
pinchtab config set security.allowedDomains '["example.com"]'  # amplía la lista permitida de IDPI deliberadamente

# Revisa la postura en cualquier momento
pinchtab security
pinchtab security up    # restaura los valores seguros recomendados
```

<Notice type="warning" title="¿Migrando desde la versión de febrero de 2026?">
Todo cambió. Las antiguas variables de entorno `BRIDGE_*` están muertas y se ignoran silenciosamente. Aquí está el mapeo:
<br /><br />
<code>BRIDGE_PORT</code> → <code>server.port</code> · <code>BRIDGE_TOKEN</code> → <code>server.token</code> · <code>BRIDGE_HEADLESS</code> → <code>instanceDefaults.mode</code> · <code>BRIDGE_STEALTH</code> → <code>instanceDefaults.stealthLevel</code> · <code>BRIDGE_PROFILE</code> → perfiles con nombre (<code>POST /profiles</code>) · <code>BRIDGE_BLOCK_IMAGES</code> → <code>instanceDefaults.blockImages</code> · <code>BRIDGE_BLOCK_MEDIA</code> → <code>instanceDefaults.blockMedia</code> · <code>BRIDGE_NO_ANIMATIONS</code> → <code>instanceDefaults.noAnimations</code> · <code>BRIDGE_TIMEZONE</code> → <code>instanceDefaults.timezone</code> · <code>CHROME_BINARY</code> → <code>browser.binary</code> · <code>CHROME_FLAGS</code> → <code>browser.extraFlags</code> · <code>CDP_URL</code> → modo attach (<code>POST /instances/attach</code>, protegido por <code>security.attach.enabled</code>, por defecto false).
<br /><br />
También cambió: los tipos de acción <code>humanType</code>/<code>humanClick</code> ya no existen (usa <code>"humanize": true</code> en <code>kind:"type"</code> o <code>kind:"click"</code>); <code>seccomp=unconfined</code> ya no es necesario para Docker; <code>/health</code> ahora requiere el token de autenticación; y la autenticación por query string se ha eliminado por completo.
</Notice>

## La API REST de Pinchtab

Pinchtab expone una API de automatización de navegador sobre HTTP simple. Cada ruta, incluyendo `/health`, requiere un encabezado `Authorization: Bearer <token>`. Estos son los endpoints principales:

| Método | Endpoint | Descripción |
|--------|----------|-------------|
| `GET` | `/health` | Estado del servidor y de Chrome (requiere token) |
| `GET` | `/tabs` | Lista las pestañas abiertas |
| `GET` | `/snapshot` | Árbol de accesibilidad como JSON o texto |
| `GET` | `/screenshot` | Captura de pantalla JPEG con control de calidad |
| `GET` | `/text` | Texto legible de la página (Readability o innerText sin procesar) |
| `POST` | `/navigate` | Ir a una URL |
| `POST` | `/action` | Clic, escribir, rellenar, presionar, enfocar, hover, seleccionar, desplazar |
| `POST` | `/evaluate` | Ejecutar JavaScript (protegido: `security.allowEvaluate`, por defecto false) |
| `POST` | `/tab` | Abrir o cerrar pestañas |
| `POST` | `/lock` / `/unlock` | Bloqueo por pestaña: `POST /tabs/{id}/lock` / `unlock` |
| `POST` | `/cookies` | Inyectar cookies (protegido: `security.allowCookies`, por defecto false) |

Existen formas con ámbito de pestaña para la mayoría de las rutas: `/tabs/{id}/snapshot`, `/tabs/{id}/action`, etc. Las rutas planas (`/navigate`, `/snapshot`, `/action`) apuntan a la pestaña actual y siguen funcionando exactamente como siempre.

### Parámetros de consulta del snapshot

El endpoint de snapshot tiene varias opciones que reducen el uso de tokens significativamente. Las cinco siguen funcionando tal como está documentado:

```bash
# Solo elementos interactivos: ~75% menos nodos
curl -H "Authorization: Bearer $PINCHTAB_TOKEN" \
  "localhost:9867/snapshot?filter=interactive"

# Formato compacto de una línea por nodo: 56-64% menos tokens que JSON
curl -H "Authorization: Bearer $PINCHTAB_TOKEN" \
  "localhost:9867/snapshot?format=compact"

# Solo cambios desde el último snapshot
curl -H "Authorization: Bearer $PINCHTAB_TOKEN" \
  "localhost:9867/snapshot?diff=true"

# Limitar a una sección específica de la página
curl -H "Authorization: Bearer $PINCHTAB_TOKEN" \
  "localhost:9867/snapshot?selector=main"

# Limitar la salida a aproximadamente N tokens
curl -H "Authorization: Bearer $PINCHTAB_TOKEN" \
  "localhost:9867/snapshot?maxTokens=2000"
```

Combinar `filter=interactive` con `format=compact` te da el payload más pequeño posible para tareas orientadas a acciones. Usa `diff=true` para páginas que se actualizan incrementalmente (sondeando un dashboard en vivo, por ejemplo) para que solo envíes lo que cambió. Desde v0.15.1, las refs de nodo están vinculadas a la identidad del DOM y sobreviven a cambios de filter/selector/depth, expirando solo al navegar a un nuevo documento.

### Acciones similares a las humanas

Los antiguos tipos de acción `humanClick` y `humanType` ya no existen. La entrada similar a la humana es ahora un flag por acción en las acciones estándar `click` y `type`:

```bash
curl -X POST localhost:9867/action \
  -H "Authorization: Bearer $PINCHTAB_TOKEN" \
  -d '{"kind":"type","ref":"e12","text":"hola mundo","humanize":true}'
```

Cuando `humanize` se omite, el comportamiento sigue a `instanceDefaults.humanize`, que por defecto es `false`: entrada CDP pura, rápida y determinista. Activa `humanize` por acción cuando necesites retrasos realistas y patrones de movimiento para superar la detección de bots de comportamiento. Para una evasión anti-bot más fuerte, `instanceDefaults.stealthLevel` acepta `light` (por defecto, normalización mínima), `medium`, o `full` (spoofing de canvas/WebGL/fuentes, opt-in explícito).

Y `pinchtab compare <live> <staging> --fail-on-diff` funciona como puerta de CI: si staging se desvía de live, el build falla.

## Servidor MCP e integraciones con agentes

Pinchtab incluye un servidor MCP de navegador integrado, así que cualquier agente compatible con MCP puede usarlo sin escribir glue HTTP personalizado. La integración MCP incluye herramientas como `pinchtab_screenshot`, `pinchtab_scrape`, y controles de navegación (back/forward/reload desde v0.15.1). Si no hay ningún servidor en ejecución, las herramientas MCP auto-inician uno.

Si eres nuevo en el protocolo, lee primero [cómo funciona el Model Context Protocol](/es/introduccion-mcp-principiantes/).

El paquete npm incluye un skill de agente y lo autocopia a los homes de agentes detectados (`~/.claude/skills`, `~/.cursor/skills`, `~/.windsurf/skills`, `~/.codex/skills`, y OpenClaw). Gestiona la instalación del skill con:

```bash
pinchtab skill status
pinchtab skill update --force
```

Para usuarios de OpenClaw, hay un plugin oficial. Si estás [autoalojando OpenClaw en un VPS o Mac mini](/es/guia-configuracion-openclaw/):

```bash
openclaw plugins install @pinchtab/pinchtab
```

Los usuarios de Grok Build pueden instalarlo mediante:

```bash
grok plugin install pinchtab --trust
```

Al apuntar a un servidor Pinchtab remoto desde el CLI o MCP, configura `PINCHTAB_URL` o usa el flag `--server`.

El modo headed se niega a lanzarse en el contenedor ya que no hay X11. Si quieres autoalojar Pinchtab en un servidor, este es el camino más limpio. El antiguo requisito `seccomp=unconfined` ha desaparecido. La capa del contenedor en sí es el límite de seguridad: la imagen se ejecuta como usuario `pinchtab` no-root con `HOME=/data`, y el archivo compose elimina todas las capacidades, usa un sistema de archivos de solo lectura y mantiene el perfil seccomp por defecto. Chrome se ejecuta con `--no-sandbox` dentro del contenedor precisamente porque ese límite existe.

### Configuración básica de docker-compose

```yaml
# docker-compose.yml
services:
  pinchtab:
    image: pinchtab/pinchtab:v0.15.2
    container_name: pinchtab
    restart: unless-stopped
    ports:
      - "127.0.0.1:9867:9867"
    volumes:
      - pinchtab-data:/data
    environment:
      PINCHTAB_TOKEN: ${PINCHTAB_TOKEN:-}
    shm_size: "2gb"
    read_only: true
    tmpfs:
      - /tmp:size=512m,noexec,nosuid,nodev
      - /run:size=64m,noexec,nosuid,nodev
    security_opt:
      - no-new-privileges:true
    cap_drop:
      - ALL
    mem_limit: 2g
    cpus: "2.0"

volumes:
  pinchtab-data:
```

<Notice type="warning" title="shm_size no es opcional">
Las pestañas de Chrome fallarán aleatoriamente sin 2GB de memoria compartida. La línea `shm_size: "2gb"` es la diferencia entre un despliegue estable y misteriosos OOM del renderer. No la elimines.
</Notice>

Puntos clave sobre este archivo compose:

- El binding de puerto `127.0.0.1:9867:9867` mantiene el servicio fuera de la red pública. El compose oficial usa `"9867:9867"`. Ajústalo.
- El token se autogenera en el primer arranque. Léelo con `docker exec pinchtab pinchtab config token --stdout`. Si quieres suministrar el tuyo propio, usa [secretos de Docker Compose](/es/secretos-docker-compose/) para `PINCHTAB_TOKEN`. La imagen soporta secretos de Docker nativamente.
- Si montas tu propia configuración vía `PINCHTAB_CONFIG`, establece `server.token` en ella o pasa `-e PINCHTAB_TOKEN=...`. De lo contrario el servidor se niega a arrancar.
- La persistencia de la configuración vive en el volumen `pinchtab-data` bajo `/data` (la imagen establece `HOME=/data`, así que la configuración cae en `/data/.config/pinchtab/config.json`).

<li><code>docker exec pinchtab pinchtab health</code> devuelve el estado del servidor</li>
<li>Token recuperado: <code>TOKEN=$(docker exec pinchtab pinchtab config token --stdout)</code></li>
<li>La comprobación de salud autenticada pasa (ver abajo)</li>
<li>Chrome reporta <code>"status":"running"</code> (no solo el dashboard arriba)</li>
<li>Una prueba de humo: <code>nav</code> + <code>--snap</code> devuelve un snapshot</li>
</ul>
</ListCheck>

```bash
# Obtener el token autogenerado
TOKEN=$(docker exec pinchtab pinchtab config token --stdout)

# Comprobación de salud autenticada
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:9867/health

# Esperar a que Chrome esté listo (no solo el dashboard)
until curl -sf -H "Authorization: Bearer $TOKEN" http://127.0.0.1:9867/health \
  | grep -q '"status":"running"'; do sleep 1; done
```

Preparación en dos etapas: que `/health` devuelva 200 significa que el dashboard está arriba, pero Chrome puede no estar listo todavía. Antes de que Chrome esté listo, las solicitudes a la API devuelven HTTP 503. Sondea `.defaultInstance.status == "running"` antes de tu primera navegación.

Modos de fallo:
- 503 en cada llamada → Chrome no está listo todavía. Usa el sondeo de preparación de arriba.
- 401 → token ausente o incorrecto. Revisa el encabezado `Authorization`.
- OOM kills → aumenta `mem_limit`.
- Pestañas de Chrome muriendo aleatoriamente → falta `shm_size: "2gb"`.

### Detrás de un proxy inverso Caddy

Si quieres exponer Pinchtab sobre HTTPS con un dominio:

```yaml
# docker-compose.yml (añade Caddy junto a Pinchtab)
services:
  pinchtab:
    image: pinchtab/pinchtab:v0.15.2
    container_name: pinchtab
    restart: unless-stopped
    ports:
      - "127.0.0.1:9867:9867"
    volumes:
      - pinchtab-data:/data
    environment:
      PINCHTAB_TOKEN: ${PINCHTAB_TOKEN:-}
    shm_size: "2gb"
    read_only: true
    tmpfs:
      - /tmp:size=512m,noexec,nosuid,nodev
      - /run:size=64m,noexec,nosuid,nodev
    security_opt:
      - no-new-privileges:true
    cap_drop:
      - ALL
    mem_limit: 2g
    cpus: "2.0"
    networks:
      - proxy

  caddy:
    image: caddy:2-alpine
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile
      - caddy-data:/data
      - caddy-config:/config
    networks:
      - proxy

networks:
  proxy:
    driver: bridge

volumes:
  pinchtab-data:
  caddy-data:
  caddy-config:
```

```
# Caddyfile
pinchtab.tudominio.com {
    reverse_proxy pinchtab:9867
}
```

Caddy gestiona TLS automáticamente. Con `PINCHTAB_TOKEN` configurado, las solicitudes necesitan un encabezado `Authorization: Bearer <token>`, así que la API no queda abierta ni siquiera con HTTPS.

Dos ajustes relacionados con el proxy a conocer:
- `server.trustProxyHeaders`: déjalo desactivado a menos que tu proxy reconstruya correctamente los encabezados `Forwarded` y `X-Forwarded-*`.
- `server.cookieSecure`: por defecto `auto`; fuerza `true` detrás de TLS. El dashboard avisa cuando se sirve sobre HTTP plano en un bind no-loopback.

Si prefieres [Traefik como proxy inverso alternativo](/es/traefik-proxy-docker/), el patrón es el mismo. Solo cambia el servicio de Caddy. Para el dashboard específicamente, consulta [exponer el panel de un agente de forma segura detrás de Caddy](/es/guia-panel-hermes/).

Verifica a través del dominio:

```bash
curl -H "Authorization: Bearer $TOKEN" https://pinchtab.tudominio.com/health
```

Un 502 significa que el contenedor de Pinchtab no está en la red `proxy`.

## Consideraciones de seguridad y mitigaciones

Pinchtab le da a un agente de IA control total de un navegador Chrome real, incluyendo cualquier cuenta en la que hayas iniciado sesión a través de ese navegador. El propio planteamiento del proyecto es directo:

<Notice type="warning" title="Piensa en Pinchtab como darle a alguien tu laptop desbloqueada">
Un agente con acceso a Pinchtab puede hacer cualquier cosa que un humano con ese navegador pueda hacer. La postura de seguridad ha cambiado desde febrero de 2026. Pinchtab ahora es seguro por defecto (bind 127.0.0.1, token autogenerado, gates de capacidad desactivados, IDPI estricto activado). El riesgo se ha movido a debilitar deliberadamente esa postura o a malentender lo que los valores por defecto protegen.
</Notice>

Las versiones con soporte de seguridad son **solo v0.14.0+** (según SECURITY.md). Ejecuta `pinchtab security` en cualquier momento para ver tu postura actual; `pinchtab security up` restaura los valores recomendados.

### La autenticación está activada por defecto

El token se autogenera durante la configuración de primera ejecución. La autenticación por query string se ha eliminado por completo. El dashboard usa una cookie de sesión `HttpOnly` del lado del servidor con limitación de tasa de inicio de sesión y elevación de re-autenticación para acciones sensibles.

El bind por defecto es `127.0.0.1`, no `0.0.0.0`. La única excepción es dentro de Docker: el entrypoint escribe `bind: 0.0.0.0` en la configuración gestionada para que la publicación de puertos funcione. Tu exposición real depende del mapeo de host `-p`, que es la razón por la que el compose de arriba usa `127.0.0.1:9867:9867`. Aquí es también donde [cómo los puertos Docker publicados pueden evitar tu firewall](/es/docker-evita-firewall/) se vuelve relevante: la publicación `-p` de Docker puede anular las expectativas de tu firewall del host.

El riesgo de mala configuración es establecer `server.bind = 0.0.0.0` y abrir el firewall. Si debes exponer la API, hazlo a través de un proxy inverso con TLS y limitación de tasa. Para la rotación manual del token:

```bash
pinchtab config set server.token "$(openssl rand -hex 32)"
```

El modo de fallo más común para los lectores de la guía anterior: un 401 en `/health` porque falta el encabezado `Authorization`. Ahora cada ruta lo requiere.

### IDPI y la lista de navegación permitida

La defensa contra Inyección de Prompts Indirecta (IDPI) está activada por defecto en modo estricto. Escanea el contenido extraído en busca de patrones de inyección y envuelve la salida como no confiable. Más importante para empezar: **restringe la navegación a una lista permitida de sitios solo locales por defecto**. Tu agente no puede navegar por el internet público hasta que permitas dominios explícitamente.

Esto cambia las expectativas de la primera ejecución. Si `pinchtab nav https://example.com` es rechazado, es IDPI funcionando tal como está diseñado. Amplía la lista permitida deliberadamente:

```bash
pinchtab config set security.allowedDomains '["example.com", "docs.example.com"]'
```

<Notice type="warning" title="Tu agente aún no puede navegar por el internet público">
El modo estricto de IDPI incluye una lista de navegación permitida solo local. Este es el comportamiento de v0.15 más sorprendente si actualizas desde la versión anterior. Amplía `security.allowedDomains` solo para los dominios que tus agentes necesitan.
</Notice>

Todos los gates de capacidad están por defecto en `false`. Activa solo lo que un flujo de trabajo necesite:

| Gate | Qué desbloquea |
|------|----------------|
| `security.allowEvaluate` | `POST /evaluate` (ejecución de JavaScript) |
| `security.allowCookies` | `POST /cookies` (inyección de cookies) |
| `security.allowMacro` | Grabación/reproducción de macros |
| `security.allowScreencast` | Screencast en vivo |
| `security.allowDownload` | Descargas de archivos |
| `security.allowUpload` | Subidas de archivos |
| `security.allowStateExport` | Exportación de estado |
| `security.allowNetworkIntercept` | Intercepción de solicitudes |
| `security.allowMemory` | Inspección de memoria |
| `security.allowClipboard` | Acceso al portapapeles |
| `security.allowFileScheme` | Acceso a URLs `file://` |
| `security.attach.enabled` | Attach a Chrome remoto (lista permitida loopback por defecto) |
| `autosolver.enabled` | Resolución de desafíos (incl. Cloudflare Turnstile) |

También relevante: `PINCHTAB_RATE_LIMIT_MAX` limita las solicitudes por cliente por ventana de 10 segundos, `security.trustedProxyCIDRs` maneja el bypass de la guarda SSRF detrás de proxies conocidos, y el dashboard incluye encabezados CSP y HSTS.

Para endurecimiento a nivel de servidor junto a la postura propia de Pinchtab, mira [asegurar un VPS con CrowdSec](/es/crowdsec-servidor-seguro/).

### El perfil de Chrome contiene sesiones activas

Cuando inicias sesión en un sitio a través del Chrome de Pinchtab, esa sesión persiste en el directorio del perfil. Cookies, tokens de autenticación, estado guardado. Un agente con acceso a la API puede usar esas sesiones para actuar como tú en cualquier sitio en el que hayas iniciado sesión. Esto no ha cambiado. El modelo de perfiles simplemente te da mejores herramientas de aislamiento.

Mitigación:
- Usa perfiles dedicados (vía `POST /profiles` o `profiles.baseDir`) con solo las cuentas que tus agentes necesitan
- No inicies sesión con cuentas personales (correo, banca, redes sociales) en perfiles gestionados por agentes
- Trata `~/.pinchtab/` como sensible: `chmod 700 ~/.pinchtab`
- En Docker, el estado persiste en el volumen `pinchtab-data` bajo `/data`. No lo montes donde otros contenedores puedan alcanzarlo

### Modelo de confianza del agente

Un agente con acceso a Pinchtab puede hacer cualquier cosa que un humano con ese navegador pueda hacer. Si tu agente toma instrucciones arbitrarias de usuarios o entradas externas, la inyección de prompts es una preocupación real: un sitio web malicioso podría incrustar instrucciones que engañen al agente para que tome acciones no deseadas. IDPI es la primera línea de defensa, pero no sustituye la delimitación de alcance.

Mitigación:
- Delimita lo que tu agente puede hacer. Si solo necesita leer páginas, no actives `allowEvaluate` ni `allowCookies`
- Registra todas las llamadas a `/action` y `/navigate` para auditoría
- Usa sesiones de agente (`POST /sessions {agentId, grants?}`) para delimitación de autenticación por agente
- Usa auto-handoff (`/tabs/{id}/handoff` / `resume`) como la válvula de escape humana. El handoff pausado bloquea las rutas de acción, y el estado es visible en el dashboard
- Ejecuta agentes con entradas no confiables contra un perfil aislado sin cuentas reales
- Limita la tasa a nivel de proxy inverso para agentes externos

## Un flujo de trabajo típico de agente

Las rutas planas no han cambiado. Aquí hay un ejemplo Python funcional actualizado para v0.15.x:

```python
import httpx
import os

BASE = "http://localhost:9867"
HEADERS = {"Authorization": f"Bearer {os.environ['PINCHTAB_TOKEN']}"}

# Esperar a que Chrome esté listo (no solo el dashboard)
import time
for _ in range(30):
    r = httpx.get(f"{BASE}/health", headers=HEADERS)
    if r.json().get("defaultInstance", {}).get("status") == "running":
        break
    time.sleep(1)

# Navegar a una página
httpx.post(f"{BASE}/navigate", json={"url": "https://example.com"}, headers=HEADERS)

# Obtener solo elementos interactivos para mantener bajos los tokens
snapshot = httpx.get(f"{BASE}/snapshot?filter=interactive&format=compact", headers=HEADERS)
refs = snapshot.json()

# Hacer clic en un botón por su ref
httpx.post(f"{BASE}/action", json={"kind": "click", "ref": "e5"}, headers=HEADERS)

# Leer el resultado
text = httpx.get(f"{BASE}/text", headers=HEADERS)
print(text.text)
```

Ten en cuenta que `/evaluate` devuelve un rechazo a menos que `security.allowEvaluate=true`. Si tu flujo de trabajo necesita ejecución de JavaScript, activa el gate explícitamente.

Para páginas que se actualizan sin una carga completa (SPAs de React, Vue), usa `?diff=true` para ver qué cambió en lugar de volver a obtener todo el árbol. Las refs de nodo sobreviven a cambios de filter/selector/depth (desde v0.15.1) y expiran solo al navegar.

El CLI agrupa acción+snapshot en un solo round trip con `--snap` y `--snap-diff`, que es de donde vienen los ahorros de costo:

```bash
pinchtab nav https://example.com --snap
pinchtab click e5 --snap
```

Para configuraciones multiagente donde varios agentes comparten una instancia del navegador, usa el bloqueo de pestañas:

```bash
# Bloquear la pestaña 1 para uso exclusivo
curl -X POST localhost:9867/tabs/1/lock \
  -H "Authorization: Bearer $PINCHTAB_TOKEN"

# ... haz tu trabajo ...

# Liberarla
curl -X POST localhost:9867/tabs/1/unlock \
  -H "Authorization: Bearer $PINCHTAB_TOKEN"
```

Si quieres conectar la API HTTP de Pinchtab a un framework de agentes real, [construye tu propio agente de IA con Mastra](/es/crear-agente-ia-mastra/) recorre el bucle completo.

## Cuándo encaja bien

Pinchtab encaja bien para la automatización de navegador con IA donde los agentes necesitan navegar por la web sin estar estrechamente acoplados a un framework de pruebas de navegador. Específicamente:

- Scraping web y monitoreo de contenido a cualquier escala
- Automatización de formularios (registros, entrada de datos, flujos de trabajo de múltiples pasos)
- Scraping autenticado después de una configuración de inicio de sesión única
- Agentes ejecutándose en bash, Go, Python, o cualquier lenguaje con soporte HTTP
- Configuraciones donde quieres compartir un plano de control de navegador entre muchos agentes (multi-instancia + bloqueo + sesiones)
- Puertas de calidad de CI usando `pinchtab audit` y `pinchtab compare`
- Cambiar entre frameworks de agentes sin cambiar la integración del navegador

No es la herramienta adecuada para pruebas visuales de precisión de píxeles (Playwright es mejor ahí) ni para sitios donde el árbol de accesibilidad es escaso. Algunas SPAs construidas con componentes personalizados no exponen muchos datos ARIA, y una captura de pantalla completa se convierte en la opción más práctica.

Si no quieres autoalojar, [el MCP de BrightData para scraping web con IA](/es/guia-brightdata-mcp/) cubre casos de uso intensivos de scraping con una red de proxy gestionada, y [la plataforma de datos web de Bright Data](https://go.bitdoze.com/brightdata) maneja scraping a escala. Para una API de navegador gestionada sin infraestructura, [las APIs de navegador gestionado y web-fetch de TinyFish para agentes de IA](https://go.bitdoze.com/tinyfish) te dan una clave de API y cero gestión de servidor. La compensación es el costo por solicitud frente a un VPS de €5/mes ejecutando Pinchtab 24/7.

## Solución de problemas y modos de fallo

<ListCheck>
<ul>
<li><code>pinchtab doctor</code> pasa (ejecuta <code>pinchtab doctor browsers</code> en macOS)</li>
<li><code>pinchtab health</code> con token devuelve <code>"status":"running"</code></li>
<li>El sondeo de preparación se completa antes de la primera navegación</li>
<li><code>pinchtab config validate</code> no reporta errores</li>
<li>La postura de <code>pinchtab security</code> coincide con las expectativas</li>
<li>Prueba de humo: <code>pinchtab nav https://example.com --snap</code> devuelve un snapshot</li>
</ul>
</ListCheck>

Modos de fallo consolidados y correcciones:

| Síntoma | Causa | Corrección |
|---------|-------|------------|
| 401 en cada ruta | Token requerido en todas las rutas incluyendo `/health` | Exporta `PINCHTAB_TOKEN` o añade el encabezado `Authorization: Bearer` |
| 503 en todas las solicitudes | Chrome no está listo (dashboard arriba ≠ Chrome arriba) | Sondea `.defaultInstance.status == "running"` antes de la primera navegación |
| 404 con `browser_crashed` | Chrome se estrelló; la instancia se relanza automáticamente pero todas las pestañas se perdieron | Reconstruye el estado; vigila el bloque `crashes` en `/health`, no solo `status` |
| 400 con pistas "did you mean" | `/action` rechaza parámetros inexpresables en lugar de despachar un clic | Lee la pista, luego corrige el nombre o tipo del parámetro |
| Rechazo con `details.hint` / `details.remedy` | Gate de capacidad o lista permitida IDPI | Lee el campo remedy; activa el gate o amplía `security.allowedDomains` |
| El agente no puede alcanzar un sitio público | Lista permitida solo local de IDPI | `pinchtab config set security.allowedDomains '["domain.com"]'` |
| Pestañas de Chrome muriendo / OOM del renderer | `shm_size` demasiado bajo o `mem_limit` demasiado bajo | Establece `shm_size: "2gb"` y `mem_limit: 2g` como mínimo |
| Config no recogida en Docker | Config montada sin `server.token` → el servidor se niega a arrancar | Establece `server.token` en la config o pasa `-e PINCHTAB_TOKEN=...` |
| Comportamiento extraño del navegador en macOS | Conflicto de perfil con el Chrome habitual | `pinchtab doctor browsers`; usa Chrome for Testing |

## Preguntas frecuentes

<Accordion label="¿Dejaron de funcionar las antiguas variables de entorno BRIDGE_*?" group="faq" expanded="true">
Sí. Las variables de entorno `BRIDGE_*` de la versión de principios de 2026 están muertas y se ignoran silenciosamente. La configuración es ahora un archivo JSON anidado en `~/.pinchtab/config.json` gestionado mediante `pinchtab config get/set/show/validate`, más cinco variables de entorno `PINCHTAB_*` que lo anulan. Consulta el cuadro de migración en la sección de configuración para el mapeo completo de antiguo a nuevo.
</Accordion>

<Accordion label="¿Por qué /health devuelve 401 ahora?" group="faq">
La autenticación está activada por defecto desde la revisión de seguridad. El token se autogenera durante la configuración de primera ejecución. Expórtalo con `export PINCHTAB_TOKEN=$(pinchtab config token --stdout)` e incluye `Authorization: Bearer $PINCHTAB_TOKEN` en cada solicitud. No hay forma de desactivar la autenticación y no debería haberla. La antigua postura de "sin autenticación por defecto" ha desaparecido.
</Accordion>

<Accordion label="¿Por qué mi agente no puede alcanzar example.com?" group="faq">
IDPI (defensa contra Inyección de Prompts Indirecta) se incluye en modo estricto con una lista de navegación permitida solo local. Tu agente literalmente no puede navegar por el internet público hasta que amplíes `security.allowedDomains`. Esto es deliberado: evita que páginas con prompts inyectados redirijan a tu agente a sitios arbitrarios. Amplía la lista permitida solo para los dominios que tus agentes necesitan: `pinchtab config set security.allowedDomains '["example.com"]'`.
</Accordion>

<Accordion label="¿Sigo necesitando seccomp=unconfined para Docker?" group="faq">
No. El requisito `seccomp=unconfined` se ha eliminado por completo. La imagen oficial de Docker está endurecida por defecto: usuario no-root, `cap_drop: ALL`, `read_only: true`, `no-new-privileges`, y el perfil seccomp por defecto. Chrome se ejecuta con `--no-sandbox` dentro del contenedor precisamente porque el límite del contenedor es la capa de seguridad. El antiguo workaround es obsoleto.
</Accordion>

<Accordion label="¿Cuánto cuesta ejecutar Pinchtab?" group="faq">
Pinchtab en sí tiene licencia MIT sin telemetría y sin suscripción. Tus costos son un VPS (€4-10/mes por una máquina de 2 vCPU / 2-4GB que lo ejecuta cómodamente) más los costos de tokens del modelo. Los árboles de accesibilidad mantienen bajo el uso de tokens: `/text` ronda los 800 tokens por página frente a miles para capturas de pantalla, así que la factura del modelo es manejable incluso para automatización pesada.
</Accordion>
