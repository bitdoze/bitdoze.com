Esta guía de despliegue de NullClaw cubre todo lo que necesitas para autoalojar el asistente de IA más pequeño que he encontrado que aún hace de todo. [NullClaw](https://github.com/nullclaw/nullclaw) es un único binario estático escrito en Zig, aproximadamente 1 MB de RAM en ejecución, sin dependencias de runtime, sin overhead de framework. Arranca en menos de 2 milisegundos y corre en cualquier cosa que tenga CPU, incluyendo placas ARM de $5. El proyecto tiene ~8,200 estrellas en GitHub e incluye 5,300+ tests, 50+ proveedores LLM y 19 canales de chat.

Una nota honesta antes de descargar nada: la cifra del "binario de 678 KB" proviene de una compilación `ReleaseSmall` hecha a mano. Los binarios oficiales de GitHub pesan 4.4-6.5 MB. Ambos son diminutos; simplemente no pienses que descargaste el archivo equivocado si tu descarga pesa más de 678 KB.

Esta guía recorre la instalación, los proveedores, los canales, la memoria, el sandboxing y la ejecución del gateway bajo systemd en un VPS.

Los dos principales bloqueos de la instalación son una versión incorrecta de Zig (la compilación requiere 0.16.0 exacto) y un plugin de Docker Compose ausente. Ambos aparecen en la sección de resolución de problemas más abajo.

## Qué es NullClaw

NullClaw es un asistente de IA escrito completamente en Zig. El eslogan es "null overhead, null compromise". Se distribuye como un binario estático con cero dependencias de runtime que corre en el hardware más barato que puedas encontrar.

La arquitectura usa interfaces vtable para cada subsistema. ¿Quieres cambiar tu proveedor LLM? Cambia una línea de configuración. Lo mismo para canales, backends de memoria, herramientas, túneles, sandboxes y periféricos. El ecosistema a su alrededor también está creciendo: NullHub (una UI web para gestión de configuración y procesos), NullBoiler (orquestación de flujos de trabajo) y NullWatch (observabilidad).

```
678 KB source build · <2 ms startup · 5,300+ tests · 50+ providers · 19 channels · Pluggable everything
```

## Por qué Zig

Zig es un lenguaje de sistemas que compila a rendimiento tipo C con cero overhead de runtime. Para NullClaw, los beneficios prácticos son:

| Propiedad | Qué significa para NullClaw |
|----------|---------------------------|
| Sin recolector de basura | Memoria determinística, sin pausas |
| Sin asignaciones ocultas | Tú controlas cada byte |
| Binario estático | Sin dependencias, soltar y ejecutar |
| Ejecución en tiempo de compilación | Validación de config en tiempo de build |
| Compilación cruzada | Compilar para ARM desde x86 |

Esa compilación de 678 KB desde el código fuente cubre el mismo conjunto de funciones que alternativas que pesan decenas de megabytes o más.

## Instalación

Hay cinco formas de poner NullClaw en marcha. El orden de abajo coincide con la documentación oficial: de más fácil a más difícil.

<Notice type="warning" title="Fija tu versión (pre-1.0, CalVer)">
NullClaw usa CalVer (`vYYYY.M.D`) y es pre-1.0. El README dice explícitamente que "la configuración y el CLI pueden cambiar entre releases". Fija `NULLCLAW_IMAGE=ghcr.io/nullclaw/nullclaw:v2026.5.29` en producción y compara tu configuración con `config.example.json` en el tag que despliegues. El último tag estable es v2026.5.29 (mayo 2026); `main` tiene meses de commits más nuevos y hay un canal prerelease `nightly` si quieres ir a la última.
</Notice>

### Instalar con Homebrew

La vía recomendada en macOS y Linux:

```bash
brew install nullclaw
nullclaw --version   # should print the formula version (stable 2026.5.29)
```

La fórmula viene embotellada, así que no hay compilación. Para actualizar después: `brew upgrade nullclaw`. NullClaw también incluye un comando de auto-actualización: `nullclaw update --check` y luego `nullclaw update --yes`.

### Ejecutar la imagen oficial de Docker

La imagen de contenedor está en `ghcr.io/nullclaw/nullclaw`. El estado vive en un volumen con nombre en `/nullclaw-data` (`/nullclaw-data/config.json`, `/nullclaw-data/workspace`).

```bash
# Onboard first (interactive wizard)
docker run --rm -it -v nullclaw-data:/nullclaw-data \
  ghcr.io/nullclaw/nullclaw:latest onboard --interactive

# Run the gateway
docker run -d \
  -p 127.0.0.1:3000:3000 \
  -v nullclaw-data:/nullclaw-data \
  --name nullclaw \
  ghcr.io/nullclaw/nullclaw:latest
```

Verifica: `docker logs nullclaw` debería mostrar el banner de arranque y el gateway escuchando en el puerto 3000.

### Desplegar con Docker Compose

El repositorio incluye un `docker-compose.yml` y un Makefile con perfiles:

```bash
git clone https://github.com/nullclaw/nullclaw.git && cd nullclaw

# Pin the image
export NULLCLAW_IMAGE=ghcr.io/nullclaw/nullclaw:v2026.5.29

# Onboard (runs interactive wizard in the agent container)
make config

# Start the gateway
make up

# Verify
curl http://127.0.0.1:3210/health
```

El contenedor del gateway se vincula a `0.0.0.0:3210` internamente y publica en `127.0.0.1:3210` del host. Otros targets útiles: `make logs`, `make down`, `make shell`. Los builds de Compose usan `ZIG_VERSION: "0.16.0"`.

<Notice type="error" title="Nunca pases secretos vía CONFIG_ARGS">
`make config` acepta valores no secretos a través de `CONFIG_ARGS`, pero pasar claves API ahí las deja en el historial del shell y en los listados de procesos. Además, NullClaw no expande variables de entorno estilo `VAR` en `config.json`, así que genera el archivo con tu herramienta de despliegue (envsubst, Ansible) en su lugar. Consulta [secretos de Docker Compose y alternativas seguras](/es/secretos-docker-compose/) para el panorama completo.
</Notice>

Fallos comunes de Compose: nombre de proyecto equivocado (volúmenes obsoletos de un proyecto `docker compose` anterior), `docker compose down -v` borrando tu volumen de estado, y el puerto 3210 ya en uso.

### Descargar binarios precompilados

La release v2026.5.29 incluye 15 assets: linux x86_64 (5.48 MB), linux aarch64 (4.40 MB), arm32 gnu/musl, riscv64, macOS x86_64/aarch64, Windows x86_64/aarch64 y Android aarch64/armv7/x86_64.

```bash
curl -LO https://github.com/nullclaw/nullclaw/releases/download/v2026.5.29/nullclaw-linux-x86_64.bin
chmod +x nullclaw-linux-x86_64.bin
sudo mv nullclaw-linux-x86_64.bin /usr/local/bin/nullclaw
nullclaw --version
```

Estos binarios pesan 4.4-6.5 MB. Ese es el build oficial del CI. La cifra de 678 KB corresponde a un build `ReleaseSmall` optimizado a mano que compilas tú mismo.

### Compilar desde el código fuente

Haz esto solo si necesitas un build personalizado o quieres el binario más pequeño posible. Necesitas Zig 0.16.0 exacto. Otras versiones fallan con errores de compilación crípticos.

```bash
# Install Zig 0.16.0
curl -L https://ziglang.org/download/0.16.0/zig-linux-x86_64-0.16.0.tar.xz | tar -xJ
sudo mv zig-linux-x86_64-0.16.0 /usr/local/zig
sudo ln -s /usr/local/zig/zig /usr/local/bin/zig
zig version   # MUST print 0.16.0

# Clone and build
git clone https://github.com/nullclaw/nullclaw.git && cd nullclaw
zig build -Doptimize=ReleaseSmall

# Binary at zig-out/bin/nullclaw
ls -lh zig-out/bin/nullclaw

# Optional: run the test suite (5,300+ tests)
zig build test --summary all

# Install
zig build -Doptimize=ReleaseSmall -p "$HOME/.local"
```

Compilación cruzada para ARM: `zig build -Dtarget=aarch64-linux -Doptimize=ReleaseSmall` funciona para targets genéricos. Android necesita la libc del NDK, así que la mayoría de lectores deberían simplemente descargar el binario precompilado de las releases.

### Onboarding y primera verificación

Tras cualquier vía de instalación, ejecuta el asistente de onboarding:

```bash
# Quick non-interactive setup
nullclaw onboard --api-key sk-or-... --provider openrouter

# Or the interactive wizard
nullclaw onboard --interactive
```

Esto crea `~/.nullclaw/` con un `config.json` y una carpeta de workspace.

## Configurar proveedores LLM

NullClaw soporta 50+ proveedores de fábrica. Cada proveedor usa una interfaz compatible con OpenAI, así que cambiar es solo un cambio de configuración.

<Notice type="warning" title="No existe la clave default_provider">
Las claves de nivel superior `default_provider` y `default_model` **no están soportadas**. No hacen nada silenciosamente. La selección de proveedor pasa por `agents.defaults.model.primary` con una ruta de modelo con prefijo de proveedor como `openrouter/anthropic/claude-sonnet-4`. Un formato de ruta inválido es una causa documentada de errores 401/403.
</Notice>

### Obtener una clave API

Para OpenRouter (recomendado por flexibilidad):

1. Ve a [openrouter.ai](https://openrouter.ai)
2. Crea una cuenta y genera una clave API
3. La clave empieza con `sk-or-`

### Agregar a la configuración

Edita `~/.nullclaw/config.json`:

```json
{
  "default_temperature": 0.7,
  "models": {
    "providers": {
      "openrouter": {
        "api_key": "sk-or-your-key"
      }
    }
  },
  "agents": {
    "defaults": {
      "model": {
        "primary": "openrouter/anthropic/claude-sonnet-4"
      }
    }
  }
}
```

Fíjate en el formato de ruta con prefijo de proveedor: `openrouter/anthropic/claude-sonnet-4`, no `anthropic/claude-sonnet-4` a secas. Los IDs de modelo mostrados aquí son ejemplos. Comprueba los nombres actuales en OpenRouter antes de desplegar.

### Usar proveedores personalizados

Cualquier endpoint compatible con OpenAI funciona:

```json
{
  "models": {
    "providers": {
      "minimax": {
        "api_key": "your-minimax-key",
        "base_url": "https://api.minimax.chat/v1"
      }
    }
  },
  "agents": {
    "defaults": {
      "model": {
        "primary": "minimax/minimax-m2.7"
      }
    }
  }
}
```

Las rutas de modelo también soportan la sintaxis `custom:https://endpoint/model-name` para endpoints que no están en la lista de proveedores integrada.

### Probar

```bash
nullclaw agent -m "What's 42 * 17?"
```

Salida esperada: una respuesta del modelo con la respuesta (714). Si obtienes un 401/403, revisa la clave API, el nombre del proveedor en `models.providers` y el formato de la ruta del modelo (el prefijo de proveedor es obligatorio). Consulta la tabla de resolución de problemas más abajo.

## Fiabilidad y failover

Esta es la sección que convierte un bot de demostración en uno que puedes dejar corriendo desatendido. El bloque `reliability` maneja los fallos de proveedor con elegancia.

```json
{
  "reliability": {
    "provider_retries": 1,
    "provider_backoff_ms": 3000,
    "fallback_providers": ["groq"],
    "model_fallbacks": [
      {
        "model": "openrouter/anthropic/claude-sonnet-4",
        "fallbacks": ["openrouter/z-ai/glm-5.3"]
      }
    ]
  }
}
```

- `provider_retries` / `provider_backoff_ms`: reintentos ante errores transitorios (429, 5xx). Yo mantendría los reintentos conservadores (`1`) y el backoff en 3000 ms para no quemar tokens en fallos repetidos.
- `fallback_providers`: una lista de nombres de proveedores a probar si el primario falla por completo.
- `model_fallbacks`: cadenas de fallback por modelo. Si el modelo primario está caído, NullClaw recorre la lista.
- `api_keys`: varias claves para rotación si estás alcanzando los límites de tasa en un equipo.

También hay opciones de circuit breaker a nivel de memoria: `circuit_breaker_failures` y `circuit_breaker_cooldown_ms` para dejar de machacar a un proveedor de embeddings que está fallando.

Nota de costes: los reintentos cuestan tokens (pagas por los intentos fallidos que llegan a la API). Los fallbacks no cuestan nada hasta que se usan.

### Enrutado de modelos y recarga en caliente

Los comandos interactivos de NullClaw te dan control en vivo sobre la selección de modelo:

- `/model`: muestra todas las rutas con metadatos `cost_class` y `quota_class`. Fija un modelo específico o cambia a enrutado automático (`model_routes`).
- `/config reload`: recarga en caliente las claves de configuración soportadas sin reiniciar el gateway.

Esto significa que puedes cambiar de modelo a mitad de conversación o tras una caída del proveedor sin tocar el proceso.

### Bot de Telegram con NullClaw

1. Crea un bot vía [@BotFather](https://t.me/BotFather)
2. Copia el token del bot
3. Obtén tu ID de usuario de Telegram (envía un mensaje a [@userinfobot](https://t.me/userinfobot))

Configuración:

```json
{
  "channels": {
    "telegram": {
      "accounts": {
        "main": {
          "bot_token": "123456789:ABCdefGHIjklMNOpqrSTUvwxYZ",
          "allow_from": ["your_telegram_user_id"],
```

`allow_from` vacío significa **denegar todos**. Usa `["*"]` para permitir a todos, o agrega IDs de usuario específicos para restringir el acceso.
</Notice>

### Enrutar chats a agentes (multi-agente)

Si necesitas bots con ámbitos diferenciados (digamos, un asistente de "trabajo" y uno de "casa"), NullClaw soporta `agents.list` con `id`, `model`, `system_prompt` y `workspace_path` por agente. Cada agente obtiene namespaces de memoria duraderos `agent:<id>`.

Enruta chats específicos o temas de foros de Telegram a agentes con `bindings[]`. El enrutado por temas usa `"<chat_id>:thread:<topic_id>"`. En runtime: `/bind` para enrutar, `/bind status` o `/bind clear` para inspeccionar o deshacer. Los subagentes funcionan vía `/subagents spawn --agent <id>` y la herramienta `delegate`.

Mi recomendación: sáltate esto a menos que ejecutes varios bots con ámbitos diferenciados. Un solo agente es más simple de depurar.

## Ejemplo de configuración completa

Aquí tienes un `~/.nullclaw/config.json` completo usando el esquema actual. Sin clave `default_provider`. En su lugar, una ruta de modelo con prefijo de proveedor:

```json
{
  "default_temperature": 0.7,

  "models": {
    "providers": {
      "openrouter": { "api_key": "sk-or-..." }
    }
  },

  "agents": {
    "defaults": {
      "model": { "primary": "openrouter/anthropic/claude-sonnet-4" },
      "heartbeat": { "every": "30m" }
    }
  },

  "channels": {
    "telegram": {
```

## Sistema de memoria

La memoria por defecto de NullClaw está basada en SQLite sin dependencias externas: búsqueda por palabras clave FTS5 con puntuación BM25 y similitud coseno vectorial, fusionadas con pesos configurables.

Ahora hay **10 motores de memoria**: SQLite (por defecto), Markdown, ClickHouse, PostgreSQL, Redis, LanceDB, Lucid, LRU, API y None. El backend PostgreSQL encaja bien si ya ejecutas Postgres. Consulta nuestra guía para [autoalojar pgvector con Docker](/es/desplegar-pgvector-pgadmin-docker/).

Las claves de configuración usan un esquema anidado:

```json
{
  "memory": {
    "backend": "sqlite",
    "auto_save": true,
    "embedding_provider": "openai",
    "search": {
      "query": {
        "hybrid": { "enabled": true, "vector_weight": 0.7, "text_weight": 0.3 }
      },
      "store": {
        "type": "builtin"
      }
    },
    "lifecycle": {
      "hygiene_enabled": true,
      "archive_after_days": 30,
      "purge_after_days": 90,
      "snapshot_enabled": true,
      "auto_hydrate": true
    }
  }
}
```

La búsqueda híbrida está desactivada por defecto, así que actívala explícitamente con `search.query.hybrid.enabled: true`. La clave `search.store` también soporta opciones sidecar de Qdrant y pgvector.

Configura `embedding_provider` a `noop` si no quieres pagar por embeddings. La búsqueda por palabras clave FTS5 sigue funcionando sin embeddings.

### Archivos de identidad

NullClaw soporta dos formatos de identidad:

| Formato | Archivos | Caso de uso |
|--------|-------|----------|
| `openclaw` | `IDENTITY.md`, `SOUL.md`, `USER.md` | Basado en Markdown |
| `aieos` | Un solo archivo JSON | Personas de IA portables |

Edita estos en `~/.nullclaw/workspace/` para personalizar la personalidad del bot y su conocimiento sobre ti.

### Operaciones de memoria

Comandos de memoria de nivel operador para backup y mantenimiento:

```bash
# Export all memory (PII-redacted by default, stable schema_version)
nullclaw memory export-jsonl > memory-backup.jsonl

# Non-destructive duplicate report
nullclaw memory hygiene-report

# Rebuild search indexes
nullclaw memory reindex

# Drain the outbox queue
nullclaw memory drain-outbox

# Forget specific memories
nullclaw memory forget <id>
```

`memory export-jsonl` es tu primitiva de backup de memoria. Ejecútala antes de las actualizaciones. La redacción de PII está activada por defecto, que es el comportamiento correcto para cualquier cosa que salga de la máquina.

## Modelo de seguridad

NullClaw bloquea las cosas en múltiples niveles, no solo listas de permitidos a nivel de aplicación.

### Seguridad del gateway

| Capa | Por defecto | Qué hace |
|-------|---------|-------------|
| Vinculación a localhost | `127.0.0.1` | Rechaza exposición pública |
| Emparejamiento requerido | `true` | Intercambio de código de 6 dígitos por bearer token |
| Túnel requerido | `false` | Rechaza `0.0.0.0` sin túnel |

`/pair` es solo POST y tiene límite de tasa, y los códigos incorrectos repetidos disparan un bloqueo temporal. El flujo de emparejamiento:

```bash
# Start gateway (shows pairing code)
nullclaw gateway

# Exchange code for token
curl -X POST http://127.0.0.1:3000/pair \
  -H "X-Pairing-Code: 123456"

# Use token for requests
curl -X POST http://127.0.0.1:3000/webhook \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"message": "Hello, nullclaw!"}'
```

Para exponer el gateway externamente, configura un túnel:

```json
{
  "tunnel": {
    "provider": "cloudflare"
  }
}
```

Túneles soportados: Cloudflare, Tailscale, ngrok o un binario personalizado con `start_command`/`health_url`. Si prefieres usar port forwarding por SSH, consulta [túneles SSH en Linux](/es/tuneles-ssh-linux/).

### Aislamiento con sandbox

NullClaw auto-detecta el mejor backend de sandbox:

| Backend | Plataforma | Nivel de seguridad |
|---------|----------|---------------|
| Landlock | Linux 5.13+ | Nivel de kernel |
| Firejail | Linux | Namespaces |
| Bubblewrap | Linux | Contenedores ligeros |
| Docker | Cualquiera | Aislamiento completo por contenedor |

```json
{
  "security": {
    "sandbox": { "backend": "auto" }
  }
}
```

Configura `"backend": "docker"` para máximo aislamiento. La imagen de runtime de Docker es configurable (actualmente `alpine:3.24`) con opciones de aislamiento de red y rootfs de solo lectura. El vtable de runtime también soporta WASM (wasmtime) junto a Native y Docker.

### Secretos encriptados

Las claves API se encriptan con ChaCha20-Poly1305 (prefijo `enc2:` en la configuración):

```json
{
  "secrets": { "encrypt": true }
}
```

La clave de encriptación se almacena localmente en `~/.nullclaw/`. Para la ruta de arranque del servicio, `~/.nullclaw/service-env` (si es ejecutable) corre antes de que el servicio arranque. Es el hook limpio para inyección de secretos con sops o dotenvx.

### Alcance del workspace y auditoría de secretos

Con `workspace_only = true`, el bot solo puede acceder a archivos dentro de su workspace. Los intentos de escape vía symlink se bloquean mediante canonicalización de rutas.

`nullclaw workspace audit` escanea el workspace en busca de credenciales filtradas:

```bash
# Scan for secrets (token prefixes, PEM blocks, creds-in-URLs, entropy)
nullclaw workspace audit

# CI-friendly output
nullclaw workspace audit --json --fail-on high
```

Detecta prefijos de tokens `AKIA...`, `ghp_`, `sk-`, bloques PEM, credenciales embebidas en URLs y cadenas de alta entropía. La opción `--llm-triage external` envía contexto redactado a un LLM para triaje sin exponer el secreto en sí. Los resultados de la auditoría van a `audit-log.jsonl`.

Para un hardening de seguridad más amplio más allá de NullClaw, consulta [nuestra guía de seguridad de OpenClaw que cubre skills maliciosos y más de 40 correcciones](/es/guia-seguridad-openclaw/). NullClaw comparte la superficie de configuración compatible con OpenClaw.

### Hardening de autonomía

Nuevas claves de configuración controlan lo que el bot puede ejecutar:

```json
{
  "autonomy": {
    "level": "supervised",
    "workspace_only": true,
    "max_actions_per_hour": 20,
    "block_high_risk_commands": true,
    "block_medium_risk_commands": true,
    "require_approval_for_medium_risk": true
  }
}
```

- `block_high_risk_commands`: bloquea operaciones destructivas.
- `block_medium_risk_commands`: bloquea `curl`, `wget`, `nc`, `scp`, `git commit`, `npm install` y similares.
- `require_approval_for_medium_risk`: humano en el bucle para cualquier cosa de riesgo medio.
- `allowed_paths`: restringe el acceso al sistema de archivos a directorios específicos.
- Los procesos hijo del shell reciben una lista mínima de variables de entorno permitidas (PATH, HOME, TERM...) por defecto. Usa `tools.path_env_vars` para variables de ruta validadas como `LD_LIBRARY_PATH`.

<Notice type="warning" title="Ajustes de alto riesgo">
Nunca configures `autonomy.level` a `full` o `yolo` en un VPS público. Nunca uses `allowed_commands: ["*"]`. Nunca desactives ambos bloques en un bot siempre activo. El modo supervisado con ambos bloques activados es el valor por defecto correcto.
</Notice>

## Tareas programadas

NullClaw tiene un programador cron integrado con tareas recurrentes y de una sola ejecución:

```bash
# Recurring shell command
nullclaw cron add "0 9 * * *" "curl -s https://api.example.com/health"

# Recurring agent prompt (with model, channel, and announce options)
nullclaw cron add-agent "0 9 * * *" "What's on my calendar today?" \
  --model openrouter/anthropic/claude-sonnet-4 --channel telegram --announce

# One-shot delayed command
nullclaw cron once 10m "echo done"

# One-shot delayed agent prompt
nullclaw cron once-agent 10m "Summarize today's logs" --session-target isolated

# Manage tasks
nullclaw cron list
nullclaw cron status <id>
nullclaw cron runs <id>
nullclaw cron update <id> --expression "0 10 * * *"
nullclaw cron pause <id>
nullclaw cron resume <id>
nullclaw cron run <id>
nullclaw cron remove <id>
```

Las tareas se persisten en JSON y sobreviven a reinicios. También puedes gestionar los cron jobs por HTTP vía los endpoints `/cron*` del gateway.

### Servicio systemd

Hay dos formas de ejecutar NullClaw como servicio.

**Oficial: `nullclaw service install`.** En Linux, esto usa `systemd --user` (no a nivel de sistema). En un VPS root, esto necesita `loginctl enable-linger` o el servicio muere cuando cierras sesión:

```bash
loginctl enable-linger root
nullclaw service install
nullclaw service start
nullclaw service status
```

**Pragmático para un VPS root: unidad manual a nivel de sistema.** Esto evita el problema del linger:

```ini
[Unit]
Description=NullClaw AI Assistant
After=network.target

[Service]
Type=simple
ExecStart=/usr/local/bin/nullclaw gateway
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```

Guárdalo en `/etc/systemd/system/nullclaw.service`, luego:

```bash
systemctl daemon-reload
systemctl enable nullclaw
systemctl start nullclaw
systemctl status nullclaw
journalctl -u nullclaw -f
```

Los logs van a `~/.nullclaw/logs/daemon.stdout.log` y `daemon.stderr.log` (los nombres de archivo conservan el antiguo nombre "daemon". Es solo la nomenclatura de logs; el comando es `gateway`).

Modos de fallo: linger no habilitado (el servicio muere al cerrar sesión) y `ExecStart` referenciando el antiguo comando `daemon` (la unidad falla inmediatamente).

### Fallos comunes y soluciones

| Fallo | Causa | Solución |
|---------|-------|-----|
| 401/403 en la llamada al agente | Clave incorrecta/caducada, nombre de proveedor equivocado o ruta de modelo inválida | Revisa la clave API, verifica que el nombre del proveedor coincida con `models.providers`, usa la ruta con prefijo de proveedor (`openrouter/model-name`) |
| Límite de tasa 429 | Cuota del plan excedida | Ajusta `reliability` de forma conservadora: `provider_retries: 1`, `provider_backoff_ms: 3000` |
| Gateway inalcanzable externamente | Sigue en `127.0.0.1`, túnel no levantado o firewall | Configura un túnel o revisa las reglas del firewall; `allow_public_bind` requiere opt-in explícito |
| La compilación falla de forma críptica | Versión de Zig incorrecta | `zig version` debe imprimir `0.16.0` exacto |
| Estado de Docker ausente | Ruta de volumen equivocada o `down -v` lo borró | El estado vive en `/nullclaw-data`; nunca uses `docker compose down -v` a la ligera |
| Claves de config ignoradas | Placeholders de variables de entorno no expandidos, o clave renombrada entre releases | Genera la config con envsubst/Ansible; haz diff contra `config.example.json` de tu tag |
| El servicio muere al cerrar sesión | `systemd --user` sin linger | `loginctl enable-linger` o usa la unidad manual a nivel de sistema |
| Error `scheduler_tool` de Ollama | Bug conocido en builds antiguos | Actualiza NullClaw. No reconfigures |
| Bloqueo de código de emparejamiento | Demasiados intentos fallidos de `/pair` | Espera a que pase la ventana de bloqueo |

## API del gateway

| Endpoint | Método | Auth | Descripción |
|----------|--------|------|-------------|
| `/health` | GET | Ninguna | Chequeo de salud |
| `/pair` | POST | `X-Pairing-Code` | Intercambiar código por token (con límite de tasa) |
| `/webhook` | POST | Bearer token | Enviar mensaje (modo sync para workers con token emparejado) |
| `/whatsapp` | GET | Parámetros de query | Verificación de webhook de Meta |
| `/whatsapp` | POST | Firma de Meta | WhatsApp entrante |
| `/media/transcribe` | POST | Bearer token | STT: audio en base64 a texto (p. ej. Groq whisper-large-v3) |
| `/cron`, `/cron/add`, `/cron/remove` | GET/POST | Bearer token | Gestión de cron por HTTP |
| `/cron/pause`, `/cron/resume`, `/cron/update` | POST | Bearer token | Ciclo de vida del cron |
| `/telegram` | POST | `X-Telegram-Bot-Api-Secret-Token` | Webhook de Telegram (coincide con `webhook_secret`) |
| `/max` | POST | `X-Max-Bot-Api-Secret` | Webhook del messenger Max |
| `/api/messages` | POST | JWT de Teams | MS Teams Bot Framework |
| `/.well-known/agent-card.json` | GET | Ninguna | Tarjeta de agente A2A (pública) |
| `/a2a` | POST | Bearer token | Protocolo A2A (JSON-RPC 2.0) |

El soporte A2A sigue el protocolo v0.3.0: métodos `message/send`, `message/stream` y `tasks/*`. Nota: algunas versiones de la documentación referencian `/.well-known/agent.json` en lugar de `agent-card.json`. Verifícalo en tu gateway en vivo.

Claves de ajuste del gateway: `max_body_size_bytes`, `request_timeout_secs`, `webhook_rate_limit_per_minute`. Configúralas en el bloque `gateway` de la configuración.

El emparejamiento es solo POST y tiene límite de tasa con bloqueo temporal tras códigos incorrectos repetidos. Si te bloqueas a ti mismo, reinicia el gateway para obtener un código de emparejamiento nuevo.

<Accordion label="Preguntas frecuentes" group="faq" expanded="true">

**¿Cuánto cuesta ejecutar NullClaw?**

Hardware: $5 por una placa ARM barata, o $0 si ya tienes un VPS de [Hetzner](https://go.bitdoze.com/hetzner) o [Hostinger](https://go.bitdoze.com/hostinger-vps). Los costes de API dependen de tu proveedor. Espera $5-50/mes para uso personal como orden de magnitud, no como promesa. La mayor palanca de coste es la elección del modelo: los modelos open-source económicos a través de OpenRouter cuestan una fracción de los modelos frontera.

**¿Puedo ejecutar NullClaw sin costes de API?**

Sí. Configura Ollama como tu proveedor y apúntalo a un modelo local. Necesitas hardware que pueda ejecutar inferencia. Un [mini PC como el ASUS DC510](https://go.bitdoze.com/asus-dc510) maneja bien los modelos pequeños. Consulta nuestra [configuración de Ollama con Docker Compose y Open WebUI](/es/ollama-docker-instalacion/) para el stack de modelos locales, y los [mejores mini PC para LLMs locales](/es/mejores-mini-pc-llm-local/) para elegir hardware.

**¿NullClaw funciona en una Raspberry Pi Zero?**

El proyecto apunta a placas de $5 y la Pi Zero 2 W (512 MB) está en su tabla de hardware soportado. El asistente en sí corre bien en hardware mínimo; la limitación es siempre la inferencia del LLM si ejecutas modelos locales.

**¿Pueden varias personas usar una instancia de NullClaw?**

Sí. Agrega múltiples IDs de usuario a `allow_from`. Cada persona obtiene su propio contexto de conversación.

**¿Cuál es la diferencia entre gateway y daemon?**

`nullclaw gateway` **es** el runtime de larga duración. Arranca el gateway más todos los canales configurados, el heartbeat y el programador. No hay un comando `daemon` separado en el CLI actual (la palabra "daemon" solo sobrevive en nombres de archivos de log internos como `daemon.stdout.log`).

**¿Cómo actualizo NullClaw?**

Depende de tu método de instalación: `nullclaw update --check` y luego `nullclaw update --yes` (instalaciones binarias), `brew upgrade nullclaw` (Homebrew), o descarga un nuevo tag de Docker fijado y recrea el contenedor. Para Compose: `NULLCLAW_IMAGE=ghcr.io/nullclaw/nullclaw:vNEW make up`. Rollback: fija el tag anterior. CalVer pre-1.0 implica churn en la configuración. Haz diff de `config.example.json` tras cada actualización.

**¿Puedo migrar de OpenClaw a NullClaw?**

Sí. NullClaw tiene un comando de migración integrado:

```bash
nullclaw migrate openclaw --dry-run
nullclaw migrate openclaw
```

Ejecuta siempre `--dry-run` primero para ver qué cambiará.

**¿Por qué se ignoran mis claves de configuración tras una actualización?**

Churn del esquema pre-1.0. Compara tu configuración con `config.example.json` en el tag que desplegaste. Por ejemplo, las claves de memoria pasaron del nivel superior (`vector_weight`, `keyword_weight`) a un esquema anidado (`search.query.hybrid.*`, `lifecycle.*`). En caso de duda, vuelve a derivar tu configuración del archivo de ejemplo del tag.

**¿Cómo agrego un canal que no está soportado?**

Implementa la interfaz vtable `Channel` en `src/channels/` y envía un PR. La arquitectura está diseñada para extensiones.
