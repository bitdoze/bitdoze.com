Astro gana para sitios de contenido, Next.js para apps de React construidas sobre Server Components, y TanStack Start para apps por usuario que necesitan rutas tipadas. Versiones estables el 28 de noviembre de 2026: Astro 7.4.13, Next.js 16.4.6, TanStack Start 1.169.7.

Deja de preguntar "qué framework es mejor". Empieza a preguntar "qué estoy construyendo".

**Astro**, **Next.js** y **TanStack Start** son los tres contendientes claros en el espacio de los meta-frameworks de 2026. Astro pone el contenido primero, no envía JavaScript por defecto, y tiene a Cloudflare detrás desde enero de 2026. Next.js es el caballo de batalla full-stack de React, con RSC como base y ajustado para Vercel. TanStack Start es el retador construido sobre el control del desarrollador, la seguridad de tipos y Vite.

La mayoría de las comparaciones cubren dos de ellos. Esta pone a los tres lado a lado con mediciones públicas, precios de hosting comprobados el 28 de noviembre de 2026 y un marco de decisión. Sin defensas de fan. Sin un ganador falso.

## El estado de los meta-frameworks en 2026

La [encuesta State of JS 2025](https://2025.stateofjs.com/en-US/libraries/meta-frameworks/) pone a Astro en cabeza de satisfacción entre meta-frameworks, 39 puntos por delante de Next.js. Next.js sigue dominando el uso con un 60-70% de adopción, pero su satisfacción no para de caer. TanStack Start no estaba en la lista porque seguía en beta en el momento del lanzamiento, y los encuestados lo escribieron a mano como la principal respuesta "otra". Luego ganó el premio "Revelación del año" en los [Open Source Awards 2026](https://tanstack.com/blog/tanstack-open-source-awards-2026).

En los doce meses hasta noviembre de 2026 se lanzó mucho:

### Qué cambió desde 2025

Cloudflare anunció el 16 de enero de 2026 que The Astro Technology Company, la empresa detrás de Astro, se une a Cloudflare. Astro sigue con licencia MIT y siendo open source, mantiene su gobernanza abierta y su hoja de ruta, y sigue desplegándose en cualquier destino de hosting. Todos los empleados a tiempo completo de Astro pasaron a Cloudflare. Es la misma dinámica que Vercel tiene con Next.js, pero en la otra acera.

Astro publicó dos versiones mayores en 2026, Astro 6 el 10 de marzo y Astro 7 el 22 de junio. Next.js pasó de 16.0 a 16.4 en el mismo periodo: 16.2 añadió una Adapter API estable, y 16.4 activó Cache Components en las apps nuevas.

TanStack Start pasó del RC de v1 el 23 de septiembre de 2025 a una versión 1.0 estable el 13 de octubre de 2026. El equipo de Inngest informó de una [reducción del 83% en el tiempo de desarrollo local](https://inngest.com/blog/migrating-off-nextjs-tanstack-start) tras migrar fuera de Next.js.

## Tres frameworks, tres filosofías

La elección no va de funcionalidades. Va de qué cree cada framework que es la web. Astro apuesta que la web es contenido, así que se optimiza para la entrega estática. Next.js apuesta que la web son aplicaciones, así que se optimiza para el renderizado en servidor de React. TanStack Start apuesta que la web son datos, así que se optimiza para la comunicación cliente-servidor con tipos seguros.

Son apuestas distintas, y los compromisos se derivan de ellas.

### Astro: contenido primero, cero JS por defecto

- **Veredicto:** la opción por defecto para blogs, documentación y sitios de marketing.
- **Ideal para:** páginas de contenido que necesitan unos pocos widgets interactivos.
- **Compromisos:** las islas se ejecutan aisladas, así que el estado compartido entre widgets hay que cablearlo a mano.
- **Precio:** licencia MIT; el hosting estático en Cloudflare es gratis.

Astro usa una arquitectura de islas: las páginas se entregan como HTML estático por defecto, y los componentes interactivos solo se hidratan donde los marcas con una directiva `client:*`. La documentación lo dice sin rodeos: Astro renderiza cada componente de UI a HTML y CSS y elimina el JavaScript del lado del cliente. Un blog típico con Astro envía 0KB de JavaScript al navegador. Cero.

El framework además es agnóstico del framework. Puedes usar React, Vue, Svelte, Solid, Preact o Lit, y mezclarlos en la misma página. Las Content Collections dan gestión de contenido estructurada y con tipos seguros mediante esquemas de Zod (Zod 4 desde Astro 6).

Astro 6 salió el 10 de marzo de 2026 con la Environment API de Vite para la paridad dev/prod y una Content Security Policy integrada. Las Live Content Collections llegaron en la misma versión, para datos que cambian sin recompilar. Astro 7 le siguió el 22 de junio de 2026 con un compilador en Rust y Vite 8.

Entre sus usuarios están Microsoft, Google, Porsche, Cloudflare, OpenAI y NBC News, según la [página principal de Astro](https://astro.build/). Puedes [desplegar un blog de Astro en Cloudflare](/es/desplegar-astrojs-cloudflare/) en minutos. Su capa de base de datos también merece un vistazo; mira cómo [funciona Astro DB con Bunny Database](/es/astro-db-bunny-database/).

### Next.js: el full-stack por defecto de React

- **Veredicto:** la opción por defecto para equipos de React que construyen aplicaciones.
- **Ideal para:** productos SaaS y dashboards que se apoyan en Server Components.
- **Compromisos:** la frontera servidor/cliente y las capas de caché tardan semanas en asimilarse.
- **Precio:** licencia MIT; Vercel Pro cuesta $20 por asiento al mes, o ejecútalo en cualquier servidor Node.

Next.js es el gorila de 800 libras. Con 143,753 estrellas en GitHub y un 60-70% de adopción entre meta-frameworks, es la elección por defecto de los equipos de React. El App Router, React Server Components y el SSR con streaming están diseñados para que el desarrollo full-stack con React se sienta cohesivo.

Next.js 16 llegó el 21 de octubre de 2025. Turbopack es ahora el bundler por defecto (compilaciones 2-5x más rápidas). Cache Components te permite optar por el caché con directivas `"use cache"` en lugar de depender de las viejas capas de caché implícitas. Desde la 16.4 (6 de octubre de 2026), todos los proyectos nuevos de `create-next-app` empiezan con ellas activadas. El soporte de React Compiler significa memoización automática cuando lo activas. Un nuevo `proxy.ts` sustituye al confuso patrón de `middleware.ts`.

Aun así, los puntos débiles son reales. Las fronteras de RSC siguen siendo la fuente de confusión número 1: entender dónde se ejecuta el código (¿servidor? ¿cliente? ¿ambos?) tarda semanas en asimilarse. Los patrones del App Router (layouts, `loading.tsx`, `error.tsx`, rutas paralelas, rutas de intercepción) son potentes pero densos. El autoalojamiento mejoró en la 16.2, que publicó una Adapter API estable; el adaptador del propio Vercel es open source y usa el mismo contrato público.

Next.js 16 también convirtió `params` y `searchParams` en Promises, así que una página hace await de ellos:

```tsx
// app/blog/[slug]/page.tsx
export default async function BlogPost({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  const post = await getPost(slug);
  return (
    <article>
      <h1>{post.title}</h1>
      <div>{post.content}</div>
    </article>
  );
}
```

Configuración de Cache Components en Next.js 16:

```ts
// next.config.ts
const nextConfig = {
  cacheComponents: true,
};
export default nextConfig;
```

### TanStack Start: control del desarrollador por encima de la convención

- **Veredicto:** la opción para apps de React con mucho estado en cliente y un equipo que quiere rutas tipadas.
- **Ideal para:** dashboards, herramientas internas y frontends SaaS que se renderizan por usuario.
- **Compromisos:** un ecosistema más pequeño, menos tutoriales y más configuración si el equipo no conoce TanStack Query.
- **Precio:** licencia MIT; el hosting cuesta lo mismo que cualquier app Node.

TanStack Start sigue un enfoque distinto: trabajo de servidor explícito en lugar de un árbol de componentes propiedad del servidor. Cada componente es un componente de React normal que se renderiza en el servidor y se hidrata en el cliente. El trabajo del servidor va en un `loader` de ruta o en una llamada a `createServerFn`. Cada ruta elige su renderizado: `ssr: true` (el valor por defecto) renderiza en el servidor, `'data-only'` ejecuta solo los loaders allí, y `false` renderiza en el navegador. La versión 1.0 es estable desde el 13 de octubre de 2026.

Su punto fuerte es el sistema de tipos. El enrutado tipado basado en archivos detecta errores de parámetros en tiempo de compilación. `createServerFn` hace explícitas las fronteras del servidor, sin adivinar dónde se ejecuta el código. Los loaders isomórficos funcionan con TanStack Query para la obtención y el caché de datos. La validación de parámetros de búsqueda con Zod evita errores en ejecución por URLs mal formadas.

TanStack Start se compila con Vite 8 o Rsbuild. La documentación lista Cloudflare Workers, Netlify y Railway como socios de hosting oficiales, además de presets de Nitro para Vercel, un servidor Node sin extras, Docker y Bun. Sin vendor lock-in. Para un primer proyecto, sigue la [introducción a TanStack Start y Convex](/es/empezar-tanstack-start/), o construye una [app de tareas con TanStack Start y Drizzle](/es/tanstack-start-bunny-database-drizzle/) para verlo en acción.

```tsx
import { createServerFn } from '@tanstack/react-start';
import { z } from 'zod';

export const createPost = createServerFn({ method: 'POST' })
  .validator(z.object({ title: z.string().min(1) }))
  .middleware([authMiddleware])
  .handler(async ({ data, context }) => {
    return db.posts.create({ title: data.title });
  });
```

Ruta con tipos seguros y loader:

```tsx
export const Route = createFileRoute('/dashboard/')({
  loader: async () => {
    const data = await fetchDashboardData();
    return data;
  },
  component: DashboardPage,
});
```

## ¿Qué framework envía menos JavaScript?

Astro envía menos: una página sin islas no envía JavaScript, mientras que Next.js y TanStack Start envían un runtime de React y un router con cada página. En los datos de HTTP Archive que Astro publica, el 71% de los sitios con Astro tenían buenos Core Web Vitals frente al 35% de los sitios con Next.js.

Cuánto JavaScript envía cada framework por defecto tiene consecuencias reales. Cada kilobyte afecta al Time to Interactive, a los Core Web Vitals y, al final, a tu posicionamiento SEO y a la retención de usuarios.

*Modelos de renderizado el 28 de noviembre de 2026. Astro envía solo islas, Next.js envía React más Client Components, TanStack Start envía React más su router.*

### Qué se envía por defecto

Astro envía 0KB por defecto. El framework elimina el JavaScript del lado del cliente de cada componente a menos que lo marques como isla con una directiva `client:*`. Para una página de blog típica, eso es todo.

Next.js envía su runtime de React más el JavaScript de la página. Aunque React Server Components reducen lo que llega al cliente, una página sigue cargando React, el router y el cliente de hidratación. Los proveedores no publican ninguna cifra base, así que mira los números medidos y léalos como específicos de cada app.

Una comparación de la misma app publicada el 18 de octubre de 2026 midió una página de producto en Next.js 16.4.2 en 135 KB de JavaScript gzip. La misma página construida con TanStack Start 1.169.3 se quedó en 109 KB. Una comparación de junio de 2026 con los Server Components experimentales de TanStack activados midió 193 KB frente a 116 KB. Toma ambas como específicas de cada app, no como constantes del framework.

| Métrica | Astro | Next.js | TanStack Start |
|--------|-------|---------|----------------|
| JavaScript por defecto | ninguno (solo islas) | runtime de React, router, cliente de hidratación RSC | runtime de React, router |
| JS de cliente medido, gzip (test de la misma app, octubre de 2026) | 0KB sin islas | 135 KB | 109 KB |
| Sitios con buenos Core Web Vitals (HTTP Archive) | 71% | 35% | no listado |

Los porcentajes de vitals vienen de los datos de HTTP Archive y Chrome UX Report mostrados en la [página principal de Astro](https://astro.build/) el 28 de noviembre de 2026. Los totales de JavaScript de cliente vienen del [benchmark de la misma app de Waseem Anjum](https://www.fabwaseem.com/blog/tanstack-start-vs-nextjs) y de la [comparación de RSC de LogRocket](https://blog.logrocket.com/tanstack-start-rsc-vs-next-js-rsc-performance-dx-production-readiness/).

Estos números son para sitios de contenido simples y apps pequeñas. A medida que crece el número de islas interactivas en Astro, o el de componentes de cliente en los otros, la diferencia se reduce. Pero la ventaja base es real.

<Notice type="warning" title="Los benchmarks dependen del contexto">
Estos números describen apps de prueba pequeñas. Los benchmarks de apps complejas son muy distintos. La ventaja de Astro se reduce al crecer el número de islas interactivas: un dashboard con 20 islas de React envía mucho más JS que un blog con cero.
</Notice>

Puedes [desplegar Astro en un VPS](/es/desplegar-astro-en-vps/) y medir los vitals en producción.

### Benchmarks de velocidad de compilación

Astro 7 compila un 15-61% más rápido que Astro 6 en los benchmarks del propio proyecto, y los sitios con mucho Markdown ganan más porque el pipeline de Markdown se movió a Rust. El [benchmark de Astro 7 en un sitio de 743 páginas](/es/astro-7-compilaciones-mas-rapidas/) muestra el resultado en este blog: 103 segundos con Astro 6, 47 segundos con Astro 7. La [guía de optimización de la velocidad de compilación de Astro](/es/astro-ssg-optimizacion-build/) cubre las demás palancas.

Next.js 16 con Turbopack es 2-5x más rápido que las antiguas compilaciones con Webpack. TanStack Start se compila con Vite 8. En el test de la misma app citado antes, `next build` tardó 4.86 segundos y la compilación de Start tardó 1.26 segundos. El servidor de desarrollo sirvió la primera página en 2.96 segundos con Next.js y en 1.52 segundos con Start.

## Experiencia de desarrollador y curva de aprendizaje

Los números de rendimiento se pueden medir. La DX se acumula durante meses de desarrollo diario. El mejor framework sobre el papel no es el mejor si tu equipo pelea con él cada sprint.

### El modelo mental de Astro

Astro tiene el modelo mental más simple de los tres: HTML + CSS + islas. El formato de archivo `.astro` usa frontmatter para la lógica y una sintaxis de plantilla parecida a HTML para el marcado. Si sabes HTML, puedes leer un archivo de Astro.

Ser agnóstico del framework significa que tu equipo no queda atado a React. Un desarrollador de Vue puede aportar componentes Svelte al mismo proyecto de Astro. Las Content Collections te dan contenido con tipos seguros y validación por esquema, la mejor DX nativa para gestión de contenido de cualquier framework.

La pega: en cuanto necesitas mucha interactividad, el modelo de islas añade sobrecoste de coordinación. Las islas se ejecutan aisladas entre sí, así que compartir estado entre dos widgets significa cablear un store o un contexto del framework a mano. Ahí es donde Next.js y TanStack Start tienen ventajas naturales.

Si estás aprendiendo Astro, mira los [mejores cursos de Astro.js](/es/mejores-cursos-astrojs-online/) para rutas de aprendizaje estructuradas.

### El impuesto de complejidad de Next.js

Next.js paga su potencia con complejidad. El modelo mental de RSC, entender la frontera servidor/cliente, es la fuente de confusión número 1 para desarrolladores noveles y con experiencia por igual. Los patrones del App Router (layouts, `loading.tsx`, `error.tsx`, rutas paralelas, rutas de intercepción) son potentes pero densos.

El caché ha sido históricamente el peor punto de dolor. Sin Cache Components, el App Router apila cuatro cachés (memoización de peticiones, la Data Cache, la Full Route Cache y la Router Cache), cada una con sus propias reglas de invalidación. Next.js 16 mejora esto con Cache Components y APIs más claras como `updateTag` y `revalidateTag`, pero la curva de aprendizaje sigue siendo empinada.

El compromiso: una vez que lo aprendes, la profundidad del ecosistema es difícil de batir. Más tutoriales, más respuestas en Stack Overflow, más integraciones de terceros y el mayor mercado de contratación de cualquier meta-framework.

### Seguridad de tipos en TanStack Start

TanStack Start se siente como lo más cercano a "React puro" con capacidades de servidor añadidas. No hay ningún modelo mental nuevo que aprender: son componentes de React, hooks de React y TanStack Query. Los componentes se renderizan en el servidor y se hidratan en el cliente, y los Server Components siguen siendo una opción experimental.

El verdadero diferencial es el enrutado con tipos seguros. La validación de parámetros en tiempo de compilación detecta errores de URL antes de que lleguen a producción. `createServerFn` hace explícitas las fronteras del servidor: defines una función, la marcas como función de servidor, y los tipos te dicen exactamente qué tienes disponible. Sin fronteras implícitas, sin adivinaciones.

El compromiso: ecosistema más pequeño, menos tutoriales y una configuración inicial más empinada si no conoces TanStack Query. Encaja mejor con equipos senior cómodos con primitivas más finas pero bien diseñadas.

## ¿Cuánto cuesta alojar cada framework?

Un sitio estático con Astro es gratis de alojar con cualquier nivel de tráfico en Cloudflare, que sirve las peticiones de recursos estáticos gratis y sin límite. Next.js y TanStack Start necesitan un servidor en cuanto renderizan en el servidor, desde $5 al mes en Cloudflare Workers Paid o el precio de un VPS pequeño.

Esta es la sección que la mayoría de comparaciones de frameworks se saltan. Los costes de hosting son el factor oculto de la decisión: eliges un framework, construyes tu app y luego descubres que tu factura de hosting con 50K visitantes es de $500/mes.

### Sitios de contenido estático (10K-100K visitantes)

Los despliegues estáticos de Astro son baratos de alojar, pero "gratis a cualquier escala" depende del host. Cloudflare sirve las peticiones de recursos estáticos gratis y sin límite en sus planes gratuito y de pago. Vercel Hobby incluye 100 GB de transferencia de datos al mes y no vende más en el plan gratuito. El plan Free de Netlify tiene un límite de 300 créditos, y el ancho de banda cuesta 20 créditos por GB. GitHub Pages tiene un límite blando de 100 GB al mes.

Next.js en Vercel Hobby ($0) sirve para sitios pequeños, pero los límites llegan rápido. Hobby incluye 1M de peticiones de CDN, 100 GB de transferencia de datos, 1M de invocaciones de funciones y 4 horas de CPU de funciones al mes. Cuando superas el nivel gratuito, Pro empieza en $20/mes por asiento más un crédito de uso de $20 al mes.

TanStack Start renderiza en el servidor por defecto, así que necesita un servidor o una plataforma serverless desde el primer día. El hosting Node estándar cuesta $4-20/mes en cualquier VPS. Cloudflare Workers Paid cuesta $5 al mes con 10 millones de peticiones incluidas, y el nivel gratuito permite 100,000 peticiones al día con 10 ms de tiempo de CPU por petición.

Fuentes, todas comprobadas el 28 de noviembre de 2026: [precios de Cloudflare Workers](https://developers.cloudflare.com/workers/platform/pricing/), [precios de Cloudflare Pages](https://developers.cloudflare.com/pages/functions/pricing/), [precios de Vercel](https://vercel.com/pricing), [precios de Netlify](https://www.netlify.com/pricing/) y [límites de GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits).

### Apps full-stack a escala

Aquí es donde se pone caro. Vercel factura peticiones, tiempo de CPU y transferencia de datos, no usuarios, así que la tabla de abajo es una estimación del gasto en Vercel Pro por usuarios activos mensuales, no una cotización:

| Usuarios activos mensuales | Coste en Vercel | VPS autoalojado |
|---------------------|-------------|-----------------|
| 10K | $0-50/mes | $4-10/mes |
| 50K | $230-1,180/mes | $10-20/mes |
| 100K | $560-2,250/mes | $20-40/mes |

Contrasta la columna de Vercel con la [lista de precios](https://vercel.com/pricing). Pro incluye 10M de peticiones de CDN y 1 TB de transferencia de datos al mes, y luego cobra $2 por 1M de peticiones y $0.15 por GB. Las invocaciones de funciones se facturan a $0.60 por 1M, y Fluid compute factura la CPU activa desde $0.128 la hora.

<Notice type="warning" title="Los costes de Vercel escalan rápido">
Con 50K MAU podrías estar pagando $1,180/mes en Vercel Pro. Un VPS de Hetzner a $20/mes soporta el mismo tráfico. El impuesto por comodidad es real. Tenlo en cuenta en tu decisión de framework antes de construir.
</Notice>

Consulta los [precios de Hetzner Cloud](/es/hetzner-cloud-precios-2026/) para datos concretos de coste de VPS.

### Autoalojamiento y Docker

Los tres frameworks funcionan en Docker. La diferencia está en lo que produce la compilación y en lo que necesita el servidor.

**Astro**: una compilación estática es una carpeta de archivos que va a cualquier sitio: un CDN, un VPS de $4 con Nginx, S3. El renderizado bajo demanda necesita un adaptador. `@astrojs/node` en modo standalone arranca con `node ./dist/server/entry.mjs`.

**Next.js**: necesita un servidor Node. `next start` sirve la app en cualquier VPS, y la optimización de imágenes, `proxy.ts` y Cache Components funcionan allí sin configuración específica de Vercel. Varias instancias necesitan un cache handler compartido y una clave de cifrado para las funciones de servidor.

**TanStack Start**: una compilación de Vite con Nitro produce un servidor autocontenido. Arráncalo con `node .output/server/index.mjs`. Sin comportamiento específico de plataforma del que preocuparse.

| Framework | Salida de la compilación | Comando de arranque |
|-----------|--------------|---------------|
| Astro (estático) | `dist/` | cualquier servidor de archivos estáticos o CDN |
| Astro (renderizado bajo demanda) | `dist/server/entry.mjs` | `node ./dist/server/entry.mjs` |
| Next.js | `.next/` | `next start` |
| TanStack Start (Vite con Nitro) | `.output/server/index.mjs` | `node .output/server/index.mjs` |

Las salidas y los comandos vienen de las guías de [@astrojs/node](https://docs.astro.build/en/guides/integrations-guide/node/), [autoalojamiento de Next.js](https://nextjs.org/docs/app/guides/self-hosting) y [hosting de TanStack Start](https://tanstack.com/start/latest/docs/framework/react/guide/hosting). Para Dockerfiles y pasos de proxy inverso, sigue [alojar apps de Node.js en CloudPanel](/es/instalar-cloudpanel-alojar-nodejs/) o [desplegar TanStack Start en un VPS con Dokploy](/es/desplegar-tanstack-start-dokploy/).

El punto medio de las PaaS: herramientas como Coolify, Railway y Render ofrecen una comodidad parecida a la de Vercel sin su precio. Si quieres despliegues de un clic en tu propia infraestructura, mira [Coolify como alternativa autoalojada](/es/instalar-coolify-alternativa-heroku/).

## El factor Cloudflare: qué significa la compra de Astro

Cloudflare [anunció el 16 de enero de 2026](https://blog.cloudflare.com/astro-joins-cloudflare/) que The Astro Technology Company se une a Cloudflare. Astro sigue con licencia MIT y siendo open source, mantiene su gobernanza abierta y su hoja de ruta, y sigue desplegándose en todas las plataformas. Para un sitio estático con Astro, nada cambia en el hosting.

![Anuncio de Cloudflare del 16 de enero de 2026, Astro se une a Cloudflare, con la sección sobre qué cambia para Astro](@assets/images/26/07/astro-vs-nextjs-vs-tanstack-start-which-wins-cloudflare-announcement.webp)

*Anuncio de Cloudflare del 16 de enero de 2026 con su sección "What this means for Astro". Se omite la imagen de cabecera entre los dos recortes.*

Un cambio sí llegó al adaptador. Desde la v13, `@astrojs/cloudflare` apunta solo a Workers y ya no es compatible con Cloudflare Pages, y desde Astro 6 ejecuta `workerd` durante el desarrollo y el prerenderizado. Un sitio estático no se ve afectado porque no necesita adaptador.

El incentivo de Cloudflare está claro: convertir a Astro en el mejor framework sobre Cloudflare Workers. Refleja la relación de Vercel con Next.js. Vamos hacia un duopolio: optimizado para Vercel contra optimizado para Cloudflare.

El riesgo: ¿se convertirá Astro en Cloudflare-first de la misma forma que Next.js es Vercel-first? ¿Crearán las funciones específicas de plataforma un vendor lock-in blando?

La tranquilidad: la arquitectura de islas de Astro y su filosofía agnóstica del framework son neutrales respecto a la plataforma por diseño. El enfoque static-first de Astro significa que la salida son solo archivos. Los archivos van a cualquier sitio.

La inversión de Cloudflare probablemente signifique un desarrollo más rápido y una integración más estrecha con Workers. El balance de 2026 hasta ahora: Astro 6 en marzo, Astro 7 en junio y Astro 7.4 en octubre con un flag `--timings` que muestra en qué gasta su tiempo una compilación. En agosto de 2026, Matthew Phillips tomó el relevo de Fred Schott como Project Steward. Para la comunidad de Astro, el respaldo es un beneficio neto, siempre que sigas desplegando también en plataformas que no son Cloudflare.

<Notice type="info" title="La dinámica del respaldo corporativo">
Vercel respalda Next.js: integración profunda, pero riesgo de vendor lock-in. Cloudflare respalda a Astro: la misma dinámica en otra plataforma. TanStack LLC respalda TanStack Start, financiado por una empresa bootstrapped y patrocinadores como Cloudflare, Netlify y Vercel. Cada modelo tiene sus compromisos.
</Notice>

Puedes [desplegar un blog de Astro en Cloudflare](/es/desplegar-astrojs-cloudflare/) hoy mismo para ver la integración en la práctica.

## ¿Está TanStack Start listo para producción?

Sí, TanStack [declaró Start 1.0 estable el 13 de octubre de 2026](https://tanstack.com/blog/tanstack-start-1-0), y la documentación abre con la frase "TanStack Start is stable". Solo su soporte de React Server Components sigue siendo experimental y está desactivado por defecto.

La versión 1.0 compromete al equipo con las APIs: enrutado con tipos seguros, SSR de documento completo con streaming, funciones de servidor, rutas de servidor y middleware. `@tanstack/react-start` 1.169 es la primera versión estable, y requiere Vite 8. La fase de release candidate fue del 23 de septiembre de 2025 hasta esa fecha, más larga de lo que el equipo había planeado.

Su uso en producción está documentado. MakerKit vende un starter de SaaS sobre TanStack Start en variantes con Drizzle, Prisma y Supabase. [Appwrite reconstruyó su Consola y su web sobre Start](https://appwrite.io/blog/post/announcing-console-iv), con más de 600 páginas de documentación incluidas, y aloja apps de Start en Appwrite Sites. El [premio Revelación del año](https://tanstack.com/blog/tanstack-open-source-awards-2026) de los Open Source Awards de junio de 2026 llegó el mismo año.

<ListCheck>
**Madurez de TanStack Start para producción:**
- Enrutado con tipos seguros: estable
- Funciones de servidor (`createServerFn`): estable
- SSR con streaming: estable
- Despliegue con Docker y Node: estable
- Integración con TanStack Query: la misma librería Query que usa el resto del ecosistema de React
- React Server Components: experimental, desactivado por defecto
- Ecosistema grande de plugins: todavía no
- Mercado de contratación enterprise: todavía no
</ListCheck>

Opinión honesta: si eres una startup que publica rápido con un equipo senior cómodo con las primitivas de TanStack, TanStack Start es viable hoy. Si necesitas garantías de contratación enterprise, un ecosistema grande de plugins, o tu equipo es mayoritariamente junior, espera 6-12 meses a que el ecosistema madure.

## Cuándo elegir cada framework

No hay un ganador universal. La elección correcta depende de qué construyes, quién lo construye y dónde se ejecuta.

![Diagrama de flujo con cuatro preguntas que llevan a Astro, Next.js o TanStack Start según el contenido, la stack, las necesidades de RSC y el estado en cliente](@assets/images/26/07/astro-vs-nextjs-vs-tanstack-start-which-wins-decision-flowchart.webp)

*Ruta de decisión para elegir entre Astro, Next.js y TanStack Start. Gana la primera respuesta que encaje.*

### Elige Astro cuando

Construyes sitios de contenido: blogs, documentación, páginas de marketing, portfolios. El rendimiento y los Core Web Vitals no son negociables. Quieres el mínimo JavaScript. Tu equipo usa varios frameworks (React + Vue). El presupuesto es ajustado, y el hosting estático en Cloudflare es gratis a cualquier escala. Quieres el modelo mental más simple con la curva de aprendizaje más baja.

### Elige Next.js cuando

Construyes aplicaciones web complejas: productos SaaS, plataformas de comercio electrónico, dashboards. Necesitas React Server Components, streaming, ISR. Tu equipo solo usa React y valora la profundidad del ecosistema. Desplegar en Vercel es aceptable o preferible. Necesitas el mayor mercado de contratación para escalar tu equipo de ingeniería.

### Elige TanStack Start cuando

Construyes aplicaciones con estado de cliente complejo. El modelo mental de RSC genera fricción en tu equipo. El enrutado con tipos seguros es prioridad. Quieres la flexibilidad de desplegar en cualquier sitio sin vendor lock-in. Tu equipo tiene ingenieros senior cómodos con primitivas más finas pero bien diseñadas. Ya estás invertido en el ecosistema TanStack Query/Router.

## Consideraciones de migración

¿Y si eliges mal? Los costes de cambio son reales pero manejables.

De Astro a Next.js: esfuerzo moderado. Reescribe las plantillas `.astro` como componentes de React, adopta el modelo RSC y mueve la lógica de contenido estático a Server Components.

De Next.js a Astro: esfuerzo moderado. Quita la lógica de servidor, mueve la interactividad a islas y convierte las páginas del App Router en páginas de Astro. Los sitios con mucho contenido migran más fácil que los sitios con mucha app.

De Next.js a TanStack Start: esfuerzo menor. Ambos son React, pero los patrones de enrutado y el enfoque de las funciones de servidor difieren. Reescribirás las definiciones de rutas y sustituirás los patrones de RSC por loaders + funciones de servidor. TanStack publica una [guía de migración desde Next.js](https://tanstack.com/start/latest/docs/framework/react/migrate-from-next-js).

De TanStack Start a Next.js: esfuerzo moderado. Pierdes el enrutado con tipos seguros, adoptas los patrones de RSC y reestructuras la obtención de datos en torno a Server Components.

<Notice type="success" title="La mejor migración es la que no necesitas">
Elegir bien el framework desde el principio ahorra semanas de refactoring. Si tu proyecto es 80% contenido, empieza con Astro; siempre puedes añadir un subdominio SPA más adelante. Si es 80% app, empieza con Next.js o TanStack Start. Usa el marco de decisión de arriba.
</Notice>

## Veredicto

No hay un único ganador. Hay tres frameworks fuertes para tres apuestas distintas sobre la web.

**Astro** gana para sitios de contenido. Cero JS por defecto, la mejor cuota de Core Web Vitals de los tres, hosting estático gratis en Cloudflare y el respaldo de Cloudflare desde enero de 2026. Si construyes un blog, un sitio de documentación o una página de marketing, es la elección evidente.

**Next.js** gana para aplicaciones complejas de React. La profundidad del ecosistema, el mercado de contratación y el modelo RSC no tienen rival para equipos que construyen productos SaaS, plataformas de comercio electrónico o dashboards enterprise. Prepara presupuesto para la factura de hosting y acepta la curva de aprendizaje.

**TanStack Start** gana para el control del desarrollador. Enrutado con tipos seguros, fronteras de servidor explícitas, flexibilidad para desplegar en cualquier sitio y una versión 1.0 estable desde el 13 de octubre de 2026. Lo mejor para equipos senior que quieren primitivas finas y bien diseñadas sin vendor lock-in. Espera a que el ecosistema madure si tu equipo necesita barreras de protección.

Comprueba las versiones estables antes de crear el proyecto. El 28 de noviembre de 2026 eran Astro 7.4.13, Next.js 16.4.6 y TanStack Start 1.169.7.

## Preguntas frecuentes

<Accordion label="¿Qué framework envía menos JavaScript para un sitio de contenido?" group="faq" expanded="true">
Astro. Una página sin islas envía 0KB de JavaScript porque Astro elimina los scripts de cliente de cada componente que no marques con una directiva `client:*`. Next.js y TanStack Start envían ambos React y un router: un test de la misma app en octubre de 2026 midió 135 KB gzip para Next.js 16.4.2 y 109 KB para TanStack Start 1.169.3.
</Accordion>

<Accordion label="¿Puede TanStack Start sustituir a Next.js de forma realista en un producto SaaS?" group="faq">
Sí, si tu equipo está cómodo con las primitivas de TanStack y no necesitas la profundidad del ecosistema de Next.js. TanStack Start 1.0 es estable desde el 13 de octubre de 2026, y Appwrite ejecuta su Consola y su web sobre él. La diferencia está en el ecosistema: menos integraciones de terceros, menos tutoriales y un mercado de contratación más pequeño.
</Accordion>

<Accordion label="¿Basta con Astro para un proyecto que puede acabar siendo una app?" group="faq">
Sí, hasta cierto punto. Las islas de Astro te permiten añadir interactividad poco a poco: un widget de React aquí, un componente de Svelte allí. Pero si tu proyecto acaba siendo 80%+ interactivo, notarás la fricción de la sobrecarga de coordinar islas. En ese punto, un framework diseñado para apps (Next.js o TanStack Start) es una base mejor.
</Accordion>

<Accordion label="¿Cómo se comparan los tres con un CMS headless?" group="faq">
Los tres funcionan con Strapi, Sanity, Contentful y otros CMS headless. Las Content Collections de Astro tienen la mejor DX nativa para obtener contenido, con esquemas con tipos seguros validados por Zod 4. Next.js se integra mediante Server Components y `fetch()`. TanStack Start usa loaders de ruta con el caché de TanStack Query.
</Accordion>

<Accordion label="¿Cuál es la forma más barata de alojar una app de Next.js?" group="faq">
Autoaloja en un VPS de Hetzner con Docker. Un CX23 (2 vCPU, 4 GB RAM) cuesta €5.99 al mes más IVA. Compila con `next build`, ejecuta con `next start` detrás de un proxy inverso y olvídate de Vercel Pro salvo que necesites sus funciones de edge o sus despliegues de preview. Vercel Hobby se queda en 100 GB de transferencia de datos al mes.
</Accordion>

<Accordion label="¿La compra por Cloudflare es buena o mala para Astro?" group="faq">
De momento, buena. La licencia sigue siendo MIT, la gobernanza y la hoja de ruta siguen abiertas, y Astro sigue desplegándose en todas las plataformas. Un cambio ya ha llegado: desde la v13 el adaptador de Cloudflare apunta solo a Workers y ya no es compatible con Cloudflare Pages. Sigue desplegando en plataformas que no son Cloudflare para que esa promesa se mantenga honesta.
</Accordion>

<Accordion label="¿Es TanStack Start lo bastante estable para producción?" group="faq">
Sí. TanStack declaró Start 1.0 estable el 13 de octubre de 2026, y `@tanstack/react-start` 1.169 es la primera versión estable. La documentación sigue marcando React Server Components como experimental y desactivado por defecto, así que construye sobre SSR, loaders y `createServerFn` en lugar de sobre Server Components.
</Accordion>

<Accordion label="¿Qué versión de cada framework es estable ahora mismo?" group="faq">
El 28 de noviembre de 2026 las versiones estables eran Astro 7.4.13 (publicada el 18 de noviembre de 2026), Next.js 16.4.6 (9 de noviembre de 2026) y TanStack Start 1.169.7 (19 de noviembre de 2026). Compruébalo con `npm view astro version`, `npm view next version` o `npm view @tanstack/react-start version` antes de empezar un proyecto.
</Accordion>
