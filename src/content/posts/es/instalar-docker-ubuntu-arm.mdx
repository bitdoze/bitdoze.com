Para instalar Docker en Ubuntu ARM, usa el repositorio apt de Docker y cinco paquetes: `docker-ce`, `docker-ce-cli`, `containerd.io`, `docker-buildx-plugin` y `docker-compose-plugin`. El repositorio ofrece las compilaciones `arm64` junto a las de amd64: Docker Engine 29.10.1 y Compose v5.8.1 el 2026-11-27.

Capturé cada bloque de salida de abajo el 2026-11-27 en contenedores desechables de Ubuntu 24.04 y 22.04 sobre un host x86_64, no en una máquina ARM. Buildx v0.39.1 llegó con las versiones anteriores. La columna `arm64` del repositorio sale de una comprobación por URL, y los puntos que dependen de ella lo dicen. Los extractos conservan solo las líneas que importan. Los pasos siguen [la documentación de Docker](https://docs.docker.com/engine/install/ubuntu/).

## ¿Cómo instalo Docker en Ubuntu ARM?

Descarga la clave de firma de Docker en `/etc/apt/keyrings/docker.asc` y escribe `/etc/apt/sources.list.d/docker.sources` con el nombre en clave de tu Ubuntu y `arm64` como arquitectura. Luego ejecuta `sudo apt update` y `sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin`, añade tu usuario al grupo `docker` y comprueba el resultado con `docker run --rm hello-world`.

## Comprueba la máquina antes de empezar

Dos comandos te dicen si estos pasos encajan con tu host:

```bash
uname -m
dpkg --print-architecture
```

Estos pasos son para hosts que responden `aarch64` y `arm64`: Ubuntu de 64 bits sobre Oracle Ampere, AWS Graviton, las instancias Ampere de Hetzner o una Raspberry Pi 5. `armv7l` y `armhf` indican un userland de 32 bits. El repositorio de Docker también sirve esa columna, pero no comprobé nada de lo de abajo en 32 bits.

La documentación de Docker, leída el 2026-11-27, lista cuatro versiones de Ubuntu admitidas: 26.10 (`stonking`), 26.04 (`resolute`, LTS), 24.04 (`noble`, LTS) y 22.04 (`jammy`, LTS). Las suites antiguas como focal siguen en el repositorio, con columna arm64, pero quedan fuera de esa lista.

## Añade el repositorio apt de Docker en Ubuntu

El repositorio de Docker vive en `download.docker.com/linux/ubuntu`, y dos archivos hacen que apt lo acepte: la clave de firma en `/etc/apt/keyrings` y un archivo de fuentes en `/etc/apt/sources.list.d`. Ubuntu trae su propio paquete `docker.io`, y va por detrás. El 2026-11-27 el repositorio de Ubuntu ofrecía Docker 29.1.3, Compose 2.40.3 y Buildx 0.30.1 en 22.04 y en 24.04. El repositorio de Docker tenía 29.10.1, 5.8.1 y 0.39.1, por eso los pasos de abajo lo añaden.

### Quita los paquetes en conflicto

La documentación de Docker empieza quitando los paquetes que chocan con los oficiales:

```bash
sudo apt remove $(dpkg --get-selections docker.io docker-compose docker-compose-v2 docker-doc docker-buildx podman-docker containerd runc | cut -f1)
```

En un host limpio dpkg responde `no packages found matching docker.io` por cada nombre y apt no quita nada. Las imágenes y los volúmenes bajo `/var/lib/docker` sobreviven a este comando y al purge del final de la página.

### Actualiza y añade la clave de firma

```bash
sudo apt update
sudo apt install ca-certificates curl
```

El siguiente comando necesita `curl`. Sin él, la descarga de la clave se detiene en `sudo: curl: command not found`. Sin `ca-certificates` en el host, apt rechaza el repositorio con `No system certificates available. Try installing ca-certificates.`

```bash
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
```

Comprueba lo que llegó:

```bash
ls -l /etc/apt/keyrings/docker.asc
head -1 /etc/apt/keyrings/docker.asc
```

```text
-rw-r--r-- 1 root root 3817 Nov 27 14:26 /etc/apt/keyrings/docker.asc
-----BEGIN PGP PUBLIC KEY BLOCK-----
```

Los tutoriales antiguos pasan la clave por `gpg --dearmor` hacia un archivo `docker.gpg`. La documentación actual conserva el archivo blindado, que apt acepta en `Signed-By` tal cual. El `chmod` importa porque apt lee el keyring como el usuario `_apt`, y `sources.list(5)` pide un archivo legible por todos. Con el umask por defecto llega igualmente como `-rw-r--r--`.

### El archivo del repositorio: docker.sources o docker.list

La documentación de Docker escribe el repositorio en formato deb822. Los tutoriales antiguos y el script de `get.docker.com` usan un archivo de una línea. apt acepta ambos. Elige uno.

<Tabs>
<Tab name="docker.sources (documentación actual)">

```bash
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
```

`tee` muestra el archivo que escribió, con ambas sustituciones resueltas:

```text
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: noble
Components: stable
Architectures: amd64
Signed-By: /etc/apt/keyrings/docker.asc
```

</Tab>
<Tab name="docker.list (una línea)">

```bash
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}") stable" | sudo tee /etc/apt/sources.list.d/docker.list
```

Salida de un contenedor con 22.04:

```text
deb [arch=amd64 signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu jammy stable
```

</Tab>
</Tabs>

| Opción | Veredicto | Contrapartida |
|---|---|---|
| `docker.sources` (deb822) | Lo que usa ahora la documentación de Docker. Un campo por línea, así que corregir la suite tras un upgrade de Ubuntu es editar una palabra | El archivo no tiene línea `deb`, así que un script que busque una en las fuentes no encuentra nada |
| `docker.list` (una línea) | Lo que escribe get.docker.com y lo que muestran los tutoriales antiguos. En 22.04 dio el mismo resultado de `apt update` que el archivo deb822 | Arquitectura, ruta de la clave, URL, suite y canal comparten una línea |

| Línea | Contiene | Por qué importa |
|---|---|---|
| `Suites` | el nombre en clave de tu Ubuntu | elige la compilación de tu versión |
| `Architectures` | `arm64` en estos hosts | apt descarga una sola columna, y la línea `Get:` de abajo la muestra |
| `Signed-By` | el archivo de la clave | apt comprueba con esta clave la firma del repositorio |
| `Components` | `stable` | el canal de publicación; el repositorio tiene también `edge`, `test` y `nightly` |

El shell resuelve el nombre en clave cuando escribes el archivo, así que `Suites: noble` sigue siendo `noble` hasta que alguien lo edita. Tras un upgrade de versión de Ubuntu, abre el archivo y revisa esa línea. La forma `${UBUNTU_CODENAME:-$VERSION_CODENAME}` existe para las derivadas: en Linux Mint 22, `VERSION_CODENAME` es `wilma` y `UBUNTU_CODENAME` es `noble`, y el repositorio de Docker sirve `noble`, no `wilma`.

| Ubuntu | Nombre en clave | Columna `arm64` | `docker-ce` más reciente en el repositorio |
|---|---|---|---|
| 22.04 LTS | `jammy` | sí | `5:29.10.1-1~ubuntu.22.04~jammy` |
| 24.04 LTS | `noble` | sí | `5:29.10.1-1~ubuntu.24.04~noble` |
| 26.04 LTS | `resolute` | sí | `5:29.10.1-1~ubuntu.26.04~resolute` |
| 26.10 | `stonking` | sí | `5:29.10.1-1~ubuntu.26.10~stonking` |

Leí los índices de arm64 y amd64 el 2026-11-27. Las cadenas de versión son las mismas en ambos.

### Actualiza las listas de paquetes

`sudo apt update` descarga el índice de tu arquitectura:

```bash
sudo apt update
```

```text
Get:1 https://download.docker.com/linux/ubuntu noble InRelease [48.5 kB]
Get:2 https://download.docker.com/linux/ubuntu noble/stable amd64 Packages [91.6 kB]
Fetched 140 kB in 1s (229 kB/s)
```

En un host ARM64 la segunda línea dice `arm64 Packages`, y el nombre en clave es el tuyo. Después confirma que el candidato viene de Docker y no de Ubuntu:

```bash
apt-cache policy docker-ce
```

```text
docker-ce:
  Installed: (none)
  Candidate: 5:29.10.1-1~ubuntu.24.04~noble
  Version table:
     5:29.10.1-1~ubuntu.24.04~noble 500
        500 https://download.docker.com/linux/ubuntu noble/stable amd64 Packages
```

`Candidate: (none)` aquí significa que apt no aceptó el repositorio, y el paso de instalación termina entonces con `Package 'docker-ce' has no installation candidate`.

## ¿Por qué apt dice NO_PUBKEY tras añadir el repositorio de Docker?

Falta el archivo de la clave o está vacío, así que apt no puede comprobar la firma del repositorio. Repite los tres comandos de la clave y confirma que `head -1 /etc/apt/keyrings/docker.asc` imprime `-----BEGIN PGP PUBLIC KEY BLOCK-----`.

Con el archivo de la clave borrado, `apt update` imprimió:

```text
Err:3 https://download.docker.com/linux/ubuntu noble InRelease
  The following signatures couldn't be verified because the public key is not available: NO_PUBKEY 7EA0A9C3F273FCD8
W: GPG error: https://download.docker.com/linux/ubuntu noble InRelease: The following signatures couldn't be verified because the public key is not available: NO_PUBKEY 7EA0A9C3F273FCD8
E: The repository 'https://download.docker.com/linux/ubuntu noble InRelease' is not signed.
```

Otros fallos, cada uno provocado a propósito en un contenedor de pruebas:

| apt imprime | Causa | Arreglo |
|---|---|---|
| `GPG: add_keyblock_resource 33587281  GPG: keydb_search 33554445` | el archivo de la clave existe pero está vacío | repite los tres comandos de la clave; `head -1` debe imprimir `-----BEGIN PGP PUBLIC KEY BLOCK-----` |
| `404  Not Found`, y después `does not have a Release file` | `Suites` nombra una suite que el repositorio no sirve: un nombre en clave de una derivada, o uno antiguo que quedó tras un upgrade de Ubuntu | pon en `Suites` el nombre en clave de Ubuntu |
| ningún error, pero `apt-cache policy docker-ce` muestra `22.04~jammy` en un host con 24.04 | `jammy` sigue existiendo en el repositorio, así que una suite obsoleta instala la compilación de 22.04 sin aviso | el mismo arreglo |
| `No system certificates available. Try installing ca-certificates.` | no hay bundle de CA en el host | `sudo apt install ca-certificates` |

## Instala los paquetes y comprueba

Una línea de instalación descarga el motor, la CLI, el runtime y los dos plugins desde el repositorio de Docker:

```bash
sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

Seis descargas vienen del repositorio de Docker (numeradas 1 y de 3 a 7 porque las dependencias propias de Ubuntu se llevan los otros números):

En Ubuntu el nombre resuelve a la versión 1.29.2 del archivo universe, y en 24.04 esa muere al arrancar con `ModuleNotFoundError: No module named 'distutils'`. ## ¿Cómo ejecuto docker sin sudo?

Añade tu usuario al grupo `docker` con `sudo usermod -aG docker $USER`, luego cierra la sesión y vuelve a entrar. El paquete crea el grupo y lo deja vacío, y pertenecer a él concede privilegios de root en el host.

El grupo existe tras la instalación y no tiene miembros: `docker:x:995:` en el contenedor con 24.04, `docker:x:999:` en 22.04. Hasta que tu usuario se una, cada comando `docker` sin sudo se detiene con:

```text
permission denied while trying to connect to the docker API at unix:///var/run/docker.sock
```

El comando:

```bash
sudo usermod -aG docker $USER
```

En la sesión nueva, `id -nG` lista `docker` entre tus grupos: con un usuario de prueba en el contenedor la lista pasó de `decker` a `decker docker`, y `docker run --rm hello-world` funcionó sin sudo. En una VM a veces hace falta un reinicio, y `newgrp docker` abre una shell con el grupo para la sesión actual.

Si ejecutaste `docker` con sudo primero, el daemon puede dejar `~/.docker` perteneciendo a root, y la CLI avisa con `~/.docker/config.json: permission denied`. La documentación de Docker lo arregla con:

```bash
sudo chown "$USER":"$USER" /home/"$USER"/.docker -R
sudo chmod g+rwx "$HOME/.docker" -R
```

<Notice type="warning" title="El grupo docker es acceso de nivel root">
La documentación de Docker lo dice sin rodeos: el grupo docker concede privilegios de nivel root al usuario. Cualquier proceso que se ejecute como ese usuario puede montar el disco del host en un contenedor y leerlo entero. En un host que solo operas tú, ese es el precio de no escribir sudo todo el día. Donde otras personas tienen cuenta, déjalas fuera del grupo o ejecuta el daemon en [modo rootless](https://docs.docker.com/engine/security/rootless/).
</Notice>

## ¿Por qué Docker dice no matching manifest for linux/arm64?

El índice de la imagen no tiene compilación para `linux/arm64`, y un host ARM64 pide esa plataforma por defecto. Busca un tag con compilación `arm64`, construye la imagen sobre una base arm64, o ejecuta la compilación amd64 bajo emulación como último recurso.

### Tres nombres para una misma CPU

`uname`, dpkg y `docker info` imprimen cada uno su propio nombre para ella:

| Comando | Host x86_64 (capturado) | Host ARM64 |
|---|---|---|
| `uname -m` | `x86_64` | `aarch64` |
| `dpkg --print-architecture` | `amd64` | `arm64` |
| `docker info`, `Architecture` | `x86_64` | `aarch64` |

La columna ARM64 es la nomenclatura documentada: [la guía de instalación de Arm](https://learn.arm.com/install-guides/docker/docker-engine) da `aarch64` para `uname` en 64 bits, y `docker info` informa de la plataforma en ejecución (el nombre del kernel) en lugar del `arm64` de Go. La línea capturada:

```bash
docker info --format 'server={{.ServerVersion}} os={{.OperatingSystem}} arch={{.Architecture}} driver={{.Driver}} live-restore={{.LiveRestoreEnabled}}'
```

```text
server=29.10.1 os=Ubuntu 24.04.5 LTS arch=x86_64 driver=overlayfs live-restore=false
```

`arch=` es el valor que hay que comprobar. Los dos últimos campos son el storage driver y el ajuste de live restore, que está desactivado por defecto.

### La imagen no tiene compilación arm64

Una imagen multi-arquitectura lleva una lista de manifiestos, uno por plataforma. Comprueba la lista antes de descargar:

```bash
docker buildx imagetools inspect hello-world --format '{{range .Manifest.Manifests}}{{if ne .Platform.OS "unknown"}}{{.Platform.OS}}/{{.Platform.Architecture}}{{println}}{{end}}{{end}}'
```

```text
linux/amd64
linux/arm
linux/arm
linux/arm
linux/arm64
linux/386
linux/ppc64le
linux/riscv64
linux/s390x
windows/amd64
windows/amd64
```

Las tres líneas `linux/arm` son las compilaciones de 32 bits (v5, v6 y v7). Cuando la lista no tiene `linux/arm64`, el daemon rechaza la imagen antes de descargar ninguna capa. `mysql:5.7` es un ejemplo: su índice solo contiene `linux/amd64`. Si le pides `linux/arm64`, responde:

```bash
docker run --rm --platform linux/arm64 mysql:5.7 --version
```

```text
docker: Error response from daemon: no matching manifest for linux/arm64 in the manifest list entries: no match for platform in manifest: not found
```

En un host ARM64 el daemon pide `linux/arm64` por defecto, así que un simple `docker run mysql:5.7` falla con esa línea. Pasé la plataforma a mano con `--platform linux/arm64` para reproducir el error en x86_64.

### Forzar la compilación amd64

`--platform linux/amd64` descarga la variante x86-64 en un host ARM64, pero solo se ejecuta cuando el kernel puede ejecutar binarios x86-64, lo que necesita QEMU registrado mediante binfmt_misc. Sin ello el contenedor muere al arrancar. La línea de abajo viene del caso inverso, una imagen arm64 en este host x86_64, que tampoco tiene emulador:

```bash
docker run --rm --platform linux/arm64 alpine uname -m
```

```text
exec /bin/uname: exec format error
```

La documentación de Docker da el comando que registra los emuladores: `docker run --privileged --rm tonistiigi/binfmt --install all`. La misma página da el motivo para no apoyarse en él. En sus palabras: "Emulation with QEMU can be much slower than native builds, especially for compute-heavy tasks like compilation and compression or decompression." Un script puntual va bien bajo emulación. Una base de datos o cualquier cosa que se ejecute durante semanas debería usar una imagen nativa.

## ¿Cómo actualizo o revierto Docker Engine?

Con el repositorio en su sitio, `sudo apt update` y `sudo apt upgrade` pasan al `docker-ce` más reciente del repositorio. Para revertir, instala una cadena de versión anterior con `--allow-downgrades` y retén los paquetes con `apt-mark hold` para que el siguiente upgrade no los toque.

| Opción | Veredicto | Contrapartida |
|---|---|---|
| `sudo apt upgrade` | apt pasa a la versión más alta del índice sin pasos extra | El salto puede cruzar una versión mayor |
| `VERSION_STRING` fijada con `apt-mark hold` | Se queda en la compilación que elegiste, y el mismo comando de instalación revierte a una anterior | `apt upgrade` informa de los paquetes como retenidos hasta que los liberes |

La actualización lleva dos comandos:

```bash
sudo apt update
sudo apt upgrade
```

La documentación de Docker trata la versión como una elección. Lista lo que ofrece el repositorio y luego instala la que quieras:

```bash
apt list --all-versions docker-ce
```

```text
docker-ce/noble,now 5:29.10.1-1~ubuntu.24.04~noble amd64 [installed]
docker-ce/noble 5:29.10.0-1~ubuntu.24.04~noble amd64
docker-ce/noble 5:29.9.3-1~ubuntu.24.04~noble amd64
```

Para volver una compilación atrás, instala una versión fijada como muestra la documentación. Ir hacia atrás es un downgrade. Con `-y` apt lo rechaza con `Packages were downgraded and -y was used without --allow-downgrades.`, de ahí el flag:

```bash
VERSION_STRING=5:29.10.0-1~ubuntu.24.04~noble
sudo apt install --allow-downgrades docker-ce=$VERSION_STRING docker-ce-cli=$VERSION_STRING containerd.io docker-buildx-plugin docker-compose-plugin
```

```text
The following packages will be DOWNGRADED:
  docker-ce docker-ce-cli
0 upgraded, 0 newly installed, 2 downgraded, 0 to remove and 2 not upgraded.
dpkg: warning: downgrading docker-ce-cli from 5:29.10.1-1~ubuntu.24.04~noble to 5:29.10.0-1~ubuntu.24.04~noble
dpkg: warning: downgrading docker-ce from 5:29.10.1-1~ubuntu.24.04~noble to 5:29.10.0-1~ubuntu.24.04~noble
Setting up docker-ce (5:29.10.0-1~ubuntu.24.04~noble) ...
```

Después `docker --version` muestra `Docker version 29.10.0, build fdd4b8e`. Escrito a mano, apt pregunta `Do you want to continue? [Y/n]` antes del downgrade.

Si no haces nada, el siguiente `apt upgrade` instala otra vez 29.10.1. Para quedarte en la compilación fijada, retén los paquetes:

```bash
sudo apt-mark hold docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

```text
docker-ce set on hold.
docker-ce-cli set on hold.
containerd.io set on hold.
docker-buildx-plugin set on hold.
docker-compose-plugin set on hold.
```

Entonces `apt upgrade` informa de `The following packages have been kept back: docker-ce docker-ce-cli`, y `sudo apt-mark unhold` con los mismos nombres de paquete los libera (`Canceled hold on docker-ce.`).

Mi regla: deja que apt actualice un host que ejecuta contenedores sin estado, y retén los paquetes en un host con bases de datos hasta haberte leído las notas de la versión.

### Mantén los contenedores en ejecución durante el reinicio

Una actualización del motor reinicia el daemon, y por defecto eso detiene los contenedores en ejecución. Con `live-restore` activado siguen corriendo. Pon esto en `/etc/docker/daemon.json`:

```json
{
  "live-restore": true
}
```

Luego recarga el daemon con `sudo systemctl reload docker`. En el daemon de pruebas, `docker info --format 'live-restore={{.LiveRestoreEnabled}}'` pasó de `live-restore=false` a `live-restore=true` tras la recarga. Dos contenedores de prueba, uno arrancado antes del ajuste y otro después, conservaron su uptime a través de un stop y un start del daemon. La documentación limita la garantía a las versiones de parcheo (29.10.x), no a los saltos de versión mayor, y a opciones del daemon sin cambios, como la IP del bridge.

## ¿Debes usar get.docker.com o el repositorio apt?

El repositorio apt, en cualquier host que guarde datos. El script llega al mismo motor pero añade `docker-model-plugin` y siempre toma la última versión, y la documentación de Docker no lo recomienda para producción ni para actualizaciones.

| Opción | Veredicto | Contrapartida |
|---|---|---|
| repositorio apt, a mano | El método de la documentación de Docker. Tú nombras los cinco paquetes, y las actualizaciones llegan por apt | Escribes tú el archivo del repositorio |
| script `get.docker.com` | Mismo repositorio y mismo motor, Docker 29.10.1 por ambos caminos el 2026-11-27, con un solo comando | Añade `docker-model-plugin` y siempre instala la última versión; la documentación no lo recomienda para producción ni para actualizaciones |

Lee el script antes de ejecutarlo. La prueba en seco imprime cada comando:

```bash
curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh ./get-docker.sh --dry-run
```

```text
# Executing docker install script, commit: 8ad27bd3ac871feabe62f1d926c4067800c1732f
apt-get -qq update >/dev/null
DEBIAN_FRONTEND=noninteractive apt-get -y -qq install ca-certificates curl >/dev/null
install -m 0755 -d /etc/apt/keyrings
curl -fsSL "https://download.docker.com/linux/ubuntu/gpg" -o /etc/apt/keyrings/docker.asc
chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=amd64 signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu jammy stable" > /etc/apt/sources.list.d/docker.list
apt-get -qq update >/dev/null
DEBIAN_FRONTEND=noninteractive apt-get -y -qq install docker-ce docker-ce-cli containerd.io docker-compose-plugin docker-ce-rootless-extras docker-buildx-plugin docker-model-plugin >/dev/null
```

La ejecución real, `sudo sh get-docker.sh`, dejó el mismo Docker 29.10.1 y Compose v5.8.1 que los pasos manuales, y escribió el `docker.list` de una línea con el nombre en clave incluido en él.

Después actualiza con apt. Mi regla: vale para una Pi que reflasheas o un VPS desechable; en cualquier cosa con datos, los pasos manuales instalan solo lo que nombraste.

## ¿Cómo desinstalo Docker de Ubuntu?

Ejecuta `sudo apt purge docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin docker-ce-rootless-extras`. El purge deja imágenes, contenedores y volúmenes en `/var/lib/docker`, así que borra ese directorio solo cuando quieras deshacerte de ellos.

Comando y salida:

```bash
sudo apt purge docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin docker-ce-rootless-extras
```

```text
The following packages will be REMOVED:
  containerd.io* docker-buildx-plugin* docker-ce* docker-ce-cli*
  docker-ce-rootless-extras* docker-compose-plugin*
0 upgraded, 0 newly installed, 6 to remove and 2 not upgraded.
After this operation, 378 MB disk space will be freed.
Removing docker-ce (5:29.10.1-1~ubuntu.24.04~noble) ...
Removing containerd.io (2.4.2-4~ubuntu.24.04~noble) ...
Removing docker-buildx-plugin (0.39.1-1~ubuntu.24.04~noble) ...
Removing docker-ce-cli (5:29.10.1-1~ubuntu.24.04~noble) ...
Removing docker-ce-rootless-extras (5:29.10.1-1~ubuntu.24.04~noble) ...
Removing docker-compose-plugin (5.8.1-1~ubuntu.24.04~noble) ...
dpkg: warning: while removing docker-ce, directory '/etc/docker' not empty so not removed
```

Tras el purge de arriba, `/var/lib/docker` seguía listando `containers`, `image` y `volumes` entre sus directorios. `/etc/docker/daemon.json`, la clave y el archivo de fuentes también seguían ahí. Quita lo que ya no quieras:

```bash
sudo rm -rf /var/lib/docker /var/lib/containerd
sudo rm /etc/apt/sources.list.d/docker.sources
sudo rm /etc/apt/keyrings/docker.asc
```

Para la forma de una línea, el comando `rm` nombra `docker.list` en su lugar. `/var/lib/docker` guarda todos los volúmenes. El [paso de copia de seguridad de la guía de actualización de Compose](/es/actualizar-contenedor-docker-compose/) muestra el comando tar de una línea para un volumen con nombre. ## Preguntas frecuentes

<Accordion label="¿Cómo instalo Docker Compose en Ubuntu ARM?" group="faq">
Compose llega como el paquete `docker-compose-plugin`, incluido en la misma línea de instalación que el motor, y `docker compose version` imprime `Docker Compose version v5.8.1` después. El comando es `docker compose`, con un espacio. El paquete antiguo `docker-compose` (v1, 1.29.2) no está en el repositorio de Docker y se rompe en Ubuntu 24.04 con `No module named 'distutils'`.
</Accordion>

<Accordion label="¿Todavía tengo que pasar la clave GPG de Docker por dearmor?" group="faq">
No. La documentación actual de Docker guarda la clave blindada en `/etc/apt/keyrings/docker.asc` y ejecuta `chmod a+r` sobre ella, y apt acepta ese archivo en `Signed-By`. Ejecutar `gpg --show-keys --with-fingerprint` sobre ella muestra el uid `Docker Release (CE deb) <docker@docker.com>` y la huella `9DC8 5822 9FC7 DD38 854A E2D8 8D81 803C 0EBF CD88`. El `7EA0A9C3F273FCD8` de una línea `NO_PUBKEY` es la subclave de firma de esa misma clave, no una segunda clave.
</Accordion>

<Accordion label="¿Puedo instalar en su lugar el paquete docker.io de Ubuntu?" group="faq">
Puedes. El 2026-11-27 el repositorio de Ubuntu ofrecía Docker 29.1.3 con Compose 2.40.3 y Buildx 0.30.1, mientras que el repositorio de Docker tenía 29.10.1, 5.8.1 y 0.39.1. El paquete separado `docker-compose` de Ubuntu, la herramienta v1, también se rompe en 24.04 con `No module named 'distutils'`.
</Accordion>

<Accordion label="¿Cómo sé si una imagen tiene compilación para ARM64?" group="faq">
Ejecuta `docker buildx imagetools inspect` sobre la imagen y lee las líneas `Platform:`, o usa el bucle con `--format` de esta página para imprimir solo esas. `hello-world` lista `linux/arm64`. `mysql:5.7` lista solo `linux/amd64`, y pedírselo a un host ARM64 falla con `no matching manifest for linux/arm64`.
</Accordion>

<Accordion label="¿Puede un host ARM ejecutar imágenes Docker amd64?" group="faq">
Solo mediante emulación. `--platform linux/amd64` descarga la compilación x86-64, y arranca solo después de registrar QEMU con `docker run --privileged --rm tonistiigi/binfmt --install all`. La documentación de Docker califica QEMU como "much slower than native builds", así que sirve para un script puntual y no para una base de datos.
</Accordion>

<Accordion label="¿Cómo hago un downgrade de Docker Engine con apt?" group="faq">
Pon `VERSION_STRING` a una versión de `apt list --all-versions docker-ce` y ejecuta el comando de instalación con `--allow-downgrades`, como en la sección de reversión. Sin ese flag apt rechaza un downgrade con `-y`. Retén después los paquetes con `sudo apt-mark hold docker-ce docker-ce-cli`, o la siguiente actualización vuelve a poner la compilación más reciente.
</Accordion>

<Accordion label="¿Es seguro el script get.docker.com para un servidor con datos?" group="faq">
El script escribe el mismo repositorio e instala el mismo motor: Docker 29.10.1 por ambos caminos el 2026-11-27. También añade `docker-model-plugin` y siempre toma la última versión, y la documentación de Docker no lo recomienda para producción ni como ruta de actualización. Úsalo en un host desechable, y los pasos manuales en cualquier sitio con datos.
</Accordion>

<Accordion label="¿Una Raspberry Pi 5 sigue el mismo procedimiento?" group="faq">
Sí, con un Ubuntu de 64 bits en la placa. Informa de `aarch64` con `uname -m` y de `arm64` con `dpkg --print-architecture`, así que aplican la misma columna del repositorio y los mismos cinco paquetes. Un sistema de 32 bits informa de `armv7l` y `armhf` y recibe en su lugar las compilaciones `armhf`.
</Accordion>
