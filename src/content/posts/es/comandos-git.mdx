## Sección 1: Comandos básicos de Git

Estos son los comandos que usarás cada día. Domínalos primero.

### 1.1 git init

Inicializa un repositorio Git nuevo. Crea el directorio `.git` con todos los metadatos que Git necesita para rastrear cambios.

**Ejemplo de uso:**

```bash
mkdir my_project
cd my_project
git init
# Initialized empty Git repository in /path/to/my_project/.git/
```

**Verifica:** ejecuta `git status`. Deberías ver "On branch main" (o master, según la rama por defecto de tu configuración) sin commits todavía.

### 1.2 git clone

Crea una copia local de un repositorio remoto.

**Ejemplo de uso:**

```bash
git clone https://github.com/user/repository.git
# Cloning into 'repository'...
# remote: Enumerating objects: 10, done.
# remote: Counting objects: 100% (10/10), done.
# remote: Compressing objects: 100% (8/8), done.
# remote: Total 10 (delta 2), reused 10 (delta 2), pack-reused 0
# Unpacking objects: 100% (10/10), done.
```

**Verifica:** `ls -la .git/` debería mostrar la estructura del repositorio. Para mayor seguridad, ejecuta `git fsck` para verificar la integridad.

Para clones superficiales y parciales (útiles en un VPS con ancho de banda limitado o en CI), consulta la Sección 3.5.

### 1.3 git status

Muestra el estado actual del directorio de trabajo y del área de preparación (staging).

**Ejemplo de uso:**

```bash
git status
# On branch main
# Your branch is up to date with 'origin/main'.
#
# Untracked files:
#   (use "git add <file>..." to include in what will be committed)
#     newfile.txt
#
# nothing added to commit but untracked files present (use "git add" to track)
```

Es el comando que más ejecuto. Úsalo antes de cada commit para asegurarte de que estás preparando exactamente lo que crees.

### 1.4 git add

Añade el contenido de archivos al área de preparación para el próximo commit.

**Ejemplo de uso:**

```bash
# Prepara un solo archivo
git add newfile.txt

# Prepara todos los cambios
git add .

# Prepara de forma interactiva (elige hunks)
git add -p
```

Merece la pena aprender `git add -p` pronto. Te permite preparar partes de un archivo, lo que genera commits más limpios.

### 1.5 git commit

Registra los cambios preparados como un commit nuevo.

**Ejemplo de uso:**

```bash
git commit -m "Add newfile.txt"
# [main 1a2b3c4] Add newfile.txt
#  1 file changed, 1 insertion(+)
#  create mode 100644 newfile.txt
```

**Modifica el último commit** (antes de haber hecho push):

```bash
git commit --amend -m "Updated commit message"
```

### 1.6 git config

Configura los ajustes de Git. En Git 2.46+ (julio de 2024) hay una sintaxis más limpia basada en subcomandos:

<Tabs>
<Tab name="Sintaxis nueva (Git 2.46+)">
```bash
git config set --global user.name "John Doe"
git config set --global user.email "johndoe@example.com"
git config list
git config get user.name
git config unset user.name
```
</Tab>
<Tab name="Sintaxis heredada (aún funciona)">
```bash
git config --global user.name "John Doe"
git config --global user.email "johndoe@example.com"
git config --list
git config --get user.name
git config --unset user.name
```
</Tab>
</Tabs>

<Notice type="info" title="Subcomandos de git config en Git 2.46">
La nueva sintaxis `git config set/get/list/unset` es más limpia y fácil de leer. Las flags antiguas `--global`/`--get` siguen funcionando: Git mantiene compatibilidad hacia atrás. Pero si enseñas a desarrolladores nuevos, usa la forma con subcomandos. Git 3.0 seguirá avanzando en esta dirección.
</Notice>

### 1.7 git grep

Busca un patrón en los archivos rastreados. Más rápido que `grep -r` porque opera sobre el índice de Git.

**Ejemplo de uso:**

```bash
# Busca "TODO" en todos los archivos rastreados
git grep "TODO"

# Busca con números de línea
git grep -n "function_name"

# Busca en un commit concreto
git grep "pattern" HEAD~3

# Búsqueda sin distinguir mayúsculas
git grep -i "error"
```

### 1.8 git rm

Elimina archivos del directorio de trabajo y del área de preparación.

**Ejemplo de uso:**

```bash
# Elimina un archivo rastreado
git rm oldfile.txt

# Deja de rastrearlo pero conserva el archivo en disco
git rm --cached secret.env
```

La flag `--cached` es útil cuando hiciste commit por accidente de un archivo que debería estar en `.gitignore`.

### 1.9 git mv

Mueve o renombra un archivo rastreado.

**Ejemplo de uso:**

```bash
git mv old_name.txt new_name.txt
```

Equivale a `mv old_name.txt new_name.txt && git add new_name.txt && git rm old_name.txt`, pero más limpio.

## Sección 2: Ramas y fusiones

Las ramas te permiten trabajar en funcionalidades, correcciones y experimentos de forma aislada. Esta sección usa el moderno `git switch` como comando principal. Si todavía usas `git checkout` para todo, lee la nota sobre la sintaxis heredada en 2.3.

### 2.1 git branch

Lista, crea y elimina ramas.

**Ejemplo de uso:**

```bash
# Lista las ramas locales
git branch
# * main
#   feature-branch

# Lista todas las ramas (incluidas las remotas)
git branch -a

# Crea una rama nueva
git branch new-feature

# Fuerza el borrado de una rama sin fusionar
git branch -D experimental
```

### 2.2 git switch

La forma moderna de cambiar entre ramas y de crearlas. Introducido en Git 2.23 (agosto de 2019).

**Ejemplo de uso:**

```bash
# Cambia a una rama existente
git switch main

# Crea una rama nueva y cambia a ella
git switch -c new-feature

# Cambia a la rama anterior
git switch -

# Crea una rama desde un commit concreto
git switch -c hotfix abc1234
```

<Notice type="info" title="Por qué git switch y no git checkout">
`git checkout` hace dos cosas sin relación: cambiar de rama y restaurar archivos. Eso genera confusión y errores. `git switch` solo gestiona operaciones con ramas, dejando clara la intención. Git 3.0 recomendará encarecidamente `git switch` y `git restore` frente a `git checkout`.
</Notice>

### 2.3 git checkout (heredado)

Sigue funcionando, pero `git switch` (ramas) y `git restore` (archivos) son los reemplazos recomendados desde Git 2.23.

```bash
# Heredado: cambiar de rama (usa git switch)
git checkout new-feature

# Heredado: crear y cambiar (usa git switch -c)
git checkout -b new-feature

# Heredado: restaurar archivo (usa git restore)
git checkout -- file.txt
```

<Notice type="warning" title="git checkout mezcla dos operaciones">
Usar `git checkout` tanto para cambiar de rama como para restaurar archivos es una fuente habitual de errores. `git checkout -- file.txt` descarta los cambios sin confirmar de un archivo, mientras que `git checkout main` cambia de rama. El mismo comando, resultados completamente distintos. Usa `git switch` y `git restore` para explicitar tu intención.
</Notice>

### 2.4 git merge

Combina los cambios de una rama en la rama actual.

**Ejemplo de uso:**

```bash
# Fusiona una rama en la rama actual
git merge feature-branch

# Fusión con un merge commit explícito (aunque sea posible fast-forward)
git merge --no-ff feature-branch -m "Merge feature-branch"

# Aborta una fusión con conflictos
git merge --abort
```

**Verifica:** `git log --oneline --graph -10` para ver la fusión en la topología de commits.

**Modo de fallo (conflictos de fusión):** cuando Git no puede fusionar automáticamente, marca los conflictos en los archivos. Edita los archivos en conflicto, luego haz `git add` y `git commit`. O `git merge --abort` para deshacerlo por completo.

### 2.5 git rebase

Reaplica commits sobre otra base. Crea un historial lineal (sin merge commits).

**Ejemplo de uso:**

```bash
# Rebase de la rama actual sobre main
git rebase main

# Rebase interactivo (squash, reordenar, editar commits)
git rebase -i HEAD~5

# Aborta un rebase
git rebase --abort

# Continúa tras resolver los conflictos
git rebase --continue
```

<Notice type="warning" title="No hagas rebase de ramas compartidas">
Nunca hagas rebase de commits que ya has publicado y compartido con otros. Rebase reescribe los hashes de los commits, lo que causará conflictos a cualquiera que esté trabajando sobre ellos. Rebase es seguro en ramas solo locales.
</Notice>

### 2.6 git worktree

Te permite desplegar varias ramas simultáneamente en directorios separados, todos vinculados al mismo repositorio. Sin stash ni segundos clones.

**Ejemplo de uso:**

```bash
# Crea un worktree de main en ../hotfix
git worktree add ../hotfix main

# Crea un worktree con una rama nueva
git worktree add -b hotfix-123 ../hotfix-123 main

# Lista todos los worktrees
git worktree list
# /home/user/project          abc1234 [main]
# /home/user/hotfix           def5678 [main]

# Elimina un worktree
git worktree remove ../hotfix

# Limpia metadatos de worktrees obsoletos
git worktree prune
```

<Notice type="info" title="Los worktrees están infravalorados">
Los worktrees te permiten trabajar en una rama de funcionalidad mientras corriges rápido un bug en main: sin stash, sin un segundo clon. También son útiles para [herramientas de codificación con IA](/es/herramientas-codificacion-ia/) que pueden trabajar en ramas paralelas. Cada worktree comparte la misma base de datos `.git`, así que evitas el coste de disco de un clon completo. Yo uso worktrees siempre que necesito cambiar de contexto entre ramas.
</Notice>

**Modo de fallo (detached HEAD):** hacer `git switch` a un hash de commit concreto (no a un nombre de rama) te deja en estado detached HEAD. Tu trabajo no está en ninguna rama. Arréglalo con:

```bash
git switch -c new-branch-name
```

Esto guarda tu trabajo en una rama de verdad.

## Sección 3: Comandos de repositorios remotos

Trabajar con repositorios remotos: GitHub, GitLab, Gitea, [Forgejo](/es/forgejo-woodpecker-ci-cicd/) o cualquier servidor Git. Si haces push por SSH, asegúrate primero de tener configurada tu [clave SSH para GitHub](/es/vincular-github-ssh-macos-linux/).

### 3.1 git remote

Gestiona las conexiones con repositorios remotos.

**Ejemplo de uso:**

```bash
# Lista los remotos
git remote
# origin

# Lista los remotos con sus URL
git remote -v
# origin  https://github.com/user/repo.git (fetch)
# origin  https://github.com/user/repo.git (push)

# Añade un remoto
git remote add upstream https://github.com/original/repo.git

# Elimina un remoto
git remote remove upstream

# Cambia la URL de un remoto
git remote set-url origin git@github.com:user/repo.git

# Poda las ramas de seguimiento remoto obsoletas
git remote prune origin
```

### 3.2 git fetch

Descarga objetos y refs de un repositorio remoto sin fusionar.

**Ejemplo de uso:**

```bash
# Fetch desde origin
git fetch

# Fetch desde un remoto concreto
git fetch upstream

# Fetch y poda las ramas remotas borradas
git fetch --prune

# Fetch de una rama concreta
git fetch origin feature-branch
```

Uso `git fetch --prune` por costumbre. Limpia las ramas de seguimiento remoto que se han borrado en el servidor.

### 3.3 git pull

Descarga y fusiona los cambios de una rama remota. Equivale a `git fetch` seguido de `git merge`.

**Ejemplo de uso:**

```bash
# Pull con fusión
git pull

# Pull con rebase en lugar de merge (historial más limpio)
git pull --rebase

# Pull desde un remoto y una rama concretos
git pull upstream main
```

### 3.4 git push

Sube los commits locales a un repositorio remoto.

**Ejemplo de uso:**

```bash
# Push de la rama actual a origin
git push

# Push y establece el seguimiento upstream
git push -u origin new-feature

# Borra una rama remota
git push --delete origin old-branch
```

### 3.5 git push --force-with-lease (push forzado seguro)

<Notice type="warning" title="Nunca uses --force en ramas compartidas">
`git push --force` sobrescribe la rama remota incondicionalmente. Si alguien subió commits después de tu último fetch, esos commits desaparecen. Usa siempre `--force-with-lease`: comprueba que la ref remota no ha cambiado desde tu último fetch y aborta si lo ha hecho.
</Notice>

**Ejemplo de uso:**

```bash
# Push forzado seguro (comprueba primero el estado remoto)
git push --force-with-lease origin main

# Aún más seguro (también comprueba el reflog local)
git push --force-with-lease --force-if-includes origin main
```

`--force-with-lease` me ha salvado más de una vez. Es la diferencia entre «reescribí el historial de forma segura» y «acabo de destruir el trabajo de mi compañero».

### 3.6 Clones superficiales y parciales

Cuando estás en un VPS con ancho de banda medido, ejecutas CI o trabajas con un repo enorme, los clones completos desperdician ancho de banda y disco. Estas flags ayudan.

**Ejemplo de uso:**

```bash
# Clone superficial: solo el último commit (ideal para CI)
git clone --depth 1 https://github.com/user/large-repo.git

# Clone parcial: descarga los blobs bajo demanda (ahorra disco)
git clone --filter=blob:none https://github.com/user/large-repo.git

# Convierte un clone superficial en historial completo más adelante
git fetch --unshallow
```

<Notice type="info" title="Clones superficiales para CI/CD">
Un clon `--depth 1` descarga solo el último commit y su árbol: nada de historial. Esto reduce drásticamente el tiempo de clonación en repos grandes. En pipelines de CI donde solo necesitas el código más reciente para compilar y probar, los clones superficiales son la opción por defecto por una razón. Para despliegues en VPS, los clones parciales (`--filter=blob:none`) son un buen punto intermedio: tienes el historial pero descargas el contenido de los archivos bajo demanda.
</Notice>

## Sección 4: Ver el historial y comparar cambios

Entender qué pasó y cuándo. Estos comandos son tu máquina del tiempo.

### 4.1 git log

Muestra el historial de commits. La salida por defecto es verbosa: aprende las flags que importan.

**Ejemplo de uso:**

```bash
# Log básico
git log

# Formato de una línea (mi uso diario)
git log --oneline

# Grafo visual de ramas
git log --graph --oneline --all

# Limita la salida
git log -10

# Muestra los archivos cambiados por commit
git log --stat

# Busca commits que introdujeron/eliminaron una cadena (pickaxe)
git log -S"buggy_function"

# Traza el historial de una función concreta
git log -L :function_name:file.c

# Muestra commits desde una fecha
git log --since="2026-01-01"

# Muestra commits por autor
git log --author="Dragos"

# Limita el ancho del grafo (Git 2.55+)
git log --graph --oneline --all --graph-lane-limit=5
```

<Notice type="info" title="La búsqueda pickaxe es potente">
`git log -S"string"` encuentra cada commit que añadió o eliminó esa cadena. Es como `git blame` pero a lo largo de todo el historial. Yo lo uso para averiguar cuándo se introdujo un bug. Para coincidencias con regex, usa `git log -G"pattern"`.
</Notice>

### 4.2 git diff

Muestra los cambios entre commits, ramas o el directorio de trabajo.

**Ejemplo de uso:**

```bash
# Cambios aún no preparados
git diff

# Cambios preparados para el commit
git diff --cached

# Diff entre dos ramas
git diff main..feature-branch

# Resumen de cambios (archivos y recuento de líneas)
git diff --stat

# Diff de un archivo concreto
git diff HEAD -- file.txt
```

### 4.3 git show

Muestra los detalles de un commit concreto (diff, mensaje, autor).

**Ejemplo de uso:**

```bash
# Muestra el último commit
git show

# Muestra un commit concreto
git show abc1234

# Muestra solo los archivos cambiados
git show --stat abc1234
```

### 4.4 git blame

Muestra quién modificó por última vez cada línea de un archivo y cuándo.

**Ejemplo de uso:**

```bash
# Blame de un archivo
git blame file.txt

# Blame de un rango de líneas concreto
git blame -L 10,20 file.txt

# Usa un algoritmo de diff distinto (Git 2.54+)
git blame --diff-algorithm=patience file.txt
```

### 4.5 git shortlog

Resume la salida de `git log` por autor. Útil para ver la actividad de los colaboradores.

**Ejemplo de uso:**

```bash
# Resumen por autor
git shortlog -sn

# Resumen desde una fecha
git shortlog -sn --since="2026-01-01"
```

### 4.6 git describe

Genera un identificador legible a partir de la etiqueta más cercana.

**Ejemplo de uso:**

```bash
git describe --tags
# v1.2.3-14-gabc1234
# (14 commits después de la etiqueta v1.2.3, commit que empieza por abc1234)
```

Úsalo en scripts de compilación para el versionado: la salida es siempre única y te dice exactamente a qué distancia estás de la última release.

### 4.7 git range-diff

Compara dos versiones de un rango de commits. El caso de uso principal: verificar que un rebase no ha perdido ni alterado nada.

**Ejemplo de uso:**

```bash
# Compara la versión antigua y la nueva de una rama tras un rebase
git range-diff origin/main..old-branch origin/main..new-branch
```

**Verifica tras el rebase:** ejecuta `git range-diff` después de rebasar para confirmar que el diff de cada commit es el mismo (o intencionadamente distinto). Si faltan commits o sus diffs cambiaron inesperadamente, algo salió mal.

## Sección 5: Deshacer cambios y corregir errores

Todo el mundo comete errores. Estos comandos son tu red de seguridad.

### 5.1 git reset

Mueve HEAD y opcionalmente modifica el área de preparación y el directorio de trabajo.

**Ejemplo de uso:**

```bash
# Reset soft: mantiene los cambios preparados
git reset --soft HEAD~1

# Reset mixto (por defecto): mantiene los cambios sin preparar
git reset HEAD~1

# Reset hard: descarta todo desde ese commit
git reset --hard HEAD~1
```

<Notice type="warning" title="git reset --hard es destructivo">
`git reset --hard` descarta los cambios sin confirmar y mueve HEAD. Pero los commits no desaparecen de inmediato: siguen en el reflog. Si hiciste un hard reset por accidente, consulta la sección de recuperación más abajo.
</Notice>

<Accordion label="Recuperarse de un git reset --hard" group="recovery">

Si acabas de ejecutar `git reset --hard` y perdiste commits, siguen en el reflog:

```bash
# Consulta el reflog (tu red de seguridad)
git reflog
# abc1234 HEAD@{0}: reset: moving to HEAD~3
# def5678 HEAD@{1}: commit: Important work here

# Restaura al commit anterior al reset
git reset --hard HEAD@{1}
# o
git reset --hard def5678
```

El reflog conserva las entradas durante 90 días por defecto. Mientras el recolector de basura no se haya ejecutado, puedes recuperarlo.

</Accordion>

### 5.2 git restore

La forma moderna de descartar cambios del directorio de trabajo o sacar archivos del staging. Sustituye a `git checkout -- <file>`.

**Ejemplo de uso:**

```bash
# Descarta los cambios de un archivo (restaura al último estado confirmado)
git restore file.txt

# Saca un archivo del área de preparación
git restore --staged file.txt

# Restaura un archivo desde un commit concreto
git restore --source=HEAD~2 file.txt

# Restaura todos los archivos del directorio de trabajo
git restore .
```

### 5.3 git revert

Crea un commit nuevo que deshace un commit concreto. A diferencia de `reset`, no reescribe el historial.

**Ejemplo de uso:**

```bash
# Revierte un commit concreto
git revert abc1234

# Revierte sin hacer commit (deja la reversión preparada)
git revert --no-commit abc1234
```

Usa `git revert` en ramas compartidas donde no puedes reescribir el historial. Usa `git reset` en ramas solo locales.

### 5.4 git clean

Elimina los archivos no rastreados del directorio de trabajo.

**Ejemplo de uso:**

```bash
# Simulacro: muestra qué se borraría
git clean -n

# Elimina archivos no rastreados
git clean -f

# Elimina archivos y directorios no rastreados
git clean -fd

# Incluye también los archivos ignorados
git clean -fdx
```

Ejecuta siempre primero con `-n` para previsualizar. `git clean` no tiene deshacer.

### 5.5 git stash

Aparta temporalmente los cambios para que puedas cambiar de rama o trabajar en otra cosa.

**Ejemplo de uso:**

```bash
# Guarda los cambios actuales en el stash
git stash

# Stash con un mensaje descriptivo
git stash push -m "WIP: login feature"

# Lista todos los stashes
git stash list
# stash@{0}: On main: WIP: login feature
# stash@{1}: On main: experimental changes

# Aplica el stash más reciente (lo mantiene en la lista)
git stash apply

# Aplica y elimina el stash más reciente
git stash pop

# Aplica un stash concreto
git stash apply stash@{1}

# Crea una rama desde un stash
git stash branch new-feature-branch stash@{0}

# Elimina un stash concreto
git stash drop stash@{0}

# Elimina todos los stashes
git stash clear

# Muestra el contenido de un stash
git stash show -p stash@{0}
```

### 5.6 git cherry-pick

Aplica un commit concreto de una rama a la rama actual.

**Ejemplo de uso:**

```bash
# Cherry-pick de un solo commit
git cherry-pick abc1234

# Cherry-pick sin hacer commit
git cherry-pick --no-commit abc1234

# Cherry-pick de un rango de commits
git cherry-pick abc1234..def5678
```

## Sección 6: Comandos avanzados de Git

Depuración, automatización y flujos de trabajo de usuario avanzado.

### 6.1 git bisect

Usa búsqueda binaria para encontrar el commit que introdujo un bug.

**Bisect manual:**

```bash
git bisect start
git bisect bad          # el commit actual está roto
git bisect good v1.0    # esta etiqueta/commit funcionaba

# Git despliega un commit intermedio. Pruébalo y luego:
git bisect good         # este commit funciona
# o
git bisect bad          # este commit está roto

# Git va acotando hasta encontrar el commit malo
# Al terminar:
git bisect reset
```

**Bisect automatizado con un script:**

```bash
git bisect start HEAD v1.0
git bisect run ./test-script.sh
```

El script de prueba debe salir con 0 para «bueno» y con un valor distinto de cero para «malo». Git desplegará commits automáticamente y ejecutará el script hasta encontrar el primer commit malo. Este es el verdadero poder de bisect: deja que el ordenador haga el trabajo.

<Notice type="info" title="git bisect run ahorra horas">
Escribe un script de prueba que reproduzca el bug, hazlo ejecutable y pásalo a `git bisect run`. Hará búsqueda binaria a través de cientos de commits en minutos. Yo lo he usado para localizar regresiones a lo largo de meses de historial de commits.
</Notice>

### 6.2 git tag

Crea referencias con nombre a commits concretos (normalmente para releases).

**Ejemplo de uso:**

```bash
# Etiqueta ligera
git tag v1.0.0

# Etiqueta anotada (recomendado: incluye metadatos)
git tag -a v1.0.0 -m "Release 1.0.0"

# Etiqueta un commit concreto
git tag -a v1.0.0 abc1234

# Lista etiquetas
git tag

# Lista etiquetas con mensajes
git tag -n

# Sube las etiquetas al remoto
git push origin v1.0.0

# Sube todas las etiquetas
git push origin --tags
```

### 6.3 git submodule

Gestiona repositorios externos incrustados en tu repositorio.

**Ejemplo de uso:**

```bash
# Añade un submódulo
git submodule add https://github.com/user/library.git libs/library

# Inicializa los submódulos tras clonar
git submodule init
git submodule update

# O combina ambos
git submodule update --init --recursive

# Actualiza los submódulos a los últimos commits remotos
git submodule update --remote
```

### 6.4 git archive

Crea un archivo tar o zip del repositorio en un punto concreto.

**Ejemplo de uso:**

```bash
# Crea un tar de HEAD
git archive --format=tar HEAD > project.tar

# Crea un zip de una etiqueta concreta
git archive --format=zip v1.0.0 > project-v1.0.0.zip

git archive --format=tar HEAD src/ > src-only.tar
```

### 6.5 git reflog

Muestra un registro de dónde ha estado HEAD. Tu red de seguridad para operaciones de recuperación.

**Ejemplo de uso:**

```bash
# Consulta el reflog

# def5678 HEAD@{1}: reset: moving to HEAD~1

# Resetea a una entrada del reflog
git reset --hard HEAD@{2}
```

### 6.6 git notes

Adjunta metadatos a los commits sin reescribir el historial. Piensa en ello como comentarios sobre commits.

**Ejemplo de uso:**

```bash
# Añade una nota a un commit
git notes add -m "Reviewed-by: Jane" abc1234

# Muestra las notas de un commit
git notes show abc1234

# Lista todas las notas
git notes list

# Sube las notas al remoto (no se suben por defecto)
git push origin refs/notes/commits
```

Casos de uso: adjuntar resultados de CI, metadatos de code review o información de cobertura de tests a commits concretos.

### 6.7 git commit --fixup y --autosquash

Limpia el historial de commits antes de fusionar.

**Ejemplo de uso:**

```bash
# Crea un commit fixup dirigido a un commit concreto
git commit --fixup=abc1234

# Rebase interactivo que aplasta automáticamente los commits fixup
git rebase -i --autosquash main
```

Este es mi flujo preferido para pull requests: hago commits fixup según los revisores piden cambios y luego los aplasto en el lugar correcto antes de fusionar.

### 6.8 git bundle

Crea un archivo portable del repositorio que se puede clonar. Útil para entornos sin conexión (air-gapped), transferencias offline o copias de seguridad.

**Ejemplo de uso:**

```bash
# Crea un bundle con todas las ramas
git bundle create repo.bundle --all

# Crea un bundle con ramas concretas
git bundle create repo.bundle main feature-branch

# Clona desde un bundle
git clone repo.bundle new-repo

# Verifica que un bundle es válido
git bundle verify repo.bundle
```

### 6.9 git am

Aplica parches desde un mailbox (flujos basados en email). Todavía lo usan el kernel de Linux y otros proyectos con revisión de código por email.

**Ejemplo de uso:**

```bash

git am < patch-file.patch

# Aplica una serie de parches desde un directorio
git am patches/*.patch

# Aborta si algo va mal
git am --abort

# Aplica con merge de 3 vías (resuelve más casos)
git am --3way < patch-file.patch
```

## Sección 7: Colaboración y flujos de trabajo con parches

Trabajar con parches, envíos por email y revisión de código.

### 7.1 git cherry

Encuentra commits que no se han aplicado en upstream.

**Ejemplo de uso:**

```bash
# Muestra los commits de la rama actual que no están en upstream
git cherry upstream/main
```

Aplica un parche creado por `git diff` o `git format-patch`.

```bash
git apply --check changes.patch

# Aplica un parche
```

```bash
git format-patch main..feature-branch

git format-patch -3 -o patches/
```

### 7.4 git send-email

Envía archivos de parche por email. Se usa en proyectos con revisión de código por email (el kernel de Linux, el propio Git).

**Ejemplo de uso:**

```bash
# Envía una serie de parches
git send-email patches/*.patch

# Envía a un destinatario concreto
git send-email --to=maintainer@example.com patches/*.patch
```

### 7.5 git request-pull

Genera un mensaje de pull request para flujos basados en email.

**Ejemplo de uso:**

```bash
git request-pull v1.0 https://github.com/user/repo.git main
```

## Sección 8: Mantenimiento y rendimiento del repositorio

Mantén tus repositorios rápidos y sanos. Especialmente importante si alojas repos en un VPS con disco e I/O limitados.

### 8.1 git gc

Recolección de basura: limpia archivos innecesarios y optimiza el repositorio.

**Ejemplo de uso:**

```bash
# Recolección de basura estándar
git gc

# Agresiva (más lenta pero más exhaustiva: úsala ocasionalmente)
git gc --aggressive

# Auto-gc con umbrales más altos (empaquetado menos frecuente)
git gc --auto
```

**Verifica:** ejecuta `git log -1` después del gc para confirmar que el repo sigue funcionando.

<Notice type="warning" title="git gc --aggressive puede ser lento">
`--aggressive` reescribe los pack files para una mejor compresión. En repos grandes puede tardar de minutos a horas. Úsalo ocasionalmente, no como tarea diaria. Para el mantenimiento rutinario, un simple `git gc` o `git maintenance` es mejor.
</Notice>

### 8.2 git fsck

Verifica la integridad de la base de datos del repositorio.

**Ejemplo de uso:**

```bash
# Comprueba objetos corruptos
git fsck

# Comprueba e informa de objetos sueltos (dangling)
git fsck --dangling
```

Ejecuta `git fsck` tras un clon sospechoso o cuando sospeches corrupción. Si informa de errores, vuelve a clonar desde una fuente fiable.

### 8.3 git maintenance

Programa tareas en segundo plano para mantener los repositorios rápidos. Introducido en Git 2.30.

**Ejemplo de uso:**

```bash
# Activa el mantenimiento en segundo plano (programa vía cron/systemd)
git maintenance start

# Ejecuta las tareas de mantenimiento manualmente
git maintenance run

# Desactiva el mantenimiento en segundo plano
git maintenance stop

# Ejecuta una tarea concreta
git maintenance run --task=commit-graph
```

<Notice type="info" title="git maintenance evita las pausas del auto-packing">
Sin `git maintenance`, Git ejecuta `gc --auto` durante ciertas operaciones (push, merge, etc.), lo que puede pausar durante segundos o minutos en repos grandes. Con `git maintenance start`, las tareas en segundo plano se ejecutan según lo programado y esas operaciones siguen siendo rápidas. Desde Git 2.54, el reempaquetado geométrico es la estrategia por defecto: mejor rendimiento para la mayoría de repos.
</Notice>

### 8.4 git rerere

«Reuse recorded resolution»: recuerda cómo resolviste un conflicto y aplica la misma resolución automáticamente la próxima vez.

**Ejemplo de uso:**

```bash
# Activa rerere
git config set rerere.enabled true

# Una vez activado, Git registra automáticamente las resoluciones
# de conflictos y las reaplica durante rebases o merges
```

Si haces rebase con frecuencia o mantienes ramas longevas, `rerere` ahorra mucho tiempo.

### 8.5 git count-objects

Muestra el uso de disco de la base de datos de objetos de Git.

**Ejemplo de uso:**

```bash
# Recuento básico
git count-objects

# Legible con detalles
git count-objects -vH
# count: 0
# size: 0 bytes
# in-pack: 1523
# packs: 1
# size-pack: 2.34 MiB
# garbage: 0
# size-garbage: 0 bytes
```

Útil para vigilar el tamaño del repo en instancias VPS con disco limitado.

### 8.6 git prune

Elimina los objetos inalcanzables de la base de datos. Normalmente lo gestiona `git gc`, pero es útil para limpieza manual.

**Ejemplo de uso:**

```bash
# Simulacro
git prune -n

# Poda los objetos inalcanzables
git prune
```

## Sección 9: Comandos para scripting y automatización

Analiza especificaciones de revisión. El recurso principal para extraer información en scripts de shell.

**Ejemplo de uso:**

```bash
# Cuenta el total de commits
git rev-list --count HEAD

# Lista los commits entre dos refs
git rev-list main..feature-branch
```

Comandos de inspección de bajo nivel.

```bash
# Lista los archivos del índice (área de preparación)
```

<Accordion label="Fragmentos de Git para CI/CD listos para copiar" group="cicd">

## Sección 10: Git moderno: switch, restore, worktrees y más

Esta sección consolida las funcionalidades modernas de Git que han madurado desde 2019. Si todavía usas flujos de Git como si fuera 2015, empieza aquí.

### 10.1 git sparse-checkout

Trabaja con un subconjunto de un repositorio grande. Esencial para monorepos.

**Ejemplo de uso:**

```bash
# Clona con sparse checkout
git clone --filter=blob:none --sparse https://github.com/large/repo.git
cd repo

# Define qué directorios quieres
git sparse-checkout set src/frontend docs/

# Añade más directorios después
git sparse-checkout add src/shared/

# Lista las rutas sparse-checkout actuales
git sparse-checkout list

# Desactiva sparse-checkout (obtén todo)
git sparse-checkout disable
```

Combinado con el clone parcial (`--filter=blob:none`), solo descargas los archivos que necesitas. Genial para monorepos en los que solo trabajas en un servicio.

### 10.2 Firma de commits con SSH

La firma con GPG ha sido la forma tradicional de firmar commits, pero la firma con SSH es mucho más sencilla de configurar y está soportada por GitHub, GitLab y Gitea.

<Tabs>
<Tab name="Firma con SSH (recomendado)">
```bash
# Configura Git para usar la firma SSH
git config set gpg.format ssh

# Define tu clave de firma (tu clave pública SSH)
git config set user.signingkey ~/.ssh/id_ed25519.pub

# Firma un commit
git commit -S -m "Signed commit"

# Firma todos los commits por defecto
git config set commit.gpgsign true

# Registra tu clave SSH como clave de firma en GitHub/GitLab
# GitHub: Settings → SSH and GPG keys → New SSH key (select "Signing key")
```
</Tab>
<Tab name="Firma con GPG (heredado)">
```bash
# Genera una clave GPG
gpg --full-generate-key

# Configura Git para usar la clave GPG
git config set user.signingkey YOUR_GPG_KEY_ID

# Firma un commit
git commit -S -m "Signed commit"

# Exporta la clave pública para GitHub/GitLab
gpg --armor --export YOUR_GPG_KEY_ID
```
</Tab>
</Tabs>

La firma con SSH es más sencilla: ya tienes las claves, no hay gestión de claves más allá de la que usas para push/pull y no hay un agente GPG que configurar. Si empiezas de cero, usa SSH.

### 10.3 El comando git history (Git 2.54+)

Nuevo en Git 2.54, el comando `git history` simplifica los flujos de rebase interactivo.

```bash
# Reescribe el mensaje de un commit (sustituye al rebase interactivo en ediciones simples)
git history reword HEAD~3

# Divide un commit en varios commits
git history split HEAD~2

# Crea un commit fixup y prepáralo para autosquash
git history fixup HEAD~5
```

<Notice type="info" title="git history es experimental">
El comando `git history` sigue siendo experimental en Git 2.55. Funciona, pero la interfaz puede cambiar. Si necesitas un comportamiento estable, usa `git rebase -i` por ahora. Pero no le pierdas de vista: es hacia donde se dirige Git.
</Notice>

### 10.4 Hooks basados en config (Git 2.54+)

Los hooks ahora se pueden configurar vía `git config` en lugar de colocar scripts en `.git/hooks/`. Esto facilita compartir hooks en un equipo.

```bash
# Define un hook vía config
git config set core.hooksPath .githooks
```

Coloca tus scripts de hook en `.githooks/` y haz commit de ese directorio. Todo el que clone el repo recibe los hooks automáticamente.

### 10.5 git stash export/import

Transfiere stashes entre repositorios o máquinas.

```bash
# Exporta el stash a un archivo
git stash export > stash.bundle

# Impórtalo en otro repo
git stash import < stash.bundle
```

<Notice type="info" title="Plugins de Zsh para productividad con Git">
Los plugins y aliases del shell pueden acelerar mucho tu flujo de trabajo con Git. Si usas Zsh, echa un vistazo a los [plugins de Zsh para productividad con Git](/es/mejores-plugins-oh-my-zsh/): completado con tab, integración en el prompt y aliases de atajos.
</Notice>

## Sección 11: Git 3.0: lo que viene

Git 3.0 apunta a finales de 2026. Esto es lo que necesitas saber para prepararte.

### 11.1 SHA-256 como algoritmo de hash por defecto

Git ha usado SHA-1 desde su creación, pero SHA-1 tiene ataques de colisión conocidos (el ataque SHAttered de 2017 lo hizo práctico). Git 3.0 hará de SHA-256 el valor por defecto para repositorios nuevos.

**Qué cambia:**
- La longitud del hash pasa de 40 caracteres hexadecimales a 64
- Los repos nuevos creados con Git 2.51+ ya usan SHA-256 por defecto
- Los repos SHA-1 existentes siguen funcionando (no hay migración forzada)

**El problema:** GitHub, GitLab y otras forjas aún no soportan repositorios SHA-256. El ecosistema necesita ponerse al día antes de que SHA-256 sea práctico para la mayoría de equipos.

### 11.2 Backend de referencias reftable

Reftable es un formato nuevo para almacenar las referencias de Git (ramas, etiquetas). Ya está disponible:

```bash
# Crea un repo con backend reftable
git init --ref-format=reftable
```

**Por qué importa:**
- Hasta 22x más rápido en fetch y 18x más rápido en push en repos con más de 10.000 referencias
- Actualizaciones de referencias atómicas (adiós a escrituras parciales tras un fallo)
- Sin conflictos de nombres de rama a nivel de sistema de archivos (sistemas de archivos que no distinguen mayúsculas)
- Menor huella de disco para el almacenamiento de referencias

Para repos con muchas ramas (monorepos, equipos grandes), reftable es una mejora significativa. Si [autoalojas Git con Forgejo](/es/forgejo-woodpecker-ci-cicd/), comprueba el estado de su soporte de reftable.

### 11.3 Rust como requisito de compilación

Git 3.0 requerirá Rust como dependencia de compilación. Esto permite implementaciones memory-safe de las rutas de código críticas para el rendimiento. La integración del sistema de compilación Meson continúa.

**Impacto:** la mayoría de usuarios no lo notarán: instalan Git desde gestores de paquetes. Pero compilar Git desde el código fuente en plataformas sin toolchains de Rust requerirá un paso extra.

### 11.4 Cambios que rompen compatibilidad

- **`git-whatchanged` eliminado.** Usa `git log --raw` en su lugar (misma salida, más flags).
- **`git switch` y `git restore` dejan de ser experimentales.** Git 3.0 los recomendará encarecidamente frente a `git checkout`. Empieza a migrar ya.
- **Varias opciones obsoletas eliminadas.** Consulta `BreakingChanges.txt` en el código fuente de Git para la lista completa.

<Notice type="warning" title="Verifica el calendario de Git 3.0">
La fecha de finales de 2026 es aspiracional. Consulta [git-scm.com](https://git-scm.com/) para ver el estado más reciente antes de depender de cualquier funcionalidad de Git 3.0 en producción.
</Notice>

<Accordion label="Checklist de preparación para Git 3.0" group="git3">

- **Cámbiate a `git switch` y `git restore`**: deja de usar `git checkout` para operaciones de ramas/archivos
- **Usa la nueva sintaxis `git config set/get/list`**: las flags antiguas siguen funcionando pero la nueva forma es más limpia
- **Prueba `git init --ref-format=reftable`** en un repo que no sea de producción para ver si funciona en tu flujo
- **Actualiza los scripts de CI** para manejar hashes SHA-256 (64 caracteres frente a 40) si parsean hashes de commits
- **Vigila tu forja** (GitHub, GitLab, Gitea) por si anuncia soporte de repos SHA-256
- **Mantén Git actualizado**: las correcciones de seguridad y las funcionalidades llegan en cada release

</Accordion>

## Sección 12: Fundamentos de seguridad

La seguridad de Git importa a todo equipo. Estos comandos y configuraciones ayudan a proteger tu repositorio.

### 12.1 Verificación de objetos en fetch/push

Detecta objetos corruptos o maliciosos durante la transferencia.

```bash
# Activa la verificación de objetos para todos los fetch/push
git config set transfer.fsckObjects true
```

Con esto activado, Git verifica la integridad de cada objeto recibido de un remoto. Actívalo globalmente o por repositorio.

### 12.2 Verificación de commits y etiquetas

Verifica que los commits y las etiquetas están firmados por claves de confianza.

```bash
# Verifica la firma de un commit
git verify-commit abc1234

# Verifica la firma de una etiqueta
git verify-tag v1.0.0
```

### 12.3 Mantén Git actualizado

Vulnerabilidades de seguridad recientes que deberías conocer:

<Notice type="error" title="Actualiza Git inmediatamente si estás en una versión antigua">
**CVE-2025-48384** (julio de 2025): escritura arbitraria de archivos en Linux/macOS vía `git clone`. Está en el catálogo CISA KEV: se explota activamente. **CVE-2024-50349** y **CVE-2024-52006** (octubre de 2024): problemas de manejo de credenciales que afectan a todas las versiones anteriores. Actualiza siempre a la última versión estable de Git.
</Notice>

```bash
# Comprueba tu versión de Git
git --version

# Actualiza en Ubuntu/Debian
sudo apt update && sudo apt install git

# Actualiza en macOS
brew upgrade git

# Actualiza en Fedora/RHEL
sudo dnf update git
```
