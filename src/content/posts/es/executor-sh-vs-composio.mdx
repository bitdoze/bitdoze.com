Todo agente de IA necesita herramientas. Ya sea enviar mensajes de Slack, consultar una base de datos o llamar a una API de terceros, el agente tiene que conectarse a servicios externos de alguna forma. Composio construyó un negocio alrededor de esto: más de 1,500 toolkits preconstruidos, OAuth gestionado y un runtime alojado que se encarga de todo por ti. Funciona, y funciona bien para equipos que quieren una plataforma totalmente gestionada.

Pero si quieres autoalojar, inspeccionar el runtime o evitar los precios por llamada a escala, el planteamiento de Composio se desmorona. El runtime es de código cerrado. El autoalojamiento requiere un contrato Enterprise. Y las credenciales pasan por su nube en los planes self-serve.

Ahí es donde entra [Executor.sh](https://executor.sh/). Es un gateway MCP totalmente de código abierto. Configura tus integraciones una vez y cada agente compatible con MCP las comparte a través de un solo endpoint. Puedes ejecutarlo en tu propia infraestructura con un único comando de Docker. Sin llamadas comerciales. Sin dependencia del proveedor. Sin tarifas por llamada cuando lo autoalojas.

Este artículo te ofrece una comparación directa entre las dos plataformas, los compromisos honestos y una guía paso a paso para autoalojar Executor.sh con Docker.

## ¿Qué es Composio?

Composio se lanzó en 2024 y se convirtió en la plataforma por defecto para las llamadas a herramientas de agentes de IA. Levantó una Serie A de $25M de Lightspeed Ventures en julio de 2025 (financiación total: ~$29M) y tiene aproximadamente 30,300 estrellas en GitHub a septiembre de 2026. La propuesta: dale a tu agente de IA acceso a más de 1,500 toolkits SaaS preconstruidos y preautenticados (Gmail, Slack, GitHub, Notion, Jira, Salesforce y cientos más) sin escribir código de integración.

La plataforma gestiona los flujos OAuth de principio a fin, administra la renovación de tokens y limita las credenciales por usuario. Ofrece SDKs para más de 25 frameworks (OpenAI, Anthropic, LangChain, CrewAI, Vercel AI SDK y el [framework de agentes de IA Mastra](/build-ai-agent-mastra/)), un Tool Router para el descubrimiento basado en intención, un workbench en sandbox para ejecución remota de Python/JS, triggers para trabajo orientado a eventos y un leaderboard Composio Bench para medir agentes en tareas reales de uso de herramientas. Ahora también se pueden registrar servidores MCP personalizados gratis, así que el catálogo va más allá de la lista preconstruida. Para el recorrido completo por la parte gestionada, consulta mi [guía de Composio MCP](/es/guia-composio-mcp/).

Composio tiene las certificaciones SOC 2 Type II e ISO 27001. Si tu equipo necesita credenciales de cumplimiento desde el primer día, esto es una ventaja real.

En el fondo, Composio es una plataforma gestionada. El backend que almacena las credenciales y ejecuta las llamadas a herramientas es propietario. El repositorio de código abierto en GitHub solo contiene los SDKs y las herramientas del CLI, no el runtime. Tus credenciales y datos de ejecución pasan por la infraestructura en la nube de Composio en todos los planes self-serve.

## ¿Por qué buscar una alternativa a Composio?

Composio no es mal software. Pero tiene limitaciones estructurales que empujan a los desarrolladores a buscar alternativas:

<ListCheck>
<ul>
<li>Runtime de código cerrado. El repo de GitHub solo contiene SDKs, no la plataforma que almacena y ejecuta las llamadas a herramientas</li>
<li>Autoalojamiento solo para Enterprise. El issue de GitHub #291 que pide autoalojamiento self-serve lleva abierto desde 2024 sin resolución</li>
<li>Las credenciales pasan por la nube de Composio en los planes self-serve, algo inaceptable para equipos con requisitos de cumplimiento</li>
<li>Los precios por llamada escalan mal. El plan de $29/mes es un crédito de uso y luego $0.0003 por llamada: 500K llamadas cuestan unos $150. Las apps OAuth gestionadas por Composio lo empeoran, al limitar la cuota gratuita a 20K de las 100K llamadas mensuales</li>
<li>Los servidores MCP personalizados ya están soportados y son gratis, pero sigues sin poder inspeccionar, bifurcar ni modificar el runtime que los ejecuta</li>
<li>Sobrecarga de la ventana de contexto. Cargar miles de definiciones de herramientas consume muchos tokens incluso con el Tool Router</li>
</ul>
</ListCheck>

Si alguna de estas te suena de cerca, las [alternativas de código abierto](/es/mejores-llms-opensource-alternativa-claude/) merecen una mirada seria.

## ¿Qué es Executor.sh?

Executor.sh es un gateway MCP de código abierto creado por Rhys Sullivan, ex ingeniero de OpenCode. Pasó por el batch S26 de Y Combinator y ha crecido hasta las 3,982 estrellas en GitHub a septiembre de 2026 (desde ~2,600 en julio). Toda la plataforma tiene licencia MIT.

La idea central: configura tus integraciones una vez (servidores MCP, especificaciones OpenAPI, endpoints GraphQL, herramientas JS personalizadas) y cada agente compatible con MCP las comparte a través de un solo endpoint. Claude Code, Cursor, Codex, extensiones de VS Code, cualquier cosa que hable [MCP (Model Context Protocol)](/mcp-introduction-beginners/) funciona de inmediato. El modelo es integración → conexión → política: una integración puede tener muchas conexiones, y cada herramienta dentro puede estar permitida, requerir aprobación o estar bloqueada.

![Diagrama de arquitectura de Executor.sh: los clientes MCP se conectan a través del gateway Executor a APIs externas mediante el sandbox SES con inyección de credenciales del lado del host](@assets/images/26/07/executor-architecture.svg)

### Diferenciadores clave

**Eficiencia de contexto.** En lugar de mostrar a un agente miles de definiciones de herramientas (~278,800 tokens), Executor muestra una herramienta (~1,044 tokens). Los esquemas de las herramientas se cargan dinámicamente solo cuando se necesitan. Esto puede reducir los costes de API de forma notable en sesiones largas de agentes.

**Profundidad a nivel de protocolo.** Conectores nativos para MCP, OpenAPI, GraphQL y Google Discovery. Apunta Executor a cualquier spec e indexa automáticamente cada endpoint como una herramienta tipada.

**Descubrimiento semántico de herramientas.** Los agentes buscan herramientas por intención en lugar de memorizar nombres:

```js
tools.discover({ query: "send a slack message" })
```

**Sandbox SES.** Las llamadas a herramientas se ejecutan en un sandbox QuickJS aislado. Las credenciales se inyectan del lado del host en el momento de la llamada y nunca entran en el heap del sandbox. Es una mejora de seguridad real frente a plataformas donde las credenciales viven en el entorno de ejecución.

**Pausa/reanudación.** La ejecución se pausa para flujos OAuth o aprobación humana, y luego se reanuda limpiamente con `executor resume --execution-id exec_123`. Sin soluciones improvisadas.

**Motor de políticas.** Cada herramienta puede estar permitida, requerir aprobación o estar bloqueada. Las políticas se derivan de la semántica de la spec: `GET` frente a `DELETE` para OpenAPI, `destructiveHint` para MCP.

**Cinco opciones de despliegue:** Cloud (alojado), app de escritorio (Mac/Windows/Linux), CLI (`npm i -g executor`, y luego `executor install` lo ejecuta como un servicio duradero en segundo plano), Docker y Cloudflare Workers. El sistema de plugins está abierto a cualquier tipo de integración, y un SDK de TypeScript (`@executor-js/sdk`, con APIs nativas de Promise y Effect) incrusta el runtime en tu propio código.

<Notice type="success" title="Totalmente de código abierto">
Cada opción de despliegue, incluidos el autoalojamiento con Docker y el CLI, tiene licencia MIT. Puedes inspeccionar, modificar y bifurcar todo el código.
</Notice>

Puedes añadir [integraciones de servidores MCP como BrightData](/brightdata-mcp-guide/) o cualquier otro servidor MCP para ampliar lo que tus agentes pueden hacer. Y si necesitas gestionar los [comandos esenciales de Docker](/docker-commands/) para tu despliegue, también tenemos una guía para eso.

## Executor.sh vs Composio: comparación cara a cara

| Dimensión | Executor.sh | Composio |
|-----------|------------|----------|
| **Licencia** | MIT (totalmente de código abierto) | MIT (solo SDK); runtime cerrado |
| **Autoalojamiento** | Docker / Cloudflare (gratis, self-serve) | Solo Enterprise (requiere contacto comercial) |
| **Arquitectura** | Gateway MCP / proxy de integraciones | Plataforma gestionada de toolkits |
| **Fuentes de herramientas** | MCP, OpenAPI, GraphQL, Google Discovery, JS personalizado | Más de 1,500 toolkits SaaS preconstruidos + servidores MCP personalizados |
| **Eficiencia de contexto** | Carga dinámica (se muestra 1 herramienta) | Tool Router para buscar en el catálogo |
| **Modelo de seguridad** | Sandbox SES + inyección de credenciales del lado del host | OAuth gestionado + workbench en sandbox |
| **Integraciones personalizadas** | Añade cualquier spec OpenAPI/GraphQL/MCP | Servidores MCP personalizados (gratis); el runtime sigue cerrado |
| **Soporte de frameworks** | Cualquier cliente compatible con MCP + SDK de TS | Más de 25 adaptadores de frameworks |
| **Modelo de precios** | Tarifa plana por miembro, ejecuciones ilimitadas | Crédito de uso + coste por llamada adicional |
| **Nivel gratuito** | 3 miembros, 100K ejecuciones/mes | 100K llamadas a herramientas/mes, con tope duro (20K en apps OAuth gestionadas) |
| **Pago inicial** | $15/miembro/mes | Crédito de uso de $29/mes, luego $0.0003/llamada |
| **Estrellas** | ~3,982 | ~30,300 |
| **Madurez** | Feb 2026 (7 meses) | 2024+ (más de 2 años) |
| **SOC 2/ISO** | Bajo petición (Enterprise) | SOC 2 Type II, ISO 27001 |

Las diferencias más importantes son arquitectónicas. Composio te da un catálogo curado de integraciones preconstruidas: eliges lo que necesitas y la plataforma se encarga de la autenticación, la ejecución y el monitoreo. Executor te da un proxy a nivel de protocolo: tú traes tus propias specs y él las indexa, las ejecuta en sandbox y las expone como herramientas MCP.

Composio gana en amplitud de integraciones preconstruidas y cobertura de adaptadores de frameworks. Executor gana en apertura, autoalojamiento, eficiencia de contexto, modelo de seguridad (las credenciales nunca tocan el heap del sandbox) y predictibilidad de precios.

## Autoalojar Executor.sh con Docker

Esta es la sección que más importa. Si estás leyendo este artículo, probablemente quieres ejecutarlo en tu propia infraestructura. La buena noticia: es genuinamente sencillo.

Si solo quieres Executor en un portátil sin Docker, el CLI mejoró mucho desde julio: `npm i -g executor`, luego `executor install` registra un servicio duradero en segundo plano que sobrevive a los reinicios, y `executor web` abre la consola (en `http://127.0.0.1:4788`). `executor daemon status|stop|restart` gestiona el servicio. Para un servidor sí conviene la ruta Docker de abajo, pero para uso local el CLI es la instalación más limpia.

### Requisitos previos

<ListCheck>
<ul>
<li>Docker instalado en tu máquina o VPS</li>
<li>Un VPS o máquina local con 1GB+ de RAM</li>
<li>Un nombre de dominio (opcional, para proxy inverso con HTTPS)</li>
</ul>
</ListCheck>

Si necesitas un VPS, [Hetzner Cloud](https://go.bitdoze.com/hetzner) ofrece servidores europeos asequibles desde unos €4.49/mes, más que suficiente para ejecutar contenedores Docker como este. [Hostinger VPS](https://go.bitdoze.com/hostinger-vps) es otra opción económica con almacenamiento NVMe SSD si prefieres un proveedor diferente.

_Los precios de los VPS subieron en general en 2026 — si estás reconsiderando un servidor alquilado, mira [qué cambió y cuándo gana un mini PC](/es/subidas-precios-vps/)._

Para gestionar tus despliegues Docker, [Dokploy](/dokploy-install/) o [Coolify](/es/instalar-coolify-alternativa-heroku/) te dan una experiencia PaaS autoalojada con paneles web y HTTPS automático. También puedes consultar nuestra guía sobre [backends autoalojados con Docker](/convex-self-host/) para más patrones.

### Inicio rápido con docker run

Un solo comando te deja en marcha:

```bash
docker run -d \
  --name executor-selfhost \
  -p 4788:4788 \
  -v executor-data:/data \
  ghcr.io/rhyssullivan/executor-selfhost:latest
```

Eso es todo. Esto es lo que hace cada flag:

- `-p 4788:4788`: expone la consola web de Executor y el endpoint MCP en el puerto 4788
- `-v executor-data:/data`: persiste todos los datos (base de datos SQLite, credenciales, config) en un volumen Docker con nombre
- La imagen incluye todo: API tipada, servidor MCP, autenticación, ejecución de código QuickJS y consola web

Abre `http://localhost:4788` en tu navegador. La primera cuenta que crees se convierte en la propietaria. Todos los usuarios siguientes se unen mediante enlaces de invitación de un solo uso.

Para instalaciones sin interfaz (CI/CD, aprovisionamiento automatizado), pasa las credenciales de arranque:

```bash
docker run -d \
  --name executor-selfhost \
  -p 4788:4788 \
  -v executor-data:/data \
  -e EXECUTOR_BOOTSTRAP_ADMIN_EMAIL=admin@example.com \
  -e EXECUTOR_BOOTSTRAP_ADMIN_PASSWORD=your-secure-password \
  -e EXECUTOR_WEB_BASE_URL=https://executor.yourdomain.com \
  ghcr.io/rhyssullivan/executor-selfhost:latest
```

### Configuración con Docker Compose

Para una configuración más fácil de mantener, usa Docker Compose:

```yaml
services:
  executor:
    image: ghcr.io/rhyssullivan/executor-selfhost:latest
    container_name: executor-selfhost
    restart: unless-stopped
    ports:
      - "4788:4788"
    volumes:
      - executor-data:/data
    environment:
      - PORT=4788
      - EXECUTOR_DATA_DIR=/data
      # Optional: set your public URL
      # - EXECUTOR_WEB_BASE_URL=https://executor.yourdomain.com
      # Optional: headless bootstrap
      # - EXECUTOR_BOOTSTRAP_ADMIN_EMAIL=admin@example.com
      # - EXECUTOR_BOOTSTRAP_ADMIN_PASSWORD=changeme

volumes:
  executor-data:
```

Guárdalo como `docker-compose.yml` y ejecuta:

```bash
docker compose up -d
```

Hacer copias de seguridad es sencillo. Haz una instantánea del archivo `data.db` dentro del volumen `/data`. Esa única base de datos SQLite contiene todo: configuración, credenciales, definiciones de herramientas y cuentas de usuario.

Si buscas más [despliegues de IA basados en Docker](/cognee-self-host/) para ejecutar junto a Executor, hay muchas opciones.

### Proxy inverso con Caddy

Para HTTPS en un dominio personalizado, pon Caddy delante:

```
executor.yourdomain.com {
    reverse_proxy localhost:4788
}
```

Caddy aprovisiona y renueva los certificados TLS automáticamente. No se necesita más configuración que la línea del proxy inverso.
### Despliegue con Dokploy

Si quieres una interfaz web para gestionar tu despliegue de Executor.sh en lugar de conectarte por SSH a un servidor y editar archivos compose manualmente, [Dokploy](https://dokploy.com/) es una opción sólida. Obtienes un panel para despliegues, HTTPS automático, monitoreo y copias de seguridad de bases de datos sin tocar la línea de comandos tras la instalación inicial.

Si aún no tienes Dokploy instalado, sigue nuestra [guía de instalación de Dokploy](/dokploy-install/) para ponerlo en marcha en tu VPS primero.

**Paso 1: Crea un proyecto nuevo y un servicio compose**

En el panel de Dokploy, crea un proyecto nuevo y luego añade un servicio **Docker Compose**. Pega el siguiente archivo compose:

```yaml
services:
  executor:
    image: ghcr.io/rhyssullivan/executor-selfhost:latest
    container_name: executor-selfhost
    networks:
      - dokploy-network
    restart: unless-stopped
    volumes:
      - executor-data:/data
    environment:
      - PORT=4788
      - EXECUTOR_DATA_DIR=/data
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.executor.rule=Host(`executor.yourdomain.com`)"
      - "traefik.http.routers.executor.entrypoints=websecure"
      - "traefik.http.routers.executor.tls.certresolver=letsencrypt"
      - "traefik.http.services.executor.loadbalancer.server.port=4788"

volumes:
  executor-data:

networks:
  dokploy-network:
    external: true
```

Sustituye `executor.yourdomain.com` por tu dominio real. La red `dokploy-network` se crea automáticamente cuando se instala Dokploy.

**Paso 2: Define las variables de entorno**

Ve a la pestaña **Environment** y añade las variables de arranque que necesites:

```
EXECUTOR_BOOTSTRAP_ADMIN_EMAIL=admin@yourdomain.com
EXECUTOR_BOOTSTRAP_ADMIN_PASSWORD=your-secure-password
EXECUTOR_WEB_BASE_URL=https://executor.yourdomain.com
```

**Paso 3: Apunta tu dominio y despliega**

Añade un registro A en tu DNS apuntando `executor.yourdomain.com` a la IP de tu servidor. Luego ve a la pestaña **Domains** en Dokploy, añade el dominio y activa HTTPS. Pulsa **Deploy** y Dokploy se encarga del resto: descargar la imagen, arrancar el contenedor y configurar Traefik con un certificado TLS.

Para un recorrido completo sobre el despliegue de apps Docker Compose en Dokploy, incluida la configuración de dominio y las etiquetas de Traefik, consulta nuestra guía sobre [desplegar una app Docker Compose en Dokploy](/dokploy-docker-compose-app/).

Mantener el despliegue actualizado es sencillo. Dokploy te permite redesplegar desde el panel cada vez que se publica una imagen nueva. ### Conectar agentes de IA

Una vez que tu instancia esté en marcha, apunta cualquier cliente MCP hacia ella. El endpoint es HTTP streamable en `/mcp`. Para Claude Code:

```bash
claude mcp add executor --transport http https://executor.yourdomain.com/mcp
```

O usa el comando genérico `npx add-mcp`, que detecta el cliente y escribe su configuración por ti:

```bash
npx add-mcp https://executor.yourdomain.com/mcp --transport http --name executor
```

Para Cursor, añade la URL del servidor MCP en Settings → MCP Servers. Cualquier cliente que soporte el protocolo MCP funciona. La tarjeta **Connect** de la interfaz web muestra el comando exacto para tu instancia con la URL ya rellenada. El endpoint autoalojado se comporta igual que la versión cloud, y la mayoría de los clientes solo cargan los servidores MCP al arrancar, así que reinicia el cliente o abre un chat nuevo si las herramientas de Executor no aparecen.

<Notice type="info" title="El primer usuario se convierte en propietario">
La primera cuenta creada en tu instancia autoalojada se convierte en la propietaria de la organización. Invita a miembros del equipo mediante enlaces de invitación de un solo uso desde el panel de administración. La versión autoalojada admite miembros ilimitados, sin coste por asiento.
</Notice>

## Autoalojar Executor.sh en Cloudflare Workers

Si no quieres gestionar un VPS, Executor también se despliega en Cloudflare Workers. La arquitectura: un único Cloudflare Worker + almacenamiento D1 + Cloudflare Access para la autenticación.

```bash
git clone https://github.com/UsefulSoftwareCo/executor.git
cd executor/apps/host-cloudflare
bun run deploy:setup
```

El endpoint MCP vive en `/mcp`, protegido por Cloudflare Access. No hace falta una app de login separada. Cloudflare gestiona la autenticación.

<Notice type="info" title="Coste de infraestructura cero">
El nivel gratuito de Cloudflare cubre despliegues de Executor de bajo volumen. Sin servidor que gestionar, sin Docker que mantener. El compromiso es menos control y una dependencia de la infraestructura de Cloudflare.
</Notice>

Esta opción funciona bien para uso personal o equipos pequeños. Para cargas de producción donde necesitas control total sobre el entorno de ejecución, Docker es el mejor camino.

## Añadir integraciones a tu Executor autoalojado

Desplegar Executor es el paso uno. Conectarlo a servicios reales es de donde viene el valor.

<Tabs>
<Tab name="OpenAPI">

Apunta Executor a cualquier spec OpenAPI e indexará automáticamente cada endpoint como una herramienta tipada:

```bash
executor call executor openapi addIntegration '{
  "spec": "https://api.example.com/openapi.json",
  "namespace": "my-api",
  "baseUrl": "https://api.example.com"
}'
```

Todos los endpoints `GET`, `POST`, `PUT` y `DELETE` se convierten en herramientas llamables. El motor de políticas requiere aprobación automáticamente para las operaciones destructivas. Usa `baseUrl` cuando la spec tenga entradas `servers` relativas, y confirma que está en marcha con `executor tools integrations`.

</Tab>
<Tab name="MCP Server">

Añade cualquier servidor MCP a tu instancia de Executor:

```bash
executor call executor mcp addServer '{
  "name": "my-mcp-server",
  "command": "npx",
  "args": ["@my-org/mcp-server"]
}'
```

Puedes añadir [integraciones de servidores MCP como BrightData](/brightdata-mcp-guide/) para acceso a datos web, o cualquier servidor MCP de la comunidad desde npm.

</Tab>
<Tab name="GraphQL">

Conecta un endpoint GraphQL y cada query y mutation se convierte en una herramienta:

```bash
executor call executor graphql addIntegration '{
  "endpoint": "https://api.example.com/graphql",
  "namespace": "my-graphql-api",
  "headers": {"Authorization": "Bearer $TOKEN"}
}'
```

La introspección del esquema se ejecuta automáticamente, así que no hacen falta definiciones de herramientas manuales.

</Tab>
</Tabs>

El descubrimiento semántico de herramientas significa que los agentes no necesitan conocer los nombres de las herramientas. Describen lo que quieren hacer y Executor encuentra la herramienta adecuada:

```bash
executor tools search "send email"        # find tools by intent
executor tools describe github issues     # show a tool's schema
executor resume --execution-id exec_123   # resume a paused execution
```

Si estás [creando tu propio agente de IA](/create-your-own-ai-agent/) o construyendo con el [framework Mastra](/build-ai-agent-mastra/), Executor te da un único endpoint MCP que agrupa todas tus integraciones. Para enrutar entre varios agentes de codificación con IA como Claude Code y Codex, [Agent Router](https://go.bitdoze.com/agentrouter) ofrece acceso unificado junto a tu gateway Executor. Y para integraciones de datos web, [Bright Data](https://go.bitdoze.com/brightdata) ofrece APIs de datos estructurados que puedes conectar vía MCP.

## Cuándo elegir Executor.sh (y cuándo quedarse con Composio)

Este no es un artículo de «Composio malo, Executor bueno». Ambas plataformas sirven a necesidades diferentes. Aquí va un desglose honesto:

<Tabs>
<Tab name="Elige Executor.sh">

- Necesitas autoalojamiento por cumplimiento, coste o soberanía de datos
- Quieres acceso completo al código fuente y la capacidad de modificar el runtime
- Traes tus propias specs de API (OpenAPI, GraphQL, MCP) en lugar de necesitar más de 1,500 toolkits preconstruidos
- Quieres minimizar el uso de la ventana de contexto de tus agentes
- Ejecutas flujos de trabajo multiagente a escala y el precio por llamada es un problema
- Prefieres el estándar del protocolo MCP frente a adaptadores específicos de cada framework

</Tab>
<Tab name="Elige Composio">

- Necesitas más de 1,500 integraciones SaaS preconstruidas y preautenticadas desde el primer momento
- Necesitas gestión de OAuth para muchas apps de terceros sin configuración
- Requieres cumplimiento SOC 2 Type II / ISO 27001 hoy (no bajo petición)
- Tu equipo usa LangChain, CrewAI u otros frameworks que necesitan adaptadores dedicados
- Prefieres una plataforma totalmente gestionada sin infraestructura que mantener
- Eres un equipo pequeño o un desarrollador en solitario que necesita el punto de entrada más barato

</Tab>
</Tabs>

<Notice type="warning" title="Compromisos honestos">
Executor.sh tiene unos 7 meses (a septiembre de 2026). Tiene una comunidad más pequeña, menos despliegues en producción y menos pruebas de batalla que Composio. La opción Docker autoalojada es estable, pero evalúala para tu carga de trabajo concreta antes de comprometerte en producción.
</Notice>

Para equipos que exploran infraestructura de IA autoalojada, las guías sobre [ejecutar agentes de IA en tu propio servidor](/es/guia-configuracion-hermes-agent/) pueden ayudarte a construir una visión más amplia.

## Preguntas frecuentes

<Accordion label="¿Executor.sh es realmente de código abierto completo?" group="faq" expanded="true">
Sí. Cada opción de despliegue (Cloud, Desktop, CLI, Docker y Cloudflare Workers) tiene licencia MIT. Todo el código fuente está en [GitHub](https://github.com/UsefulSoftwareCo/executor). Puedes inspeccionar, modificar y bifurcar cualquier parte.
</Accordion>

<Accordion label="¿Puedo migrar de Composio a Executor.sh?" group="faq">
No hay una herramienta de migración directa. Los modelos de integración son diferentes: Composio usa toolkits SaaS preconstruidos, mientras Executor usa integraciones basadas en specs (OpenAPI, GraphQL, MCP). Traerías tus propias specs de API y las configurarías en Executor. Si tus flujos de trabajo dependen mucho de los toolkits preconstruidos de Composio, la migración lleva más esfuerzo.
</Accordion>

<Accordion label="¿Executor.sh soporta MCP?" group="faq">
Sí. Executor está construido como un gateway MCP. Cualquier cliente compatible con MCP (Claude Code, Cursor, Codex, extensiones de VS Code) se conecta directamente. Consulta nuestra [guía de MCP para principiantes](/mcp-introduction-beginners/) si el protocolo es nuevo para ti.
</Accordion>

<Accordion label="¿Cómo gestiona Executor.sh las credenciales y los secretos?" group="faq">
Las credenciales se almacenan en la base de datos SQLite (cifradas). El sandbox SES usa inyección del lado del host: las credenciales se inyectan en las llamadas a herramientas en el momento de la ejecución y nunca entran en el heap del sandbox. Es una frontera de seguridad real. Incluso si una llamada a una herramienta se ve comprometida, el sandbox no puede acceder a las credenciales en crudo.
</Accordion>

<Accordion label="¿Executor.sh está listo para producción?" group="faq">
Es joven pero cuenta con el respaldo de Y Combinator S26. Los despliegues Docker autoalojados son estables para cargas de trabajo pequeñas y medianas. La funcionalidad central (gateway MCP, indexación OpenAPI/GraphQL, sandbox SES) funciona bien. Para sistemas críticos de producción, haz una evaluación exhaustiva primero. El impulso del proyecto (casi 4,000 estrellas en unos 7 meses, con commits a diario) sugiere un desarrollo activo y una adopción creciente.
</Accordion>

<Accordion label="¿Puedo autoalojar Composio en su lugar?" group="faq">
Solo en planes Enterprise a través de un proceso comercial. El repositorio de GitHub contiene solo SDKs y herramientas del CLI, no el runtime de la plataforma. El [issue de GitHub #291](https://github.com/ComposioHQ/composio/issues/291) que pide autoalojamiento self-serve lleva abierto desde julio de 2024 sin resolución.
</Accordion>

## ¿Es Executor.sh la alternativa a Composio adecuada para ti?

Si eres un entusiasta del autoalojamiento, un defensor del código abierto o un desarrollador consciente de los costes que ejecuta flujos de trabajo multiagente, Executor.sh merece una mirada seria. Resuelve los problemas centrales que alejan a los desarrolladores de Composio: runtime cerrado, sin autoalojamiento y precios por llamada que escalan mal.

El despliegue Docker autoalojado lleva menos de un minuto. Obtienes un gateway MCP con licencia MIT completa, carga dinámica de herramientas, ejecución en sandbox y aislamiento de credenciales, corriendo enteramente en tu infraestructura.

Composio sigue siendo la opción más fuerte si necesitas más de 1,500 integraciones preconstruidas y OAuth gestionado sin tocar infraestructura. Es una necesidad válida, y Composio la cubre bien.

Pero si quieres control, transparencia y cero costes por llamada a escala, Executor.sh es la alternativa de código abierto que vale la pena probar.
