GitHub Actions funciona bien hasta que miras la factura, chocas con límites de uso o caes en la cuenta de que todo tu código corre en servidores ajenos. Si ya autoalojas tus aplicaciones en un VPS, montar tu propia forja Git y tu pipeline CI/CD es el paso siguiente.

Esta guía despliega **Forgejo y Woodpecker CI** en un solo VPS: una alternativa autoalojada a GitHub donde Forgejo gestiona repositorios, issues y pull requests, mientras Woodpecker ejecuta compilaciones, pruebas y despliegues en tu propia infraestructura.

## ¿Por qué cambiar a una alternativa autoalojada a GitHub?

Una forja propia resuelve problemas concretos. El primero es el coste: el plan gratuito de GitHub Actions se agota rápido en repositorios privados y un VPS de 4 GB mueve la forja, la CI y tus apps por 7 a 15 EUR/mes fijos. El segundo es la propiedad de datos: código, issues, pull requests y logs viven en tu servidor sin cambios unilaterales de condiciones. Además reduces la dependencia de la disponibilidad de GitHub y evitas quedarte atado a workflows propietarios.

Aun así, muchos mantienen espejos en GitHub para proyectos públicos. Puedes tener ambas cosas.

## Forgejo vs Gitea: ¿cuál es la diferencia?

Forgejo nació como fork de Gitea en octubre de 2022 después de que una empresa con ánimo de lucro asumiera el control del proyecto Gitea sin consultar a la comunidad.

A finales de 2026 Forgejo es un hard fork con bases de código divergentes:

| | Forgejo | Gitea |
|---|---|---|
| **Gobierno** | Sin ánimo de lucro (Codeberg e.V.) | Empresa con ánimo de lucro |
| **Licencia** | Software libre exclusivo | Open Core (funciones propietarias) |
| **Desarrollado en** | El propio Forgejo | GitHub |
| **CI/CD probado con** | Forgejo Actions | GitHub Actions |
| **Seguridad** | Aviso anticipado para todos los usuarios | Aviso anticipado solo para clientes de pago |
| **Federación** | Trabajo activo en ActivityPub | Sin planes de federación |
| **Cadencia de versiones** | Estables trimestrales + LTS anual con EOL público | Definida por la empresa |
| **Migración desde Gitea** | Soportada mediante ruta documentada; revisa la [guía de actualización de Forgejo](https://forgejo.org/docs/latest/admin/upgrade/) | N/A |

Gitea ya va por v28.x (saltó de 1.27.x a v28.0.0 en septiembre de 2026). Con trayectorias separadas, no asumas una sustitución directa: lee la guía de migración antes de mover datos.

<Notice type="info" title="Cambios incompatibles en Gitea v28">

Si migras desde Gitea, ten en cuenta que v28 enruta operaciones de red git mediante un proxy interno con controles de salida (afecta a hosts restringidos) y añadió `RUN_RETENTION_DAYS` para Actions.

</Notice>

Cubro el fork y el runner de Forgejo Actions en detalle en [la guía de Forgejo vs Gitea y Forgejo Actions](/es/forgejo-vs-gitea-autoalojado/). Si empiezas de cero, elige Forgejo.

## Paso 1: instalar Forgejo con Docker Compose

Crea el directorio y el `docker-compose.yml`:

```sh
mkdir -p /opt/forgejo && cd /opt/forgejo
```

```yaml
services:
  forgejo:
    image: codeberg.org/forgejo/forgejo:15
    container_name: forgejo
    environment:
      - USER_UID=1000
      - USER_GID=1000
      - FORGEJO__database__DB_TYPE=sqlite3
      - FORGEJO__server__DOMAIN=git.yourdomain.com
      - FORGEJO__server__ROOT_URL=https://git.yourdomain.com
      - FORGEJO__server__SSH_DOMAIN=git.yourdomain.com
      - FORGEJO__server__SSH_PORT=2222
      - FORGEJO__server__SSH_LISTEN_PORT=22
      - FORGEJO__service__DISABLE_REGISTRATION=true
      - FORGEJO__actions__ENABLED=true
      - FORGEJO__webhook__ALLOWED_HOST_LIST=external,loopback  # recommended for same-host Woodpecker
    restart: unless-stopped
    volumes:
      - ./data:/data
      - /etc/timezone:/etc/timezone:ro
      - /etc/localtime:/etc/localtime:ro
    ports:
      - "3000:3000"
      - "2222:22"
    networks:
      default:
        name: forgejo
```

Puntos clave:

- `:15` apunta a Forgejo 15 LTS (soporte hasta 2027-07-15). Forgejo 10 alcanzó EOL en abril de 2025; no expongas una versión sin parches. Usa `:17` si prefieres la última estable.
- El demonio SSH de la imagen (OpenSSH) escucha en el puerto 22 dentro del contenedor y se publica como 2222, así no choca con el SSH del host (puerto 22). Clonarás con `ssh://git@yourdomain.com:2222/user/repo.git`.
- El registro público está desactivado a propósito.
- SQLite basta para uso personal o equipos pequeños; pasa a PostgreSQL a partir de 10+ usuarios.
- `ALLOWED_HOST_LIST=external,loopback` evita un bloqueo: Forgejo rechaza webhooks hacia direcciones loopback por defecto, y si `ci.yourdomain.com` resuelve a una de ellas desde dentro del contenedor de Forgejo, los pipelines nunca arrancan.
- Nombrar la red `forgejo` permite al agente de Woodpecker conectar los contenedores de build para clonar repositorios.

<Notice type="warning" title="Parchea rápido o fija LTS">

Forgejo 17.0.2 (noviembre de 2026) corrigió un fallo crítico de omisión de autenticación en el servidor SSH integrado sobre SQLite, una configuración parecida a la de esta guía (corregido en 15.0.12 y 17.0.2). El Compose de arriba usa el demonio OpenSSH de la imagen, así que solo te afecta si activas el servidor SSH integrado. Suscríbete al RSS de avisos de seguridad de Forgejo desde la [guía de actualización](https://forgejo.org/docs/latest/admin/upgrade/).

</Notice>

### Arrancar Forgejo

```sh
docker compose up -d
docker compose logs forgejo | tail -5
```

Deberías ver los puertos 3000 (HTTP) y 22 (SSH) escuchando. Abre `https://git.yourdomain.com`, completa el asistente inicial y verifica que `curl -I https://git.yourdomain.com` devuelve 200 tras poner el proxy inverso.

### Proxy inverso con Nginx y Certbot

```nginx
server {
    server_name git.yourdomain.com;

    location / {
        proxy_pass http://localhost:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    listen 443 ssl;
    ssl_certificate /etc/letsencrypt/live/git.yourdomain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/git.yourdomain.com/privkey.pem;
    include /etc/letsencrypt/options-ssl-nginx.conf;
    ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem;
}
```

```sh
certbot --nginx -d git.yourdomain.com
```

<Notice type="warning" title="Firewall">

Abre los puertos 80, 443 y 2222 en UFW:

```sh
sudo ufw allow 'Nginx Full'
sudo ufw allow 2222
```

Para endurecer el host Docker revisa [cómo aseguré mi servidor Docker con UFW](/es/informe-seguridad-bsi-docker-ufw/).

</Notice>

## Paso 2: instalar Woodpecker CI

Woodpecker es un servidor CI/CD independiente que se autentica contra Forgejo por OAuth. Cada paso de pipeline corre en su propio contenedor Docker.

### Crear aplicación OAuth en Forgejo

1. Ve a **Administración del sitio -> Aplicaciones** (o Ajustes de usuario -> Aplicaciones)
2. Crea una aplicación OAuth2 llamada Woodpecker CI con URI de redirección exacta `https://ci.yourdomain.com/authorize`
3. Guarda el **Client ID** y **Client Secret**

### Docker Compose de Woodpecker

```sh
mkdir -p /opt/woodpecker && cd /opt/woodpecker
```

```yaml
services:
  woodpecker-server:
    image: woodpeckerci/woodpecker-server:v3
    container_name: woodpecker-server
    restart: unless-stopped
    ports:
      - "8000:8000"
    volumes:
      - woodpecker_data:/var/lib/woodpecker
    environment:
      - WOODPECKER_OPEN=false
      - WOODPECKER_HOST=https://ci.yourdomain.com
      - WOODPECKER_FORGEJO=true
      - WOODPECKER_FORGEJO_URL=https://git.yourdomain.com
      - WOODPECKER_FORGEJO_CLIENT=YOUR_CLIENT_ID
      - WOODPECKER_FORGEJO_SECRET=YOUR_CLIENT_SECRET
      - WOODPECKER_AGENT_SECRET=YOUR_RANDOM_SECRET
      - WOODPECKER_DATABASE_DRIVER=sqlite3
      - WOODPECKER_DATABASE_DATASOURCE=/var/lib/woodpecker/woodpecker.db

  woodpecker-agent:
    image: woodpeckerci/woodpecker-agent:v3
    container_name: woodpecker-agent
    command: agent
    restart: unless-stopped
    depends_on:
      - woodpecker-server
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - woodpecker-agent-config:/etc/woodpecker
    environment:
      - WOODPECKER_SERVER=woodpecker-server:9000
      - WOODPECKER_AGENT_SECRET=YOUR_RANDOM_SECRET
      - WOODPECKER_MAX_WORKFLOWS=2
      - WOODPECKER_BACKEND_DOCKER_NETWORK=forgejo

volumes:
  woodpecker_data:
  woodpecker-agent-config:
```

Genera el secreto compartido con `openssl rand -hex 32` y úsalo en ambos servicios. Las variables `WOODPECKER_FORGEJO_*` usan el driver nativo de Forgejo (disponible desde Woodpecker 2.6.0).

<Notice type="warning" title="Los webhooks hacia direcciones loopback vienen bloqueados">

Forgejo rechaza webhooks a direcciones loopback por defecto. Si `ci.yourdomain.com` resuelve a una de ellas desde dentro del contenedor de Forgejo, sin `FORGEJO__webhook__ALLOWED_HOST_LIST=external,loopback` en el Paso 1 los pipelines nunca arrancan.

</Notice>

`WOODPECKER_BACKEND_DOCKER_NETWORK=forgejo` conecta los contenedores de build a la red de Forgejo para evitar bloqueos en el paso de clonado. `WOODPECKER_MAX_WORKFLOWS=2` protege la RAM en un VPS de 4 GB.

<Notice type="warning" title="Acceso al socket de Docker">

Montar `/var/run/docker.sock` da acceso completo al demonio Docker del host. En un VPS individual es aceptable; en hosts compartidos estudia Podman rootless, Kaniko o [ejecutar contenedores Docker como usuario no root](/es/anadir-usuarios-contenedor-docker/).

</Notice>

Arranca con `docker compose up -d`, comprueba `docker compose logs -f woodpecker-agent`, añade el proxy Nginx para `ci.yourdomain.com` hacia el puerto 8000 e inicia sesión vía OAuth.

### Tu primer pipeline en Woodpecker

Crea `.woodpecker.yml` en la raíz del repositorio:

```yaml
steps:
  - name: build
    image: node:24-alpine
    commands:
      - npm ci
      - npm run build

  - name: test
    image: node:24-alpine
    commands:
      - npm test
    depends_on: [build]

  - name: deploy
    image: alpine:3.22
    commands:
      - apk add --no-cache openssh-client
      - ssh -o StrictHostKeyChecking=no deploy@yourserver "cd /var/www/myapp && git pull && ./build.sh"
    depends_on: [test]
    when:
      - event: push
        branch: main
```

La clave raíz obligatoria es `steps:` (la antigua `pipeline:` desapareció en Woodpecker 3.0.0). En cuanto un paso usa `depends_on`, Woodpecker activa el modo DAG en paralelo.

<Notice type="warning" title="Combina siempre branch con event">

Usar solo `branch: main` también se dispara cuando se actualiza un pull request dirigido a main. Incluye siempre `event: push` en pasos de despliegue.

</Notice>

### Construir y subir imágenes Docker

```yaml
steps:
  - name: build-image
    image: plugins/docker
    settings:
      repo: git.yourdomain.com/youruser/myapp
      registry: git.yourdomain.com
      tags:
        - latest
        - ${CI_COMMIT_SHA:0:8}
      username:
        from_secret: docker_username
      password:
        from_secret: docker_password
    when:
      - event: push
        branch: main
```

Añade secretos con `woodpecker-cli`:

```sh
woodpecker-cli repo secret add \
  --repository youruser/myapp \
  --name docker_username \
  --value 'youruser'

woodpecker-cli repo secret add \
  --repository youruser/myapp \
  --name docker_password \
  --value 'your_token'
```

Para manejar secretos en Compose de forma segura revisa [manejo seguro de secretos en Docker Compose](/es/secretos-docker-compose/).

## Paso 3: despliegues automáticos y registro de contenedores

Para aplicaciones Docker Compose, un script de despliegue básico en el servidor:

```sh
#!/bin/bash
cd /opt/myapp
git pull --force origin main
docker compose down
docker compose up -d --build
docker image prune -f
```

Si buscas despliegues sin tiempo de inactividad sin escribir scripts, revisa [Kamal](https://kamal-deploy.org/) o nuestra comparativa [Coolify vs Dokploy vs Kamal 2](/es/coolify-vs-dokploy-vs-kamal-2/).

Para activar el registro Docker integrado de Forgejo, habilita `[packages] ENABLED=true` en `app.ini` y comprueba tras el primer build con `docker pull git.yourdomain.com/youruser/myapp:latest`.

## ¿Por qué Woodpecker CI frente a Forgejo Actions?

Forgejo Actions ha madurado mucho y facilita copiar archivos `.github/workflows` con pocos cambios. Woodpecker gana cuando prefieres una interfaz dedicada, independencia de forja (puede conectar repositorios de GitHub y GitLab al mismo servidor), matrices de hasta 64 workflows (`matrix:`) y dependencias entre workflows. Si prefieres un despliegue estilo PaaS en su lugar, revisa [cómo instalar Coolify como alternativa a Heroku](/es/instalar-coolify-alternativa-heroku/).

## Copias de seguridad de Forgejo y Woodpecker

La guía de actualización de Forgejo **exige** copia completa antes de cualquier salto de versión mayor (por ejemplo de v15 a v16).

<Tabs>
<Tab name="Stop-and-tar">

```sh
#!/bin/bash
DATE=$(date +%Y-%m-%d)
BACKUP_DIR="/home/backups/forgejo"

cd /opt/forgejo && docker compose stop
tar -czf "$BACKUP_DIR/forgejo-$DATE.tar.gz" -C /opt/forgejo/data .
docker compose up -d

gpg --encrypt --armor -r your@email.com \
  -o "$BACKUP_DIR/forgejo-$DATE.tar.gz.gpg" \
  "$BACKUP_DIR/forgejo-$DATE.tar.gz"
rm "$BACKUP_DIR/forgejo-$DATE.tar.gz"
```

</Tab>
<Tab name="forgejo dump">

```sh
docker exec --user 1000:1000 forgejo forgejo dump \
  --file /data/forgejo-dump-$(date +%Y-%m-%d).zip
```

Verifica los flags exactos de tu versión en la [documentación oficial de backups de Forgejo](https://forgejo.org/docs/latest/admin/setup/backup/).

</Tab>
</Tabs>

Respalda también el volumen `woodpecker_data` y programa una limpieza periódica de imágenes Docker para no llenar el disco:

```sh
0 3 * * * docker system prune -af --filter "until=72h"
```

## Problemas comunes

- **No arranca ningún pipeline:** falta `FORGEJO__webhook__ALLOWED_HOST_LIST=external,loopback` o la URI de redirección OAuth no coincide exactamente.
- **Workflow bloqueado en clonado:** `WOODPECKER_BACKEND_DOCKER_NETWORK` no coincide con el nombre de red de Forgejo, o `WOODPECKER_AGENT_SECRET` difiere entre servidor y agente.
- **Bloqueos de SQLite en paralelo:** si ejecutas muchos workflows simultáneos, migra a PostgreSQL.
- **"Unexpected database version" al actualizar Forgejo:** sigue la sección de resolución de problemas de la [guía de actualización de Forgejo](https://forgejo.org/docs/latest/admin/upgrade/).

## Preguntas frecuentes

<Accordion label="¿Funciona esto en un VPS de 2 GB?" group="faq">
Forgejo solo corre sin problema en 2 GB. Con Woodpecker CI en el mismo host, 4 GB es el suelo cómodo porque el agente crea contenedores por cada paso. Mantén <code>WOODPECKER_MAX_WORKFLOWS=2</code>.
</Accordion>

<Accordion label="¿Necesito Forgejo Actions si uso Woodpecker?" group="faq">
No, elige uno. Forgejo Actions si quieres compatibilidad con <code>.github/workflows</code>; Woodpecker por su UI dedicada y soporte multiforja.
</Accordion>

<Accordion label="¿Por qué fijar Forgejo 15 LTS en lugar de 17?" group="faq">
Las versiones LTS reciben parches durante 15 meses (Forgejo 15 hasta 2027-07-15), frente a unos 3 meses en estables trimestrales. Fija <code>:15</code> si prefieres estabilidad; usa <code>:17</code> solo si aplicas parches de seguridad el mismo día.
</Accordion>

<Accordion label="¿Cómo actualizo Forgejo a una nueva versión mayor?" group="faq">
Lee las notas de lanzamiento, haz copia completa obligatoria, sube la etiqueta en tu Compose y ejecuta <code>docker compose up -d</code> revisando los logs.
</Accordion>

<Accordion label="¿Es un riesgo montar el socket de Docker en el agente?" group="faq">
En un VPS individual es un riesgo asumible. En servidores compartidos usa Podman rootless, Kaniko o <a href="/es/anadir-usuarios-contenedor-docker/">contenedores Docker sin root</a>.
</Accordion>
