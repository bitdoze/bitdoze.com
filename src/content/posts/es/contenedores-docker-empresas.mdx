## Dónde se pueden alojar contenedores Docker para empresas

Tienes dos caminos reales: alquilar un VPS, o correr tu propio hardware. Ambos funcionan. La diferencia es quién carga con el buscapersonas cuando se va la luz, y lo rápido que puedes añadir recursos.

Si quieres saltarte la mayor parte de la capa de sysadmin, un panel PaaS encima de Docker (Coolify, Dokploy, Kamal 2) convierte los despliegues en una tarea de UI web en vez de trabajo por SSH. Los comparo en [Coolify vs Dokploy vs Kamal 2](/coolify-vs-dokploy-vs-kamal-2/).

> En caso de que te interese monitorizar recursos del servidor como CPU, memoria y espacio en disco puedes mirar: [How To Monitor Server and Docker Resources](/sever-monitoring/)

Orden de magnitud de costes: una máquina pequeña de clase VPS europea corre el stack "pequeño" de más abajo por unos 5-10 EUR al mes. Los precios de proveedores se movieron mucho en 2025-2026, así que lee [qué cambió y cuándo gana un mini PC](/vps-price-increases/) antes de firmar nada.

### Servidor VPS con Hetzner, Hostinger, DigitalOcean, etc.

Los Virtual Private Servers son el default por una razón. [Hetzner](https://go.bitdoze.com/hetzner), [Hostinger](https://go.bitdoze.com/hostinger-vps), [DigitalOcean](https://go.bitdoze.com/do) y [Vultr](https://go.bitdoze.com/vultr) venden VMs fiables a precios razonables. Esto es lo que obtienes con un VPS:

- **Escalabilidad**: aumenta recursos fácilmente a medida que tu negocio crece
- **Alta disponibilidad**: benefíciate de infraestructura de grado empresarial y redundancia
- **Opciones gestionadas**: los proveedores manejan el hipervisor, la red y el reemplazo de hardware
- **Alcance global**: elige entre datacenters de todo el mundo para reducir la latencia de tus usuarios
- **Rentable**: paga solo por los recursos que usas, con planes de precios flexibles

_Los precios de VPS saltaron en bloque en 2026 — si estás replanteándote una máquina alquilada, mira [qué cambió y cuándo gana un mini PC](/vps-price-increases/)._

Una línea honesta para que no sobreconstruyas: salta el Kubernetes gestionado para esta carga. Veinte apps de negocio self-hosted no necesitan un orquestador. Un único VPS con Docker Compose es el default sensato; la orquestación añade modos de fallo que solo quieres cuando de verdad necesitas programación multi-nodo. Al elegir proveedor, pesa precios, rendimiento, ubicaciones de datacenters y soporte. Los cuatro de arriba tienen interfaces y docs usables para llevarte a un host Docker funcionando.

### Home server

Para empresas que necesitan un control más estrecho sobre su hardware, o que quieren los datos físicamente en la oficina, un home server funciona bien para contenedores Docker. Dos opciones principales:

#### Mini PC

Los mini PCs se han convertido en el home server por defecto: compactos, silenciosos y lo bastante potentes para correr un stack de contenedores serio. Una máquina de clase N100 o N305 corre todo en la tabla de recursos "pequeña" de abajo sin despeinarse. Ventajas:

- **Bajo consumo**: ideal para operación 24/7 sin costes de energía significativos
- **Operación silenciosa**: muchos modelos son fanless o tienen sistemas de refrigeración de bajo ruido
- **Personalizable**: elige RAM y tamaño de NVMe para tu carga real
- **Rentable**: a menudo más barato que un año de facturación de VPS

Para una máquina compacta que sirva como servidor de oficina o máquina de home lab, algo como el [ASUS DC510 mini PC](https://go.bitdoze.com/asus-dc510) tiene la forma de hardware adecuada. Para un repaso completo de modelos, mira [los mejores mini PCs para home servers](/best-mini-pc-home-server/).

#### NAS

Los dispositivos Network Attached Storage (NAS) son la otra opción común: mucho disco, bajo consumo y una UI web. Muchos NAS modernos corren contenedores Docker, lo que los hace tentadores como máquinas todo-en-uno para una pequeña empresa. Beneficios:

- **Almacenamiento integrado**: gran capacidad con soporte RAID para redundancia de datos
- **Gestión fácil**: interfaces amigables para gestionar tanto el almacenamiento como los contenedores
- **Eficiencia energética**: diseñados para operación 24/7 con bajo consumo
- **Soluciones de backup**: a menudo incluyen software de backup integrado e integración cloud

Una salvedad antes de comprometerte: los runtimes de contenedores en Synology y QNAP van por detrás del Docker Engine a pelo, y la CPU/RAM en las máquinas NAS es limitada. Para cualquier cosa más allá de un servidor de archivos y un par de contenedores ligeros, la división más limpia es un mini PC para el cómputo más el NAS como almacenamiento. Si estás construyendo ese tipo de homelab, mira [los mejores NAS para homelabs con Docker y Proxmox](/best-nas-homelab-docker-proxmox/).

### Open source vs fair-code: comprobación de realidad de licencias

"Open source" ya no es una sola cosa, y un par de los nombres más grandes de esta lista cambiaron términos recientemente. Para uso interno de empresa, casi todo aquí está bien. Los términos muerden cuando revendes el propio software como servicio.

- **Permisivas (MIT / Apache-2.0)**: Baserow, Activepieces, Gitea, Beszel, Uptime Kuma, Dockge, Zulip, Stirling PDF. Haz lo que quieras, conserva el aviso.
- **Sustainable Use License**: n8n y NocoDB. Gratis para correr tu negocio sobre ellas; no puedes ofrecer el software como servicio de pago a otros. Misma familia fair-code, redacción distinta.
- **AGPL-3.0**: Plausible, Zammad, Docmost, Twenty, Formbricks, Listmonk, Vaultwarden, Cal.com, DocuSeal. Bien para uso interno. Si modificas el código y lo ofreces por red, debes devolver el fuente.
- **Propietaria o híbrida**: Kasm Workspaces (propietaria con nivel gratis), Portainer CE (Zlib, con una edición Business de pago), Dokploy (núcleo Apache-2.0 con módulos propietarios source-available).

<Notice type="warning" title="La licencia de NocoDB cambió en enero de 2026">El LICENSE.md de NocoDB se reescribió el 29-01-2026. El núcleo pasó a la Sustainable Use License y ya no es AGPL-3.0. El uso interno de empresa está bien; revenderlo como servicio no.</Notice>

Si la pureza de licencia importa, prefiere Baserow sobre NocoDB y Activepieces sobre n8n. Los compromisos de funciones son más pequeños de lo que sugiere el marketing.

### Nextcloud

[Nextcloud](https://nextcloud.com/) es una plataforma open-source de compartición de archivos y colaboración que funciona como hub central para los datos de tu empresa.

**Funciones:**
- Compartición y sincronización de archivos entre dispositivos
- Edición colaborativa de documentos
- Gestión de calendario y contactos
- Videoconferencia y chat
- Gestión de tareas y planificación de proyectos

**Cómo ayuda a pequeñas empresas:**
Nextcloud es una alternativa self-hosted a Dropbox o Google Drive. Mantienes control total sobre tus datos mientras obtienes funciones similares. Maneja sync de archivos, edición de documentos, calendarios y videollamadas en un solo sitio. La línea de versión actual es Nextcloud v35 (24-09-2026), comercializada como Hub 26. Para Docker, usa la imagen oficial **Nextcloud AIO** en vez de hacer compose a mano más una base de datos más un runtime PHP: AIO cablea las piezas juntas y maneja las actualizaciones. Bien con 2 GB para un equipo pequeño, cómodo con 4 GB.

**Funciones:**
- Hilos por tema para discusiones organizadas
- Búsqueda potente
- Integraciones con varias herramientas y servicios

El hilo por tema de Zulip mantiene las conversaciones organizadas, lo que importa más a medida que tu equipo crece. En vez de mensajes enterrados en un chorro de chat, las discusiones se quedan agrupadas por tema. Hace más fácil ponerse al día tras una ausencia.

### Zammad

[Zammad](https://zammad.com/) es un sistema open-source de help desk y soporte al cliente que puede ayudar a las empresas a gestionar las consultas de clientes eficientemente.

**Funciones:**
- Soporte multi-canal (email, chat, redes sociales)
- Gestión y automatización de tickets
- Base de conocimiento para autoservicio

- Reporting y analítica

**Cómo ayuda a pequeñas empresas:**
Zammad centraliza el soporte al cliente para que tu equipo no esté haciendo malabares con herramientas separadas para email, chat y redes sociales. La automatización recorta los tiempos de respuesta, y la base de conocimiento deja que los clientes encuentren respuestas por sí mismos. Para un equipo pequeño, eso es importante. Habla SAML/OIDC, así que puedes ponerlo detrás de tu propio login.

### Kasm Workspaces

[Kasm Workspaces](https://www.kasmweb.com/) es una plataforma de streaming de contenedores Docker que entrega acceso por navegador a escritorios, aplicaciones y servicios web.

**Funciones:**
- Acceso remoto seguro a aplicaciones y escritorios
- Espacios de trabajo personalizables para distintos roles de usuario
- Integración con sistemas de autenticación existentes
- Analítica y monitorización de uso
- Soporte para aplicaciones aceleradas por GPU

**Cómo ayuda a pequeñas empresas:**
Kasm Workspaces deja a los empleados acceder a aplicaciones desde cualquier dispositivo a través del navegador. Todo corre dentro de contenedores, así que los datos sensibles nunca salen de tu servidor. Es una forma práctica de montar trabajo remoto sin comprar hardware nuevo a todos. La versión actual es 1.19.0. El nivel gratis tiene un límite de sesiones concurrentes (verifica la cifra actual en kasmweb.com/pricing antes de planear sobre él), y el coste de recursos es real: varios GB de sobrecarga base más memoria por sesión.

Ojo si migras desde 1.x: el flujo de configuración de 2.x cambió, así que trátalo como instalación nueva y recrea las comprobaciones en vez de asumir una actualización directa. Más detalle en la [comparación Uptime Kuma vs Gatus](/uptime-kuma-vs-gatus/) si estás eligiendo un primer monitor.

**Funciones:**
- Interfaz tipo hoja de cálculo para gestión de bases de datos

- Acceso API para integración con otras herramientas
- Roles y permisos de usuario
- Capacidades de automatización y flujos

**Cómo ayuda a pequeñas empresas:**
Ambas herramientas te dejan gestionar datos a través de una interfaz de hoja de cálculo familiar sin necesitar un admin de bases de datos. Puedes construir vistas personalizadas para seguimiento de inventario, gestión de proyectos o CRM. Los miembros no técnicos del equipo pueden usarlas de inmediato porque se ven y se sienten como una hoja de cálculo normal. Ahora listo Baserow primero: su núcleo es MIT, mientras NocoDB pasó a la Sustainable Use License en enero de 2026. NocoDB sigue siendo un software excelente y está bien para uso interno; ahora usa tags de versión de calendario (ejemplo: `nocodb/nocodb:2026.09.1`), lo cual es cómodo para fijar. Si actualizas desde 1.x, lee las notas de versión y repueba tus flujos en una copia antes de tocar producción. n8n corre bajo la Sustainable Use License; Activepieces es núcleo MIT con paquetes enterprise comerciales, así que elige Activepieces si tu política de licencias exige permisiva. Windmill es una tercera opción para equipos que prefieren escribir scripts a cablear nodos. Ruta completa de montaje en [cómo self-hostear n8n con Docker, Traefik y Dokploy](/n8n-self-host-workflow-automation/).

- Monitorización de recursos y logging

**Cómo ayuda a pequeñas empresas:**
Si no tienes una persona de IT dedicada, estas herramientas de gestión hacen Docker mucho menos intimidante. Obtienes una interfaz web para desplegar y gestionar contenedores en vez de trabajar solo desde la línea de comandos. Mi default en 2026 es Dokploy: v0.30.x, muy activo, núcleo Apache-2.0, y maneja reverse proxy más TLS nada más sacarlo. Mira la [guía de instalación de Dokploy](/dokploy-install/). Portainer CE (2.45.x) es el generalista veterano; la licencia Zlib es permisiva para uso interno, y la edición Business es el upsell.

## Consideraciones de seguridad para contenedores self-hosted

Cuando corres herramientas de negocio self-hosted en internet público, la lista de comprobación es corta pero innegociable:

- **Reverse proxy con TLS**: un solo sitio para terminar HTTPS y enrutar apps. [Traefik](/traefik-proxy-docker/) o Nginx Proxy Manager son las opciones comunes; [CloudPanel como reverse proxy para Docker](/cloudpanel-setup-dockge/) es un patrón más ligero si ya lo usas.
- **Backups con restauraciones probadas**: no solo un trabajo de backup, una restauración que hayas ejecutado de verdad. Mira la sección de actualizaciones más abajo.
- **Actualizaciones con un plan**: fija versiones, actualiza a propósito, nunca actualices bases de datos a ciegas.
- **Segregación de red**: una red Docker por stack, bases de datos sin puertos publicados. Para una capa extra barata, un firewall DNS como [NextDNS](https://go.bitdoze.com/nextdns) bloquea dominios de malware y tracking en toda la red.
- **Control de acceso y MFA**: para cualquier cosa con cuentas de usuario, pon SSO delante.
- **Monitorización y logging**: entérate de cuándo algo está caído antes que tus clientes.

### La trampa del firewall Docker: Docker pasa por encima de UFW

<Notice type="error" title="Docker publica puertos pasando por encima de UFW">Un contenedor con `-p 8080:8080` es accesible desde internet digan lo que digan tus reglas UFW. Docker escribe sus propias reglas iptables/nftables para puertos publicados, y tienen efecto independientemente de la política de firewall del host.</Notice>

Esta es la forma más común por la que un panel de admin de base de datos self-hosted acaba en Shodan. Configuras UFW, permites 22/80/443, te sientes seguro, y luego descubres que la UI de admin de Postgres que arrancaste "solo un minuto" es pública.

Si tu reverse proxy corre en el mismo host (el montaje normal), enlaza todo lo demás a localhost:

```yaml
services:
  app:
    ports:
      - "127.0.0.1:8080:8080"   # only reachable from the host
```

Las bases de datos no deberían publicar puertos en absoluto. Ponlas en la misma red Docker que la app y deja que los nombres de servicio resuelvan. Solo el proxy publica 80 y 443.

Verifica lo que está realmente expuesto:

```bash
ss -tlnp | grep docker
# anything bound to 0.0.0.0 or a public IP is internet-facing
```

Tras una corrección, recrea los contenedores (`docker compose up -d`) y escanea desde fuera, no desde el propio host. Para la historia completa de un informe de abuso real de Hetzner y el repaso de endurecimiento que siguió, mira [cómo Docker pasa por encima de UFW y cómo aseguré mi servidor Docker](/bsi-security-report-docker-ufw/).

<Accordion label="Ya he publicado puertos, ¿y ahora qué?" group="firewall-fixes">
1. Lista lo que Docker expone realmente: `ss -tlnp` y `docker ps` desde el host.
2. Para cada servicio que no debería ser público, cambia el mapeo a `127.0.0.1:PUERTO:PUERTO` en el archivo compose.
3. `docker compose up -d` para que los contenedores se recreen con el nuevo enlace.
4. Para bases de datos, elimina el bloque `ports:` por completo y mantenlas en la red interna.
5. Vuelve a escanear desde fuera de tu servidor. Si filtras a nivel de host, recuerda que los puertos publicados necesitan reglas en la cadena DOCKER-USER para verse afectados por la política de firewall.
</Accordion>

### Añade MFA y SSO con Authentik o Authelia

La mitad de las apps de esta lista vienen con un prompt de usuario y contraseña y nada más. En internet público, eso es un riesgo.

Pon una capa SSO delante: tanto Authentik como Authelia hacen forward-auth con Traefik o Nginx Proxy Manager, así que la app nunca ve una petición no autenticada. Obtienes MFA en cada servicio detrás del proxy, incluso en los que nunca lo implementaron.

Las apps con soporte nativo de SAML u OIDC deberían usarlo directamente en vez de forward-auth: Nextcloud, Zammad y Gitea soportan federación. Acabas con un solo sitio donde añadir o quitar gente (importante cuando alguien se va), una política MFA, y muchas menos preguntas de "¿es falsificable el formulario de login de esta app?".

### Fija versiones de imágenes y actualiza con seguridad

Nunca corras `:latest` en uso de empresa. Cuando upstream publica un cambio rompedor, te enteras en el peor momento. Fija tags (o digests) y actualiza en tu calendario.

```yaml
# starter stack pattern: pin versions, limit memory, rotate logs, add healthchecks
services:
  app:
    image: example/app:3.2.1        # pin; avoid :latest
    restart: unless-stopped
    mem_limit: 1g
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:3000/healthz"]
      interval: 30s
      timeout: 5s
      retries: 3
```

El bloque de logging no es opcional en un VPS pequeño. El driver json-file por defecto nunca rota, y una app parlanchina es el clásico fallo de "disco lleno a las 3 de la mañana". Pon `max-size` y `max-file` en cada servicio.

## Cómo actualizar contenedores Docker con seguridad

Usa la sintaxis de Compose v2: `docker compose` con espacio, no el binario legado `docker-compose`.

El bucle de actualización que no te despierta por la noche:

```bash
# 0. backup first: DB dump + volume snapshot (see the next section)
docker compose pull
docker compose up -d
docker compose ps                 # everything "running"/"healthy"?
docker compose logs -f --tail=100 # scan for stack traces
docker image prune -f
```

Nunca actualices bases de datos a ciegas. Un salto de versión mayor de Postgres o MariaDB es una migración, no un cambio de tag: toma un volcado, lee las notas de actualización de upstream, y prepárate para restaurar. Los contenedores de aplicación son baratos de revertir; las bases de datos no.

Tras cada actualización, recorre esta lista de comprobación:

<ListCheck><ul>
<li>Todos los contenedores reportan <code>running</code> o <code>healthy</code> en <code>docker compose ps</code></li>
<li>El login funciona con una cuenta real (no solo un 200 en la página principal)</li>
<li>Un flujo central funciona: se crea una factura, se responde un ticket, corre un trabajo de backup</li>
<li>Sin nuevos stack traces en <code>docker compose logs</code></li>
<li>La monitorización está en verde de nuevo (Beszel y Uptime Kuma)</li>
<li>Imágenes viejas purgadas para que el disco se quede aburrido</li>
</ul></ListCheck>

![Flujo seguro de actualización de Docker: backup, pull, up, verificar, prune, con una rama de rollback al tag fijado anterior y una restauración de base de datos](@assets/images/24/11/docker-safe-update-workflow.svg)

### Haz Backup Primero — y Prueba la Restauración

Un backup es una hipótesis. Una restauración es un hecho. Apunta al 3-2-1: tres copias, dos medios, una offsite. Para un stack de pequeña empresa eso suele significar:

- Volcados de base de datos nocturnos (`pg_dump` para Postgres, `mysqldump`/`mariadb-dump` para MariaDB). Las copias a nivel de archivo de una base de datos corriendo no bastan; el directorio de datos no es consistente a nivel de crash mientras la BD escribe.
- Snapshots de volúmenes para subidas y datos de usuario.
- Copias cifradas e incrementales a almacenamiento compatible con S3: Cloudflare R2 o Backblaze B2, orden de magnitud unos pocos dólares al mes para los datos de una pequeña empresa.

Duplicati (v2.4.0.1 estable, tras años en beta) te da una UI web para esto; restic o Borg te dan scripts. Si despliegas con Dokploy, el panel puede empujar [backups de Dokploy a Cloudflare R2](/dokploy-backups-cloudflare-r2/) en un calendario.

<Notice type="info" title="Prueba restauraciones, no backups">Un trabajo de backup en verde no significa nada. Una vez al trimestre, restaura un volcado en un contenedor de pruebas y abre la app. El día que lo necesitas es el día equivocado para descubrir que tus volcados estaban vacíos.</Notice>

<Accordion label="Puerto ya en uso / el contenedor no arranca" group="update-failures">
Otro proyecto compose ya publica el puerto, o un contenedor obsoleto aún lo retiene. Ejecuta `ss -tlnp` y `docker ps` para ver quién lo posee. Solución: para el otro proyecto, cambia el mapeo de puerto del host, o usa un `COMPOSE_PROJECT_NAME` único por stack para que los proyectos dejen de chocar por los nombres por defecto.
</Accordion>

<Accordion label="La versión mayor de la base de datos cambió: se requiere volcado/restauración" group="update-failures">
Subiste `postgres:15` a `postgres:17` y el contenedor hace crash-loop sobre el directorio de datos. Las actualizaciones menores suelen ir bien; las mayores no. Solución: vuelve primero al tag viejo, toma un volcado con la versión vieja, luego arranca la mayor nueva con un directorio de datos vacío y restaura el volcado dentro.
</Accordion>

<Accordion label="Contenedor unhealthy tras actualizar / volúmenes obsoletos" group="update-failures">
La nueva versión cambió un formato de config o la disposición del volumen. Revisa el changelog de upstream por notas de migración. Solución: restaura el tag de imagen fijado anterior y tu volcado previo a la actualización; si la app escribe un archivo de versión en el volumen, la imagen vieja suele negarse también a arrancar sobre un volumen degradado, que es por lo que el volcado importa más que el snapshot del volumen para bases de datos.
</Accordion>

<Accordion label="Sin memoria en un VPS pequeño" group="update-failures">
El OOM killer siega el contenedor más grande, normalmente una base de datos o una app Java/Node, y el bucle de reinicio se come el resto. Revisa `dmesg | grep -i oom` y tus valores `mem_limit`. Solución: pon `mem_limit` y swap en el host, mueve apps pesadas (ERPNext, Kasm, Nextcloud a escala) a una máquina más grande, y nunca planees RAM en reposo por encima de aproximadamente el 70% de lo que tiene la máquina.
</Accordion>

## Primeros pasos con contenedores Docker

Herramientas esenciales para gestionar tu infraestructura de contenedores:

1. **Docker Engine + Compose v2** para orquestación de contenedores
2. **Reverse proxy** (Traefik o Nginx Proxy Manager) con TLS
3. **Solución de backup** (Duplicati, restic o Borg) apuntando a almacenamiento compatible con S3
4. **Monitorización** (Beszel + Uptime Kuma, o Prometheus/Grafana si ya los conoces)
5. **Gestión de contenedores** (Dokploy o Portainer)

Hay dos caminos sensatos. Elige uno y sé consistente.

<Tabs>
<Tab name="Camino 1: Docker Compose a mano">
1. Aprovisiona el VPS y apunta el DNS hacia él. 4 GB de RAM cubren el stack pequeño.
2. Instala Docker Engine y el plugin compose. Confirma con `docker compose version`.
3. Crea `/opt/stacks/tu-app/docker-compose.yml` por app: tags de imagen fijados, `mem_limit`, rotación de logs, healthchecks.
4. Pon Traefik (o Nginx Proxy Manager) delante, termina TLS ahí, y enlaza los puertos de las apps solo a `127.0.0.1`.
5. Configura backups y monitorización antes de añadir la segunda app, no después.

Este es el camino de máximo control, y al que yo vuelvo por defecto para un único VPS.
</Tab>
<Tab name="Camino 2: Dokploy / panel de gestión">
1. Aprovisiona el VPS e instala Dokploy (o Portainer, o un panel más ligero).
2. Despliega desde el panel: pega un archivo compose o usa una plantilla.
3. Deja que el panel maneje el reverse proxy y la emisión de TLS.

## Conclusión: empieza pequeño con apps de empresa self-hosted

Los contenedores Docker self-hosted dan a las pequeñas empresas una forma práctica de correr el software que usan cada día sin alquilar una herramienta SaaS para cada problema. El stack de este artículo cubre la mayor parte de lo que usa una oficina: colaboración y docs (Nextcloud, Zulip, Docmost), soporte al cliente y calidad de servicio (Zammad, Chatwoot, Uptime Kuma), automatización de procesos y datos (ERPNext o Twenty, Baserow, n8n), y marketing y analítica (Mautic, Listmonk, Plausible). Self-hostear también mantiene los datos en hardware que controlas, lo que ayuda con el cumplimiento normativo siempre que hagas el trabajo (TLS, MFA, actualizaciones), y reemplaza suscripciones por asiento con un servidor y algo de tiempo de operador.

Una cosa más, porque nadie lo dice en los docs de los proveedores: self-hostear es un contrato de mantenimiento, no una compra. Las actualizaciones, la monitorización y las restauraciones probadas son el coste real. El lado del dinero es pequeño; un VPS de clase Hetzner más backups compatibles con S3 son unos 10 EUR al mes todo incluido para el stack pequeño. El lado del tiempo es por lo que estás firmando.

Al decidir qué contenedores desplegar, empieza con tres que resuelvan un problema que tienes este mes, no veinte que podrías necesitar el año que viene. Elige un VPS o mini PC dimensionado con margen, pon un reverse proxy y backups delante, y luego expande a medida que el negocio crece. Después de eso, el bucle de actualización y la prueba de restauración trimestral de las secciones de arriba son lo que mantiene el stack aburrido.
