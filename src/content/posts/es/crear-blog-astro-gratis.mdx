## ¿Qué demonios es Astro?

[Astro](https://astro.build/) es un generador moderno de sitios estáticos. Construyes páginas con tu framework de UI favorito (React, Vue, Svelte) o con Markdown a pelo, y Astro envía cero JavaScript por defecto.

Mientras otros frameworks mandan megabytes de JS al navegador, Astro entrega principalmente HTML. Las páginas cargan rápido por sí solas, sin un plugin de caché haciendo el trabajo pesado.

Cronología de versiones, para que sepas dónde estás (verificado oct 2026): Astro 5 salió en dic 2024, Astro 6 aterrizó en mar 2026, y **Astro 7** llegó el 22 de junio de 2026 con un compilador basado en Rust. La versión actual es 7.3.8 (8 de octubre de 2026). El tema de esta guía corre Astro 7.

### Por qué Astro es perfecto para tu blog

- HTML estático y cero JS por defecto: tus páginas son archivos simples en una CDN, que es lo que quieren los buscadores y los móviles lentos
- Arquitectura de islas: solo se hidratan las partes interactivas
- Usa cualquier framework de UI que te guste, o ninguno
- Soporte de Markdown para escribir posts
- Valores por defecto sin configuración, para que pases el tiempo escribiendo en vez de cableando

Piensa en Astro como el mullet de los frameworks web: negocios delante (HTML estático para velocidad) y fiesta detrás (JavaScript solo donde lo necesitas). Hoy lo usamos para construirte un blog que no necesita un niñero de devops. ¿Ya tienes un sitio WordPress? Mira [cómo migré mi sitio WordPress a Astro](/es/migracion-wordpress-a-astro/) — fue mucho menos doloroso de lo que esperaba.

## Nivel 2: Node tu camino al éxito (5 minutos)

Antes de ponernos a programar, instala Node.js y npm:

1. Visita [nodejs.org](https://nodejs.org/)
2. Descarga la versión **LTS** (24.x a octubre de 2026; cualquier cosa v22.12.0+ funciona)
3. Instálala como cualquier otra app
4. Abre Terminal/Símbolo del sistema y escribe:

```bash
node --version   # expect v22.12.0 or newer (Astro 7 requirement)
npm --version    # expect 10.8.2 or newer
```

Si ves números en el rango correcto, vas bien. Si ves números en el rango *incorrecto* (`v18.x`, `v20.x`), ahora posees un modo de fallo conocido: `npm install` lanzará errores de engine y el servidor de dev se negará a arrancar. Arréglalo antes de seguir.

Para los curiosos: Node 26 se convierte en LTS el 28-10-2026. No necesitas perseguir la versión más nueva, solo necesitas superar el suelo de v22.12.0.

<Notice type="info" title="Para más sobre Node.js">
Varias versiones en una máquina, sin dramas de sudo: [instala Node.js con nvm en macOS/Ubuntu](/install-nodejs-using-nvm-macos-ubuntu/).
</Notice>

## Nivel 4: haz fork de un tema de blog Astro gratis (2 minutos)

Hora de coger la plantilla del blog. Esta es toda la razón por la que la guía funciona: un tema de blog Astro gratis con búsqueda, RSS, modo oscuro y unos 20 posts de demo ya cableados.

1. Visita [Bitdoze Astro Theme](https://github.com/bitdoze/bitdoze-astro-theme)
2. Pulsa **Fork** (esquina superior derecha)
3. Nómbralo como quieras (`my-awesome-blog` funciona)
4. Haz clic en **Create fork**

Ahora posees una copia.

<Notice type="info" title="¿Dónde está el botón 'Use this template'?">
El README del tema menciona el atajo "Use this template" de GitHub, pero el repo no está marcado actualmente como plantilla de GitHub, así que ese botón puede no aparecer. No lo busques. **Fork** es el camino fiable (y mantiene funcionando el flujo de merge con upstream de "Mantén tu blog fresco"). Si odias los forks, usa el Método B de abajo.
</Notice>

<Tab name="Método A: Fork (recomendado)">

</Tab>

### Actualiza `src/config/site.ts` (la identidad de tu blog)

Este es ahora el único archivo de identidad. Edita los strings obvios, deja la estructura quieta:

```typescript
export const siteConfig = {
  // Identity
  title: "Your Amazing Blog Title",
  brandName: "Your Blog Name",
  logoText: "Your Blog Name",
  author: "Your Name",
  description: "Your captivating blog description",
  heroDescription: "One or two sentences under your hero headline.",
  footerDescription: "What your blog is about, in one line.",
  postsPerPage: 11,
  // Below this you'll find hero { title, titleAccent, primaryCta, ... }
  // and homepage { showFeaturedPosts, showTaxonomyCards, ... }
  // leave the rest alone for now
};
```

Nota para quien siga tutoriales viejos: **ya no hay clave `name`**. Si un post te dice que pongas `siteConfig.name`, está describiendo una versión muerta del tema. `title` y `brandName` son tus nuevas amigas.

### Actualiza `src/config/config.json` (solo cosas de contacto)

`config.json` ya no guarda el título ni la URL de tu sitio. Solo guarda el endpoint del formulario de contacto y los datos de contacto:

```json
{
  "params": {
    "contact_form_action": "#"
  },
  "contactinfo": {
    "address": "",
    "email": "you@example.com",
    "phone": ""
  }
}
```

Deja `contact_form_action` como `"#"` hasta que tengas un endpoint de formulario, luego [añade un formulario de contacto a Astro gratis, sin backend](/es/anadir-formulario-contacto-astro/) y apunta el action a tu endpoint.

### Menús y redes sociales (sin cambios)

La navegación vive en `src/config/menu.json` y los iconos sociales viven en `src/config/social.json`, igual que en la guía vieja. Las rutas y las formas están en "Personaliza aún más" más abajo si las necesitas.

<Notice type="info" title="El modelo mental de una línea">
`site.ts` = identidad · `config.json` = contacto · `menu.json` = nav · `social.json` = redes. Ten esto claro y el tema nunca te peleará.
</Notice>

**Verifica:** con `npm run dev` aún corriendo, cambia `title` y `brandName` en `site.ts`, guarda, y haz hard-refresh de `http://localhost:4321`. El texto del hero/footer debería cambiar. Si el servidor de dev lanza un error de TypeScript, probablemente quitaste una coma o una comilla — la línea del error apunta justo ahí.

## Nivel 8: escribe tu primer post (5 minutos)

1. Ve a `src/content/posts/`
2. Crea `my-first-post.md`
3. Pega esto dentro:

```markdown
---
title: "My First Blog Post"
meta_title: "My First Amazing Blog Post"
description: "This is the beginning of my blogging journey!"
date: 2023-07-15
image: "../../assets/images/web-development.svg"
authors: ["admin"]
categories: ["Personal"]
tags: ["beginnings", "blogging"]
featured: true
---

## Hello World!

Welcome to my shiny new blog! I'm excited to overshare my thoughts with the internet.

### Why I Started This Blog

- To rant
- To teach
- To learn
- To procrastinate productively

Stay tuned for more!

![Celebration](https://media.giphy.com/media/3o6fJ1BM7R2EBRDnxK/giphy.gif)
```

Dos notas de frontmatter. Primero, `featured: true` (opcional) saca el post en la rejilla "Featured Posts" de la página de inicio, así que úsalo para tu mejor material. Segundo, sobre las rutas de imágenes: el esquema de contenido se volvió más estricto en la actualización de 2026. En vez de fiarte de cualquier ruta que veas en un tutorial (incluida la de arriba), copia la línea `image:` de uno de los posts de demo que aún no hayas borrado, y apúntala a una imagen que hayas añadido de verdad. Con una ruta mala obtienes una imagen rota o un error de build, no una pista amigable.

4. Guarda y refresca `http://localhost:4321`

**Logro desbloqueado:** primer post publicado.

**Verifica:** el post aparece en la página de inicio *y* se abre en su propia página. ¿Quieres medios en tus posts más adelante? Aquí está [cómo añadir vídeos de YouTube a tu blog Astro](/es/anadir-videos-youtube-blog-astro/).

**Roto se ve así:** un error mencionando una etiqueta sin cerrar o HTML inválido. Astro 7 se volvió más estricto, el HTML pegado ahora hace fallar el build en vez de arreglarse silenciosamente. Mira la sección de Resolución de problemas al final.

## Nivel 9: guarda y haz push (2 minutos)

1. Haz clic en el icono de Source Control (el coso con ramas)
2. Prepara todos los cambios (botón +)
3. Escribe un mensaje de commit
4. Haz clic en la marca de verificación para commitear
5. Haz push vía el menú "..." > **Push**

<Notice type="warning" title="Construye en local antes de hacer push">
Las reglas HTML más estrictas de Astro 7 significan que las etiquetas sin cerrar y los atributos sin terminar ahora **hacen fallar el build** en vez de autocorregirse. El error imprime archivo + línea, mucho más amigable en tu máquina que en un log de build de Cloudflare. Ejecuta `npm run build` (o el doble seguro `npm run verify`) antes de cada push. Tarda segundos en un blog recién creado.
</Notice>

**Verifica:** `npm run build` termina limpio e imprime la carpeta `dist/`. Si no, el último error en la terminal te dice qué archivo abrir.

El nav del dashboard cambió en 2026, así que sigue esto exactamente:

1. Dashboard de Cloudflare → **Workers & Pages**
2. **Create application** → pestaña **Pages** → **Connect to Git**
3. Autoriza GitHub, elige tu fork
4. Pon el nombre del proyecto (`my-awesome-blog` funciona) y la rama de producción: **`main`**
5. Framework preset: **Astro** (o configura manualmente): Build command **`npm run build`**, Output directory **`dist`**
6. Haz clic en **Save and Deploy**

Hora del café mientras Cloudflare construye.

Dos trampas que conviene conocer antes de clicar:

- Un proyecto integrado con Git **no puede** cambiarse a Direct Upload después. Elige Git (lo hicimos) y estás bien.
- Cada rama que no sea `main` se convierte en su propio **despliegue de preview** con una URL única. Es staging gratis, úsalo sin vergüenza.

## Personaliza aún más

Tu proyecto es flexible. Esto es lo que puedes retocar dentro de la carpeta `src/`:

### Estilos y colores

- Edita `src/styles/global.css` para cambiar los colores del tema, las fuentes o añadir CSS personalizado.

```css
:root {
  --color-primary-500: #3b82f6; /* Change this to your fav color */
}
```

- Personaliza los colores del modo oscuro bajo `.dark { ... }` en el mismo archivo.

### Enlaces sociales

- `src/config/social.json` guarda las URLs de tus perfiles sociales (mira el Nivel 7 para el mapa de archivos).

### Menú de navegación

- `src/config/menu.json` personaliza los enlaces de navegación de tu sitio.

### Imágenes, logos y favicons

- Pon las imágenes en `src/assets/images/` o `public/images/` (la primera se optimiza en el build, la segunda se copia tal cual).
- Reemplaza favicons/logos en `src/assets/favicons/` o `public/`.
- Actualiza las referencias si hace falta en configs o archivos de layout.

### Contenido: posts, páginas, autores

- Los posts del blog viven en `src/content/posts/`
- Las páginas estáticas viven en `src/content/pages/` (p. ej., Privacidad, Términos)
- La página de "about" es `src/content/about/index.md`
- Los perfiles de autor viven en `src/content/authors/`, genial para blogs multi-autor

### Información del sitio y metadatos

- `src/config/site.ts` es el archivo de identidad: título, marca, texto del hero, toggles de la página de inicio (Nivel 7).
- `src/config/config.json` es solo de contacto: endpoint del formulario más datos de contacto (Nivel 7).

### Layouts y componentes

- Personaliza cómo se ve tu blog editando los componentes en `src/layouts/` y sus subcarpetas.
- Cambia headers, footers, layouts de post, widgets, etc.

### Páginas y enrutado

- Añade o edita páginas en `src/pages/` (p. ej., `/about`, `/contact`, `/blog`).
- Crea nuevos archivos `.astro` para rutas personalizadas.

## Mantén tu blog fresco

1. Añade el repo original como upstream:

```bash
git remote add upstream https://github.com/bitdoze/bitdoze-astro-theme.git
```

2. Trae las actualizaciones:

```bash
git fetch upstream
```

3. Mergea:

```bash
git merge upstream/main
```

4. ¡Arregla conflictos, haz push, y listo!

**Lee el `CHANGELOG.md` del tema antes de mergear una nueva versión de upstream.** Es la diferencia entre "ah, esa clave se movió" y una tarde confusa de arqueología. La rama por defecto sigue siendo `main`.

**¿Conflictos de merge en `site.ts` o `config.json`?** Normalmente significa que upstream renombró o dividió una clave de config. El changelog te dice la nueva forma, luego reaplica tus valores encima.

## "¿Pero por qué Astro?" (para los escépticos)

"¿No podría simplemente usar WordPress/Wix/Medium?" Claro, también podrías usar un cuchillo de untar para talar un árbol. Aquí está el caso honesto, con cifras incluidas:

- El compilador Rust de Astro 7 construyó las 743 páginas de este mismo blog en 47s, bajando de 103s en Astro 6. Ese es el [benchmark de Astro 7: tiempos de build reducidos a la mitad en un sitio de 743 páginas](/es/astro-7-compilaciones-mas-rapidas/). Para un blog de diez posts, los builds son instantáneos de todas formas — el punto es que el tooling crece contigo.
- La velocidad que sienten tus lectores viene del HTML estático y el cero JS por defecto. Tus páginas son archivos servidos desde una CDN. Nada que parchear, ningún PHP que seguir actualizando, ningún plugin de caché haciendo heroicidades.
- Coste y operaciones se quedan aburridos: $0 al mes y las únicas piezas móviles son git y un build. Compara eso con planes de builders gestionados o un host de WordPress con staging, backups y una suscripción a plugin de seguridad.
- Un sitio estático es una superficie de ataque diminuta, pero sigues siendo dueño de la seguridad de tu cuenta de GitHub (activa 2FA) y de las actualizaciones de dependencias vía merges de upstream. Nada es "configura y olvida".
- WordPress ES la elección correcta para ecosistemas de plugins pesados, varios editores no técnicos, o una tienda con necesidades reales de e-commerce. Si ese eres tú, lee [un desglose honesto de costes y operaciones de Astro vs WordPress](/es/astro-vs-wordpress/) antes de comprometerte a nada.

Construirlo tú mismo también significa que puedes decir "ah, ¿mi blog? Lo construí con Astro" en las fiestas, si te va eso.

## Resolución de problemas

### ¿El sitio no construye?

- Revisa los errores de la terminal
- Valida la sintaxis Markdown
- Ejecuta `npm run build` en local para pistas

### El build falla con "unclosed tag" o HTML inválido

Astro 7 dejó de autocorregir markup roto. Las etiquetas sin cerrar y los atributos sin terminar ahora **hacen fallar el build**, y el error imprime el archivo y el número de línea.

- **Solución:** abre ese archivo, cierra la etiqueta (o termina el atributo), ejecuta `npm run build` en local, haz push de nuevo. Pegar HTML de la web es el culpable habitual.

### Funciona en local, falla en Cloudflare

Si el build se pone verde en tu máquina y rojo en el log de Cloudflare, comprueba la versión de Node en el host de build. El tema trae `.node-version` fijado a `22.12.0` y la imagen de build de Cloudflare lo lee automáticamente.

- **Solución:** si moviste el tema a tu propio repo, conserva el archivo `.node-version`. Si no puedes, pon `NODE_VERSION=22.16.0` (o cualquier 22.12+) en las variables de entorno de build del proyecto Pages.

### npm install falla o lanza errores de engine

¿Ves `EBADENGINE` o "unsupported engine"? Tu Node está por debajo del suelo de v22.12.0.

- **Solución:** comprueba `node --version`, actualiza Node ([guía de nvm aquí](/install-nodejs-using-nvm-macos-ubuntu/)), luego:

```bash
npm cache clean --force
```

- Borra `node_modules` y `package-lock.json`, reinstala.

### ¿Faltan imágenes?

- Comprueba las rutas
- Usa rutas relativas o URLs completas
- Pon las imágenes en `public/images/`

### El botón "Use this template" no aparece en GitHub

El repo del tema no está marcado como plantilla de GitHub, así que el botón a menudo no se renderiza. Usa **Fork** (Nivel 4, Método A) o la ruta de clonar-y-push (Método B).

### ¿Todo explotó?

Respira hondo. Lee el último error del log de build, comprueba la versión de Node, y reconstruye en local. Esos tres atrapan casi todo. Si sigue roto, los issues de GitHub del tema son el lugar correcto para preguntar.
