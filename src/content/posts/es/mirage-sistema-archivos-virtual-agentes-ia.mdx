Si has construido algo con agentes de IA que se comunique con más de un servicio, ya conoces el problema. Tu agente necesita leer un archivo de S3, revisar un hilo de Slack, extraer un Google Doc y consultar un repo de GitHub. Cada uno requiere su propio SDK, su propio flujo de autenticación, su propio conjunto de llamadas a métodos. Tu prompt engineering se convierte en un malabarismo de instrucciones de API.

[Mirage](https://github.com/strukto-ai/mirage) adopta un enfoque diferente. Monta todos esos servicios como ramas de un único árbol de sistema de archivos virtual — S3, Google Drive, Slack, GitHub, Redis, Gmail, lo que necesites. Tu agente los recorre con `ls`, `cat`, `grep` y pipes.

La razón por la que esto funciona bien es simple: todos los LLM importantes ya conocen bash. El sistema de archivos de Unix es probablemente la interfaz para la que los LLM tienen más datos de entrenamiento. Mirage se apoya en ese conocimiento existente en lugar de pedir a los modelos que aprendan otra superficie de API más.

Esta guía te lleva por la configuración de Mirage, el montaje de tus primeros backends y su integración en un framework de agentes. Tendrás una configuración funcional en unos 10 minutos.

## Qué hace Mirage realmente

Mirage te da un objeto `Workspace`. Montas servicios en rutas de ese workspace y luego ejecutas comandos de shell contra el árbol combinado.

```python
from mirage import Workspace
from mirage.resource.s3 import S3Config, S3Resource
from mirage.resource.slack import SlackConfig, SlackResource
from mirage.resource.ram import RAMResource

ws = Workspace({
    "/data":  RAMResource(),
    "/s3":    S3Resource(S3Config(bucket="my-bucket")),
    "/slack": SlackResource(SlackConfig()),
})

# These commands hit different backends, but the agent sees one tree
await ws.execute("ls /s3/logs/")
await ws.execute("grep error /slack/engineering/*.json | wc -l")
await ws.execute("cp /s3/report.csv /data/local.csv")
```

El shell no es un `/bin/bash` real — es un parser tree-sitter con un ejecutor personalizado que dirige los comandos a handlers por montaje. Los pipes, globs, `&&`, `||` y la mayoría de los verbos Unix comunes funcionan. El agente nunca toca tu sistema de archivos del anfitrión ni genera subprocesos.

### Backends soportados

Mirage cubre una buena variedad de servicios de serie:

| Categoría | Backends |
|---|---|
| **Almacenamiento** | S3, R2, OCI, Supabase, GCS, RAM, Disk |
| **Google** | Gmail, Google Drive, Google Docs, Sheets, Slides |
| **Colaboración** | GitHub, Linear, Notion, Trello, Slack, Discord, Telegram, Email |
| **Bases de datos** | Redis, MongoDB, Postgres |
| **Remoto** | SSH |

Cada uno se monta en la ruta que elijas. El agente no necesita saber con qué backend está hablando — solo lee y escribe archivos.

### Mirage vs servidores MCP por servicio

<Accordion label="¿Cómo se compara esto con MCP?" group="comparison" expanded="true">

| Aspecto | Mirage | Servidores MCP por servicio |
|---|---|---|
| **Configuración** | Un workspace, configuración de montaje por servicio | Un servidor por servicio |
| **Vocabulario del agente** | Bash estándar (`ls`, `cat`, `grep`, pipes) | Esquemas de herramientas personalizados por servidor |
| **Pipelines entre servicios** | Nativos (pipes entre montajes) | Orquestación manual en código |
| **Caché** | Caché integrada de dos capas (índice + archivo) | Varía según el servidor |
| **Portabilidad** | Snapshots y clonación de workspaces | Estado disperso entre servidores |
| **Soporte de frameworks** | OpenAI Agents SDK, Vercel AI SDK, LangChain, Pydantic AI | Depende del cliente MCP |

Los servidores MCP siguen siendo útiles para servicios que necesitan llamadas a herramientas estructuradas (como "crear un evento de calendario"). Mirage funciona mejor cuando el patrón de interacción es leer/escribir/buscar, que cubre una gran parte de lo que los agentes hacen realmente.

</Accordion>

## Paso 2: Crear un workspace y montar servicios

El workspace es el objeto central. Lo defines con un diccionario que mapea rutas de montaje a instancias de recursos.

### Python

```python
from mirage import Workspace
from mirage.resource.ram import RAMResource
from mirage.resource.s3 import S3Config, S3Resource
from mirage.resource.slack import SlackConfig, SlackResource
from mirage.resource.gdocs import GDocsConfig, GDocsResource
from mirage.resource.github import GitHubConfig, GitHubResource

ws = Workspace({
    "/data":   RAMResource(),
    "/s3":     S3Resource(S3Config(bucket="my-logs-bucket")),
    "/slack":  SlackResource(SlackConfig()),
    "/docs":   GDocsResource(GDocsConfig()),
    "/github": GitHubResource(GitHubConfig()),
})
```

### TypeScript

```ts
import {
  Workspace,
  RAMResource,
  S3Resource,
  SlackResource,
  GDocsResource,
  GitHubResource,
} from '@struktoai/mirage-node'

const ws = new Workspace({
  '/data':   new RAMResource(),
  '/s3':     new S3Resource({ bucket: 'my-logs-bucket' }),
  '/slack':  new SlackResource({}),
  '/docs':   new GDocsResource({}),
  '/github': new GitHubResource({}),
})
```

Cada recurso necesita sus propias credenciales. Mirage las lee de variables de entorno o de objetos de configuración explícitos. Consulta la [matriz de recursos](https://docs.mirage.strukto.ai/home/resource-matrix) para los detalles de configuración por backend.

## Paso 3: Ejecutar comandos contra el árbol combinado

Una vez configurado el workspace, cada comando pasa por `execute()`:

```python
# List files in S3
await ws.execute("ls /s3/logs/2026/05/")

# Search across Slack messages
await ws.execute("grep 'incident' /slack/incidents/*.json")

# Pipe data between backends
await ws.execute("cat /s3/report.csv | head -20 > /data/preview.txt")

# Read a Google Doc
await ws.execute("cat /docs/meeting-notes.md")

# Search GitHub repo contents
await ws.execute("grep -r 'TODO' /github/my-repo/src/")
```

El agente usa los mismos comandos que usaría en un sistema de archivos local. No hay vocabulario nuevo que aprender ni llamadas a métodos de SDK que memorizar.

### Comandos personalizados

Puedes registrar tus propios comandos que funcionan en todos los montajes:

```python
# Register a summarize command available everywhere
ws.command('summarize', summarize_handler)

# Override a command for a specific resource + filetype
# cat on a Parquet file in /s3 renders rows as JSON
ws.command('cat', {'resource': 's3', 'filetype': 'parquet'}, parquet_cat_handler)

await ws.execute('summarize /github/my-repo/README.md')
await ws.execute('cat /s3/events/2026-05-06.parquet | jq .user')
```

## Paso 4: Integrarlo en tu framework de agentes

Mirage incluye adaptadores para los principales frameworks de agentes. Así es como se conecta.

### OpenAI Agents SDK

```python
from agents import Runner
from agents.run import RunConfig
from agents.sandbox import SandboxAgent, SandboxRunConfig
from mirage.agents.openai_agents import MirageSandboxClient

client = MirageSandboxClient(ws)
agent = SandboxAgent(
    name="Filesystem Agent",
    model="gpt-4.1",
    instructions=ws.file_prompt,
)

result = await Runner.run(
    agent,
    "Find all error logs from last week in /s3 and summarize them.",
    run_config=RunConfig(sandbox=SandboxRunConfig(client=client)),
)
```

La propiedad `ws.file_prompt` genera un prompt de sistema que describe al modelo la estructura del sistema de archivos montado. El agente ejecuta comandos bash contra tus montajes a través del cliente sandbox.

### Vercel AI SDK (TypeScript)

```ts
import { generateText } from 'ai'
import { openai } from '@ai-sdk/openai'
import { mirageTools } from '@struktoai/mirage-agents/vercel'
import { buildSystemPrompt } from '@struktoai/mirage-agents/openai'

const { text } = await generateText({
  model: openai('gpt-4.1'),
  system: buildSystemPrompt({
    mountInfo: { '/s3': 'S3 bucket', '/slack': 'Slack messages' }
  }),
  prompt: "Read /s3/data/report.pdf, then describe what's in it.",
  tools: mirageTools(ws),
})
```

También hay adaptadores para LangChain, Pydantic AI, CAMEL y OpenHands. El patrón es el mismo: pasas el workspace y recibes herramientas.

### CLI con Claude Code o Codex

El CLI de Mirage se conecta directamente a agentes de codificación. Funciona con [Hermes Agent](/es/guia-configuracion-hermes-agent/), [OpenCode](/es/guia-configuracion-opencode/), [Pi Agent](/es/guia-configuracion-pi-agent/) y cualquier herramienta que exponga una interfaz de shell.

```bash
# Create a workspace config
mirage workspace create ws.yaml --id my-agent

# Run commands
mirage execute --workspace_id my-agent --command "grep alert /s3/logs/*.json"

# Snapshot for reuse
mirage workspace snapshot my-agent my-agent.tar
```

## Paso 5: Configurar la caché

Cada workspace incluye una caché de dos capas para que las lecturas repetidas no lleguen a la red:

- **La caché de índice** almacena los listados de directorios y los metadatos. El primer `ls` llega a la API; los siguientes se sirven desde la caché hasta que el TTL expira.
- **La caché de archivos** almacena los bytes de los objetos. El primer `cat` se transmite desde el origen; las lecturas posteriores vienen de la caché.

Por defecto, Mirage usa una caché RAM en el propio proceso (caché de archivos de 512 MB, TTL de índice de 10 minutos). Para configuraciones de producción con múltiples workers o procesos, cambia a Redis:

```ts
import { RedisFileCacheStore, RedisIndexCacheStore, Workspace } from 'mirage/node'

const ws = new Workspace(
  { '/s3': new S3Resource({ bucket: 'my-bucket' }) },
  {
    cache: new RedisFileCacheStore({
      url: 'redis://localhost:6379/0',
      limit: '8GB',
    }),
    index: new RedisIndexCacheStore({
      url: 'redis://localhost:6379/0',
      ttl: 600,
    }),
  },
)
```

Si ejecutas Mirage dentro de un contenedor, puedes combinarlo con una [configuración de Redis en Docker](/es/multiples-bases-datos-postgres-docker/) para un stack totalmente autocontenido.

## Workspaces portables

Los workspaces son portables. Puedes hacer snapshots, clonarlos y versionarlos.

```python
# Save workspace state
ws.snapshot("my-workspace.tar")

# Load it elsewhere
restored = Workspace.load("my-workspace.tar", id="restored")
```

```bash
# CLI equivalent
mirage workspace snapshot my-agent my-agent.tar
mirage workspace load my-agent.tar --id restored
```

Puedes guardar el entorno de trabajo de un agente y restaurarlo en otra máquina, versionar las configuraciones del workspace junto a tu código, o reproducir ejecuciones del agente restaurando exactamente el mismo estado del sistema de archivos.

## Ejemplo real: análisis de logs multiservicio

Aquí tienes un flujo de trabajo concreto que extrae datos de tres servicios para producir un informe:

```python
from mirage import Workspace
from mirage.resource.ram import RAMResource
from mirage.resource.s3 import S3Config, S3Resource
from mirage.resource.slack import SlackConfig, SlackResource
from mirage.resource.github import GitHubConfig, GitHubResource

ws = Workspace({
    "/data":   RAMResource(),
    "/s3":     S3Resource(S3Config(bucket="app-logs")),
    "/slack":  SlackResource(SlackConfig()),
    "/github": GitHubResource(GitHubConfig()),
})

# Find errors in S3 logs
await ws.execute("grep -i 'error' /s3/production/2026-05-*.log > /data/errors.txt")

# Count by frequency
await ws.execute("sort /data/errors.txt | uniq -c | sort -rn > /data/top-errors.txt")

# Check if these were reported in Slack
await ws.execute("grep -f /data/errors.txt /slack/incidents/*.json > /data/slack-matches.txt")

# Cross-reference with GitHub issues
await ws.execute("grep -i 'error' /github/my-app/issues/ > /data/github-issues.txt")

# Combine into a report
await ws.execute("cat /data/top-errors.txt /data/slack-matches.txt /data/github-issues.txt > /data/report.txt")
```

El agente maneja esto de la misma manera que un desarrollador lo haría en una máquina local — `grep`, `sort`, `uniq`, pipes. La diferencia es que los datos viven en S3, Slack y GitHub, y el agente no necesita saberlo.

## Consejos para trabajar con Mirage

<ListCheck>
<ul>
<li>Usa RAMResource como bloc de notas local para resultados intermedios, como `/tmp`</li>
<li>Nombra las rutas de montaje con claridad — `/s3`, `/slack`, `/github` son más fáciles de razonar para los agentes que `/m1`, `/m2`, `/m3`</li>
<li>Cambia a caché Redis para producción; la caché RAM por defecto no sobrevive a reinicios ni se comparte entre procesos</li>
<li>Guarda el estado del workspace antes de tareas largas del agente para poder restaurarlo si algo sale mal</li>
<li>Combina Mirage con agentes de codificación como [OpenCode](/es/guia-configuracion-opencode/) o [Hermes Agent](/es/guia-configuracion-hermes-agent/) que ya usan interfaces de shell</li>
<li>Consulta la [matriz de recursos](https://docs.mirage.strukto.ai/home/resource-matrix) antes de construir — no todos los backends soportan todas las operaciones</li>
</ul>
</ListCheck>

## Solución de problemas

<Accordion label="Los comandos devuelven resultados vacíos" group="faq">
Comprueba que tus credenciales están configuradas correctamente. Mirage lee las credenciales de servicio de variables de entorno por defecto. Verifica con:

```bash
# Check what's mounted
await ws.execute("ls /")

# Check a specific mount
await ws.execute("ls /s3/")
```

Si el montaje está vacío pero no debería estarlo, verifica la configuración del bucket/token/credencial para ese recurso específico.
</Accordion>

<Accordion label="Los pipes fallan entre montajes" group="faq">
La mayoría de los pipes funcionan entre montajes, pero algunos comandos tienen un comportamiento específico del recurso. Si un pipe falla, prueba a dividirlo en pasos separados usando un RAMResource como almacenamiento intermedio:

```python
await ws.execute("cat /s3/data.json > /data/temp.json")
await ws.execute("jq '.items[]' /data/temp.json > /data/filtered.json")
```
</Accordion>

<Accordion label="El rendimiento parece lento" group="faq">
Las primeras lecturas siempre llegan a la red. Las lecturas posteriores usan la caché. Si haces I/O intensivo:

1. Cambia a caché Redis para compartir caché entre procesos
2. Usa `mirage provision` (CLI) para precalentar la caché antes de las ejecuciones del agente
3. Comprueba si tu backend tiene límites de velocidad (especialmente las APIs de Slack y Google)
</Accordion>

<Accordion label="¿Qué modelo funciona mejor con Mirage?" group="faq">
Cualquier modelo que maneje bien bash sirve. Los modelos entrenados intensamente en código y comandos de shell tienden a rendir mejor. Si buscas opciones asequibles, consulta [Los Mejores LLMs Open Source para Codificación](/es/mejores-llms-opensource-alternativa-claude/) o [Los Mejores Modelos Baratos para Hermes Agent](/es/mejores-modelos-baratos-hermes-agent/). También puedes ejecutar Mirage con modelos gratuitos a través de [OpenRouter](/hermes-agent-mimo-v2-pro/) o [LiteLLM](/es/litellm-docker-instalacion/).
</Accordion>
