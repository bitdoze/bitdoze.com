Si has construido agentes de IA que consultan varios servicios a la vez, ya conoces el problema. Tu agente necesita leer un archivo en S3, revisar un hilo de Slack, abrir un Google Doc y consultar un repositorio de GitHub. Cada uno exige su propio SDK, autenticación y llamadas.

[Mirage](https://github.com/strukto-ai/mirage) cambia el enfoque: monta todos esos servicios como ramas de un único sistema de archivos virtual para agentes de IA. Tu agente recorre S3, Google Drive, Slack, GitHub, Redis o Gmail con `ls`, `cat`, `grep` y pipes.

Funciona tan bien porque los LLMs se entrenan a fondo en entornos de terminal. El sistema de archivos Unix es probablemente la interfaz que mejor dominan. Desde la primera versión de esta guía, Mirage pasó de sistema de archivos virtual a terminal virtual completo para agentes de IA: mismo núcleo de árbol y bash, más CLIs virtuales, máquinas virtuales y una capa de políticas. Todo abajo está actualizado a **v0.0.8**.

<Notice type="warning" title="Probado con Mirage v0.0.8">
Versión probada: v0.0.8 (publicada el 2026-11-03). El proyecto sigue marcado como experimental (0.0.x) y ha incluido cambios incompatibles en cada menor. Fija <code>mirage-ai==0.0.8</code> en producción y revisa las notas de lanzamiento antes de actualizar.
</Notice>

## Qué hace Mirage realmente

Mirage te entrega un objeto `Workspace`. Montas servicios en rutas de ese espacio de trabajo y ejecutas comandos shell contra el árbol combinado. La idea recuerda a usar herramientas FUSE para [montar un bucket S3 como sistema de archivos en un VPS](/es/montar-bucket-s3-sistema-archivos-vps/), pero Mirage ejecuta el árbol en proceso para tu agente, sin montar nada en el host.

```python
import asyncio
from mirage import MountMode, Workspace
from mirage.vfs.ram import RAMVFS
from mirage.vfs.s3 import S3Config, S3VFS
from mirage.vfs.slack import SlackConfig, SlackVFS

async def main() -> None:
    ws = Workspace(
        {
            "/data":  RAMVFS(),
            "/s3":    S3VFS(S3Config(bucket="my-logs-bucket")),
            "/slack": SlackVFS(SlackConfig(token="xoxb-...")),
        },
        mode=MountMode.WRITE,
    )
    result = await ws.shell("ls /s3/logs/")
    print(await result.stdout_str())
    await ws.close()

asyncio.run(main())
```

El shell no invoca `/bin/bash`. Mirage corre en proceso con su propio parser bash escrito en Rust (compartido por PyO3 para Python y WebAssembly para TypeScript; tree-sitter se retiró en v0.0.8) y un despachador por montaje. Sin subprocesos. Los kernels de comandos (`jq`, `awk`, `sed`, `grep`, `rg`, `sort`, `tar`, `patch`) viven en el crate Rust `mirage-rs`.

Desde v0.0.5 también virtualiza CLIs (`git`, `gh`, `slack`, `office`) y máquinas remotas (SSH, Docker, Kubernetes). Algo clave antes de escribir código: **los montajes son solo lectura por defecto**. Debes habilitar escritura explícitamente con `MountMode.WRITE` (y ejecución con `MountMode.EXEC`), globalmente o por montaje.

![Arquitectura de terminal virtual Mirage: el agente ejecuta comandos bash contra un parser Rust que despacha a montajes VFS, CLIs virtuales y máquinas pasando por una capa de políticas](@assets/images/25/05/mirage-architecture-diagram.svg)

### Backends soportados

| Categoría | Backends | Modo |
|---|---|---|
| **Almacenamiento de objetos** | S3, Cloudflare R2, GCS, OCI, MinIO, B2, Spaces, Wasabi, Ceph, SeaweedFS | Lectura/escritura |
| **Archivos y discos** | Google Workspace (Drive, Docs, Sheets, Slides), OneDrive, SharePoint, Dropbox, Box, WebDAV, SSH (SFTP) | Lectura/escritura |
| **Bases de datos** | Postgres, MongoDB, Redis, SQL, Airtable | Principalmente solo lectura |
| **IA / vectores / observabilidad** | Chroma, Qdrant, HF Datasets/Models, Weights & Biases, Langfuse, Jaeger | Solo lectura |
| **Chat / productividad** | Slack, Discord, Email (IMAP), Notion, Trello, Linear, Google Calendar | Principalmente solo lectura |
| **Control de versiones** | GitHub (repo en rama/tag/commit) | Solo lectura |
| **Borrador temporal** | RAM, Disk | Lectura/escritura |

Detalles importantes del comportamiento de montajes:

- **Search push-down:** en algunos backends `grep` consulta la API de búsqueda del servicio en vez de bajar cada archivo.
- **Límites de recorrido:** en S3, `grep -r`, `find` y `du` se detienen en 1.000 archivos por defecto (`walk_limit` configurable en `command_limits`).
- **No todo admite escritura:** vistas de GitHub, Slack, Discord, Notion o Postgres son solo lectura.

<Notice type="info" title="No todos los backends soportan lo mismo">
Ejecuta <code>mirage workspace vfs-md</code> o <code>mirage workspace vfs</code> para ver qué operaciones admite cada montaje. Consulta las guías por backend en <a href="https://docs.mirage.strukto.ai/home/setup/s3">docs.mirage.strukto.ai</a>.
</Notice>

### Mirage frente a servidores MCP por servicio

<Accordion label="¿Cómo se compara con MCP?" group="comparison" expanded="true">

Si vienes de [qué es MCP (Model Context Protocol)](/es/introduccion-mcp-principiantes/) y dudas si necesitas ambos:

| Aspecto | Mirage | Servidores MCP por servicio |
|---|---|---|
| **Configuración** | Un workspace con montajes por servicio | Un servidor por servicio |
| **Vocabulario del agente** | Bash estándar (`ls`, `cat`, `grep`, pipes) | Esquemas de herramientas por servidor |
| **Pipelines entre servicios** | Nativos (pipes entre montajes) | Orquestación manual |
| **Caché** | Caché integrada de dos capas (índice + archivos) | Varía según servidor |
| **Portabilidad** | Snapshots y clonado de workspaces | Estado repartido |
| **Frameworks** | OpenAI Agents SDK, Vercel AI SDK, Agno, LangChain, Pydantic AI, Mastra | Depende del cliente MCP |

MCP sigue siendo útil para acciones estructuradas (crear un evento o enviar un mensaje en Slack; ver [herramientas de Mastra vs MCP](/es/herramientas-mastra-vs-mcp/)). Ahora además son complementarios: la función **"From MCP"** de Mirage (v0.0.8) instala las herramientas de un servidor MCP como una única CLI dentro del shell de Mirage. Si ya usas conectores vía la [guía de Composio MCP](/es/guia-composio-mcp/) o [Context7 MCP con Agno](/es/agno-herramientas-mcp-context7/), puedes reutilizarlos.

</Accordion>

const ws = new Workspace(

</Tab>
<Tab name="CLI (workspace.yaml)">

```yaml
# workspace.yaml
mode: read
mounts:
  /data:
    vfs: s3
    config:
      bucket: my-bucket
      region: us-east-1
      aws_access_key_id: ${AWS_ACCESS_KEY_ID}
      aws_secret_access_key: ${AWS_SECRET_ACCESS_KEY}
  /repo:
    vfs: github
    config:
      owner: my-org
      repo: my-app
      token: ${GITHUB_TOKEN}
  /scratch:
    vfs: ram
    mode: write

  "@all": { walk_limit: 2000 }
```

```bash
mirage workspace create workspace.yaml --id my-agent
```

</Tab>
</Tabs>

<Notice type="warning" title="Solo lectura por defecto">
Los montajes rechazan escrituras salvo que indiques <code>MountMode.WRITE</code>. Empieza siempre en solo lectura y abre permisos solo donde haga falta.
</Notice>

`/` es ahora una raíz virtual real (la antigua ruta `/_default` desapareció en v0.0.3).

## Paso 3: ejecutar comandos y CLIs virtuales

Todo pasa por `ws.shell()`:

```python
result = await ws.shell("ls /s3/logs/2026/05/")
print(await result.stdout_str())

result = await ws.shell("cat /s3/report.csv | head -20 > /data/preview.txt")
if result.exit_code != 0:
    print(await result.stderr_str())
```

<Notice type="warning" title="ws.shell() no lanza excepciones">
Comprueba siempre <code>result.exit_code</code> y lee <code>await result.stderr_str()</code>. Códigos: 0 = ok, 1 = error de herramienta/VFS, 2 = uso o rechazo por política, 130 = Ctrl-C, 141 = broken pipe.
</Notice>

Verifica rápido desde la CLI:

```bash
mirage shell -w demo -c 'echo ok > /data/x && cat /data/x'
mirage shell -w demo -c 'ls /s3' --json | jq .stdout
```

La antigua API `ws.command()` fue sustituida desde v0.0.5 por **CLIs virtuales** declaradas bajo `clis:` (`git`, `gh`, `slack`, `office`, `pdftotext`, scripts propios en Python/JS). Los agentes las descubren con `man`, `which` y `SKILL.md`.

| OpenAI Agents | `mirage-ai[openai]` | `MirageShellExecutor(ws)`, `MirageEditor(ws)`, `MirageSandboxClient(ws)` | Shell/patch/sandbox |

| LangChain Deep Agents | `mirage-ai[deepagents]` | `LangchainWorkspace(ws)` | Archivos + shell |

| Mastra | `@struktoai/mirage-mastra` | por paquete | Herramientas Mastra |

Las 7 herramientas de sesión son `shell`, `read`, `write`, `edit`, `ls`, `grep` y `glob`.

<Notice type="info" title="VFS.md reemplaza a file_prompt">
La propiedad antigua <code>ws.file_prompt</code> desapareció. Genera el mapa con <code>vfs_md = await ws.vfs_md(session_id="agent")</code>; el agente lo lee con <code>cat /VFS.md</code> siguiendo la especificación <a href="https://agentvfs.org/vfs">AgentVFS</a>.
</Notice>

Si trabajas con [empezar con agentes Agno](/es/empezar-agno/) o construyes un [agente de IA con Mastra](/es/crear-agente-ia-mastra/), usa su adaptador directo.

## Paso 5: configurar caché y políticas de seguridad

Cada workspace incluye caché de índice y caché de archivos (32 MB RAM por defecto). En producción con varios workers cambia a Redis (`RedisCacheConfig(url="redis://localhost:6379/0")`).

<Notice type="warning" title="El límite de Redis en Mirage no desaloja claves">
El ajuste <code>limit</code> de Redis (512 MB por defecto) no expulsa entradas viejas. Limita la memoria del servidor Redis con <code>maxmemory</code> en tu configuración de Redis. Ver también <a href="/es/multiples-bases-datos-postgres-docker/">contenedores Docker de datos</a>.
</Notice>

![Capa de políticas de Mirage: reglas de perfil en puertas de comando, ruta y red que producen permitir, preguntar o denegar, con puerta de aprobación y registro de decisiones](@assets/images/25/05/mirage-policy-doors-diagram.svg)

Los perfiles definen rutas ocultas (invisibles en `ls`, `grep` y `VFS.md`), comandos permitidos/denegados/con aprobación humana (`ask`), reglas de salida de red (`allowed_domains`/`denied_domains`) y scripts de política en Python/JS:

```yaml
profiles:
  analyst:
    paths:
      hide: ["/s3/secrets", "/data/credentials"]
    commands:
      deny: ["slack send-message", "curl", "rm -rf"]
      allow: ["ls", "cat", "grep", "sort", "wc", "head", "tail"]
      ask: ["cp", "mv"]
network:
  allowed_domains: ["api.github.com:443", "*.slack.com"]
  denied_domains: ["*:22"]
```

Usa `--explain` en la CLI para simular cualquier comando contra tus políticas sin ejecutarlo.

## Ejecutar Mirage en producción en un VPS

v0.0.8 incluye un servidor HTTP multi-worker (`http://127.0.0.1:8765`, autenticado con `MIRAGE_TOKEN`), imagen sandbox `ghcr.io/strukto-ai/mirage-sandbox:0.0.8` (amd64 + arm64), métricas OpenTelemetry y snapshots asíncronos a disco o S3 (`await ws.snapshot("snapshots/run.tar", s3={"bucket": "my-backups"})`).

## Resolución de problemas

<Accordion label="Los comandos devuelven salida vacía" group="faq">
Verifica tus credenciales y lista la raíz con <code>await ws.shell("ls /")</code> y <code>await ws.shell("ls /s3/")</code>.
</Accordion>

<Accordion label="Los pipes fallan o los comandos en árboles grandes se rechazan" group="faq">
En S3 el límite <code>walk_limit</code> corta en 1.000 archivos. Sube <code>command_limits</code> o divide el pipeline usando <code>/data</code> en RAM como paso intermedio.
</Accordion>

<Accordion label="Comando rechazado (código de salida 2)" group="faq">
<code>ws.shell</code> no lanza excepciones. Inspecciona <code>result.exit_code</code>, <code>await result.stderr_str()</code> y ejecuta el comando con <code>--explain</code> en la CLI para ver qué regla lo bloqueó.
</Accordion>

<Accordion label="Errores EDQUOT o de capacidad" group="faq">
Has alcanzado <code>max_memory</code> o la capacidad del montaje. Limpia <code>/data/*</code> o aumenta <code>max_memory</code> en la configuración.
</Accordion>
