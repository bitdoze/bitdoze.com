## Instalar Docker

Si aún no tienes Docker en tu servidor:

```sh
curl -fsSL https://get.docker.com -o get-docker.sh
sh get-docker.sh
```

Guía completa: [Instalar Docker y Docker Compose en Ubuntu](/install-docker-ubuntu-arm/).

Los comandos de esta guía funcionan con Docker Engine 29.x y Docker Compose v5.x (comprobado en octubre de 2026). Antes de seguir:

```sh
docker compose version   # prints a v5.x version
sudo docker ps           # lists running containers, empty list is fine
```

Si `docker compose version` da error, la instalación no terminó. Si `sudo docker ps` se queja del daemon, ejecuta `sudo systemctl enable --now docker`.

## Configurar Caddy como proxy inverso

Caddy gestiona HTTPS automáticamente. Sin certbot, sin crons de renovación, sin archivos de configuración de nginx. Obtiene los certificados de Let's Encrypt por sí solo y los renueva antes de que caduquen.

Yo ejecuto Caddy como contenedor Docker dentro de la misma estructura de directorios donde viven todas mis apps. El tag `caddy:2-alpine` sigue siendo el correcto (la línea 2.11.x; la 2.11.7 era la actual en octubre de 2026). Nada de la configuración de abajo cambió entre esas versiones.

### Crear la estructura de directorios

```sh
mkdir -p /home/$USER/docker-apps/caddy
cd /home/$USER/docker-apps/caddy
```

### Docker Compose para Caddy

Crea un `docker-compose.yml` en el directorio de Caddy:

```yaml
services:
  caddy:
    image: caddy:2-alpine
    container_name: caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
      - "443:443/udp"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile
      - ./data:/data
      - ./config:/config
    networks:
      - caddy

networks:
  caddy:
    external: true
```

### Crear la red Docker

Todas tus apps se conectarán a esta red compartida para que Caddy pueda alcanzarlas:

```sh
sudo docker network create caddy
```

### Crear el Caddyfile

Crea un `Caddyfile` en la misma carpeta. Empieza con un marcador de posición:

```
# Apps will be added here by the AI assistant or manually
```

### Arrancar Caddy

```sh
cd /home/$USER/docker-apps/caddy
sudo docker compose up -d
```

Verifica antes de tocar el DNS:

```sh
sudo docker compose ps           # caddy should show running
sudo docker logs caddy --tail 20
```

Si el contenedor se reinicia en bucle, el Caddyfile es el sospechoso habitual. Corrige el archivo y ejecuta `sudo docker compose up -d` de nuevo. Cualquier app que añadas después solo necesita una entrada en este Caddyfile y una conexión a la red `caddy`.

<Notice type="info" title="Valida antes de cada recarga">
Ejecuta `sudo docker exec caddy caddy validate --config /etc/caddy/Caddyfile` antes de recargar Caddy. Un error de sintaxis en ese archivo tumba todos los sitios que alojas, no solo la app nueva. Esta regla también vive en el archivo de skill de abajo.
</Notice>

## Configurar el DNS wildcard

Necesitas un registro DNS que envíe todos los subdominios a tu servidor. En tu registrador de dominios o proveedor de DNS (Cloudflare, etc.), añade un registro A:

| Tipo | Nombre | Valor | TTL |
|------|------|-------|-----|
| A | `*` | `IP_DE_TU_SERVIDOR` | Auto |

Si tu dominio es `example.com`, esto significa que `anything.example.com` resolverá a tu VPS. Caddy se encarga luego de enrutar cada subdominio al contenedor correcto.

Compruébalo antes de confiar en él:

```sh
dig +short anything.yourdomain.com
# must print your VPS IP
```

Si la emisión del certificado falla más adelante, este registro es lo primero que hay que revisar. Un DNS que no se ha propagado es la razón más común por la que Let's Encrypt se rinde con un subdominio nuevo.

<Notice type="info" title="Usuarios de Cloudflare">
Si usas Cloudflare, puedes activar el proxy en el registro wildcard (nube naranja), pero tendrás que configurar Caddy para que funcione con el modo SSL de Cloudflare. La configuración más sencilla es usar «Solo DNS» (nube gris) y dejar que Caddy gestione los certificados directamente.
</Notice>

## La convención de directorios

Cada app tiene su propia carpeta dentro de `/home/$USER/docker-apps/`. La estructura queda así después de unas cuantas apps:

```
/home/user/docker-apps/
  caddy/
    docker-compose.yml
    Caddyfile
    data/
    config/
  plausible/
    docker-compose.yml
    .env
  arcane/
    docker-compose.yml
    .env
  dockhand/
    docker-compose.yml
    .env
```

Esto mantiene todo predecible. El asistente de IA sabe dónde poner los archivos, y tú sabes dónde encontrarlos cuando necesitas revisar algo manualmente. Esa predictibilidad es lo que permite que el archivo de skill sea corto y estricto: una ruta que conocer, una red a la que unirse, un lugar para los secretos.

## Qué hace el asistente de IA con todo esto

Con la infraestructura lista, puedes decirle a tu asistente de IA que despliegue apps. He instalado [Arcane](/es/instalar-arcane/) y [Dockhand](/es/instalar-dockhand/) de esta forma. Para más contexto sobre ambas, escribí una [comparación de las dos](/es/arcane-vs-dockhand/).

El asistente sigue el mismo flujo de trabajo cada vez:

1. Crea una nueva carpeta en `/home/user/docker-apps/app-name/`
2. Escribe un `docker-compose.yml` con rutas de volúmenes locales `./` (sin volúmenes nombrados)
3. Pone contraseñas y claves API en un archivo `.env`, no hardcodeadas en el archivo compose
4. Valida el archivo compose con `docker compose config -q` antes de arrancar nada
5. Arranca los contenedores con `sudo docker compose up -d`
6. Actualiza el Caddyfile en `/home/user/docker-apps/caddy/` con un nuevo bloque de subdominio
7. Valida el Caddyfile con `caddy validate` antes de recargar Caddy
8. Recarga Caddy para aplicar la nueva configuración
9. Ejecuta un curl con reintentos contra el subdominio e informa del estado HTTP
10. Confirma el stack con `docker compose ps` en lugar de confiar en el código de salida de `up -d`

Funciona porque hay un archivo de skill que le dice al asistente exactamente cómo está configurado este servidor y qué reglas seguir. Sin la skill, el asistente adivinaría las rutas, podría usar volúmenes nombrados, podría saltarse el proxy inverso o poner secretos directamente en el archivo compose.

```markdown
# Docker + Caddy Server Rules

Apply these rules for all deployment, operations, and setup tasks on this server.

## Environment facts
- Docker is installed and available.
- Caddy is installed and managed from `/home/dragos/docker-apps/caddy`.
- Docker app projects must be placed under `/home/dragos/docker-apps`.
- Wildcard DNS `*.ai.bitdoze.com` points to this server and should be used for app subdomains.

## Permission model
- Use `sudo` for commands that manage Docker runtime/services, networking, filesystem locations requiring elevation, or system-level setup.
- Prefer explicit commands that can be audited and repeated.

## Compose placement and style
- Prefer Docker Compose-based deployments.
- Place each app in its own folder under `/home/dragos/docker-apps/<app-name>`.
- Keep compose and related app files together in the app folder.
- Do not use named volumes for app data/config in compose files.
- Use local relative paths (`./...`) in the location where the compose file is created.
- Pin image tags. Never deploy `latest` unless asked.

## Caddy integration
- Route apps through Caddy using subdomains under `*.ai.bitdoze.com`.
- Keep Caddy config changes under `/home/dragos/docker-apps/caddy`.
- When adding a new app, include the target hostname and upstream container/service mapping.

## Expected workflow
1. Create app directory in `/home/dragos/docker-apps/<app-name>`.
2. Add `docker-compose.yml` with services and `./...` path mappings.
3. Place sensitive data into a `.env` file, not in compose directly (passwords, hashes, API keys).
4. Run `docker compose config -q` in the app folder and fix any errors before `up -d`.
5. Run required Docker/Caddy commands with `sudo`.
6. Add/update Caddy config in `/home/dragos/docker-apps/caddy` for `<app>.ai.bitdoze.com`.
7. Run `sudo docker exec caddy caddy validate --config /etc/caddy/Caddyfile` before any reload. If validation fails, fix the Caddyfile before continuing.
8. Reload Caddy, then validate service health and public routing.
9. Run a retrying curl against the subdomain (up to 10 tries, 5 seconds apart) and report the HTTP status, not just the exit code.
10. Confirm the stack with `docker compose ps` before reporting success.

## Validation
- Run `docker compose config -q` in the app folder before `up -d`.
- Run `sudo docker exec caddy caddy validate --config /etc/caddy/Caddyfile` before any Caddy reload.
- Verify with a retrying curl against the subdomain; report HTTP status, not just exit code.
- Pin image tags; never deploy `latest` unless asked.

## Safety rules
- Never modify files outside `/home/dragos/docker-apps`.
- Never run `curl | bash` from non-official URLs; no firewall, SSH, or systemd changes.
- Ask before touching the `caddy` stack itself; a broken Caddyfile takes down every site.

## Guardrails
- Reject plans that place apps outside `/home/dragos/docker-apps`.
- Reject plans that use named Docker volumes for persistent files.
- Reject plans that bypass Caddy when public HTTP(S) access is required.
- Place sensitive data into `.env` file not in compose directly like passwords and hashes.
```

Y lo arranca todo:


## Verifica el despliegue y soluciona los fallos comunes

Un despliegue no termina cuando `up -d` devuelve el control. Termina cuando la app responde en su subdominio. Comprueba tres cosas:

1. `sudo docker compose ps` en la carpeta de la app muestra el servicio en marcha (y healthy si tiene healthcheck).
2. El curl con reintentos devuelve 200 y lees el código de estado tú mismo.
3. `sudo docker logs caddy --tail 20` está limpio: certificado emitido, sin errores de upstream.

Cuando algo falla, suele ser una de estas causas:

| Síntoma | Causa | Solución |
|---|---|---|
| La emisión del certificado falla, Caddy sigue reintentando | El DNS no se ha propagado | `dig +short app.tudominio.com` debe devolver la IP del VPS antes de desplegar |
| Caddy 502 o 504 | Contenedor en la red equivocada | El archivo compose necesita `networks: caddy: external: true` y el servicio debe unirse a la red `caddy` |
| Puerto ya asignado al arrancar | 80/443 ocupados por otro proxy o servicio del host | `ss -tlnp \| grep -E ':80\|:443'` y detén el otro listener |
| Todos los sitios caídos tras un despliegue | Error de sintaxis en el Caddyfile | `sudo docker exec caddy caddy validate --config /etc/caddy/Caddyfile` antes de cada recarga |
| `429` o «too many certificates» | Límite de tasa de Let's Encrypt por despliegues de prueba repetidos | Usa la CA staging de LE mientras experimentas; vuelve a la normal para algo real |

<Notice type="warning" title="Un Caddyfile roto tumba todos los sitios">
El Caddyfile es compartido. Un error de sintaxis y todas las apps detrás de Caddy se apagan, no solo la nueva. `caddy validate` antes de cada recarga es la regla que lo evita.
</Notice>

El rollback es el despliegue a la inversa:

```sh
cd /home/$USER/docker-apps/uptime-kuma
sudo docker compose down

cd /home/$USER/docker-apps/caddy
# remove the app block from the Caddyfile, then:
sudo docker exec caddy caddy validate --config /etc/caddy/Caddyfile
sudo docker compose exec caddy caddy reload --config /etc/caddy/Caddyfile

cd /home/$USER/docker-apps
# tar the folder if the data matters, then:
rm -rf uptime-kuma
```

Y recuerda que [los puertos publicados de Docker se saltan UFW](/es/docker-evita-firewall/) si también ejecutas un firewall en el host. Eso importa más, no menos, cuando es una IA la que publica los puertos.

## Por qué importan las salvaguardas

Sin la skill, los asistentes de IA toman decisiones razonables pero inconsistentes. Podrían:

- Poner los datos de la app en `/opt/` o `/var/` o donde les parezca
- Usar volúmenes nombrados de Docker, lo que complica los backups (tienes que rebuscar en `/var/lib/docker/volumes/`)
- Saltarse el proxy inverso y exponer puertos directamente
- Hardcodear contraseñas en el archivo compose, donde aparecen en `docker inspect`
- Olvidar comprobar si la app realmente arrancó

Las salvaguardas de la skill evitan todo esto. Si el asistente intenta crear un archivo compose con un volumen nombrado, la skill le dice que no. Si intenta exponer un puerto directamente sin pasar por Caddy, la skill dice que no.

La mayoría de las veces la diferencia es la consistencia. Un asistente sin la skill puede desplegar apps. Un asistente con la skill las despliega como tú quieres, cada vez.

## Seguridad: dar sudo a una IA

<Notice type="warning" title="Esto es acceso equivalente a root">
El acceso a Docker es acceso root. Un asistente operado por chat que puede ejecutar `sudo docker` puede arrancar contenedores privilegiados, montar cualquier ruta del host y leer cada secreto de cada `.env` de la máquina. Trátalo como entregar el root.
</Notice>

Déjame decir la parte incómoda claramente. Esta configuración le da a un asistente de IA `sudo` sin contraseña sobre Docker, y lo controlas desde Telegram. Si otra persona puede enviarle mensajes a ese bot, es dueña del servidor.

Si el asistente es OpenClaw, los valores por defecto no están mal. El gateway se vincula a loopback, los remitentes desconocidos de DM reciben un código de emparejamiento en lugar de ejecución de comandos, y el acceso de grupo está detrás de una lista de permitidos más una barrera de mención. Comprueba tu configuración real contra esos valores por defecto:

```sh
openclaw security audit
```

La [guía completa de seguridad de OpenClaw](/es/guia-seguridad-openclaw/) cubre la política de DM, las listas de permitidos y las configuraciones endurecidas. Más allá de los valores por defecto de la plataforma, la propia skill lleva las reglas de seguridad del bloque `## Safety rules` de arriba: nada fuera de `/home/user/docker-apps`, nada de `curl | bash` desde URLs aleatorias, nada de ediciones de firewall, SSH o systemd, y preguntar antes de tocar el stack de `caddy`.

Si quieres un aislamiento más fuerte que reglas bien escritas para un modelo de lenguaje, las opciones reales son:

- Ejecutar el agente en un contenedor o sandbox en lugar del host.
- Poner un proxy de socket Docker (Tecnativa) entre el agente y el daemon para que solo pueda tocar contenedores etiquetados. La [instalación de Arcane](/es/instalar-arcane/) ya usa ese patrón.
- Limitar el agente a una sola carpeta de app en lugar de todo el árbol `docker-apps`.

Antes de soltar un agente en un servidor que te importa:

<ListCheck>
<ul>
<li>Ejecuta `openclaw security audit` (o el equivalente de tu plataforma) y corrige lo que marque</li>
<li>Confirma que los códigos de emparejamiento y las listas de permitidos de DM están activos, para que solo tú puedas hablar con el bot</li>
<li>Fija las reglas de seguridad de la skill en el archivo de skill, no en un mensaje de chat</li>
<li>Haz un backup antes del primer despliegue dirigido por IA, y sigue haciéndolos</li>
</ul>
</ListCheck>

Esta no es la única capa. El endurecimiento del host sigue importando: mira [cómo protegí mi servidor Docker tras el informe del BSI](/es/informe-seguridad-bsi-docker-ufw/), por qué [los puertos publicados de Docker se saltan UFW](/es/docker-evita-firewall/), y cómo [proteger un VPS con CrowdSec](/es/crowdsec-servidor-seguro/). La skill reduce el radio de impacto de un despliegue normal. No hace inofensivo a un bot comprometido.

## Gestionar las apps desplegadas

Después de unos cuantos despliegues, querrás revisar cómo van las cosas. Algunos comandos útiles:

```sh
# See all running containers
sudo docker ps

# Check logs for a specific app
sudo docker logs uptime-kuma --tail 50

# Restart an app
cd /home/$USER/docker-apps/uptime-kuma
sudo docker compose restart

# Update an app to latest image
cd /home/$USER/docker-apps/uptime-kuma
sudo docker compose pull
sudo docker compose up -d

# Remove an app completely
cd /home/$USER/docker-apps/uptime-kuma
sudo docker compose down
cd ..
rm -rf uptime-kuma
# Also remove the Caddyfile entry
```

<Notice type="info" title="Backup antes de destruir">
Antes de cualquier `down` más `rm -rf`, comprime la carpeta de la app incluyendo el `.env`: `tar czpf /root/backups/uptime-kuma-$(date +%F).tar.gz uptime-kuma/`. Súbelo a almacenamiento compatible con S3 si los datos importan. La skill debería hacer que el asistente lo haga automáticamente. Hasta que lo haga, hazlo tú.
</Notice>

Para gestionar contenedores desde una UI web en lugar de la terminal, echa un vistazo a [Arcane](/es/instalar-arcane/) o [Dockhand](/es/instalar-dockhand/). Escribí sobre [cuál elegir](/es/arcane-vs-dockhand/) si estás decidiendo entre ambas. Si solo quieres un gestor de archivos compose sencillo, el [gestor de compose Dockge](/es/instalar-dockge/) es una opción más ligera. Incluso puedes pedirle a tu asistente de IA que instale cualquiera de ellas usando esta misma skill.

Si quieres actualizaciones automáticas de contenedores, [Tugtainer](/es/tugtainer-autoactualizacion-docker/) se encarga de eso sin necesidad de reconstruir los stacks de compose.

## Qué asistente de IA usar

Cualquier asistente de IA que admita skills o prompts de sistema puede usar este archivo. Tres vías funcionan:

- **[OpenClaw](/es/guia-configuracion-openclaw/)** ejecutándose en el mismo VPS, chateando por Telegram. Tiene acceso directo a la shell del servidor, así que ejecuta los comandos Docker él mismo. Instálalo con `curl -fsSL https://openclaw.ai/install.sh | bash`; las versiones llevan fecha (v2026.10.x en octubre de 2026).
- **Un [bot de Agno](/es/crear-tu-propio-agente-ia/) personalizado** en Discord con herramientas de shell habilitadas. La misma idea, distinta plataforma de chat. La guía cubre la instalación, la integración con Discord, la memoria y los agentes de equipo.
- **Claude Code u OpenCode** conectados por SSH. La vía de los agentes de código. Claude Code lee la skill desde `~/.claude/skills/` y la invocas con `/docker-deploy`; OpenCode la descubre desde `.opencode/skills/`.

La configuración con OpenClaw es la más desatendida. Le envías mensajes por Telegram desde tu teléfono, y él hace todo en el servidor sin que abras una terminal. La [guía de configuración](/es/guia-configuracion-openclaw/) cubre la instalación. Si quieres el asistente en hardware de casa en lugar de un VPS alquilado, el [mejor Mac mini para OpenClaw](/es/mejor-mac-mini-openclaw/) cubre la vía local.

## Ampliar la skill

El archivo de skill es solo markdown. Puedes añadir reglas a medida que tu configuración crece. Algunas cosas que he añadido a la mía con el tiempo:

- Una sección de backups que le dice al asistente que cree un script `backup.sh` en cada carpeta de app. La regla concreta: antes de `down` o `rm -rf`, comprime la carpeta de la app más el `.env` (la misma regla que en «Gestionar las apps desplegadas»).
- Preferencias de base de datos (usar PostgreSQL en lugar de MySQL cuando la app admite ambas)
- Límites de recursos para los contenedores (`deploy.resources.limits` en compose)
- Una regla de monitorización que añade todas las apps nuevas a mi instancia de Uptime Kuma automáticamente

Si tu archivo de skill aún no fija los tags de imagen, añade esa línea. `latest` es como ocurren las actualizaciones sorpresa.

También puedes pedirle al asistente que actualice la propia skill. «Añade una regla para que todas las apps nuevas incluyan un healthcheck en el archivo compose» funciona bien. Lee la skill, añade la regla y la sigue a partir de entonces.

## El panorama general

Esta configuración convierte un VPS en algo que gestionas mediante conversación. El servidor sigue ejecutando Docker y Caddy como cualquier configuración normal. La diferencia es que tu asistente de IA conoce las reglas y las sigue de forma consistente.

He desplegado decenas de apps de esta forma en los meses desde que lo configuré. Algunas las mantuve, otras las probé una hora y las eliminé. Lo que cambió es la velocidad a la que pruebas cosas. Cuando instalar una app lleva 30 segundos escribiendo un mensaje en lugar de 10 minutos escribiendo archivos compose, pruebas más cosas.

<Accordion label="Preguntas frecuentes" group="faq" expanded="true">

**¿El asistente necesita acceso root?**

Necesita ejecutar comandos Docker con `sudo`. Si tu usuario está en el grupo `docker`, puedes modificar la skill para eliminar el requisito de `sudo`, pero prefiero mantenerlo explícito. Ten en cuenta que pertenecer al grupo `docker` es en sí mismo equivalente a root, así que el grupo no reduce el riesgo. Solo quita cuatro letras de los comandos.

**¿Es seguro darle sudo a un asistente de IA?**

No automáticamente. Es acceso equivalente a root, así que trátalo como entregar el root. Mantén las reglas de seguridad en el archivo de skill, usa los controles de acceso de tu plataforma (los códigos de emparejamiento de OpenClaw, las listas de permitidos de DM y `openclaw security audit`), considera un proxy de socket Docker o un agente en sandbox, y guarda backups. La sección «Seguridad: dar sudo a una IA» de arriba recorre los detalles.

**¿Puedo usar Nginx o Traefik en lugar de Caddy?**

Sí, pero tendrías que reescribir las partes específicas de Caddy de la skill. Caddy es la opción más sencilla porque gestiona los certificados automáticamente sin configuración extra. Si ya usas [Traefik](/es/traefik-proxy-docker/), adapta la skill para usar labels en lugar de entradas de Caddyfile.

**¿Qué pasa si el asistente estropea algo?**

Cada app está aislada en su propia carpeta. Si algo sale mal, `docker compose down` en esa carpeta la detiene, y borrar la carpeta la limpia por completo. El peor caso es una entrada rota en el Caddyfile, que se arregla editando un solo archivo. La sección «Verifica el despliegue y soluciona los fallos comunes» tiene el rollback completo.

**¿Pueden varios asistentes compartir la misma skill?**

Sí. La skill describe convenciones del servidor, no comportamientos específicos del asistente. Pon el mismo archivo en el directorio de skills de cada asistente y todos seguirán las mismas reglas.

**¿Funciona esto en servidores ARM (Raspberry Pi)?**

La skill en sí es agnóstica a la arquitectura. Que las imágenes Docker que despliegues tengan builds para ARM es otra cuestión. La mayoría de las apps self-hosted populares ya publican imágenes multi-arquitectura. El CAX11 (ARM) de Hetzner ejecuta este stack sin problemas.
