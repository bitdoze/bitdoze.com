## ¿Qué son los plugins Herdr?

Un plugin Herdr es un directorio con un manifiesto `herdr-plugin.toml` más comandos que Herdr lanza como arrays argv. Ese es todo el modelo. No hay SDK ni superficie de API restringida: la CLI `herdr` entera es la API de plugins, y los plugins llaman de vuelta a través de `HERDR_BIN_PATH`, que funciona igual sobre sockets Unix y named pipes de Windows. Cualquier lenguaje funciona, porque Herdr simplemente ejecuta lo que declara el manifiesto: Bash, JavaScript, Lua, Rust, Go, Python, PowerShell.

El marketplace de plugins Herdr en `herdr.dev/plugins` no es un catálogo que alguien haya revisado. Es un índice automático de repositorios públicos de GitHub con tag `herdr-plugin`, refrescado cada 30 minutos. Los forks, repos archivados y repos cuyos manifiestos no parsean quedan excluidos. Todo lo demás aparece.

<Notice type="warning" title="Sin sandbox, sin revisión">
  Los docs oficiales lo dicen claro: "Un plugin es código ordinario que corre en tu máquina." Herdr valida los campos del manifiesto y nada más. "No revisa ni hace sandbox del código de plugins." Un plugin corre como tu usuario, con tus variables de entorno y tu acceso CLI completo. Auditar es tu trabajo, y el checklist de abajo es la mitigación.
</Notice>

![Diagrama de arquitectura de plugins Herdr: secciones del manifiesto, comandos argv, variables de entorno de runtime inyectadas, y callbacks a través de la CLI herdr](@assets/images/26/10/herdr-plugin-anatomy.webp)

El manifiesto es el contrato. Los campos requeridos son `id`, `name`, `version` y `min_herdr_version` (la API de plugins existe desde herdr 0.7.0, y Herdr se niega a instalar un plugin que exige un binario más nuevo que el que corres). Las secciones opcionales cubren las partes interesantes: `[[build]]` compila cosas en instalaciones desde GitHub, `[[startup]]` corre un init de un disparo tras la restauración de sesión y se re-ejecuta en handoff en vivo, `[[actions]]` son comandos con nombre que puedes invocar o enlazar a teclas, `[[events]]` disparan en cosas como `on = "worktree.created"`, `[[panes]]` colocan una UI (overlay por defecto, o `popup`, `split`, `tab`, `zoomed`), y `[[link_handlers]]` convierten Ctrl+clic en una URL en una acción vía una regex de Rust.

En runtime Herdr inyecta `HERDR_SOCKET_PATH`, `HERDR_BIN_PATH`, `HERDR_ENV=1`, `HERDR_PLUGIN_ID`, `HERDR_PLUGIN_ROOT`, `HERDR_PLUGIN_CONFIG_DIR`, `HERDR_PLUGIN_STATE_DIR`, y `HERDR_PLUGIN_CONTEXT_JSON`. Recuerda una regla sobre esas rutas: `HERDR_PLUGIN_ROOT` es un checkout gestionado que una reinstalación reemplaza. Nunca guardes credenciales ahí. Los directorios de config y estado son tuyos.

La escala importa para cómo navegas. La página de topics de GitHub lista unos 1.500 repositorios públicos al 08-10-2026, y ese conteo incluye colecciones de dotfiles y herramientas cross-etiquetadas de otros ecosistemas. El índice curado en herdr.dev muestra solo repos con manifiestos parseables en la rama por defecto, lo que pone el marketplace real en aproximadamente 1.000+ entradas. El descubrimiento es o el índice o la búsqueda de topics de GitHub, del mismo modo que navegarías [top AI GitHub repos que vale la pena estrellar](/top-ai-github-repos/) y filtrarías fuerte.

## Cómo instalar plugins Herdr de forma segura

Instalar plugins Herdr es un comando. Instalarlos sin arrepentirte lleva cinco minutos de lectura primero. El flujo de operador es: prerequisitos, auditar (el checklist completo es su propia sección abajo), instalar con preview, fijar la revisión que revisaste, verificar, y conocer la ruta de rollback.

### Prerequisitos (lo que necesitas)

Herdr 0.7.0 o más nuevo, porque ahí aterrizó la API de plugins. Los plugins individuales pueden exigir más: herdr-reviewr necesita >= 0.7.5, y el instalador de herdr-web-ui espera 0.9.0+. Git, porque `plugin install` clona un repositorio. Y el toolchain con el que el plugin compila: node o bun para plugins TypeScript, Go para la gente herdr-plus y tsk, cargo para las TUIs Rust. Herdr no instala toolchains por ti. Un `cargo` ausente aparece como un paso de build fallido que aborta el registro.

<ListCheck>
  <ul>
    <li>herdr >= 0.7.0, confirmado con `herdr --version`</li>
    <li>git en PATH (la instalación clona el repo)</li>
    <li>el toolchain con el que compila tu elección: node/bun, go, o cargo</li>
    <li>5 minutos para leer el `herdr-plugin.toml` del repo antes de instalar</li>
  </ul>
</ListCheck>

### Instala con preview, fija una revisión

1. Navega el índice en https://herdr.dev/plugins o busca en GitHub `topic:herdr-plugin`.
2. Abre el repo y lee `herdr-plugin.toml` antes que cualquier otra cosa. Si los comandos se ven mal, para ahí.
3. Corre `herdr plugin install owner/repo[/subdir]`. En un terminal interactivo Herdr muestra un preview de la fuente y los comandos que está a punto de correr. Léelo. **Nunca pases `--yes` en una primera instalación.**
4. Fija lo que revisaste: `herdr plugin install owner/repo --ref v1.2.0`. El fijado es tu ancla de rollback.
5. Los comandos de build corren solo en instalaciones desde GitHub. Un fallo de build aborta el registro, y editar el manifiesto tras el preview aborta la instalación. Ambas son funciones. Para desarrollo local, `herdr plugin link /path` registra un directorio y se salta los builds por completo.

```bash
# install with the interactive preview
herdr plugin install persiyanov/herdr-reviewr

# install the exact revision you reviewed
herdr plugin install persiyanov/herdr-reviewr --ref v1.2.0

# local development: register a directory, no build step
herdr plugin link /home/you/src/my-herdr-plugin
```

<Notice type="info" title="No hay comando de actualización de plugins">
  El plugin v1 no tiene `herdr plugin update`. "Actualizar" significa re-correr `herdr plugin install owner/repo` (opcionalmente con un nuevo `--ref`), y eso **reemplaza el checkout gestionado**. Todo lo que dejaras en `HERDR_PLUGIN_ROOT` se borra. Mantén secretos y ajustes en `HERDR_PLUGIN_CONFIG_DIR`, que sobrevive reinstalaciones y desinstalaciones.
</Notice>

### Verifica que funcionó

Tras cada instalación, confirma el registro y una primera ejecución limpia:

```bash
herdr plugin list --json                      # registered + enabled, with ids
herdr plugin action list --plugin plugin.id   # what actions exist
herdr plugin action invoke plugin.id.action   # run one once
herdr plugin log list --plugin plugin.id --limit 20
```

Abre el pane o la acción del plugin una vez y espera salida normal en los logs con código de salida 0. Cómo se ve "roto": el plugin ausente de `plugin list`, una salida no-cero en `plugin log list`, o una acción que se cuelga porque falta su toolchain o un archivo de config.

Para enlazar una acción a una tecla, añádela a `~/.config/herdr/config.toml` y recarga:

```toml
[[keys.command]]
key = "prefix+l"
type = "plugin_action"
command = "example.layout.apply"
description = "apply layout"
```

```bash
herdr server reload-config
```

### Rollback / deshacer

```bash
herdr plugin disable ID        # keep it, stop it running
herdr plugin enable ID
herdr plugin uninstall ID      # removes the managed checkout
herdr plugin unlink ID         # local dev deregistration
```

`uninstall` elimina el checkout gestionado pero deja los directorios de config y estado en su sitio, que es tu ruta de recuperación si desinstalas por error. Dos rarezas a conocer: instalar sobre un plugin enlazado es rechazado, así que `unlink` primero; y en 0.7.3, los plugins registrados solo dentro de una sesión con nombre necesitan re-enlazarse o reinstalarse.

Modos de fallo en esta sección: un abort de build con stdout/stderr capado es casi siempre un `cargo`/`npm`/`go` ausente, instala el toolchain y reintenta. Una instalación rechazada sobre un directorio local significa que chocaste con la regla de plugins enlazados. Un abort tras el preview significa que el manifiesto cambió entre preview y confirmación, que es Herdr negándose a correr código que no viste.

### Revisa el diff del agente (herdr-reviewr)

`persiyanov/herdr-reviewr` (804 estrellas) abre el diff del agente en un panel de terminal y envía comentarios de línea de vuelta a Claude Code, Codex, OpenCode y Pi. Rust, con binarios precompilados así que no hay paso cargo en la instalación. Quiere herdr >= 0.7.5 y corre en macOS y Linux. Cierra la brecha que importa una vez que un agente escribe código: la que hay entre "escribió código" y "lo leíste". Este es el caso de uso asesino de los plugins Herdr en general, porque el bucle de revisión vive junto al agente en vez de en una pestaña de navegador que olvidas mirar.

```bash
herdr plugin install persiyanov/herdr-reviewr
```

![herdr-reviewr corriendo dentro de la TUI de Herdr: un panel de diff git con un comentario de línea encolado para enviar de vuelta al agente](@assets/images/26/10/herdr-reviewr-ui.webp)

Nota de confianza: superficie Rust pequeña, el manifiesto declara las acciones y panes habituales, sin sorpresas en los arrays de comandos más allá del propio binario de revisión. Verifica abriendo el pane de revisión una vez en un repo con cambios sin commit y confirmando que el diff renderiza, luego deja un comentario de línea de prueba y míralo llegar al input del agente. Cómo se ve "roto": un pane de diff vacío en un working tree sucio, que suele significar que el plugin no está apuntando a la pestaña de workspace correcta.

Si quieres algo más ligero, `jhochenbaum/herdr-hunk-diff` (143 estrellas) hace revisión por hunks con comentarios inline y menos piezas móviles. Instálalo igual: `herdr plugin install jhochenbaum/herdr-hunk-diff`. `plannotator/herdr-annotate` es el primo anota-cualquier-cosa si tu bucle de feedback es sobre texto de terminal en general, no solo diffs.

### Mira qué tocó el agente (herdr-file-viewer)

`smarzban/herdr-file-viewer` (636 estrellas) es una TUI de árbol de archivos consciente de git y solo-lectura: árbol más contenido, diffs de working tree, markdown renderizado, resaltado de sintaxis. Solo-lectura es una función cuando el agente es quien escribe archivos. Tú miras, él escribe, y no puedes meter la pata editando en el visor.

```bash
herdr plugin install smarzban/herdr-file-viewer
```

![herdr-file-viewer a pantalla completa: árbol de archivos a la izquierda, contenido de archivo renderizado con resaltado de sintaxis a la derecha](@assets/images/26/10/herdr-file-viewer-ui.webp)

Nota de confianza: plugin de capa de presentación, la parte arriesgada es lo que ejecute para leer el estado de git. Verifica abriendo el pane de árbol y confirmando que el diff del working tree muestra el último cambio del agente. Si el árbol renderiza pero los diffs quedan vacíos, comprueba que abriste el pane en la misma pestaña de workspace que el repo; el plugin lee el estado git del contexto de su propio pane.

Si quieres un explorador estilo VS Code con capacidad de escritura en su lugar, `alexarthurs/herdr-sidebar` (424 estrellas) te da explorador de archivos, source control de git, diffs, y mensajes de commit con IA. Nota la diferencia antes de instalar: puede cambiar tu repo, herdr-file-viewer no.

![alexarthurs/herdr-sidebar: explorador de archivos, panel de source control, y panes de agente dentro de la barra lateral de Herdr](@assets/images/26/10/herdr-sidebar-ui.webp)

El coste de tokens es la factura real en un stack de agentes. Los plugins solo lo observan, pero observarlo es la diferencia entre un fin de semana divertido y una factura sorpresa.

### Inicialización de workspace y navegación (herdr-plus, herdr-auto-title, herdr-navigator)

`cloudmanic/herdr-plus` (345 estrellas) es el único plugin aquí con su propio sitio web por una razón. Projects reconstruye un workspace entero desde un único archivo TOML que posees: pestañas, divisiones, comandos de arranque. Quick Actions es un launcher difuso que funciona en cualquier pestaña, con archivos de acciones `.herdr-plus/` por repo. Binario Go, docs propios en herdrplus.com, tap de Homebrew si lo quieres así.

```bash
herdr plugin install cloudmanic/herdr-plus
```

![selector de Projects de herdr-plus: una lista difusa de workspaces agrupados por proyecto, abierta sobre un pane](@assets/images/26/10/herdr-plus-projects.webp)

El sitio anuncia teclas por defecto en prefix + up/down tras el binding. Confirma el binding en `~/.config/herdr/config.toml` si no responde, luego `herdr server reload-config`. Verifica definiendo un TOML de proyecto de dos pestañas, reiniciando, y confirmando que el layout vuelve. La parte "TOML que posees" es lo que me vendió este: sin estado oculto, sin base de datos, el layout vive en un archivo que puedes commitear a tus dotfiles y editar a mano a las 2 de la mañana cuando un pane está en el sitio equivocado.

`kryptamine/herdr-auto-title` (238 estrellas) auto-nombra pestañas y panes desde la rama git, la actividad del terminal y las sesiones de Claude Code. A 10+ panes esto no es un detalle, es cómo encuentras cualquier cosa.

```bash
herdr plugin install kryptamine/herdr-auto-title
```

![herdr-auto-title: barra de pestañas con nombres generados como claude-1:oauth y títulos de rama-git en vez de números de pane genéricos](@assets/images/26/10/herdr-auto-title-ui.webp)

`thanhdat77/herdr-navigator` (178 estrellas) es un navegador difuso único para workspaces, agentes, proyectos, remotos y directorios. Si ya vives en un saltador difuso como [navegación de terminal más inteligente con zoxide](/zoxide/), es la misma memoria muscular aplicada al modelo de objetos de Herdr.

```bash
herdr plugin install thanhdat77/herdr-navigator
```

![popup del buscador difuso de herdr-navigator emparejando workspaces, agentes, proyectos y directorios sobre un pane en vivo](@assets/images/26/10/herdr-navigator-fuzzy.webp)

Una mención para los auditores: `qu8n/herdr-automatic-rename` (209 estrellas) es el gemelo en Shell puro de auto-title y probablemente el plugin más fácil de leer de extremo a extremo de todo este artículo. Buen candidato a "primer plugin que auditas".

### Recuperación de crashes y gestión de plugins (herdr-resurrect, herdr-plugin-manager)

`ntindle/herdr-resurrect` (37 estrellas) es tmux-resurrect para herdr: hace snapshots de workspaces, pestañas, panes, cwd, programas y agentes, y los restaura tras un crash o reinicio. El conteo de estrellas es bajo, el valor no. Perder una granja de agentes de 12 panes por un reinicio es una mala tarde. Los snapshots se disparan en los eventos que el plugin declara y restauran a través de la misma CLI herdr que todo lo demás usa, así que no hay daemon separado que cuidar.

```bash
herdr plugin install ntindle/herdr-resurrect
```

`speardragon/herdr-plugin-manager` (51 estrellas) gestiona plugins instalados desde un popup: instalar, activar, desinstalar, navegar el marketplace. El binding por defecto es `prefix+p`.

```bash
herdr plugin install speardragon/herdr-plugin-manager
```

![popup de herdr-plugin-manager: lista de plugins instalados con acciones por plugin y un navegador de marketplace ordenado por estrellas](@assets/images/26/10/herdr-plugin-manager.webp)

Trampa: los popups son recursos de sesión singleton. No tienen ID de pane ni eventos de ciclo de vida, y devuelven `ui_busy` si hay un modal de Settings o Copy-mode abierto. Eso es Herdr, no un plugin roto.

Los snapshots no son backups. Versiona tu `config.toml` y el contenido del `HERDR_PLUGIN_CONFIG_DIR` de cada plugin en git o [backups self-hosted con Restic](/pluton-self-hosted-backup/). El propio código del plugin se re-instala desde refs fijados, así que no necesita vivir en tu conjunto de backup.

Alertas push, Tailscale por defecto, sin app store implicada. Es el cliente remoto más popular del espacio de plugins y el que elegiría si la máquina se queda en casa detrás de Tailscale.

```bash
herdr plugin install AltanS/collie
```

## Cómo auditar un plugin Herdr en 5 minutos

![Diagrama de flujo de auditoría para plugins Herdr: repositorio, manifiesto, comandos, scripts, historial del autor, luego fijar e instalar, con salidas de abandono en cada puerta](@assets/images/26/10/herdr-plugin-vetting-flow.webp)

La propia página del marketplace dice "Los listados no están revisados por Herdr, así que instala bajo tu propia discreción." El diálogo de preview interactivo es la única puerta en todo el sistema. Aquí está el checklist que yo corro antes de que ese diálogo aparezca siquiera.

<Notice type="warning" title="El marketplace no es un catálogo">
  herdr.dev/plugins es un índice automático. Nadie en Herdr ha leído estos repos. Cinco minutos de lectura ganan a una mala instalación, y re-auditar solo se necesita cuando mueves el fijado.
</Notice>

1. **Lee `herdr-plugin.toml`.** Cada entrada `[[build]]`, `[[startup]]`, `[[actions]]`, `[[events]]` y `[[link_handlers]]` es código que correrá en tu máquina. Comprueba los campos requeridos (`id`, `name`, `version`, `min_herdr_version`) y lee cada array `command` antes de mirar cualquier otra cosa.
2. **Lee cada comando como argv.** No hay expansión de shell a menos que el comando arranque una shell. Las sorpresas de quoting se esconden en envoltorios `["bash", "-c", "..."]`, no en `["node", "index.js"]`.
3. **Ojeda los scripts.** Cualquier cosa que toque `~/.aws`, `~/.ssh`, archivos `.env`, o directorios de credenciales de agentes merece una lectura completa, no un vistazo. Esa es la diferencia entre un plugin de UI y algo que puede exfiltrar tus tokens.
4. **Comprueba el autor y el historial del repo.** Las estrellas no son confianza, y un topic tag no garantiza que la cosa siquiera se instale como plugin Herdr. Cuentas frescas más pasos de build ofuscados es un abandono. Si quieres una primera auditoría suave, `qu8n/herdr-automatic-rename` y `tdi/herdr-worktree-setup` son pequeños y legibles de extremo a extremo.
5. **Fija el tag que revisaste.** `herdr plugin install owner/repo --ref vX.Y.Z`. Nunca `--yes` en una primera instalación. Si el manifiesto cambia tras el preview, Herdr aborta; déjalo abortado y vuelve a leer.

<ListCheck>
  <ul>
    <li>Lee herdr-plugin.toml, incluyendo cada comando [[startup]] y [[build]]</li>
    <li>Lee comandos como arrays argv; desconfía de envoltorios de shell</li>
    <li>Ojeda scripts, con atención completa en rutas de credenciales</li>
    <li>Comprueba el historial del autor; abandona cuentas frescas con builds ofuscados</li>
    <li>Fija el tag que revisaste; nunca instales a ciegas con --yes</li>
  </ul>
</ListCheck>

Nota de coste: auditar son 5 minutos una vez por plugin. Reinstalar desde un ref fijado es la ruta de actualización, y re-auditar es solo el delta entre el tag viejo y el nuevo. Para plugins de relay remoto específicamente, el modelo de amenaza es tu terminal entera. Si estás exponiendo una máquina en absoluto, lee [endurecer un servidor expuesto](/bsi-security-report-docker-ufw/) antes de exponer un relay.

## Plugins Herdr vs tmux: qué es distinto

La pregunta "Herdr vs tmux" se reduce a plugins más que a panes. Si solo quieres panes y scrollback, tmux sigue bien y seguirá bien en cinco años.

| Capacidad | tmux | Plugins Herdr |
|---|---|---|
| Distribución de plugins | Copiar scripts de shell al territorio `.tmux.conf` | `herdr plugin install owner/repo` desde un índice de marketplace |
| Definición de plugin | Funciones de shell ad hoc | Manifiesto `herdr-plugin.toml` con build/startup/actions/events/panes |
| Superficie de API | Comandos tmux | La CLI herdr entera vía `HERDR_BIN_PATH` |
| Eventos | Hooks que cableas tú mismo | `[[events]]` declarativos como `on = "worktree.created"` |
| Manejo de URLs | Manual | `[[link_handlers]]` con regex Rust, dispatch por Ctrl+clic |
| Sandboxing | Ninguno | Ninguno |
| Canal de actualización | Lo que diga el README del plugin | Ninguno en v1, reinstala para refrescar |
| Proceso de revisión | Ninguno | Ninguno, es un índice automático |

Lo que Herdr te da: comandos argv declarados en manifiesto, eventos, colocación de panes, link handlers, e integración de keybindings en `~/.config/herdr/config.toml`. Lo que no te da: sandboxing, almacenamiento gestionado (el estado duradero son los propios archivos del plugin), un canal de actualización, o cualquier proceso de revisión. La escena de plugins de tmux es más pequeña y más tonta, y esa es también su historia de seguridad.

Mi veredicto: el ecosistema de plugins es la razón para moverte cuando corres CLIs de agentes, no la parte de multiplexor. tmux ya multiplexa. La ventaja de Herdr es que los flujos de agente como revisión de diffs, grafos de sesión y bootstrap de workspace están a un comando en vez de un fin de semana de scripts. Si tu montaje de tmux ya es una pila de shell a medida y corres agentes en él a diario, migrar vale un fin de semana. Si mayormente corres dos shells y un log tail, tmux tiene menos piezas móviles y nada que auditar. Para la comparación del runtime en sí, mira [nuestra reseña de Herdr (multiplexor de agentes open-source)](/herdr-agent-multiplexer/), que cubre la pregunta de tmux en profundidad. Y si lo que realmente compras es el multiplexor en sí más que la capa de agente, [Superlogical Rex](/superlogical-rex/) es la nueva opción del lado del terminal que vale la pena seguir.

## Gotchas que nadie te cuenta

Estas son las cosas que te morderán en el primer mes.

1. **No hay comando `plugin update`.** Actualizar significa re-correr `herdr plugin install`, que reemplaza el checkout gestionado. Todo lo que esté en `HERDR_PLUGIN_ROOT` se ha ido. Mantén secretos y ajustes en `HERDR_PLUGIN_CONFIG_DIR` y puedes reinstalar a voluntad.
2. **Las colisiones de nombres son reales.** Hay dos repos `herdr-auto-title` (kryptamine 238 estrellas vs sh1ma 51 estrellas), dos repos `herdr-agent-usage` (levi-qiao 168 estrellas vs senna-lang 47 estrellas), y al menos tres plugins estilo navegador (`ogulcancelik/herdr-browser` 357 estrellas, StructuPath 23 estrellas, más `zenbu-labs/terminal-browser`). Arreglo: usa siempre `plugin.id.action` completamente calificado, y anota el `owner/repo` que instalaste.
3. **Licencias ausentes.** `herdr-remote` y `herdr-mobile-relay` muestran ambos NOASSERTION. `pi-extensible-workflows` no tiene campo de licencia en absoluto. No construyas sobre estos en nada por lo que te paguen sin una licencia con la que puedas vivir.
4. **`ui_busy` en popups.** Los popups son recursos de sesión singleton sin ID de pane y sin eventos de pane. Un modal de Settings o Copy-mode los bloquea. Si el popup de un plugin "no hace nada", cierra tus modales primero.
5. **Colisiones de keybinding.** Las entradas `[[keys.command]]` pueden ensombrecer el keymap integrado. Elige teclas sin usar y corre `herdr server reload-config` tras cada edición, o nada cambia y culparás al plugin.
6. **Los hooks de startup no son daemons.** `[[startup]]` es init de un disparo que se re-ejecuta en handoff en vivo. Un plugin que lo abuse como supervisor se portará mal. Si escribes uno, haz el hook idempotente.
7. **Los fallos de build abortan la instalación** con stdout y stderr capados. Casi siempre un toolchain ausente. Instala `cargo`/`npm`/`go`, reintenta, y lee el log capado.
8. **Churn de API 0.7.x.** Este ecosistema tiene meses. Fija refs, espera subidas de `min_herdr_version`, y trata cada reinstalación como una oportunidad de re-leer el diff del manifiesto.

<Notice type="warning" title="El conteo de estrellas no es confianza">
  Los plugins populares siguen llegando con colisiones de nombres, licencias NOASSERTION y rarezas de popups. Las estrellas te dicen qué instaló otra gente, no qué corre seguro en tu entorno. Emparéjalas con la auditoría de 5 minutos y refs fijados, y espera que la API 0.7.x se mueva debajo de ti.
</Notice>

## Escribe tu propio plugin en 20 líneas

La mayor parte de lo que hacen los plugins es: correr un comando, mostrar un pane, llamar a la CLI herdr de vuelta. Aquí hay un manifiesto mínimo.

```toml
# herdr-plugin.toml
id = "example.workspace-tools"
name = "Workspace Tools"
version = "0.1.0"
min_herdr_version = "0.7.0"
platforms = ["linux", "macos", "windows"]

[[actions]]
id = "list-workspaces"
title = "List workspaces"
contexts = ["workspace"]
command = ["node", "index.js"]
```

Y el patrón de callback. La CLI entera es la API:

```javascript
// index.js
const { spawnSync } = require("node:child_process");
const herdr = process.env.HERDR_BIN_PATH ?? "herdr";

const res = spawnSync(herdr, ["workspace", "list"], { encoding: "utf8" });
console.log(res.stdout);
```

Bucle de desarrollo local:

```bash
herdr plugin link /abs/path/to/plugin   # register, no build commands run
herdr plugin action invoke example.workspace-tools.list-workspaces
herdr plugin log list --plugin example.workspace-tools --limit 20
herdr plugin unlink example.workspace-tools
```

Dónde va el estado: `HERDR_PLUGIN_CONFIG_DIR` para ajustes y secretos, `HERDR_PLUGIN_STATE_DIR` para estado duradero. No hay API de almacenamiento gestionado en v1, así que el plugin escribe sus propios archivos. Y nunca escribas en `HERDR_PLUGIN_ROOT`; la reinstalación lo reemplaza.

Plugins versus skills, ya que la gente los confunde: los plugins extienden el runtime del terminal (panes, eventos, keybindings). Las skills extienden el contexto del agente (instrucciones que el modelo carga). Capa distinta, archivo distinto, problema distinto. Si el problema es "el agente no sabe hacer X", eso es una skill, y [Agent Skills comparadas](/best-ai-skills-for-web-design/) es la lectura correcta.

<Button text="Navega los ejemplos oficiales de plugins" link="https://github.com/ogulcancelik/herdr-plugin-examples" variant="outline" color="gray" size="sm" />

Los docs de Herdr usan ese cookbook para ejemplos de instalación, con la advertencia de que Herdr no mantiene esos plugins. Trátalos como muestras legibles, no código bendecido.

## FAQ: plugins Herdr

<Accordion label="¿Son seguros de instalar los plugins Herdr?" group="faq" expanded="true">
  Son código sin revisar corriendo como tu usuario. Herdr valida el manifiesto y no hace sandbox de nada. La mitigación es el checklist de auditoría de 5 minutos (manifiesto, comandos, scripts, historial del autor) más instalar con el diálogo de preview y fijar el tag que revisaste. Nunca pases `--yes` en una primera instalación. Si sigues eso, el riesgo residual es el riesgo open-source normal en vez de confianza ciega.
</Accordion>

<Accordion label="¿Cómo actualizo plugins Herdr?" group="faq">
  No hay `herdr plugin update` en plugin v1. Re-corre `herdr plugin install owner/repo` (opcionalmente con un nuevo `--ref`) y Herdr reemplaza el checkout gestionado. Mantén ajustes y secretos en `HERDR_PLUGIN_CONFIG_DIR`, nunca en `HERDR_PLUGIN_ROOT`, y las reinstalaciones se vuelven indoloras. Re-audita el diff cuando muevas el fijado.
</Accordion>

<Accordion label="¿Cuántos plugins hay en el marketplace de plugins Herdr?" group="faq">
  Aproximadamente 1.000+ plugins indexados en herdr.dev/plugins, contra unos 1.500 repositorios con tag `herdr-plugin` en GitHub (conteo de topic, 08-10-2026). El conteo crudo de topic incluye dotfiles y herramientas cross-etiquetadas; el índice curado solo muestra repos con manifiestos parseables. Ambos números se mueven rápido en un ecosistema de 7 meses, así que re-comprueba el índice en vivo cuando leas esto.
</Accordion>

<Accordion label="¿Funcionan los plugins Herdr con Claude Code, Codex y OpenCode?" group="faq">

Las mejores elecciones de este artículo soportan explícitamente Claude Code, Codex, OpenCode y Pi: herdr-reviewr envía comentarios de línea a los cuatro, zoetrope grafica sesiones de Claude Code y Codex, y collie los conduce desde tu teléfono. Si un plugin solo nombra un agente en su README, es una elección de documentación en la mayoría de casos; lo que importa es si lee el pane y la transcripción, y los comandos del manifiesto te lo dirán.
</Accordion>
