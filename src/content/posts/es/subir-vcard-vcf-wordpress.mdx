No puedes subir archivos vCard (.vcf) a WordPress sin un pequeño ajuste. WordPress bloquea la extensión en la biblioteca de medios y la subida muere con «Sorry, this file type is not permitted for security reasons».

Hay una trampa que pilla a la gente en el WordPress actual: la solución son dos filtros pequeños, no uno. El núcleo valida el tipo MIME real del archivo con fileinfo de PHP, y muchos servidores reportan algo distinto de `text/vcard` para un archivo .vcf perfectamente válido. El viejo fragmento de un solo filtro falla silenciosamente en ese caso. Los dos filtros están en el Método 2.

Mi opción por defecto para un solo tipo de archivo es el fragmento de código. Son unas 20 líneas, no tiene dependencias que vigilar y no se romperá cuando el autor de un plugin se desentienda. Elige el plugin si prefieres no tocar código.

<Notice type="warning" title="Nota de seguridad">
Una vCard es texto plano (RFC 6350) y no ejecuta nada por sí misma. Los riesgos reales: un payload malicioso renombrado a .vcf (exactamente lo que detecta la comprobación de MIME real del núcleo, y lo que la lista de permitidos alternativa del fragmento de abajo relaja ligeramente), campos o enlaces hostiles dirigidos a bugs en apps de contactos, y usuarios con pocos privilegios alojando archivos en tu dominio de confianza. Habilita la subida solo desde fuentes de confianza y vigila quién tiene permisos de subida.
</Notice>

## Por qué WordPress bloquea las subidas de vCard (VCF)

WordPress mantiene una lista fija de tipos permitidos en `wp_get_mime_types()`, y vCard no está en ella. Comprobé la lista contra la versión estable actual (7.1.4, noviembre de 2026): cero entradas `vcf` o `vcard`. La extensión falla la primera comprobación y el archivo nunca llega al almacenamiento.

Para tipos que no son imagen hay una segunda puerta. `wp_check_filetype_and_ext()` ejecuta `finfo_file()` de PHP sobre el archivo real y compara el tipo MIME reportado con el esperado. Cuando las reglas de comparación del núcleo rechazan el par, WordPress anula el tipo y obtienes el mismo error de «not permitted» aunque `upload_mimes` esté parcheado. Esa segunda puerta es la razón por la que la mitad de los fragmentos que circulan por ahí no funcionan.

### Comprueba qué reporta tu servidor para los archivos .vcf (diagnóstico con finfo/file)

Antes de elegir una solución, averigua qué cree tu servidor que es un archivo .vcf. Ejecuta esto en el servidor web, o en cualquier máquina con las mismas versiones de PHP y libmagic:

```bash
file --mime-type contact.vcf
php -r '$f = new finfo(FILEINFO_MIME_TYPE); echo $f->file("contact.vcf"), "\n";'
```

Luego compara la salida:

| finfo reporta | Qué funciona |
|---|---|
| `text/vcard` (Debian/Ubuntu actuales) | solo el filtro `upload_mimes` |
| `text/x-vcard` (libmagic antigua, algunos hostings compartidos) | el fragmento de dos filtros o el plugin |
| `text/plain` (bases de datos MIME recortadas) | el fragmento de dos filtros o el plugin |
| `application/octet-stream` (contenedores mínimos, algunas builds de PHP en Windows) | el fragmento de dos filtros o el plugin |

Los sistemas modernos de la familia Debian reportan `text/vcard` y mapean `text/vcard vcf vcard` en `/etc/mime.types`. Cualquier otra cosa en esa tabla y deberías saltarte la versión de un filtro e ir directamente al Método 2.

## Método 1: permitir subidas de vCard con un plugin

Instala [Enable virtual card upload (vcf,vcard)](https://wordpress.org/plugins/enable-virtual-card-upload-vcardvcf/) (gratis, v2.3.1, más de 7.000 instalaciones activas, probado hasta WordPress 6.9.1). Tras activarlo, **Medios → Añadir nuevo** acepta archivos .vcf y .vcard, de uno en uno o en lote.

El plugin conecta los mismos dos filtros que incluye este artículo en el Método 2. La entrada del changelog de la 2.3.1 dice «Fixed upload compatibility with modern WordPress MIME validation for vcf/vcard files», que es exactamente el problema de `wp_check_filetype_and_ext`. La reseña de una estrella de 2023 es anterior a esa corrección.

Una advertencia honesta: es un plugin de un solo mantenedor, y su «probado hasta» (6.9.1) va por detrás del núcleo actual (7.1.4). Las dos APIs del núcleo que usa han sido estables durante años, así que valoro el riesgo como bajo, pero es una dependencia que aceptas.

## Método 2: permitir subidas de vCard con un fragmento de código

Antes de editar `functions.php`, [haz una copia de seguridad de tu sitio con un plugin gratuito de backups](/es/mejores-plugins-gratuitos-backup-wordpress/). Luego añade esto al `functions.php` de tu child theme, o gestiónalo sin editar archivos del tema con [FluentSnippets](https://wordpress.org/plugins/easy-code-manager/) (WPManageNinja, +50.000 instalaciones, probado hasta 7.1.4):

<Button text="Conseguir FluentSnippets (gratis)" link="https://wordpress.org/plugins/easy-code-manager/" variant="outline" color="purple" size="sm" />

```php
// 1) Allow the extensions (as before)
add_filter('upload_mimes', function ($m) {
    $m['vcf']   = 'text/vcard';
    $m['vcard'] = 'text/vcard';
    return $m;
});

// 2) Pass WordPress real-MIME validation for vCard variants
add_filter('wp_check_filetype_and_ext', function ($data, $file, $filename, $mimes, $real_mime = false) {
    $ext = strtolower(pathinfo($filename, PATHINFO_EXTENSION));
    if (!in_array($ext, ['vcf', 'vcard'], true)) return $data;
    if (!empty($data['ext']) && !empty($data['type'])) return $data; // already validated
    $allowed = ['text/vcard', 'text/x-vcard', 'text/plain', 'application/octet-stream'];
    if (!empty($real_mime) && !in_array(strtolower($real_mime), $allowed, true)) return $data;
    $data['ext']  = $ext;
    $data['type'] = 'text/vcard';
    $data['proper_filename'] = $data['proper_filename'] ?? false;
    return $data;
}, 10, 5);
```

Si usas FluentSnippets, configura el fragmento para que se ejecute solo en el área de administración. Ahí es donde WordPress comprueba los tipos MIME durante la subida. Misma familia de plugins si más tarde necesitas correo saliente: [envía emails de WordPress con FluentSMTP](/es/enviar-emails-wordpress-zoho-smtp-fluentsmtp/).

<Picture formats={["webp"]} fallbackFormat="webp" src={imgVcardAllow} alt="Fragmento de código de FluentSnippets para permitir la subida de vCard en la administración de WordPress" />

Ve a **Medios → Añadir nuevo** y sube el archivo .vcf. El éxito se ve como el archivo en la biblioteca de medios con una URL de adjunto normal. El fallo sigue siendo «Sorry, this file type is not permitted for security reasons», lo que significa que tu servidor reporta un tipo MIME real que el segundo filtro no permite. Ejecuta el comando finfo de arriba y compruébalo.

### Por qué el fragmento necesita un segundo filtro (wp_check_filetype_and_ext)

Esto es lo que hace el núcleo en `wp_check_filetype_and_ext()` (misma lógica en la etiqueta 6.6 y en el trunk actual, así que no es un comportamiento nuevo):

1. Mapea la extensión a MIME con `wp_check_filetype()`. Aquí es donde ayuda el filtro `upload_mimes`.
2. Para archivos que no son imagen, ejecuta `finfo_file()` sobre el contenido real.
3. Compara bajo tres reglas: la mayoría de los tipos deben coincidir exactamente, así que `text/x-vcard` falla contra el `text/vcard` esperado. `text/plain` solo pasa cuando el tipo esperado está en una lista corta de permitidos que no incluye `text/vcard`. Los tipos inespecíficos como `application/octet-stream` solo pasan para expectativas `application/*`, `video/*` o `audio/*`, y una expectativa `text/*` los rechaza.

<Image src={imgMimePipeline} alt="Diagrama de flujo de la validación MIME de WordPress para subidas de vCard y dónde interviene cada filtro" />

Con solo el primer filtro instalado, tres de los cuatro resultados de finfo acaban en «rechazado». El segundo filtro se ejecuta después de la comprobación del núcleo, ve una extensión .vcf o .vcard y, cuando el MIME real es uno de `text/vcard`, `text/x-vcard`, `text/plain` o `application/octet-stream`, marca el archivo como `text/vcard`. Está limitado a esas dos extensiones, así que no debilita la validación para nada más. El plugin hace el mismo trabajo en su archivo principal.

## Servir archivos .vcf con el tipo MIME correcto (nginx y Apache)

Subir el archivo es la mitad del trabajo. El servidor web decide el `Content-Type` de la URL de descarga, y esa cabecera es lo que le dice a un teléfono si debe abrir Contactos o simplemente guardar un archivo genérico. Esta sección necesita acceso al servidor, así que aplica si autoalojas WordPress en un VPS (por ejemplo un [VPS de Hetzner Cloud](https://go.bitdoze.com/hetzner)) o si [instalas WordPress en Ubuntu con CloudPanel](/es/instalar-wordpress-ubuntu-arm/). En un hosting gestionado sin SSH puede que no puedas cambiarlo; salta a resolución de problemas en ese caso.

nginx no trae mapeo de .vcf en su `conf/mime.types` de serie, así que los archivos salen como `application/octet-stream`. Apache en Debian/Ubuntu modernos lo hace bien de fábrica (`text/vcard vcf vcard` en `/etc/mime.types`), pero una línea explícita no hace daño.

<Tabs>
<Tab name="nginx">

Añade esto dentro de tu bloque `server { }`, o en la config del vhost de tu proxy inverso si ejecutas [WordPress instalado con Docker Compose](/es/instalar-wordpress-docker/):

```nginx
location ~* \.(vcf|vcard)$ {
    default_type text/vcard;
    # opcional: forzar la descarga en lugar de manejo en línea
    # add_header Content-Disposition 'attachment; filename="contact.vcf"' always;
}
```

Prueba y recarga:

```bash
nginx -t && systemctl reload nginx
```

</Tab>
<Tab name="Apache">

Añade esto a `.htaccess` o a la config del vhost:

```apache
AddType text/vcard .vcf .vcard
```

Prueba y recarga:

```bash
apachectl configtest && systemctl reload apache2
```

</Tab>
</Tabs>

<Notice type="warning" title="Trampa de nginx">
No metas un bloque `types { }` en un contexto `server` o `location` para añadir un solo tipo. En nginx eso reemplaza todo el mapa MIME, y todos los demás tipos de archivo empiezan a servirse con Content-Type incorrectos. Usa `default_type` en un bloque location en su lugar.
</Notice>

Verifica desde tu máquina:

```bash
curl -sI https://example.com/wp-content/uploads/2026/11/contact.vcf | grep -i content-type
# quieres: text/vcard  (application/octet-stream es tolerable; text/html es una señal de alarma)
```

## Mostrar el enlace de descarga de la vCard en WordPress

Obtén la URL del archivo desde la biblioteca de medios: haz clic en el archivo y copia el campo **URL del archivo**. El enlace de descarga más simple:

```html
<a href="https://example.com/wp-content/uploads/2026/11/contact.vcf" download="contact.vcf">Download contact card</a>
```

El atributo `download` funciona porque las subidas son del mismo origen. Si necesitas un elemento button en su lugar:

```html
<button onclick="window.location.href='https://example.com/wp-content/uploads/2026/11/contact.vcf'">Download vCard</button>
```

O sáltate el HTML por completo. En el editor de bloques, inserta el bloque **Archivo** y genera un botón de descarga por ti, lo cual es cómodo cuando [trabajas con bloques de Gutenberg](/es/crear-bloque-fijo-gutenberg/) y quieres la tarjeta en línea con el contenido.

## Verifica que la subida y la descarga funcionan (curl + importación en dispositivo)

Repasa esta checklist antes de darlo por terminado:

<ListCheck>
<ul>
<li>El archivo .vcf aparece en **Medios → Biblioteca** con una URL que funciona</li>
<li>`curl -sI` sobre la URL devuelve `Content-Type: text/vcard` (o al menos no `text/html`)</li>
<li>El archivo se descarga en un navegador sin un 404 ni una extensión `.html` forzada</li>
<li>La tarjeta se importa en al menos una app de contactos en un dispositivo real (Apple Contacts, Google Contacts, Outlook, lo que use tu audiencia)</li>
</ul>
</ListCheck>

La importación en dispositivo es la prueba que importa. Las comprobaciones de cabeceras te dicen que el servidor está configurado; solo un teléfono confirma que el pase de la tarjeta funciona de punta a punta. Prueba en las plataformas que usan tus visitantes.

## Deshacer los cambios (rollback)

Cada pieza se revierte de forma independiente:

- Fragmento: borra los dos filtros de FluentSnippets o de `functions.php`. Las nuevas subidas de vCard volverán a bloquearse, que es lo esperado y está bien.
- Plugin: desactiva el plugin Enable virtual card upload.
- nginx: quita el bloque `location` y ejecuta `nginx -t && systemctl reload nginx`.
- Apache: quita la línea `AddType` y ejecuta `apachectl configtest && systemctl reload apache2`.
- `ALLOW_UNFILTERED_UPLOADS`: si alguna vez lo definiste en `wp-config.php`, quítalo ahora.

Verifica el rollback: `curl -sI` sobre un archivo existente sigue devolviendo 200 (quitar el mapeo MIME solo cambia el Content-Type), y una subida nueva es rechazada con el habitual error «not permitted».

## Resolución de problemas con la subida de vCard

Si sigues viendo «This file type is not permitted for security reasons», recorre la tabla de arriba abajo. La primera fila es el caso que pilla a la mayoría.

| Síntoma | Causa probable | Solución |
|---|---|---|
| Fragmento o plugin activo, sigue «This file type is not permitted for security reasons» | El MIME real no coincide (ver la sección del segundo filtro) | Ejecuta el comando finfo; usa el fragmento de dos filtros o el plugin v2.3.1+ |
| Funciona en el sitio único, bloqueado en un subsitio | Ajuste de red multisitio | Ver la sección de multisitio más abajo |
| Bloqueado solo mientras un plugin de seguridad está activo | Reglas de subida dentro del plugin de seguridad | Revisa sus ajustes de subida de archivos; permite .vcf si mantiene una lista de extensiones |
| Rechazado en un hosting gestionado, funciona en otros sitios | Algunos hostings gestionados sobrescriben los ajustes MIME a nivel de servidor | Pide a soporte que permita `text/vcard`. Si no quieren, los [proveedores de hosting PHP en la nube](/es/alojamiento-cloud-php/) que te dan acceso al servidor son la solución más limpia |
| `file --mime-type` no reporta nada sensato | Base de datos MIME recortada | El fragmento de dos filtros lo maneja; para eso está la lista de permitidos |
| La subida funciona, el enlace da 404 | Caché de CDN de `wp-content/uploads` | Ver la siguiente sección |

<Notice type="error" title="Solo como último recurso">
`define('ALLOW_UNFILTERED_UPLOADS', true);` en `wp-config.php` desactiva todas las comprobaciones de tipo de archivo para cualquiera que tenga la capacidad. Un admin podría subir un payload .php con eso activo, y en multisitio solo ayuda a los super administradores de todas formas. Orden de operaciones: (1) el ajuste de dos filtros, (2) soporte del hosting y ajustes del plugin de seguridad, (3) solo entonces esta constante. Si la usas, defínela, sube tu archivo y quítala inmediatamente. Nunca la dejes definida.
</Notice>

### La subida funciona pero el enlace da 404 (CDN/enlaces permanentes)

Subida bien, descarga rota: normalmente un CDN o una regla de página cacheando `wp-content/uploads` y sirviendo un 404 viejo, o una estructura de enlaces permanentes que necesita un flush. Si sirves las subidas a través de un CDN como [Bunny.net CDN](https://go.bitdoze.com/bunny) o Cloudflare, purga la caché de esa ruta o excluye `wp-content/uploads` de las reglas de página agresivas (detalles en esta [configuración de caché con Cloudflare y Varnish](/es/acelerar-wordpress-cloudflare-varnish-redis/)). Luego vuelve a guardar **Ajustes → Enlaces permanentes** una vez. Verifica con `curl -sI` sobre la URL exacta: quieres un 200 tras la purga.

### Multisitio: añade vcf a upload_filetypes

En multisitio, el administrador de la red controla los tipos de archivo permitidos en **Administración de la red → Ajustes → Tipos de archivo de subida** (guardado en la opción de red `upload_filetypes`). Añade `vcf` a la lista separada por comas y guarda. Ojo al matiz de capacidades: `ALLOW_UNFILTERED_UPLOADS` en multisitio concede `unfiltered_upload` solo a super administradores, así que la constante no es un rodeo para administradores de sitio normales.

## ¿Qué debes saber sobre consideraciones de seguridad?

Quién puede subir importa más que qué suben. Las subidas están limitadas por la capacidad `upload_files`, rol Autor en adelante por defecto. Si el punto de la vCard es que los visitantes la descarguen, solo Editores y Administradores necesitan permisos de subida. Ya que estás reforzando los accesos, [securiza los inicios de sesión de WordPress con autenticación de dos factores gratis](/es/securizar-wordpress-2fa/).

Un compromiso a tener en cuenta: la lista de permitidos del segundo filtro con `text/plain` y `application/octet-stream` relaja ligeramente la detección de payloads renombrados del núcleo para archivos con nombre .vcf. Para la mayoría de los sitios es un precio aceptable a cambio de subidas que funcionan en cualquier servidor. No des permisos de subida a roles en los que no confíes.

## Preguntas frecuentes

<Accordion label="¿Por qué WordPress bloquea los archivos .vcf en primer lugar?" group="faq" expanded="true">
WordPress trae una lista fija de tipos MIME permitidos en `wp_get_mime_types()`, y vCard no está en ella (sigue siendo así en 7.1.4). La denegación por defecto en las subidas es deliberada: cualquier cosa que falte en la lista falla la comprobación de extensión, así que tipos de archivo arbitrarios no pueden acabar en el directorio de subidas sin una activación explícita como esta.
</Accordion>

<Accordion label="¿Es text/x-vcard lo mismo que text/vcard?" group="faq">
Misma familia de formato, etiqueta distinta. RFC 6350 define `text/vcard` como el tipo oficial; `text/x-vcard` es la grafía antigua que reportan versiones viejas de libmagic. WordPress compara las cadenas exactamente, así que la diferencia por sí sola dispara el rechazo. Por eso el segundo filtro y el plugin permiten ambas grafías.
</Accordion>

<Accordion label="¿Pueden los visitantes del front-end subir vCards?" group="faq">
No con esta guía. Las subidas a la biblioteca de medios requieren la capacidad `upload_files` (rol Autor o superior por defecto), así que esto es un flujo de usuarios con sesión iniciada. Un formulario de subida público es un problema distinto: la validación del front-end, el almacenamiento y los controles de abuso corren por tu cuenta. No uses `ALLOW_UNFILTERED_UPLOADS` para hacer funcionar un formulario público.
</Accordion>

<Accordion label="¿Necesito los dos filtros?" group="faq">
No siempre. Si el comando finfo reporta exactamente `text/vcard`, el filtro `upload_mimes` por sí solo pasa la validación del núcleo. El segundo filtro no hace nada cuando el núcleo ya aceptó el archivo, así que instalar ambos es el valor seguro por defecto cuando no quieres hacer el diagnóstico.
</Accordion>

Diagnostica primero con el comando finfo y luego elige el camino: el plugin para cero código, el fragmento de dos filtros para una solución sin dependencias. Para un solo tipo de archivo yo sigo prefiriendo el fragmento. Si la subida sigue fallando después de todo esto, la tabla de resolución de problemas y las preguntas frecuentes cubren las peculiaridades de servidor que vale la pena revisar.
