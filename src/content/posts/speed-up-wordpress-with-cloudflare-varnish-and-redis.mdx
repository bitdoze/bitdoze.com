## How the three-layer WordPress caching stack works

Each layer handles a different type of request:

1. **Cloudflare**: visitors hit Cloudflare first. If the page is cached on their CDN, it's served from the nearest edge node without touching your server.
2. **Varnish**: if the page isn't in Cloudflare's cache (first visit, post-publish, dynamic content), the request hits Varnish on your server. Varnish serves the cached HTML without running PHP.
3. **Redis**: when Varnish needs to generate a fresh page, PHP talks to Redis for object and query caching instead of hitting MySQL repeatedly.

On a full cache miss, the request falls all the way through to PHP-FPM, which reads objects from Redis and only queries MySQL on Redis misses. The result is fast loads for returning visitors and manageable server load during traffic spikes.

## Plugins needed

Three free plugins wire WordPress to the stack.

<Notice type="warning" title="Don't stack page-cache plugins">
Super Page Cache's own docs say to disable page caching in WP Rocket, LiteSpeed Cache, and W3 Total Cache before activating it. It's safe alongside Optimole, Autoptimize, Perfmatters, and ShortPixel. Also note that Super Page Cache now does disk caching and claims Varnish auto-purge. Running it next to CLP Varnish Cache means two plugins may try to purge the same layer. See the purge-ownership note in Troubleshooting below.
</Notice>

### CLP Varnish Cache

Purges CloudPanel's Varnish when content changes. This is the plugin CloudPanel's own docs recommend for WordPress. It works out of the box. Once activated, it exposes cache settings and purge actions in wp-admin and handles automatic purging when you publish or update content.

- [CLP Varnish Cache on wordpress.org](https://wordpress.org/plugins/clp-varnish-cache/)

### Redis Object Cache

Connects WordPress to Redis for object and query caching. After activating, go to **Settings → Redis** and click **Enable Object Cache**. The plugin drops an `object-cache.php` file into `wp-content/` and WordPress starts storing transients, queries, and objects in Redis instead of the options table.

There's a paid tier called Object Cache Pro with cache analytics and WooCommerce-specific optimizations, but the free version handles most sites fine. If you run a heavy WooCommerce store with lots of concurrent shoppers, it's worth a look.

- [Redis Object Cache on wordpress.org](https://wordpress.org/plugins/redis-cache/)

### Super Page Cache for Cloudflare

Full name on wordpress.org: **Super Page Cache - Cloudflare Cache, Page Speed & Core Web Vitals**. Backed by Themeisle, this plugin bridges WordPress to Cloudflare's Cache Rules and purges the edge cache automatically on publish. It also bundles disk caching, lazy loading, unused CSS/JS removal, database optimization, and cache preloading. For this guide we only use the Cloudflare cache and purge features.

<Notice type="info" title="Disable the extras you don't need">
Super Page Cache v5 does a lot more than Cloudflare bridging. If you already have a separate optimization plugin for lazy loading or asset minification, turn off those features inside Super Page Cache to avoid conflicts. The Cloudflare cache + purge integration is all you need from it here.
</Notice>

- [Super Page Cache on wordpress.org](https://wordpress.org/plugins/wp-cloudflare-page-cache/)


## Varnish setup in CloudPanel

Enable Varnish for your site in CloudPanel:

1. Go to **CloudPanel → your site → Settings → Varnish Cache** and enable it.
2. Confirm the site still loads after enabling.
3. The CLP Varnish Cache plugin handles automatic purging when you publish or update content.

<Picture formats={["webp"]} fallbackFormat="webp" src={imgVarnish} alt="CloudPanel Varnish cache settings for a WordPress site" />

For operators who want to go deeper into VCL tuning, cache tag prefixes, and excluded params, see the [CloudPanel Varnish Cache setup guide](/cloudpanel-varnish-cache/).

Where things live on the server: the VCL config is at `/etc/varnish/default.vcl` (run `varnishreload` after edits), the service unit is at `/lib/systemd/system/varnish.service`, and Varnish listens on port 6081 for purge requests.

## Cloudflare setup with Super Page Cache

Walk through the Super Page Cache settings in wp-admin. The exact labels shift between plugin versions, but the flow is:

1. **Create a scoped Cloudflare API token** (not the Global API key) with **Zone.Cache Purge** and **Zone.Settings Read** permissions for your domain. Scoping limits blast radius if the key ever leaks.

<Notice type="info" title="Use an API token, not the Global API key">
A scoped token can only purge cache and read settings for one zone. The Global API key gives full account access. Always prefer the token.
</Notice>

2. Paste the token into Super Page Cache settings and select your domain from the zone list.
3. Enable page caching. The plugin drives Cloudflare Cache Rules. It's not the old "Standard mode" toggle from pre-v5 versions.
4. Confirm the plugin reports that cache rules were created successfully.
5. Set bypass rules for dynamic pages (cart, checkout, my-account). Details are in the next section.

On publish, the plugin purges the Cloudflare copy of the changed page automatically.

## How to verify each caching layer

Before you trust any cache setup, measure it. [Benchmark your VPS with YABS](/benchmark-cloud-servers/) or at least note your current load times so you can compare after. Then check each layer with a single command.

<ListCheck>
<ul>
<li>Cloudflare: `cf-cache-status: HIT` on the second request</li>
<li>Varnish: `x-cache-age` header present and climbing</li>
<li>Redis: Settings → Redis shows "Connected" and `redis-cli ping` returns `PONG`</li>
</ul>
</ListCheck>

### Check Cloudflare cache headers

Run this from your local machine (or from a private browser window):

```bash
curl -sI https://example.com | grep -iE 'cf-cache-status|x-wp-cf-super-cache'
```

Expected output on a cached page:

```
cf-cache-status: HIT
x-wp-cf-super-cache: cache
x-wp-cf-super-cache-active: 1
```

What the values mean: `HIT` means the page was served from Cloudflare's edge, which is what you want. `MISS` means first request or an expired cache. Load the page again and it should become `HIT`. `BYPASS` means a rule excluded the page. That is not necessarily an error, but check your bypass rules if you didn't expect it. `EXPIRED` means the cached copy is stale and Cloudflare is revalidating. `DYNAMIC` means not cached, which is usually correct for dynamic pages.

`x-wp-cf-super-cache: cache` means the plugin is caching this page. `x-wp-cf-super-cache-active: 1` means the page landed in Cloudflare's cache.

### Check Varnish cache headers

CloudPanel's PHP controller emits `x-cache-age`, `x-cache-lifetime`, and `x-cache-tags` headers on cached pages:

```bash
curl -sI https://example.com | grep -iE 'x-cache-age|x-cache-tags'
```

Expected output:

```
x-cache-age: 3
x-cache-tags: aac6
```

Repeat the request and confirm `x-cache-age` climbs (4, 5, 6…). If it resets to 0 every time, the page isn't being cached by Varnish. Check your excludes.

Manual purge smoke test (from the server):

```bash
curl -v -X PURGE -H 'X-Cache-Tags: aac6' 127.0.0.1:6081
```

Replace `aac6` with the actual tag from your `x-cache-tags` header. Then re-request the page and confirm it re-caches (x-cache-age resets and starts climbing again).

### Check Redis object cache

Three quick checks:

1. In wp-admin, open **Settings → Redis**. It shows "Connected" with hit/miss metrics after enabling.
2. At the OS level, run `redis-cli ping`. It should return `PONG`.
3. The drop-in file `wp-content/object-cache.php` should exist.

If Settings → Redis shows a connection error, the usual cause is a wrong PHP socket path or port. Check your PHP version's Redis config in CloudPanel and compare with the Redis server's listen address.

## Dynamic content and cache bypass rules

This stack works well for mostly static content: blog posts, landing pages, product pages that don't change per user. Anything per-user must be excluded from **both** cache layers.

<Notice type="warning" title="Never cache carts, checkouts, or logged-in pages">
Serving cached pages to logged-in users means one customer sees another customer's cart, account details, or session data. This is the most common and most damaging cache misconfiguration.
</Notice>

On the Varnish side, add these regex **Excludes** in CloudPanel's Varnish settings (straight from the CloudPanel docs):

```
^/my-account/
/cart/
wp-login.php
```

Also use the **Excluded Params** field for GET parameters that should never be cached (e.g. `__SID`).

On the Cloudflare side, add matching bypass rules for the same paths in Super Page Cache. The plugin also has a per-page metabox to exclude individual pages from caching.

For deeper Varnish configuration (cache tag prefixes, PHP controller behavior), see the [CloudPanel Varnish developer docs](https://www.cloudpanel.io/docs/v2/frontend-area/varnish-cache/developer-guide/php-controller/).

## Troubleshooting common cache problems

### Logged-in users see stale pages

Super Page Cache appends a `swcfpc` cache-buster query var to internal links while logged in. If editors see stale content, that's usually why. The cache-buster forces a fresh load, but if a custom role bypasses the plugin's logged-in detection, the bypass doesn't trigger.

Fix: confirm the plugin's logged-in bypass is active and add the page to exclusions if a custom role isn't being detected.

### WooCommerce and membership page excludes

Symptom: cart contents shared between visitors, checkout breakage, or account pages showing wrong data.

Fix: apply the regex excludes from the previous section in CloudPanel Varnish settings (`^/my-account/`, `/cart/`, `wp-login.php`) plus matching Cloudflare exclusions in Super Page Cache. Both layers need the same excludes. Fixing only one leaves the other layer serving stale dynamic pages.

### Raising Varnish memory past 512MB

CloudPanel's Varnish default is only `-s malloc,512m`. On multi-site servers or sites with large page counts, that fills up fast and you'll see eviction churn.

Edit the service unit:

```bash
sudo nano /lib/systemd/system/varnish.service
```

Change `-s malloc,512m` to something like `-s malloc,2048m`, then:

```bash
sudo systemctl daemon-reload && sudo systemctl restart varnish
```

RAM budget note: Varnish malloc + Redis + PHP-FPM share your VPS memory. A 4 GB box is comfortable for this stack; 2 GB is tight and you'll need to keep Varnish at 512 MB or swap aggressively. This ties into the "upgrade to a bigger VPS" advice below.

### Cache not purging on publish

Symptom: you update a post but visitors still see the old version.

Checklist:
1. CLP Varnish Cache plugin is active.
2. No other optimization plugin owns purging. Disable page caching in WP Rocket / LiteSpeed Cache / W3 Total Cache (Super Page Cache's own requirement).
3. Manual purge works: `curl -X PURGE -H 'X-Cache-Tags: <tag>' 127.0.0.1:6081` (see verify section).
4. Cloudflare purge happens via Super Page Cache. Check its status/log page.

<Notice type="error" title="One purge owner per layer">
CLP Varnish Cache owns the Varnish purge (tag-based on :6081). Super Page Cache owns the Cloudflare purge (Cache Rules API). If Super Page Cache's Varnish auto-purge conflicts with CLP's tag-based purge on CloudPanel, disable one of them. Two plugins purging the same layer leads to race conditions and phantom cache misses.
</Notice>

### Where things live on the server

| Component | Path / detail |
|---|---|
| Varnish service unit | `/lib/systemd/system/varnish.service` (listen :6081) |
| VCL config | `/etc/varnish/default.vcl` (run `varnishreload` after edits) |
| PHP controller | `/home/$siteUser/.varnish-cache/controller.php` (injected via `auto_prepend_file`) |
| Redis drop-in | `wp-content/object-cache.php` |
| Purge port | 6081 (Varnish, tag-based PURGE) |

The PHP controller is what sets `X-Cache-*` headers and runs purges. Its source lives at [github.com/cloudpanel-io/varnish-controllers](https://github.com/cloudpanel-io/varnish-controllers/).

Before running Super Page Cache's database optimization features (revision cleanup, OPTIMIZE TABLE), make sure you have working backups. See [free WordPress backup plugins](/best-free-wordpress-backup-plugins/) if you don't have a backup strategy yet.

### How to roll back or disable a layer

Safe teardown in reverse order:

1. **Cloudflare layer**: disable page cache in Super Page Cache (or purge and disable the Cache Rules it created).
2. **Varnish layer**: turn off Varnish Cache in CloudPanel site settings.
3. **Redis layer**: go to Settings → Redis and click Disable Object Cache. That removes the drop-in. Optionally stop the Redis service.

Confirm with the same `curl -sI` checks from the verify section. The `cf-cache-status` and `x-cache-age` headers should disappear. Disabling a cache layer does not touch your content, so it is safe to do at any point.

## Cloudflare APO vs Super Page Cache (free alternative)

Cloudflare APO (Automatic Platform Optimization) costs $5/month per domain on the Free plan and caches HTML at Cloudflare's edge. The Super Page Cache plugin does roughly the same thing for free using Cloudflare's Cache Rules API.

<Notice type="info" title="APO needs the official Cloudflare plugin">
APO requires the official [Cloudflare WordPress plugin](https://developers.cloudflare.com/automatic-platform-optimization/), a different plugin from Super Page Cache. Don't install both and expect them to cooperate. Pick one path.
</Notice>

Pricing as of late 2026:

| Path | Monthly cost | What you get |
|---|---|---|
| This guide's stack (Cloudflare Free + Super Page Cache + CloudPanel Varnish/Redis) | **$0** | Edge cache + full-page cache + object cache |
| Cloudflare APO (Free plan) | **$5/mo per domain** | Edge HTML cache, no page-cache plugin needed |
| Cloudflare Pro | **$20/mo annual / $25 monthly** | APO included + Pro features |

The only real cost is the VPS itself. See my [Hetzner Cloud review](/hetzner-cloud-review/) for what I run this stack on.

Decision rule: if you're on the free Cloudflare plan, use Super Page Cache. If you're already paying for Cloudflare Pro, APO is included, so use it and skip the extra plugin. For most solo operators on a budget, the free path wins.

## When this stack isn't enough

This three-layer setup handles most WordPress sites well. If you're still hitting performance walls, the next steps in order:

- **Upgrade to a bigger VPS.** More CPU cores help with uncached/dynamic requests. Check [ARM vs x86 VPS benchmarks for WordPress](/arm-vs-x86-vps-server-benchmarks/) before buying. ARM boxes often give more cores per euro. If you're switching providers, the [DigitalOcean vs Vultr vs Hetzner comparison](/digitalocean-vs-vultr-vs-hetzner/) covers the trade-offs.

- **Switch to a purpose-built caching plugin** like FlyingPress for more aggressive page optimization. Skip LiteSpeed Cache on CloudPanel. It only helps on LiteSpeed servers, and CloudPanel runs NGINX.
- **Look at Object Cache Pro** if you run WooCommerce with heavy database load. The cache analytics and WooCommerce-specific optimizations help identify slow queries.

If you'd rather not operate a VPS at all, move to managed WordPress hosting like [Cloudways](https://go.bitdoze.com/cloudways) and let them handle the caching stack.

## FAQ

<Accordion label="Do I need all three layers?" group="faq" expanded="true">
No, but each layer covers a different gap. Cloudflare handles global edge caching, Varnish covers your server's full-page cache for requests that miss the edge, and Redis speeds up PHP object/query reads. You could run just Cloudflare + Redis and skip Varnish, but then every edge miss hits PHP directly. On a budget VPS under real traffic, all three layers earn their keep.
</Accordion>

<Accordion label="Does this stack work with WooCommerce?" group="faq">
Yes, with the cache bypass rules from the dynamic content section applied. Exclude `/cart/`, `^/my-account/`, `wp-login.php`, and checkout pages from both Varnish and Cloudflare caching. Product and category pages cache fine and see the biggest gains. For heavy stores, Object Cache Pro adds WooCommerce-specific Redis optimizations.
</Accordion>

<Accordion label="Does this work without CloudPanel?" group="faq">
The concepts do. Cloudflare + Varnish + Redis is a standard stack. But the specific setup in this guide (CLP Varnish Cache plugin, CloudPanel's Varnish settings UI, the PHP controller that sets X-Cache headers) is CloudPanel-specific. On a different panel or bare NGINX, you'd configure Varnish and Redis manually and use different purge plugins.
</Accordion>

<Accordion label="Is Super Page Cache really as good as APO?" group="faq">
For most sites, yes. Both cache full pages on Cloudflare's edge and purge on publish. APO uses Workers and KV storage; Super Page Cache uses Cache Rules. The plugin's own FAQ claims it offers more features than APO for free-plan users. The one scenario where APO wins is if you're already on Cloudflare Pro, since it's included and you skip a plugin. See the [verify section](#how-to-verify-each-caching-layer) to confirm either approach is caching your pages.
</Accordion>
