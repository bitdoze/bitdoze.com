It sends alerts via email, Slack, Discord, Telegram, and 90+ other channels when something goes down, and it keeps a history of response times so you can spot what's been slow. Five command blocks to get running. Full explanations and verify steps below.

**1. Install Docker:**

```bash
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /usr/share/keyrings/docker-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/docker-archive-keyring.gpg] https://download.docker.com/linux/ubuntu $(lsb_release -cs) stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt update && sudo apt install docker-ce docker-ce-cli containerd.io docker-compose-plugin -y
```

**2. Write the compose file:**

```bash
mkdir -p /docker-vol/uptime-kuma /opt/uptime-kuma && cd /opt/uptime-kuma
cat > docker-compose.yml << 'EOF'
services:
  uptime-kuma:
    image: louislam/uptime-kuma:2
    container_name: uptime-kuma
    volumes:
      - /docker-vol/uptime-kuma:/app/data
    ports:
      - 8001:3001
    restart: unless-stopped
    security_opt:
      - no-new-privileges:true
EOF
```

**3. Start it:**

```bash
docker compose up -d
```

**4. Nginx reverse proxy:**

```bash
sudo apt install nginx -y
sudo tee /etc/nginx/sites-available/uptime-kuma.conf > /dev/null << 'EOF'
server {
    listen 80;
    server_name your_domain_here;
    location / {
        proxy_set_header   X-Real-IP $remote_addr;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header   Host $host;
        proxy_pass         http://localhost:8001;
        proxy_http_version 1.1;
        proxy_set_header   Upgrade $http_upgrade;
        proxy_set_header   Connection "upgrade";
    }
}
EOF
sudo ln -s /etc/nginx/sites-available/uptime-kuma.conf /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

**5. SSL with Certbot:**

```bash
sudo apt install certbot python3-certbot-nginx -y
sudo certbot --nginx -d your_domain_here
```

## Why Uptime Kuma

Uptime Kuma monitors HTTP(s), HTTP(s) keyword and JSON query checks, TCP ports, Ping, DNS records, Docker containers, Steam game servers, push (inbound webhook) monitors, WebSocket endpoints, SNMP/SNMPv3 devices, domain expiry via RDAP, SFTP, NTP, and OracleDB. That's a lot of coverage from one container.

On the notification side it pushes alerts through 90+ services: Telegram, Discord, Slack, Gotify, SMTP, WhatsApp, Plivo SMS, Jira Service Management, Google Sheets, and plenty more. It ships with a fast status-page UI (multiple status pages, incident history, incidents RSS), Prometheus metrics, proxy support, and multi-language options. All free and self-hosted.

If you also want server-level metrics (CPU, RAM, disk, Docker stats) alongside uptime checks, you can run Beszel alongside Uptime Kuma for full server monitoring.

Compared to SaaS options like Uptime Robot or BetterStack, self hosted monitoring with Uptime Kuma gives you unlimited monitors, unlimited history, and no monthly bill. The trade-off is you operate it yourself: updates, backups, and uptime of the monitor are your problem. For a solo operator running a handful of sites on a VPS already, that trade is worth it.

## 2. Install Uptime Kuma on Ubuntu

Everything from here is copy-pasteable on a fresh Ubuntu VPS.

### 2.1 Update the system and install Nginx

```bash
sudo apt update && sudo apt upgrade -y
sudo reboot
sudo apt install nginx git -y
```

**Verify:** `systemctl status nginx` shows `active (running)` and `curl -I http://localhost` returns HTTP 200.

### 2.2 Install Docker and Docker Compose

Follow the [official Docker install guide](https://docs.docker.com/engine/install/ubuntu/) or run:

```bash
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /usr/share/keyrings/docker-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/docker-archive-keyring.gpg] https://download.docker.com/linux/ubuntu $(lsb_release -cs) stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt update
sudo apt install docker-ce docker-ce-cli containerd.io docker-compose-plugin -y
```

> **Note:** The current recommended way is the `docker-compose-plugin` (v2). Use `docker compose` (no hyphen) going forward.

If you're on ARM (Oracle Ampere, Raspberry Pi), see how to [install Docker and Docker Compose on Ubuntu ARM](/install-docker-ubuntu-arm/). The repo lines differ slightly.

**Verify:**

```bash
docker --version && docker compose version
docker run --rm hello-world
```

If `hello-world` doesn't pull and run, the Docker daemon isn't running or the apt repo didn't register. Re-run the `gpg --dearmor` step and check that `lsb_release -cs` matches your Ubuntu codename.

### 2.3 Create directories and write a compose file

```bash
mkdir -p /docker-vol/uptime-kuma
mkdir -p /opt/uptime-kuma
cd /opt/uptime-kuma
```

Create `docker-compose.yml`:

```yaml
services:
  uptime-kuma:
    image: louislam/uptime-kuma:2
    # Use louislam/uptime-kuma:2-slim for a smaller image (no MariaDB/Chromium)
    container_name: uptime-kuma
    volumes:
      - /docker-vol/uptime-kuma:/app/data
    ports:
      - 8001:3001
    restart: unless-stopped
    security_opt:
      - no-new-privileges:true
```

<Notice type="warning" title="Do not use NFS or network mounts for /app/data">
The official wiki explicitly warns that NFS and similar network filesystems are NOT supported. SQLite requires POSIX file locks which NFS doesn't provide correctly. Map <code>/app/data</code> to a local directory or Docker volume only.
</Notice>

<Notice type="warning" title="Do not use the :latest tag">
The <code>latest</code> tag is deprecated and still points to v1. Always pin to <code>:2</code> to stay on the v2 branch and avoid unexpected breaking changes when v3 eventually releases.
</Notice>

Pick an image variant depending on your needs:

<Tabs>
<Tab name="Full (default)">
<code>louislam/uptime-kuma:2</code>: ~590MB. Includes embedded MariaDB (for large deployments) and embedded Chromium (for the Browser Engine monitor). Use this unless you know you don't need those.
</Tab>
<Tab name="Slim">
<code>louislam/uptime-kuma:2-slim</code>: ~176MB. Drops embedded MariaDB and Chromium. Fine for HTTP, TCP, DNS, and keyword checks with external notifications. That saves disk and pull time on a small VPS.
</Tab>
<Tab name="Rootless">
<code>louislam/uptime-kuma:2-rootless</code> or <code>2-slim-rootless</code>: runs as <code>node:node</code> (1000:1000) instead of root. Better security practice for shared servers. Make sure the data directory is owned by 1000:1000 before starting. The Docker container monitor needs extra socket config on rootless images.
</Tab>
</Tabs>

For Raspberry Pi or other low-power hardware, add `UPTIME_KUMA_SQLITE_SINGLE_CONNECTION=true` as an environment variable to avoid SQLite locking issues.

If you'd rather skip the manual compose file entirely, you can [deploy Uptime Kuma in one click with Coolify](/deploy-uptime-kuma/). And if you want a web UI to manage the compose stack going forward, [manage this compose stack with Dockge](/dockge-install/).

Start the container:

```bash
docker compose up -d
```

**Verify:**

```bash
docker compose ps          # Container should show "Up"
docker compose logs -f     # Check for startup errors (Ctrl+C to exit)
curl -I http://localhost:8001   # Should return HTTP response
```

If port 8001 is already in use, check with `ss -tlnp | grep 8001` and change the host port in compose (e.g. `8002:3001`). Then update the Nginx `proxy_pass` to match.

### 2.4 Open the firewall for Nginx

```bash
sudo ufw allow "Nginx Full"
sudo ufw enable
```

**Verify:** `sudo ufw status` shows `Nginx Full` as ALLOW.

<Notice type="warning" title="Docker bypasses UFW">
Published container ports bypass UFW rules. Docker manipulates iptables directly. That's why the compose file maps 8001 on the host. Once the reverse proxy works, you can tighten this to <code>127.0.0.1:8001:3001</code> in the compose file so the port is only reachable from localhost. See [how Docker interacts with UFW rules](/docker-bypasses-firewall/) for details.
</Notice>

### 2.5 Configure Nginx as a reverse proxy

Create `/etc/nginx/sites-available/uptime-kuma.conf` and paste:

```nginx
server {
    listen 80;
    server_name your_domain_here;

    location / {
        proxy_set_header   X-Real-IP $remote_addr;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header   Host $host;
        proxy_pass         http://localhost:8001;
        proxy_http_version 1.1;
        proxy_set_header   Upgrade $http_upgrade;
        proxy_set_header   Connection "upgrade";
    }
}
```

The `Upgrade` and `Connection "upgrade"` headers are mandatory. Uptime Kuma's UI communicates over WebSocket. Without these headers the page loads but the dashboard hangs or shows a "WebSocket error". This is the number one reverse-proxy failure for Uptime Kuma.

Enable the site and reload Nginx:

```bash
sudo ln -s /etc/nginx/sites-available/uptime-kuma.conf /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx
```

**Verify:** `sudo nginx -t` returns `syntax is ok`, and `curl -I http://your_domain_here` returns a response from Nginx (not "connection refused").

If you prefer a GUI over hand-written Nginx, you can [set up CloudPanel as a reverse proxy instead](/cloudpanel-setup-dockge/).

<Notice type="info" title="Enable Trust Proxy">
Once the site is live, go to Settings → Reverse Proxy → HTTP Headers in the Uptime Kuma UI and enable <strong>Trust Proxy</strong>. Without it, client IPs in the logs will show the Nginx server IP instead of the real visitor IP.
</Notice>

## 3. Point your domain to the server

Log in to your DNS provider and add an **A record** pointing your domain or subdomain to the VPS IP address.

**Verify:** before running Certbot, confirm DNS has propagated:

```bash
dig +short your_domain_here
```

This must return your VPS IP. If it doesn't, wait. Certbot will fail if DNS hasn't propagated.

## 4. Add an SSL certificate with Let's Encrypt

Install Certbot and generate a certificate:

```bash
sudo apt install certbot python3-certbot-nginx -y
sudo certbot --nginx -d your_domain_here
```

Certbot patches the Nginx config automatically and sets up auto-renewal. Your site will be available over HTTPS right away.

**Verify:**

```bash
certbot renew --dry-run
```

This should complete without errors. Open `https://your_domain_here` in a browser and confirm the padlock shows.

If Certbot times out or returns "connection refused", port 80 isn't reachable. Check your firewall (§2.4) and DNS propagation (§3). If you're hosting multiple services on the same box and want a wildcard certificate instead, [set up a free Let's Encrypt wildcard certificate with Traefik](/traefik-wildcard-certificate/).

<Notice type="info" title="Your dashboard is now internet-exposed">
Enable 2FA right away (covered in §5) and consider hardening the server with CrowdSec: [secure the VPS with CrowdSec](/crowdsec-secure-server/) for ongoing protection against brute-force and exploit scans.
</Notice>

## 5. Set up your first monitor

On first login you create an admin account. Before adding monitors, go to Settings → Security and enable **2FA**. This dashboard is internet-exposed and holds credentials for your notification channels. Treat it accordingly.

Then add a monitor: set the type to HTTP(s), give it a friendly name, and set the heartbeat interval to 300 seconds. Checking every 5 minutes is enough for most sites. The minimum interval is 20 seconds, and since 2.5.0 there's no upper cap on intervals (previously 24 days).

## How to Update Uptime Kuma

Updating is one command sequence. The `:2` tag floats to the latest 2.x patch on pull:

```bash
cd /opt/uptime-kuma
docker compose pull
docker compose up -d --force-recreate
```

**Verify:** `docker compose logs` shows a clean startup, and the version in the UI footer matches the expected release.

Before pulling in production, check the [GitHub release notes](https://github.com/louislam/uptime-kuma/releases) for breaking changes, and back up your data directory first (next section). If the container won't start after an update, check the release notes for migration steps and restore from backup if needed.

## Back up Uptime Kuma data

The v1 backup/restore JSON feature is gone in v2. The only supported backup method is copying the `data` directory. One command:

```bash
tar -czf /backups/kuma-$(date +%F).tar.gz /docker-vol/uptime-kuma
```

Schedule it daily with cron:

```bash
# crontab -e
0 3 * * * tar -czf /backups/kuma-$(date +\%F).tar.gz /docker-vol/uptime-kuma
```

To restore: stop the container, untar to the same path, and start again:

```bash
cd /opt/uptime-kuma && docker compose down
tar -xzf /backups/kuma-2026-11-13.tar.gz -C /
docker compose up -d
```

<ListCheck>
<ul>
<li>Create a tar archive of <code>/docker-vol/uptime-kuma</code></li>
<li>Verify the archive (<code>tar -tzf kuma-*.tar.gz | head</code>)</li>
<li>Copy the tarball off the box to S3-compatible storage, another host, anywhere that isn't the same dying disk</li>
<li>Test a restore once so you know the process works</li>
</ul>
</ListCheck>

A backup on the same disk isn't a backup. Push the tarball to S3-compatible storage or another host. Backups cost nothing but discipline; the offsite copy is the one non-negotiable step.

## Troubleshooting Uptime Kuma

If the dashboard won't load or alerts don't fire, it's almost always one of these.

<Accordion label="WebSocket error / UI hangs behind Nginx" group="troubleshooting">
Missing <code>Upgrade</code> and <code>Connection "upgrade"</code> headers in the Nginx config. This is the number one reverse-proxy issue. The correct block:

```nginx
proxy_http_version 1.1;
proxy_set_header   Upgrade $http_upgrade;
proxy_set_header   Connection "upgrade";
```

Reload Nginx after fixing (<code>sudo nginx -t && sudo systemctl reload nginx</code>).
</Accordion>

<Accordion label="&quot;database is locked&quot; / SQLite errors" group="troubleshooting">
Don't use NFS or network mounts for <code>/app/data</code>. SQLite needs POSIX file locks. On low-power hardware (Raspberry Pi), set <code>UPTIME_KUMA_SQLITE_SINGLE_CONNECTION=true</code>. Also check disk space with <code>df -h</code>. A full disk will lock up SQLite.
</Accordion>

<Accordion label="Subdirectory not supported" group="troubleshooting">
Uptime Kuma requires a dedicated domain or subdomain. Running at <code>example.com/kuma</code> will never work. Use <code>status.example.com</code> instead.
</Accordion>

<Accordion label="Rootless image won't start / Docker monitor missing" group="troubleshooting">
The data directory must be owned by <code>node:node</code> (1000:1000) for rootless images: <code>chown -R 1000:1000 /docker-vol/uptime-kuma</code>. The Docker container monitor requires extra socket configuration on rootless images.
</Accordion>

<Accordion label="Port already in use (8001)" group="troubleshooting">
Check with <code>ss -tlnp | grep 8001</code>. If something else occupies 8001, change the host port in <code>docker-compose.yml</code> (e.g. <code>8002:3001</code>) and update the Nginx <code>proxy_pass</code> to match.
</Accordion>

<Accordion label="Certbot / TLS failures" group="troubleshooting">
Three common causes: DNS not propagated (<code>dig +short your_domain_here</code> must return your VPS IP), port 80 blocked (check <code>sudo ufw status</code>), or a stale symlink in <code>sites-enabled</code>. For renewal issues, run <code>certbot renew --dry-run</code>. Also check you didn't accidentally pull the deprecated <code>latest</code> tag (which is v1). Change to <code>:2</code> and recreate the container.
</Accordion>
