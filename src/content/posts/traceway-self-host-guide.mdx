Observability bills sneak up on you. One day you're logging a few services, the next you're staring at a Datadog invoice that rivals your cloud spend. This guide shows how to **self-host Traceway**, the MIT-licensed **open source observability platform**, as a **free Datadog alternative**. ## What is Traceway?

[Traceway](https://github.com/tracewayapp/traceway) is an open-source observability platform that handles logs, traces, metrics, session replay, exceptions, AI tracing, and more under one roof. It ingests data directly over OTLP/HTTP, so you skip the collector, the vendor SDKs, and the glue code. Point any OpenTelemetry SDK at it, and data starts flowing.

The project sits at about 1,786 stars on GitHub with near-weekly releases since September 2026 (latest as of this writing: `backend/v2.0.16`). It ships under a clean MIT license. No BSL, no "open core" tier that reserves features for paid plans. Every feature is in the box.

<Notice type="info" title="New but functional">
Traceway is a younger project compared to the big names. It's under active development and patches land frequently. Traceway 2.0 was a breaking upgrade with new telemetry tables and changed APIs, which is exactly why you should test upgrades before rolling them out. For production use, keep an eye on releases and read the changelog before pulling.
</Notice>

## Architecture overview

Traceway runs as three main services when deployed standalone:

| Service | Technology | Role |
| --- | --- | --- |
| Backend | Go 1.26, Gin | OTLP ingest, REST API, alerts, migrations |
| Frontend | SvelteKit 2, Svelte 5, Tailwind CSS v4 | Dashboard SPA |
| Database | ClickHouse + PostgreSQL | Telemetry storage (ClickHouse) and relational data (PostgreSQL) |

Everything communicates over the internal Docker network. The backend exposes OTLP/HTTP endpoints for traces, metrics, and logs at `/api/otel/v1/traces`, `/api/otel/v1/metrics`, and `/api/otel/v1/logs`. There's also a blob storage volume (`traceway-storage`) for source maps, session recordings, and AI traces.

```
App (OTel SDK) ──OTLP/HTTP──▶ Backend (Go/Gin)
                                 │
                    ┌────────────┼────────────┐
                    ▼            ▼            ▼
              ClickHouse    PostgreSQL   Blob Storage
              (telemetry)   (relational)  (S3 or volume)
                    │            │            │
                    └────────────┼────────────┘
                                 ▼
                          Frontend (SvelteKit)
```

Traceway is **OTLP/HTTP only, with no gRPC**. This matters more than you'd think. If your SDK silently falls back to gRPC (Python does this by default), every export lands nowhere. Keep this in mind when wiring up instrumentation.

Beyond the standard three-service deployment, Traceway also ships SQLite (single container, zero external DBs), DuckDB (columnar telemetry, zero dependencies), and embedded mode (run inside a Go app via `tracewaybackend.Run(...)`). For a real observability stack, stick with the ClickHouse + PostgreSQL setup below.

## Deploy Traceway with Docker Compose

The current recommended path uses the pre-built `ghcr.io/tracewayapp/traceway:minimal` image. No source build required. If you want to hack on Traceway itself, clone the repo and run `docker compose up --build` instead. For a production deploy, the pre-built image is faster and less failure-prone.

### Step 1: Write the compose file

Create a directory and drop in a `docker-compose.yml`:

```bash
mkdir -p /opt/traceway && cd /opt/traceway
```

```yaml
services:
  traceway:
    image: ghcr.io/tracewayapp/traceway:minimal
    ports: ["80:80"]
    environment:
      CLICKHOUSE_SERVER: "clickhouse:9000"
      CLICKHOUSE_DATABASE: "traceway"
      CLICKHOUSE_USERNAME: "default"
      CLICKHOUSE_PASSWORD: clickhouse
      CLICKHOUSE_TLS: "false"
      POSTGRES_HOST: "postgres"
      POSTGRES_PORT: "5432"
      POSTGRES_DATABASE: "traceway"
      POSTGRES_USERNAME: "traceway"
      POSTGRES_PASSWORD: traceway
      POSTGRES_SSLMODE: "disable"
      JWT_SECRET: change-me-openssl-rand-hex-32   # generate with: openssl rand -hex 32
      # APP_BASE_URL: "https://traceway.example.com"   # set behind a proxy
      # TRUSTED_PROXIES: "172.18.0.0/16"
    volumes:
      - traceway-storage:/app/storage          # source maps, recordings, AI traces
    depends_on:
      clickhouse: { condition: service_healthy }
      postgres:  { condition: service_healthy }
    restart: unless-stopped
  clickhouse:
    image: clickhouse/clickhouse-server:24.8-alpine
    environment: { CLICKHOUSE_DB: traceway, CLICKHOUSE_PASSWORD: clickhouse }
    volumes: [clickhouse-data:/var/lib/clickhouse]
    healthcheck:
      test: ["CMD", "clickhouse-client", "--password", "clickhouse", "--query", "SELECT 1"]
      interval: 5s
      timeout: 3s
      start_period: 10s
      retries: 10
    restart: unless-stopped
  postgres:
    image: postgres:17
    environment: { POSTGRES_USER: traceway, POSTGRES_PASSWORD: traceway, POSTGRES_DB: traceway }
    volumes: [postgres-data:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U traceway"]
      interval: 5s
      timeout: 3s
      start_period: 10s
      retries: 10
    restart: unless-stopped
volumes:
  clickhouse-data: {}
  postgres-data: {}
  traceway-storage: {}
```

<Notice type="warning" title="Set a real JWT_SECRET">
The compose file above ships with a placeholder. Generate a real one before first boot:

```bash
openssl rand -hex 32
```

Paste the output into `JWT_SECRET` and keep it stable. Changing it later invalidates all dashboard sessions and CLI/MCP tokens.
</Notice>

Three named volumes matter here:
- `clickhouse-data`: telemetry (traces, metrics, logs)
- `postgres-data`: projects, users, alert rules
- `traceway-storage`: source maps, session recordings, AI traces. Without it, those files are lost when the container is recreated and symbolication silently stops matching.

If you'd rather use S3-compatible storage instead of the local volume, set `STORAGE_TYPE=s3` along with `S3_BUCKET`, `S3_REGION`, and optionally `S3_ACCESS_KEY`/`S3_SECRET_KEY` (the default AWS credential chain works too). For MinIO or Cloudflare R2, also set `S3_ENDPOINT`.

### Step 2: Start the stack

```bash
docker compose up -d
```

First boot takes a couple of minutes while ClickHouse and PostgreSQL initialize and the backend runs migrations. Migrations are automatic, so you don't need to run them by hand.

Verify the health endpoint:

```bash
curl -s http://localhost/health
```

You should get a `200` response. If you get a connection refused or a 502, the backend is still starting. Wait 30 seconds and try again. Check `docker compose logs traceway` for migration errors or database connection issues.

### Step 3: Register and create your first project

<Notice type="info" title="First boot is /register">
Open `http://your-server-ip/register` to create your first account. There are no seeded default credentials in Docker deployments. The old `admin@localhost.com` / `admin` defaults only apply to embedded mode, not Compose. Set a strong password and store it in your password manager.
</Notice>

Once you're in, create a project. Choose **OpenTelemetry** as the framework. The UI gives you an ingest endpoint and a **project token**. Copy that token. You'll need it for every OTLP export and for the browser SDK.

## Verify it works

Before instrumenting anything, run through this checklist to confirm the stack is healthy:

<ListCheck>

- `curl http://localhost/health` returns `200`
- Dashboard loads in your browser at `http://your-server-ip`
- You registered a user and can log in
- You created a project and copied the project token
- `docker compose logs traceway` shows no repeated errors (occasional warnings about missing env vars are fine on first boot)
- `docker compose ps` shows all three services as `running` or `healthy`

</ListCheck>

If the dashboard loads but OTLP ingestion seems dead, the problem is almost always auth or protocol. Here are the failure modes worth knowing:

| Symptom | Cause | Fix |
| --- | --- | --- |
| OTLP `401` with empty body | Missing or wrong `Authorization: Bearer <project_token>` header | Add the header to every exporter. The value must literally start with `Bearer`. |
| No data appears (Python) | SDK silently defaults to gRPC; Traceway is HTTP-only | Set `OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf` in the environment |
| `413` on OTLP export | Body exceeds 10 MB (compressed or not) | Cap `maxExportBatchSize`. SDK default of 512 spans is safe |
| `503` + `Retry-After` | Ingest saturation | Exporters back off automatically. If persistent, scale ClickHouse or the backend. |
| Empty Logs page | No logging bridge wired | `console.log`/`print` sends nothing. Wire `LoggingHandler` (Python), `slog` handler (Go), or Monolog (PHP). |
| Browser data missing | Using 1.x SDK | Migrate to `@tracewayapp/frontend@2` (see the browser SDK section below) |

<Notice type="error" title="OTLP is HTTP only, no gRPC">
This is the single most common gotcha. Traceway has no gRPC endpoint. If your exporter defaults to gRPC (Python's OTLP exporter does exactly this), data silently disappears. No errors, no warnings, just an empty dashboard. Always set `OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf`.
</Notice>

Once the stack is healthy and you can see the dashboard, it's worth setting up basic monitoring on the box itself. [Monitor your server with Beszel and Uptime Kuma](/beszel-uptime-kuma/) to catch resource problems before they eat your ingest.

## Instrument a Node.js app with OpenTelemetry

Let's wire up a real application so you can see data flowing. The key change from older Traceway guides: every exporter now needs an `Authorization: Bearer` header with your project token.

### Set up a basic Express app

```bash
mkdir traceway-demo && cd traceway-demo
npm init -y
npm install express @opentelemetry/api @opentelemetry/sdk-node \
  @opentelemetry/auto-instrumentations-node \
  @opentelemetry/exporter-trace-otlp-http \
  @opentelemetry/exporter-metrics-otlp-http \
  @opentelemetry/exporter-logs-otlp-http \
  @opentelemetry/sdk-metrics \
  @opentelemetry/sdk-logs \
  @opentelemetry/resources
```

### Wire up OpenTelemetry

Create `telemetry.mjs`:

```javascript
import { register } from "node:module";
register("@opentelemetry/instrumentation/hook.mjs", import.meta.url);
import { NodeSDK } from "@opentelemetry/sdk-node";
import { OTLPTraceExporter } from "@opentelemetry/exporter-trace-otlp-http";
import { OTLPMetricExporter } from "@opentelemetry/exporter-metrics-otlp-http";
import { OTLPLogExporter } from "@opentelemetry/exporter-logs-otlp-http";
import { PeriodicExportingMetricReader } from "@opentelemetry/sdk-metrics";
import { BatchLogRecordProcessor } from "@opentelemetry/sdk-logs";
import { resourceFromAttributes } from "@opentelemetry/resources";
import { getNodeAutoInstrumentations } from "@opentelemetry/auto-instrumentations-node";

const BASE = "http://your-server-ip/api/otel";
const headers = { Authorization: "Bearer your-project-token" };

new NodeSDK({
  resource: resourceFromAttributes({ "service.name": "my-service" }),
  traceExporter: new OTLPTraceExporter({ url: `${BASE}/v1/traces`, headers }),
  metricReaders: [new PeriodicExportingMetricReader({
    exporter: new OTLPMetricExporter({ url: `${BASE}/v1/metrics`, headers }),
    exportIntervalMillis: 30000,
  })],
  logRecordProcessors: [new BatchLogRecordProcessor({
    exporter: new OTLPLogExporter({ url: `${BASE}/v1/logs`, headers }),
  })],
  instrumentations: [getNodeAutoInstrumentations()],
}).start();
```

Replace `your-project-token` with the token you copied from the dashboard. This wires all three signals (traces, metrics, and logs) through a single setup file.

### Create the server

Create `index.js`:

```javascript
const express = require('express');
const app = express();

app.get('/', (req, res) => {
  res.json({ message: 'Traceway is watching' });
});

app.get('/slow', async (req, res) => {
  await new Promise(resolve => setTimeout(resolve, 2000));
  res.json({ message: 'This one took a while' });
});

app.listen(3000, () => console.log('App running on port 3000'));
```

Run it with the ESM loader hook so auto-instrumentation patches modules before they load:

```bash
node --import ./telemetry.mjs index.js
```

Hit both endpoints a few times:

```bash
curl http://localhost:3000/
curl http://localhost:3000/slow
```

Switch back to the Traceway dashboard. Traces appear within seconds. Spans break down each request, the `/slow` endpoint visibly takes longer, and you can click through the waterfall to see exactly where time goes.

The Traceway repo ships working examples for [Express](https://github.com/tracewayapp/traceway/tree/main/examples/express-otel), [NestJS](https://github.com/tracewayapp/traceway/tree/main/examples/nestjs-otel), [Next.js](https://github.com/tracewayapp/traceway/tree/main/examples/nextjs-otel), and [Hono](https://github.com/tracewayapp/traceway/tree/main/examples/hono-otel) if you want a reference beyond this minimal setup.

## Instrument a Python app with OpenTelemetry

Python works the same way, but there's a critical protocol gotcha. Here's a minimal Flask setup:

```bash
mkdir traceway-python && cd traceway-python
python3 -m venv venv && source venv/bin/activate
pip install flask opentelemetry-distro opentelemetry-exporter-otlp-proto-http
```

Create `app.py`:

```python
from flask import Flask
from opentelemetry import trace
from opentelemetry.exporter.otlp.proto.http.trace_exporter import OTLPSpanExporter
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.instrumentation.flask import FlaskInstrumentor

# Point the exporter at your Traceway instance with auth
exporter = OTLPSpanExporter(
    endpoint="http://your-server-ip/api/otel/v1/traces",
    headers={"Authorization": "Bearer your-project-token"}
)

provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(exporter))
trace.set_tracer_provider(provider)

app = Flask(__name__)
FlaskInstrumentor().instrument_app(app)

@app.route("/")
def home():
    return {"message": "Traceway sees this too"}

@app.route("/error")
def error():
    1 / 0  # Intentional, shows up in exceptions
    return "never reached"

if __name__ == "__main__":
    app.run(port=5000)
```

<Notice type="warning" title="Python silently drops spans over gRPC">
Set this environment variable before running the app. Without it, the Python SDK resolves to gRPC (which Traceway doesn't support) and every export vanishes silently:

```bash
export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
```

You can also use the auto-instrumentation route: `pip install opentelemetry-distro opentelemetry-exporter-otlp`, then `opentelemetry-bootstrap -a install` and run under `opentelemetry-instrument`. Either way, the protocol env var is non-negotiable.
</Notice>

Run it and hit both endpoints:

```bash
export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
python app.py
curl http://localhost:5000/
curl http://localhost:5000/error
```

Back in Traceway, you'll see spans for each Flask route plus a grouped exception entry for the division by zero.

## Frontend session replay with the Traceway browser SDK

Traceway 2.x ships a new browser SDK. The old 1.x snippet (`@tracewayapp/browser` with `init({projectToken, endpoint, sessionReplay})`) no longer works. The API changed to a connection-string format and the endpoint is now `/api/report`, not `/api/otel/v1/traces`.

Add the 2.x SDK to your frontend:

```html
<script src="https://cdn.jsdelivr.net/npm/@tracewayapp/frontend@2/dist/traceway.iife.global.js"></script>
<script>
  Traceway.init("your-project-token@https://your-server-ip/api/report");
</script>
```

Or install from npm:

```bash
npm install @tracewayapp/frontend
# or framework-specific: @tracewayapp/react, @tracewayapp/vue, @tracewayapp/svelte, @tracewayapp/jquery
```

Session replay in 2.x works differently than before. Breadcrumbs and replay data live in an on-device ring buffer (roughly the last 10 minutes plus a 30-second recording). Data uploads only when an error fires, a trigger condition is met, or you explicitly capture, not on every page visit. This keeps storage and bandwidth usage proportional to actual problems, not traffic volume.

The browser SDK works with React, Vue, Svelte, Next.js, plain HTML, and more. There are also packages for Flutter, React Native, and native Android/iOS.

If you're shipping minified JS bundles, upload source maps from CI so stack traces get symbolicated:

```bash
npx traceway-sourcemaps --directory ./dist
```

## Production hardening checklist

Once you've confirmed everything works, lock it down. This is where most self-hosted observability setups fall short. They're useful until the first disk fills up or the first token leaks.

<ListCheck>

- Set up HTTPS with a reverse proxy in front of the dashboard. [Set up a Traefik reverse proxy in Docker](/traefik-proxy-docker/) for an automated approach, or grab a [free Let's Encrypt wildcard certificate with Traefik](/traefik-wildcard-certificate/) if you have multiple subdomains. [CloudPanel as a reverse proxy for Docker and Dockge](/cloudpanel-setup-dockge/) works too if you prefer a panel.
- Set `JWT_SECRET` to a real random value (`openssl rand -hex 32`) and keep it stable across upgrades
- Set `APP_BASE_URL` to your public URL (required behind any proxy that rewrites Host headers; used for SDK instructions, email links, OAuth callbacks, and CLI/MCP device logins)
- Set `TRUSTED_PROXIES` to your reverse proxy's IP range (e.g., `172.18.0.0/16` for Docker's default bridge). Without this, every visitor shares a single rate-limit bucket and RUM sees the proxy IP as the client.
- Restrict the OTLP ingest port to internal services only. Don't expose it publicly. Note that [why Docker bypasses your firewall and how to fix it](/docker-bypasses-firewall/) applies here: `iptables` rules set with `ufw` won't stop Docker-published ports.
- Mount the `traceway-storage` volume for source maps, session recordings, and AI traces (or use `STORAGE_TYPE=s3` for S3-compatible storage)
- Named volumes for ClickHouse and PostgreSQL data so data survives container restarts
- Resource limits on containers so ClickHouse doesn't starve the API under heavy ingest
- Back up three things: ClickHouse, PostgreSQL, AND blob storage (the volume or S3 bucket). All three hold data you can't regenerate. Use `clickhouse-backup` or `BACKUP TABLE` for ClickHouse, `pg_dump` for PostgreSQL, and S3 versioning or a sync job for the blob volume.
- Enable self-monitoring with `MONITORING_TRACEWAY_URL="<project_token>@https://your-host"`. The backend reports ingest pressure, ClickHouse health, cache sizes, and Go runtime metrics back into a project, with recommended alert thresholds
- Regular security updates for the host and Docker images (Traceway images are Cosign-signed if you want to verify provenance)

</ListCheck>

<Notice type="info" title="Three things to back up">
ClickHouse, PostgreSQL, and blob storage. Missing any one of them means losing data you can't reconstruct. ClickHouse holds telemetry (traces, metrics, logs). PostgreSQL holds projects, users, and alert rules. Blob storage holds source maps, session recordings, and AI traces. Back up all three on the same schedule.
</Notice>

ClickHouse disk usage grows with ingest volume. Plan for at least 20 GB and monitor growth over the first few weeks. When the disk fills up, [add a new drive to Ubuntu LVM and mount it permanently](/add-new-drive-lvm/) rather than shrinking retention blindly.

For host-level security beyond Traceway itself, [how I secured my Docker server with UFW](/bsi-security-report-docker-ufw/) covers firewall rules and the Docker-specific gotchas that catch people out.

## Updating Traceway (2.x migration notes)

### Same-major updates (happy path)

For minor updates within 2.x:

```bash
cd /opt/traceway
docker compose pull && docker compose up -d
```

Schema migrations run automatically when the new backend starts. Check the [release notes on GitHub](https://github.com/tracewayapp/traceway/releases) before pulling. Breaking changes are called out there.

### Major upgrades: 1.x to 2.x

<Notice type="warning" title="V2.0 is a breaking upgrade">
Traceway 2.0 (2026-09-20) changed the telemetry table layout and parts of the API. Old and new backends write to different tables. Running them simultaneously causes data loss or corruption. Back up before you start.
</Notice>

The 1.x to 2.x migration sequence:

1. **Back up** ClickHouse, PostgreSQL, and blob storage. All three. No exceptions.
2. **Upgrade backend and dashboard together.** Stop all old backend writers first. Old and new versions write to different tables and mixing them is the main failure mode.
3. New V2 tables create themselves on first boot. **History copy is opt-in**: set `V2_MOVE_OVER=true` on one upgraded instance. A background worker copies data newest-day-first. Without it, endpoints/tasks/AI traces/exceptions/spans views show only newly ingested data.
4. Use `V2_MOVE_OVER_OLDEST` to cap how far back the backfill goes if you have a lot of history.
5. Note: logs, metrics, sessions, profiles, and synthetic checks are **not** copied by the migration worker. Blob storage is not moved either. Keep your volume or S3 config as-is.
6. The [full migration guide](https://docs.tracewayapp.com/server/upgrade-v2-tables) covers rollback, recheck-a-day tooling, and API/SDK compatibility notes.

The plain `docker compose pull && docker compose up -d` line is fine for same-major updates. For anything crossing a major version boundary, follow the numbered sequence above.

## FAQ

<Accordion label="How does Traceway compare to Grafana + Loki + Tempo?" group="faq" expanded="true">
Grafana's stack is battle-tested but requires you to configure and maintain Loki for logs, Tempo for traces, Prometheus for metrics, and Grafana for dashboards. Each piece has its own configuration language, storage backend, and upgrade path. Traceway gives you the same capabilities (logs, traces, metrics) plus on-call paging, SLOs, and RUM that the DIY stack doesn't give you for free. One Docker Compose stack, one configuration surface. If you already run the Grafana stack and it works for you, Traceway probably isn't worth the migration. If you're starting fresh or tired of stitching things together, it's worth a look.
</Accordion>

<Accordion label="Can I use Traceway with existing OpenTelemetry instrumentation?" group="faq">
Yes. If your services already export OTLP, repoint the exporter URL at your Traceway instance and add the `Authorization: Bearer <project_token>` header. Two things to watch: the protocol must be HTTP (set `OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf`), and the auth header is required in 2.x. Beyond that, no code changes needed.
</Accordion>

<Accordion label="What's the storage footprint?" group="faq">
It depends heavily on your traffic. ClickHouse compresses well, but V2.0 uses more database space than 1.x due to the new telemetry tables. A reasonable starting point is 20 GB of disk for a handful of services in production. You also need blob storage (the `traceway-storage` volume or S3) for source maps, session recordings, and AI traces. That grows with pages and releases, not visitors. Measure your own ingest over the first few weeks and adjust. When the disk fills up, [add a new drive to Ubuntu LVM](/add-new-drive-lvm/) rather than deleting data.
</Accordion>

<Accordion label="Does Traceway support alerting?" group="faq">
Yes. You can set up alerts for error rate thresholds, latency spikes, or custom metric conditions. Notifications go to Slack, GitHub issues, email, any webhook endpoint, Pushover, or Telegram. The on-call paging feature adds SMS delivery, escalation policies, and one-click acknowledge links on top of that.
</Accordion>

<Accordion label="Is there a managed cloud option?" group="faq">
Traceway Cloud exists at cloud.tracewayapp.com if you'd rather not self-host. It runs the same MIT code. Pricing is fixed-tier: **Free** (10k exceptions/month, 1 GB ingest/month, 3 projects), **Premium at $24.99/month** (1M exceptions/month, 150 GB ingest/month, unlimited projects, $0.25/GB overage), or Enterprise (custom). Metered on exceptions and data ingest only. No per-host, no per-seat charges. The Free tier is a low-risk way to try the product before committing to a server.
</Accordion>

<Accordion label="Does Traceway support gRPC?" group="faq">
No. Traceway ingests OTLP over HTTP only. Set `OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf` in your environment (PHP uses `http/json`). The Python OTLP SDK defaults to gRPC and will silently drop all data if you don't override the protocol. This trips people up more than any other configuration detail.
</Accordion>

<Accordion label="Do I need an OpenTelemetry Collector?" group="faq">
No. Traceway ingests OTLP/HTTP directly at `/api/otel/v1/traces`, `/api/otel/v1/metrics`, and `/api/otel/v1/logs`. Point your SDKs straight at those endpoints. A Collector is optional: useful if you want buffering, sampling, or fan-out to multiple backends at scale, but not required for a single Traceway instance.
</Accordion>

## Wrapping up

Traceway scratches a real itch. Observability shouldn't require a procurement process and a four-figure monthly commitment just to know why your API is slow. The project gives you logs, traces, metrics, exception tracking, session replay, RUM, SLOs, and on-call paging in a stack you control, with an MIT license that doesn't pull the rug later.

The trade-off is maturity. Datadog has a decade of polish behind it. Traceway is early and moving fast, with 1,786 stars and near-weekly releases as of late 2026. But the 2.0 breaking upgrade shows the API surface is still settling. For small teams, side projects, and anyone who'd rather spend money on servers than dashboards, it's worth your evening to try.

If you don't want to manage the infrastructure yourself, Traceway Cloud's Free tier is a no-risk way to kick the tires. And if you're running this at home rather than on a rented VPS, [the best mini PCs for a home server](/best-mini-pc-home-server/) cover the hardware. Something like a compact mini PC such as the [ASUS DC510](https://go.bitdoze.com/asus-dc510) handles a small-to-medium observability stack without racking up a cloud bill.
