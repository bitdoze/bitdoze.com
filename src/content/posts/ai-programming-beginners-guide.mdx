## Why Programming with AI Works for Complete Beginners

Traditional programming had a brutal feedback loop. You'd spend weeks on syntax before you could build anything that did something visible, and one cryptic error message could eat an evening. AI collapses that loop. You describe what you want, you get code, you run it, you see the result.

**With AI assistance, you can:**

<ListCheck>
- **Start building immediately** - Focus on what you want to create, not memorizing syntax
- **Learn by doing** - AI explains code as you build, helping you understand concepts in context
- **Fix errors faster** - Paste the stack trace, get the likely cause and the fix
- **Access expert knowledge** - Get architectural advice and best practices from day one
- **Iterate quickly** - Test ideas and make changes without fear of breaking everything
</ListCheck>

Think of it as a senior developer on call at any hour: patient with beginner questions, generous with explanations, and occasionally, confidently wrong. Remember the last part.

### What AI won't do for you

This is the part most beginner guides skip. AI writing the code does not remove the four jobs that decide whether you have a working product or a pile of files:

<ListCheck>
- **Deciding what to build.** The AI has no opinion about your product. You do.
- **Verifying.** Code that compiles is not code that works. Someone has to click the button on a phone.
- **Understanding enough to debug.** When the deploy breaks at 11pm, "the AI wrote it" is not a debugging strategy.
- **Owning the blast radius.** If the agent has your production database credentials, it can absolutely run the wrong migration.
</ListCheck>

So the goal is to build real things on day one while steadily understanding more of what you're shipping. That is a different thing from pretending you'll never read code. Everything below is arranged around that.

## Step 2: Set Up Your Code Repository (GitHub + SSH)

Before writing any code, create a GitHub repository. This gives you version control, backup, and enables automatic deployments. It also gives your AI agent a diff to look at, which is how it knows what changed.

### Create a GitHub Account

1. Visit [github.com](https://github.com)
2. Sign up for a free account
3. Verify your email address

### Set Up SSH Keys (Recommended)

SSH keys let you push code securely without entering passwords every time:

```bash
# Generate a new SSH key
ssh-keygen -t ed25519 -C "your_email@example.com"

# Start the ssh-agent
eval "$(ssh-agent -s)"

# Add your SSH key
ssh-add ~/.ssh/id_ed25519

# Copy your public key
cat ~/.ssh/id_ed25519.pub
```

Add the public key to GitHub:
1. Go to GitHub Settings → SSH and GPG keys
2. Click "New SSH key"
3. Paste your public key
4. Save

For the longer version, including the macOS keychain step: [Link GitHub with SSH on Mac/Linux](/link-github-with-ssh-maco-linux/).

### Verify Your SSH Setup

Before you create anything, confirm authentication works:

```bash
ssh -T git@github.com
```

Expected output:

```
Hi your-username! You've successfully authenticated, but GitHub does not provide shell access.
```

That "does not provide shell access" line is success, not an error. If you instead see `Permission denied (publickey)`, it's almost always one of these:

<ListCheck>
- The key isn't loaded: run `ssh-add -l`. Empty list means you skipped `ssh-add`.
- You added the wrong key to GitHub: compare `ssh-add -l` fingerprint with the one in GitHub Settings.
- You're using a non-default key name: add `-i ~/.ssh/your_key` or a `Host github.com` block in `~/.ssh/config`.
</ListCheck>

### Create Your Repository

1. Click the "+" icon in GitHub
2. Select "New repository"
3. Name it (e.g., `my-first-ai-project`)
4. Keep it public or private (your choice)
5. Don't initialize with README (you'll create it locally)
6. Click "Create repository"

### Make Your First Commit

In an empty project folder, create a `.gitignore` *before* you add anything else. This is the single cheapest way to avoid committing secrets:

```bash
mkdir my-first-ai-project && cd my-first-ai-project
printf '%s\n' 'node_modules/' 'dist/' '.env' '.env.local' '.DS_Store' > .gitignore

git init -b main
git add -A
git commit -m "chore: initial commit"
git remote add origin git@github.com:your-username/my-first-ai-project.git
git push -u origin main
```

Verify:

```bash
git log --oneline
git status            # should say "working tree clean"
git check-ignore -v .env   # should print the matching .gitignore rule
```

If `git check-ignore` prints nothing, your `.gitignore` isn't catching `.env` and any key you paste later goes to GitHub. Fix it before you write code.

**Other common failures:** `remote origin already exists` means you need `git remote set-url origin <url>` instead of `add`. A push rejected as non-fast-forward means the remote has commits you don't; run `git pull --rebase origin main` and push again.

### Recommended: GitHub Copilot Pro ($10/month)

Copilot Pro is still the cheapest way I know to get a frontier-model agent, unlimited completions, a CLI, and an editor plugin under one subscription. What changed on June 1, 2026 is what that $10 buys.

| Plan | Price | What you get |
|------|-------|--------------|
| Copilot Free | $0 | 2,000 completions/month, 50 chat requests/month, plus a small AI Credits allowance |
| **Copilot Pro** | **$10/month** | 1,000 AI Credits + 500 flex credits (1,500 total), unlimited completions, CLI, agent mode |
| Copilot Pro+ | $39/month | 3,900 AI Credits + 3,100 flex (7,000 total) |
| Copilot Max | $100/month | 10,000 AI Credits + 10,000 flex (20,000 total) for long agent runs |

**What actually changed:**

<ListCheck>
- **AI Credits replaced premium requests.** 1 credit = $0.01, consumed at published per-token API rates for whichever model you pick, so $10 of subscription buys 1,000 base credits.
- **There's a flex allotment on top.** Pro adds 500 more credits, Pro+ adds 3,100, Max adds 10,000. Flex credits are variable, so treat the base number as the floor you can plan on.
- **No automatic downgrade.** Under the old system, running out of premium requests dropped you to a cheaper model and you kept working. Now you either turn on additional usage (it's a budget you set, and it can be capped) or wait for the monthly reset. Included credits never carry over; they reset each month.
- **Completions are still free.** Inline completions and Next Edit suggestions don't consume credits on any paid plan.
- **Code review costs twice.** Copilot's PR review also burns GitHub Actions minutes on top of AI Credits.
</ListCheck>

The practical consequence for a beginner: short chat questions are cheap, and a one-hour agentic session on a frontier model can eat a meaningful chunk of the month. The fix is not to avoid agents, it's to run them on scoped tasks and keep completions for the small stuff. ## Step 4: Write Project Documentation Your AI Can Actually Use

This is important and most beginners skip it. A well-maintained documentation folder helps AI understand your project and make better decisions.

### Why Documentation Matters

AI is powerful, but it doesn't automatically know:
- How your specific project is structured
- What commands to run for testing
- What conventions you're following
- What libraries and versions you're using

With clear documentation, your AI assistant provides help tailored to your project. Without it, you get generic advice for a project that doesn't exist.

One rule before you write a wall of text: every line you add here is a line the model reads on every turn, and it competes for context with your actual code. Short and specific beats comprehensive. If a section is stale, delete it.

### Create a `docs/` Folder

In your project root, create a `docs` folder with these files:

```bash
mkdir docs
```

### Essential Documentation Files

#### 1. Framework Documentation

If you're using Astro, create `docs/astro.md`:

````markdown
# Astro Framework Guide

## Installation & Setup
npm create astro@latest

## Development Commands
- `npm run dev` - Start dev server (http://localhost:4321)
- `npm run build` - Build for production
- `npm run preview` - Preview production build

## Project Structure
- `src/pages/` - File-based routing
- `src/layouts/` - Reusable page layouts
- `src/components/` - React/Vue/Svelte components
- `src/content/` - Markdown content collections
- `public/` - Static assets

## Key Concepts
- Islands Architecture - Only hydrate interactive components
- Content Collections - Type-safe markdown content
- Zero JS by default - Ship less JavaScript

## Common Patterns
- Use `---` frontmatter for component scripts
- Import components: `import Header from '../components/Header.astro'`
- Access props: `const { title } = Astro.props`
````

#### 2. Stack-Specific Guides

For TanStack Start, create `docs/tanstack-start.md`:

````markdown
# TanStack Start Guide

## Project Structure
- `src/routes/` - File-based routing
- `src/components/` - React components
- `src/server/` - Server-side functions
- `src/lib/` - Utilities and helpers

## Key Features
- Server functions with `createServerFn()`
- Type-safe routing
- Built-in data loading
- SSR and SSG support

## Backend Options
- Convex - Realtime serverless backend
- Drizzle + PostgreSQL - Traditional database
- Supabase - Backend as a service
````

#### 3. Styling Documentation

Create `docs/tailwind.md` if using Tailwind CSS:

### Verify Your Documentation Works

Close your editor, open a fresh AI session, and ask:

```
Read docs/ and AGENTS.md, then tell me the exact command to run the dev
server, which framework version this project uses, and where server
functions live. Don't look at any other file.
```

If the model answers all three correctly without opening source files, your docs are doing their job. If it hedges or guesses, the file it needed isn't there yet.

## Step 5: Create an AGENTS.md File Your AI Assistant Obeys

The `AGENTS.md` file is your AI assistant's instruction manual for your project. It tells the AI exactly how to work with your codebase. Agents converged on this filename during 2025, so it's read by Amp, Codex, Devin Desktop, Cursor, Copilot agents, OpenCode, Pi and most others. Write it once, and every tool you try later behaves better.

### Create AGENTS.md in Your Root

```bash
touch AGENTS.md
```

### What to Include

Here's a template based on my production projects:

```markdown
# Agent Instructions

You don't need to create any documentation unless I specifically ask for it. Just provide short summaries of what you did.

## Commands

- **dev**: `npm run dev` (runs on http://localhost:4321)
- **build**: `npm run build`
- **test**: `npm test`

## Architecture

- **Framework**: Astro v7 static site generator
- **Content**: Markdown files in `src/content/posts/`
- **Styling**: Tailwind CSS v4
- **Components**: Reusable components in `src/components/`

## Code Style

- Use TypeScript for type safety
- Follow existing file naming conventions
- Use Tailwind utilities for styling
- Keep components simple and focused

## Important Notes

- Always test changes locally before committing
- Follow existing code patterns in similar files
- Check that all images exist before referencing them
- Run the build to verify no errors
- Never commit or print the contents of `.env` files

## Testing Workflow

1. Make changes
2. Run `npm run dev` to test locally
3. Run `npm run build` to check for errors
4. Review changes carefully
5. Commit with a descriptive message

## Common Pitfalls

- Don't add libraries that aren't already installed
- Check TypeScript errors before committing
- Verify all imports are correct
- Test responsive design at different screen sizes
```

### Why This Matters

Without `AGENTS.md`, AI makes assumptions: it installs a library you didn't want, invents an npm script that doesn't exist, or reorganizes your folders because it prefers a different structure. With it, the agent follows your patterns and the diff stays reviewable.

Keep secrets out of it. This is a file the agent reads *and* often quotes back into a conversation, and on free tiers conversations can be shared.

### Go Further With Reusable Skills

Once `AGENTS.md` feels natural, the next step is Agent Skills: `SKILL.md` files that encode a workflow (design rules, deploy steps, review checklists) so you don't repeat yourself in every prompt. I compared the ones worth installing for web work in [AI agent skills for web design](/best-ai-skills-for-web-design/). The same pattern is what lets an assistant [deploy Docker apps from a single message](/ai-docker-deploy-skill/).

## Step 6: Add MCP Servers to Your AI Assistant

Model Context Protocol (MCP) servers connect your AI assistant to external services and tools. If the term is new to you, my [introduction to MCP for beginners](/mcp-introduction-beginners/) covers the protocol itself. The short version: MCP is USB for AI tools. Build one server, and it works with Claude, Cursor, Copilot, Codex, Amp, and anything else that speaks the protocol.

### What Are MCP Servers?

Instead of just writing code, your AI can:
- Search the web for current information
- Access up-to-date framework documentation
- Test your application automatically
- Interact with databases and APIs

### Essential MCP Servers for Beginners

#### 1. Context7 - Up-to-Date Documentation

Context7 provides fresh documentation for frameworks and libraries. Instead of the AI using outdated training data, it fetches the current docs at query time. Context7 shipped v4 in August 2026 with new tool schemas, so pin `@latest` (or a known v4 version) and don't mix instructions written for v3 tool names.

**What it helps with:**
- Latest API references
- Current best practices
- Recent framework updates
- New features and deprecations

#### 2. Bright Data MCP - Web Search & Data

Bright Data MCP lets your AI search the web and extract data from websites, with a 5,000 request/month free tier. This is the one that makes a difference when the model's answer is two years out of date and the actual page says something else.

**What it helps with:**
- Searching for solutions to problems
- Finding examples and tutorials
- Researching competitors
- Gathering data for your project

Learn more: [Bright Data MCP guide](/brightdata-mcp-guide/) and the [Bright Data platform](https://go.bitdoze.com/brightdata) itself. If you'd rather have web search, fetch and a headless browser behind a single key without the proxy stack, [TinyFish](https://go.bitdoze.com/tinyfish) is the other option I'd look at.

#### 3. Playwright MCP - Application Testing

Playwright MCP enables your AI to test your application automatically by controlling a browser. This is how an agent verifies that the form it just built actually submits.

**What it helps with:**
- Testing user workflows
- Verifying forms work correctly
- Checking responsive design
- Catching bugs before deployment

GitHub: [playwright-mcp](https://github.com/microsoft/playwright-mcp)

The setup process depends on your AI tool. Here's how to do it for the popular options:

```bash
claude mcp add context7 -- npx -y @upstash/context7-mcp@latest
claude mcp add brightdata --transport sse "https://mcp.brightdata.com/sse?token=YOUR_TOKEN"

# Confirm what's registered
claude mcp list
```

Scope matters: add `-s project` and the config lands in `.mcp.json` in the repo, which teammates inherit. Never do that with a server that takes a credential.

</Accordion>

<Accordion label="Codex CLI" group="mcp">

</Accordion>

### Verify an MCP Server Actually Works

Don't assume it loaded. Ask a question that *requires* the server:

```
Use context7 to fetch the current Astro docs for content collections,
then tell me the exact current API.
```

If the agent answers with citations from the fetched docs, it's wired up. If it answers from memory or says it has no such tool, check:

<ListCheck>
- The server shows up in the tool list (`claude mcp list`, `/agent-files` in Amp, or your editor's MCP panel).
- `npx` resolves. Editors launched from the Dock or Start menu don't inherit your shell PATH; on macOS that means pointing at `/opt/homebrew/bin/npx` instead of `npx`.
- The config file is valid JSON. A trailing comma silently kills the whole file.
- Restart the editor after editing config. Most clients only read it at startup.
</ListCheck>

### Don't Overdo It

<Notice type="warning" title="Keep It Simple">

Start with just 2-3 MCP servers. Every server adds tool definitions to your context window, and a pile of tools you never call costs tokens on every turn and makes the model pick worse.

**Recommended starter set:**
- Context7 (documentation)
- Bright Data MCP (web search)
- That's it.

</Notice>

For a complete list of available MCP servers, visit [mcpservers.org](https://mcpservers.org/).

## Step 7: Start Building Features Incrementally

This is where most beginners make mistakes. They try to build everything at once, overwhelming both themselves and the AI.

### Think Small and Focused

Break your project into tiny, manageable features. Instead of "build a blog," think:

1. Create the homepage layout
2. Add a navigation menu
3. Create a single blog post page
4. Add a blog post listing page
5. Implement search functionality
6. Add categories and tags

### Create a Project Architecture First

Before writing code, ask your AI to help plan the structure:

**Good prompt:**
```
I want to build a personal blog with Astro. It should have:
- Homepage with recent posts
- Individual post pages
- About page
- Contact form
- Categories and tags

Please create a project architecture document that outlines:
- Folder structure
- Key components needed
- Content organization
- Routing approach

Don't write code yet, just plan the structure.
```

This gives you a roadmap and helps you understand what you're building.

### Work on One Feature at a Time

When building, focus on a single feature completely before moving on:

**Bad approach:**
```
Build the homepage, blog pages, contact form, and about page
```

**Good approach:**
```
Create the homepage layout with:
- Header with site title and navigation
- Hero section with welcome message
- Grid of latest 3 blog posts
- Footer with copyright

Use Tailwind for styling and make it responsive.
```

### Example: Building a Blog Post Page

Here's how to approach a single feature step by step:

**Step 1: Create the basic page structure**
```
Create a blog post page template at src/pages/blog/[slug].astro
- It should accept a slug parameter
- Display post title, date, and author
- Render markdown content
- Use the main layout
```

**Step 2: Add styling**
```
Style the blog post page:
- Use Tailwind typography plugin for content
- Add a max-width container
- Style the header with gradient
- Make code blocks look good
```

**Step 3: Add metadata**
```
Add SEO metadata to the blog post template:
- Title tag with post title
- Meta description from frontmatter
- Open Graph tags for social sharing
- Canonical URL
```

**Step 4: Test and refine**
```
Test the blog post page with different content:
- Long posts with many headings
- Posts with images
- Posts with code blocks
- Short posts
```

Each step is focused and manageable. AI can handle these easily without getting confused.

### Verify Each Feature Before the Next One

The habit that separates people who ship from people who accumulate a broken repo:

```bash
npm run dev          # dev server on http://localhost:4321
npm run build        # production build; catches type and import errors
git diff --stat      # see what the agent actually touched
```

Then open the page in a browser and use it. A feature isn't done when the AI says "done". It's done when you've clicked the thing. If the agent touched ten files for a one-file feature, that's a signal it guessed; ask it to explain the extra changes.

### Keep the AI Focused

If you notice the AI starting to add features you didn't ask for, rein it back:

```
That's good, but I only asked for the header right now.
Let's finish the header completely before moving to other sections.
Can you remove the footer and sidebar code and focus only on the header?
```

## Step 8: Review Every Line of Code (So You Don't Just Vibe Code)

This is the step that turns "I built a thing with AI" into "I'm learning to program". It's also how you avoid the failure mode everyone warns you about.

### What "Vibe Coding" Actually Means

Vibe coding is accepting generated code without reading it, iterating on the behavior instead of the implementation. It got a name in early 2025 and it's a legitimate technique for throwaway prototypes: a script to rename 400 files, a landing page you'll delete next week, a demo for a pitch. You don't need to understand code you're going to throw away.

It stops being legitimate the moment the code holds something up. Auth, payments, user data, anything with a database behind it, anything that runs on a schedule, anything with credentials in reach. That's where "it seems to work" turns into a 2am incident where the symptom is in one place and the cause is in another.

So the rule I'd give a beginner: **vibe code the prototypes, review the production path.**

### Ask for Explanations

After AI generates code, ask it to explain:

**Good follow-up prompts:**
```
Explain what this component does line by line

Why did you use this approach instead of [alternative]?

What are the potential issues with this code?

How would I modify this to add [feature]?
```

### Run It and Break It

Reading a diff catches typos. Running the code catches logic. Two cheap habits:

<ListCheck>
- <strong>Read the diff, not the file.</strong> `git diff` shows exactly what the agent changed. A 400-line diff for a button is a red flag.
- <strong>Try to break it.</strong> Empty form, 5000-character input, network off, wrong password, two tabs at once. Every one of those is a bug report you file for free instead of reading about later.
</ListCheck>

### Request Comments

For complex code, ask AI to add explanations:

```
Add comments to this code explaining what each section does.
Focus on the "why" not just the "what."
```

### Identify Learning Opportunities

When you see something you don't understand:

```
I don't understand this TypeScript syntax: `const { data }: { data: Post[] }`
Can you explain what this means and why we use it?
```

### Keep a Learning Log

Create a `LEARNING.md` file in your project. This one habit turns "I built a thing with AI" into "I learned to program":

````markdown
# Things I've Learned

## TypeScript Destructuring
```typescript
const { title, date } = post;
```
This extracts specific properties from an object. More concise than:
```typescript
const title = post.title;
const date = post.date;
```

## Component Props in Astro
Props are passed to components and accessed via `Astro.props`:
```astro
---
const { title } = Astro.props;
---
<h1>{title}</h1>
```

## Tailwind Responsive Classes
`sm:`, `md:`, `lg:` prefixes apply styles at breakpoints:
- `sm:` = 640px and up
- `md:` = 768px and up
- `lg:` = 1024px and up
````

This log becomes your personal reference as you learn.

## Step 9: Get a Second Opinion From a Different AI Model

AI can make mistakes or use suboptimal approaches. Getting a second AI's perspective catches issues early, and it's the cheapest code review you'll ever get.

### Use a Different AI for Code Review

If you built features with Claude Sonnet 4.6, ask GPT-5.5 to review. If you used GPT-5.5, ask Claude or Gemini 3 to review. The point isn't that one model is smarter; it's that different models hallucinate differently, so the overlap is much more trustworthy than either answer alone.

**Code review prompt:**
```
Please review this [component/feature/file] for:

1. Security vulnerabilities
2. Performance issues
3. Code quality and maintainability
4. Potential bugs
5. Best practice violations

Be thorough and critical. I want to improve this code.
```

### Create a Review Document

Ask the second AI to create `REVIEW.md`:

```
After reviewing the entire codebase, create a REVIEW.md file with:

## Security Issues
List any security concerns found

## Performance Optimizations
Suggest improvements for speed and efficiency

## Code Quality
Note areas that could be cleaner or more maintainable

## Best Practices
Identify where we deviate from best practices

## Recommended Changes
Prioritized list of improvements

Be specific with file names and line numbers where relevant.
```

### Iterate Based on Feedback

Don't just collect feedback. Act on it:

```
Based on the review, let's fix the top 3 security issues first.
Start with [specific issue from review].
```

### Example Review Process

Here's what a typical review session looks like:

1. **Build feature with AI #1** (e.g., Claude Sonnet 4.6)
2. **Switch to AI #2** (e.g., GPT-5.5) and share the code
3. **Request detailed review** focusing on security and performance
4. **Review the feedback** and ask questions about anything unclear
5. **Prioritize fixes** starting with security issues
6. **Implement improvements** with AI #1
7. **Verify fixes** with AI #2

This back-and-forth catches issues that a single AI might miss. And it's not free on credit-based plans, so point it at the risky files, not the CSS.

### Rollback: What to Do When the Deploy Breaks

This is the step beginners skip, and it's the one that saves you at 11pm. Make sure you know the rollback path *before* you need it.

```bash
# Revert the bad commit without rewriting history
git revert --no-edit <bad-commit-sha>
git push origin main
```

Then, per platform:

<ListCheck>
- <strong>Vercel:</strong> Deployments → pick the last good one → Promote to Production. Instant, no rebuild.
- <strong>Cloudflare Pages:</strong> Deployments → select the previous deployment → Rollback.
- <strong>Dokploy:</strong> Deployments → pick the previous commit → Redeploy.
- <strong>Database:</strong> rollbacks don't undo migrations. If the bad commit changed the schema, restoring the previous code may not be enough.
</ListCheck>

That last line is the real footgun. App code rolls back in seconds; a dropped column doesn't. Before you let an agent run migrations against production, take a dump. Which brings us to backups.

## Step 12: Keep Shipping Features Without Breaking What Works

Your project is live. Now you'll iterate and improve. But do it carefully to avoid breaking what works.

### Always Work on a Branch

Never commit directly to `main` when your site is live:

```bash
# Create a new feature branch
git checkout -b feature/add-dark-mode

# Make your changes and test locally

# Commit to the branch
git add -A
git commit -m "Add dark mode toggle"

# Push the branch
git push origin feature/add-dark-mode
```

Then create a Pull Request on GitHub, review the diff yourself, and merge from there. The PR diff is the last place you can catch a bad change cheaply.

### Test Locally First

Before deploying new features:

<ListCheck>

1. **Run the dev server** - `npm run dev`
2. **Test the new feature** thoroughly
3. **Check existing features** still work
4. **Test on mobile** sizes
5. **Run the build** - `npm run build`
6. **Fix any errors** that appear
7. **Preview the build** - `npm run preview`
</ListCheck>

Only after all these checks pass should you deploy.

### Use Staging Environments

For serious projects, have a staging site:

**Setup:**
1. Create a separate branch (e.g., `staging`)
2. Deploy it to a different URL (e.g., `staging.yourdomain.com`)
3. Test new features on staging first
4. Merge to `main` only after verification

Most hosting platforms make this easy:
- Vercel: Automatic preview deployments for branches
- Cloudflare Pages: Can deploy multiple branches
- Self-hosted: Deploy a second Dokploy app pointing at the `staging` branch

### Keep Features Small

Remember Step 7? This applies forever:

**Bad:**
```
Add user authentication, profile pages, and social sharing all at once
```

**Good:**
```
Step 1: Add user registration form with email/password
Step 2: Add login functionality
Step 3: Add password reset flow
Step 4: Add email verification
```

Small changes are easier to test, debug, and roll back if needed.

### Back Up Anything You Can't Recreate

The single most common way beginners lose real work is not a bad deploy, it's a database without a dump. Two rules:

<ListCheck>
- <strong>Dump before migrations.</strong> `pg_dump "$DATABASE_URL" -Fc -f backup-$(date +%F).dump` before any schema change, agent-driven or not.
- <strong>Get the dump off the machine.</strong> A backup on the same VPS as the database is not a backup. Push it to S3-compatible object storage on a schedule and test a restore once.
</ListCheck>

If you want an assistant to handle repetitive deploy steps safely, the pattern in [letting an AI assistant deploy Docker apps](/ai-docker-deploy-skill/) is worth copying: the skill holds the steps, the agent executes them, and you review the diff.

### Document New Features

Update your `AGENTS.md` when adding new patterns:

```markdown
## Recent Additions

### Dark Mode (Added 2026-09-01)
- Theme toggle in header
- Saved to localStorage
- CSS variables in `theme.css`
- Usage: Add `dark:` prefix to Tailwind classes

### User Authentication (Added 2026-09-08)
- Using Clerk for auth
- Protected routes in `src/middleware/auth.ts`
- User object available in `Astro.locals.user`
```

This helps AI (and future you) understand the full project context.

## Common Pitfalls When You Learn to Code with AI

### Pitfall 1: Overwhelming the AI

**Symptom:** AI generates buggy code or misses requirements

**Solution:** Break tasks into smaller pieces. If AI is struggling, your request is too big.

### Pitfall 2: Trusting AI Output Blindly

**Symptom:** Accumulating technical debt, or a security hole you never see

**Solution:** Review all code, ask questions, get second opinions. Especially on anything that touches auth, money, or user data.

### Pitfall 3: Not Testing Locally

**Symptom:** Deployments fail or bugs appear in production

**Solution:** Always run `npm run dev` and `npm run build` locally first.

### Pitfall 4: Burning Through Your AI Credits

**Symptom:** Your $10 Copilot Pro balance is gone by the 8th of the month and agent mode stops working

**Solution:** Credit spend is token spend. Keep small edits on completions, scope agent sessions to one feature, start a fresh conversation when the context gets long, and check your remaining balance weekly. If flat pricing suits you better than metering, a $10 subscription like OpenCode Go removes the ceiling.

### Pitfall 5: Giving an Agent Shell Access You Wouldn't Give an Intern

**Symptom:** The agent deletes a file, rewrites a working module, or runs a migration you didn't ask for

**Solution:** Treat the agent like a new contractor with your credentials. Work on a branch, keep `.env` out of the repo, don't hand an agent production database credentials while you're experimenting, and read the diff before merging anything.

### Pitfall 6: Committing Secrets

**Symptom:** An API key shows up in a public repo and gets scraped within minutes

**Solution:** `.gitignore` `.env` before your first commit. Verify with `git check-ignore -v .env`. If a key does leak, rotate it first and clean up history second; rewriting history doesn't un-leak it.

### Pitfall 7: Coding Against a Deprecated API

**Symptom:** Every tutorial's approach fails, or the code compiles and the feature doesn't work

**Solution:** Model training data has a cutoff, and frameworks moved a lot in 2025 and 2026. This is what Context7 MCP is for. When something behaves strangely, ask for the current docs rather than a fix.

### Pitfall 8: Too Many Dependencies

**Symptom:** Project becomes slow, bloated, or breaks on upgrade

**Solution:** Only add libraries when necessary. Ask the agent "what does this dependency buy me over doing it in 20 lines?" and don't accept "it's the standard choice."

### Pitfall 9: No Version Control Discipline

**Symptom:** Lost code, unclear what changed, hard to roll back

**Solution:** Commit often with descriptive messages. Branch for features. Never let an agent make twenty changes between commits.

### Pitfall 10: Treating Deploy as the Finish Line

**Symptom:** An outage you find out about from a friend, and no way to roll back

**Solution:** Monitoring, backups, and a rehearsed rollback are part of building the feature, not an afterthought. Steps 10, 11 and 12 above are the minimum.

## FAQ: Programming with AI for Beginners

<Accordion label="Do I need to learn to code to build an app with AI?" group="faq" expanded="true">

For a prototype, no. You can describe what you want and deploy something functional without reading most of the code.

For anything you intend to keep running, yes, and the more the better. The three things that actually require you are deciding what to build, verifying it works, and fixing it when it breaks at 2am. An agent can do a lot of the middle, but it can't own the outcome for you.

Realistic path: build with AI from day one, and spend 30 minutes a day understanding what it wrote. You'll be reading your own code within a couple of weeks, which is far more than the old approach gave you in the first month.

</Accordion>

<Accordion label="What is the best AI coding assistant for beginners?" group="faq">

There's no single winner, but there is a sensible default:

<ListCheck>
- <strong>Free and good enough to learn on:</strong> FreeBuff (free CLI and web agent, funded by text ads) or Copilot Free (2,000 completions and 50 chat requests a month, plus a small AI Credits allowance). Amp Free was the third option; it's paused.
- <strong>$10/month, tightest editor integration:</strong> GitHub Copilot Pro. $15 a month in AI Credits at per-token rates ($10 base + $5 flex), unlimited completions, CLI, agent mode.
- <strong>$10/month, flat and predictable:</strong> OpenCode Go. More than two dozen models behind one OpenAI-compatible key, $5 for the first month.
</ListCheck>

If you're unsure, start on Copilot Free and upgrade after a week of actually building. The tool you use matters far less than the loop: ask for a small change, run it, read the diff, repeat.

</Accordion>

<Accordion label="Can AI write a whole app for me?" group="faq">

It can generate a whole app's worth of code, and for small things (a landing page, an internal tool, a script) that's often the same thing.

The catch is that "generated" and "works" are different states. Agents regularly produce code that runs, looks right, and quietly breaks on edge cases: an empty input field, a slow network, a second user, a timezone. They also can't know your constraints (cost ceiling, compliance, what your users actually do).

So the honest answer: yes for scope you can verify, no for scope you can't. Which is why every serious AI-coding workflow ends with a review step, a monitoring step, and a rollback plan.

</Accordion>

<Accordion label="How long does it take to learn programming with AI?" group="faq">

Rough timeline, in the order things usually click:

<ListCheck>
- <strong>Day 1:</strong> a deployed page you built by prompting
- <strong>Week 1-2:</strong> you can read the code you generated and change it
- <strong>Month 1:</strong> one real feature, end to end, in production
- <strong>Month 3:</strong> you can debug something the AI got wrong without help
- <strong>Month 6+:</strong> architecture decisions stop being guesswork
</ListCheck>

The variable isn't intelligence, it's how much you insist on understanding. People who accept every diff without reading plateau fast. People who ask "why this and not that?" grow quickly.

</Accordion>

<Accordion label="Is using AI to learn to code bad for skill development?" group="faq">

It depends entirely on how you use it, and both failure modes are real.

<ListCheck>
- <strong>Bad:</strong> accepting diffs without reading them. You ship things, learn little, and hit a wall the first time something subtle breaks.
- <strong>Bad:</strong> refusing to use it and hand-writing boilerplate for two months. You'll learn syntax and quit from boredom.
- <strong>Good:</strong> use it to build, then interrogate it. "Explain this line by line." "Why this approach?" "What breaks if the input is empty?" Treat it as a senior dev sitting next to you, not a vending machine.
</ListCheck>

The skill that matters most in 2026 isn't typing syntax quickly. It's reading code critically, knowing what to test, and being honest about what you don't understand. AI makes that skill more valuable, not less.

</Accordion>
