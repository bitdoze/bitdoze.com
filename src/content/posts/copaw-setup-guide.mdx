## What QwenPaw does

QwenPaw is a self-hosted AI assistant built on [AgentScope](https://github.com/agentscope-ai/agentscope) and [ReMe](https://github.com/agentscope-ai/ReMe) for memory management. The name stands for Qwen Personal Agent Workstation. The pitch hasn't changed since the first version: one assistant that connects to your messaging apps and runs tasks on a schedule without you having to ask.

What has changed since I first covered it: there's now a plugin architecture with a marketplace, MCP integration for bolting on external tools, multi-agent support via ACP for spawning sub-agents, a full-screen terminal UI, and a desktop app in Beta. The web console at `http://127.0.0.1:8088/` is still the recommended place to configure everything instead of editing config files blind.

### QwenPaw vs OpenClaw vs nanobot

If you're deciding between the three, this is how they stack up. The OpenClaw and nanobot columns reflect their state when I last checked them; those projects move too, so treat those cells as a snapshot.

| Feature | QwenPaw | OpenClaw | nanobot |
|---|---|---|---|
| **Language** | Python | TypeScript | Python |
| **Built by** | AgentScope (Alibaba) | Community | HKUDS |
| **Install** | pip / script / Docker / desktop / hosted | curl one-liner | pip |
| **Web console** | Yes (built-in at :8088) | No (third-party dashboards) | No |
| **Channels** | DingTalk, Lark, WeChat, Discord, Telegram, iMessage, QQ | Telegram, WhatsApp, Slack, Discord | Telegram, Discord, WhatsApp, Slack, Feishu, DingTalk, Email, QQ |
| **Local models** | QwenPaw Local (llama.cpp), Ollama, LM Studio | Ollama | vLLM |
| **Memory** | Three-layer: working context, history.db + FTS5, ReMe knowledge base | File-based + semantic search | File-based |
| **Skills & plugins** | Built-in skills, Plugin Market, MCP | Community skills | Built-in |
| **Scheduled tasks** | Cron + heartbeat | Cron | Cron |
| **Extra surfaces** | TUI, desktop app, REST API, multi-agent (ACP) | None | None |
| **License** | Apache 2.0 | MIT | MIT |

Where QwenPaw pulls ahead: the built-in web console means you don't need third-party dashboards, DingTalk/Lark/WeChat support is first-class instead of bolted on, and the security stack (sandbox, Tool Guard, File Guard) is the most complete of the three (see [Security](#security-sandbox-tool-guard-and-file-guard) below). OpenClaw still wins on Western messaging apps like WhatsApp and Slack. If DingTalk or Lark is where your team lives, QwenPaw saves you a lot of config headaches.

## Installation

QwenPaw has seven ways to get running: pip, the one-line script, Docker, an Alibaba Cloud ECS one-click deploy (ComputeNest), the free hosted AgentScope Platform, a ModelScope Studio fork (keep that one non-public), and a [desktop app in Beta](https://github.com/agentscope-ai/QwenPaw/releases) for Windows 10+ and macOS 14+. I cover the three that suit self-hosters.

<Tabs>
<Tab name="pip install">

The cleanest path if you already have Python:

```bash
pip install qwenpaw          # requires Python >= 3.11, < 3.14
qwenpaw init --defaults
qwenpaw app
```

Open `http://127.0.0.1:8088/` and you'll see the Console. That's a working basic setup.

For interactive configuration where you pick your LLM provider and channels upfront:

```bash
qwenpaw init
```

This walks you through heartbeat interval, target channel, active hours, and optional skill setup. Two things worth knowing: the `copaw` command still works as an alias for `qwenpaw`, and `init --defaults` auto-accepts anonymous usage telemetry while interactive `init` prompts you (details in the [FAQ](#faq)).

</Tab>
<Tab name="One-line install">

No Python needed. The installer handles everything using [uv](https://docs.astral.sh/uv/).

**macOS / Linux:**

```bash
curl -fsSL https://qwenpaw.agentscope.io/install.sh | bash
```

**Windows (PowerShell):**

```powershell
irm https://qwenpaw.agentscope.io/install.ps1 | iex
```

Open a new terminal after install (PATH changes only apply to new shells), then:

```bash
qwenpaw init --defaults
qwenpaw app
```

Useful installer flags:

```bash
# pin a version
curl -fsSL https://qwenpaw.agentscope.io/install.sh | bash -s -- --version 2.3.0

# install from source
curl -fsSL https://qwenpaw.agentscope.io/install.sh | bash -s -- --from-source

# extras: local, whisper, channels, full
# channels/full apply the channel plugin preset offline during install
curl -fsSL https://qwenpaw.agentscope.io/install.sh | bash -s -- --extras channels,whisper
```

To upgrade later, just re-run the installer. It runs `qwenpaw plugins prepare-upgrade` for you. If you have the old `copaw.agentscope.io` URLs in scripts, replace them: that domain no longer resolves.

</Tab>
<Tab name="Docker">

The QwenPaw Docker image lives at `agentscope/qwenpaw` (99 tags; `latest` is stable, `pre` is pre-release). Unlike the 1.x image, it now uses three volumes:

```bash
docker pull agentscope/qwenpaw:latest

docker run -d --name qwenpaw --restart unless-stopped \
  -p 127.0.0.1:8088:8088 \
  -v qwenpaw-data:/app/working \
  -v qwenpaw-secrets:/app/working.secret \
  -v qwenpaw-backups:/app/working.backups \
  -e DASHSCOPE_API_KEY=your_key_here \
  agentscope/qwenpaw:latest
```

- `qwenpaw-data:/app/working`: config, memory, skills
- `qwenpaw-secrets:/app/working.secret`: model provider settings and API keys
- `qwenpaw-backups:/app/working.backups`: backup archives

Pin `agentscope/qwenpaw:v2.3.0` if you want boring deploys; `latest` moves weekly. There's an ACR mirror for users in China: `agentscope-registry.ap-southeast-1.cr.aliyuncs.com/agentscope/qwenpaw`. The upstream [docker-compose.yml](https://github.com/agentscope-ai/QwenPaw/blob/main/docker-compose.yml) is worth a look; it adds `restart: always` and `init: true`, plus console auth env vars.

If you need QwenPaw in Docker to reach Ollama on the host:

```bash
docker run -p 127.0.0.1:8088:8088 \
  --add-host=host.docker.internal:host-gateway \
  -v qwenpaw-data:/app/working \
  -v qwenpaw-secrets:/app/working.secret \
  agentscope/qwenpaw:latest
```

Then set the Ollama Base URL to `http://host.docker.internal:11434/v1` in the Console. LM Studio users: `http://host.docker.internal:1234/v1`. On Linux, `--network=host` also works (no `-p` needed).

<Notice type="warning" title="If you expose the console">
The container binds `127.0.0.1:8088` on purpose. If you ever reverse-proxy the console to the internet, set `QWENPAW_AUTH_ENABLED=true`, `QWENPAW_AUTH_USERNAME` and `QWENPAW_AUTH_PASSWORD`, or put it behind your proxy's auth. Better: don't expose it at all and reach it through an [SSH port forwarding guide](/ssh-tunneling-linux/) tunnel.
</Notice>

</Tab>
</Tabs>

Open a new shell session, then:

To keep it running after you close the SSH session, use systemd (a tmux session works too, but systemd survives reboots). Find your binary path with `which qwenpaw`, then create `/etc/systemd/system/qwenpaw.service`:

```ini
[Unit]
Description=QwenPaw assistant
After=network.target

[Service]
WorkingDirectory=/root/.qwenpaw
ExecStart=/root/.local/bin/qwenpaw app
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload
systemctl enable --now qwenpaw
systemctl status qwenpaw
curl -sI http://127.0.0.1:8088
```

That last command should return HTTP 200. The console binds to localhost only, so manage it over an [SSH port forwarding guide](/ssh-tunneling-linux/) tunnel: `ssh -L 8088:127.0.0.1:8088 root@YOUR_SERVER_IP`. If you put it behind a reverse proxy instead, read the console auth warning in the Docker tab above.

### Uninstalling

```bash
qwenpaw uninstall          # keeps config and data
qwenpaw uninstall --purge  # removes everything
```

Same semantics as before, just renamed. On Docker, purge does not remove the volumes. That's on you:

```bash
docker volume rm qwenpaw-data qwenpaw-secrets qwenpaw-backups
```

## Upgrading from CoPaw to QwenPaw

If you installed this assistant back when it shipped under the old name, here's the migration in one place. The rename landed at v1.1.0 on 2026-04-12 ([release note](https://github.com/agentscope-ai/QwenPaw/releases/tag/v1.1.0)).

What changed for you comes down to five things. Install `qwenpaw`; the old `copaw` package is frozen at 1.0.2 and has had no updates since 2026-04-09, so it will not get 2.x features. The command is `qwenpaw` now, with `copaw` kept as an alias pointing at the same entry point, so muscle memory works. The Docker image moved from `agentscope/copaw` to `agentscope/qwenpaw`, and the data layout went from one volume to three (`working`, `working.secret`, `working.backups`). Everything lives at `qwenpaw.agentscope.io`; the old `copaw.agentscope.io` domain is dead, so update any scripts or cron jobs that call it. Local data lives in `~/.qwenpaw/` now (plus `~/.qwenpaw.secret/`). If you have data under `~/.copaw`, don't assume it auto-migrates. Check the [QwenPaw docs](https://qwenpaw.agentscope.io/docs), copy the directory over yourself, and confirm memory and config load before you delete anything. I have not verified an automatic migration path.

## Model configuration

Before QwenPaw can do anything useful, configure an LLM. Open the Console at `http://127.0.0.1:8088/` and go to **Settings → Models**.

### Cloud providers

QwenPaw works with 14+ cloud providers out of the box: DashScope/Qwen, OpenAI, Anthropic, Google Gemini, DeepSeek, Kimi, OpenRouter and more. For any of them:

1. Go to **Settings → Models** in the Console
2. Find the provider card and click **Settings**
3. Enter your API key and click **Save**
4. The card status changes to **Available**. That's your verify step
5. In the **LLM Configuration** section at the top, select the provider and model, then click **Save**

You can also set API keys as environment variables. For DashScope:

```bash
export DASHSCOPE_API_KEY=your_key_here
```

Or put it in a `.env` file in the working directory (`~/.qwenpaw/` for native installs, `/app/working` in Docker). Tool keys (a web search key like `TAVILY_API_KEY`, for example) can also be set in **Console → Settings → Environment variables**.

### Using OpenAI or Azure OpenAI

Anything with an OpenAI-compatible API works through the custom provider system:

1. Click **Add provider** on the Models page
2. Enter a Provider ID (for example `openai`) and display name
3. Click **Settings**, enter the Base URL (`https://api.openai.com/v1` for OpenAI) and API key
4. Click **Models**, add the model ID your account has access to
5. Select it in the LLM Configuration dropdown

### Local models: QwenPaw-Flash, Ollama and LM Studio

Local backends need no API keys. The old per-backend pip extras are gone; local model support is built in.

| Backend | Best for | Setup |
|---|---|---|
| **QwenPaw Local** (built-in llama.cpp runtime) | Cross-platform, zero config | Click **Download** in the web UI; it gives hardware-aware model recommendations |
| **Ollama** | Anyone already running Ollama | Install Ollama, pull a model, set context length to at least 32k |
| **LM Studio** | Desktop users with LM Studio | Enable the Local Server; Base URL `http://localhost:1234/v1` (`http://host.docker.internal:1234/v1` from Docker) |

<Notice type="warning" title="Ollama context length">
Set Ollama's context length to 32k or more for the model you connect. Below that you get truncated replies and weird mid-sentence cutoffs that look like model quality problems but aren't.
</Notice>

The recommended local models are now **QwenPaw-Flash**, purpose-trained agent models in 2B / 4B / 9B / 35B-A3B / 27B sizes with Q4 and Q8 quantizations, published on ModelScope and Hugging Face under the `agentscope-ai/models` org. The 2B and 4B variants run on modest hardware, the 9B wants around 16 GB RAM, and the MoE 35B-A3B is the quality pick if you have the memory. For hardware that runs these models well, see [best mini PCs for local LLMs](/best-mini-pc-local-llm/). If you'd rather keep a quiet box at home than rent a VPS, something like the [ASUS DC510 mini PC](https://go.bitdoze.com/asus-dc510) runs the small models comfortably.

v2.3.0 also added **Piccolo** decision models (4B/9B/27B) for opt-in tool review and context compaction. Nice to have, not a setup blocker.

Model downloads happen in the web UI: **Settings → Models**, then **Download** on the QwenPaw Local card. For Ollama, pull models through Ollama as usual (`ollama pull qwen3:4b`) and QwenPaw syncs with whatever is available. See the [Ollama Docker Compose setup with Open WebUI](/ollama-docker-install/) if you're running Ollama in a container.

## Channel setup: Discord, Telegram, DingTalk and more

Channels are how you talk to QwenPaw from your messaging apps. Since v2.3.0 channels are plugins: the `channels` and `full` installer extras run `qwenpaw plugins preset apply channels-full --offline`, and the Console (**Control → Channels**) is where you enable and configure them.

*Config key names can shift between releases. Save the channel in the Console first, then peek at `config.json` in your working directory to see the current shape. The snippets below show the 2.x layout, not a contract.*

### Discord

1. Create a Discord application at [discord.com/developers](https://discord.com/developers/applications)
2. Go to the **Bot** tab, click **Reset Token**, and copy the bot token
3. Under **Privileged Gateway Intents**, enable **Message Content Intent**
4. Generate an OAuth2 invite URL with `bot` scope and `Send Messages` + `Read Message History` permissions
5. Invite the bot to your server
6. In the QwenPaw Console, go to **Control → Channels**, click **Discord**, enable it, and paste the token

```json
{
  "channels": {
    "discord": {
      "enabled": true,
      "token": "YOUR_DISCORD_BOT_TOKEN"
    }
  }
}
```

Verify: send the bot a DM and expect a reply. No reply plus a silent log usually means Message Content Intent is off.

### Telegram

1. Open Telegram, search for **@BotFather**, send `/newbot`
2. Pick a name and username, copy the token
3. In the Console, enable Telegram and paste the token

```json
{
  "channels": {
    "telegram": {
      "enabled": true,
      "token": "YOUR_TELEGRAM_BOT_TOKEN"
    }
  }
}
```

Verify: message your bot and confirm the first reply arrives.

### DingTalk

DingTalk setup involves creating a custom app in the DingTalk developer console. QwenPaw has a built-in skill called `dingtalk_channel_connect` that walks you through credential lookup, Client ID/Secret configuration, and the manual steps. Enable the DingTalk channel in the Console and follow the guided prompts.

### Feishu (Lark)

Same idea as DingTalk. Create an app in the Lark (Feishu) Open Platform, grab the App ID and App Secret, and enter them in the Console. QwenPaw also supports a SOCKS proxy for Lark if you're behind a corporate firewall.

### WeChat and QQ

WeChat is a recent addition to the channel lineup and QQ has been there since the start. Setup differs per region and platform policy, so I'm not going to pretend the steps are stable. The [channel docs](https://qwenpaw.agentscope.io/docs/channels) have the current flow. Expect to create a platform-side app and paste credentials into the Console like the other channels.

### iMessage (macOS only)

If you're running QwenPaw on a Mac, iMessage works as a channel. This is still one of the few self-hosted assistants that supports iMessage natively.

### Multiple channels at once

QwenPaw can connect to several channels simultaneously. Messages go to whichever channel you last talked in, or you can target specific channels for scheduled messages.

## Skills and plugins

Skills are how QwenPaw does more than chat. Several come built-in, and since 2.x there's a plugin architecture with a marketplace and MCP integration. That extensibility is now the headline.

### Built-in skills

Core skills as of v2.3.0:

| Skill | What it does |
|---|---|
| **cron** | Scheduled jobs: create, list, pause, resume, delete |
| **file_reader** | Read and summarize text files (.txt, .md, .json, .csv, .py, etc.) |
| **pdf** | Read, extract, merge, split, rotate, watermark, OCR PDFs |
| **docx** | Create, read, and edit Word documents |
| **xlsx** | Read, edit, and create spreadsheets |
| **pptx** | Create, read, and edit PowerPoint files |
| **news** | Fetch and summarize latest news from configured sources |
| **browser_visible** | Launch a headed browser for demos or CAPTCHA scenarios |

v2.1.0 through v2.3.0 added browser-use, computer-use and Code Mode on top of these.

### Managing skills in the Console

Go to **Agent → Skills** in the Console to see all loaded skills, toggle them on or off, create custom skills, or edit existing ones.

### Importing skills from hubs

The official Plugin Market (unified marketplace since v2.2.0) is the first place to look. Community hubs like `skills.sh`, `clawhub.ai` and `skillsmp.com` worked with 1.x, and importing from any GitHub repository with a `SKILL.md` file is the underlying mechanism. Check the [skills docs](https://qwenpaw.agentscope.io/docs/skills) for what the current release officially supports.

<Notice type="warning" title="Untrusted skills run on your box">
A skill is code and instructions that execute with your agent's permissions. Run Tool Guard in STRICT mode while evaluating third-party skills, and use the Skill Scanner (see [Security](#security-sandbox-tool-guard-and-file-guard) below).
</Notice>

### Creating custom skills

Drop a folder with a `SKILL.md` file into `~/.qwenpaw/customized_skills/` (the path follows the working directory, so on Docker it's under `/app/working`):

```
~/.qwenpaw/
  customized_skills/
    my_research_skill/
      SKILL.md
```

The `SKILL.md` is plain Markdown that describes what the skill does:

```markdown
---
name: my_research_skill
description: Research a topic and summarize findings
---

# Research Skill

When asked to research something:
1. Search the web for current information
2. Summarize key findings in bullet points
3. List sources
```

QwenPaw picks up new skills on restart. Custom skills take priority over built-in ones when names collide. For a real-world example of what a custom skill looks like in practice, see my [Docker AI deploy skill guide](/ai-docker-deploy-skill/).

### Plugins, the marketplace and MCP

Since v2.3.0, channels themselves are plugins, and **Settings → Plugins** is the hub: install from the Plugin Market, manage presets, and connect **MCP servers** as tool providers. If you use MCP tools elsewhere in your stack, this is how you reuse them inside your assistant.

Two plugins matter if you run coding agents: the **Codex** and **Qoder** backends are optional installs via **Settings → Plugins** (the `full` installer extra excludes their SDKs, so install them explicitly). There are [migration notes for optional Codex and Qoder backends](https://qwenpaw.agentscope.io/docs/plugins#optional-codex-and-qoder-backends) in the docs. If a plugin install gets interrupted, see [Troubleshooting](#interrupted-plugin-or-skill-install) below before you re-run blindly.

## Memory system

QwenPaw's memory is the part that makes it feel like an assistant instead of a chatbot. Since v2.0.0 it runs on three layers:

1. The **live working context** is the current conversation and what the agent is doing right now.
2. The **full verbatim history** is a SQLite `history.db` with FTS5 full-text search, 30-day default retention, and usage-aware ranking (recency plus frequency). Old turns are recallable through the `recall_history_python` REPL. v2.2.1 added Auto Fin, a proactive memory review pass; v2.3.0 added image memory and tag browsing.
3. The **self-evolving knowledge base** is backed by [ReMe](https://github.com/agentscope-ai/ReMe) v0.4.0. It writes memory as it goes (turn-based, not at session close) and stores it as Markdown you can read and edit by hand.

That last layer is the one worth knowing about. It looks like this:

```
~/.qwenpaw/
  MEMORY.md                    # Long-term facts, preferences, decisions
  memory/
    2026-11-15.md              # Daily log
    2026-11-14.md
    ...
```

`MEMORY.md` holds persistent information: things like "I prefer Python 3.12" or "My team uses Slack for standups." Daily logs capture what happened in each conversation. Search across all of it is hybrid: vector semantic search plus full-text, and since v2.0.0 the embedding model is selected in the config UI instead of a pile of environment variables.

Tell it what to remember directly:

> "Remember: I always deploy to staging before production."

It writes this to `MEMORY.md`. You can edit the files yourself whenever the agent gets something wrong:

```bash
nano ~/.qwenpaw/MEMORY.md
```

## Scheduled tasks and heartbeat

QwenPaw runs things on a schedule two ways: cron jobs for specific commands, and heartbeat for periodic check-ins.

### Cron jobs

```bash
# Create a job that runs at 9am every day
qwenpaw cron create --type agent --name "morning-digest" --cron "0 9 * * *" --message "Summarize my pending tasks and calendar for today"

# List all jobs
qwenpaw cron list

# Check a job's state
qwenpaw cron state <job_id>
```

You can also manage cron jobs from the Console under **Control → Cron Jobs**. Check `qwenpaw cron --help` for the full flag list in your version. Verify: `qwenpaw cron list` shows the job after creation.

### Heartbeat

Heartbeat is the scheduled check-in. You write a block of questions in a Markdown file, and QwenPaw runs through them on a timer and sends the answers to your last-used channel. Set it up during `qwenpaw init` or edit `HEARTBEAT.md` in the working directory.

Example `HEARTBEAT.md`:

```markdown
Check the following and report back:
- Any new emails from clients?
- What meetings do I have today?
- Summarize overnight GitHub notifications
```

Interval and active hours live in the Console settings, or in `config.json` (key names have shifted between releases, so confirm the shape in your own file after setting it in the UI):

```json
{
  "heartbeat": {
    "enabled": true,
    "interval": "2h",
    "active_hours": "08:00-22:00"
  }
}
```

Verify: wait for the first heartbeat to land in your channel. If nothing arrives, check that a target channel is configured and that active hours cover the current time.

## Security: sandbox, Tool Guard and File Guard

An agent that runs tools on your box is a blast-radius question first. QwenPaw ships a five-layer security stack. It's the strongest argument for picking it over the alternatives if you plan to run third-party skills:

| Layer | What it does |
|---|---|
| **Sandbox** | Kernel-level isolation for tool execution: Seatbelt on macOS, Bubblewrap + Landlock on Linux, AppContainer on Windows |
| **Tool Guard** | YAML rules with approval levels: STRICT / SMART / AUTO / OFF |
| **File Guard** | Default-protects `~/.qwenpaw.secret/` and `~/.ssh` from skill and plugin access |
| **Skill Scanner** | Inspects skills before running: block / warn / off |
| **Access Policy** | Restricts what the agent can reach at all |

Practical defaults I'd use: run Tool Guard on STRICT while you evaluate any skill you didn't write, keep API keys in the protected secrets directory (the Docker layout separates `working.secret` into its own volume for exactly this reason), and leave the Skill Scanner on block. For the wider threat model of untrusted skills in self-hosted agents, my [OpenClaw security guide](/openclaw-security-guide/) covers the same blast-radius framing from the other project's angle.

## Backups, updates and day-2 operations

<Notice type="info" title="Back up three things">
Config, memory and skills live in <code>working</code>. API keys and provider settings live in <code>working.secret</code>. Backup archives live in <code>working.backups</code>. Those three are what matter.
</Notice>

On Docker, grab all three volumes in one tar:

```bash
docker run --rm \
  -v qwenpaw-data:/data \
  -v qwenpaw-secrets:/secrets \
  -v qwenpaw-backups:/backups \
  -v "$PWD":/backup alpine \
  tar czf /backup/qwenpaw-$(date +%F).tar.gz data secrets backups
```

Natively:

```bash
tar czf qwenpaw-$(date +%F).tar.gz ~/.qwenpaw ~/.qwenpaw.secret
```

The official [backup docs](https://qwenpaw.agentscope.io/docs/backup) cover restore. Schedule the tar with cron and push it to S3 or whatever offsite target you already trust.

Updates: `pip install -U qwenpaw` for pip installs, re-run the installer for the script path (it handles plugin upgrades), or re-pull the image for Docker. Pin `agentscope/qwenpaw:v2.3.0` in compose if you want to review release notes before moving. `latest` changes weekly and this project went from 2.0.0 to 2.3.0 in four months with weekly betas in between. Read the [release notes](https://github.com/agentscope-ai/QwenPaw/releases) before jumping a minor version.

One disclosure for the ops crowd: `qwenpaw init --defaults` auto-accepts anonymous usage telemetry (once per version, no personal data). The interactive `init` asks first. Details in the FAQ.

## What should you know about troubleshooting?

### Console won't load / QwenPaw not responding

If `http://127.0.0.1:8088/` doesn't load:

1. Is the process running? (`systemctl status qwenpaw` or `docker ps`)
2. Is the port taken? `ss -ltnp | grep 8088`. A leftover process or `--network=host` run can squat on it
3. Check the terminal output or `docker logs qwenpaw` for startup errors
4. If the console loads but nothing works, go to **Settings → Models** and verify a provider is **Available** with a model selected

### API key issues

If you see authentication errors:

- Double-check the API key in **Settings → Models**
- For DashScope, verify the key at [dashscope.console.aliyun.com](https://dashscope.console.aliyun.com/)
- Try setting the key as an environment variable instead: `export DASHSCOPE_API_KEY=xxx`
- Remember Docker env vars only apply when set on `docker run` or in compose

### Docker can't reach Ollama

Inside a container, `localhost` points to the container, not the host. Use `--add-host=host.docker.internal:host-gateway` and set the Ollama Base URL to `http://host.docker.internal:11434/v1`.

On Linux you can also use `--network=host`:

```bash
docker run --network=host \
  -v qwenpaw-data:/app/working \
  -v qwenpaw-secrets:/app/working.secret \
  agentscope/qwenpaw:latest
```

And set Ollama's context length to at least 32k, or you'll hit the truncation issue below.

### Channel not receiving messages

- Verify the channel is enabled in **Control → Channels**
- Check that tokens and credentials are correct
- For Discord, make sure **Message Content Intent** is enabled in the developer portal
- Restart QwenPaw after changing channel config

### Local model truncation or weird replies

If local model answers get cut off mid-sentence or lose the thread of a long request, the usual cause is an Ollama or LM Studio context length below 32k. Check the model's context settings on the serving side, not in QwenPaw.

### Windows quirks

On LTSC editions or with Constrained Language Mode, the installer may not update PATH. Add `%USERPROFILE%\.qwenpaw\bin` and the uv directory manually. The desktop app's first launch takes 10 to 60 seconds. That's normal, not a hang.

### Interrupted plugin or skill install

If a plugin or skill install dies halfway, re-run the installer (it runs `qwenpaw plugins prepare-upgrade` on upgrade) or re-apply the preset by hand:

```bash
qwenpaw plugins preset apply channels-full --offline
```

Then restart and check **Settings → Plugins** for the expected entries.

## FAQ

<Accordion label="Frequently Asked Questions" group="faq" expanded="true">

**What happened to CoPaw?**

The project was renamed to QwenPaw at v1.1.0 on 2026-04-12. Same team (AgentScope, Alibaba), same codebase, new name. The pip package is now `qwenpaw` (the old one is frozen at 1.0.2), the Docker image is `agentscope/qwenpaw`, and the `copaw` command still works as a CLI alias. Old GitHub links redirect. This guide's URL kept the original slug, which is why it still says `copaw-setup-guide`.

**Do I need to know Python?**

No. The one-line installer, Docker and the desktop app need no Python. Only the `pip install qwenpaw` path does, and it wants Python 3.11 to 3.13. Python skills only matter if you write custom skills or install from source.

**Which cloud provider should I start with?**

DashScope is the default and usually the cheapest entry. If you already have an OpenAI, Anthropic or Gemini key, add it and go. For zero API cost, use QwenPaw Local or Ollama with a local model.

**Can I run it on a Raspberry Pi?**

Fine as a relay to cloud models on a Pi 4 or 5 with 4 GB RAM. Weak for local models; even QwenPaw-Flash 4B will be slow. A cheap VPS or a used mini PC is a better experience.

**Does it work on Windows?**

Yes. Use the PowerShell installer (`irm https://qwenpaw.agentscope.io/install.ps1 | iex`), Docker, or the [desktop app in Beta](https://github.com/agentscope-ai/QwenPaw/releases) (Windows 10+, no Python needed). The pip path works too if you have Python 3.11+. On LTSC, see the Windows quirks note in Troubleshooting.

**Can multiple people use one instance?**

Two options. QwenPaw replies in the channel where you last talked, so group channels in DingTalk, Lark or Discord work for shared use. For proper multi-user isolation, v2.2.0 added QwenPaw Hub, a self-hosted multi-user mode.

**Is my data private?**

Your config, memory, conversations and files stay on your machine, and the only external calls are to the LLM provider you configured. With local models, nothing leaves the box at all. One honest caveat: `qwenpaw init` sends anonymous usage data once per version (version, install method, OS, Python version, architecture, GPU yes/no; no personal data, no IP, no files). `init --defaults` auto-accepts; interactive `init` prompts you. Check the docs for the opt-out if the prompt matters to you.

**How does it compare to OpenClaw?**

OpenClaw has broader Western messaging support (WhatsApp, Slack). QwenPaw has first-class DingTalk, Lark and WeChat support, a built-in web console, three local model backends and a real security stack. Both are open source and self-hosted. See my [OpenClaw setup guide](/clawdbot-setup-guide/) for the other side.

The built-in QwenPaw Local runtime plus Ollama and LM Studio support means you can run it with zero API cost, and if DingTalk or Lark is where your team lives, it's the most polished option I've found for those platforms.
