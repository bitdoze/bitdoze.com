## CVE-2026-25253: The 1-click RCE, already fixed

A correction before we go further. CVE-2026-25253 is **not** the ClawHub supply chain attack. Early coverage conflated the two because the GitHub issue reporting the ClawHub attack (#16052) referenced the CVE number in its title. But CVE-2026-25253 is a separate bug: a 1-click remote code execution via authentication token exfiltration from the `gatewayUrl` parameter. The ClawHub 341-skill attack does not appear to have its own CVE assigned.

CVE-2026-25253 is tracked as [GHSA-g8p2-7wf7-98mq](https://github.com/openclaw/openclaw/security/advisories/GHSA-g8p2-7wf7-98mq), with a CVSS score of 8.8 (HIGH). It affected package `clawdbot` (the old name) in versions up to and including v2026.1.28. It was **fixed in v2026.1.29**. If you're running anything from the 2026.2.x releases onward, you are already patched. Credit goes to Mav Levin at [depthfirst](https://depthfirst.com/post/1-click-rce-to-steal-your-moltbot-data-and-keys) (writeup published 2026-02-01) and the fix commit `a7534dc2`.

### How the gatewayUrl token exfiltration worked

The Control UI (the web dashboard) trusted a `gatewayUrl` parameter from the query string. When someone opened the UI with a crafted URL, the UI would:

1. Take the `gatewayUrl` value from the query string
2. Persist it as the gateway address
3. Auto-connect on page load via WebSocket
4. Send the stored gateway authentication token in the WebSocket handshake

A single crafted link or a malicious page embedding the link = token theft = full gateway access. The attacker could then change configuration, make privileged calls, and pivot further.

One important nuance: this worked **even when the gateway binds to loopback**. The victim's browser is the bridge. The browser can reach `localhost:18789`, so the gateway's loopback binding doesn't protect against this attack.

```
crafted link → browser opens Control UI → gatewayUrl from query string persisted
    → auto-connect sends gateway token over WebSocket → attacker receives token
        → full gateway access (config changes, privileged calls)
```

The fix: users must now confirm new gateway URLs in the UI before the connection is established. The UI no longer silently trusts query-string `gatewayUrl` values.

### Are you affected?

Run `openclaw --version`. If your version is v2026.1.29 or newer, this is patched.

```bash
openclaw --version
# Want: 2026.1.29 or later (any 2026.2.x or newer is fine)
```

If you were running v2026.1.28 or older in January-February 2026, rotate your gateway token once as a precaution. This section stays for reference: the attack shape (browser as a bridge past loopback) is exactly what the Control UI origins step in the hardening guide below defends against.

<Notice type="info" title="Already Patched: Kept for Reference">
This section is historical context. The bug has been fixed for months. But the attack pattern (using the victim's browser to reach a loopback-bound service) is a class of defense worth understanding. See hardening step 7 for the origin controls that prevent it.
</Notice>

## The ClawHub supply chain attack: 341 malicious skills

On February 13, 2026, security researchers reported ([GitHub issue #16052](https://github.com/openclaw/openclaw/issues/16052), closed 2026-02-21) that 341 of 2,857 audited skills on ClawHub, the community skill marketplace, were compromised in a coordinated supply chain attack. That is a 12% infection rate. No CVE ID was assigned to the ClawHub attack itself.

### How the attack worked

The malicious skills looked like normal tools. The most documented example, `deeps-agnw6h`, posed as a "Deep-Agent/Deep-Search" research tool. Infected skills contained up to three attack vectors:

**1. macOS dropper (base64-encoded shell)**

A base64 payload decoded to a curl command that downloaded and executed arbitrary code from an attacker-controlled server at `91.92.242.30` (Bulgarian hosting range, linked to info-stealer infrastructure).

**2. Fake Windows installer**

A GitHub repository (`toolitletolate/openclaw_windriver`) hosted a malicious MSI installer disguised as a driver package.

**3. MCP backdoor**

A hidden MCP server endpoint routed through `bore.pub` tunneling to attacker infrastructure, giving remote access to any machine running the infected skill.

### Indicators of compromise

If you suspect your instance may be affected, check for these:

| Type | Value | Notes |
|------|-------|-------|
| **IP address** | `91.92.242.30` | macOS payload delivery server |
| **URL path** | `http://91.92.242.30/6wioz8285kcbax6v` | Dropper payload |
| **Tunnel domain** | `bore.pub` | Reverse tunneling for MCP backdoor |
| **Tunnel port** | `44876` | MCP backdoor endpoint |
| **GitHub repo** | `toolitletolate/openclaw_windriver` | Fake Windows installer |

Check your network logs for connections to these addresses. If you find matches, assume compromise and rotate all API keys and credentials stored in your OpenClaw config.

### What to do right now

If you installed any skills from ClawHub before mid-February 2026, work through this checklist:

<ListCheck>
<ul>
<li>Update OpenClaw: `openclaw update`</li>
<li>Run `openclaw security audit --deep` and review every finding</li>
<li>Check installed skills: `openclaw skills list`; remove anything you don't recognize</li>
<li>Search your network logs for `91.92.242.30` and `bore.pub`</li>
<li>If compromised: rotate all API keys, gateway tokens, and channel credentials</li>
<li>Review open connections: `ss -tlnp | grep openclaw` to check for unexpected listeners</li>
</ul>
</ListCheck>

<Notice type="warning" title="IoC Match = Full Compromise">
If any indicator above matches, treat it as full compromise. Rotate first, investigate second. The official incident response sequence is **contain, rotate, audit, evidence** (see the [operator incident response runbook](https://docs.openclaw.ai/gateway/security/operator-incident-response)). Key rotation is free, but budget 30-60 minutes per instance to do it properly.
</Notice>

If the supply chain risk changes your calculus on community skills entirely, there are [OpenClaw alternatives with different security models](/openclaw-alternatives/) worth evaluating.

## 300+ OpenClaw vulnerabilities fixed in four 2026 waves

The "40+ fixes" story from February 2026 is obsolete. As of November 2026, the [GitHub security advisories list](https://github.com/openclaw/openclaw/security/advisories) for openclaw/openclaw shows **300 published advisories**: 153 high severity, 132 medium, and 15 low. They were disclosed in two batches (75 on 2026-06-30, 225 on 2026-09-11) and remediated in waves across the 2026.6.x through 2026.10.x releases.

### The February wave

The fixes shipped in the 2026.2.x releases right after the incidents. Here's what was patched, grouped by category. This is historical context: all of these are long since fixed.

**Exec approval bypasses (7 fixes):**

| Fix | What Was Wrong |
|-----|---------------|
| Cross-node replay | Approved `system.run` requests could be replayed across different nodes |
| Orphaned approvals | Two-phase approval registration had a race condition that let approvals skip the wait step |
| `env -S` bypass | `env --split-string` wrapper interpretation mismatch let commands bypass allowlist checks |
| `busybox`/`toybox` applets | Multiplexer binaries weren't recognized in wrapper analysis, allowing allow-always bypasses |
| `autoAllowSkills` path collision | Absolute-path basename collisions could satisfy skill auto-allow checks |
| Safe-bin flag denylist gaps | Unknown GNU long-option abbreviations and filesystem-dependent `sort` flags weren't blocked |
| Obfuscated command detection | Obfuscated commands weren't checked before exec allowlist decisions |

**Sandbox and path traversal escapes (4 fixes):**

| Fix | What Was Wrong |
|-----|---------------|
| `apply_patch` workspace escape | Sandbox-mounted paths like `/agent` allowed writes/deletes outside the workspace boundary |
| Image tool path traversal | `tools.fs.workspaceOnly` wasn't enforced for sandboxed `image` path resolution |
| Shell env fallback | Trusted-prefix shell-path fallback allowed untrusted shells; now only `/etc/shells` entries are trusted |
| Config path traversal | Prototype-key segments and inherited-property traversal weren't rejected in `config get/set/unset` paths |

**XSS and injection (5 fixes):**

| Fix | What Was Wrong |
|-----|---------------|
| Session export HTML injection | Raw HTML markdown tokens in exported session viewer weren't escaped |
| Export image data-URL injection | Image MIME/base64 fields in exported HTML weren't validated |
| Skill HTML gallery XSS | `openai-image-gen` skill didn't escape user-controlled values in generated HTML |
| Skill packaging symlink escape | `skill-creator` didn't skip symlinks or reject paths escaping the skill root |
| iOS deep link exfiltration | `openclaw://agent` requests forwarded to gateway without local confirmation |

**Prototype pollution and config safety (3 fixes):**

| Fix | What Was Wrong |
|-----|---------------|
| Account-ID normalization | Reserved prototype keys weren't blocked in account-id normalization |
| Config write mutations | `unsetPaths` could mutate caller-provided objects |
| CLI config credential leakage | `openclaw config get` output wasn't redacted before printing |

**Channel and access control (5 fixes):**

| Fix | What Was Wrong |
|-----|---------------|
| Command sender spoofing | `commands.allowFrom` matched conversation-shaped `From` identities (channels, groups, threads) |
| Mutable name matching | `allowFrom` matched on mutable names/tags/emails instead of stable IDs |
| Name-matching policy inconsistency | `dangerouslyAllowNameMatching` checks varied between core and extension channels |
| ACP auto-approval scope | Unknown tool names and out-of-scope file reads were auto-approved |
| `selfChatMode` bypass | WhatsApp inbound access control didn't honor `selfChatMode` setting |

**SSRF and network (2 fixes):**

| Fix | What Was Wrong |
|-----|---------------|
| Telegram media SSRF | RFC2544 benchmark range (`198.18.0.0/15`) wasn't blocked by default for media downloads |
| Browser SSRF policy | Private network access defaulted to allowed without explicit config |

**Voice, webhooks, and other (4+ fixes):**

| Fix | What Was Wrong |
|-----|---------------|
| Twilio webhook replay | Provider event IDs weren't preserved through normalization, allowing replay attacks |
| OTEL credential leakage | API keys and tokens were included in OTLP export diagnostics |
| Reasoning/thinking leakage | Internal reasoning blocks leaked as user-visible replies in WhatsApp, Discord, Web |
| Session reset credential leakage | `/new` and `/reset` confirmation messages exposed API key prefixes |

## Reading ClawHub audit labels before you install

After the February 2026 attack, ClawHub rolled out a full audit and moderation system. This is the ecosystem's direct answer to the supply chain problem, and you should use it.

### Audit statuses and risk levels

Every ClawHub skill release gets a security audit with two dimensions:

**Status** (the verdict):

| Status | Meaning |
|--------|---------|
| **Pass** | No significant findings. Safe to install per the audit. |
| **Review** | Findings that need human judgment. Read the details before installing. |
| **Warn** | Risky patterns found. Proceed only if you understand the findings. |
| **Malicious** | Do not install. The skill contains hostile code or patterns. |
| **Pending** | Audit not yet complete (new or updated release). |
| **Error** | Audit failed to complete. Treat with caution. |

**Risk level** (the severity): Low, Medium, or High. Individual findings are graded from Info to Critical. Low-confidence findings are hidden from the rollup so you don't drown in noise.

What ClawHub checks: skill instructions and metadata, declared environment variables and permissions, install instructions, file manifests, and capability metadata. The core question is **coherence**: does the skill's actual content match its claimed purpose? A "weather lookup" skill that shells out to `curl` and base64-decodes payloads will fail the coherence check.

ClawHub also has a moderation layer: user reports, holds on suspicious listings, hidden listings, and bans. External listings (marked `skills-sh:`) are flagged **"Not scanned by ClawHub"** and that state persists across updates.

### Verify and pin skill versions

The CLI gives you verification and pinning tools:

```bash
# Verify a specific skill and show its audit card
openclaw skills verify @owner/my-skill --card

# Install a pinned version
openclaw skills install @owner/my-skill --version 1.2.0

# Update all installed skills (deliberately unpins)
openclaw skills update --all
```

Before installing any skill:

<ListCheck>
<ul>
<li>Audit status is **Pass** (or you've read and accepted the **Review** findings)</li>
<li>Risk level is **Low** (or you understand the Medium/High risks)</li>
<li>Run `openclaw skills verify @owner/slug --card` and read the audit card</li>
<li>Pin a specific version with `--version` for predictable upgrades</li>
<li>Read the install instructions and declared permissions before confirming</li>
</ul>
</ListCheck>

<Notice type="success" title="This Is the Ecosystem's Fix">
The audit labels, moderation system, and version pinning are exactly what was missing in February 2026. Use them. A skill labeled Pass with Low risk has been scanned for the same patterns that caught the 341 malicious skills.
</Notice>

Version pinning means predictable upgrades: you decide when to move to a new version. When you're ready to update everything at once, `openclaw skills update --all` does it deliberately.

If you want a container-isolated alternative for running third-party agent code, [NanoClaw in Docker](/nanoclaw-deploy-guide/) keeps the blast radius contained to a single container.

## The soul-evil hook: A removed built-in risk

Separate from the ClawHub attack, researchers flagged another problem in [issue #8776](https://github.com/openclaw/openclaw/issues/8776): OpenClaw shipped with a bundled hook called `soul-evil` that could silently swap the agent's core system prompt (`SOUL.md`) with an alternate file (`SOUL_EVIL.md`). Disabled by default, but the code was there in every installation.

The mechanism was bad: an attacker with prompt injection access could chain the `write` tool to create `SOUL_EVIL.md` and then use `config.patch` to enable the hook. The agent would then run under attacker-controlled instructions with no notification. Worse when paired with CVE-2026-25253, since an exfiltrated gateway token could enable this hook remotely.

<Notice type="success" title="Removed From the Codebase">
The soul-evil hook was removed from the codebase entirely in the February 2026 releases (PR #14757, merged 2026-02-12). It is no longer present in any current install. If your installation predates February 2026, update it. Don't just disable the hook.
</Notice>

The lesson: bundled capabilities are bundled risk. Hooks are now first-class documented features, and you should know which ones your install loads. After updating, check your config for hook entries you didn't add yourself.

**Verify:** `openclaw --version` shows a post-February-2026 release. Grep your config for `soul-evil` or `SOUL_EVIL`. You should find nothing.

## Understanding the OpenClaw trust model

Before changing any settings, know what OpenClaw considers in-scope vs. out-of-scope for security. Misunderstanding this leads to either false confidence or wasted effort.

### Core principles

<Tabs>
<Tab name="What's Trusted">

- **Authenticated gateway callers** are treated as trusted operators
- **Session identifiers** (sessionKey, session IDs, labels) are routing controls, not authorization boundaries
- **Plugins/extensions** run in-process with full OS privileges
- **Workspace memory files** (MEMORY.md, memory/*.md) are treated as trusted local operator state
- **Exec approvals** are operator guardrails, not a multi-tenant authorization boundary

</Tab>
<Tab name="What's NOT a Boundary">

- One gateway is NOT a multi-tenant, adversarial user boundary
- If one operator can view data from another on the same gateway, that's expected
- Memory search returning content written by another process is expected behavior
- Plugins having the same OS privileges as the OpenClaw process is by design

</Tab>
<Tab name="Recommended Setup">

- **One user per machine/host** (or VPS). For dedicated hardware, see the [best Mac mini for OpenClaw](/best-mac-mini-for-openclaw/). If that Mac mini needs more ports, the [ASUS DC510](https://go.bitdoze.com/asus-dc510) is a Thunderbolt 5 dock built for the job.
- **One gateway per user** with one or more agents inside
- For multiple users: use separate VPS instances or OS user boundaries. A [small Hetzner Cloud VPS](https://go.bitdoze.com/hetzner) per trust domain runs about EUR 4-5/month (cx22 class), so one instance per trust domain is affordable.
- For remote access: SSH tunnel or Tailscale, not public internet exposure

</Tab>
</Tabs>

Here's the mental model:

```
┌────── One machine / OS user = one trust domain ──────┐
│                                                      │
│   Gateway (18789)  Agents  Plugins  Memory  API keys │
│                                                      │
│     Everything in this box can see everything else   │
└──────────────────────────────────────────────────────┘
       ▲               ▲                  ▲
       │               │                  │
  Channel users   ClawHub skills   Prompt injection
```

If someone shares a gateway with you, they can see your conversations, your API keys, and your memory files. That's by design. OpenClaw's security boundary is the machine/OS user level, not the gateway level. Separate trust domains need separate instances.

A few boundary clarifications worth keeping straight: session identifiers are routing controls, not auth tokens. Exec approvals are guardrails for a single trusted operator, not a multi-tenant permission system. Plugins run with the same OS privileges as the OpenClaw process. Think **identity, scope, model** in that order: who is calling, what they can reach, and which model runs the agent.

The defaults are permissive. Per the trust-model docs, `tools.sessions.visibility` and `tools.agentToAgent.enabled` ship with broad cross-agent reach (the exact defaults have shifted between releases). Set them explicitly; don't rely on defaults matching your threat model. The hardening guide below sets them to locked-down values.

Running [OpenClaw with local Ollama models](/openclaw-ollama-local-models/) is another way to reduce blast radius: no third-party API keys sitting in config if a skill or instance is compromised.

## OpenClaw hardening guide (2026 baseline)

This is the operator-grade hardening path. Prerequisites: OpenClaw installed and running, access to the config file, and comfort with JSON config edits. Every command assumes a Linux VPS or Mac host.

Before touching anything, back up your config:

```bash
cp openclaw.json openclaw.json.bak.$(date +%F)
```

The official hardened baseline from the docs looks like this. Start here, then the numbered steps below explain each area and how to verify:

```json
{
  "gateway": {
    "mode": "local",
    "bind": "loopback",
    "auth": {
      "mode": "token",
      "token": "replace-with-long-random-token"
    }
  },
  "session": {
    "dmScope": "per-channel-peer"
  },
  "tools": {
    "profile": "messaging",
    "deny": ["group:automation", "group:runtime", "group:fs", "sessions_spawn", "sessions_send"],
    "fs": {
      "workspaceOnly": true
    },
    "exec": {
      "security": "deny",
      "ask": "always"
    },
    "elevated": {
      "enabled": false
    },
    "sessions": {
      "visibility": "agent"
    },
    "agentToAgent": {
      "enabled": false
    }
  },
  "channels": {
    "whatsapp": {
      "dmPolicy": "pairing",
      "groups": {
        "*": {
          "requireMention": true
        }
      }
    }
  }
}
```

### 1. Keep OpenClaw updated

This is the single highest-value thing you can do. Check your version and update:

```bash
openclaw --version
openclaw update
```

`openclaw update` handles the update flow for all install types. If you installed via the installer script (`curl -fsSL https://openclaw.ai/install.sh | bash`), it also manages the service. After a fresh install, run `openclaw gateway install` to set up the systemd service (Linux) or LaunchAgent (macOS).

Also run `openclaw doctor --fix`. It rotates a `hooks.token` that was accidentally reusing the gateway auth value.

**Verify:** `openclaw --version` prints v2026.8.1 or later (target: current stable).

**Failure modes:** npm-managed installs that keep running `npm update -g openclaw` instead of `openclaw update`. Document which install flow you used. Service not restarted after update: `systemctl restart openclaw` on Linux, or restart the LaunchAgent on macOS.

### 2. Run the built-in security audit

OpenClaw ships a built-in security scanner with roughly 135 check IDs:

```bash
openclaw security audit --deep
```

`--deep` adds live gateway and plugin collector checks. Without it, the audit stays cold and read-only. Add `--fix` to auto-remediate what it can:

```bash
openclaw security audit --deep --fix
```

For CI or cron, use `--json`:

```bash
openclaw security audit --deep --json > /var/log/openclaw-audit-$(date +%F).json
```

For authenticated runs against a live gateway: `openclaw security audit --deep --token <token>` or `--auth password --password <pw>`.

Representative check IDs worth knowing about: `gateway.bind_no_auth`, `gateway.control_ui.allowed_origins_required`, `runtime.node_security_patch`, `fs.state_dir.perms_world_writable`, `config.insecure_or_dangerous_flags`. The full catalog is in the [audit checks reference](https://docs.openclaw.ai/gateway/security/audit-checks).

**Suppressions:** if the audit flags something you've deliberately configured, document the suppression instead of running `--fix` in a loop:

```json
{
  "security": {
    "audit": {
      "suppressions": [
        {
          "checkId": "gateway.bind_no_auth",
          "titleIncludes": "loopback",
          "reason": "Single-operator dev instance behind Tailscale"
        }
      ]
    }
  }
}
```

Suppressed findings move to `suppressedFindings` in the JSON output. Every suppression needs a reason.

The audit is SecretRef-aware, flags `hooks.token` reuse of gateway auth values, and warns when small models (300B parameters or fewer) run without a sandbox while web or browser tools are enabled.

**Verify:** audit exits with no critical findings. Save the `--json` output for the record.

**Failure modes:** noisy audit after a deliberate config choice -> use documented suppressions, not `--fix` loops. Cron the `--json` audit weekly (this appears in the checklist below too).

### 3. Bind the gateway to loopback

The gateway HTTP surface (Control UI, canvas, API endpoints) is not hardened for the public internet. Keep it on localhost. The default gateway port is **18789**:

```json
{
  "gateway": {
    "bind": "loopback"
  }
}
```

For remote access, use SSH tunneling or Tailscale:

```bash
# SSH tunnel (note: port 18789, not 3000)
ssh -L 18789:localhost:18789 user@your-server

# Or Tailscale serve
tailscale serve --https=443 http://localhost:18789
```

Before choosing an exposure pattern, check the [gateway exposure runbook](https://docs.openclaw.ai/gateway/security/exposure-runbook). The short version:

| Exposure pattern | When to use |
|---|---|
| Loopback + SSH tunnel | Default. Maximum safety. |
| Tailscale Serve | When you want HTTPS without managing certs. |
| Tailnet / LAN bind | Trusted network only. |
| Trusted reverse proxy | When you need a stable URL behind auth. |
| Public internet | **Don't.** The gateway is not hardened for it. |

If you go the SSH route, make sure the SSH server itself is locked down; see this [SSH server hardening guide for Linux](/secure-ssh-server-linux/). If you'd rather self-host the Tailscale control plane, [Headscale setup](/headscale-self-hosted-tailscale-setup/) covers that.

For the Control UI specifically, there are [security-hardened OpenClaw dashboards with TOTP MFA](/best-openclaw-dashboards/) worth considering before you expose anything.

**Verify:** `ss -tlnp | grep openclaw` shows `127.0.0.1:18789` only. The tunnel works: `curl http://localhost:18789` through the SSH tunnel returns the Control UI.

**Failure modes:** port 18789 already in use by another service. Tunnel pointing at port 3000 (the old default, so update your muscle memory). Tailscale serve misconfigured to expose beyond the tailnet.

**Rollback:** binding back to loopback is the instant remediation for any exposure scare. Change `gateway.bind` back, restart, done.

### 4. Set explicit gateway auth

The hardened baseline sets `gateway.auth` to token mode. Loopback binding is not authentication. Anyone with access to the machine can reach a loopback service.

```json
{
  "gateway": {
    "mode": "local",
    "auth": {
      "mode": "token",
      "token": "replace-with-long-random-token"
    }
  }
}
```

Generate a long random token (for example, `openssl rand -hex 32`). Store it in an environment variable or SecretRef where possible, not inline in the config. Supported auth modes: token, password, trusted-proxy, and device auth. Token mode is the default recommendation.

Keep the gateway auth token distinct from channel `hooks.token` values. The audit flags reusing one for the other. `openclaw doctor --fix` rotates a reused `hooks.token`.

**Verify:** gateway rejects unauthenticated requests. The token works from the tunnel.

**Failure modes:** lost token means recovery via config file access on the host (another reason to keep the backup). Token reuse across gateway and hooks (audit will flag it).

### 5. Enable sandbox mode

The sandbox modes are `off`, `non-main`, and `all`. The old `"on"` value is no longer valid. The default is `off`.

```json
{
  "agents": {
    "defaults": {
      "sandbox": {
        "mode": "non-main",
        "backend": "docker"
      }
    }
  }
}
```

**Recommend `non-main` as the minimum.** It sandboxes all non-primary agents while leaving the main agent with host access. Use `all` if your main agent doesn't need raw host access. Backends: `docker`, `podman`, `ssh`, `openshell`. Additional keys: `scope`, `workspaceAccess`.

Memory poisoning hardening is also relevant here: recalled memories are now treated as untrusted context, and `autoCapture` is off by default.

**Verify:** `openclaw sandbox recreate --browser --all` completes cleanly. A test skill can't write outside the workspace.

**Failure modes:** stale sandbox containers after updates: run `openclaw sandbox recreate --browser --all`. Docker `host` network defeats the sandbox entirely (don't use it). On bridge networks, set `sandbox.browser.cdpSourceRange` appropriately. Skills that break under `all`: drop to `non-main` deliberately, not silently.

### 6. Restrict filesystem and exec tools

Keep tools inside the workspace directory:

```json
{
  "tools": {
    "fs": {
      "workspaceOnly": true
    },
    "exec": {
      "applyPatch": {
        "workspaceOnly": true
      },
      "security": "deny",
      "ask": "always"
    }
  }
}
```

The `security: "deny"` plus `ask: "always"` combination is for hostile-input scenarios (any time the agent processes untrusted content). Note that the current single-operator default is `security: "full"`, `ask: "off"`. Exec approvals are opt-in guardrails, not an always-on prompt layer. Tighten them deliberately.

For broader tool restriction, use tool profiles and deny groups (from the baseline config above):

```json
{
  "tools": {
    "profile": "messaging",
    "deny": ["group:automation", "group:runtime", "group:fs", "sessions_spawn", "sessions_send"],
    "elevated": {
      "enabled": false
    },
    "sessions": {
      "visibility": "agent"
    },
    "agentToAgent": {
      "enabled": false
    }
  }
}
```

The `"messaging"` profile limits tools to communication tasks. The deny list blocks automation, runtime, and filesystem tool groups entirely, plus session spawning and cross-agent messaging. `tools.elevated.enabled: false` prevents privilege escalation. `tools.sessions.visibility: "agent"` restricts cross-agent session reach. `tools.agentToAgent.enabled: false` blocks agent-to-agent calls.

**Verify:** the audit shows no `plugins.tools_reachable_permissive_policy` finding. A denied tool call is refused (test one).

**Failure modes:** over-restriction breaking daily use. Tighten in layers: deny groups first, exec-deny second. For human-in-the-loop workflows where you want to approve each command, `security: "deny"` with `ask: "always"` is the right combo.

### 7. Set explicit Control UI origins

For non-loopback deployments, specify which origins the Control UI accepts:

```json
{
  "gateway": {
    "controlUi": {
      "allowedOrigins": ["https://your-tailscale-domain.ts.net"]
    }
  }
}
```

Without this, the gateway will refuse to start (fail-closed behavior). This is the class of defense that CVE-2026-25253 bypassed via the browser: the `gatewayUrl` trick turned the victim's browser into a bridge. Explicit origins plus a patched version (2026.1.29 or later) close that path.

**Verify:** gateway starts normally. A request from a non-listed origin is rejected.

### 8. Vet skills before installing

Beyond the ClawHub audit labels covered above, apply this checklist before installing anything:

<ListCheck>
<ul>
<li>Read the skill source code before installing</li>
<li>Check for base64-encoded payloads or obfuscated commands</li>
<li>Look for outbound network connections to unknown hosts</li>
<li>Verify the skill author's identity and history</li>
<li>Prefer skills with significant community usage and reviews</li>
<li>Consider running skills in a sandboxed environment first</li>
<li>Confirm the ClawHub audit status is Pass and risk is Low</li>
<li>Run `openclaw skills verify @owner/slug --card`</li>
<li>Pin a version with `--version` for predictable upgrades</li>
</ul>

Treat every skill as potentially hostile until verified. The ClawHub labels answer half of these questions for you now. Use them.

### 9. Docker hardening

If running OpenClaw in Docker, the pre-built images come from `ghcr.io/openclaw/openclaw` (the primary, provenance-checked registry) with a Docker Hub mirror at `openclaw/openclaw`. Pin version tags. Don't use `latest`. Variants include `slim`, `-browser`, and `extended-stable`.

```bash
docker run --read-only --cap-drop=ALL \
  -v openclaw-data:/app/data \
  ghcr.io/openclaw/openclaw:2026.11.1
```

`--read-only` prevents filesystem writes outside mounted volumes. `--cap-drop=ALL` drops Linux capabilities. Avoid unofficial mirrors.

For the compose-based flow, use `./scripts/docker/setup.sh` from the repo.

At the network level, don't use Docker `host` network (it defeats the sandbox). Keep a host firewall in front of everything. A [DNS firewall like NextDNS](https://go.bitdoze.com/nextdns) adds another layer: DNS-level blocking of known-bad C2 domains would have caught the `91.92.242.30` and `bore.pub` callbacks from the February attack.

For a broader look at host-level defense in depth, see [how I secured my Docker server with BSI report findings, Hetzner, and UFW](/bsi-security-report-docker-ufw/).

**Verify:** `docker run` example comes up. Container can't write outside volumes. `docker ps` shows the pinned version tag.

**Failure modes:** stale `latest` pulls that change underneath you. Unofficial mirrors serving tampered images. Sandbox browser containers needing recreate after image updates.

### 10. Node.js version

OpenClaw requires Node.js **24.16.0+** (on 24.x) or **26.1.0+**. Node 26 is recommended. The security patch levels to target are **24.22.1+** or **26.12.1+**. Older patch levels have known vulnerabilities.

```bash
node --version
# Want: v24.22.1+ or v26.12.1+
```

The audit check `runtime.node_security_patch` warns if you're below those levels. Docker users get Node from the base image, so this step matters for bare-metal and npm installs.

**Verify:** `node --version` prints a qualifying version. The audit no longer warns on `runtime.node_security_patch`.

Use this table as a periodic review. Run through it monthly, and after any config change or skill install.

| Check | Command / Action | Expected |
|-------|-----------------|----------|
| OpenClaw version | `openclaw --version` | v2026.8.1+ (current stable recommended) |

<Accordion label="Frequently Asked Questions" group="faq" expanded="true">

**Was my data stolen in the CVE-2026-25253 attack?**

These are two separate incidents. CVE-2026-25253 was the `gatewayUrl` token theft bug: a crafted link could steal your gateway token via the browser. Fixed in v2026.1.29. The ClawHub malicious skills were the more dangerous incident: if you installed one of the 341 infected skills, the malware had access to everything OpenClaw could access, including your API keys, conversation history, and files in the workspace. Potentially the entire machine if sandbox mode was off. If that applies to you, assume full compromise and rotate all credentials.

**How do I know if I installed a malicious skill?**

Run `openclaw skills list` and check each skill against the ClawHub audit labels (`openclaw skills verify @owner/slug --card`). Search your system logs and network traffic for the IoC addresses listed above (`91.92.242.30`, `bore.pub:44876`). The `openclaw security audit --deep` command also checks for known malicious patterns.

**What version is safe to run?**

v2026.8.1 is the minimum for the disclosed advisory waves (153 fixes ship there). v2026.9.3 or later is better. The current stable release (v2026.11.1 as of November 2026) is recommended. Run `openclaw update` to get there.

**Why doesn't exec ask by default?**

The current default for a trusted single-operator host is `security: "full"`, `ask: "off"`. Exec approvals are opt-in guardrails, not an always-on prompt layer. This makes sense for a solo operator who trusts their own inputs. If the agent processes untrusted content (web scraping, community skills, channel messages), tighten it: `tools.exec: { security: "deny", ask: "always" }`.

**Which sandbox mode should I use?**

`non-main` is the minimum recommendation. It sandboxes all non-primary agents. Use `all` if your main agent doesn't need raw host access. `off` (the default) is only acceptable on a machine where nothing untrusted reaches the agent. Backends: `docker`, `podman`, `ssh`, `openshell`. Docker is the most common.

**Is OpenClaw safe to run on the public internet?**

No. The gateway HTTP surface is not hardened for public exposure. Bind to loopback and use SSH tunneling or Tailscale for remote access. Multiple security advisories have been for issues that only matter with network exposure. The [exposure runbook](https://docs.openclaw.ai/gateway/security/exposure-runbook) covers the safe patterns.

**Should I enable `dangerouslyAllowNameMatching`?**

No, unless you have no other option. Name-based allowlists are vulnerable because users can change their display names, usernames, or email addresses at any time. The ID-only matching enforcement has shipped. Migrate to stable IDs. The audit still warns on mutable names/emails/tags in allowlists.

**What's the difference between `sandbox.mode` and `workspaceOnly`?**

`sandbox.mode` controls whether the agent runs in an isolated container (`off`, `non-main`, or `all`). `workspaceOnly` restricts file operations to the workspace directory even without a sandbox runtime. They complement each other. Enable both for maximum protection.

**How often should I run `openclaw security audit`?**

After every OpenClaw update, after installing any new skill, and at least weekly for actively used instances. Use `--deep` for the thorough scan. Save `--json` output in cron for a historical record. Add suppressions for deliberate config choices rather than ignoring findings.

**Does the trust model mean OpenClaw is insecure?**

No. It means the security boundary is at the machine/OS user level, not the gateway level. This is common for self-hosted tools. Understand that everyone with gateway access has full operator privileges and plan your deployment accordingly. One trust domain per instance.

**Can prompt injection compromise my OpenClaw instance?**

Prompt injection is listed as out-of-scope in OpenClaw's security model when it doesn't bypass a boundary. But the soul-evil hook showed how prompt injection can chain with other features to achieve persistent compromise. Keep the attack surface small: sandbox on, workspace-only filesystem, skills audited. Recalled memories are now treated as untrusted context, and `autoCapture` is off by default. Keep it that way unless you need it.
