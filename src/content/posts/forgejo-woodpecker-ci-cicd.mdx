GitHub Actions is great until you look at the bill, hit rate limits, or realize your code runs on someone else's servers. If you already self-host your apps on a VPS, hosting your own Git server and CI/CD pipeline is the next logical step. And it's easier than you'd think.

This guide sets up **Forgejo and Woodpecker CI** on one VPS: a self-hosted GitHub alternative where Forgejo handles your repos, issues, and pull requests, and Woodpecker runs your builds, tests, and deployments. Together they replace GitHub and GitHub Actions without leaving your code on someone else's infrastructure.

## Why switch to a self-hosted GitHub alternative?

A self-hosted GitHub alternative solves real problems, not hypothetical ones. Cost is the obvious one: the GitHub Actions free tier runs out fast on private repos, and self-hosted runners still phone home to GitHub. One 4 GB VPS runs the forge, CI, and your apps for 7 to 15 EUR/month flat. Data ownership is the second: your code, issues, pull requests, and CI logs live on your server, with no terms-of-service surprises. A VPS in your region also keeps local development independent of GitHub's uptime. And GitHub Actions lock-in grows with every workflow you write. Forgejo + Woodpecker keeps things portable.

That said, plenty of people mirror to GitHub for the social coding side. You can have both.

## Forgejo vs Gitea: what's the difference?

Forgejo vs Gitea is the first question most people ask. Forgejo forked from Gitea in October 2022 after a for-profit company took over the Gitea project (domains, trademark, everything). The community wasn't consulted, and an open letter went ignored. So they forked.

As of late 2026, Forgejo is a hard fork. The codebases have diverged. Here's where they differ:

| | Forgejo | Gitea |
|---|---|---|
| **Governance** | Non-profit (Codeberg e.V.) | For-profit company |
| **License** | Exclusively Free Software | Open Core (some proprietary features) |
| **Developed on** | Forgejo itself | GitHub |
| **CI/CD tested with** | Forgejo Actions | GitHub Actions |
| **Security** | Advance notice for all users | Advance notice for paying customers only |
| **Federation** | Working on ActivityPub support | No federation plans |
| **Release cadence** | Quarterly stables + yearly LTS, public EOL dates | Company-driven |
| **Migration from Gitea** | Supported via documented upgrade path; check the [Forgejo upgrade guide](https://forgejo.org/docs/latest/admin/upgrade/) for your Gitea version | N/A |

Gitea is now on v28.x (versioning jumped from 1.27.x at v28.0.0 in September 2026). With the codebases on separate trajectories, don't assume a drop-in migration. Read the upgrade guide before moving.

<Notice type="info" title="Gitea v28 breaking changes">

If you're migrating from Gitea, note that v28 routes git network operations through an internal proxy with egress settings (affects locked-down hosts) and added `RUN_RETENTION_DAYS` for Actions. Check the v28 release notes before upgrading.

</Notice>

I cover the fork and the Forgejo Actions runner setup in more detail in [the Forgejo vs Gitea and the Forgejo Actions runner guide](/forgejo-vs-gitea-self-hosted/).

Functionally, they're very similar. The UI and config format match, and the Docker setup is nearly identical. If you're starting fresh, go with Forgejo. If you're already on Gitea and it works fine, migrating isn't urgent. It's a documented upgrade when you're ready.

## Step 1: Install Forgejo with Docker Compose

Create a directory for Forgejo and set up the Docker Compose file:

```sh
mkdir -p /opt/forgejo && cd /opt/forgejo
```

### Docker Compose

```yaml
services:
  forgejo:
    image: codeberg.org/forgejo/forgejo:15
    container_name: forgejo
    environment:
      - USER_UID=1000
      - USER_GID=1000
      - FORGEJO__database__DB_TYPE=sqlite3
      - FORGEJO__server__DOMAIN=git.yourdomain.com
      - FORGEJO__server__ROOT_URL=https://git.yourdomain.com
      - FORGEJO__server__SSH_DOMAIN=git.yourdomain.com
      - FORGEJO__server__SSH_PORT=2222
      - FORGEJO__server__SSH_LISTEN_PORT=22
      - FORGEJO__service__DISABLE_REGISTRATION=true
      - FORGEJO__actions__ENABLED=true
      - FORGEJO__webhook__ALLOWED_HOST_LIST=external,loopback  # recommended for same-host Woodpecker
    restart: unless-stopped
    volumes:
      - ./data:/data
      - /etc/timezone:/etc/timezone:ro
      - /etc/localtime:/etc/localtime:ro
    ports:
      - "3000:3000"
      - "2222:22"
    networks:
      default:
        name: forgejo
```

A few things to note:

- The image pin `:15` points at Forgejo 15, the current LTS (supported until 2027-07-15). Forgejo 10 has been EOL since April 2025: don't run an unpatched forge on the public internet. If you'd rather track the latest stable, use `:17` and patch on advisory day.
- The image's SSH daemon (OpenSSH) listens on 22 inside the container and is published as 2222, so it doesn't conflict with your system SSH on 22. You'll clone repos with `ssh://git@yourdomain.com:2222/user/repo.git`.
- Registration is disabled on purpose. You don't want random people creating accounts on your Git server. Create accounts manually or re-enable registration briefly.
- SQLite is fine for small teams and personal use. If you're running 10+ users, switch to PostgreSQL.
- `ALLOWED_HOST_LIST=external,loopback` needs explaining: Forgejo blocks webhook delivery to loopback addresses by default. If `ci.yourdomain.com` resolves to a loopback address from inside the Forgejo container, delivery is refused and pipelines never trigger. Full explanation in Step 2.
- The network named `forgejo` gives the Docker network a predictable name so the Woodpecker agent can attach pipeline containers to it (needed for git clone, see Step 2).

<Notice type="warning" title="Patch fast or pin LTS">

The Forgejo 17.0.2 release (November 2026) fixed a critical auth bypass in the built-in SSH server when running on SQLite, a setup close to this guide's. The compose above keeps the image's OpenSSH daemon instead, so it is only affected if you switch to the built-in server. Case-insensitive key matching let an attacker forge a public key in about a minute. Fixed in 15.0.12 and 17.0.2. The lesson: self-hosting means you *can* patch same-day, but you must watch advisories. Subscribe to Forgejo's security-announcements RSS (linked from the [upgrade guide](https://forgejo.org/docs/latest/admin/upgrade/)). This is the "advance notice for all users" policy in action.

</Notice>

### Start Forgejo

```sh
docker compose up -d
```

Verify it's running:

```sh
docker compose logs forgejo | tail -5
```

You should see listen lines for port 3000 (HTTP) and 22 (SSH). Then visit `https://git.yourdomain.com`, complete the initial setup wizard, and create your admin account.

If `curl -I https://git.yourdomain.com` returns 200 after the reverse proxy is in place, you're good.

### Reverse proxy with Nginx and Certbot

If you're running Nginx on the host (not in Docker), add a server block:

```nginx
server {
    server_name git.yourdomain.com;

    location / {
        proxy_pass http://localhost:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    listen 443 ssl;
    ssl_certificate /etc/letsencrypt/live/git.yourdomain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/git.yourdomain.com/privkey.pem;
    include /etc/letsencrypt/options-ssl-nginx.conf;
    ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem;
}
```

Get the certificate first:

```sh
certbot --nginx -d git.yourdomain.com
```

If certbot fails, DNS probably hasn't propagated yet. Check with `dig git.yourdomain.com` and wait.

<Notice type="warning" title="Firewall">

Make sure ports 80, 443, and 2222 are open. If you're using UFW:

```sh
sudo ufw allow 'Nginx Full'
sudo ufw allow 2222
```

For a deeper look at hardening the Docker host itself, see [how I secured my Docker server with UFW](/bsi-security-report-docker-ufw/).

</Notice>

If port 3000 is already in use, change the left side of the port mapping (`"3001:3000"`) and update the Nginx `proxy_pass` accordingly.

## Step 2: Install Woodpecker CI (self-hosted CI/CD)

Woodpecker is a standalone self-hosted CI/CD server that connects to Forgejo via OAuth. It's a community fork of Drone CI, maintained after Drone changed its license. Each pipeline step runs in its own Docker container, so your build environment is always clean and reproducible.

### Create an OAuth application in Forgejo

1. Go to **Site Administration -> Applications** (or your user settings -> Applications)
2. Create a new OAuth2 application named Woodpecker CI with the redirect URI `https://ci.yourdomain.com/authorize`
3. Save the **Client ID** and **Client Secret**

The redirect URI must match exactly, including the `https://` scheme and the `/authorize` path. A mismatch silently breaks login later (you'll get a vague OAuth error in the browser).

### Docker Compose for Woodpecker

```sh
mkdir -p /opt/woodpecker && cd /opt/woodpecker
```

```yaml
services:
  woodpecker-server:
    image: woodpeckerci/woodpecker-server:v3
    container_name: woodpecker-server
    restart: unless-stopped
    ports:
      - "8000:8000"
    volumes:
      - woodpecker_data:/var/lib/woodpecker
    environment:
      - WOODPECKER_OPEN=false
      - WOODPECKER_HOST=https://ci.yourdomain.com
      - WOODPECKER_FORGEJO=true
      - WOODPECKER_FORGEJO_URL=https://git.yourdomain.com
      - WOODPECKER_FORGEJO_CLIENT=YOUR_CLIENT_ID
      - WOODPECKER_FORGEJO_SECRET=YOUR_CLIENT_SECRET
      - WOODPECKER_AGENT_SECRET=YOUR_RANDOM_SECRET
      - WOODPECKER_DATABASE_DRIVER=sqlite3
      - WOODPECKER_DATABASE_DATASOURCE=/var/lib/woodpecker/woodpecker.db

  woodpecker-agent:
    image: woodpeckerci/woodpecker-agent:v3
    container_name: woodpecker-agent
    command: agent
    restart: unless-stopped
    depends_on:
      - woodpecker-server
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - woodpecker-agent-config:/etc/woodpecker
    environment:
      - WOODPECKER_SERVER=woodpecker-server:9000
      - WOODPECKER_AGENT_SECRET=YOUR_RANDOM_SECRET
      - WOODPECKER_MAX_WORKFLOWS=2
      - WOODPECKER_BACKEND_DOCKER_NETWORK=forgejo

volumes:
  woodpecker_data:
  woodpecker-agent-config:
```

Generate the agent secret:

```sh
openssl rand -hex 32
```

Use the same secret for both `WOODPECKER_AGENT_SECRET` entries.

The `WOODPECKER_FORGEJO_*` env vars use Woodpecker's native Forgejo driver (available since Woodpecker 2.6.0). Older guides use `WOODPECKER_GITEA_*`, which still works through the Gitea-compatible driver, but the native driver is the right choice for new setups.

<Notice type="warning" title="Webhooks to loopback addresses are blocked by default">

Forgejo refuses to deliver webhooks to loopback addresses by default. If `ci.yourdomain.com` resolves to a loopback address from inside the Forgejo container (a hosts entry or local DNS), **pipelines silently never start**. The Forgejo compose file in Step 1 adds `FORGEJO__webhook__ALLOWED_HOST_LIST=external,loopback` to pre-empt it. If you missed it, add the env var and `docker compose up -d` again.

</Notice>

`WOODPECKER_BACKEND_DOCKER_NETWORK=forgejo` tells the agent to attach pipeline containers to the `forgejo` Docker network (the one we named in Step 1). Without it, workflows hang in the "clone" step because the containers can't reach Forgejo. If your Forgejo network has a different name, adjust accordingly.

`WOODPECKER_MAX_WORKFLOWS=2` is the memory governor on a 4 GB box: it limits concurrent pipeline runs. Bump it if you have more RAM.

<Notice type="warning" title="Docker socket access">

The agent mounts `/var/run/docker.sock`, which gives it full access to the host's Docker daemon. For a single-user VPS this is fine. For shared environments, look into rootless Podman or Kaniko, or [run Docker containers as a non-root user](/add-users-to-docker-container/).

</Notice>

One compatibility note: Woodpecker requires Forgejo's API max page size to be at least 50 (the default). Don't lower it.

Start it up:

```sh
docker compose up -d
```

Quick check before moving on: `docker compose logs -f woodpecker-agent` should show the agent connecting to the server. Open `https://ci.yourdomain.com` and log in via Forgejo OAuth. If the round-trip works, the integration is live. Full end-to-end checks land in Step 5.

Add an Nginx reverse proxy for `ci.yourdomain.com` the same way as Forgejo (proxy to port 8000).

### Your first Woodpecker pipeline

Create `.woodpecker.yml` in the root of a Forgejo repo:

```yaml
steps:
  - name: build
    image: node:24-alpine
    commands:
      - npm ci
      - npm run build

  - name: test
    image: node:24-alpine
    commands:
      - npm test
    depends_on: [build]

  - name: deploy
    image: alpine:3.22
    commands:
      - apk add --no-cache openssh-client
      - ssh -o StrictHostKeyChecking=no deploy@yourserver "cd /var/www/myapp && git pull && ./build.sh"
    depends_on: [test]
    when:
      - event: push
        branch: main
```

Each step runs in its own container. The top-level key is `steps:` (a list). The old `pipeline:` keyword was removed in Woodpecker 3.0.0.

Steps run serially in definition order by default. The moment any step sets `depends_on`, Woodpecker switches to DAG mode and steps without explicit dependencies can run in parallel.

<Notice type="warning" title="Always pair branch with event">

`branch: main` alone also fires when a pull request *targeting* main is updated. If your deploy step only checks the branch, a PR will deploy to production. Always add `event: push` to limit it to actual pushes. Branch patterns support globs too (`branch: prefix/*`).

</Notice>

### Building and pushing Docker images

Woodpecker has a built-in Docker plugin:

```yaml
steps:
  - name: build-image
    image: plugins/docker
    settings:
      repo: git.yourdomain.com/youruser/myapp
      registry: git.yourdomain.com
      tags:
        - latest
        - ${CI_COMMIT_SHA:0:8}
      username:
        from_secret: docker_username
      password:
        from_secret: docker_password
    when:
      - event: push
        branch: main
```

Add the secrets via the Woodpecker UI or CLI:

```sh
woodpecker-cli repo secret add \
  --repository youruser/myapp \
  --name docker_username \
  --value 'youruser'

woodpecker-cli repo secret add \
  --repository youruser/myapp \
  --name docker_password \
  --value 'your_token'
```

You can scope secrets by `--image` and `--event` so they're only available to specific pipeline steps. And for compose-based apps, prefer the `.env` file / `*_FILE` pattern over pasting secret values into YAML. See [secure Docker Compose secrets handling](/docker-compose-secrets/) for the details.

## Step 3: Set up automatic deployments

Push code, Woodpecker runs tests, and if they pass, the app deploys to the same VPS.

### The deploy workflow

The simplest approach: SSH into the server, pull the latest code, rebuild.

<Notice type="info" title="Same-server deploys">

If Forgejo, CI, and your app all run on the same VPS, the SSH connection is just localhost. This seems redundant, but it keeps your workflow portable. Change the SSH target to a different server and everything still works.

</Notice>

### With Docker Compose apps

If your app runs in Docker Compose, the deploy script gets slightly fancier:

```sh
#!/bin/bash
cd /opt/myapp
git pull --force origin main
docker compose down
docker compose up -d --build
docker image prune -f
```

The `--build` flag rebuilds the image from the Dockerfile. `docker image prune` cleans up old images so they don't eat disk space.

### Zero-downtime deploys

For zero-downtime, you have a few options depending on your stack. With Nginx, build the new container on a different port, test it, then switch the upstream and reload. Docker Compose healthchecks work too: define a healthcheck in your compose file and Docker won't route traffic until the new container is healthy. If you want zero-downtime deploys without writing scripts, [Kamal](https://kamal-deploy.org/) handles this out of the box. It's from the Basecamp/Rails team but works with any Docker app. For a broader look at self-hosted PaaS options, see [Coolify vs Dokploy vs Kamal 2 for self-hosted PaaS deploys](/coolify-vs-dokploy-vs-kamal-2/).

## Step 4: Forgejo container registry (optional)

Forgejo has a built-in container registry. Enable it in `app.ini`:

```ini
[packages]
ENABLED=true
```

Then push images to `git.yourdomain.com/youruser/myapp:tag` from your CI pipeline. Woodpecker's Docker plugin handles this out of the box.

This saves you from running a separate Docker registry or paying for Docker Hub. Recent Forgejo releases improved the package UI too: OCI manifest annotations and cleanup-by-last-download make it more than a toy registry.

To verify after your first CI push:

```sh
docker pull git.yourdomain.com/youruser/myapp:latest
```

## Why Woodpecker CI over the alternatives?

Forgejo has a built-in CI system too (Forgejo Actions, compatible with GitHub Actions syntax). So why bother with a separate Woodpecker installation for self-hosted CI/CD?

The honest answer: Forgejo Actions has matured. It now has workflow-job webhooks, rerun APIs, and richer step summaries. It's a real option, especially if you want to copy `.github/workflows` files over with minimal changes. But Woodpecker wins on being forge-agnostic with its own mature UI and agent model.

Woodpecker's dedicated web interface handles build monitoring, logs, and secrets in one place. Matrix builds run the same pipeline across multiple versions via the `matrix:` top-level key (up to 64 workflows per matrix, 10 variables per axis). Cross-workflow `depends_on` (with optional dependencies) and `status: [failure]` steps cover complex pipelines and post-failure cleanup. YAML anchors keep the config DRY.

Multi-forge support is the structural difference: repos on GitHub or GitLab connect to the same Woodpecker server, so you're not locked to one Git provider. Org-scoped agents with label filters help once you outgrow one agent. The plugin ecosystem covers Docker image builds, Slack notifications, and S3 artifact uploads.

If you're coming from GitHub and just want to copy your `.github/workflows` files over, Forgejo Actions is the simpler path. But if you're setting up CI/CD from scratch and want a forge-agnostic tool, Woodpecker is the better choice. And if you want a PaaS-style deploy experience instead, look at [a self-hosted Heroku alternative with Coolify](/coolify-install-heroku-alternative/).

## Backing up Forgejo and Woodpecker

Don't skip this. Your Git server is the source of truth for all your projects. And the Forgejo upgrade guide **requires** a full backup before every major upgrade (v15 to v16, for example). This is not optional.

<Tabs>
<Tab name="Stop-and-tar">
The straightforward approach: stop Forgejo for consistency, archive, encrypt, store off-site:

```sh
#!/bin/bash
DATE=$(date +%Y-%m-%d)
BACKUP_DIR="/home/backups/forgejo"

# Stop Forgejo for a consistent backup
cd /opt/forgejo && docker compose stop

# Create compressed archive
tar -czf "$BACKUP_DIR/forgejo-$DATE.tar.gz" -C /opt/forgejo/data .

# Restart Forgejo
docker compose up -d

# Encrypt
gpg --encrypt --armor -r your@email.com \
  -o "$BACKUP_DIR/forgejo-$DATE.tar.gz.gpg" \
  "$BACKUP_DIR/forgejo-$DATE.tar.gz"

# Remove unencrypted backup
rm "$BACKUP_DIR/forgejo-$DATE.tar.gz"
```

Run this nightly via cron. Copy the encrypted backups off-server (rsync to a NAS, rclone to S3, whatever works for you).
</Tab>
<Tab name="forgejo dump">
Forgejo has a built-in dump command that creates a full archive without stopping the service. The exact syntax varies by version, so check the [Backups and Backup Restoration](https://forgejo.org/docs/latest/admin/setup/backup/) admin doc for your release. The general form is:

```sh
docker exec --user 1000:1000 forgejo forgejo dump \
  --file /data/forgejo-dump-$(date +%Y-%m-%d).zip
```

The dump lands inside the container's `/data` volume. Copy it out, encrypt it, and store it off-site. Less disruptive than stop-and-tar, but verify the exact flags for your Forgejo version before relying on it.
</Tab>
</Tabs>

For Woodpecker, back up the `woodpecker_data` volume the same way.

CI image churn is the real disk cost on a shared VPS. Keep the prune cron (see gotchas) and `WOODPECKER_MAX_WORKFLOWS=2` as the memory governor.

## Common gotchas and troubleshooting

If no pipeline appears in Woodpecker, the webhook loopback block is the usual suspect. Check that `FORGEJO__webhook__ALLOWED_HOST_LIST=external,loopback` is set in the Forgejo environment (Step 1). Also verify the OAuth redirect URI matches exactly (including the `https://` scheme and the `/authorize` path).

A workflow stuck in "pending" or "cloning" usually means the agent can't reach the clone URL. Check that `WOODPECKER_BACKEND_DOCKER_NETWORK` matches the name of Forgejo's Docker network. Also verify `WOODPECKER_AGENT_SECRET` is identical on both the server and agent.

SSH port conflicts bite when Forgejo's SSH (published as 2222 in this guide) is blocked. Make sure your firewall allows it and your clone URLs include the port.

If the agent is not picking up jobs, check the agent logs with `docker compose logs woodpecker-agent`. Make sure the `WOODPECKER_AGENT_SECRET` matches between server and agent.

SQLite lock errors under parallel workflows: Woodpecker retries on SQLite lock contention, but if you're running many concurrent workflows, move to PostgreSQL.

Forgejo "Unexpected database version" after an upgrade is documented in the [Forgejo upgrade guide](https://forgejo.org/docs/latest/admin/upgrade/) troubleshooting section. Always take the pre-upgrade backup first.

Docker socket permissions: if the CI runner can't access Docker, make sure the container has `/var/run/docker.sock` mounted and the user has Docker permissions.

Disk space is the slow-burn problem. CI runners generate a lot of Docker images over time. Add a cron job to prune old images:

```sh
0 3 * * * docker system prune -af --filter "until=72h"
```

This removes unused images older than 3 days.

## FAQ

<Accordion label="Can this run on a 2 GB VPS?" group="faq">
Forgejo alone runs fine on 2 GB. With Woodpecker CI on the same box, 4 GB is the comfortable floor. The agent spawns Docker containers for each pipeline step, and those eat RAM fast. Set <code>WOODPECKER_MAX_WORKFLOWS=2</code> as a memory governor.
</Accordion>

<Accordion label="Do I still need Forgejo Actions if I run Woodpecker?" group="faq">
No. Pick one. Forgejo Actions if you want GitHub-workflow portability (copy <code>.github/workflows</code> files with minimal changes). Woodpecker for the dedicated UI and agent model. Running both is possible but adds complexity for no real gain.
</Accordion>

<Accordion label="Why pin Forgejo 15 LTS instead of 17?" group="faq">
LTS releases get security fixes for 15 months (Forgejo 15 runs to 2027-07-15). Quarterly stables get about 3 months. Pin <code>:15</code> if you want a set-and-forget setup. Use <code>:17</code> only if you patch on advisory day. The 17.0.2 SSH-key bypass is a good example of why that matters.
</Accordion>

<Accordion label="How do I upgrade Forgejo when a new major ships?" group="faq">
Read the release notes first. Take a full backup (the upgrade guide requires this). Bump the image tag in your compose file. <code>docker compose up -d</code>. Check the logs. If you see "Unexpected database version," the upgrade guide's troubleshooting section has the fix.
</Accordion>

<Accordion label="Is mounting the Docker socket into the agent a security risk?" group="faq">
On a single-user VPS, it's an accepted risk. The agent needs it to spawn pipeline containers. On shared hosts, look at rootless Podman or Kaniko, or restrict container access with [non-root Docker containers](/add-users-to-docker-container/).
</Accordion>

Push to Forgejo, CI runs tests, deploys to the same server, Nginx serves it. The whole loop runs on one box.
