# Docker FileBrowser Setup: Self-Hosted File Management Guide

<Notice type="warning" title="FileBrowser Project Archived (2026)">
**FileBrowser is being archived on 2026-09-01.** The final release (v2.63.23) has already shipped. There will be no further security patches or bug fixes. Docker images will remain online but unmaintained.

Known unpatched security issues include command execution vulnerabilities ([#5199](https://github.com/filebrowser/filebrowser/issues/5199)) and non-revocable JWT sessions ([#5216](https://github.com/filebrowser/filebrowser/issues/5216)). If you keep running it, follow the security hardening section below.

For new deployments, consider [FileBrowser Quantum](#filebrowser-quantum-the-actively-maintained-alternative), the actively maintained fork covered later in this article.
</Notice>

[FileBrowser](https://filebrowser.org/) is a web-based file manager for self-hosted use. It gives you a browser UI for uploading, downloading, previewing, renaming, and editing files on your server. It still works fine despite the archival, and Docker Compose makes the setup straightforward.

This guide covers the Docker FileBrowser setup from scratch: Docker Compose deployment, Cloudflare Tunnel access for SSL, security hardening, and the FileBrowser Quantum alternative if you want something actively maintained. If you're looking for other containers to run alongside it, check the [best Docker containers for your home server](/docker-containers-home-server/).

### Create a Modern Docker Compose File for FileBrowser

<Notice type="info" title="s6 vs non-s6 images">
The `v2-s6` image (44MB) includes s6-overlay, which handles PUID/PGID environment variables for file ownership. The non-s6 image (16MB) is lighter but doesn't support PUID/PGID. You set the user with `user:` instead. Use s6 if you want flexible UID/GID control; use non-s6 if you prefer a smaller image and are OK hardcoding the user.
</Notice>

Create a new directory for the stack, then create two files: `docker-compose.yml` and `.env`.

<Tabs>
<Tab name="s6 image (recommended)">
Create `docker-compose.yml`:

```yaml
services:
  filebrowser:
    image: filebrowser/filebrowser:v2.63.23-s6
    container_name: filebrowser
    restart: unless-stopped
    volumes:
      - /opt/stacks:/srv
      - ./filebrowser.db:/database/filebrowser.db
      - ./settings.json:/config/settings.json
    environment:
      PUID: ${PUID}
      PGID: ${PGID}
    ports:
      - "5040:80"
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:80/health"]
      interval: 30s
      timeout: 3s
      retries: 3
    security_opt:
      - no-new-privileges:true
```

Create `.env` in the same directory:

```
PUID=1000
PGID=1000
```

Adjust `PUID` and `PGID` to match your host user. Run `id -u` and `id -g` to find your values. Using a `.env` file means it works in Dockge, Portainer, and any management UI. Shell substitution like `$(id -u)` only resolves from bash.
</Tab>
<Tab name="Non-s6 image (lightweight)">
Create `docker-compose.yml`:

```yaml
services:
  filebrowser:
    image: filebrowser/filebrowser:v2.63.23
    container_name: filebrowser
    restart: unless-stopped
    user: "1000:1000"
    volumes:
      - /opt/stacks:/srv
      - ./filebrowser.db:/database/filebrowser.db
      - ./settings.json:/config/settings.json
    ports:
      - "5040:80"
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:80/health"]
      interval: 30s
      timeout: 3s
      retries: 3
    security_opt:
      - no-new-privileges:true
```

No `.env` file needed. The `user: "1000:1000"` sets the container's UID/GID directly. Change these numbers to match your host user.
</Tab>
</Tabs>

A few notes on the compose file:

- **Image pinned to `v2.63.23-s6`**, the final release. Since the project is archived, there won't be updates, so pinning prevents surprises.
- **No `version:` field**. That was obsolete since Docker Compose v2. Docker Compose v1 (`docker-compose` with a hyphen) was fully removed in April 2025. Always use `docker compose` (space, no hyphen).
- **`/opt/stacks:/srv`**: the left side is your host directory (change it to wherever your files live). The right side (`/srv`) is where FileBrowser looks for files, as defined in `settings.json`.
- **`5040:80`**: left is the host port you connect to, right is the container-internal port (set in `settings.json`). Change `5040` if that port is taken.
- **Healthcheck**: Docker will report the container as "healthy" once it passes. Useful if you run multiple containers and want automated status.
- **`no-new-privileges`**: prevents the container process from gaining new privileges via setuid binaries. Free security hardening.

FileBrowser is free and open source (Apache 2.0). The container is lightweight (~44MB image, minimal CPU/RAM). A basic [Hetzner](https://go.bitdoze.com/hetzner) VPS at ~€4/mo handles it without breaking a sweat.

For more on how PUID/PGID environment variables work in Docker Compose, see [how Docker Compose environment variables work](/docker-env-vars/).

### Configure FileBrowser Settings and Database Files

In the same directory as your `docker-compose.yml`, create the database and settings files:

**Create the database file:**

```sh
touch filebrowser.db
```

**Create `settings.json`:**

```sh
cat > settings.json << 'EOF'
{
  "port": 80,
  "baseURL": "",
  "address": "",
  "log": "stdout",
  "database": "/database/filebrowser.db",
  "root": "/srv"
}
EOF
```

Each field:

- `port: 80`: the port FileBrowser listens on inside the container. Must match the right side of your port mapping.
- `baseURL`: leave empty unless you're running behind a reverse proxy with a path prefix (e.g., `/files`).
- `database`: where the SQLite database lives inside the container.
- `root`: the directory FileBrowser serves. Must match the right side of your volume mount.

<Notice type="warning" title="filebrowser.db is critical">
`filebrowser.db` contains all user accounts, hashed passwords, and settings. If you lose it, you lose every user account. Back it up before any upgrade or migration. See the [backup section](#backing-up-your-filebrowser-database-and-configuration) below.
</Notice>

### Deploy and Verify Your FileBrowser Container

Start the container:

```sh
docker compose up -d
```

<Notice type="success" title="Verify deployment">
Run these commands to confirm everything is working:

```sh
# Check the container is running and healthy
docker ps --filter name=filebrowser

# Check the logs for "Listening on :80"
docker logs filebrowser

# Verify the web UI responds
curl -I http://localhost:5040

# Confirm the database file exists
ls -la filebrowser.db
```

Expected output from `docker ps`: the container should show "Up" status with "(healthy)" in the status column after ~30 seconds. `curl` should return `HTTP/1.1 200 OK`.
</Notice>

If `docker logs filebrowser` shows `permission denied` on the database file, see the [troubleshooting section](#troubleshooting-common-filebrowser-docker-permission-issues) below.

### Secure Remote Access with Cloudflare Tunnels or a Reverse Proxy

<Notice type="warning" title="Never expose FileBrowser directly">
FileBrowser has known unpatched session handling issues. Always put it behind a reverse proxy that terminates TLS and performs its own authentication. Never expose port 5040 to the public internet.
</Notice>

**Option 1: Cloudflare Tunnels**

Go to **Access > Tunnels** in the Cloudflare dashboard, choose your tunnel, and add a hostname that maps your domain/subdomain to the service and port:

<Picture src={imag1} alt="Cloudflare Tunnel setup" />

Point the service to `http://localhost:5040` (or whatever host port you chose in the compose file).

**Option 2: Traefik or Caddy**

You can also use [Traefik as a reverse proxy for Docker](/traefik-proxy-docker/) or Caddy for automatic HTTPS. The key is that TLS terminates at the proxy, not at FileBrowser.

If you get a 502 or 503 through the tunnel, check that the FileBrowser container is running (`docker ps`) and that the port in the tunnel config matches the host port in your compose file.

> You can also check [CloudPanel as Reverse Proxy with Docker and Dockge](/cloudpanel-setup-dockge/) to use CloudPanel as a reverse proxy.

### Access and Secure Your FileBrowser Web Interface

Once the tunnel or reverse proxy is configured, access FileBrowser at your domain. Log in with the default credentials:

- **Username:** `admin`
- **Password:** `admin`

<Notice type="warning" title="Change the default password now">
Change the admin password immediately after first login. Create separate user accounts with restricted permissions for anyone else who needs access. Set each user's root directory to only the folders they should see.
</Notice>

One thing to be aware of: FileBrowser uses self-contained JWTs for sessions. These cannot be revoked. If you suspect a compromised session, changing the password does NOT invalidate existing tokens. They remain valid until they expire naturally.

## FileBrowser Project Status: What Changed in 2025-2026

The original FileBrowser project (github.com/filebrowser/filebrowser) is being archived on **2026-09-01**. The final release, **v2.63.23**, has already shipped. There will be no further releases, bug fixes, or security patches.

Docker images will remain on Docker Hub and won't be withdrawn. The project has 34.9k GitHub stars, so it's widely used, but unmaintained software requires extra caution.

### Known unpatched security issues

<Accordion label="Command execution/runner (#5199)" group="security">
The command runner feature has been plagued with vulnerabilities. It is **disabled by default**. If you've never turned it on, this doesn't affect you.

If you've re-enabled it with `--disable-exec=false`, treat it as equivalent to giving shell access on the host. The maintainer recommends keeping it disabled and has stated it will not be fixed.
</Accordion>

<Accordion label="Session/JWT handling (#5216)" group="security">
FileBrowser sessions use self-contained JWTs that **cannot be revoked**. This means:

- Logging out does not invalidate the token
- Changing a password does not invalidate existing tokens
- The same refresh token can be redeemed repeatedly until it expires

If a token leaks, there's no way to kill it server-side. The only mitigation is short token expiry times, which FileBrowser doesn't expose as a config option.
</Accordion>

<Accordion label="CVE-2025-53893 DoS vulnerability" group="security">
A denial-of-service vulnerability exists in certain API endpoints. Since the project is archived, this will not be patched. Running behind a reverse proxy with rate limiting helps mitigate this.
</Accordion>

## FileBrowser Quantum: The Actively Maintained Alternative

**FileBrowser Quantum** by Graham Steffaniak is the actively maintained fork that has become the de facto successor. It has 7.2k+ GitHub stars and a stable release track available since December 2025.

<Tabs>
<Tab name="Quick Docker Compose setup">
```yaml
services:
  filebrowser:
    image: gtstef/filebrowser:stable
    container_name: filebrowser-quantum
    restart: unless-stopped
    volumes:
      - /opt/stacks:/srv
      - ./data:/database
      - ./config.yaml:/config/config.yaml
    ports:
      - "5040:80"
```

Docker image: `gtstef/filebrowser:stable` (60MB with ffmpeg + doc preview) or `stable-slim` (15MB core only). Also available on GHCR: `ghcr.io/gtsteffaniak/filebrowser`.
</Tab>
<Tab name="Key differences from original">
- **Multiple source directories** with include/exclude rules (original only supports one root)
- **OIDC, LDAP, JWT, password+2FA**, and proxy authentication
- **SQLite indexing with real-time search** across files
- **OnlyOffice integration** for editing office documents in the browser
- **Directory-level access control** scoped to user/group
- **API tokens + Swagger docs** at `/swagger`
- **Shell commands completely removed**, the biggest security improvement over the original
- **Config via `config.yaml`** instead of `settings.json`. Different format, not interchangeable
- **Better UI** with animations, gallery view, folder thumbnails
</Tab>
</Tabs>

<Notice type="info" title="Not a drop-in replacement">
FileBrowser Quantum uses a different config format (`config.yaml` vs `settings.json`) and a different database schema. You cannot swap the Docker image and expect things to work. Migration means reconfiguring from scratch. The original `filebrowser.db` is not compatible.
</Notice>

## Security Hardening for Your FileBrowser Docker Deployment

Whether you stick with the original or switch to Quantum, these practices apply:

<ListCheck>
<ul>
<li>Never expose FileBrowser directly to the internet. Always use a reverse proxy with TLS termination</li>
<li>Keep the command runner disabled (it's off by default, don't turn it on)</li>
<li>Run as a non-root user inside the container (use PUID/PGID or the `user:` directive)</li>
<li>Mount only the directory you need to serve. Don't mount `/` or your entire home directory</li>
<li>Use the `no-new-privileges` security option in your compose file</li>
<li>Change the default admin password immediately after first login</li>
<li>Create separate user accounts with restricted directory access</li>
<li>Back up `filebrowser.db` regularly. It contains all user accounts and settings</li>
<li>Keep the container image pinned to a known version</li>
<li>Set up firewall rules to block direct access to the container port from outside</li>
</ul>
</ListCheck>

<Notice type="info" title="JWT sessions cannot be revoked">
As noted in the [project status section](#filebrowser-project-status-what-changed-in-2025-2026), FileBrowser JWT sessions cannot be revoked server-side. A leaked token is valid until it expires. Factor this into your security posture, especially if you expose FileBrowser to multiple users.
</Notice>

For VPS-level intrusion prevention beyond FileBrowser itself, consider [securing your VPS with CrowdSec](/crowdsec-secure-server/). For managing secrets in your compose files, see [Docker Compose secrets management](/docker-compose-secrets/).

## Troubleshooting Common FileBrowser Docker Permission Issues

<Accordion label="permission denied on filebrowser.db" group="faq">
The s6 image runs as UID 911 by default (the PUID/PGID vars override this). If you see:

```
filebrowser  | 2024/04/25 07:17:26 open /database/filebrowser.db: permission denied
```

Check the container startup logs for the actual UID/GID:

```
filebrowser  | GID/UID
filebrowser  | ───────────────────────────────────────
filebrowser  | User UID:    911
filebrowser  | User GID:    1001
```

Then fix ownership:

```sh
chown 911:1001 filebrowser.db
```

If you're using the non-s6 image with `user: "1000:1000"`, chown to 1000:1000 instead.
</Accordion>

<Accordion label="permission denied on mounted /srv directory" group="faq">
The host directory (`/opt/stacks` in the examples) must be writable by the container user. If FileBrowser can read but not write, or can't list directories:

```sh
chown -R 1000:1000 /opt/stacks
```

Match the UID/GID to your compose config (PUID/PGID for s6, or the `user:` value for non-s6).
</Accordion>

<Accordion label="SELinux permission errors (RHEL/Fedora)" group="faq">
On SELinux-enabled systems (RHEL, Fedora, CentOS), volume mounts may be blocked. Add the `:z` or `:Z` suffix to your mount paths:

```yaml
volumes:
  - /opt/stacks:/srv:z
```

`:z` relabels for shared access. `:Z` relabels for private access. Use `:z` unless you have a reason not to.
</Accordion>

<Accordion label="Container starts but UI shows blank or 502 through reverse proxy" group="faq">
Check `docker logs filebrowser` for errors. Common causes:

1. **Port mismatch**: the port in your reverse proxy config doesn't match the host port in the compose file
2. **`baseURL` mismatch**: if you set a path prefix in your reverse proxy (e.g., `/files`), set the same value in `settings.json` `"baseURL"` field
3. **Container not healthy** — wait 30 seconds after startup for the healthcheck to pass
</Accordion>

<Accordion label="$(id -u) not resolving in Dockge/Portainer" group="faq">
Shell command substitution (`$(id -u)`) only works when running `docker compose` from a bash shell. Dockge, Portainer, and other management UIs don't process shell commands.

Fix: use a `.env` file with hardcoded values, or use the non-s6 image with `user: "1000:1000"` directly in the compose file.
</Accordion>

## Backing Up Your FileBrowser Database and Configuration

<Notice type="info" title="Back up filebrowser.db">
Without `filebrowser.db`, you lose all user accounts, hashed passwords, and settings. Back it up before upgrading or migrating. The `settings.json` is also worth backing up but can be recreated from scratch.
</Notice>

A quick one-liner backup:

```sh
cp filebrowser.db filebrowser.db.bak-$(date +%Y%m%d)
```

For a more robust approach, add it to your existing backup routine. If you're already backing up Docker volumes or your `/opt/stacks` directory, make sure the compose project directory (where `filebrowser.db` lives) is included.

The actual files in `/srv` (your documents, media, etc.) should have their own backup strategy separate from FileBrowser's database.

If you use S3-compatible storage for backups, you can set up a cron job:

```sh
# Example: daily backup to a local archive directory
0 2 * * * cp /path/to/filebrowser.db /backups/filebrowser.db.bak-$(date +\%Y\%m\%d)
```

Test your restore process at least once. A backup you've never restored from is not a backup.

## Conclusion

You now have FileBrowser running behind a reverse proxy with TLS, proper file permissions, and security hardening in place. The Docker Compose setup makes it easy to manage — `docker compose up -d` to start, `docker compose down` to stop, and `docker compose pull && docker compose up -d` to update if a new image ever appears (it won't, since the project is archived).

If you're setting this up for the first time today, I'd recommend starting with [FileBrowser Quantum](https://github.com/gtsteffaniak/filebrowser) instead. It's actively maintained, has better authentication options (OIDC, LDAP, 2FA), and removed the shell command feature entirely. The config format is different, so you'd configure from scratch anyway.

For existing FileBrowser users: it still works fine. Follow the security hardening checklist, back up your `filebrowser.db`, and keep it behind a reverse proxy. Don't re-enable the command runner.
