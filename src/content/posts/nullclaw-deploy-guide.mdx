This NullClaw deploy guide covers everything you need to self-host the smallest AI assistant I've found that still does everything. [NullClaw](https://github.com/nullclaw/nullclaw) is a single static binary written in Zig, about 1 MB of RAM at runtime, no runtime dependencies, no framework overhead. It boots in under 2 milliseconds and runs on anything with a CPU, including $5 ARM boards. The project has ~8,200 GitHub stars and ships 5,300+ tests, 50+ LLM providers, and 19 chat channels.

One honest note before you download anything: the "678 KB binary" figure comes from a hand-built `ReleaseSmall` compile. Official release binaries from GitHub are 4.4-6.5 MB. Both are tiny; just don't think you grabbed the wrong file when your download is bigger than 678 KB.

This guide walks through install, providers, channels, memory, sandboxing, and running the gateway under systemd on a VPS.

## What NullClaw is

NullClaw is an AI assistant written entirely in Zig. The tagline is "null overhead, null compromise". It ships as a static binary with zero runtime dependencies that runs on the cheapest hardware you can find.

The architecture uses vtable interfaces for every subsystem. Want to swap your LLM provider? Change one config line. Same for channels, memory backends, tools, tunnels, sandboxes, and peripherals. The ecosystem around it is growing too: NullHub (a web UI for config and process management), NullBoiler (workflow orchestration), and NullWatch (observability).

```
678 KB source build · <2 ms startup · 5,300+ tests · 50+ providers · 19 channels · Pluggable everything
```

## Why Zig

Zig is a systems language that compiles to C-like performance with zero runtime overhead. For NullClaw, the practical benefits are:

| Property | What it means for NullClaw |
|----------|---------------------------|
| No garbage collector | Deterministic memory, no pauses |
| No hidden allocations | You control every byte |
| Static binary | No dependencies, drop and run |
| Compile-time execution | Config validation at build time |
| Cross-compilation | Build for ARM from x86 |

That 678 KB source build covers the same feature set as alternatives that weigh in at tens of megabytes or more.

## Installation

There are five ways to get NullClaw running. The order below matches the official docs: easiest first.

<Notice type="warning" title="Pin your version (pre-1.0, CalVer)">
NullClaw uses CalVer (`vYYYY.M.D`) and is pre-1.0. The README explicitly says "config and CLI may change between releases." Pin `NULLCLAW_IMAGE=ghcr.io/nullclaw/nullclaw:v2026.5.29` in production and compare your config with `config.example.json` on the tag you deploy. The latest stable tag is v2026.5.29 (May 2026); `main` has months of newer commits and there's a `nightly` prerelease channel if you want bleeding edge.
</Notice>

### Install with Homebrew

The recommended path on macOS and Linux:

```bash
brew install nullclaw
nullclaw --version   # should print the formula version (stable 2026.5.29)
```

The formula is bottled, so no compilation. To update later: `brew upgrade nullclaw`. NullClaw also ships a self-update command: `nullclaw update --check` then `nullclaw update --yes`.

### Run the official Docker image

The container image lives at `ghcr.io/nullclaw/nullclaw`. State lives in a named volume at `/nullclaw-data` (`/nullclaw-data/config.json`, `/nullclaw-data/workspace`).

```bash
# Onboard first (interactive wizard)
docker run --rm -it -v nullclaw-data:/nullclaw-data \
  ghcr.io/nullclaw/nullclaw:latest onboard --interactive

# Run the gateway
docker run -d \
  -p 127.0.0.1:3000:3000 \
  -v nullclaw-data:/nullclaw-data \
  --name nullclaw \
  ghcr.io/nullclaw/nullclaw:latest
```

Verify: `docker logs nullclaw` should show the startup banner and gateway bound to port 3000.

### Deploy with Docker Compose

The repo ships a `docker-compose.yml` and Makefile with profiles:

```bash
git clone https://github.com/nullclaw/nullclaw.git && cd nullclaw

# Pin the image
export NULLCLAW_IMAGE=ghcr.io/nullclaw/nullclaw:v2026.5.29

# Onboard (runs interactive wizard in the agent container)
make config

# Start the gateway
make up

# Verify
curl http://127.0.0.1:3210/health
```

The gateway container binds `0.0.0.0:3210` internally and publishes to `127.0.0.1:3210` on the host. Other useful targets: `make logs`, `make down`, `make shell`. Compose builds use `ZIG_VERSION: "0.16.0"`.

<Notice type="error" title="Never pass secrets via CONFIG_ARGS">
`make config` accepts non-secrets through `CONFIG_ARGS`, but passing API keys there puts them in shell history and process listings. Also, NullClaw does not expand `VAR`-style environment variables in `config.json`, so render the file with your deployment tooling (envsubst, Ansible) instead. See [Docker Compose secrets and secure alternatives](/docker-compose-secrets/) for the full picture.
</Notice>

Common Compose failure modes: wrong project name (stale volumes from a previous `docker compose` project), `docker compose down -v` wiping your state volume, and port 3210 already in use.

### Download prebuilt binaries

Release v2026.5.29 ships 15 assets: linux x86_64 (5.48 MB), linux aarch64 (4.40 MB), arm32 gnu/musl, riscv64, macOS x86_64/aarch64, Windows x86_64/aarch64, and Android aarch64/armv7/x86_64.

```bash
curl -LO https://github.com/nullclaw/nullclaw/releases/download/v2026.5.29/nullclaw-linux-x86_64.bin
chmod +x nullclaw-linux-x86_64.bin
sudo mv nullclaw-linux-x86_64.bin /usr/local/bin/nullclaw
nullclaw --version
```

These binaries are 4.4-6.5 MB. That's the official CI build. The 678 KB figure is a hand-optimized `ReleaseSmall` build you compile yourself.

### Build from source

Only do this if you need a custom build or want the smallest possible binary. You need Zig 0.16.0 exactly. Other versions fail with cryptic build errors.

```bash
# Install Zig 0.16.0
curl -L https://ziglang.org/download/0.16.0/zig-linux-x86_64-0.16.0.tar.xz | tar -xJ
sudo mv zig-linux-x86_64-0.16.0 /usr/local/zig
sudo ln -s /usr/local/zig/zig /usr/local/bin/zig
zig version   # MUST print 0.16.0

# Clone and build
git clone https://github.com/nullclaw/nullclaw.git && cd nullclaw
zig build -Doptimize=ReleaseSmall

# Binary at zig-out/bin/nullclaw
ls -lh zig-out/bin/nullclaw

# Optional: run the test suite (5,300+ tests)
zig build test --summary all

# Install
zig build -Doptimize=ReleaseSmall -p "$HOME/.local"
```

Cross-compiling for ARM: `zig build -Dtarget=aarch64-linux -Doptimize=ReleaseSmall` works for generic targets. Android needs the NDK libc, so most readers should just grab the prebuilt binary from releases instead.

### Onboard and first verify

After any install path, run the onboard wizard:

```bash
# Quick non-interactive setup
nullclaw onboard --api-key sk-or-... --provider openrouter

# Or the interactive wizard
nullclaw onboard --interactive
```

This creates `~/.nullclaw/` with a `config.json` and workspace folder.

## Configuring LLM providers

NullClaw supports 50+ providers out of the box. Every provider uses an OpenAI-compatible interface, so switching is a config change.

<Notice type="warning" title="No default_provider key">
Top-level `default_provider` and `default_model` keys are **not supported**. They silently do nothing. Provider selection goes through `agents.defaults.model.primary` with a provider-prefixed model route like `openrouter/anthropic/claude-sonnet-4`. An invalid route format is a documented cause of 401/403 errors.
</Notice>

### Supported providers

| Provider | Use case |
|----------|----------|

| Anthropic | Claude models |
| OpenAI | GPT models |
| Ollama | Local models |

That's the short list: 50+ total including Bedrock, Cohere, Mistral, xAI, Together, Fireworks, Venice, Perplexity, NEAR AI Cloud, Atlas Cloud, Evolink, and Eden AI.

### Get an API key

For OpenRouter (recommended for flexibility):

1. Go to [openrouter.ai](https://openrouter.ai)
2. Create an account and generate an API key
3. The key starts with `sk-or-`

### Add to config

Edit `~/.nullclaw/config.json`:

```json
{
  "default_temperature": 0.7,
  "models": {
    "providers": {
      "openrouter": {
        "api_key": "sk-or-your-key"
      }
    }
  },
  "agents": {
    "defaults": {
      "model": {
        "primary": "openrouter/anthropic/claude-sonnet-4"
      }
    }
  }
}
```

Note the provider-prefixed route format: `openrouter/anthropic/claude-sonnet-4`, not bare `anthropic/claude-sonnet-4`. Model IDs shown here are examples. Check current names on OpenRouter before deploying.

### Using custom providers

Any OpenAI-compatible endpoint works:

```json
{
  "models": {
    "providers": {
      "minimax": {
        "api_key": "your-minimax-key",
        "base_url": "https://api.minimax.chat/v1"
      }
    }
  },
  "agents": {
    "defaults": {
      "model": {
        "primary": "minimax/minimax-m2.7"
      }
    }
  }
}
```

Model routes also support the `custom:https://endpoint/model-name` syntax for endpoints that aren't in the built-in provider list.

## Reliability and failover

This is the section that turns a demo bot into one you can leave running unattended. The `reliability` block handles provider failures gracefully.

```json
{
  "reliability": {
    "provider_retries": 1,
    "provider_backoff_ms": 3000,
    "fallback_providers": ["groq"],
    "model_fallbacks": [
      {
        "model": "openrouter/anthropic/claude-sonnet-4",
        "fallbacks": ["openrouter/z-ai/glm-5.3"]
      }
    ]
  }
}
```

- `provider_retries` / `provider_backoff_ms`: retry on transient errors (429, 5xx). I'd keep retries conservative (`1`) and backoff at 3000ms to avoid burning tokens on repeated failures.
- `fallback_providers`: a list of provider names to try if the primary fails entirely.
- `model_fallbacks`: per-model fallback chains. If the primary model is down, NullClaw walks the list.
- `api_keys`: multiple keys for rotation if you're hitting rate limits across a team.

Memory-level circuit breaker options are also available: `circuit_breaker_failures` and `circuit_breaker_cooldown_ms` to stop hammering a failing embedding provider.

Cost note: retries cost tokens (you pay for failed attempts that reach the API). Fallbacks cost nothing until they're used.

### Model routing and hot reload

NullClaw's interactive commands give you live control over model selection:

- `/model`: shows all routes with `cost_class` and `quota_class` metadata. Pin a specific model or switch to auto-routing (`model_routes`).
- `/config reload`: hot-reloads supported config keys without restarting the gateway.

This means you can swap models mid-conversation or after a provider outage without touching the process.

## Channel setup

NullClaw supports 19 chat channels. Pick what you use.

### NullClaw Telegram bot

1. Create a bot via [@BotFather](https://t.me/BotFather)
2. Copy the bot token
3. Get your Telegram user ID (message [@userinfobot](https://t.me/userinfobot))

Config:

```json
{
  "channels": {
    "telegram": {
      "accounts": {
        "main": {
          "bot_token": "123456789:ABCdefGHIjklMNOpqrSTUvwxYZ",
          "allow_from": ["your_telegram_user_id"],
          "reply_in_private": true
        }
      }
    }
  }
}
```

For restricted networks, add `"proxy": "socks5://host:port"` to the account config.

<Notice type="warning" title="Allowlist behavior">
Empty `allow_from` means **deny all**. Use `["*"]` to allow everyone, or add specific user IDs to restrict access.
</Notice>

### Routing chats to agents (multi-agent)

If you need distinctly-scoped bots (say, a "work" assistant and a "home" assistant), NullClaw supports `agents.list` with per-agent `id`, `model`, `system_prompt`, and `workspace_path`. Each agent gets durable `agent:<id>` memory namespaces.

Route specific chats or Telegram forum topics to agents with `bindings[]`. Topic routing uses `"<chat_id>:thread:<topic_id>"`. At runtime: `/bind` to route, `/bind status` or `/bind clear` to inspect or undo. Subagents work via `/subagents spawn --agent <id>` and the `delegate` tool.

My recommendation: skip this unless you run multiple distinctly-scoped bots. Single-agent is simpler to debug.

## Full config example

Here's a complete `~/.nullclaw/config.json` using the current schema. No `default_provider` key. Provider-prefixed model route instead:

```json
{
  "default_temperature": 0.7,

  "models": {
    "providers": {
      "openrouter": { "api_key": "sk-or-..." }
    }
  },

  "agents": {
    "defaults": {
      "model": { "primary": "openrouter/anthropic/claude-sonnet-4" },
      "heartbeat": { "every": "30m" }
    }
  },

  "channels": {
    "telegram": {
      "accounts": {
        "main": {
          "bot_token": "123:ABC",
          "allow_from": ["your_user_id"]
        }
      }
    }
  },

  "memory": {
    "backend": "sqlite",
    "auto_save": true,
    "embedding_provider": "openai",
    "search": {
      "query": {
        "hybrid": { "enabled": true, "vector_weight": 0.7, "text_weight": 0.3 }
      }
    },
    "lifecycle": {
      "hygiene_enabled": true,
      "archive_after_days": 30,
      "purge_after_days": 90,
      "snapshot_enabled": true
    }
  },

  "gateway": {
    "port": 3000,
    "host": "127.0.0.1",
    "require_pairing": true,
    "allow_public_bind": false
  },

  "autonomy": {
    "level": "supervised",
    "workspace_only": true,
    "max_actions_per_hour": 20,
    "block_high_risk_commands": true,
    "block_medium_risk_commands": true
  },

  "reliability": {
    "provider_retries": 1,
    "provider_backoff_ms": 3000,
    "fallback_providers": ["groq"],
    "model_fallbacks": [
      {
        "model": "openrouter/anthropic/claude-sonnet-4",
        "fallbacks": ["openrouter/z-ai/glm-5.3"]
      }
    ]
  },

  "runtime": {
    "kind": "native",
    "docker": {
      "image": "alpine:3.24",
      "network": "none",
      "memory_limit_mb": 512,
      "read_only_rootfs": true
    }
  },

  "security": {
    "sandbox": { "backend": "auto" },
    "resources": { "max_memory_mb": 512, "max_cpu_percent": 80 },
    "audit": { "enabled": true, "retention_days": 90 }
  },

  "tunnel": { "provider": "none" },
  "secrets": { "encrypt": true },
  "identity": { "format": "openclaw" },

  "http_request": {
    "enabled": false,
    "allowed_domains": [],
    "search_provider": "auto"
  }
}
```

Validate against `config.example.json` on the tag you deploy. Key names drift between CalVer releases. If a config key seems ignored after an upgrade, diff your file against the tag's example.

The `http_request` block controls the web search tool. It's **disabled by default**, so enable it deliberately with `allowed_domains` and `search_provider: auto` (which falls back to jina/duckduckgo).

### Managing config with NullHub

If hand-editing JSON isn't your thing, [NullHub](https://github.com/nullclaw/nullhub) is the point-and-click alternative. It's a single Zig binary with an embedded Svelte UI (port 19800) that provides:

- Process supervision with crash recovery
- Health checks and log tailing (SSE)
- One-click updates with config migration and rollback
- Multi-instance management

NullHub is currently in beta. Hand-editing `config.json` remains the stable path, but for solo operators who want a dashboard, it's worth a look.

## Memory system

NullClaw's default memory is SQLite-based with no external dependencies: FTS5 keyword search with BM25 scoring and vector cosine similarity, merged with configurable weights.

There are now **10 memory engines**: SQLite (default), Markdown, ClickHouse, PostgreSQL, Redis, LanceDB, Lucid, LRU, API, and None. The PostgreSQL backend is a nice fit if you already run Postgres. See our guide to [self-host pgvector with Docker](/deploy-pgvector-pgadmin-docker/).

Config keys use a nested schema:

```json
{
  "memory": {
    "backend": "sqlite",
    "auto_save": true,
    "embedding_provider": "openai",
    "search": {
      "query": {
        "hybrid": { "enabled": true, "vector_weight": 0.7, "text_weight": 0.3 }
      },
      "store": {
        "type": "builtin"
      }
    },
    "lifecycle": {
      "hygiene_enabled": true,
      "archive_after_days": 30,
      "purge_after_days": 90,
      "snapshot_enabled": true,
      "auto_hydrate": true
    }
  }
}
```

Hybrid search is off by default, so enable it explicitly with `search.query.hybrid.enabled: true`. The `search.store` key also supports Qdrant and pgvector sidecar options.

Set `embedding_provider` to `noop` if you don't want to pay for embeddings. FTS5 keyword search still works without embeddings.

### Memory operations

Operator-grade memory commands for backup and maintenance:

```bash
# Export all memory (PII-redacted by default, stable schema_version)
nullclaw memory export-jsonl > memory-backup.jsonl

# Non-destructive duplicate report
nullclaw memory hygiene-report

# Rebuild search indexes
nullclaw memory reindex

# Drain the outbox queue
nullclaw memory drain-outbox

# Forget specific memories
nullclaw memory forget <id>
```

`memory export-jsonl` is your memory backup primitive. Run it before upgrades. The PII redaction is on by default, which is the right default for anything leaving the machine.

## Security model

NullClaw locks things down at multiple levels, not just application-level allowlists.

### Gateway security

| Layer | Default | What it does |
|-------|---------|-------------|
| Localhost binding | `127.0.0.1` | Refuses public exposure |
| Pairing required | `true` | 6-digit code exchange for bearer token |
| Tunnel required | `false` | Refuses `0.0.0.0` without tunnel |

`/pair` is POST-only and rate-limited, and repeated bad codes trigger a temporary lockout. The pairing flow:

```bash
# Start gateway (shows pairing code)
nullclaw gateway

# Exchange code for token
curl -X POST http://127.0.0.1:3000/pair \
  -H "X-Pairing-Code: 123456"

# Use token for requests
curl -X POST http://127.0.0.1:3000/webhook \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"message": "Hello, nullclaw!"}'
```

To expose the gateway externally, configure a tunnel:

```json
{
  "tunnel": {
    "provider": "cloudflare"
  }
}
```

Supported tunnels: Cloudflare, Tailscale, ngrok, or a custom binary with `start_command`/`health_url`. If you'd rather use SSH port forwarding, see [SSH tunneling in Linux](/ssh-tunneling-linux/).

### Sandbox isolation

NullClaw auto-detects the best sandbox backend:

| Backend | Platform | Security level |
|---------|----------|---------------|
| Landlock | Linux 5.13+ | Kernel-level |
| Firejail | Linux | Namespaces |
| Bubblewrap | Linux | Lightweight containers |
| Docker | Any | Full container isolation |

```json
{
  "security": {
    "sandbox": { "backend": "auto" }
  }
}
```

Set `"backend": "docker"` for maximum isolation. The Docker runtime image is configurable (currently `alpine:3.24`) with network isolation and read-only rootfs options. The runtime vtable also supports WASM (wasmtime) alongside Native and Docker.

### Encrypted secrets

API keys are encrypted with ChaCha20-Poly1305 (prefix `enc2:` in config):

```json
{
  "secrets": { "encrypt": true }
}
```

The encryption key is stored locally in `~/.nullclaw/`. For the service startup path, `~/.nullclaw/service-env` (if executable) runs before the service starts. This is the clean hook for sops or dotenvx secret injection.

### Workspace scoping and secret audit

With `workspace_only = true`, the bot can only access files inside its workspace. Symlink escape attempts are blocked through path canonicalization.

`nullclaw workspace audit` scans the workspace for leaked credentials:

```bash
# Scan for secrets (token prefixes, PEM blocks, creds-in-URLs, entropy)
nullclaw workspace audit

# CI-friendly output
nullclaw workspace audit --json --fail-on high
```

It detects `AKIA...`, `ghp_`, `sk-` token prefixes, PEM blocks, credentials embedded in URLs, and high-entropy strings. Optional `--llm-triage external` sends redacted context to an LLM for triage without exposing the secret itself. Audit results land in `audit-log.jsonl`.

For broader security hardening beyond NullClaw, see [our OpenClaw security guide covering malicious skills and 40+ fixes](/openclaw-security-guide/). NullClaw shares the OpenClaw-compatible config surface.

### Autonomy hardening

New config keys control what the bot can execute:

```json
{
  "autonomy": {
    "level": "supervised",
    "workspace_only": true,
    "max_actions_per_hour": 20,
    "block_high_risk_commands": true,
    "block_medium_risk_commands": true,
    "require_approval_for_medium_risk": true
  }
}
```

- `block_high_risk_commands`: blocks destructive operations.
- `block_medium_risk_commands`: blocks `curl`, `wget`, `nc`, `scp`, `git commit`, `npm install`, and similar.
- `require_approval_for_medium_risk`: human-in-the-loop for anything medium-risk.
- `allowed_paths`: restrict filesystem access to specific directories.
- Shell child processes get a minimal environment allowlist (PATH, HOME, TERM...) by default. Use `tools.path_env_vars` for validated path variables like `LD_LIBRARY_PATH`.

<Notice type="warning" title="High-risk settings">
Never set `autonomy.level` to `full` or `yolo` on a public VPS. Never use `allowed_commands: ["*"]`. Never disable both blocks for an always-on bot. Supervised mode with both blocks enabled is the right default.
</Notice>

## Scheduled tasks

NullClaw has a built-in cron scheduler with both recurring and one-shot tasks:

```bash
# Recurring shell command
nullclaw cron add "0 9 * * *" "curl -s https://api.example.com/health"

# Recurring agent prompt (with model, channel, and announce options)
nullclaw cron add-agent "0 9 * * *" "What's on my calendar today?" \
  --model openrouter/anthropic/claude-sonnet-4 --channel telegram --announce

# One-shot delayed command
nullclaw cron once 10m "echo done"

# One-shot delayed agent prompt
nullclaw cron once-agent 10m "Summarize today's logs" --session-target isolated

# Manage tasks
nullclaw cron list
nullclaw cron status <id>
nullclaw cron runs <id>
nullclaw cron update <id> --expression "0 10 * * *"
nullclaw cron pause <id>
nullclaw cron resume <id>
nullclaw cron run <id>
nullclaw cron remove <id>
```

Tasks are persisted to JSON and survive restarts. You can also manage cron jobs over HTTP via the `/cron*` gateway endpoints.

### Systemd service

There are two ways to run NullClaw as a service.

**Official: `nullclaw service install`.** On Linux, this uses `systemd --user` (not system-level). On a root VPS, this needs `loginctl enable-linger` or the service dies when you log out:

```bash
loginctl enable-linger root
nullclaw service install
nullclaw service start
nullclaw service status
```

**Pragmatic for root VPS: manual system-level unit.** This avoids the linger problem:

```ini
[Unit]
Description=NullClaw AI Assistant
After=network.target

[Service]
Type=simple
ExecStart=/usr/local/bin/nullclaw gateway
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```

Save to `/etc/systemd/system/nullclaw.service`, then:

```bash
systemctl daemon-reload
systemctl enable nullclaw
systemctl start nullclaw
systemctl status nullclaw
journalctl -u nullclaw -f
```

Logs land in `~/.nullclaw/logs/daemon.stdout.log` and `daemon.stderr.log` (the filenames keep the old "daemon" name. That's just the log naming, the command is `gateway`).

Failure modes: linger not enabled (service dies on logout) and `ExecStart` referencing the old `daemon` command (unit fails immediately).

### Common failures and fixes

| Failure | Cause | Fix |
|---------|-------|-----|
| 401/403 on agent call | Bad/expired key, wrong provider name, or invalid model route | Check API key, verify provider name matches `models.providers`, use provider-prefixed route (`openrouter/model-name`) |
| 429 rate limit | Plan quota exceeded | Tune `reliability` conservatively: `provider_retries: 1`, `provider_backoff_ms: 3000` |
| Gateway unreachable externally | Still on `127.0.0.1`, tunnel not up, or firewall | Configure a tunnel or check firewall rules; `allow_public_bind` requires explicit opt-in |
| Build fails cryptically | Zig version mismatch | `zig version` must print `0.16.0` exactly |
| Docker state missing | Wrong volume path or `down -v` wiped it | State lives at `/nullclaw-data`; never use `docker compose down -v` casually |
| Config keys ignored | Environment variable placeholders not expanded, or key renamed between releases | Render config with envsubst/Ansible; diff against `config.example.json` for your tag |
| Service exits on logout | `systemd --user` without linger | `loginctl enable-linger` or use the manual system-level unit |
| Ollama `scheduler_tool` error | Known bug in older builds | Upgrade NullClaw. Don't reconfigure |
| Pairing code lockout | Too many bad `/pair` attempts | Wait out the lockout window |

## Gateway API

| Endpoint | Method | Auth | Description |
|----------|--------|------|-------------|
| `/health` | GET | None | Health check |
| `/pair` | POST | `X-Pairing-Code` | Exchange code for token (rate-limited) |
| `/webhook` | POST | Bearer token | Send message (sync mode for paired-token workers) |
| `/whatsapp` | GET | Query params | Meta webhook verification |
| `/whatsapp` | POST | Meta signature | WhatsApp incoming |
| `/media/transcribe` | POST | Bearer token | STT: base64 audio to text (e.g. Groq whisper-large-v3) |
| `/cron`, `/cron/add`, `/cron/remove` | GET/POST | Bearer token | Cron management over HTTP |
| `/cron/pause`, `/cron/resume`, `/cron/update` | POST | Bearer token | Cron lifecycle |
| `/telegram` | POST | `X-Telegram-Bot-Api-Secret-Token` | Telegram webhook (matches `webhook_secret`) |
| `/max` | POST | `X-Max-Bot-Api-Secret` | Max messenger webhook |
| `/api/messages` | POST | Teams JWT | MS Teams Bot Framework |
| `/.well-known/agent-card.json` | GET | None | A2A agent card (public) |
| `/a2a` | POST | Bearer token | A2A protocol (JSON-RPC 2.0) |

A2A support follows protocol v0.3.0: `message/send`, `message/stream`, and `tasks/*` methods. Note: some doc versions reference `/.well-known/agent.json` instead of `agent-card.json`. Verify on your live gateway.

Gateway tuning keys: `max_body_size_bytes`, `request_timeout_secs`, `webhook_rate_limit_per_minute`. Set these in the `gateway` config block.

Pairing is POST-only and rate-limited with temporary lockout after repeated bad codes. If you lock yourself out, restart the gateway to get a fresh pairing code.

**How much does it cost to run NullClaw?**

Hardware: $5 for a cheap ARM board, or $0 if you already have a VPS from [Hetzner](https://go.bitdoze.com/hetzner) or [Hostinger](https://go.bitdoze.com/hostinger-vps). API costs depend on your provider. Expect $5-50/month for personal use as an order-of-magnitude, not a promise. **Can I run NullClaw without any API costs?**

Yes. Configure Ollama as your provider and point it at a local model. You need hardware that can run inference. A [mini PC like the ASUS DC510](https://go.bitdoze.com/asus-dc510) handles small models well. See our [Ollama Docker Compose setup with Open WebUI](/ollama-docker-install/) for the local-model stack, and the [best mini PC for local LLMs](/best-mini-pc-local-llm/) for hardware picks.

**Does NullClaw work on a Raspberry Pi Zero?**

The project targets $5 boards and the Pi Zero 2 W (512 MB) is in their supported-hardware table. The assistant itself runs fine on minimal hardware; the constraint is always LLM inference if you're running local models.

**Can multiple people use one NullClaw instance?**

Yes. Add multiple user IDs to `allow_from`. Each person gets their own conversation context.

**What's the difference between gateway and daemon?**

`nullclaw gateway` **is** the long-running runtime. It starts the gateway plus all configured channels, heartbeat, and scheduler. There is no separate `daemon` command in the current CLI (the word "daemon" survives only in internal log filenames like `daemon.stdout.log`).

**How do I update NullClaw?**

Depends on your install method: `nullclaw update --check` then `nullclaw update --yes` (binary installs), `brew upgrade nullclaw` (Homebrew), or pull a new pinned Docker tag and recreate the container. For Compose: `NULLCLAW_IMAGE=ghcr.io/nullclaw/nullclaw:vNEW make up`. Rollback: pin the previous tag. CalVer pre-1.0 means config churn. Diff `config.example.json` after every upgrade.

**Can I migrate from OpenClaw to NullClaw?**

Yes. NullClaw has a built-in migration command:

```bash
nullclaw migrate openclaw --dry-run
nullclaw migrate openclaw
```

Always run `--dry-run` first to see what will change.

**Why are my config keys ignored after an upgrade?**

Pre-1.0 schema churn. Compare your config with `config.example.json` on the tag you deployed. For example, memory keys moved from top-level (`vector_weight`, `keyword_weight`) to nested schema (`search.query.hybrid.*`, `lifecycle.*`). When in doubt, re-derive your config from the tag's example file.

**How do I add a channel that's not supported?**

Implement the `Channel` vtable interface in `src/channels/` and submit a PR. The architecture is designed for extensions.
