Hermes Kanban ist ein persistentes SQLite-Task-Board direkt in [Hermes Agent](/hermes-agent-setup-guide/) (auf Englisch) zur Koordination von Multi-Agent-Workflows. Statt alles im Chat zu verlieren, planst du Aufgaben als Karten, weist sie benannten Agent-Profilen zu und lässt den Gateway-Dispatcher Worker starten, die Aufgaben abarbeiten, prüfen lassen und zurückmelden. Das Board siehst du im integrierten [Dashboard](/de/hermes-dashboard-anleitung/) sowie in [Hermes-Dashboards und Mobile-Apps](/de/beste-hermes-dashboards/).

Dieser Guide deckt den Stand der aktuellen Version (`v0.23.x`), alle relevanten CLI-Befehle, das Dispatcher- und Worker-Modell, Multi-Agent-Muster, Kostenkontrolle und die Fehlerdiagnose ab.

![Hermes Kanban Architektur: SQLite-Task-Board, Gateway-Dispatcher und Multi-Agent-Worker](@assets/images/25/05/hermes-kanban-setup-guide.svg)

## Was ist Hermes Kanban?

Hermes Kanban läuft als **SQLite-gestütztes Aufgabensystem** neben dem Hermes-Gateway:

- **Visuelle Boards** mit sechs aktiven Spalten: Triage, Todo, Ready, In progress, Blocked und Done.
- **Übergaben zwischen Profilen:** Karten gehen an echte Hermes-Profile (`~/.hermes/profiles/<name>/`) mit eigenem Speicher und eigener Modellwahl.
- **Persistenter Event-Verlauf:** Jeder Zustandswechsel landet mit Zeitstempel und Agent-ID in SQLite.
- **Dashboard-Anbindung:** Drag-and-drop, Worker-Logs und Live-Updates im eingebauten Kanban-Plugin.

Unter der Haube kennt die State-Machine zusätzliche Zustände: `triage | todo | scheduled | ready | running | blocked | review | done | archived`. `review` und `scheduled` sind gesperrte Spalten ohne Drag-and-drop. Das Standard-Board liegt unter `~/.hermes/kanban.db`, weitere Projekt-Boards isoliert unter `~/.hermes/kanban/boards/<slug>/kanban.db`.

<Notice type="info" title="Versionshinweis">
Das dauerhafte Kanban erschien mit **v2026.5.7** ("Tenacity Release"); die aktuelle stabile Version ist **v0.23.3** (20.11.2026). Prüfe deinen Stand mit `hermes --version` und aktualisiere per `hermes update`.
</Notice>

## Kanban vs delegate_task: Wann passt was?

`delegate_task` ist ein synchroner Unteraufruf im laufenden Chat; Kanban ist eine dauerhafte Aufgaben-Queue mit Review, Wiederaufnahme und vollständiger Historie.

<Accordion label="Schnellvergleich" group="comparison" expanded="true">

| Merkmal | `delegate_task` | Kanban |
|---|---|---|
| **Typ** | RPC-Aufruf (fork -> join) | Dauerhafte Queue + State-Machine |
| **Eltern-Agent** | Wartet blockierend | Fire-and-forget nach `create` |
| **Worker-Identität** | Anonymer Subagent | Benanntes Profil mit persistentem Speicher |
| **Wiederaufnahme** | Keine | Block -> Unblock -> Neustart; Crash -> Reclaim |
| **Mensch im Loop** | Nicht möglich | Kommentieren und Entblocken jederzeit |
| **Audit-Log** | Geht bei Kontext-Kompression verloren | Dauerhafte SQLite-Einträge |

</Accordion>

<Notice type="warning" title="Link-Deadlock vermeiden">
Ein auf `t_parent` blockierter Worker darf keine Hilfskarte als Kind von `t_parent` per `kanban_link` anlegen, weil die Hilfskarte sonst genau durch den Blocker gesperrt wird (`gated: true`). Lösung: `hermes kanban unlink <parent> <child>`.
</Notice>

## Hermes Kanban einrichten

### Voraussetzungen

<ListCheck>
<ul>
<li>Hermes Agent v0.23.x installiert</li>
<li>Mindestens ein echtes <strong>Profil</strong> pro Worker-Rolle (<code>~/.hermes/profiles/&lt;name&gt;/</code>)</li>
<li>Lauffähiges Hermes-Gateway (<code>hermes gateway start</code>)</li>
<li>Modellzugang pro Profil (<a href="/de/guenstige-hermes-agent-modelle/">günstige Modelle für Hermes Agent</a>)</li>
<li>Optionales <a href="/de/hermes-dashboard-anleitung/">Hermes Dashboard</a></li>
</ul>

### Dispatcher konfigurieren

Die Konfigurationsdatei heißt `~/.hermes/config.yaml` (eine `gateway.yaml` gibt es nicht). Secrets gehören in `.env`.

```yaml
# ~/.hermes/config.yaml
kanban:
  dispatch_in_gateway: true        # Standard: Dispatcher läuft im Gateway
  dispatch_interval_seconds: 60    # Takt in Sekunden
  review_dispatch: true            # startet Reviewer mit sdlc-review-Skill
  max_in_progress: 2               # parallele Worker begrenzen (kleiner VPS / lokale LLMs)
  failure_limit: 2                 # Auto-Block nach N Fehlern (gave_up)
  done_sub_retention_days: 30
  reconcile_orphans: true
```

Starten und prüfen:

```bash
hermes kanban init
hermes gateway start
hermes kanban stats
hermes kanban diagnostics
hermes kanban dispatch --dry-run
```

<Notice type="warning" title="Veraltet: hermes kanban daemon">
`hermes kanban daemon` ist veraltet. Betreibe niemals den alten Daemon parallel zum Gateway-Dispatcher auf derselben `kanban.db`, sonst starten zwei Dispatcher dieselbe Karte.
</Notice>

## Wichtige Befehle für Boards und Aufgaben

```bash
# Boards verwalten
hermes kanban boards list
hermes kanban boards create rest-api --name "REST API" --switch
hermes kanban boards show
hermes kanban boards export rest-api -o rest-api.tar.gz
hermes kanban boards rm rest-api              # archiviert unter boards/_archived/
hermes kanban boards rm rest-api --delete     # endgültiges rm -rf ohne Rückfrage
```

<Tabs>
<Tab name="Aufgabe anlegen">

```bash
hermes kanban create "Auth-Endpoints bauen" \
  --assignee coder --body "POST /login, Sessions, Rate-Limiting" --priority 2
```

</Tab>
<Tab name="Abhängigkeiten (--parent)">

```bash
# Verkettung über --parent (wiederholbar), NICHT --depends-on
SCHEMA=$(hermes kanban create "Auth-Schema entwerfen" --assignee coder --json | jq -r .id)
hermes kanban create "Auth-Endpoints bauen" --assignee coder --parent "$SCHEMA"
```

</Tab>
<Tab name="Worktree, Zeitplan & Goal-Mode">

```bash
hermes kanban create "Billing-Refactor" --assignee coder --workspace worktree --branch wt/billing
hermes kanban create "Backup-Check" --assignee ops --scheduled-at "2026-12-01T03:00:00Z"
hermes kanban create "Migration" --assignee coder --max-runtime 2h --model gpt-5.2 --provider openrouter
hermes kanban create "Doku übersetzen" --assignee linguist --goal --goal-max-turns 15
```

</Tab>
</Tabs>

<Notice type="warning" title="Scratch-Workspaces sind temporär">
Der Standard-Workspace `scratch` wird nach Abschluss gelöscht. Für bleibende Dateien nutze `--workspace worktree`, `--workspace dir:<absoluter Pfad>` oder `kanban_complete(artifacts=[...])`.
</Notice>

Es gibt kein `hermes kanban move`; Statuswechsel laufen über klare Verben (`assign`, `complete`, `request-review`, `request-changes`, `block`, `unblock`, `promote`, `archive`). Jeder Worker schließt per `kanban_complete`, `kanban_request_review` oder `kanban_block` ab.

## Dispatcher, Swarms, Benachrichtigungen und Betrieb

Alle 60 Sekunden räumt der Gateway-Dispatcher verwaiste Claims auf (Claim-TTL 900 s, Stale-Timeout 4 h mit `kanban_heartbeat`), befördert `todo -> ready` sobald Elternkarten `done` sind und startet `hermes -p <assignee> chat -q <prompt>`.

- **Swarms in einem Befehl:** `hermes kanban swarm "Failover-Plan" --worker researcher --worker architect --verifier reviewer --synthesizer writer`.
- **Goal-Mode (`--goal`):** iteriert gegen eigene Akzeptanzkriterien bis `--goal-max-turns` (Standard 20) und geht bei Erschöpfung auf `blocked`.
- **Telegram/Discord-Benachrichtigungen:** Karten über `/kanban create` abonnieren den Chat automatisch für `completed`, `blocked`, `gave_up`, `crashed` und `timed_out`. Aus der CLI nutzt du `hermes kanban notify-subscribe`.
- **Parallel-Session-Übersicht:** Für viele gleichzeitige Terminal-Agenten ergänzt der [Herdr Agent Multiplexer](/de/herdr-agent-multiplexer/) das Setup ideal.

- **Kostenstrategie:** starkes Modell für den Planer, günstige Modelle für Worker (siehe [günstige Modelle für Hermes Agent](/de/guenstige-hermes-agent-modelle/) oder [MiMo-Modelle](https://go.bitdoze.com/mimo)).
- **VPS-Praxis:** 2 vCPU / 2-4 GB RAM (z. B. ein [Hetzner Cloud VPS](https://go.bitdoze.com/hetzner)) mit `max_in_progress: 2`. Auf systemd-Systemen ist `sudo loginctl enable-linger <user>` Pflicht, sonst scheitern Worker-Starts mit `spawn_failed`. Datenbankpflege erledigt `hermes kanban gc --event-retention-days 30 --log-retention-days 14`.

## Fehlerbehebung

<Accordion label="Karten bleiben in ready hängen" group="faq" expanded="true">
Prüfe nacheinander: (1) Läuft das Gateway (`hermes gateway start`)? (2) Existiert das Profil unter `~/.hermes/profiles/`? (3) Zeigt `hermes kanban dispatch --dry-run` aktive Guards (`respawn_guarded`, `rate_limited`, `memory_pressure`)? (4) Prüfe `hermes kanban diagnostics`.
</Accordion>

<Accordion label="Worker starten auf einem VPS nicht" group="faq">
Führe `sudo loginctl enable-linger <user>` aus. Ohne Linger schlagen Worker-Spawns unter systemd mit `spawn_failed` + `infrastructure: true` fehl.
</Accordion>

<Accordion label="Eine Karte bricht wiederholt ab oder springt nach triage" group="faq">
`gave_up` greift nach `failure_limit` (Standard 2); `protocol_violation` nach 3 Exits ohne `kanban_*`-Aufruf; `block_loop_detected` leitet nach zwei identischen Block-Schleifen nach `triage` um. Logs liest du mit `hermes kanban log <id> --tail`.
</Accordion>
