## Was sind Herdr-Plugins?

Ein Herdr-Plugin ist ein Verzeichnis mit einem `herdr-plugin.toml`-Manifest plus Befehlen, die Herdr als argv-Arrays startet. Das ist das ganze Modell. Es gibt kein SDK und keine eingeschränkte API-Oberfläche: Die komplette `herdr`-CLI ist die Plugin-API, und Plugins rufen über `HERDR_BIN_PATH` zurück – das funktioniert über Unix-Sockets und Windows-Named-Pipes gleichermaßen. Jede Sprache geht, weil Herdr einfach ausführt, was das Manifest deklariert: Bash, JavaScript, Lua, Rust, Go, Python, PowerShell.

Der Herdr-Plugin-Marketplace auf `herdr.dev/plugins` ist kein Katalog, den irgendjemand geprüft hätte. Es ist ein automatischer Index öffentlicher GitHub-Repositories mit dem Tag `herdr-plugin`, alle 30 Minuten aktualisiert. Forks, archivierte Repos und Repos, deren Manifeste nicht parsen, sind ausgeschlossen. Alles andere taucht auf.

<Notice type="warning" title="Keine Sandbox, kein Review">
  Die offiziellen Docs sagen es klar: „Ein Plugin ist gewöhnlicher Code, der auf deinem Rechner läuft.“ Herdr validiert die Manifest-Felder und sonst nichts – es „prüft Plugin-Code weder, noch isoliert es ihn in einer Sandbox“. Ein Plugin läuft als dein User, mit deinen Umgebungsvariablen und deinem vollen CLI-Zugriff. Prüfen ist deine Aufgabe – die Checkliste unten ist die Gegenmaßnahme.
</Notice>

![Herdr-Plugin-Architekturdiagramm: Manifest-Sektionen, argv-Befehle, injizierte Runtime-Umgebungsvariablen und Callbacks über die herdr-CLI](@assets/images/26/10/herdr-plugin-anatomy.webp)

Das Manifest ist der Vertrag. Pflichtfelder sind `id`, `name`, `version` und `min_herdr_version` (die Plugin-API existiert seit herdr 0.7.0, und Herdr lehnt ein Plugin ab, das eine neuere Binary verlangt als die installierte). Die optionalen Sektionen decken die interessanten Teile ab: `[[build]]` kompiliert Dinge bei GitHub-Installationen, `[[startup]]` führt einmalige Initialisierung nach Session-Restore aus und läuft bei Live-Handoff erneut, `[[actions]]` sind benannte Befehle, die du aufrufen oder auf Keys binden kannst, `[[events]]` reagieren auf Ereignisse wie `on = "worktree.created"`, `[[panes]]` platzieren eine UI (standardmäßig Overlay, oder `popup`, `split`, `tab`, `zoomed`), und `[[link_handlers]]` machen aus Ctrl+Klick auf eine URL eine Aktion via Rust-Regex.

Zur Laufzeit injiziert Herdr `HERDR_SOCKET_PATH`, `HERDR_BIN_PATH`, `HERDR_ENV=1`, `HERDR_PLUGIN_ID`, `HERDR_PLUGIN_ROOT`, `HERDR_PLUGIN_CONFIG_DIR`, `HERDR_PLUGIN_STATE_DIR` und `HERDR_PLUGIN_CONTEXT_JSON`. Merke dir eine Regel zu diesen Pfaden: `HERDR_PLUGIN_ROOT` ist ein verwalteter Checkout, den eine Neuinstallation ersetzt. Lagere dort niemals Credentials. Config- und State-Verzeichnisse gehören dir.

## Herdr-Plugins sicher installieren

Herdr-Plugins zu installieren ist ein Befehl. Sie ohne Reue zu installieren, kostet vorher fünf Minuten Lesen. Der Ablauf in der Praxis lautet: Voraussetzungen, prüfen (die volle Checkliste steht in einem eigenen Abschnitt weiter unten), mit Preview installieren, die geprüfte Revision pinnen, verifizieren und den Rollback-Pfad kennen.

### Voraussetzungen (was du brauchst)

Herdr 0.7.0 oder neuer, weil die Plugin-API damit kam. Einzelne Plugins können mehr verlangen: herdr-reviewr braucht >= 0.7.5, und der herdr-web-ui-Installer erwartet 0.9.0+. Git, weil `plugin install` ein Repository klont. Und welche Toolchain das Plugin auch immer baut: node oder bun für TypeScript-Plugins, Go für die herdr-plus- und tsk-Fraktion, cargo für die Rust-TUIs. Herdr installiert keine Toolchains für dich. Ein fehlendes `cargo` zeigt sich als fehlgeschlagener Build-Schritt, der die Registrierung abbricht.

    <li>herdr >= 0.7.0, bestätigt mit `herdr --version`</li>
    <li>git auf dem PATH (die Installation klont das Repo)</li>
    <li>die Toolchain, mit der dein Pick baut: node/bun, go oder cargo</li>

### Mit Preview installieren, eine Revision pinnen

1. Stöbere im Index auf https://herdr.dev/plugins oder suche auf GitHub nach `topic:herdr-plugin`.
2. Öffne das Repo und lies `herdr-plugin.toml` vor allem anderen. Wenn die Befehle falsch aussehen, hör hier auf.
3. Führe `herdr plugin install owner/repo[/subdir]` aus. In einem interaktiven Terminal zeigt Herdr eine Vorschau der Quelle und der Befehle, die es gleich ausführen wird. Lies sie. **Gib bei einer Erstinstallation niemals `--yes` an.**
4. Pinne, was du geprüft hast: `herdr plugin install owner/repo --ref v1.2.0`. Der Pin ist dein Rollback-Anker.
5. Build-Befehle laufen nur bei GitHub-Installationen. Ein Build-Fehler bricht die Registrierung ab, und das Manifest nach der Vorschau zu bearbeiten, bricht die Installation ab. Beides sind gewollte Schutzfunktionen. Für lokale Entwicklung registriert `herdr plugin link /pfad` ein Verzeichnis und überspringt Builds komplett.

```bash
# mit interaktiver Vorschau installieren
herdr plugin install persiyanov/herdr-reviewr

# exakt die geprüfte Revision installieren
herdr plugin install persiyanov/herdr-reviewr --ref v1.2.0

# lokale Entwicklung: Verzeichnis registrieren, kein Build-Schritt
herdr plugin link /home/you/src/my-herdr-plugin
```

### Verifizieren, dass es funktioniert

Nach jeder Installation Registrierung und sauberen ersten Lauf bestätigen:

```bash
herdr plugin list --json                      # registriert + aktiviert, mit IDs
herdr plugin action list --plugin plugin.id   # welche Aktionen existieren
herdr plugin action invoke plugin.id.action   # eine einmalig ausführen
herdr plugin log list --plugin plugin.id --limit 20
```

Öffne das Pane oder die Aktion des Plugins einmal – in den Logs sollte eine normale Ausgabe mit Exit-Code 0 stehen. So sieht „kaputt“ aus: Das Plugin fehlt in `plugin list`, ein Non-Zero-Exit in `plugin log list`, oder eine Aktion hängt, weil ihre Toolchain oder eine Config-Datei fehlt.

Um eine Aktion auf einen Key zu binden, füge sie in `~/.config/herdr/config.toml` ein und lade neu:

```toml
[[keys.command]]
key = "prefix+l"
type = "plugin_action"
command = "example.layout.apply"
description = "apply layout"
```

```bash
herdr server reload-config
```

### Rollback / Rückgängig

```bash
herdr plugin disable ID        # behalten, aber Ausführung stoppen
herdr plugin enable ID
herdr plugin uninstall ID      # entfernt den verwalteten Checkout
herdr plugin unlink ID         # lokale Dev-Registrierung aufheben
```

`uninstall` entfernt den verwalteten Checkout, lässt aber Config- und State-Verzeichnisse stehen – dein Rettungsweg, falls du aus Versehen deinstallierst. Zwei Eigenheiten: Über ein gelinktes Plugin zu installieren wird abgelehnt, also erst `unlink`; und unter 0.7.3 müssen Plugins, die nur innerhalb einer benannten Session registriert sind, neu gelinkt oder neu installiert werden.

Fehlerbilder in diesem Abschnitt: Ein Build-Abbruch mit gekürztem stdout/stderr ist fast immer ein fehlendes `cargo`/`npm`/`go` – Toolchain installieren und nochmal versuchen. Eine abgelehnte Installation über einem lokalen Verzeichnis heißt, du bist an die Linked-Plugin-Regel geraten. Ein Abbruch nach der Vorschau heißt, das Manifest hat sich zwischen Vorschau und Bestätigung geändert – Herdr weigert sich, Code auszuführen, den du nicht gesehen hast.

### Den Diff des Agents reviewen (herdr-reviewr)

`persiyanov/herdr-reviewr` (804 Stars) öffnet den Diff des Agents in einem Terminal-Pane und schickt Zeilenkommentare zurück an Claude Code, Codex, OpenCode und Pi. Rust, mit vorgefertigten Binaries, also kein cargo-Schritt beim Installieren. Es verlangt herdr >= 0.7.5 und läuft auf macOS und Linux. Es schließt die Lücke, die zählt, sobald ein Agent Code schreibt: die zwischen „er hat Code geschrieben“ und „du hast ihn gelesen“. Das ist der Killer-Anwendungsfall für Herdr-Plugins überhaupt, weil die Review-Schleife direkt neben dem Agent liegt statt in einem Browser-Tab, den du zu prüfen vergisst.

```bash
herdr plugin install persiyanov/herdr-reviewr
```

![herdr-reviewr in der Herdr-TUI: ein git-diff-Pane mit einem Zeilenkommentar in der Warteschlange zum Zurücksenden an den Agent](@assets/images/26/10/herdr-reviewr-ui.webp)

Trust-Hinweis: kleine Rust-Fläche, das Manifest deklariert die üblichen Aktionen und Panes, keine Überraschungen in den Command-Arrays jenseits der Review-Binary selbst. Verifizieren, indem du das Review-Pane einmal auf einem Repo mit uncommitteten Änderungen öffnest und prüfst, ob der Diff rendert – dann einen Test-Zeilenkommentar hinterlassen und zusehen, wie er im Input des Agents ankommt. So sieht „kaputt“ aus: ein leeres Diff-Pane auf einem schmutzigen Working Tree, was meist heißt, dass das Plugin nicht auf den richtigen Workspace-Tab zeigt.

Wenn du es leichter willst: `jhochenbaum/herdr-hunk-diff` (143 Stars) macht Hunk-basiertes Review mit Inline-Kommentaren und weniger beweglichen Teilen. Installiert sich genauso: `herdr plugin install jhochenbaum/herdr-hunk-diff`. `plannotator/herdr-annotate` ist das „Kommentiere-alles“-Gegenstück, falls dein Feedback-Loop Terminal-Text allgemein betrifft, nicht nur Diffs.

### Sehen, was der Agent angefasst hat (herdr-file-viewer)

`smarzban/herdr-file-viewer` (636 Stars) ist ein git-bewusster, schreibgeschützter File-Tree in der TUI: Baum plus Inhalt, Working-Tree-Diffs, gerendertes Markdown, Syntax-Highlighting. Read-only ist ein Feature, wenn der Agent derjenige ist, der Dateien schreibt. Du schaust zu, er schreibt – und du kannst im Viewer keine Datei versehentlich kaputt editieren.

```bash
herdr plugin install smarzban/herdr-file-viewer
```

![herdr-file-viewer im Vollbild: Dateibaum links, gerenderter Dateiinhalt mit Syntax-Highlighting rechts](@assets/images/26/10/herdr-file-viewer-ui.webp)

Verifizieren, indem du das Tree-Pane öffnest und prüfst, ob der Working-Tree-Diff die letzte Änderung des Agents zeigt. Wenn der Baum rendert, aber Diffs leer bleiben, prüfe, ob du das Pane im selben Workspace-Tab wie das Repo geöffnet hast; das Plugin liest den Git-State seines eigenen Pane-Kontexts.

Wenn du stattdessen einen schreibfähigen Explorer im VS-Code-Stil willst: `alexarthurs/herdr-sidebar` (424 Stars) bringt Datei-Explorer, Git-Source-Control, Diffs und AI-Commit-Messages. Beachte den Unterschied vor der Installation: Es kann dein Repo verändern, herdr-file-viewer nicht.

### Crash-Recovery und Plugin-Verwaltung (herdr-resurrect, herdr-plugin-manager)

`ntindle/herdr-resurrect` (37 Stars) ist tmux-resurrect für Herdr: Es erstellt Snapshots von Workspaces, Tabs, Panes, cwd, Programmen und Agents und stellt sie nach einem Crash oder Reboot wieder her. Die Star-Zahl ist niedrig, der Wert nicht. Eine 12-Pane-Agent-Farm durch einen Reboot zu verlieren, ist ein schlechter Nachmittag. Snapshots triggern auf die Events, die das Plugin deklariert, und Restore läuft über dieselbe herdr-CLI wie alles andere – es gibt keinen separaten Daemon zu betreuen.

```bash
herdr plugin install ntindle/herdr-resurrect
```

`speardragon/herdr-plugin-manager` (51 Stars) verwaltet installierte Plugins aus einem Popup: installieren, aktivieren, deinstallieren, den Marketplace durchsuchen. Standard-Binding ist `prefix+p`.

```bash
herdr plugin install speardragon/herdr-plugin-manager
```

![herdr-plugin-manager-Popup: Liste installierter Plugins mit Aktionen pro Plugin und einem nach Stars sortierten Marketplace-Browser](@assets/images/26/10/herdr-plugin-manager.webp)

Stolperfalle: Popups sind Singleton-Session-Ressourcen. Sie haben keine Pane-ID und keine Lifecycle-Events und liefern `ui_busy`, wenn ein Settings- oder Copy-Mode-Modal offen ist. Das ist Herdr, kein kaputtes Plugin.

Snapshots sind keine Backups. Versioniere deine `config.toml` und den Inhalt von `HERDR_PLUGIN_CONFIG_DIR` jedes Plugins in Git oder mit [Self-Hosted-Backups per Restic](/pluton-self-hosted-backup/). Plugin-Code selbst installiert sich aus gepinnten Refs neu und gehört deshalb nicht in dein Backup-Set.

## Wie du ein Herdr-Plugin in 5 Minuten prüfst

![Prüf-Flussdiagramm für Herdr-Plugins: Repository, Manifest, Befehle, Skripte, Autor-Historie, dann pinnen und installieren, mit Abbruch-Ausgängen an jedem Gate](@assets/images/26/10/herdr-plugin-vetting-flow.webp)

Die Marketplace-Seite selbst sagt: „Einträge werden von Herdr nicht geprüft – die Installation erfolgt auf eigenes Risiko.“ Der interaktive Preview-Dialog ist die einzige Hürde im ganzen System. Hier ist die Checkliste, die ich durchgehe, bevor dieser Dialog überhaupt erscheint.

<Notice type="warning" title="Der Marketplace ist kein Katalog">
  herdr.dev/plugins ist ein automatischer Index. Niemand bei Herdr hat diese Repos gelesen. Fünf Minuten Lesen schlagen eine schlechte Installation, und neu prüfen musst du nur, wenn du den Pin änderst.
</Notice>

1. **Lies `herdr-plugin.toml`.** Jeder `[[build]]`-, `[[startup]]`-, `[[actions]]`-, `[[events]]`- und `[[link_handlers]]`-Eintrag ist Code, der auf deiner Maschine laufen wird. Prüfe die Pflichtfelder (`id`, `name`, `version`, `min_herdr_version`) und lies jedes `command`-Array, bevor du dir irgendetwas anderes ansiehst.
2. **Lies jeden Befehl als argv.** Es gibt keine Shell-Expansion, außer der Befehl startet eine Shell. Quoting-Überraschungen verstecken sich in `["bash", "-c", "..."]`-Wrappern, nicht in `["node", "index.js"]`.
3. **Überfliege die Skripte.** Alles, was `~/.aws`, `~/.ssh`, `.env`-Dateien oder Agent-Credential-Verzeichnisse anfasst, verdient ein volles Lesen, nicht ein Überfliegen. Das ist der Unterschied zwischen einem UI-Plugin und etwas, das deine Tokens exfiltrieren kann.
4. **Prüfe Autor und Repo-Historie.** Stars sind kein Vertrauen, und ein Topic-Tag ist keine Garantie, dass sich das Ding überhaupt als Herdr-Plugin installieren lässt. Frische Accounts plus obfuskierte Build-Schritte sind ein klarer Grund, Abstand zu halten. Wenn du einen sanften ersten Prüflauf willst: `qu8n/herdr-automatic-rename` und `tdi/herdr-worktree-setup` sind klein und end-to-end lesbar.
5. **Pinne den geprüften Tag.** `herdr plugin install owner/repo --ref vX.Y.Z`. Niemals `--yes` bei der ersten Installation. Wenn sich das Manifest nach der Vorschau ändert, bricht Herdr ab; lass es abgebrochen und lies nochmal nach.

<ListCheck>
  <ul>
    <li>herdr-plugin.toml lesen, inklusive jedes [[startup]]- und [[build]]-Befehls</li>
    <li>Befehle als argv-Arrays lesen; Shell-Wrappern misstrauen</li>
    <li>Skripte überfliegen, mit voller Aufmerksamkeit auf Credential-Pfaden</li>
    <li>Autor-Historie prüfen; Abstand halten bei frischen Accounts mit obfuskierten Builds</li>
    <li>Den geprüften Tag pinnen; niemals blind mit --yes installieren</li>
  </ul>
</ListCheck>

Kostennotiz: Prüfen kostet 5 Minuten einmal pro Plugin. Neuinstallieren aus einem gepinnten Ref ist der Update-Pfad, und neu prüfen heißt nur das Delta zwischen altem und neuem Tag. Für Remote-Relay-Plugins konkret ist das Threat Model dein ganzes Terminal. Wenn du überhaupt einen Server ins Netz stellst: Lies zuerst [Einen exponierten Server härten](/bsi-security-report-docker-ufw/), bevor du ein Relay freigibst.

## Herdr-Plugins vs. tmux: was anders ist

Die Frage „Herdr vs. tmux“ läuft mehr über Plugins als über Panes. Wenn du nur Panes und Scrollback willst, ist tmux immer noch gut – und wird es in fünf Jahren auch sein.

| Fähigkeit | tmux | Herdr-Plugins |
|---|---|---|
| Plugin-Verteilung | Shell-Skripte ins `.tmux.conf`-Umfeld kopieren | `herdr plugin install owner/repo` aus einem Marketplace-Index |
| Plugin-Definition | Ad-hoc-Shell-Funktionen | `herdr-plugin.toml`-Manifest mit build/startup/actions/events/panes |
| API-Oberfläche | tmux-Befehle | Die komplette herdr-CLI via `HERDR_BIN_PATH` |
| Events | Hooks, die du selbst verdrahtest | Deklarative `[[events]]` wie `on = "worktree.created"` |
| URL-Handling | Manuell | `[[link_handlers]]` mit Rust-Regex, Ctrl-Klick-Dispatch |
| Sandboxing | Keins | Keins |
| Update-Kanal | Was immer das README des Plugins sagt | Keiner in v1, Neuinstallation zum Aktualisieren |
| Review-Prozess | Keiner | Keiner – es ist ein automatischer Index |

Was Herdr dir gibt: manifest-deklarierte argv-Befehle, Events, Pane-Platzierung, Link-Handler und Keybinding-Integration in `~/.config/herdr/config.toml`. Was es dir nicht gibt: Sandboxing, verwalteten Storage (dauerhafter State sind die eigenen Dateien des Plugins), einen Update-Kanal oder irgendeinen Review-Prozess. tmux' Plugin-Szene ist kleiner und simpler – und das ist zugleich ihre Sicherheitsstory.

Mein Urteil: Das Plugin-Ökosystem ist der Grund zu wechseln, wenn du Agent-CLIs nutzt, nicht der Multiplexer-Teil. tmux multiplext schon. Herdrs Vorsprung ist, dass Agent-Workflows wie Diff-Review, Session-Graphen und Workspace-Bootstrap einen Befehl entfernt sind statt ein Wochenende Skripte. Wenn dein tmux-Setup ohnehin ein Haufen Custom-Shell ist und du täglich Agents darin betreibst, ist die Migration ein Wochenende wert. Wenn du meist zwei Shells und einen Log-Tail laufen lässt, hat tmux weniger bewegliche Teile und nichts zu prüfen. Für den Runtime-Vergleich selbst: [unser Herdr-Review (Open-Source-Agent-Multiplexer)](/de/herdr-agent-multiplexer/), das die tmux-Frage in der Tiefe behandelt. Und wenn das, was du eigentlich suchst, der Multiplexer selbst ist statt der Agent-Schicht, ist [Superlogical Rex](/de/superlogical-rex/) die neue Terminal-seitige Option, die man verfolgen sollte.

## Stolperfallen, die dir niemand sagt

Das sind die Dinge, die dich im ersten Monat beißen werden.

1. **Kein `plugin update`-Befehl.** Updates heißen, `herdr plugin install` erneut auszuführen – das ersetzt den verwalteten Checkout. Alles in `HERDR_PLUGIN_ROOT` ist weg. Halte Secrets und Einstellungen in `HERDR_PLUGIN_CONFIG_DIR`, und du kannst beliebig neu installieren.
2. **Namenskollisionen sind real.** Es gibt zwei `herdr-auto-title`-Repos (kryptamine 238 Stars vs. sh1ma 51 Stars), zwei `herdr-agent-usage`-Repos (levi-qiao 168 Stars vs. senna-lang 47 Stars) und mindestens drei browser-artige Plugins (`ogulcancelik/herdr-browser` 357 Stars, StructuPath 23 Stars, plus `zenbu-labs/terminal-browser`). Fix: immer vollqualifiziertes `plugin.id.action` verwenden und notieren, welches `owner/repo` du installiert hast.
3. **Fehlende Lizenzen.** `herdr-remote` und `herdr-mobile-relay` zeigen beide NOASSERTION. `pi-extensible-workflows` hat gar kein Lizenzfeld. Baue auf diesen nichts, wofür du bezahlt wirst, ohne eine Lizenz, mit der du leben kannst.
4. **`ui_busy` bei Popups.** Popups sind Singleton-Session-Ressourcen ohne Pane-ID und ohne Pane-Events. Ein Settings- oder Copy-Mode-Modal blockiert sie. Wenn das Popup eines Plugins „nichts tut“, schließe zuerst deine Modals.
5. **Keybinding-Kollisionen.** `[[keys.command]]`-Einträge können die eingebaute Keymap überschatten. Wähle unbenutzte Keys und führe `herdr server reload-config` nach jeder Änderung aus – sonst ändert sich nichts und du gibst dem Plugin die Schuld.
6. **Startup-Hooks sind keine Daemons.** `[[startup]]` ist einmalige Initialisierung, die bei Live-Handoff erneut läuft. Ein Plugin, das sie als Supervisor missbraucht, wird sich danebenbenehmen. Wenn du eins schreibst, mach den Hook idempotent.
7. **Build-Fehler brechen die Installation ab**, mit gekürztem stdout und stderr. Fast immer eine fehlende Toolchain. Installiere `cargo`/`npm`/`go`, versuch es erneut und lies das gekürzte Log.
8. **0.7.x-API-Fluktuation.** Dieses Ökosystem ist Monate alt. Pinne Refs, erwarte `min_herdr_version`-Bumps und behandle jede Neuinstallation als Gelegenheit, das Manifest-Diff nochmal zu lesen.

<Notice type="warning" title="Star-Zahl ist kein Vertrauen">
  Beliebte Plugins kommen trotzdem mit Namenskollisionen, NOASSERTION-Lizenzen und Popup-Eigenheiten. Stars sagen dir, was andere installiert haben, nicht, was sicher in deiner Umgebung läuft. Paare sie mit dem 5-Minuten-Check und gepinnten Refs – und rechne damit, dass sich die 0.7.x-API unter deinen Händen ändert.
</Notice>

## Ein eigenes Plugin in 20 Zeilen schreiben

Das meiste, was Plugins tun, ist: einen Befehl ausführen, ein Pane zeigen, die herdr-CLI zurückrufen. Hier ein minimales Manifest.

```toml
# herdr-plugin.toml
id = "example.workspace-tools"
name = "Workspace Tools"
version = "0.1.0"
min_herdr_version = "0.7.0"
platforms = ["linux", "macos", "windows"]

[[actions]]
id = "list-workspaces"
title = "List workspaces"
contexts = ["workspace"]
command = ["node", "index.js"]
```

Und das Callback-Muster. Die ganze CLI ist die API:

```javascript
// index.js
const { spawnSync } = require("node:child_process");
const herdr = process.env.HERDR_BIN_PATH ?? "herdr";

const res = spawnSync(herdr, ["workspace", "list"], { encoding: "utf8" });
console.log(res.stdout);
```

Lokale Entwicklungsschleife:

```bash
herdr plugin link /abs/path/to/plugin   # Registrieren, Build-Befehle laufen nicht
herdr plugin action invoke example.workspace-tools.list-workspaces
herdr plugin log list --plugin example.workspace-tools --limit 20
herdr plugin unlink example.workspace-tools
```

Wohin State gehört: `HERDR_PLUGIN_CONFIG_DIR` für Einstellungen und Secrets, `HERDR_PLUGIN_STATE_DIR` für dauerhaften State. Es gibt keine verwaltete Storage-API in v1, das Plugin schreibt also eigene Dateien. Und schreibe niemals in `HERDR_PLUGIN_ROOT`; eine Neuinstallation ersetzt es.

Plugins vs. Skills, weil die Leute sie verwechseln: Plugins erweitern die Terminal-Runtime (Panes, Events, Keybindings). Skills erweitern den Kontext des Agents (Anweisungen, die das Modell lädt). Andere Ebene, andere Datei, anderes Problem. Wenn das Problem „der Agent weiß nicht, wie man X macht“ ist, ist das ein Skill, und [Agent-Skills im Vergleich](/de/beste-ai-skills-webdesign/) ist die richtige Lektüre.

Herdrs Docs nutzen dieses Cookbook für Installationsbeispiele – mit dem Vorbehalt, dass Herdr diese Plugins nicht pflegt. Behandle sie als lesbare Beispiele, nicht als offiziell abgesegneten Code.

## FAQ: Herdr-Plugins

<Accordion label="Sind Herdr-Plugins sicher zu installieren?" group="faq" expanded="true">
  Es ist ungeprüfter Code, der als dein User läuft. Herdr validiert das Manifest und nutzt keine Sandbox. Die Gegenmaßnahme ist die 5-Minuten-Prüf-Checkliste (Manifest, Befehle, Skripte, Autor-Historie) plus Installieren mit dem Preview-Dialog und Pinnen des geprüften Tags. Gib niemals `--yes` bei der ersten Installation an. Wenn du das befolgst, ist das Restrisiko normales Open-Source-Risiko statt Blindvertrauen.
</Accordion>

<Accordion label="Wie aktualisiere ich Herdr-Plugins?" group="faq">
  Es gibt kein `herdr plugin update` in Plugin v1. Führe `herdr plugin install owner/repo` erneut aus (optional mit neuem `--ref`), und Herdr ersetzt den verwalteten Checkout. Halte Einstellungen und Secrets in `HERDR_PLUGIN_CONFIG_DIR`, niemals in `HERDR_PLUGIN_ROOT`, und Neuinstallationen werden schmerzlos. Prüfe das Diff neu, wenn du den Pin änderst.
</Accordion>

<Accordion label="Wie viele Plugins gibt es im Herdr-Plugin-Marketplace?" group="faq">
  Rund 1.000+ indexierte Plugins auf herdr.dev/plugins, gegenüber etwa 1.500 Repositories mit Tag `herdr-plugin` auf GitHub (Topic-Zahl, 2026-10-08). Die rohe Topic-Zahl enthält Dotfiles und mitgetaggte Tools; der kuratierte Index zeigt nur Repos mit parsebaren Manifesten. Beide Zahlen bewegen sich schnell in einem sieben Monate alten Ökosystem – prüfe den Live-Index, wenn du das liest.
</Accordion>

<Accordion label="Funktionieren Herdr-Plugins mit Claude Code, Codex und OpenCode?" group="faq">
  Ja. Plugins steuern, was immer im Pane läuft, und die herdr-CLI ist die API – Agent-Integration ist also kein Sondermodus. Die Top-Picks in diesem Artikel unterstützen explizit Claude Code, Codex, OpenCode und Pi: herdr-reviewr schickt Zeilenkommentare an alle vier, zoetrope stellt Claude-Code- und Codex-Sessions grafisch dar, und collie steuert sie vom Handy. Wenn ein Plugin in seinem README nur einen Agent nennt, ist das meist eine Doku-Entscheidung; entscheidend ist, ob es das Pane und das Transcript liest – und das sagen dir die Manifest-Befehle.
</Accordion>
