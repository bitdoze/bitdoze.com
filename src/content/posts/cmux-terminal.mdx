## What cmux actually is

![cmux terminal UI with vertical workspaces, agent panes, and notification badges](../../assets/images/26/03/cmux-ui.webp)

cmux is **not** a Ghostty fork. It uses `libghostty` for terminal rendering the same way an app might use WebKit for web content, so you get Ghostty-style rendering and config compatibility inside a different app. It is built with Swift and AppKit, and it reads `~/.config/ghostty/config` for themes, fonts, and colors, so an existing Ghostty setup carries over. My [Ghostty Terminal setup guide](/ghostty-terminal/) covers that config file in detail.

The idea is simple:

- Open several coding agents in parallel
- Keep them separated by workspace, pane, or browser surface
- Get a clear visual signal when one needs input
- Automate the terminal and browser from scripts or hooks

That maps onto a small object model: **Window → Workspace → Pane → Surface**. More on that below, because it is the part that makes multi-agent work bearable.

One licensing note before you get excited about self-hosting anything: the core app is **GPL-3.0-or-later**, but some server-side pieces (`web/`, the `workers/` directories, `cmux-tui/relays/cloudflare-do/`) are **BUSL-1.1** and need a commercial license from Manaflow for production use, including self-hosting. For the local macOS workflow in this guide it does not matter. The [LICENSE](https://github.com/manaflow-ai/cmux/blob/main/LICENSE) has the exact split.

## What the cmux terminal can do

### Run multiple AI coding agents without losing track

cmux uses four layers so work stays separated. The window is the app window. A workspace is the main vertical tab in the sidebar. A pane is a split area inside a workspace. A surface is the actual terminal or browser tab inside a pane.

![cmux hierarchy diagram: window, workspace, pane, and surface layers](../../assets/images/26/03/cmux-hierarchy.svg)

That model sounds heavier than a normal terminal at first. In practice it is how cmux shows multiple agents, multiple splits, and browser tabs without collapsing into a pile of tabs. Workspace groups keep related projects together, and global session search (⌘⌥F) finds open Claude Code or Codex sessions by the text of their conversations.

### Know which agent needs attention

This is where cmux gets the details right.

Instead of a generic desktop alert, cmux can show:

- a notification ring around the pane
- an unread badge on the workspace
- a notification panel with pending items
- a desktop notification on macOS

It supports standard terminal notification escape sequences (OSC 9, OSC 99, OSC 777) and it exposes `cmux notify` for scripts and hooks.

![cmux notification flow diagram: hooks and OSC escapes to rings, badges, panel, and desktop alerts](../../assets/images/26/03/cmux-notify-flow.svg)

Newer builds add OSC 7501 program status: a program reports idle, working, blocked, done, or error, and cmux shows it as a sidebar pill and on the `cmux-events` stream. Try it from any cmux terminal:

```bash
printf '\e]7501;state=working\e\\'
```

That means you can wire Claude Code, Codex, OpenCode, or your own shell scripts into the same notification flow. If you use Codex, see how to [run the Codex app with any model](/codex-app-any-model/). For OpenCode users, my [OpenCode vs Pi agent comparison](/opencode-vs-pi-agent/) helps pick which agent to put in the pane.

### Automate the built-in browser from the CLI

The browser surface is what separates cmux from Ghostty and tmux. A browser surface sits beside the terminal in the same pane, and you drive it from the command line:

```bash
cmux browser open https://localhost:4321
cmux browser snapshot --interactive
cmux browser fill "#email" --text "me@example.com"
cmux browser click "button[type='submit']" --snapshot-after
cmux browser wait --text "Welcome" --timeout-ms 10000
```

Note the `--text` flag on `fill` (the positional form still works, but the docs use flags) and `--snapshot-after` on `click`. The snapshot-after flag is the verification step: it dumps the page state after the action so you can see what actually happened. When something breaks:

```bash
cmux browser console list
cmux browser screenshot --out /tmp/cmux-failure.png
```

The browser surface also imports cookies, history, and sessions from Chrome, Firefox, Arc, and 20+ other browsers, so panes start authenticated instead of logged out. The automation surface (wait, eval, get, find, console, screenshot, dialog handling, tab management) was ported from `vercel-labs/agent-browser`. If you are building web apps with an agent, this is pretty compelling. The browser stops being a separate thing you alt-tab to.

### Control everything from the cmux CLI

The CLI plus a Unix socket is a programmable control plane for the app. This is the "Zen of cmux" framing: primitives, not a prescriptive workflow.

You can create workspaces and windows, split panes, create terminal or browser surfaces, send text or keys into a terminal, read visible screen or scrollback, move and reorder tabs, and set sidebar status, progress, and logs. Two things worth knowing:

- cmux sets `CMUX_WORKSPACE_ID` and `CMUX_SURFACE_ID` in every terminal it opens, so scripts know where they live
- `~/.config/cmux/cmux.json` controls cmux itself (sidebar, tabs, splits, custom commands) and applies live without a restart; `~/.config/ghostty/config` still controls terminal rendering

```bash
cmux set-status build "compiling" --icon hammer --color "#ff9500" --priority 80
cmux set-progress 0.5 --label "Building..."
cmux log --level success -- "All 42 tests passed"
```

<Notice type="info" title="Socket access modes">
The control socket lives at `/tmp/cmux.sock` (release) and its default access mode is **cmux processes only**. Scripts outside cmux terminals cannot connect unless you set `CMUX_SOCKET_MODE=allowAll` in the environment. See "Common setup problems and fixes" for the full failure-mode table.
</Notice>

## Essential cmux commands to know first

The full help is broad. These are the commands I would learn first.

| Task | Command |
|------|---------|
| Open a new workspace | `cmux new-workspace` |
| Split the current layout | `cmux new-split right` or `cmux new-split down` |
| Add a new terminal/browser surface | `cmux new-surface --type terminal` or `cmux new-surface --type browser` |
| Inspect the current layout | `cmux tree --all` |
| Send input to a terminal | `cmux send "npm run dev"` |
| Read terminal output | `cmux read-screen --scrollback --lines 200` |
| Fire a notification | `cmux notify --title "Build Complete" --body "All tests passed"` |
| Open a browser page | `cmux browser open https://localhost:4321` |
| Snapshot the browser state | `cmux browser snapshot --interactive` |
| Set up agent hooks and resume | `cmux hooks setup` |
| Open a remote workspace over SSH | `cmux ssh user@remote` |
| List/attach remote tmux sessions (beta) | `cmux ssh-tmux user@remote list` |
| Show resume state for a surface | `cmux surface resume show` |
| List socket methods and access mode | `cmux capabilities --json` |

Two details to keep scripts clean: `cmux tree` is an alias of `surface ls`, and `cmux new-surface` is a legacy facade. In new scripts prefer the `surface` command group.

```bash
# Keep the app current
brew upgrade --cask cmux

# One-shot agent hook setup (run after installing agent CLIs)
cmux hooks setup
cmux hooks setup codex      # or per-agent
```

If you are comfortable with terminal scripting, `send`, `send-key`, `read-screen`, `notify`, and `browser snapshot` are where cmux gets interesting fast.

## cmux vs tmux vs Ghostty

The cmux vs tmux question is really about where you work, and the cmux vs ghostty question is about what you want the terminal to own. Here is the practical split.

| Tool | Best for | What it does well | What to watch for |
|------|----------|-------------------|-------------------|
| **Ghostty** | Fast everyday terminal use | Native feel, GPU rendering, simple config, built-in multiplexing | Less opinionated around agent workflows |
| **tmux** | Portable sessions and remote work | Detach/attach on any OS, SSH-friendly, huge ecosystem | More setup, more keybindings, no built-in browser or GUI notifications |
| **cmux** | Local multi-agent development on macOS | Workspaces, pane notifications, browser automation, CLI control, agent session resume | macOS-only terminal app; arbitrary process state is not checkpointed; remote tmux attach is beta |

My take: if you mostly want a better terminal, start with the [Ghostty Terminal setup guide](/ghostty-terminal/). If you live on remote servers and want detach/attach from any OS, tmux still earns its keep, and my [tmux basics for beginners](/tmux-basics/) post covers that workflow. If your day is turning into "three Claude sessions, one Codex session, a dev server, and a browser you want to script," cmux starts to make a lot of sense.

One platform note: tmux runs everywhere and my [WezTerm Mac setup guide](/install-wezterm-mac/) covers a cross-platform GPU terminal, while the cmux terminal app is macOS 14+ only. Two more angles on the multiplexer problem: the [Rex terminal multiplexer](/superlogical-rex/) is Ghostty creator Mitchell Hashimoto's own take, and my [terminal multiplexer comparison for 2026](/best-terminal-multiplexers/) covers the wider field.

### Install the app (Homebrew or DMG)

<Tabs>
<Tab name="Homebrew">
```bash
brew tap manaflow-ai/cmux
brew install --cask cmux
```

Later, update with `brew upgrade --cask cmux`. Shell completions for zsh, bash, and fish ship with the cask.
</Tab>
<Tab name="DMG">
Download the DMG from [cmux.com](https://cmux.com/), drag it into Applications, and let it auto-update via Sparkle. If your shell does not pick up completions, run `eval "$(cmux completion zsh)"` (or the bash/fish equivalent) from your shell config.
</Tab>
</Tabs>

<Notice type="warning" title="Gatekeeper on first launch">
macOS may warn that the app is from an unidentified developer. The README says to click Open. Download from cmux.com or the Homebrew tap only.
</Notice>

### Add the cmux CLI to your PATH

Inside cmux terminals the CLI works automatically because cmux sets `CMUX_WORKSPACE_ID` and `CMUX_SURFACE_ID` for you. For use outside the app, there are two ways to link it.

<Tabs>
<Tab name="Command palette (recommended)">
Open the command palette (⌘⇧P) inside cmux and run **"Shell Command: Install 'cmux' in PATH"**. It links into `/usr/local/bin` and prompts for an admin password if needed.
</Tab>
<Tab name="Manual symlink (fallback)">
```bash
sudo ln -sf "/Applications/cmux.app/Contents/Resources/bin/cmux" /usr/local/bin/cmux
```
</Tab>
</Tabs>

After either method, these should work from any shell:

```bash
cmux list-workspaces
cmux current-workspace
cmux notify --title "Build Complete" --body "Your build finished"
```

### Verify your install

Do this before wiring anything else. It takes 30 seconds and catches most setup problems early.

<ListCheck>
<ul>
<li><code>cmux ping</code> returns without error, so the app is running and the socket responds</li>
<li><code>cmux identify</code> shows the focused window, workspace, pane, and surface</li>
<li><code>cmux list-workspaces --json</code> prints structured output</li>
<li><code>cmux capabilities --json</code> lists the socket methods and the current access mode</li>
<li>Visual check: sidebar on the left, one workspace open, Ghostty-powered terminal ready</li>
</ul>
</ListCheck>

If `cmux ping` fails, the app is not running or the CLI is not on PATH. If it returns an access error, read the next section.

### Common setup problems and fixes

<Notice type="warning" title="The #1 support question: socket access mode">
If `cmux` commands work inside cmux terminals but fail from your own shell or scripts, the socket access mode is the cause, not your script.
</Notice>

| Problem | What is going on | Fix |
|---------|------------------|-----|
| CLI works inside cmux, fails outside | Socket `/tmp/cmux.sock` defaults to `cmuxOnly` access | Run scripts from a cmux terminal, or set `CMUX_SOCKET_MODE=allowAll` in the environment (env-only). Keep `off` or `cmuxOnly` on shared machines. Related vars: `CMUX_SOCKET_PATH`, `CMUX_SOCKET_ENABLE` |
| Socket script broke after an update | JSON protocol changed; legacy `{"command": "..."}` payloads are rejected | Send `{"id", "method", "params"}` shaped requests |
| macOS says "app from an unidentified developer" | Gatekeeper on first launch | Click Open, and only install from cmux.com or the Homebrew tap |
| `cmux hooks setup` did nothing | It ran before the agent CLI was installed, so nothing was on PATH | Install the agent first, then re-run `cmux hooks setup` |
| Something behaves oddly after an update | Nightly builds ship fast; version drift is real | Check `cmux version` against the official changelog |

## Session restore and agent resume

This is the biggest behavioral change since I first wrote about cmux in March 2026, and it fixes the old "restart loses your work" caveat.

On relaunch, cmux restores layout, metadata, scrollback, and browser history. For supported agents it goes further: hooks capture native resume tokens, so agent sessions come back where you left them. The docs list 15+ agents with resume support, including Claude Code (`claude --resume <id>`), Codex, OpenCode, Gemini, Amp, Cursor CLI, Copilot, Pi, and more. The [Session Restore docs](https://cmux.com/docs/session-restore) keep the current matrix.

```bash
cmux hooks setup                # install all agent integrations found on PATH
cmux surface resume show        # inspect resume state for the current surface
cmux restore-session            # restore a previous session
```

If you want the old behavior, opt out in `~/.config/cmux/cmux.json`:

```json
{
  "terminal": {
    "autoResumeAgentSessions": false
  }
}
```

<Notice type="info" title="Resume security">
Sensitive environment keys (tokens, passwords, API keys) are stripped before a resume binding is stored, and only "trusted" bindings auto-run on restore. Worth knowing before you point this at a machine with production credentials in env vars.
</Notice>

Two limits to keep in mind. First, cmux does not checkpoint arbitrary process memory: tmux, vim, and plain shells reopen as normal terminals. Second, the homepage claims state survives a full computer restart; the docs word it more conservatively (restore on relaunch, agent resume when hooks captured a token). I would trust the docs wording until you have verified a full reboot yourself.

## Example workflow: Claude Code + browser + notifications

Here is the kind of setup cmux seems designed for. Keep the layout boring:

<ListCheck>
<ul>
<li>One workspace for the main coding agent</li>
<li>One split for logs or tests</li>
<li>One browser surface for the app you are building</li>
<li>Notifications wired into agent hooks</li>
</ul>
</ListCheck>

**Wire the hooks first.** You used to hand-write a Claude Code hook script that called `cmux notify` on stop events. Now one command does it, after the agent CLI is installed so its binary is on PATH:

```bash
cmux hooks setup
```

**Then script the loop** when you want it repeatable:

```bash
# Workspace for the project
cmux new-workspace --cwd ~/projects/my-app

# Split for logs
cmux new-split down

# Open the app in a browser surface
cmux browser open https://localhost:4321
cmux browser fill "#email" --text "me@example.com"
cmux browser click "button[type='submit']" --snapshot-after
cmux browser wait --text "Welcome" --timeout-ms 10000

# Notify yourself when the task is done
cmux notify --title "Claude Code" --body "Agent finished the refactor"
```

The `--snapshot-after` and `wait` steps are the verify part of the loop: if `wait` times out, something broke. Grab evidence before you debug:

```bash
cmux browser console list
cmux browser screenshot --out /tmp/cmux-failure.png
```

That is a small amount of wiring, but it is exactly the sort of thing that turns an app from "interesting demo" into "actually useful on a Tuesday." If you want a cleaner prompt inside those terminals, the [Starship + Ghostty terminal guide](/starship-ghostty-terminal/) is a good companion.

## What I like about cmux

It does not try to hide the terminal. A lot of agent tools rush to build a whole new environment around the LLM. cmux still feels like a terminal person made it.

The browser being part of the same workspace is a bigger deal than it looks on paper. When terminal, browser, and notifications all live together, the workflow feels tighter.

The project is honest about being a set of primitives. The [Zen of cmux](https://cmux.com/blog/zen-of-cmux) post says it directly: cmux is not prescriptive, and the workflow is yours to shape. I like that framing, and after a year of "AI operating system" pitches it still reads as the right call.

## What to keep in mind before switching

cmux is promising, but it is not magic.

- The terminal app is **macOS-only** (macOS 14+). The iOS companion is Pro-gated beta, and Linux exists only as paid Cloud VMs.
- Agent sessions resume via hooks; **arbitrary process state is still not checkpointed**. tmux, vim, and plain shells reopen as normal terminals.
- Remote tmux attach (`cmux ssh-tmux`) is **beta**. For portable detach/attach on any OS, tmux on the remote host is still the simpler tool.
- Server-side pieces are **BUSL-1.1**. Fine for local use, matters if you plan to self-host the infra.
- The project moves fast with ~7k open issues. Test upgrades before you depend on a specific behavior.
- If you do not need browser automation or agent notifications, **Ghostty alone may be enough**.

None of that is a knock against cmux. It means you should use it for the job it is clearly trying to solve.
