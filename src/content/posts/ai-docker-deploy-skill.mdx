I got tired of SSH-ing into my VPS every time I wanted to try a new Docker app. Install this, write a compose file, add the Caddy config, restart, check if it works. The same steps every single time.

So I built a docker-deploy skill that lets my AI assistant deploy Docker apps on my VPS from one message. I open Telegram (or Discord, or Slack), type something like "install Plausible Analytics on my server," and the assistant creates the folder, writes the compose file, updates Caddy for HTTPS, starts everything, and checks if the app responds. I don't touch the terminal at all.

This article walks through the setup that makes this work and gives you the skill file you can drop into your own AI assistant. It covers the VPS, Docker, Caddy, wildcard DNS, the directory convention, the skill itself, and the guardrails that keep a chat-operated agent from wrecking the server.

Commands in this guide work with Docker Engine 29.x and Docker Compose v5.x (checked October 2026). Before moving on:

```sh

```

If `docker compose version` errors out, the install didn't finish. If `sudo docker ps` complains about the daemon, run `sudo systemctl enable --now docker`.

## Set up Caddy as your reverse proxy

Caddy handles HTTPS automatically. No certbot, no renewal crons, no nginx config files. It gets certificates from Let's Encrypt on its own and renews them before they expire.

I run Caddy as a Docker container inside the same directory structure where all my apps live. The `caddy:2-alpine` tag is still the right one (the 2.11.x line; 2.11.7 was current as of October 2026). Nothing in the config below changed across those releases.

### Create the directory structure

```sh
mkdir -p /home/$USER/docker-apps/caddy
cd /home/$USER/docker-apps/caddy
```

### Docker Compose for Caddy

Create a `docker-compose.yml` in the caddy directory:

```yaml
services:
  caddy:
    image: caddy:2-alpine
    container_name: caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
      - "443:443/udp"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile
      - ./data:/data
      - ./config:/config
    networks:
      - caddy

networks:
  caddy:
    external: true
```

### Create the Docker network

All your apps will connect to this shared network so Caddy can reach them:

```sh
sudo docker network create caddy
```

### Create the Caddyfile

Create a `Caddyfile` in the same folder. Start with a placeholder:

```
# Apps will be added here by the AI assistant or manually
```

### Start Caddy

```sh
cd /home/$USER/docker-apps/caddy
sudo docker compose up -d
```

Verify before you touch DNS:

```sh
sudo docker compose ps           # caddy should show running
sudo docker logs caddy --tail 20
```

If the container restarts in a loop, the Caddyfile is the usual suspect. Fix the file and run `sudo docker compose up -d` again. Any app you add later just needs an entry in this Caddyfile and a connection to the `caddy` network.

<Notice type="info" title="Validate before every reload">
Run `sudo docker exec caddy caddy validate --config /etc/caddy/Caddyfile` before reloading Caddy. A syntax error in that file takes down every site you host, not just the new app. This rule also lives in the skill file below.
</Notice>

## Set up wildcard DNS

You need a DNS record that sends all subdomains to your server. In your domain registrar or DNS provider (Cloudflare, etc.), add an A record:

| Type | Name | Value | TTL |
|------|------|-------|-----|
| A | `*` | `YOUR_SERVER_IP` | Auto |

If your domain is `example.com`, this means `anything.example.com` will resolve to your VPS. Caddy then handles routing each subdomain to the right container.

Check it before you rely on it:

```sh
dig +short anything.yourdomain.com
# must print your VPS IP
```

If certificate issuance fails later, this record is the first thing to check. DNS that has not propagated is the most common reason Let's Encrypt gives up on a new subdomain.

<Notice type="info" title="Cloudflare users">
If you use Cloudflare, you can proxy the wildcard record (orange cloud) but you'll need to configure Caddy to work with Cloudflare's SSL mode. The simplest setup is to use "DNS only" (grey cloud) and let Caddy handle certificates directly.
</Notice>

## The directory convention

Every app gets its own folder under `/home/$USER/docker-apps/`. The structure looks like this after a few apps:

```
/home/user/docker-apps/
  caddy/
    docker-compose.yml
    Caddyfile
    data/
    config/
  plausible/
    docker-compose.yml
    .env
  arcane/
    docker-compose.yml
    .env
  dockhand/
    docker-compose.yml
    .env
```

This keeps everything predictable. The AI assistant knows where to put files, and you know where to find them when you need to look at something manually. That predictability is what lets the skill file stay short and strict: one path to know, one network to join, one place for secrets.

## What the AI assistant does with all this

With the infrastructure in place, you can tell your AI assistant to deploy apps. I've installed [Arcane](/arcane-docker-install/) and [Dockhand](/dockhand-docker-install/) this way. For context on those, I wrote a [comparison of the two](/arcane-vs-dockhand/).

The assistant follows the same workflow every time:

1. Creates a new folder under `/home/user/docker-apps/app-name/`
2. Writes a `docker-compose.yml` with local `./` volume paths (no named volumes)
3. Puts passwords and API keys in a `.env` file, not hardcoded in the compose file
4. Validates the compose file with `docker compose config -q` before starting anything
5. Starts the containers with `sudo docker compose up -d`
6. Updates the Caddyfile in `/home/user/docker-apps/caddy/` with a new subdomain block
7. Validates the Caddyfile with `caddy validate` before reloading Caddy
8. Reloads Caddy to pick up the new config
9. Runs a retrying curl against the subdomain and reports the HTTP status
10. Confirms the stack with `docker compose ps` instead of trusting the exit code of `up -d`

It works because there's a skill file that tells the assistant exactly how this server is set up and what rules to follow. Without the skill, the assistant would guess at paths, might use named volumes, might skip the reverse proxy, or put secrets directly in the compose file.

# Docker + Caddy Server Rules

Apply these rules for all deployment, operations, and setup tasks on this server.

## Environment facts
- Docker is installed and available.
- Caddy is installed and managed from `/home/dragos/docker-apps/caddy`.
- Docker app projects must be placed under `/home/dragos/docker-apps`.
- Wildcard DNS `*.ai.bitdoze.com` points to this server and should be used for app subdomains.

## Permission model
- Use `sudo` for commands that manage Docker runtime/services, networking, filesystem locations requiring elevation, or system-level setup.
- Prefer explicit commands that can be audited and repeated.

## Compose placement and style
- Prefer Docker Compose-based deployments.
- Place each app in its own folder under `/home/dragos/docker-apps/<app-name>`.
- Keep compose and related app files together in the app folder.
- Do not use named volumes for app data/config in compose files.
- Use local relative paths (`./...`) in the location where the compose file is created.
- Pin image tags. Never deploy `latest` unless asked.

## Caddy integration
- Route apps through Caddy using subdomains under `*.ai.bitdoze.com`.
- Keep Caddy config changes under `/home/dragos/docker-apps/caddy`.
- When adding a new app, include the target hostname and upstream container/service mapping.

## Expected workflow
1. Create app directory in `/home/dragos/docker-apps/<app-name>`.
2. Add `docker-compose.yml` with services and `./...` path mappings.
3. Place sensitive data into a `.env` file, not in compose directly (passwords, hashes, API keys).
4. Run `docker compose config -q` in the app folder and fix any errors before `up -d`.
5. Run required Docker/Caddy commands with `sudo`.
6. Add/update Caddy config in `/home/dragos/docker-apps/caddy` for `<app>.ai.bitdoze.com`.
7. Run `sudo docker exec caddy caddy validate --config /etc/caddy/Caddyfile` before any reload. If validation fails, fix the Caddyfile before continuing.
8. Reload Caddy, then validate service health and public routing.
9. Run a retrying curl against the subdomain (up to 10 tries, 5 seconds apart) and report the HTTP status, not just the exit code.
10. Confirm the stack with `docker compose ps` before reporting success.

## Validation
- Run `docker compose config -q` in the app folder before `up -d`.
- Run `sudo docker exec caddy caddy validate --config /etc/caddy/Caddyfile` before any Caddy reload.
- Verify with a retrying curl against the subdomain; report HTTP status, not just exit code.
- Pin image tags; never deploy `latest` unless asked.

## Safety rules
- Never modify files outside `/home/dragos/docker-apps`.
- Never run `curl | bash` from non-official URLs; no firewall, SSH, or systemd changes.
- Ask before touching the `caddy` stack itself; a broken Caddyfile takes down every site.

## Guardrails
- Reject plans that place apps outside `/home/dragos/docker-apps`.
- Reject plans that use named Docker volumes for persistent files.
- Reject plans that bypass Caddy when public HTTP(S) access is required.
- Place sensitive data into `.env` file not in compose directly like passwords and hashes.

## How the skill works in practice

Once the skill file is in place, the assistant reads it whenever you ask about deploying something. Here's what a real conversation looks like:

**Me:** "Install Uptime Kuma on my server"

The assistant then:

```sh
# 1. Creates the directory
sudo mkdir -p /home/dragos/docker-apps/uptime-kuma

# 2. Writes the .env file (passwords go here, not in compose)
# Creates /home/dragos/docker-apps/uptime-kuma/.env

# 3. Writes docker-compose.yml with local paths
# Creates /home/dragos/docker-apps/uptime-kuma/docker-compose.yml

# 4. Validates the compose file before starting anything
cd /home/dragos/docker-apps/uptime-kuma
sudo docker compose config -q
```

The compose file looks something like:

```yaml
services:
  uptime-kuma:
    image: louislam/uptime-kuma:2
    container_name: uptime-kuma
    restart: unless-stopped
    volumes:
      - ./data:/app/data
    networks:
      - caddy

networks:
  caddy:
    external: true
```

Notice `./data` instead of a named volume. That's what the skill enforces. The `:2` tag matters too: Uptime Kuma 2.0.0 went stable in October 2025 and the upstream README recommends `:2` now.

<Notice type="info" title="Deployed :1 earlier in 2026?">
Switching from `louislam/uptime-kuma:1` to `:2` is a major upgrade. Read the 2.x migration notes before you change the tag, and take a backup of `./data` first. If you want to understand the pieces by hand first, the [manual Uptime Kuma install walkthrough](/install-uptime-kuma/) covers it.
</Notice>

Then it updates the Caddyfile:

```
uptime-kuma.ai.bitdoze.com {
    reverse_proxy uptime-kuma:3001
}
```

And starts everything:

```sh
cd /home/dragos/docker-apps/uptime-kuma
sudo docker compose up -d

cd /home/dragos/docker-apps/caddy
sudo docker exec caddy caddy validate --config /etc/caddy/Caddyfile
sudo docker compose exec caddy caddy reload --config /etc/caddy/Caddyfile

# first cert issuance takes a few seconds; retry instead of assuming failure
for i in {1..10}; do
  code=$(curl -s -o /dev/null -w "%{http_code}" https://uptime-kuma.ai.bitdoze.com)
  echo "try $i: HTTP $code"
  [ "$code" = "200" ] && break
  sleep 5
done
```

The whole thing takes maybe 30 seconds. I just watch the messages roll in.

## Verify the deployment and fix common failures

A deploy is not done when `up -d` returns. It is done when the app answers on its subdomain. Check three things:

1. `sudo docker compose ps` in the app folder shows the service running (and healthy if it has a healthcheck).
2. The retrying curl returns 200 and you read the status code yourself.
3. `sudo docker logs caddy --tail 20` is clean: certificate issued, no upstream errors.

When something fails, it is usually one of these:

| Symptom | Cause | Fix |
|---|---|---|
| Cert issuance fails, Caddy keeps retrying | DNS not propagated | `dig +short app.yourdomain.com` must return the VPS IP before you deploy |
| Caddy 502 or 504 | Container on the wrong network | The compose file needs `networks: caddy: external: true` and the service must join the `caddy` network |
| Port already allocated on start | 80/443 taken by another proxy or host service | `ss -tlnp \| grep -E ':80\|:443'` and stop the other listener |
| Every site down after a deploy | Caddyfile syntax error | `sudo docker exec caddy caddy validate --config /etc/caddy/Caddyfile` before every reload |
| `429` or "too many certificates" | Let's Encrypt rate limit from repeated test deploys | Use the LE staging CA while experimenting, switch back for anything real |

<Notice type="warning" title="A broken Caddyfile takes down every site">
The Caddyfile is shared. One syntax error and every app behind Caddy goes dark, not just the new one. `caddy validate` before every reload is the rule that prevents this.
</Notice>

Rollback is the reverse of the deploy:

```sh
cd /home/$USER/docker-apps/uptime-kuma
sudo docker compose down

cd /home/$USER/docker-apps/caddy
# remove the app block from the Caddyfile, then:
sudo docker exec caddy caddy validate --config /etc/caddy/Caddyfile
sudo docker compose exec caddy caddy reload --config /etc/caddy/Caddyfile

cd /home/$USER/docker-apps
# tar the folder if the data matters, then:
rm -rf uptime-kuma
```

And remember that [Docker published ports bypass UFW](/docker-bypasses-firewall/) if you also run a host firewall. That matters more, not less, when an AI is the one publishing ports.

## Why the guardrails matter

Without the skill, AI assistants make reasonable but inconsistent choices. They might:

- Put app data in `/opt/` or `/var/` or wherever they feel like
- Use Docker named volumes, which makes backups harder (you have to dig around in `/var/lib/docker/volumes/`)
- Skip the reverse proxy and expose ports directly
- Hardcode passwords in the compose file where they show up in `docker inspect`
- Forget to check if the app actually started

The guardrails in the skill prevent all of this. If the assistant tries to create a compose file with a named volume, the skill tells it not to. If it tries to expose a port directly without going through Caddy, the skill says no.

Most of the time the difference is consistency. An assistant without the skill can deploy apps. An assistant with the skill deploys them the way you want, every time.

## Security: giving an AI sudo

<Notice type="warning" title="This is root-equivalent access">
Docker access is root access. A chat-operated assistant that can run `sudo docker` can start privileged containers, mount any host path, and read every secret in every `.env` on the box. Treat it like handing out root.
</Notice>

Let me say the uncomfortable part plainly. This setup gives an AI assistant passwordless `sudo` over Docker, and you drive it from Telegram. If someone else can message that bot, they own the server.

If the assistant is OpenClaw, the defaults are not bad. The gateway binds to loopback, unknown DM senders get a pairing code instead of command execution, and group access sits behind an allowlist plus a mention gate. Check your actual config against those defaults:

```sh
openclaw security audit
```

The [full OpenClaw security guide](/openclaw-security-guide/) covers the DM policy, allowlists, and hardened baselines. Beyond the platform defaults, the skill itself carries the safety rules from the `## Safety rules` block above: nothing outside `/home/user/docker-apps`, no `curl | bash` from random URLs, no firewall, SSH, or systemd edits, and ask before touching the `caddy` stack.

If you want heavier isolation than well-written rules for a language model, the real options are:

- Run the agent in a container or sandbox instead of on the host.
- Put a Docker socket proxy (Tecnativa) between the agent and the daemon so it can only touch labeled containers. The [Arcane install](/arcane-docker-install/) already uses that pattern.
- Scope the agent to a single app folder instead of the whole `docker-apps` tree.

Before you let an agent loose on a server you care about:

<ListCheck>
<ul>
<li>Run `openclaw security audit` (or your platform's equivalent) and fix what it flags</li>
<li>Confirm pairing codes and DM allowlists are on, so only you can talk to the bot</li>
<li>Pin the skill's safety rules in the skill file, not in a chat message</li>
<li>Take a backup before the first AI-driven deploy, and keep taking them</li>
</ul>
</ListCheck>

This is not the only layer. Host hardening still matters: see [how I secured my Docker server after the BSI report](/bsi-security-report-docker-ufw/), why [Docker published ports bypass UFW](/docker-bypasses-firewall/), and how to [secure a VPS with CrowdSec](/crowdsec-secure-server/). The skill reduces the blast radius of a normal deploy. It does not make a compromised bot harmless.

## Managing deployed apps

After a few deployments, you'll want to check on things. Some useful commands:

```sh
# See all running containers
sudo docker ps

# Check logs for a specific app
sudo docker logs uptime-kuma --tail 50

# Restart an app
cd /home/$USER/docker-apps/uptime-kuma
sudo docker compose restart

# Update an app to latest image
cd /home/$USER/docker-apps/uptime-kuma

sudo docker compose up -d

# Remove an app completely
cd /home/$USER/docker-apps/uptime-kuma
sudo docker compose down
cd ..
rm -rf uptime-kuma
# Also remove the Caddyfile entry
```

<Notice type="info" title="Backup before destroy">
Before any `down` plus `rm -rf`, tar the app folder including the `.env`: `tar czpf /root/backups/uptime-kuma-$(date +%F).tar.gz uptime-kuma/`. Push it to S3-compatible storage if the data matters. The skill should make the assistant do this automatically. Until it does, do it yourself.
</Notice>

- **A custom [Agno bot](/create-your-own-ai-agent/)** on Discord with shell tools enabled. Same idea, different chat platform. The guide covers installation, Discord integration, memory, and team agents.
- **Claude Code or OpenCode** connected over SSH. The coding-agent route. Claude Code reads the skill from `~/.claude/skills/` and you invoke it with `/docker-deploy`; OpenCode discovers it from `.opencode/skills/`.

The OpenClaw setup is the most hands-off. You message it on Telegram from your phone, and it does everything on the server without you opening a terminal. The [setup guide](/clawdbot-setup-guide/) covers installation. If you want the assistant on hardware at home instead of a rented VPS, the [best Mac mini for OpenClaw](/best-mac-mini-for-openclaw/) covers the local route.

## Extending the skill

The skill file is just markdown. You can add rules as your setup grows. Some things I've added to mine over time:

- A backup section that tells the assistant to create a `backup.sh` script in each app folder. The concrete rule: before `down` or `rm -rf`, tar the app folder plus the `.env` (same rule as in "Managing deployed apps").
- Database defaults (use PostgreSQL over MySQL when the app supports both)
- Resource limits for containers (`deploy.resources.limits` in compose)
- A monitoring rule that adds all new apps to my Uptime Kuma instance automatically

If your skill file does not pin image tags yet, add that line. `latest` is how surprise upgrades happen.

You can also ask the assistant to update the skill itself. "Add a rule that all new apps should include a healthcheck in the compose file" works fine. It reads the skill, adds the rule, and follows it from then on.

**Does the assistant need root access?**

It needs to run Docker commands with `sudo`. If your user is in the `docker` group, you can modify the skill to drop the `sudo` requirement, but I prefer keeping it explicit. Note that `docker` group membership is itself root-equivalent, so the group does not reduce the risk. It only removes four letters from the commands.

**Is it safe to give an AI assistant sudo?**

Not automatically. It is root-equivalent access, so treat it like handing out root. Keep the safety rules in the skill file, use your platform's access controls (OpenClaw's pairing codes, DM allowlists, and `openclaw security audit`), consider a Docker socket proxy or a sandboxed agent, and keep backups. The "Security: giving an AI sudo" section above goes through the details.

**Can I use Nginx or Traefik instead of Caddy?**

Yes, but you'd need to rewrite the Caddy-specific parts of the skill. Caddy is the simplest option because it handles certificates automatically without extra configuration. If you already run [Traefik](/traefik-proxy-docker/), adapt the skill to use labels instead of Caddyfile entries.

**What if the assistant messes something up?**

Every app is isolated in its own folder. If something goes wrong, `docker compose down` in that folder stops it, and removing the folder cleans it up. The worst case is a broken Caddyfile entry, which you fix by editing one file. The "Verify the deployment and fix common failures" section has the full rollback.

**Can multiple assistants share the same skill?**

Yes. The skill describes server conventions, not assistant-specific behavior. Put the same file in each assistant's skill directory and they'll all follow the same rules.

**Does this work on ARM servers (Raspberry Pi)?**

The skill itself is architecture-agnostic. Whether the Docker images you deploy have ARM builds is a separate question. Most popular self-hosted apps publish multi-arch images now. The CAX11 (ARM) from Hetzner runs this stack fine.
