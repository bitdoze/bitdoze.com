Termix self-hosted puts a browser-based SSH manager, file manager, stats dashboard, and remote desktop gateway on your own server. It is an Apache-2.0 licensed project and a free Termius alternative: no external accounts and no paid tier. Since late 2025 it has grown from about 8,500 to over 15,000 GitHub stars, and the 2.x releases turned it from a terminal app into a full server hub. This guide covers the whole setup: deploy with Dokploy or Docker Compose, enable RDP/VNC remote desktop, and lock the deployment down.

## What is Termix?

Termix is a self-hosted SSH and remote desktop management platform. One web interface covers terminal sessions, SSH tunnels, file management, server stats, Docker containers, and browser-based RDP/VNC/Telnet. The project is Apache 2.0 licensed, donate-supported, and the README is explicit: it is a self-hosted alternative to Termius that stays free forever.

### SSH terminal, tunnels, and split screen

The terminal is the core of the app. Tabs, up to six split panels, sessions that survive a page refresh or a container restart, and per-host keepalive. Since 2.6.0 you can save split layouts, and 2.7.0 added workspaces so you can restore a whole set of sessions at once. Terminal session logging is built in if you need an audit trail of what was typed.

The tunnel story also grew up. On top of plain local tunnels with auto reconnect and health checks, 2.2.0 added remote and bridge tunnels with presets, and the desktop app has a dedicated port-forwarding tab since 2.8.0. That covers most cases where you would otherwise reach for an SSH config file full of `-L` and `-R` flags.

### Remote desktop: RDP, VNC, and Telnet in the browser

This is the 2.0.0 headline feature. Termix uses Apache Guacamole's guacd daemon to bring Windows RDP sessions, macOS/Linux VNC screens, and even Telnet gear into the same web UI as your SSH terminals. It is enabled per host, and it needs the guacd sidecar container (or an existing guacd you point to with `GUACD_URL`). The full setup is in the remote desktop section below.

### Docker and Podman management

Since 1.10.0 the Docker view is real container management: start, stop, pause, remove, live stats, and a shell into the container. 2.2.0 added a read-only mode for restricted users, and 2.5.0 added Podman support. The README is honest about scope: it "is not meant to replace Portainer or Dockge". For anything beyond quick ops, I still use [Dockge, a self-hosted Compose stack manager](https://www.bitdoze.com/dockge-install/). Termix Docker view is for "what is running and why is it failing", not for stack editing.

### Automations, fleets, and alerts

This is where the "server hub" pitch became real. Automations (2.7.0) chain triggers and steps: metric thresholds, host up/down events, schedules, or webhooks can fire commands and send notifications through ntfy, Discord, or generic webhooks. Fleets run one command, file push, package update, or inventory query across many hosts at once. Alerts arrived in 2.5.0. For a solo operator with a dozen servers, this replaces a pile of for-loops in bash.

One paragraph on Termix AI, because self-hosters will ask: it is off by default at both the admin and user level, propose-only (it suggests commands and runs them only after you approve, using your account's permissions), has no access to credentials, keys, or settings, and strips secrets before sending anything to the provider. You bring your own API key, and Ollama works for a fully local setup.

## How Termix compares to a tool stack

The honest framing: Termix replaces the daily-driver collection of small tools, not the specialized ones.

| Task | Typical stack | Termix |
| --- | --- | --- |
| SSH access | Terminal app | Built-in web terminal, up to 6 panels |
| File edits | SFTP + editor | Built-in file manager and editor |
| Server stats | Separate monitor | Built-in stats and history graphs |
| Tunnels | CLI or GUI tool | Built-in tunnels with reconnect |
| Docker control | Portainer or CLI | Real container management + Podman (not a Portainer/Dockge replacement) |
| Remote desktop | Apache Guacamole or jump box + VNC client | Built-in RDP/VNC/Telnet in the browser |
| Fleet commands | Ansible or for-loops in bash | Built-in fleets and automations |

Where it fits among the [best self-hosted server panels](https://www.bitdoze.com/best-self-hosted-panels/): panels like Casaos or Cosmos manage the server itself, Termix manages the servers you connect to. Running both is normal, not redundant.

## Accessing private networks: jump hosts, Tailscale, and Cloudflare Tunnel

![Termix private network topology: jump host, Tailscale mesh, and Cloudflare Tunnel paths to a home lab](../../assets/images/25/12/termix-private-network-topology.svg)

If Termix runs on a public VPS but the interesting machines live in a home lab, you have three solid paths:

1. **Jump host**: configure a bastion in **Host Manager** and let Termix hop through it. The bastion is the one host you deliberately expose.
2. **Mesh VPN**: put Termix and your home nodes on the same overlay network. This is now native: Tailscale SSH authentication landed in 2.4.0, Tailscale/WireGuard host integration in 2.5.0, and 2.7.0 added a custom Headscale endpoint, so you can [self-host your own Tailscale control server with Headscale](https://www.bitdoze.com/headscale-self-hosted-tailscale-setup/) and point Termix at it.
3. **Cloudflare Tunnel**: 2.3.0 added SSH over Cloudflare Tunnel. cloudflared makes outbound connections only, so the home firewall stays closed.

One operational rule worth stealing from the project's own docs: run Termix outside the network it manages. If your management plane lives inside the lab and the lab goes down, you lose the tools you need to fix the lab.

For an always-on home node, a low-power box is the right tool; an N150 mini PC idles at 5-8W at the wall, next to nothing against an old desktop. I compared the current picks in [the mini PC home server guide](https://www.bitdoze.com/best-mini-pc-home-server/).

## Deploy Termix with Dokploy

If you already use Dokploy, this is the fastest path: automatic HTTPS, the `dokploy-network` wired up, and one-click redeploy. If you do not have Dokploy yet, start with the [Dokploy install guide](https://www.bitdoze.com/dokploy-install/).

### Step 1: Create the service

1. Open your Dokploy project
2. Click **Add Service** and choose **Compose**
3. Name it `termix`

### Step 2: Paste the compose file

The full walkthrough of service types is in [how to deploy a Docker Compose app in Dokploy](https://www.bitdoze.com/dokploy-docker-compose-app/). Use this compose, which pins the version and adds the guacd sidecar:

```yaml
services:
  termix:
    image: ghcr.io/lukegus/termix:2.8.0
    networks:
      - dokploy-network
    restart: unless-stopped
    environment:
      - PORT=8080
      - ENABLE_TELEMETRY=false   # optional, locks telemetry off
    volumes:
      - termix-data:/app/data
    depends_on:
      - guacd

  guacd:
    image: guacamole/guacd:1.6.0
    restart: unless-stopped
    networks:
      - dokploy-network
    # no ports: keep 4822 internal

networks:
  dokploy-network:
    external: true

volumes:
  termix-data:
```

<Notice type="info" title="Compose notes">
- `termix-data` stores the database, encryption keys, SSL certs, and session recordings. Keep it on local disk for performance and back it up.
- The pinned `2.8.0` tag beats `:latest` for an internet-facing credential vault. Patch releases (2.6.1, 2.7.1) arrive as separate tags.
- Dokploy maps your domain to port 8080 and terminates HTTPS for you, so neither container publishes a port directly.
</Notice>

### Step 3: Domain and port

Create a domain in Dokploy and map it to port **8080**. Deploy, then open `https://your-domain.com` and complete the first-run setup (create the admin account; the onboarding flow was reworked in 2.7.0, so it may differ from older screenshots).

### Step 4: Verify

- In Dokploy, both services show **Running**: `termix` and `guacd`
- Open the domain, log in, and confirm the version under **Admin Settings**
- If remote desktop errors later with "guacd unreachable", the fix is usually name resolution across the shared network: set `GUACD_URL=tcp://guacd:4822` explicitly on the termix service

## Deploy Termix with Docker Compose (standalone)

No Dokploy? Plain Compose works the same. This mirrors the official docs compose, with the version pinned and guacd kept internal:

```yaml
services:
  termix:
    image: ghcr.io/lukegus/termix:2.8.0
    container_name: termix
    restart: unless-stopped
    ports:
      - "8080:8080"
    environment:
      PORT: "8080"
      # ENABLE_TELEMETRY: "false"
    volumes:
      - termix-data:/app/data
    depends_on:
      - guacd
    networks:
      - termix-net

  guacd:
    image: guacamole/guacd:1.6.0
    container_name: guacd
    restart: unless-stopped
    networks:
      - termix-net
    # no ports: keep 4822 internal

volumes:
  termix-data:
    driver: local

networks:
  termix-net:
    driver: bridge
```

Start and verify:

```bash
docker compose up -d
docker compose ps                       # both containers Up
docker compose logs termix --tail 50    # watch startup/migrations
curl -fsS -o /dev/null -w '%{http_code}\n' http://localhost:8080   # expect 200
```

Then open `http://your-server-ip:8080` and finish the initial setup. After login, check **Admin Settings** for the version and the telemetry toggle.

If you plan to keep 8080 exposed on a LAN-only box, fine. On a public server, do not: put a reverse proxy in front (next section) and firewall the raw port.

Useful environment variables beyond `PORT` (full list in the [Termix docs](https://docs.termix.site/setup/environment-variables)):

| Variable | Example | Purpose |
| --- | --- | --- |
| `PORT` | `"8080"` | HTTP port. App default is 4090; avoid 30001-30005 (reserved) |
| `ENABLE_TELEMETRY` | `"false"` | Locks telemetry off for the instance |
| `DATABASE_DIALECT` / `DATABASE_URL` | `postgres://...` | External PostgreSQL/MySQL/MariaDB (2.7.0+) |
| `DATABASE_SSL` | `"require"` | TLS for an external DB over untrusted networks |
| `GUACD_URL` | `tcp://guacd:4822` | Point at an existing guacd instead of the sidecar (host:port works too) |
| `VITE_BASE_PATH` | `/termix/` | Sub-path deploys (1.11.1+) |

<Notice type="warning" title="Back up your data volume">
Everything lives in `/app/data`: the database, per-user encrypted credentials and keys, SSL certs, and session recordings. Keep the `termix-data` volume backed up like any other critical service, and test the restore. A backup without the encryption keys is a paperweight.
</Notice>

Two failure modes to expect on fresh installs: port 8080 already bound by another stack (change the host side of the mapping), and a stale `termix-data` volume from a pre-2.x install (check the logs for migration errors before assuming the image is broken).

## Enable Termix remote desktop with guacd

Remote desktop arrived in 2.0.0 and is the feature that turns Termix from an SSH tool into a genuine all-in-one. Both compose files above already include the sidecar; this section explains the knobs.

**Enable per host.** In Host Manager, enable the remote desktop feature on the host, then set the protocol and connection details. Protocols and when to use them:

| Protocol | Typical targets |
| --- | --- |
| RDP | Windows machines with Remote Desktop enabled |
| VNC | macOS Screen Sharing, Linux desktops, VM consoles |
| Telnet | Legacy network gear (use only on trusted networks) |

**Capacity.** The official benchmarks add roughly 1 core and 1 GB RAM when guacd is in play. Long RDP sessions are CPU-bound on the guacd container, not on Termix itself.

**Keep guacd private.** Some docs examples publish `4822:4822`. That is a LAN pattern. On a VPS, do not publish 4822; keep both containers on the same compose or Dokploy network and let them talk internally. guacd has no authentication of its own, so anything that can reach 4822 can drive your desktop sessions.

**Point at an existing guacd.** Already running Guacamole? Skip the sidecar and set `GUACD_URL=tcp://your-guacd-host:4822` on the termix service.

Known pain points from the 2026 releases, now fixed: RDP through a jump host works since 2.6.0, and VNC to macOS Screen Sharing stopped showing black screens with the 2.7.0/2.8.0 fixes. If you see either symptom, you are on an old tag.

## Reverse proxy and HTTPS (Nginx, Traefik, Caddy)

The golden rule: never expose raw port 8080 to the internet. Termix holds SSH credentials, so it sits behind HTTPS and ideally an additional access layer.

Termix is WebSocket-heavy (terminals, RDP, live stats), so the one reverse-proxy mistake to avoid is missing upgrade headers. Symptoms: the UI loads, then terminals disconnect or never connect.

<Tabs>
<Tab name="Nginx">

```nginx
server {
    listen 443 ssl;
    server_name termix.example.com;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 3600s;
    }
}
```

The `Upgrade`/`Connection` pair and `proxy_http_version 1.1` are the lines that make terminals work; `proxy_read_timeout` keeps long sessions from dying at the 60-second default.

</Tab>
<Tab name="Traefik">

```yaml
labels:
  - "traefik.enable=true"
  - "traefik.http.routers.termix.rule=Host(`termix.example.com`)"
  - "traefik.http.routers.termix.entrypoints=websecure"
  - "traefik.http.routers.termix.tls.certresolver=myresolver"
  - "traefik.http.services.termix.loadbalancer.server.port=8080"
```

Traefik handles WebSockets without extra config; just make sure the service port is 8080.

</Tab>
<Tab name="Caddy">

```text
termix.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

Caddy works out of the box, WebSockets included. This is my default when I am not already on Dokploy's Traefik.

</Tab>
</Tabs>

Two extras for special setups: sub-path deployments work with `VITE_BASE_PATH=/termix/` (1.11.1+), and 2.7.0 added trusted-proxy auth (`TRUSTED_PROXY_AUTH_*` env vars) if your proxy owns the login flow, for example behind Authelia or similar.

## Database options: SQLite, PostgreSQL, or MySQL

The default is SQLite in the `termix-data` volume, and for a solo operator that is the right answer: fewer moving parts, one file to back up.

PostgreSQL, MySQL, and MariaDB are supported since 2.7.0 for central backups or multi-instance setups:

```yaml
environment:
  DATABASE_DIALECT: "postgres"        # or mysql (MariaDB uses mysql + a mariadb:// URL)
  DATABASE_URL: "postgres://termix:password@db:5432/termix"
  # DATABASE_SSL: "require"           # for untrusted networks
```

<Notice type="warning" title="No automatic SQLite to Postgres migration">
Switching dialects does not carry your data over. You get an empty Termix. Use the Export/Import in Admin Settings first (hosts, credentials, snippets), or pgloader if you want the full database.
</Notice>

Keep the `termix-data` volume even on an external database. It still holds the encryption keys, SSL certificates, and session recordings, so the "just delete the volume" instinct after switching to Postgres will cost you your stored credentials.

Cost/ops note: an external DB is one more service to back up, patch, and connection-limit. Unless you have a concrete reason (shared cluster, centralized backups), SQLite plus volume backups is the boring, correct default.

## Termix security: updates, exposure, and telemetry

This section replaces the "it's self-hosted, so it's safe" hand-wave, because 2026 tested that assumption. Termix has published over 30 security advisories, several critical. An app that stores SSH credentials for all your servers deserves the same discipline as your VPN.

### Which version should you run?

<Notice type="error" title="Minimum safe version: 2.5.1">
The 2026 advisory wave included multiple criticals: file-manager and tunnel command-injection RCEs plus an IDOR that exposed other users' SSH passwords (fixed in 2.3.2), and critical tunnel/ACME handler injection bugs (fixed in 2.5.1). The same 2.5.1 release also fixed a hardcoded default encryption key, CVE-2026-79762, which allowed full offline decryption of stored SSH credentials for OIDC/WebAuthn users if the data directory leaked. Run 2.5.1 or newer; pin 2.8.0 today.
</Notice>

Three practical rules:

- **Pin the image tag** (`ghcr.io/lukegus/termix:2.8.0`), never `:latest` on an internet-facing credential vault. Updates become a deliberate `docker compose pull && docker compose up -d`, and on Dokploy that is covered by [how to update Docker Compose stacks in Dokploy](https://www.bitdoze.com/dokploy-update-docker-compose/).
- **Update faster if you run multi-user.** Much of the 2026 wave was cross-user (IDOR, credential theft). A single-admin box has a smaller blast radius; a team install does not.
- **Watch the advisories**, not just releases: the GitHub security tab is where criticals appear first.

Verify after updating: `docker compose ps` shows the pinned tag (or check the service in Dokploy), and the version in Admin Settings matches.

### Lock down access

- **Disable open registration.** Anyone who finds your URL should not be able to create an account.
- **If you use SSO, allow-list it.** `OIDC_ALLOWED_USERS` (and the admin-side allow-list setting) restricts which identities can get in. 2.7.0 added PKCE and trusted-proxy auth for stricter setups.
- **Enable the audit log** (Admin Settings, 2.4.0+). After your next login, check that entries appear; an audit log you never look at is decoration.
- **HTTPS always**, through the reverse proxy setup above. For an SSH-credential vault on a public IP, add IP allow-listing at the proxy or a VPN front door.
- **Firewall the host.** My baseline for a public Docker box is in [how I secured my Docker server with UFW](https://www.bitdoze.com/bsi-security-report-docker-ufw/), and [CrowdSec](https://www.bitdoze.com/crowdsec-secure-server/) adds brute-force protection worth having in front of any login page.
- **Be careful with session-share links.** 2.6.0 added sharing live terminal/RDP sessions via link with no account required. Convenient for pairing, risky by default. If you do not need it, disable it globally or per host.

### Telemetry and privacy

Since 2.6.0, Termix sends a daily ping to PostHog by default. Per the README it contains a random instance ID, user and host counts, version, and feature usage. No usernames, hostnames, or IPs. That is about as benign as telemetry gets. It is still your server making a daily call you did not ask for, so make the choice explicitly.

Opt out either way: **Admin Settings → General**, or set `ENABLE_TELEMETRY=false` in the environment, which locks the toggle off for the whole instance. My take: on a personal box the env var is the set-and-forget answer.

### Backups and recovery

What is in `termix-data` (the `/app/data` volume): the SQLite database, per-user encryption keys, generated SSL certs, and session recordings. Back it up like you would a database, not like a static site:

```bash
# find the exact volume name (compose prefixes it with the project name)
docker volume ls | grep termix

# tar it up
docker run --rm -v termix_termix-data:/data -v $(pwd):/backup alpine \
  tar czf /backup/termix-data-$(date +%F).tar.gz -C /data .
```

Ship the archive off-box (S3-compatible storage, restic, whatever you already use). The Export/Import in Admin Settings is a good supplement for hosts and credentials, but it is not a substitute for the volume backup.

<Notice type="warning" title="Test the restore">
Credentials in `/app/data` are encrypted per user (on patched versions; see the version note above). Restore into a fresh container at the same pinned version, log in, and open a host's credentials before you trust the backup. Do this once now, not during an outage.
</Notice>

## Troubleshooting common Termix issues

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `docker compose up` fails with "port is already allocated" | 8080 bound by another stack | Change the host side of the port mapping, or stop the other service |
| Terminals (and RDP) disconnect after ~60s behind a proxy | Missing WebSocket upgrade headers | Add `Upgrade`/`Connection` headers and raise `proxy_read_timeout` (Nginx tab above) |
| Remote desktop errors: guacd unreachable | guacd not on the same network, or name resolution failed | Put both containers on one compose network; set `GUACD_URL=tcp://guacd:4822` explicitly |
| Login or registration loop after a restore | Stale `termix-data` from an older version vs newer image | Check logs for migration errors; restore into the matching version, then upgrade |
| No CPU/memory stats for a host | Server stats not enabled per host | Enable **Server Stats** for that host in Host Manager |
| Container OOM-killed on a tiny VPS | Metrics polling + guacd on a 512 MB box | Size per the benchmarks: 1 GB base plus 1 GB with guacd |
| "Too many authentication failures" when connecting | SSH client offers too many keys | Fix the key offer on the client side; see the linked guide in the host manager section |

## FAQ

<Accordion label="Does Termix replace SSH keys?" group="faq" expanded="true">
No. Termix uses standard SSH authentication under the hood. You still manage keys and credentials the same way you do today; Termix just stores and deploys them for you, encrypted per user on patched versions (2.5.1+).
</Accordion>

<Accordion label="Where does Termix store its data?" group="faq">
All data lives under `/app/data` inside the container, which maps to the `termix-data` volume in both compose files above. That volume holds the database, encryption keys, SSL certs, and session recordings, even if you switch to an external database.
</Accordion>

<Accordion label="Can I expose Termix with HTTPS?" group="faq">
Yes, and you should. Put it behind Nginx, Traefik, or Caddy with WebSocket support, or use Dokploy's domain mapping. Never expose raw port 8080 on a public server; for an app holding your SSH credentials, add IP allow-listing or a VPN front door on top.
</Accordion>

<Accordion label="Is Termix a good free Termius alternative?" group="faq">
For self-hosters, yes, and that is the project's own positioning. You get the synced host library, snippets, and SFTP-style file management that paid Termius plans sell, but the sync server is your own and there is no subscription. What you give up is polish on mobile and someone else running the infrastructure.
</Accordion>

<Accordion label="Does Termix support remote desktop (RDP/VNC)?" group="faq">
Yes, since 2.0.0. It uses Apache Guacamole's guacd to render RDP, VNC, and Telnet sessions in the browser. You need the guacd sidecar container (or an existing guacd via `GUACD_URL`), and it is enabled per host in the Host Manager.
</Accordion>

<Accordion label="Does Termix phone home?" group="faq">
It sends opt-out telemetry by default since 2.6.0: a daily PostHog ping with a random instance ID, user/host counts, version, and feature usage. No usernames, hostnames, or IPs. Turn it off in Admin Settings, or set `ENABLE_TELEMETRY=false` to lock it off for the instance.
</Accordion>

<Accordion label="Can I use PostgreSQL with Termix?" group="faq">
Yes, since 2.7.0, via `DATABASE_DIALECT` and `DATABASE_URL` (MySQL and MariaDB too). Two gotchas: there is no automatic SQLite-to-Postgres migration, so export/import first, and keep the `termix-data` volume regardless because it holds encryption keys and certificates.
</Accordion>

<Accordion label="How much RAM does Termix need?" group="faq">
Very little. Official benchmarks show about 118 MB idle, and 1 GB total covers up to 100 hosts. Add roughly 1 GB if you use the guacd remote desktop sidecar. The smallest VPS tier you can buy is enough.
</Accordion>

<Accordion label="Do I need guacd?" group="faq">
Only for remote desktop. If you just want SSH terminals, tunnels, files, stats, and Docker, omit the guacd service and the network wiring. Termix detects it and simply hides the remote desktop features.
</Accordion>

<Accordion label="Is there a desktop or mobile app?" group="faq">
Yes, all shipped. The desktop app (Connector) runs on Windows, macOS, and Linux, standalone-first with optional server sync. Mobile apps are on Android 7.0+ (Play Store and APK) and iOS 15.1+ (App Store as "Termix SSH Companion").
</Accordion>

<Accordion label="Which version should I run?" group="faq">
At least 2.5.1, which fixed a wave of critical CVEs including a hardcoded encryption key. Today that means pinning `ghcr.io/lukegus/termix:2.8.0`. If you run multi-user with RBAC, treat updates as urgent rather than routine; much of the 2026 advisory wave was cross-user.
</Accordion>

## Final thoughts

Termix self-hosted has outgrown the "nice SSH web client" label. With remote desktop, fleet commands, and real container management in one Apache-2.0 package, it covers most of what a solo operator opens five tabs for, and the release cadence through 2026 shows a project that is very much alive. The trade-off is update discipline: run 2.5.1 or newer, pin the tag, and treat it with the respect you would give any credential vault.

If you are starting from a bare server, the [Dokploy install guide](https://www.bitdoze.com/dokploy-install/) gets you the deployment layer first, and the [self-hosted Tailscale with Headscale](https://www.bitdoze.com/headscale-self-hosted-tailscale-setup/) setup pairs perfectly with Termix 2.7.0's native Headscale support for reaching home labs.
