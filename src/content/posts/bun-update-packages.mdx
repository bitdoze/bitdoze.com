The fastest way to update packages to the latest version with Bun is `bun update`. Since Bun 1.2 it also rewrites `package.json` and `bun.lock` for you, which is the part most guides still get wrong. If you remember one thing from this post, make it this: check `git diff` after every update, because Bun will touch your manifest.

Bun is at 1.4.x now (the project moved from bun.sh to bun.com), and its package manager covers the whole update workflow without extra tools. You can update everything in range, pick packages interactively with `bun update -i`, jump majors with `bun update --latest`, or patch a single transitive dependency. These are the same Node.js packages npm manages. Bun just installs and updates them faster. If you still need a Node runtime alongside Bun, see how to [install Node.js with NVM on macOS and Ubuntu](/install-nodejs-using-nvm-macos-ubuntu/).

The workflow below is the one I use: upgrade Bun itself, check what is outdated, update, verify, and roll back if the build breaks. New to Bun? Start with the [Bun package manager guide vs NPM, Yarn, and PNPM](/bun-package-manager/). Moving an Astro site over? See [how to migrate Astro to Bun on Cloudflare Pages](/migrate-astro-bun/).

## Prerequisites and update workflow at a glance

Before touching packages, make sure you have the basics in place. This is a five-minute insurance policy that saves you an afternoon when a major bump breaks the build.

<ListCheck>
<ul>
<li>Bun installed and reasonably current (`bun --version`, target 1.4.x)</li>
<li>A project with `package.json` and a lockfile (`bun.lock`, or the old `bun.lockb`)</li>
<li>A clean git tree, or at least copies of `package.json` and `bun.lock`</li>
<li>Your test/build command known in advance (`bun run build`, `bun test`, whatever CI runs)</li>
</ul>
</ListCheck>

<Notice type="info" title="Commit first">
Every command below rewrites `package.json` and/or `bun.lock`. A clean git tree is your undo button: `git restore package.json bun.lock && bun install` gets you back in seconds. Without that, rollback is manual and miserable.
</Notice>

The full workflow, in order:

| You want to | Run |
|---|---|
| Get the newest Bun itself | `bun upgrade` |
| See what is outdated | `bun outdated` |
| Bump everything inside your declared ranges | `bun update` |
| Choose packages yourself | `bun update -i` |
| Cross major versions | `bun update --latest` |
| Update one package | `bun update zod` |
| Update globally installed tools | `bun update -g` |

Use that table as the roadmap. Everything below expands one row with verify steps and failure modes.

## Upgrade Bun to the latest version first

Outdated Bun, outdated behavior. The update flags and lockfile format have changed across 1.1, 1.2, 1.3, and 1.4, so run this first. How you upgrade depends on how Bun was installed:

<Tabs>
<Tab name="curl / install script">

```sh
bun upgrade
```

This is the default path from the official install script. It fetches the latest stable build and replaces the binary.

Want the bleeding edge or a pinned channel instead? `bun upgrade --canary` gets the development build, `bun upgrade --stable` moves you back to stable.

</Tab>
<Tab name="Homebrew">

```sh
brew upgrade bun
```

</Tab>
<Tab name="Scoop">

```sh
scoop update bun
```

</Tab>
</Tabs>

<Notice type="warning" title="Do not mix upgrade methods">
If Bun was installed with Homebrew or Scoop, do **not** run `bun upgrade` on top of it. The package manager owns the binary and will fight you: version drift, checksum errors, or a `bun` that reappears as the brew version on the next `brew upgrade`. Use `brew upgrade bun` / `scoop update bun` and stay consistent. See the [official installation docs](https://github.com/oven-sh/bun#installation) for the full matrix.
</Notice>

**Verify:** `bun --version` should print 1.4.x. If the number did not move, you upgraded a different install than the one on your PATH. Run `which bun` (or `where bun` on Windows) and compare it with where your package manager put its copy.

## Check outdated packages with `bun outdated`

Run this before every update session. `bun outdated` (since Bun 1.1.26) prints one table with three version columns:

- **Current** - what is in your lockfile right now
- **Update** - the highest version inside your declared range
- **Latest** - the newest published version, majors included

The difference between the last two columns tells you which command you actually need. If everything you care about is in the **Update** column, plain `bun update` is enough. If the versions you want sit in **Latest**, you are looking at a `--latest` run (or an interactive pick).

```sh
bun outdated
```

Output is shaped like this (versions will differ in your project):

```text
Package          Current   Update   Latest
ms               2.1.0     2.1.3    2.1.3
zod              3.22.4    3.25.0   4.1.12
typescript       5.4.5     5.9.2    5.9.2
```

Useful filters:

```sh
bun outdated '@types/*'      # glob: just the @types scope
bun outdated '!@types/*'     # negation: everything except @types
bun outdated -r              # every workspace in a monorepo
bun outdated --filter web    # one workspace
```

**Verify:** when everything is current, `bun outdated` prints just the header and exits 0. That is your "nothing to do" signal. Non-zero or a full table means there is work. Reference: [bun outdated docs](https://bun.com/docs/pm/cli/outdated), [v1.1.26 release notes](https://bun.com/blog/bun-v1.1.26).

<Notice type="info" title="Read the columns before you update">
The Update vs Latest split is the whole decision. In-range bumps are cheap and boring. Cross-major bumps are a branch, a CI run, and a changelog read. Do not let a single command decide for you.
</Notice>

## Update all packages with `bun update` (in-range)

Plain `bun update` (alias: `bun up`) bumps your direct and transitive dependencies **within** the ranges already declared in `package.json`. A `^2.1.0` dependency can land on 2.1.3 or 2.9.9, never on 3.0.0.

```sh
bun update
```

Preview first if you want a dry look at what would move:

```sh
bun update --dry-run
```

<Notice type="error" title="Correction (2026)">
Older versions of this guide said `bun update` leaves `package.json` alone. That has not been true since Bun ~1.2. A plain `bun update` rewrites the range floor for your direct dependencies and updates `bun.lock` to match. Trust `git diff`, not memory.
</Notice>

Concretely, this:

```json
"dependencies": {
  "ms": "^2.1.0"
}
```

becomes this after `bun update` picks up 2.1.3:

```json
"dependencies": {
  "ms": "^2.1.3"
}
```

The operator is preserved: `^` stays `^`, `~` stays `~`. Exact pins (`2.1.0`) and dist-tags (`latest`) are left as written. Transitive dependencies also move, and the lockfile records every change.

**Verify:**

```sh
git diff package.json bun.lock
```

You should see only the bumps you expected. If `package.json` shows a diff on a dependency you thought was pinned, that pin was probably a range after all.

**What "broken" looks like:** no output at all means nothing was out of range (or nothing is installed yet - run `bun install` first). A wall of churn in `bun.lock` with no `package.json` change is normal after registry metadata moves. The docs: [bun update](https://bun.com/docs/pm/cli/update).

## Update packages to the latest version with `bun update --latest`

This is the flag people actually want when they say "update everything to the newest". `--latest` (short: `-L`) ignores your declared ranges for **direct** dependencies, installs the newest published versions including majors, and rewrites `package.json` to match.

```sh
bun update --latest
```

Everything gets the cross-major treatment:

```sh
bun update --latest
# zod 3.22.4  ->  4.1.12   (major)
# typescript 5.4.5 -> 5.9.2 (same major, but outside your ^5.4 range floor rewrite)
```

How the rewrite works: your `"zod": "^3.22.4"` becomes `"zod": "^4.1.12"` - same style of range, new floor. Transitive dependencies still respect their dependents' ranges, and Bun never downgrades a dependency that is already ahead of `latest` (prerelease installs). Available since Bun 1.2 ([release notes](https://bun.com/blog/bun-v1.2)).

### `--force` vs `--latest`: why `--force` does not update to latest

<Notice type="warning" title="--force is not --latest">
`bun update --force` means "always request the latest versions from the registry and reinstall all dependencies". It is a cache and metadata refresh. It does **not** bypass your semver ranges. If `bun update --force` seems to "not update" packages, you wanted `bun update --latest`.
</Notice>

The two commands side by side:

```sh
bun update --force    # refresh registry metadata, reinstall what your ranges allow
bun update --latest   # cross majors, rewrite package.json to the newest versions
```

### Update only production or dev dependencies

```sh
bun update --prod       # or -P: dependencies only
bun update --dev        # or -D: devDependencies only
bun update --no-optional
```

Combine freely: `bun update --dev --latest` is the usual "take dev tooling to the majors, leave runtime deps alone" move.

### Glob patterns and exclusions

```sh
bun update '@types/*' --latest     # all @types packages to their latest
bun update '!@babel/core' --latest # everything except @babel/core
bun update jquery@3                # move jquery within the 3.x line
```

**Ops note:** majors break builds. Treat `--latest` as a branch-plus-CI event, not a Friday 17:00 command. After the majors land and CI is green, redeploy and smoke-test in production. For Astro sites, see [how to deploy an Astro blog on Cloudflare](/deploy-astrojs-cloudflare/).

## Pick packages interactively with `bun update -i`

Since Bun 1.3, the interactive picker is built in. This replaces the `bunx npm-check-updates -ui` workaround this guide used to recommend.

```sh
bun update -i
```

You get a list of outdated direct dependencies grouped by dependencies, devDependencies, peer, and optional, with Current, Target, and Latest columns. Target is the in-range bump, Latest is the newest published. Color coding: red for major, yellow for minor, green for patch.

Keys worth knowing:

| Key | Action |
|---|---|
| `Space` | Toggle the highlighted package |
| `a` | Toggle all |
| `n` | Select none |
| `i` | Invert selection |
| `l` | Flip the highlighted row between target and latest |
| `Enter` | Apply |
| `Ctrl+C` | Cancel without changes |

The `l` key is the one people miss. It lets you take most packages in-range and push a single risky one all the way to latest, in one pass. ([Bun 1.3 release notes](https://bun.com/blog/bun-v1.3).)

<Notice type="warning" title="1.4 behavior change: -i needs a real terminal">
Since Bun 1.4.0, `bun update -i` with a non-TTY stdin exits with code 1 instead of opening the picker. That means it will not work in CI scripts or piped input. Run it interactively, or use `bun update --latest` / targeted `bun update pkg` in automation. ([Bun 1.4 release notes](https://bun.com/blog/bun-v1.4).)
</Notice>

<Notice type="info" title="You no longer need npm-check-updates">
`bun update -i` and `bun update --latest` cover the old ncu workflow natively. If you want staged upgrades instead - for example, only minors for a while - ncu still does that well:

```sh
bunx npm-check-updates -t minor -u
```

That updates `package.json` to the newest minor versions only. See [npm-check-updates](https://www.npmjs.com/package/npm-check-updates) if you need it.
</Notice>

**Verify:** same as always, `git diff package.json bun.lock`, then your build.

## Targeted updates: single packages, globs, and transitive deps

You rarely need "all or nothing". Named updates handle the surgical cases:

```sh
bun update zod           # zod everywhere it appears, including transitively
bun update caniuse-lite  # patch a nested/transitive dep
bun update '@types/*'    # glob
```

Two details that changed in Bun 1.4 and matter in real projects ([release notes](https://bun.com/blog/bun-v1.4)):

1. `bun update pkg` now updates that package **everywhere it appears**, including transitive occurrences, not just the top-level entry. That is what you want for a security fix buried three levels deep.
2. Catalog dependencies (`catalog:` in workspaces) get rewritten too.

A targeted update of a package that is not in your `package.json` - the `caniuse-lite` case - fixes the lockfile without adding a dependency to your manifest. That is the right tool for "my transitive dep has an advisory and I cannot wait for the parent to bump".

### Monorepos: `--recursive` and `--filter`

```sh
bun outdated -r                  # all workspaces
bun update -r                    # update every workspace
bun update --filter web          # just the web workspace
bun update -r --latest           # cross majors everywhere (careful)
```

After a big multi-workspace pass, clean up:

```sh
bun dedupe     # collapse duplicate versions in the lockfile
bun prune      # drop packages not in package.json (new in 1.4)
```

<ListCheck>
<ul>
<li>One dependency needs a fix → `bun update pkg`</li>
<li>Everything should move within ranges → `bun update`</li>
<li>You want majors → `bun update --latest`</li>
<li>You want to choose, row by row → `bun update -i`</li>
<li>CI or a script → targeted commands or `--latest`, never `-i`</li>
</ul>
</ListCheck>

## Update global packages with `bun update -g`

Global tools are a separate story from project dependencies. Nothing here touches any project's `package.json`.

<Tabs>
<Tab name="All globals">

```sh
bun update -g
```

</Tab>
<Tab name="One global">

```sh
bun update -g typescript
```

</Tab>
<Tab name="Pin to latest">

```sh
bun add -g typescript@latest
```

</Tab>
</Tabs>

Globals live in `~/.bun/install/global`. A fresh `bun add -g pkg` is sometimes cleaner than an update when a tool changed its bin layout between majors.

**Failure modes:** "command not found" after a global update usually means the shim directory is missing from your PATH (`~/.bun/bin`). And remember the project wins: if a project has a local install of the same tool, `bun run` uses the local one even when a newer global exists.

## How `bun update` rewrites package.json and bun.lock

This is the section for the "bun update package.json" search. The mechanics are simple once you have seen them once:

- **In-range update** bumps the range floor and preserves the operator. `^1.1.0` becomes `^1.2.0`, `~1.1.0` becomes `~1.1.5`. Nothing crosses a major.
- **`--latest`** rewrites across majors to a same-style range: `^1.1.0` becomes `^2.0.0` if 2.0.0 is newest.
- **Exact pins and dist-tags** stay as written unless you pass `--latest`.
- **`--no-save`** updates `node_modules` only. `package.json` and the lockfile stay put. Useful for a quick local experiment you plan to revert.

On the lockfile side: text-based `bun.lock` replaced the binary `bun.lockb` in Bun 1.2, and Bun auto-migrates the old format. Since 1.3 it also migrates `yarn.lock` and `pnpm-lock.yaml` on install, so moving a project to Bun does not mean hand-writing a lockfile.

Before and after, the whole change can look like this:

```diff
-    "ms": "^2.1.0"
+    "ms": "^2.1.3"
```

<Notice type="info" title="Diff, do not dump">
`git diff package.json` is the honest way to see what changed. Pasting a whole `package.json` into a chat window to figure out what moved is how people lose track of pins.
</Notice>

If you need staged upgrades - take the minors now, the majors next sprint - that is the one remaining use case for [npm-check-updates](https://www.npmjs.com/package/npm-check-updates):

```sh
bunx npm-check-updates -t minor -u
```

## Security-driven updates: `bun audit` and `bun audit fix`

Dependency updates are not only about features. `bun audit` lists known advisories against your tree:

```sh
bun audit
```

Since Bun 1.4.0, you can act on the report directly ([release notes](https://bun.com/blog/bun-v1.4)):

```sh
bun audit fix --dry-run   # preview first
bun audit fix             # upgrade vulnerable packages to safe versions
bun audit fix --latest    # allow major jumps when the fix requires one
```

That removes the old "audit, open the advisory, hand-edit ranges" loop for most cases.

Two hardening notes worth acting on:

1. **Hold back brand-new packages.** Bun supports a minimum release age, so a hijacked or freshly published malicious version never gets installed on day zero:

```ini
# bunfig.toml
[install]
minimumReleaseAge = 604800   # 7 days, in seconds
```

The CLI equivalent is `--minimum-release-age`. ([Bun 1.3 notes](https://bun.com/blog/bun-v1.3).)

2. **Patched packages are held back by `bun update`.** If you used `bun patch` and have `patchedDependencies`, a normal update will not move that package - it would silently drop your patch. `--latest` and `bun audit fix` will move it, which means you need to re-create the patch afterwards.

<Notice type="warning" title="Re-patch after moving a patched dependency">
`bun update --latest` or `bun audit fix` bumps a patched package: your patch no longer applies, and `patchedDependencies` will fail on the next install until you redo `bun patch` against the new version. Budget five minutes per patched package.
</Notice>

**Ops cadence:** none of this costs money. The tooling is Bun plus the public npm registry. What pays off is habit: a weekly `bun outdated -r && bun update`, or Dependabot/Renovate on the repo with `bun.lock` in the commit. Small, frequent updates are a one-coffee job. Annual updates are an incident.

## Verify the update and roll back if needed

An update that you have not verified is just a modified lockfile. Four steps, every time:

<ListCheck>
<ul>
<li>`git diff package.json bun.lock` - eyeball what actually moved</li>
<li>`bun install --frozen-lockfile` - proves the lockfile is complete and reproducible (the same check CI should run)</li>
<li>`bun run build` and `bun test` if you have tests</li>
<li>Smoke-test the app: dev server or preview, click through the critical path</li>
</ul>
</ListCheck>

If your build time matters to you - and after a dependency bump you will be running builds more than usual - check [our Astro 7 build benchmark](/astro-7-faster-builds/). Once the build is green again, [Astro build speed optimization](/astro-ssg-build-optimization/) is the follow-up that pays off on every subsequent update cycle.

### Rollback

Because you committed first:

```sh
git restore package.json bun.lock
bun install
```

If you are mid-branch and want to revert a single dependency instead of the whole pass:

```sh
bun update zod@3.22.4     # pin back to the old version
```

No git? Keep copies of `package.json` and `bun.lock` before you start. That is the entire backup strategy; there is no hidden state elsewhere.

<Notice type="error" title="Common failure modes after a big update">
1. **Build breaks on a major.** Revert the one dependency (`bun update pkg@1.2.3`) or pin it and schedule the migration. Do not pile a second `--latest` run on top of a red build.
2. **CI fails on lockfile mismatch.** `package.json` and `bun.lock` must be committed together. A CI `bun install --frozen-lockfile` will refuse a lockfile that does not match the manifest.
3. **Build dies with OOM on a small VPS.** Not a dependency bug: add swap, build elsewhere, or lower parallelism. 1-2 GB boxes run out of heap during Astro/Next builds after heavy devDependency updates.
4. **`patchedDependencies` errors after the update.** Re-run `bun patch` against the new version of the package, or drop the patch if upstream fixed it.
</Notice>

**Cost/ops note:** the updates are free. Broken deploys are not. Run this on a branch, let CI build it, then merge. Ten minutes of pipeline beats a rollback in production.

## FAQ: updating packages with Bun

<Accordion label="Does bun update change package.json?" group="faq" expanded="true">
Yes. A plain `bun update` rewrites the version ranges of your direct dependencies within their declared bounds (`^2.1.0` becomes `^2.1.3`) and updates `bun.lock`. `bun update --latest` goes further and rewrites ranges across majors. Only `--no-save` leaves both files untouched.

```sh
git diff package.json bun.lock   # always check after updating
```
</Accordion>

<Accordion label="What is the difference between bun update and bun update --latest?" group="faq">
`bun update` stays inside the ranges already in `package.json`: no majors, just the newest versions your manifest allows. `bun update --latest` (or `-L`) ignores those ranges for direct dependencies, installs the newest published versions including majors, and rewrites `package.json` to match.

```sh
bun update           # in-range
bun update --latest  # cross-major
```
</Accordion>

<Accordion label="How do I update Bun itself?" group="faq">
Run `bun upgrade` if you installed Bun with the official script, `brew upgrade bun` on Homebrew, or `scoop update bun` on Scoop. Then confirm with `bun --version` - it should show 1.4.x.

```sh
bun upgrade && bun --version
```
</Accordion>

<Accordion label="How do I update global packages with Bun?" group="faq">
`bun update -g` updates every global package, `bun update -g pkg` updates one, and `bun add -g pkg@latest` pins a global install to the newest version. Globals live in `~/.bun/install/global` and no project's `package.json` is affected.

```sh
bun update -g
```
</Accordion>

<Accordion label="Is bun update --force the same as updating to the latest version?" group="faq">
No. `--force` means "always request the latest versions from the registry and reinstall all dependencies". It refreshes cached metadata and reinstalls what your ranges already allow. To cross major versions and get the newest published packages, use `bun update --latest`.

```sh
bun update --latest   # the one you wanted
```
</Accordion>

## Conclusions

The 2026 workflow is short: `bun upgrade`, `bun outdated`, then `bun update` / `bun update -i` / `bun update --latest` depending on how much churn you want. Verify with `git diff` and `bun install --frozen-lockfile`, and roll back with `git restore package.json bun.lock && bun install` when the build complains.

Two corrections to older advice are worth keeping: `bun update` **does** rewrite `package.json`, and `--force` is **not** the "give me the latest versions" flag - `--latest` is. With those straight, Bun's built-in tools cover the whole update job without npm-check-updates or any other wrapper.
